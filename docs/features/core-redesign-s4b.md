# core の見直し 区切り S4b — スーパーバイザーのその場の対処

## 概要

`docs/features/core-redesign.md` の区切り S4b の仕様。S4a（長く走るサイクル）の実装の間に書くので、その間だけ別の文書に書き、main に入れた後に `core-redesign.md` へ畳む（S3d・S4d と同じ進め方。オーナーの決定 2026-11-22）。

S4b は、設計書 §21.5 のスーパーバイザーの出番のうち「その場の対処」を入れる。サイクルの途中でタスクが想定外に止まったとき、いまは保留にしてオーナーへ上げる。S4b からは、スーパーバイザー（読み取りの道具だけを持つ判断点）が先に調べ、core が用意した手の一覧から 1 つ選ぶ。選んだ手を実行するのは core。委譲先からの問い（子の問い）も、スーパーバイザーが受ける（子の問いに答える判断点〔J4〕を、スーパーバイザーにまとめる。設計書 §21.6）。

サイクルの終わりの振り返り（出番 2）は S5。

あわせて、保留に「選択肢つきの問い」の土台を足す（問いの文に加えて選択肢の並びを持ち、選択肢の識別で答えられる）。使うのは、S4b では、委譲先が選択肢を付けて返した問い（S4b-1）と、スーパーバイザーがオーナーへ上げるとき（S4b-2）。後の区切り（S4c-1 の「上限を超えて足すときの問い」、S4d-2 の画面のボタンでの「選ぶだけの回答」）が、この土台を使う（オーナーの決定 2026-11-22）。

S4b は大きいので、3 つのスライスに分けて、1 回ごとに実装して確かめ、main へ入れる（オーナーの決定 2026-11-22）。S4b-1＝選択肢で答える仕組み（選択肢つきの問いの土台）、S4b-2＝想定外の止まりへの対処（スーパーバイザーの段と手）、S4b-3＝委譲先の問いに答える（子の問い）。この文書は 3 つを通して書き、どのスライスかを、節の見出しと項目の頭の印で示す（下の「スライス」）。

区切りの順は、S4a → S4b-1 → S4b-2 → S4b-3 → S4c-1（上限とタスクを足す）→ S4c-2（フォローアップを上げる）→ S4c-3（止まっている課題のほかのタスクを進める）→ S4d-2（画面の残り）（オーナーの決定 2026-11-22）。

> **「最初の Issue で確かめる」の印**: 仕様を書くときに実物のコードで確かめ切れなかった点。最初の実装の Issue で確かめ、食い違えば、仕様を変えずに PR の説明へ「仕様への指摘」として書く。

## 背景・目的

- 測った期間に、サイクルの途中でオーナーへ上がった問い 117 件のうち、スーパーバイザーが引き受けられるものが約 45 件あった（委譲先の失敗・中止 18、自己レビューが不明 15、成果物の中身を読めない 9、成果物が見つからない 3。設計書 §21.5）。いまは、想定外のことが起きると「同じことをやり直す」か「オーナーへ上げる」しか無い。
- 子の問いに答える判断点（J4）は、実行の記録が 0 回だった（設計書 §21.6）。オーナーへの問い（保留）は 470 件で、回答待ちは、委譲で完了した課題の時間の 40% だった（設計書 §21.0）。
- S4a で、サイクルは、進められるものが無くなるまで回りを繰り返す。保留がオーナーへ上がると、その課題はオーナーの回答まで止まる。スーパーバイザーが先に受ければ、同じサイクルの中で続きを進められる。

## ユーザーストーリー

オーナーとして、委譲先の一時的な失敗や、調べれば分かる食い違いのたびに呼ばれたくない。自分に上がってくる問いには、何が起きたか・何を調べたか・どうするのがよいかが、付いていてほしい。スーパーバイザーが自分の代わりに決めたことは、後から全部見たい。

## 機能要件

語は `docs/glossary.md` に合わせる。節の見出しの括弧が、その節のスライス。節のスライスと違う項目は、項目の頭に **（S4b-n）** の印を付ける。この文書では、次の語を使う。

- **止まり方**: スーパーバイザーを呼ぶきっかけの種類。下の「対象の止まり方」の閉じた一覧。
- **対処**: スーパーバイザーの判断 1 回と、core がその手を実行した結果。1 件ずつ記録する（対処の記録）。
- **スーパーバイザー待ちの保留**: core が作った保留のうち、オーナーより先にスーパーバイザーが見るもの。
- **オーナーへ上げる**: 保留を、オーナーの回答を待つ保留にする（スーパーバイザー待ちだった保留は、`supervisor_state` を `escalated` にする）。
- **最後のオーナーの回答**: その課題の、回答した者が `supervisor` でない回答済みの保留の、最大の回答時刻。回数の数えは、これより後の対処の記録だけを数える。

### スーパーバイザーを呼ぶとき（S4b-2）

- [ ] サイクルの進める段の最後に、スーパーバイザーの段（`supervise`）を足す。回りごとに 1 回通る（S4a の回りの中。完了の検証の段の後）。
- [ ] 止まり方（`stop_kind`）は、保留の理由から導かず、保留を作る呼び出し元が渡す。
- [ ] **（S4b-1・S4b-2）** 保留を作る入口を 1 つにする（入口と、選択肢の並び・「識別の無い回答を断る」印を受ける所は S4b-1 で足し、止まり方・回数の上限・スーパーバイザー待ちの印・問いの先頭の行は S4b-2 で足す）: 止まり方・選択肢の並び・「識別の無い回答を断る」印（下の「選択肢つきの問い」）・種類・直前の状態・タスクを受ける新しい入口を 1 つ足し、いまある作る関数（`insertHold`・`insertHoldID`・`insertHoldKind`・`insertHoldKindFrom`・`insertHoldKindFromTask`）は、そこへ委ねる。新しい入口が、下の「回数の上限」の判定と、スーパーバイザー待ちの印と、問いの先頭の行の付け足しを、1 か所で行う。回数の数えと問いの文の確定は、保留の行を作るのと同じ書き込みの中で、行を作る前に行う。
- [ ] 計画の承認待ちの課題に作れる保留は、いまと同じく、対話のセッションが引き取る保留（`parent_direct`）だけ（いまの検査は、新しい入口に残す。止まり方を渡す呼び出し元は、計画の承認待ちからは保留を作らない）。
- [ ] core が、サイクルの中で、対象の止まり方を渡して保留を作るとき、その保留を「スーパーバイザー待ち」にする（保留の行の `supervisor_state` を `pending` にする。課題の状態の遷移は、いまの保留と同じ）。
- [ ] 対象の止まり方（閉じた一覧）と、止まり方を渡す呼び出し元は、次のとおり。「いまの保留の理由」は参考の列（理由の値は、止まり方の判定に使わない。保留の行に理由を書かない理由もある）。

| 止まり方 | 起きること | 止まり方を渡す呼び出し元 | いまの保留の理由（参考） |
|---|---|---|---|
| `verify_uncertain` | 完了の検証・タスクの検証が「判断できない」を返した | 完了の検証の「判断できない」の保留（`judgment_j5.go`）、タスクの検証の「判断できない」の保留（`judgment_j5_task.go`） | なし |
| `artifact_missing` | 成果物が見つからない | 委譲の報告の照合で、成果物が見つからない保留（`delegate_reconcile.go`・`delegate_reconcile_retry.go`） | `artifact_missing` |
| `delegate_stopped` | 委譲先の実行が失敗・中止で終わった、委譲の連続の失敗が上限に達した | 契約の実行の終わり・回収の保留（`holdContractWithReason` に `contract_stopped` を渡す所）、委譲の連続失敗の保留（`holdForFailureLimit`） | `contract_stopped`・`failure_limit` |
| `facts_unmet` | 委譲先が返す値が、宣言の求める値を満たさないレビュー待ちが 2 回続いた | レビュー待ちの受け取り（`contract_review_intake.go`） | `facts_unmet` |
| `rework_limit` | 差し戻しが上限に達した。タスクの検証の連続の「満たしていない」が上限に達した（下の「S3b で残した点」） | 委譲の差し戻しの上限の保留（`holdForReworkLimit`・レビュー待ちへの返しの上限）、タスクの検証の連続の上限の保留（新設） | `rework_limit` |
| `checks_failed` | 検証した中身の確かめに失敗がある | 統合先へ入れる処理（`integration_land.go`） | `checks_failed` |
| `judgment_failed` | 判断点（分類・計画・完了の検証）の失敗・不正な出力が、連続の上限に達した | 判断点の連続失敗の保留（`holdForJudgmentFailureLimit`） | `failure_limit` |
| `intake_unverified` | 統合先を使う課題で、タスクの成果を受け取れない（成果物が統合先へ入らないまま実行が終わった・検証を経ずに入っていた・統合先の識別が合わない） | 統合先のタスクの受け取り（`contract_delegate_after.go`・`contract_review_intake.go` の、理由 `delegate_ended`・`merged_unverified`・`integration_ref_invalid` を渡す所） | `delegate_ended`・`merged_unverified`・`integration_ref_invalid` |
| `upstream_unreadable` | 「入れてよい」を返した後、上流を読めない回りが 3 回続いた（下の「S3b で残した点」） | 新設 | （新設） |
| `child_question`（S4b-3 で足す） | 委譲先からの問い（下の「子の問い」。答えたときは保留を作らない。上げるときだけ、この止まり方の保留を作る） | 委譲の報告の問い（`delegate_reconcile.go`）、契約の判断待ち（`contract_delegate_after.go`） | `questions`・`contract_stopped` |

- [ ] 止まり方を渡さない保留は、対象にしない（はじめからオーナーへ上がる。`supervisor_state` は NULL）。対象にしない保留を作る呼び出し元は、次のとおり。
  - 分類の判断点・計画の判断点が作る保留（`judgment_j1.go`・`judgment_j2.go` の問い。計画の判断点が立てる、対話のセッションが引き取る保留〔`parent_direct`〕を含む）
  - 完了の検証が、実物の食い違いで作る保留、人の操作の後でしか満たせない条件・反映が無くて満たせない条件で作る保留（`judgment_j5.go`）
  - 課題の単位の確かめが「満たしていない」だった保留（`challenge_check_not_met`）
  - 予算の上限を超えた保留（オーナーの決定 2026-11-22。下の「やらないこと」）
  - 承認していない反映の検知（`unapproved_merge`）
  - 反映・上げる依頼に関わる保留（`land_unavailable`・`content_ref_invalid`・`land_refused`・`reflect_unavailable`・`reflect_failed`。「入れてよい」の後に実行が終わった・止まった保留〔`integration_land.go` の `holdLandedEnd`〕を含む）
  - 前提のタスクの取りやめで進めようが無い保留（`tasks_blocked`）
  - 委譲先が「進められない」と返した保留（`blocked`）
  - 契約の判断待ちのうち、承認の待ち（`approve`）、ターミナルで人が解く待ち（`resolvable_by` が `terminal`）、成果物の無いレビューの待ち
  - オーナーが自分で作った保留（`flywheel hold`）、差し戻しのときに立つ、対話のセッションが引き取る保留（`parent_direct`）
  - （2026-11-22 のオーナーの決定で、この一覧から外した）保留の間に成功した、統合先を使う課題の実行の保留（`holdIntegrationSucceeded`。理由 `delegate_ended`・`merged_unverified`）は、止まり方 `intake_unverified` の対象で、スーパーバイザー待ちになる。
- [ ] 最初の Issue で、サイクルの中で保留を作る所（`insertHold`・`insertHoldKind`・`insertHoldWithOccurrence` の系の呼び出し元）を全部一覧にし、上の 2 つの一覧のどちらにも無い呼び出し元は、対象にしない側に置く（止まり方を渡さない）。

#### 回数の上限

- [ ] 同じタスク（タスクの無い保留は、同じ課題）の、同じ止まり方への対処は、2 回まで。数えるのは、その課題の、最後のオーナーの回答より後の、手が `defer`・`escalate`・`answer` でなく、結果が `executed` の対処の記録。
- [ ] 上の数えが 2 件ある止まり方の、次の保留は、スーパーバイザー待ちにしない（`supervisor_state` は NULL。`stop_kind` は記録する）。問いの先頭に、固定の形の 1 行「スーパーバイザーが 2 回対処したが、進まなかった（手: <1 回目の `hand`>、<2 回目の `hand`>）。」を付けて、オーナーへ上げる（手の名前は、実行の順）。
- [ ] **（S4b-3）** 子の問い（`child_question`）は、2 回の上限の対象にしない（別々の問いは「同じ止まり方」ではないため）。子の問いは、下の「答えによる再開は 3 回まで」だけで止める。
- [ ] 2 回の上限は、どの止まり方にも同じに当てる（`verify_uncertain` の `reverify` に限らない）。

#### スーパーバイザーの段

- [ ] スーパーバイザーの段は、スーパーバイザー待ちの保留を、古い順に 1 件ずつ処理する。1 件ごとに、スーパーバイザーの判断点を 1 回呼ぶ。
- [ ] オーナーは、スーパーバイザー待ちの保留にも、いまと同じ操作（`flywheel answer`）で回答できる。回答済みの保留を、スーパーバイザーの段は処理しない。
- [ ] 宣言（`agent.json`）の `supervisor`（真偽。既定は真）が偽のとき、保留をスーパーバイザー待ちにしない（S4a までと同じ動き。子の問いは、下の「子の問い」の「偽のとき」）。切る設定を置くのは、オーナーの決定（2026-11-22）。
- [ ] 宣言の `supervisor` が偽の間は、スーパーバイザー待ち（`supervisor_state` が `pending`）のまま残っている保留を、ふつうのオーナーの回答待ちとして扱う（一覧に出て、答えられる。「サイクルを回すと進むもの」に数えず、「スーパーバイザーが確認中」と表示しない）。保留の行は書き換えず（`supervisor_state` は `pending` のまま。マイグレーションは足さない）、読むときに決める。宣言を真に戻せば、まだ答えていない保留は、また確認中に出て、数えられ、スーパーバイザーの段が処理する。「宣言を見て、スーパーバイザー待ちとして扱うか」の決めは 1 か所（`supervisorEnabled`）にまとめる（オーナーの決定 2026-11-22）。
- [ ] 段の差し込み位置（回りの中の、完了の検証の段の後）は、S4a が main に入った後で、実物の段の一覧に合わせて確かめ直す。

### スーパーバイザーの判断点（S4b-2）

- [ ] スーパーバイザーの判断点（記録上の名前は `SV`）は、ほかの判断点と同じ呼び出し（`internal/invoker`。読み取りの道具〔`Read`・`Grep`・`Glob`〕だけ。作業ディレクトリはワークスペース）で呼ぶ。コマンドを実行する道具を持たない。
- [ ] 入力に渡すもの: 止まり方、保留の問い、課題とタスクの題名、タスクの完了条件（1 から始まる番号つき。保留がタスクを指すときだけ）、回せる条件（下の「条件をフォローアップへ回せる範囲」。1 から始まる番号つき。あるときだけ）、計画の方針、そのタスクの実行の記録（状態・要約・委譲先が返した値・成果物の識別。直近 5 件）、そのタスクへのこれまでの対処の記録、選べる手の一覧、記憶の索引の場所。保留がタスクを指さないときは、タスクの題名・タスクの完了条件・実行の記録の代わりに、課題の完了条件と、課題のタスクの一覧（題名と状態）を渡す。
- [ ] 判断点の入力の「保留の記録」の区画（`formatHoldsSection`。いまは問いと回答だけを出す）は、回答した者がスーパーバイザーの回答に「回答者: スーパーバイザー（オーナーの回答ではない）」の行を付ける（完了の検証・計画・分類・委譲の判断点が、スーパーバイザーの添え書きを、オーナーが範囲を変えた回答と読み違えないため）。
- [ ] 選べる手の一覧は、下の「止まり方ごとに選べる手」の表から、いまの状態では実行できない手を core が外したもの（下の「事前に外す手」）。
- [ ] 出力（型つき）: `hand`（選べる手の 1 つ）、`findings`（調べたこと。必須）、`note`（手に添える文。手ごとの必須は下）、`basis`（根拠の場所の配列。要素は `path` と `locator`〔節や行の手がかり〕）、`recommendation`（オーナーへ上げるときの推奨。`escalate` のとき必須）、`options`（オーナーへ上げるときに付ける選択肢の配列。`escalate` のときだけ。無くてもよい。下の「選択肢つきの問い」）、`conditions`（フォローアップへ回す条件の番号の配列。番号は、入力の「回せる条件」の番号。`split_followup` のとき 1 件以上）、`answers`（子の問いへの答えの配列。`answer` のとき、問いの数と同じ件数）。
- [ ] 費用の上限は、宣言の `judgment_budget_usd.SV`（既定 5 USD。オーナーの決定 2026-11-22）。時間の上限は、ほかの判断点と同じ（`timeout_sec.judgment`）。
- [ ] スーパーバイザーの判断点の費用は、判断点の費用として、課題の費用に入る。
- [ ] スーパーバイザーの判断点の費用は、サイクルの費用に入る。
- [ ] 指示文 `sv.md` を足す。書くこと: できないこと（承認・反映・取り下げ・予算の増額・範囲の変更・成果物の手直し）、手の選び方、根拠を示せないときは上げること、調べる範囲（ワークスペースの中の文書・記憶・コード。成果物の中身は、入力に渡した識別と要約まで）、子の問いの歯止め（下の「子の問い」）。開発に固有の語を書かない（禁止語の照合を通す）。

### 手の一覧（S4b-2）

- [ ] 手は、次の 8 つ（閉じた一覧）。設計書 §21.5 の手 4（委譲先に片付けを頼んで、起動し直す）は、入れない（オーナーの決定 2026-11-22。下の「やらないこと」）。

| `hand` | 手 | core がすること | 必須の出力 |
|---|---|---|---|
| `reverify` | 調べた結果を添えて、検証（受け取り）をやり直す | 保留を閉じ、保留の直前の状態へ戻す。保留の回答の文に、`findings` と `note` を「スーパーバイザーが調べた結果」として書く | `note` |

- [ ] `answer` の出力の `answers` は、問いごとに、選んだ選択肢（選択肢がある問い）か回答の文（無い問い）と、`basis`（1 件以上）を持つ。
- [ ] 根拠の検査: core は、`basis` の各 `path` について、リンクを解決した後の場所が、ワークスペースの根の下の通常のファイルであることを確かめる。ワークスペースの外・ディレクトリ・ストアの置き場（`.flywheel/`）の下・存在しない場所は、根拠として数えない。根拠として数えられる `basis` が 1 件も無い問いがあれば、出力の不備（`failed`）として、その報告の問い全部を、オーナーへ上げる。

- [ ] 宣言の `supervisor` が偽のとき、子の問いは、すべて保留にして、オーナーへ上げる（J4 は戻さない。J4 の新しい呼び出しは、宣言の値によらず外す）。

### オーナーへ上げるとき（S4b-2）

- [ ] スーパーバイザー待ち（`supervisor_state` が `pending`）の保留だけを持つ課題は、オーナー待ちに数えない（オーナーの決定 2026-11-22）。数えないのは `pending` だけで、印が無い（NULL）保留・上げた（`escalated`）保留を持つ課題は、オーナー待ちに数える。
- [ ] `flywheel status` は、「スーパーバイザーが確認中」として、件数と課題を、オーナー待ちと別に出す。
- [ ] 状況の API の値も、スーパーバイザーが確認中の課題を、オーナー待ちと別に持つ。
- [ ] スーパーバイザー待ちの保留にも、オーナーは、いまの保留と同じ操作で回答できる（割り込み）。回答した保留は、スーパーバイザーの段で処理しない。
- [ ] スーパーバイザーが `escalate` の出力に付けた選択肢（`options`）は、上げた保留の選択肢になる（S4b-1 の土台を使う）（下の「選択肢つきの問い」）。
- [ ] サイクルが走っていない間に残っているスーパーバイザー待ちの保留（見送り・起動できなかったもの）は、S4a の「いま始められるもの」に数える（次のサイクルで処理できる）。
- [ ] 見送った保留は、見送ったサイクル（`deferred_cycle_id`）が、いまのサイクルと同じ間、処理しない。そのサイクルの回りの終わりの数えにも入れない（見送りだけで回りを続けない）。

- [ ] 見送り（`defer`）が、同じ保留に 3 サイクル続いたら（`deferred_count` が 3）、次のサイクルでは、スーパーバイザーを呼ばず、オーナーへ上げる。連続の数えは、見送ったサイクルごとに 1 増える（サイクルが走らない間は、進まない）。

### 選択肢つきの問い（S4b-1）

保留が、問いの文に加えて、選択肢の並びを持てるようにする。S4b-1 は土台（持つ・答える・記録する・見せる）だけを入れる。S4b-1 の時点では、スーパーバイザーの判断点は無いので、スーパーバイザーが付ける選択肢に関わる項目（**（S4b-2）** の印）は、S4b-2 で入れる。選択肢ごとに別の動きを起こすのは、使う側の区切り（S4c-1）が決める。画面のボタンは S4d-2。

- [ ] 保留は、選択肢の並び（0 件以上）を持てる。件数の決まり（2 件以上 6 件以下）は、スーパーバイザーが付ける選択肢だけに当てる（委譲先が返した選択肢は、件数によらず、そのまま持つ）。選択肢 1 つは、識別（`id`。その保留の中で重ならない、英小文字・数字・`_`・`-` の 1〜32 文字）・見出し（`label`。必須。1 行）・説明（`description`。無くてもよい）を持つ。
- [ ] 保留を作る入口は、選択肢の並びを受ける。作り手は、意味のある識別を渡せる（後の区切りが、選ばれた識別で動きを分ける）。識別を渡さない作り手の選択肢には、core が、並びの順に `o1`・`o2`…を振る。
- [ ] 識別の形に合わない・同じ保留の中で重なる識別を渡した作り手の呼び出しは、誤りとして断る（保留を作らない。core の中の作り手の誤りで、利用者の入力ではない）。

### S3b で残した点（S4b-2）

`core-redesign.md` が「S4b で、スーパーバイザーの手と一緒に決める」とした 4 点。

- [ ] **「入れてよい」の後、上流を読めない状態が続く**: 「入れてよい」を返した実行について、上流を読めなかった回りを数える（契約の実行の記録の列）。3 回続いたら、止まり方 `upstream_unreadable` の保留にする（スーパーバイザー待ち）。読めた回りで、0 に戻す。実行は取り消さない。いまある、読めなかった回数の数えとの関係は、最初の Issue で確かめる。
- [ ] **統合先へ入ったかの確かめが、成果物の形に頼る**: 確かめの作りは、変えない（開発に固有の知識を、core に足さない）。確かめられずに保留になるとき（`intake_unverified`）、スーパーバイザーが調べて、受け取りのやり直しか、見送りか、上げるかを選ぶ。
- [ ] **終わりを記録した実行があるときの、計画の作り直し**: この区切りでは、スーパーバイザーの `replan` を、いまの「計画を作り直す回答」と同じ動きにする（動きは変えない）。作り直しのときに、終わった実行を持つタスクをどう残すかは、S4c-1（計画の後にタスクを足す）で決める。

## クリティカル設計決定

### 承認の真正性: スーパーバイザーは、保留を「閉じる」ことはできるが、承認はできない（S4b-2。`answer` は S4b-3）

- **採用案**: スーパーバイザーが閉じられるのは、core がサイクルの中で、対象の止まり方を渡して作った保留だけ。保留を閉じる手は 5 つ（`reverify`・`send_back`・`retry`・`split_followup`・`replan`）。`answer` だけは、保留を作る前の委譲先の問いに答える（閉じる保留は無く、動きは、いまの J4 の再開と同じ）。どの手も、計画の承認・完了の承認・不可逆操作の承認・予算の増額・取り下げを、通らない。`replan` は、計画の承認待ちへ戻るので、作り直した計画を承認するのはオーナー。閉じた者は `supervisor` と記録し、オーナーの回答（本人確認つき）と区別する。
- **実装の形**: 遷移表に、本人確認の要らない行を 1 つ足す（操作 `supervisor_resolve`。T20。遷移元は保留中。戻り先は、保留の直前の状態。`replan` のときは、作り直しの回答と同じ先）。スーパーバイザーの手は、この行を、判断点の行為者の遷移で通る。保留の回答の処理の中身は、本人確認を取らない内部の関数へ切り出し、人の回答（T12。本人確認の検査の後）と、この行の両方から呼ぶ。人の回答の遷移（T12）と、本人確認の登録簿は、変えない。この行を呼べるのは、スーパーバイザーの段の手の実行だけで、対象は、スーパーバイザー待ち（`pending`）の保留だけ。
- **理由**: 設計書 D27・§21.5 の「できないこと」。人の入口（T12）と別の行にすることで、人の入口の不変条件（本人確認つきの行は、本人確認つきの呼び出しだけが通る）を弱めない。対象の保留は、core が自分で作った「進め方」の保留で、5 つの手で起きることは、次のとおり、どれも承認ではない: 検証のやり直し（`reverify`）・委譲先への差し戻し（`send_back`）・起動し直し（`retry`）・フォローアップの作成（`split_followup`。条件は消えずに残り、完了の承認のときにオーナーに見える）・計画の作り直し（`replan`。作り直した計画を承認するのはオーナー）。
- **代替案**: (a) 本人確認の登録簿に（判断点・本人確認なし）の組を足して、人の回答の遷移（T12）をそのまま通す。人の本人確認つきの操作の入口に、人でない行為者を通すことになり、D11 の変更になるので採らない。(b) 遷移を足さず、T12 を判断点の行為者で通す。いまの遷移の実行が、本人確認つきの行を本人確認なしで通すことを断るので、不変条件を弱めることになる。採らない。(c) スーパーバイザーの手を、保留を作る前に呼ぶ（保留を作らない）。止まる所ごとに、呼び出しと戻り先を作ることになり、遷移が増える。保留を経由すれば、オーナーが割り込む口（回答）を、そのまま使える（子の問いだけは、いまの J4 が保留の前に呼ばれているので、その位置を引き継ぐ）。

### 子の問いに答える範囲（S4b-3）

- **採用案**: 必ず上げる種類（接続の宣言の一覧）に当たる問いは、スーパーバイザーを呼ばない。ほかの問いは、答える者が「人」と指定されていても、スーパーバイザーが先に受け（オーナーの決定 2026-11-22）、根拠の場所（ワークスペースの根の下の通常のファイル）を示せた問いだけ答える。1 問でも示せなければ、全部を上げる。契約の判断待ちは、問いの種類の値を持たないので、種類の照合なしで受ける（オーナーの決定 2026-11-22）。歯止めは、指示文の決まり（範囲・完了条件・予算・好み・取り消せない操作の問いは必ず上げる）と、根拠のファイルの実在の検査。
- **理由**: 設計書 §21.5 の歯止め。根拠の実在は、core が LLM なしで確かめられる。中身が合っているかは確かめられないので、答えた問いと根拠を記録し、完了の承認のときにオーナーへ見せる。
- **代替案**: 答えるのが「人」と指定された問いは、いまのまま、全部オーナーへ上げる。守りは強いが、J4 の実行が 0 回だった形が、そのまま残る見込みがある。契約の判断待ちについては、答える者が「人」のものだけは受けない形、claude-harness の契約に問いの種類を足してもらう形もある（どちらも、オーナーが採らなかった。2026-11-22）。

### 条件をフォローアップへ回す（`split_followup`）（S4b-2）

- **採用案**: 回せるのは、検証の判断点が、条件ごとの区分（反映の後でしか満たせない・人の操作の後でしか満たせない）を付けた条件だけ。core が、保留の原因の検証の実行の出力から、区分つきの条件を引いて番号を振り、スーパーバイザーは、その番号で返す。区分の無い条件の番号・空は、実行しない。区分つきの条件が 1 件も無い保留では、この手を選べる手から外す。回した条件は、タスクにぶら下がるフォローアップ（題名は、core が番号から引いた条件の文）として残り、課題の完了の承認のときに、オーナーに見える。
- **理由**: 設計書 §21.5 は、この手を「反映の後でしか満たせない条件」に使う手とし、「オーナーに聞かずに使ってよい。条件は消えずに残るので、範囲の変更には当たらない」としている。範囲を、検証の判断点が付けた区分で core が絞ることで、オーナーが承認した完了条件を、スーパーバイザーの判断だけで検証から外すことを防ぐ（設計書 §21.5 の「できないこと」の、範囲の変更）。番号で返させることで、スーパーバイザーが条件を書き換える・作ることも防ぐ。
- **代替案**: (a) 完了条件のどれでも回せるようにして、指示文の決まり（反映の後でしか満たせない条件だけ回す）に頼る。core が確かめられず、スーパーバイザーの判断だけで、承認した完了条件が検証から外れうるので採らない（PR #1012 の Codex レビューの指摘）。(b) 条件の文を返させて、core が文の一致で照合する。言い換えで落ちる。(c) 回す前に、オーナーへ問う。反映の後でしか満たせない条件のたびに、保留が 1 回増える。
- **残る点**: 区分を付けるのは検証の判断点で、スーパーバイザーではない。検証の判断点が区分を付けなかった条件は、回せず、オーナーへ上がる（守る側に倒す）。区分つきの条件が、タスクの完了条件の全部に当たるかは、core は確かめない（区分つきの条件の文は、検証の判断点が書いた文で、完了条件の文と機械的に突き合わせられない）。

### 選択肢つきの問いは、土台だけを S4b に置く（S4b-1）

- **採用案**: 保留に選択肢の並びと、選んだ識別を持たせ、`flywheel answer --option` で答えられるようにする。選択肢で答えたときの遷移は、いまの回答と同じ（選んだ見出しが回答の文になる）。本人確認も、いまの回答と同じ。選択肢ごとに別の動きを起こす処理と、画面のボタン（本人確認なしの経路）は、S4b に入れない。
- **理由**: オーナーの決定（2026-11-22）で、画面のボタンでの「選ぶだけの回答」（S4d-2）と、上限を超えて足すときの問いを選ぶ形にすること（S4c-1）が決まった。どちらも S4b の後に入り、同じ土台を使う。S4b にも使い手がある（スーパーバイザーが上げるときの選択肢・委譲先が返した選択肢）。いまは、委譲先の選択肢を 1 本の文に潰していて、「選ぶだけで答えられるか」を見分ける値が無い。
- **守り**: 選択肢で答える操作は、回答と同じ種類の操作で、本人確認の登録簿を変えない。スーパーバイザーが付ける選択肢は、オーナーが選ぶための見出しで、core は、選ばれた見出しを回答の文として扱うだけ（選択肢の文から、承認・予算の増額・取り下げを起こさない）。
- **代替案**: (a) 使う側の区切り（S4c-1・S4d-2）がそれぞれ足す。保留の持ち方が 2 回変わる。(b) 問いが 2 件以上の報告にも、問いごとの選択肢を持たせる。保留 1 つに選択肢の組が複数になり、回答の指定が複雑になる。問いごとに選ぶ形は、要るときに足す。

### DB スキーマ（S4a・対話の欄の次の版から。スライスごとに 1 版）

列と表は、使うスライスで足す。

- **S4b-1**: 保留の表 `hold` の `options`・`answer_option`・`option_required`。
- **S4b-2**: 保留の表 `hold` の残りの列（`stop_kind`・`supervisor_state`・`supervisor_findings`・`supervisor_recommendation`・`supervisor_action_id`・`deferred_cycle_id`・`deferred_count`）、対処の記録の表 `supervisor_action`（`questions` を除く）、フォローアップの `task_id` と出どころ `supervisor`、タスクの `verify_not_met_streak`、課題の `reconcile_supervisor_action_id`、契約の実行の記録の、上流を読めなかった回りの数。
- **S4b-3**: 対処の記録の表 `supervisor_action` の `questions`。

列ごとの中身は、次のとおり。

- 保留の表 `hold` に足す列: `stop_kind`（止まり方。渡されなければ NULL）、`supervisor_state`（NULL・`pending`〔スーパーバイザー待ち〕・`escalated`〔上げた〕・`handled`〔手を打って閉じた〕）、`supervisor_findings`、`supervisor_recommendation`、`supervisor_action_id`（その保留を閉じた・上げた対処の記録。無ければ NULL）、`deferred_cycle_id`（最後に見送ったサイクル）、`deferred_count`（見送りの連続の数え。既定 0）、`options`（選択肢の並び。JSON の配列で、要素は `id`・`label`・`description`。無ければ NULL）、`answer_option`（選んだ選択肢の識別。選んでいなければ NULL）、`option_required`（「識別の無い回答を断る」印。既定 0）。
- 対処の記録の表 `supervisor_action`: `id`・`cycle_id`・`challenge_id`・`task_id`（NULL 可）・`hold_id`（NULL 可）・`run_id`（スーパーバイザーの判断の実行。起動できたとき）・`stop_kind`・`hand`（判断できなかったときは NULL）・`findings`・`note`・`basis`（JSON）・`conditions`（回した条件の番号と文。番号は、入力の「回せる条件」の番号。JSON。無ければ NULL）・`questions`（子の問いと答え。JSON。無ければ NULL）・`result`・`reject_reason`（断りの理由。`state_changed`・`owner_answered`。結果が `rejected` でなければ NULL）・`created_at`。
- フォローアップの表 `followup` に足す列: `task_id`（ぶら下がるタスク。NULL 可）。出どころ（`source`）の値に `supervisor` を足す。
- 課題の表 `challenge` に足す列: `reconcile_supervisor_action_id`（スーパーバイザーの `reverify` による「照合をやり直す」印。その対処の記録。無ければ NULL）。
- タスクの表 `task` に足す列: `verify_not_met_streak`（タスクの検証の連続の「満たしていない」の数え。既定 0）。
- 上流を読めなかった回りの数は、契約の実行の記録に足す（列 1 つ。既定 0）。
- 検証の入力へ結ぶ持ち方: `reverify`・`replan` の文は、保留の回答の文（いまの「保留の記録」の区画）。`send_back` の指摘は、対処の記録の `note`（タスクと、最後の契約のコマンドより新しいもので引く）。`split_followup` の判定から外す条件は、対処の記録の `conditions`（タスクと、最後のオーナーの回答より後で引く）。
- 過去の行は、書き換えない（新しい列は NULL・0）。書き出しと再構築（export・import）の対象に、新しい表と列を含める。

## 機能全体の設計

### S4c・S4d-2 との境目

- フォローアップの列 `task_id` と、出どころ `supervisor` は、S4b が足す。S4b が書くのは、`split_followup` のフォローアップだけ。
- 計画の後にタスクを足すことは S4c-1、フォローアップを、開いている課題のタスクに上げることは S4c-2、保留中の課題のほかのタスクを進めることは S4c-3。S4b の保留は、いまと同じく、課題を単位に止める。
- S4c-1 が足す 2 つの保留（足した後の見込みが上限を超える・計画の判断点の「足す」の形の問い）は、スーパーバイザーが先に見る対象に入れない。S4c-1 がこれらの保留を作るときに止まり方を渡さなければ、「止まり方を渡さない保留は、対象にしない」の決まりで足りる（S4b の側に、一覧の追加は要らない）。
- 選択肢つきの問いの土台は S4b-1。S4c-1 が使う口は 5 つ: 意味のある識別つきの選択肢で保留を作る・「識別の無い回答を断る」保留にする・識別に文を添える（`--option` と `--answer`）・開いている保留の問いと選択肢の説明を、回答の処理と同じ書き込みの中から書き換える・選ばれた識別を、回答の処理の中で、同じ書き込みの中で読む。S4c-1 は、上限を超えて足すときの保留を、これらで作り、選ばれた識別で動きを分ける。S4d-2 は、画面のボタンで選択肢に答える口（本人確認なしの経路）と、表示を足す。
- `replan` の動きは、S4b では変えない。S4c-1 が、計画の作り直しと、承認なしで足すタスクの形を決めたら、スーパーバイザーの手に「タスクを足す」を足すかは、S4c-1 の仕様で決める。
- 委譲先の軽い指摘から出るフォローアップは、S4c-1 か S5（S4b は書かない）。

## 受入基準

> 実装対象の S4b-2 の分。前提は、上の受入基準（S4b-1。出荷済み）が成り立っていること。

特に断らない限り、テスト用の判断点（決めた出力を返す）とテスト用の委譲先で、宣言の `supervisor` は真（既定）で確かめる。「スーパーバイザー待ち」は、保留の `supervisor_state` が `pending` であること。「オーナーへ上がる」は、保留が開いたままで、`supervisor_state` が `pending` でないこと。

### 止まり方とスーパーバイザー待ち

- [ ] 完了の検証が「判断できない」を返して作られた保留の止まり方は `verify_uncertain` で、スーパーバイザー待ちである。
- [ ] タスクの検証が「判断できない」を返して作られた保留の止まり方は `verify_uncertain` で、スーパーバイザー待ちである。
- [ ] 成果物が見つからない保留（委譲の報告の照合）の止まり方は `artifact_missing` で、スーパーバイザー待ちである。
- [ ] 契約の実行が失敗で終わって作られた保留の止まり方は `delegate_stopped` で、スーパーバイザー待ちである。
- [ ] 委譲の連続の失敗の上限で作られた保留の止まり方は `delegate_stopped` である。
- [ ] 判断点の連続失敗の上限で作られた保留の止まり方は `judgment_failed` である（委譲の連続の失敗の保留と、理由の値が同じでも、止まり方は別になる）。
- [ ] 宣言の求める値を満たさないレビュー待ちが 2 回続いて作られた保留の止まり方は `facts_unmet` である。
- [ ] 委譲の差し戻しの上限で作られた保留の止まり方は `rework_limit` である。
- [ ] 検証した中身の確かめの失敗で作られた保留の止まり方は `checks_failed` である。
- [ ] 成果物が統合先へ入らないまま実行が終わって作られた保留の止まり方は `intake_unverified` である。
- [ ] 検証を経ずに成果物が統合先へ入っていて作られた保留の止まり方は `intake_unverified` である。
- [ ] 統合先の識別が合わずに作られた保留の止まり方は `intake_unverified` である。
- [ ] 分類の判断点の問いで作られた保留は、止まり方が NULL で、スーパーバイザー待ちにならない。
- [ ] 計画の判断点の問いで作られた保留は、スーパーバイザー待ちにならない。
- [ ] 完了の検証が、実物の食い違いで作った保留は、スーパーバイザー待ちにならない。
- [ ] 完了の検証が、人の操作の後でしか満たせない条件で作った保留は、スーパーバイザー待ちにならない。
- [ ] 課題の単位の確かめが「満たしていない」で作られた保留（`challenge_check_not_met`）は、スーパーバイザー待ちにならない。
- [ ] 予算の上限を超えて作られた保留は、スーパーバイザー待ちにならない。
- [ ] 理由が `unapproved_merge` の保留は、スーパーバイザー待ちにならない。
- [ ] 理由が `land_unavailable` の保留は、スーパーバイザー待ちにならない。
- [ ] 理由が `content_ref_invalid` の保留は、スーパーバイザー待ちにならない。
- [ ] 理由が `land_refused` の保留は、スーパーバイザー待ちにならない。
- [ ] 理由が `reflect_unavailable` の保留は、スーパーバイザー待ちにならない。
- [ ] 理由が `reflect_failed` の保留は、スーパーバイザー待ちにならない。
- [ ] 理由が `tasks_blocked` の保留は、スーパーバイザー待ちにならない。
- [ ] 理由が `blocked` の保留は、スーパーバイザー待ちにならない。
- [ ] 契約の判断待ちのうち、承認の待ちで作られた保留は、スーパーバイザー待ちにならない。
- [ ] 契約の判断待ちのうち、ターミナルで人が解く待ちで作られた保留は、スーパーバイザー待ちにならない。
- [ ] オーナーが `flywheel hold` で作った保留は、スーパーバイザー待ちにならない。
- [ ] 対話のセッションが引き取る保留（`parent_direct`）は、スーパーバイザー待ちにならない。
- [ ] 止まり方を渡さずに作った保留は、`stop_kind` も `supervisor_state` も NULL である。
- [ ] 宣言の `supervisor` が偽のとき、完了の検証の「判断できない」の保留は、スーパーバイザー待ちにならない。
- [ ] 宣言の `supervisor` に真偽値でない値を書くと、宣言の読み込みがエラーになる。
- [ ] 宣言に `supervisor` が無いとき、真として扱う。
- [ ] 契約の判断待ちのうち、成果物の無いレビューの待ちで作られた保留は、スーパーバイザー待ちにならない。
- [ ] ~~保留の間に成功した、統合先を使う課題の実行の保留は、スーパーバイザー待ちにならない。~~（**取り下げ**。オーナーの決定 2026-11-22: この保留〔`holdIntegrationSucceeded`。理由 `delegate_ended`・`merged_unverified`〕は止まり方 `intake_unverified` の対象で、スーパーバイザー待ちになる。「入れてよい」を返した後に実行が終わった・止まった保留〔`integration_land.go` の `holdLandedEnd` の呼び出し〕は、これまでどおり対象にしない。番号は変えない）
- [ ] 計画の承認待ちの課題に、対話のセッションが引き取る保留でない保留を作ろうとすると、いまと同じ誤り（成立しない遷移）で断られる。

### 回数の上限

- [ ] 同じタスクの同じ止まり方に、最後のオーナーの回答より後の、結果が `executed` の `reverify` の対処の記録が 2 件あるとき、その止まり方の次の保留は、スーパーバイザー待ちにならない。
- [ ] 同じタスクの止まり方 `delegate_stopped` に、結果が `executed` の `retry` と `replan` の対処の記録が 1 件ずつあるとき、その止まり方の次の保留は、スーパーバイザー待ちにならない（上限は、`reverify` 以外の手・止まり方でも働く）。
- [ ] `reverify` と `send_back` を、この順に実行した後に、上限に当たってスーパーバイザー待ちにならなかった保留の、問いの先頭の 1 行は、「スーパーバイザーが 2 回対処したが、進まなかった（手: reverify、send_back）。」である。
- [ ] 上限に当たってスーパーバイザー待ちにならなかった保留の、問いの 2 行目より後は、上限に当たらなかったときに作られる問いの文と同じである。
- [ ] 上限に当たってスーパーバイザー待ちにならなかった保留の `stop_kind` は、その止まり方である。
- [ ] 上限に当たってスーパーバイザー待ちにならなかった保留の `supervisor_state` は NULL である。
- [ ] 同じタスクの、別の止まり方の対処の記録が 2 件あっても、その止まり方でない新しい保留は、スーパーバイザー待ちになる。
- [ ] オーナーが保留に回答した後は、回答より前の対処の記録を数えない（同じ止まり方の新しい保留は、スーパーバイザー待ちになる）。
- [ ] スーパーバイザーが保留を閉じても、「最後のオーナーの回答」は進まない（スーパーバイザーが 2 回閉じた後の 3 回目の保留は、スーパーバイザー待ちにならない）。
- [ ] 手が `defer` の対処の記録は、2 回の上限に数えない。
- [ ] 手が `escalate` の対処の記録は、2 回の上限に数えない。
- [ ] 結果が `failed` の対処の記録は、2 回の上限に数えない。
- [ ] 結果が `rejected` の対処の記録は、2 回の上限に数えない。
- [ ] タスクの無い保留は、課題の単位で数える（同じ課題の、タスクの無い同じ止まり方の対処の記録が 2 件あるとき、次の保留は、スーパーバイザー待ちにならない）。

### スーパーバイザーの段

- [ ] スーパーバイザー待ちの保留が 1 件あるサイクルで、スーパーバイザーの判断点が 1 回呼ばれる。
- [ ] スーパーバイザー待ちの保留が 2 件あるとき、古い保留から順に、1 件ずつ呼ばれる。
- [ ] スーパーバイザー待ちの保留が無い回りでは、スーパーバイザーの判断点は呼ばれない。
- [ ] スーパーバイザーの段は、同じ回りの完了の検証の段の後に通る。
- [ ] オーナーが先に回答したスーパーバイザー待ちの保留について、スーパーバイザーの判断点は呼ばれない。
- [ ] スーパーバイザーの判断点の入力に、止まり方がある。
- [ ] スーパーバイザーの判断点の入力に、保留の問いがある。
- [ ] スーパーバイザーの判断点の入力に、課題の題名とタスクの題名がある。
- [ ] スーパーバイザーの判断点の入力に、タスクの完了条件が、1 から始まる番号つきである。
- [ ] スーパーバイザーの判断点の入力に、計画の方針がある。
- [ ] 実行の記録が 6 件あるタスクについて、スーパーバイザーの判断点の入力の実行の記録は、新しいほうの 5 件である。
- [ ] スーパーバイザーの判断点の入力に、そのタスクへのこれまでの対処の記録がある。
- [ ] スーパーバイザーの判断点の入力に、記憶の索引の場所がある。
- [ ] スーパーバイザーの判断点に許す道具は `Read`・`Grep`・`Glob` だけである。
- [ ] スーパーバイザーの判断点の費用の上限は、宣言の `judgment_budget_usd.SV` の値である。
- [ ] 宣言に `judgment_budget_usd.SV` が無いとき、上限は 5 USD である。
- [ ] スーパーバイザーの判断点の費用は、サイクルの費用に入る。
- [ ] スーパーバイザーの判断点の費用は、課題の費用に入る。
- [ ] スーパーバイザーの判断点の入力の実行の記録に、委譲先が返した値がある。
- [ ] スーパーバイザーの判断点の入力の実行の記録に、成果物の識別がある。
- [ ] スーパーバイザーの判断点の入力に、選べる手の一覧がある。
- [ ] タスクを指さない保留についての、スーパーバイザーの判断点の入力に、課題の完了条件がある。
- [ ] タスクを指さない保留についての、スーパーバイザーの判断点の入力に、課題のタスクの一覧（題名と状態）がある。
- [ ] 判断点の入力の「保留の記録」の区画で、スーパーバイザーが閉じた保留の回答に、「回答者: スーパーバイザー（オーナーの回答ではない）」の行がある。
- [ ] 判断点の入力の「保留の記録」の区画で、オーナーが回答した保留の回答に、「回答者: スーパーバイザー」の行は無い。

### 止まり方ごとに選べる手

入力の選べる手は、「止まり方ごとに選べる手」の表の手から、「事前に外す手」に当たるものを除いたもの。下の「だけである」の行は、外す条件に当たらない状態（保留がタスクを指す・保留の直前の状態が着手中か検証中・作業している契約の実行が無い・最後のオーナーの回答より後に、そのタスクへの対処の記録が無い・`send_back` を選べる組）で確かめる。

- [ ] 止まり方 `verify_uncertain`（タスクの検証の「判断できない」。開いている、契約のレビュー待ちの実行がある。検証の出力に、区分つきの条件が 1 件以上ある）の入力の選べる手は、`reverify`・`send_back`・`split_followup`・`replan`・`defer`・`escalate` だけである。
- [ ] 止まり方 `verify_uncertain` で `retry` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 止まり方 `verify_uncertain` の保留で、原因の、タスクの検証の実行の出力に、区分つきの条件（`deferred_conditions`）が 1 件も無いとき、入力の選べる手に `split_followup` が無い。
- [ ] 区分つきの条件が 1 件も無い `verify_uncertain` の保留に `split_followup` を返すと、対処の記録の結果は `failed` である。
- [ ] 止まり方 `artifact_missing` の入力の選べる手は、`reverify`・`retry`・`defer`・`escalate` だけである。
- [ ] 止まり方 `artifact_missing` で `send_back` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 止まり方 `delegate_stopped` の入力の選べる手は、`retry`・`replan`・`defer`・`escalate` だけである。
- [ ] 止まり方 `delegate_stopped` で `reverify` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 止まり方 `facts_unmet`（開いている、契約のレビュー待ちの実行がある）の入力の選べる手は、`send_back`・`escalate` だけである。
- [ ] 止まり方 `facts_unmet` で `retry` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 止まり方 `checks_failed` の入力の選べる手は、`escalate` だけである（`send_back` は、選べる組が無いので、いつも外れる）。
- [ ] 止まり方 `checks_failed` で `send_back` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 止まり方 `rework_limit`（開いている、契約のレビュー待ちの実行がある）の入力の選べる手は、`send_back`・`replan`・`escalate` だけである。
- [ ] 止まり方 `rework_limit` で `retry` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 止まり方 `judgment_failed` の入力の選べる手は、`retry`・`escalate` だけである。
- [ ] 止まり方 `judgment_failed` で `replan` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 止まり方 `intake_unverified` の入力の選べる手は、`reverify`・`defer`・`escalate` だけである。
- [ ] 止まり方 `intake_unverified` で `retry` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 止まり方 `upstream_unreadable` の入力の選べる手は、`defer`・`escalate` だけである。
- [ ] 止まり方 `upstream_unreadable` で `reverify` を返すと、手は実行されず、対処の記録の結果は `failed` である。
- [ ] 同じタスクの同じ止まり方に、結果が `executed` の `retry` の対処の記録が 1 件あるとき、次の入力の選べる手に `retry` が無い。
- [ ] 作業している契約の実行がある課題の保留について、入力の選べる手に `replan` が無い。
- [ ] 保留の直前の状態が着手中でも検証中でもない保留について、入力の選べる手に `replan` が無い。
- [ ] タスクを指さない `verify_uncertain` の保留（課題の単位の完了の検証の「判断できない」）の入力の選べる手は、`reverify`・`replan`・`defer`・`escalate` だけである。
- [ ] 保留が指すタスクの最後の実行が、委譲の報告の形の実行である `verify_uncertain` の保留について、入力の選べる手に `send_back` が無い。
- [ ] 保留が指すタスクの契約の実行が終わっている `rework_limit` の保留について、入力の選べる手に `send_back` が無い。
- [ ] 保留の直前の状態が検証中の保留について、入力の選べる手に `send_back` が無い。
- [ ] 最後のオーナーの回答より後に、そのタスクの `rework_limit` に、結果が `executed` の `send_back` の対処の記録が 1 件あるとき、次の `rework_limit` の保留の入力の選べる手に `send_back` が無い。
- [ ] 人の作り直しの回答（`flywheel answer --replan`）は、作業している契約の実行がある課題では、いまと同じに、検証の誤りで断られる（判定を共有の関数に切り出した後も変わらない）。

### 手の実行

- [ ] `reverify` を実行すると、保留は回答済みになる。
- [ ] 保留を閉じる 5 つの手（`reverify`・`send_back`・`retry`・`split_followup`・`replan`）のどれで閉じた保留も、`supervisor_state` は `handled` である。
- [ ] 保留を閉じる 5 つの手のどれで閉じた保留も、回答した者（`answered_by`）は `supervisor` である。
- [ ] 保留を閉じる 5 つの手のどれで閉じた保留も、経路（`answered_channel`）は `invoker` である。
- [ ] 保留を閉じる 5 つの手のどれで閉じた保留も、本人確認（`answered_verification`）は `none` である。
- [ ] 保留を閉じる 5 つの手の遷移は、作業ログに、操作 `supervisor_resolve` として残る（人の回答の操作 `answer` としては残らない）。
- [ ] 遷移表に、操作 `supervisor_resolve`（遷移元は保留中）の行があり、本人確認の要らない行である。
