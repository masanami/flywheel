# core の見直し 区切り S4b — スーパーバイザーのその場の対処

## 概要

`docs/features/core-redesign.md` の区切り S4b の仕様。S4a（長く走るサイクル）の実装の間に書くので、その間だけ別の文書に書き、main に入れた後に `core-redesign.md` へ畳む（S3d・S4d と同じ進め方。オーナーの決定 2026-11-22）。

S4b は、設計書 §21.5 のスーパーバイザーの出番のうち「その場の対処」を入れる。サイクルの途中でタスクが想定外に止まったとき、いまは保留にしてオーナーへ上げる。S4b からは、スーパーバイザー（読み取りの道具だけを持つ判断点）が先に調べ、core が用意した手の一覧から 1 つ選ぶ。選んだ手を実行するのは core。委譲先からの問い（子の問い）も、スーパーバイザーが受ける（子の問いに答える判断点〔J4〕を、スーパーバイザーにまとめる。設計書 §21.6）。

サイクルの終わりの振り返り（出番 2）は S5。

> **仮の決定の印**: 本文で「（仮）」と書いた所は、オーナーに伺う前の推奨案で書いている。伺う点は、PR の説明に並べる。

## 背景・目的

- 測った期間に、サイクルの途中でオーナーへ上がった問い 117 件のうち、スーパーバイザーが引き受けられるものが約 45 件あった（委譲先の失敗・中止 18、自己レビューが不明 15、成果物の中身を読めない 9、成果物が見つからない 3。設計書 §21.5）。いまは、想定外のことが起きると「同じことをやり直す」か「オーナーへ上げる」しか無い。
- 子の問いに答える判断点（J4）は、実行の記録が 0 回だった（設計書 §21.6）。オーナーへの問い（保留）は 470 件で、回答待ちは、委譲で完了した課題の時間の 40% だった（設計書 §21.0）。
- S4a で、サイクルは、進められるものが無くなるまで回りを繰り返す。保留がオーナーへ上がると、その課題はオーナーの回答まで止まる。スーパーバイザーが先に受ければ、同じサイクルの中で続きを進められる。

## ユーザーストーリー

オーナーとして、委譲先の一時的な失敗や、調べれば分かる食い違いのたびに呼ばれたくない。自分に上がってくる問いには、何が起きたか・何を調べたか・どうするのがよいかが、付いていてほしい。スーパーバイザーが自分の代わりに決めたことは、後から全部見たい。

## 機能要件

語は `docs/glossary.md` に合わせる。この文書では、次の語を使う。

- **止まり方**: スーパーバイザーを呼ぶきっかけの種類。下の「対象の止まり方」の閉じた一覧。
- **対処**: スーパーバイザーの判断 1 回と、core がその手を実行した結果。1 件ずつ記録する（対処の記録）。
- **スーパーバイザー待ちの保留**: core が作った保留のうち、オーナーより先にスーパーバイザーが見るもの。

### スーパーバイザーを呼ぶとき

- [ ] サイクルの進める段の最後に、スーパーバイザーの段（`supervise`）を足す。回りごとに 1 回通る（S4a の回りの中。完了の検証の段の後）。
- [ ] core が、サイクルの中で、対象の止まり方の保留を作るとき、その保留を「スーパーバイザー待ち」にする（保留の行に印を付ける。課題の状態の遷移は、いまの保留と同じ）。
- [ ] 対象の止まり方（閉じた一覧）と、保留の理由（`holdReason`）の対応は、次のとおり。一覧に無い理由の保留は、いまと同じく、はじめからオーナーへ上がる。

| 止まり方 | 起きること | いまの保留の理由 |
|---|---|---|
| `verify_uncertain` | 完了の検証・タスクの検証が「判断できない」を返した | （理由なしの保留。検証の判断点の問い） |
| `artifact_missing` | 成果物が見つからない | `artifact_missing` |
| `delegate_stopped` | 委譲先の実行が失敗・中止で終わった、連続の失敗が上限に達した | `contract_stopped`・`failure_limit` |
| `facts_unmet` | 委譲先が返す値が、宣言の求める値を満たさないレビュー待ちが 2 回続いた | `facts_unmet` |
| `rework_limit` | 差し戻しが上限に達した（タスクの検証の連続の「満たしていない」を含む。下の「S3b で残した点」） | `rework_limit` |
| `checks_failed` | 検証した中身の確かめに失敗がある | `checks_failed` |
| `judgment_failed` | 判断点（分類・計画・完了の検証）の失敗・不正な出力が、連続の上限に達した | （判断点の連続失敗の保留） |
| `intake_unverified` | 統合先を使う課題で、タスクの成果を受け取れない（成果物が統合先へ入らないまま実行が終わった・検証を経ずに入っていた・統合先の識別が合わない） | `delegate_ended`・`merged_unverified`・`integration_ref_invalid` |
| `upstream_unreadable` | 「入れてよい」を返した後、上流を読めない回りが 3 回続いた（下の「S3b で残した点」） | （新設） |
| `child_question` | 委譲先からの問い（下の「子の問い」） | `questions`・契約の判断待ち |

- [ ] 次の保留は、対象にしない（はじめからオーナーへ上がる）: 予算の上限を超えた保留、承認していない反映の検知（`unapproved_merge`）、反映・上げる依頼に関わる保留（`land_unavailable`・`content_ref_invalid`・`land_refused`・`reflect_unavailable`・`reflect_failed`）、前提のタスクの取りやめで進めようが無い保留（`tasks_blocked`）、課題の単位の確かめが「満たしていない」だった保留（`challenge_check_not_met`）、委譲先が「進められない」と返した保留（`blocked`）、オーナーが自分で作った保留（`flywheel hold`）、対話のセッションが引き取る保留（`parent_direct`）。
- [ ] 同じタスク（タスクの無い保留は、同じ課題）の、同じ止まり方への対処は、2 回まで。数えるのは、その課題の、最後にオーナーが回答した保留より後の、対処の記録（手が「見送る」のものは数えない）。3 回目に当たる保留は、スーパーバイザー待ちにせず、「スーパーバイザーが 2 回対処したが、進まなかった」旨と、その 2 回の手を、問いの冒頭に付けて、オーナーへ上げる。
- [ ] スーパーバイザーの段は、スーパーバイザー待ちの保留を、古い順に 1 件ずつ処理する。1 件ごとに、スーパーバイザーの判断点を 1 回呼ぶ。
- [ ] オーナーは、スーパーバイザー待ちの保留にも、いまと同じ操作（`flywheel answer`）で回答できる。回答済みの保留を、スーパーバイザーの段は処理しない。
- [ ] 宣言（`agent.json`）の `supervisor`（真偽。既定は真）が偽のとき、保留をスーパーバイザー待ちにしない（S4a までと同じ動き。子の問いは、下の「子の問い」の「偽のとき」）。

### スーパーバイザーの判断点

- [ ] スーパーバイザーの判断点（記録上の名前は `SV`）は、ほかの判断点と同じ呼び出し（`internal/invoker`。読み取りの道具〔`Read`・`Grep`・`Glob`〕だけ。作業ディレクトリはワークスペース）で呼ぶ。コマンドを実行する道具を持たない。
- [ ] 入力に渡すもの: 止まり方、保留の問い、課題とタスクの題名・完了条件、計画の方針、そのタスクの実行の記録（状態・要約・委譲先が返した値・成果物の識別。直近 5 件）、そのタスクへのこれまでの対処の記録、選べる手の一覧（下の表で、その止まり方に許すものだけ）、記憶の索引の場所。
- [ ] 出力（型つき）: `hand`（選べる手の 1 つ）、`findings`（調べたこと。必須）、`note`（手に添える文。手ごとの必須は下）、`basis`（根拠の場所の配列。要素は `path` と `locator`〔節や行の手がかり〕）、`recommendation`（オーナーへ上げるときの推奨。`escalate` のとき必須）、`conditions`（フォローアップへ回す条件の文の配列。`split_followup` のとき 1 件以上）。
- [ ] 費用の上限は、宣言の `judgment_budget_usd.SV`（既定 3 USD）。時間の上限は、ほかの判断点と同じ（`timeout_sec.judgment`）。費用は、判断点の費用として、課題とサイクルの費用に入る。
- [ ] 指示文 `sv.md` を足す。書くこと: できないこと（承認・反映・取り下げ・予算の増額・範囲の変更・成果物の手直し）、手の選び方、根拠を示せないときは上げること、調べる範囲（ワークスペースの中の文書・記憶・コード。成果物の中身は、入力に渡した識別と要約まで）。開発に固有の語を書かない。

### 手の一覧

- [ ] 手は、次の 8 つ（閉じた一覧）。設計書 §21.5 の手 4（委譲先に片付けを頼んで、起動し直す）は、入れない（オーナーの決定 2026-11-22。下の「やらないこと」）。

| `hand` | 手 | core がすること | 添える文 |
|---|---|---|---|
| `reverify` | 調べた結果を添えて、検証をやり直す | 保留を閉じ、課題・タスクを検証の前の状態へ戻す。次の検証の入力に、`findings` と `note` を「スーパーバイザーが調べた結果」として渡す | `note` 必須 |
| `send_back` | 添え書きを付けて、委譲先へ差し戻す | 保留を閉じ、`note` を指摘として、いまある差し戻し（委譲先の続き）へ渡す。差し戻しの回数に数える | `note` 必須 |
| `retry` | 同じ入力でやり直す | 保留を閉じ、止まる前の状態へ戻す。委譲先の実行が終わっていれば、次の回りで、同じタスクを起動し直す。判断点の連続失敗は、数え直す | なし |
| `split_followup` | 残った条件をフォローアップへ回して、ほかの条件で判定する | `conditions` の 1 件ごとに、そのタスクにぶら下がるフォローアップを作る（出どころは `supervisor`）。保留を閉じ、検証をやり直す。次の検証の入力に「フォローアップへ回した条件（判定から外す）」として渡す | `note` 必須 |
| `replan` | 計画を作り直す | 保留を、計画を作り直す回答（`--replan`）と同じ扱いで閉じる（次の回りで計画の判断点が作り直し、計画の承認待ちへ戻る。承認するのはオーナー） | `note` 必須（作り直す理由。計画の判断点の入力になる） |
| `defer` | このサイクルでは見送る | 保留は、スーパーバイザー待ちのまま残す。このサイクルでは、もう処理しない | `note` 必須（何を待つか） |
| `escalate` | 調べた内容と推奨を付けて、オーナーへ上げる | 保留を「オーナーへ上げた」にし、`findings` と `recommendation` を保留に残す | `recommendation` 必須 |
| `answer` | 根拠を示して、子の問いに答える | 下の「子の問い」 | `basis` 1 件以上 |

- [ ] 止まり方ごとに選べる手は、次のとおり（core が、出力の `hand` を、この表で検査する）。

| 止まり方 | 選べる手 |
|---|---|
| `verify_uncertain` | `reverify`・`send_back`・`split_followup`・`replan`・`defer`・`escalate` |
| `artifact_missing` | `reverify`・`retry`・`defer`・`escalate` |
| `delegate_stopped` | `retry`・`replan`・`defer`・`escalate` |
| `facts_unmet`・`checks_failed` | `send_back`・`escalate` |
| `rework_limit` | `send_back`・`replan`・`escalate` |
| `judgment_failed` | `retry`・`escalate` |
| `intake_unverified` | `reverify`・`defer`・`escalate` |
| `upstream_unreadable` | `defer`・`escalate` |
| `child_question` | `answer`・`escalate` |

- [ ] `retry` は、同じタスクの同じ止まり方に、1 回まで。2 回目の対処では、選べる手の一覧から `retry` を外して渡す。
- [ ] `rework_limit` の `send_back` は、上限の後の 1 回だけの差し戻しになる（対処の上限 2 回のうちの 1 回）。
- [ ] `split_followup` で回せる条件は、入力に渡した完了条件のうちのもの。core は、`conditions` の各文が、そのタスクの完了条件のどれかと一致することを確かめ、一致しないものが 1 件でもあれば、手を実行せず、オーナーへ上げる（条件を、スーパーバイザーが作らない）。完了条件の全部を回す出力も、実行せず、オーナーへ上げる。
- [ ] 手を実行できない状態（例: `replan` を選んだが、計画を作り直す回答を受けられない状態・戻す先の状態が無い）のとき、core は手を実行せず、`findings` を付けて、オーナーへ上げる。対処の記録の結果は `rejected`。
- [ ] スーパーバイザーの判断点が、失敗した・不正な出力を返した・費用か時間の上限に当たった・表に無い手を返した → 手を実行せず、「スーパーバイザーが判断できなかった」旨を付けて、オーナーへ上げる（やり直さない）。対処の記録の結果は `failed`。
- [ ] 利用上限・サイクルの費用の上限で、スーパーバイザーの判断点を起動できなかった保留は、スーパーバイザー待ちのまま残す（対処の記録を作らない）。
- [ ] スーパーバイザーが閉じた保留は、回答した者を「スーパーバイザー」として記録する（`answered_by` が `supervisor`。経路は `invoker`・本人確認は `none`）。オーナーの回答・承認として数えない。

### 子の問い

- [ ] 委譲先からの問い（契約の判断待ちで、答えるのが親のもの。委譲の報告の結末が「問い」のもの）は、子の問いに答える判断点（J4）ではなく、スーパーバイザーが受ける。J4 の呼び出し・指示文は外す。
- [ ] 必ずオーナーへ上げる問い（スーパーバイザーを呼ばない）は、いまの規則のまま: 問いの種類が、接続の宣言の「人に聞く種類」（`human_question_kinds`）に当たるもの。
- [ ] （仮）答えるのが「人」と指定された問い（意思決定者が `human`）も、上の種類に当たらなければ、スーパーバイザーが先に受ける。スーパーバイザーは、根拠を示せるものだけ答え、ほかは上げる。
- [ ] 子の問いは、保留を作る前に、スーパーバイザーの判断点を呼ぶ（いまの J4 と同じ位置。段の中で呼び、スーパーバイザーの段を待たない）。対処の回数・記録・費用の決まりは、ほかの止まり方と同じ。
- [ ] `answer` の出力は、問いごとに、選んだ選択肢（選択肢がある問い）か回答の文（無い問い）と、`basis`（1 件以上）を持つ。core は、`basis` の各 `path` が、ワークスペースの中に実在するファイルであることを確かめる。1 件も実在しない問いがあれば、その報告の問い全部を、オーナーへ上げる。
- [ ] 全部の問いに答えたときだけ、委譲先へ答えを返して再開する（いまの J4 と同じ返し方）。1 問でも上げるなら、全部の問いを 1 つの保留にして、オーナーへ上げる（答えられた問いの答えの案と根拠は、`findings` に残す）。
- [ ] 答えによる再開は、1 つの課題の委譲の連なり（最後にオーナーが回答した保留より後）で 3 回まで（いまの J4 の上限のまま）。4 回目は、オーナーへ上げる。
- [ ] 指示文に書く歯止め: 範囲・完了条件・予算を変える問い、好みを問う問い、取り消せない操作に関わる問いは、必ず上げる。
- [ ] 宣言の `supervisor` が偽のとき、子の問いは、すべて保留にして、オーナーへ上げる（J4 は戻さない）。

### オーナーへ上げるとき

- [ ] スーパーバイザーが上げた保留には、調べたこと（`findings`）と推奨（`recommendation`）が付く。`flywheel show <課題>`・`flywheel status` の保留の表示と、API の保留の値に出す。
- [ ] 上げた保留は、いまの保留と同じ操作で回答できる。回答の後の動きは、いまと同じ。
- [ ] スーパーバイザー待ちの保留は、オーナー待ちに数えない。`flywheel status` は、「スーパーバイザーが確認中」として、件数と課題を別に出す。API の値も、同じ区別を持つ。（仮）
- [ ] サイクルが走っていない間に残っているスーパーバイザー待ちの保留（見送り・起動できなかったもの）は、S4a の「いま始められるもの」に数える（次のサイクルで処理できる）。ただし、同じサイクルで見送った保留は、そのサイクルの数えには入れない（見送りだけで回りを続けない）。
- [ ] 見送り（`defer`）が、同じ保留に 3 サイクル続いたら、4 回目は、スーパーバイザーを呼ばず、オーナーへ上げる。

### 記録と表示

- [ ] 対処は、1 件ずつ記録する（対処の記録）。持つ値: サイクル、課題、タスク（あれば）、保留（子の問いに答えて保留を作らなかったときは無し）、スーパーバイザーの判断の実行、止まり方、手、調べたこと、添えた文、根拠、結果（`executed`・`rejected`・`failed`）、時刻。子の問いに答えたときは、問いと答えも持つ。
- [ ] 作業ログに、対処を 1 行で残す（行為者は `invoker`。操作の種類は `supervise`）。
- [ ] `flywheel show <課題>`（テキストと `--json`）と、課題の詳細の API に、その課題の対処の記録（`supervisor_actions[]`）を、古い順に出す。
- [ ] 完了の承認待ちの課題の要約（`flywheel show`・承認待ちの API）に、「スーパーバイザーが答えた子の問い」（問い・答え・根拠）と「打った手」の件数を出す。オーナーは、承認の前に、まとめて見られる。
- [ ] `flywheel cycle` の出力の段（`phases`）に `supervise` を足し、処理した件数・手ごとの件数を出す。
- [ ] 画面の表示は、S4d-2（この区切りでは、型と偽のデータの追従だけ）。

### S3b で残した点

`core-redesign.md` が「S4b で、スーパーバイザーの手と一緒に決める」とした 4 点。

- [ ] **タスクの検証の、連続の「満たしていない」の上限**: タスクの検証にも、宣言の差し戻しの上限（`rework_limit`。既定 3）を当てる。同じタスクの検証が、上限の回数だけ続けて「満たしていない」を返したら、差し戻さず、止まり方 `rework_limit` の保留にする（スーパーバイザー待ち）。
- [ ] **「入れてよい」の後、上流を読めない状態が続く**: 「入れてよい」を返した実行について、上流を読めなかった回りを数える。3 回続いたら、止まり方 `upstream_unreadable` の保留にする（スーパーバイザー待ち）。読めた回りで、数え直す。実行は取り消さない。
- [ ] **統合先へ入ったかの確かめが、成果物の形に頼る**: 確かめの作りは、変えない（開発に固有の知識を、core に足さない）。確かめられずに保留になるとき（`intake_unverified`）、スーパーバイザーが調べて、検証のやり直しか、見送りか、上げるかを選ぶ。
- [ ] **終わりを記録した実行があるときの、計画の作り直し**: この区切りでは、スーパーバイザーの `replan` を、いまの「計画を作り直す回答」と同じ動きにする（動きは変えない）。作り直しのときに、終わった実行を持つタスクをどう残すかは、S4c（計画の後にタスクを足す）で決める。

## 技術的な制約・方針

  - `internal/invoker`: 判断点の一覧に `SV` を足し、指示文 `sv.md` を足す。`j4.md` を外す。
  - `internal/cli`・`internal/view`・`internal/server`: 表示と API の値。
  - `web/src`: 型と偽のデータの追従だけ。
- 手の実行は、新しい遷移を足さず、いまある保留の回答の遷移（止まる前の状態へ戻る・計画を作り直す）を、行為者を変えて使う。スーパーバイザーの判断点は、型つきの値を返すだけで、ストアを書かない（設計書 P2・§7 のまま）。
- 止まり方と、選べる手の表は、core の中に 1 か所で持つ（閉じた一覧。`internal/view` の閉じた一覧にも足す）。
- 保留の理由を値として持たない保留（検証の「判断できない」・判断点の連続失敗）にも、止まり方を付けられるよう、保留を作る呼び出し元で、止まり方を渡す。最初の Issue で、サイクルの中で保留を作る所を一覧にし、止まり方との対応を PR の説明に書く（上の表と食い違うものがあれば、仕様への指摘として上げる）。
- `judgment_budget_usd.J4` は、宣言に書いてあっても読み込める（使わない。いまの宣言を壊さない）。過去の J4 の実行の記録は、そのまま読める。
- S4a が前提。S4a が main に入ってから実装する。ストアの版は、S4a（版 31）・対話の欄（版 32）の次。S4c と並べて進めるなら、後から main に入る側が、番号を並べ直す。
- 試験は、テスト用の判断点（決めた出力を返す）と、テスト用の委譲先で行う。実物のスーパーバイザーの判断は、要人間判定。

## クリティカル設計決定

### 承認の真正性: スーパーバイザーは、保留を「閉じる」ことはできるが、承認はできない

- **採用案**: スーパーバイザーが閉じられるのは、core がサイクルの中で作った、対象の止まり方の保留だけ。閉じ方は、手の一覧の 6 つ（`reverify`・`send_back`・`retry`・`split_followup`・`replan`・`answer`）に限る。どの手も、計画の承認・完了の承認・不可逆操作の承認・予算の増額・取り下げを、通らない。`replan` は、計画の承認待ちへ戻るので、作り直した計画を承認するのはオーナー。閉じた者は `supervisor` と記録し、オーナーの回答（本人確認つき）と区別する。
- **理由**: 設計書 D27・§21.5 の「できないこと」。保留の回答は、いまは本人確認つきの操作（D11）だが、対象の保留は、core が自分で作った「進め方」の保留で、回答で起きることは、いまもサイクルの中で core が自分で行っている動き（検証・差し戻し・起動）に限られる。
- **代替案**: スーパーバイザーの手を、保留を作る前に呼ぶ（保留を作らない）。止まる所ごとに、呼び出しと戻り先を作ることになり、遷移が増える。保留を経由すれば、いまの遷移と、オーナーが割り込む口（回答）を、そのまま使える。

### 子の問いに答える範囲

- **採用案**: 必ず上げる種類（接続の宣言の一覧）は、スーパーバイザーを呼ばない。ほかの問いは、スーパーバイザーが受け、根拠の場所（ワークスペースの中に実在するファイル）を示せた問いだけ答える。1 問でも示せなければ、全部を上げる。（仮: 答えるのが「人」と指定された問いも、種類に当たらなければ受ける）
- **理由**: 設計書 §21.5 の歯止め。根拠の実在は、core が LLM なしで確かめられる。中身が合っているかは確かめられないので、答えた問いと根拠を記録し、完了の承認のときにオーナーへ見せる。
- **代替案**: 答えるのが「人」と指定された問いは、いまのまま、全部オーナーへ上げる。守りは強いが、J4 の実行が 0 回だった形が、そのまま残る見込みがある。

### 条件をフォローアップへ回す（`split_followup`）

- **採用案**: 回せるのは、そのタスクの完了条件に、文が一致するものだけ。全部は回せない。回した条件は、タスクにぶら下がるフォローアップとして残り、課題の完了の承認のときに、オーナーに見える。
- **理由**: 設計書 §21.5 は、この手を「オーナーに聞かずに使ってよい。条件は消えずに残るので、範囲の変更には当たらない」としている。条件の文を core が照合することで、スーパーバイザーが条件を書き換える・作ることを防ぐ。
- **代替案**: 回す前に、オーナーへ問う。反映の後でしか満たせない条件のたびに、保留が 1 回増える。

### DB スキーマ（S4a・対話の欄の次の版）

- 保留の表 `hold` に足す列: `stop_kind`（止まり方。対象でなければ NULL）、`supervisor_state`（NULL・`pending`〔スーパーバイザー待ち〕・`escalated`〔上げた〕・`handled`〔手を打って閉じた〕）、`supervisor_findings`、`supervisor_recommendation`、`deferred_cycle_id`（最後に見送ったサイクル）、`deferred_count`。
- 対処の記録の表 `supervisor_action`: `id`・`cycle_id`・`challenge_id`・`task_id`（NULL 可）・`hold_id`（NULL 可）・`run_id`（スーパーバイザーの判断の実行。起動できたとき）・`stop_kind`・`hand`（判断できなかったときは NULL）・`findings`・`note`・`basis`（JSON）・`questions`（子の問いと答え。JSON。無ければ NULL）・`result`・`created_at`。
- フォローアップの表 `followup` に足す列: `task_id`（ぶら下がるタスク。NULL 可）。出どころ（`source`）の値に `supervisor` を足す。
- 上流を読めなかった回りの数は、契約の実行の記録に足す（列 1 つ）。
- 過去の行は、書き換えない（保留の新しい列は NULL・0）。書き出しと再構築（export・import）の対象に、新しい表と列を含める。

## 機能全体の設計

### S4c との境目

- フォローアップの列 `task_id` と、出どころ `supervisor` は、S4b が足す。S4b が書くのは、`split_followup` のフォローアップだけ。
- フォローアップを、開いている課題のタスクに上げること・計画の後にタスクを足すこと・保留中の課題のほかのタスクを進めることは、S4c。S4b の保留は、いまと同じく、課題を単位に止める。
- `replan` の動きは、S4b では変えない。S4c が、計画の作り直しと、承認なしで足すタスクの形を決めたら、スーパーバイザーの手に「タスクを足す」を足すかは、S4c の仕様で決める。
- 委譲先の軽い指摘から出るフォローアップは、S4c か S5（S4b は書かない）。

### 実装計画（チケット分解の見通し）

1. 土台: マイグレーション、止まり方と手の閉じた一覧、対処の記録の API、宣言の項目、判断点 `SV` の登録と入出力の型、指示文。サイクルの中で保留を作る所の一覧。
2. スーパーバイザー待ちの印: 保留を作る所で、止まり方と回数の上限を見て、印を付ける。表示の区別（`status`・API）。「いま始められるもの」の数え。

4. `split_followup`（検証の入力の追加を含む）。
5. 子の問い（J4 の付け替え・`answer`・根拠の検査）。

## やらないこと

- 手 4「委譲先に片付けを頼んで、起動し直す」（理由: 委譲先との契約に、片付ける口が無い。オーナーの決定 2026-11-22。作業場所のぶつかりで止まったときは、ほかの止まり方と同じく、調べた内容と推奨を付けてオーナーへ上げる。claude-harness に Issue を作る）
- サイクルの終わりの振り返り、事例の記憶、改善の候補、対処の後に「進んだか」の判定、時間の集計（理由: S5）
- 予算の上限を超えた保留を、スーパーバイザーが受けること（理由: 打てる手が「上げる」だけで、数字は core が出せる。判断の費用に見合わない）
- 反映・上げる依頼・承認していない反映の検知に関わる保留を、スーパーバイザーが受けること（理由: 取り消せない操作に関わる）
- 「同じ場所で 2 回止まる」を、止まり方をまたいで検知すること（理由: 止まり方ごとの上限〔対処 2 回〕で足りる。いまある個別の上限は残す）
- スーパーバイザーに、コマンドを実行する道具や、成果物の中身を取りに行く道具を持たせること（理由: 設計書 D5・§21.5）
- 保留を、タスクの単位に下げること、保留中の課題のほかのタスクを進めること（理由: S4c）
- 計画の後に、承認なしでタスクを足すこと（理由: S4c）
- 画面の表示（スーパーバイザーが確認中の札・打った手・答えた問い）（理由: S4d-2）
- スーパーバイザーの手の一覧・止まり方・できないことを、宣言で変えられるようにすること（理由: 設計書 §21.5。変更は、課題としてオーナーの承認を通す）
- 開発に固有の知識（ブランチ・プルリクエストなど）を、core に新しく足すこと（理由: flywheel#981）

## 受入基準

特に断らない限り、テスト用の判断点（決めた出力を返す）とテスト用の委譲先で、宣言の `supervisor` は真（既定）で確かめる。「対象の保留」は、サイクルの中で core が作った、対象の止まり方の保留。

### スーパーバイザー待ちにする

- [ ] 完了の検証が「判断できない」を返した → 作られた保留の止まり方は `verify_uncertain` である。
- [ ] その保留は、スーパーバイザー待ち（`supervisor_state` が `pending`）である。
- [ ] 保留の理由が `artifact_missing` の保留の止まり方は `artifact_missing` である。
- [ ] 保留の理由が `contract_stopped` の保留の止まり方は `delegate_stopped` である。
- [ ] 保留の理由が `failure_limit` の保留の止まり方は `delegate_stopped` である。
- [ ] 保留の理由が `facts_unmet` の保留の止まり方は `facts_unmet` である。
- [ ] 保留の理由が `rework_limit` の保留の止まり方は `rework_limit` である。
- [ ] 保留の理由が `checks_failed` の保留の止まり方は `checks_failed` である。
- [ ] 判断点の連続失敗の上限で作られた保留の止まり方は `judgment_failed` である。
- [ ] 保留の理由が `delegate_ended` の保留の止まり方は `intake_unverified` である。
- [ ] 保留の理由が `merged_unverified` の保留の止まり方は `intake_unverified` である。
- [ ] 保留の理由が `integration_ref_invalid` の保留の止まり方は `intake_unverified` である。
- [ ] 予算の上限を超えた保留は、スーパーバイザー待ちにならない（`supervisor_state` が NULL）。
- [ ] 保留の理由が `unapproved_merge` の保留は、スーパーバイザー待ちにならない。
- [ ] 保留の理由が `land_refused` の保留は、スーパーバイザー待ちにならない。
- [ ] 保留の理由が `reflect_failed` の保留は、スーパーバイザー待ちにならない。
- [ ] 保留の理由が `tasks_blocked` の保留は、スーパーバイザー待ちにならない。
- [ ] 保留の理由が `challenge_check_not_met` の保留は、スーパーバイザー待ちにならない。
- [ ] 保留の理由が `blocked` の保留は、スーパーバイザー待ちにならない。
- [ ] オーナーが `flywheel hold` で作った保留は、スーパーバイザー待ちにならない。
- [ ] 宣言の `supervisor` が偽 → 完了の検証の「判断できない」の保留は、スーパーバイザー待ちにならない。
- [ ] 宣言の `supervisor` に真偽値でない値を書く → 宣言の読み込みがエラーになる。
- [ ] 宣言に `supervisor` が無い → 真として扱う。

### 回数の上限

- [ ] 同じタスクの同じ止まり方に、結果が `executed` の対処の記録が 2 件ある → 3 回目の保留は、スーパーバイザー待ちにならない。
- [ ] その保留の問いの冒頭に、スーパーバイザーが 2 回対処した旨がある。
- [ ] その保留の問いに、その 2 回の手の名前がある。
- [ ] 同じタスクの、別の止まり方の対処の記録が 2 件ある → その止まり方でない新しい保留は、スーパーバイザー待ちになる。
- [ ] オーナーが保留に回答した後は、回答より前の対処の記録を数えない（新しい保留は、スーパーバイザー待ちになる）。
- [ ] 手が `defer` の対処の記録は、2 回の上限に数えない。

### スーパーバイザーの段

- [ ] スーパーバイザー待ちの保留が 1 件あるサイクル → スーパーバイザーの判断点が 1 回呼ばれる。
- [ ] スーパーバイザー待ちの保留が 2 件 → 古い保留から順に、1 件ずつ呼ばれる。
- [ ] スーパーバイザー待ちの保留が無い回り → スーパーバイザーの判断点は呼ばれない。
- [ ] スーパーバイザーの段は、同じ回りの完了の検証の段の後に通る。
- [ ] 判断点の入力に、止まり方がある。
- [ ] 判断点の入力に、保留の問いがある。
- [ ] 判断点の入力に、そのタスクの完了条件がある。
- [ ] 判断点の入力に、その止まり方で選べる手の一覧だけがある。
- [ ] 判断点の入力に、そのタスクへのこれまでの対処の記録がある。
- [ ] 判断点に許す道具は `Read`・`Grep`・`Glob` だけである。
- [ ] 判断点の費用の上限は、宣言の `judgment_budget_usd.SV` の値である。
- [ ] 宣言に `judgment_budget_usd.SV` が無い → 3 USD である。
- [ ] 宣言に `judgment_budget_usd.J4` があっても、宣言の読み込みはエラーにならない。
- [ ] スーパーバイザーの判断点の費用は、サイクルの費用に入る。
- [ ] オーナーが先に回答した保留について、スーパーバイザーの判断点は呼ばれない。

### 手の実行

- [ ] `reverify` → 保留が閉じる（`supervisor_state` が `handled`）。
- [ ] `reverify` → 閉じた保留の `answered_by` は `supervisor` である。
- [ ] `reverify` → 課題は、保留の前の状態へ戻る。
- [ ] `reverify` の後の検証の判断点の入力に、スーパーバイザーの `findings` がある。
- [ ] `reverify` の後の検証の判断点の入力に、スーパーバイザーの `note` がある。
- [ ] `send_back` → 委譲先の続きに、`note` が指摘として渡る。
- [ ] `send_back` → そのタスクの差し戻しの回数が 1 増える。
- [ ] `retry`（委譲先の実行が終わっている）→ 次の回りで、同じタスクの実行が起動する。
- [ ] `retry`（止まり方 `judgment_failed`）→ その判断点の連続失敗の数えが 0 から始まる。
- [ ] 同じタスクの同じ止まり方に `retry` の対処の記録が 1 件ある → 次の判断点の入力の、選べる手の一覧に `retry` が無い。
- [ ] `replan` → 保留は、計画を作り直す回答と同じ印（`replan`）で閉じる。
- [ ] `replan` → 次の回りで、計画の判断点が呼ばれる。
- [ ] `replan` の後の計画の判断点の入力に、スーパーバイザーの `note` がある。
- [ ] `replan` で作り直した計画は、計画の承認待ちになる（承認なしで起動しない）。
- [ ] `defer` → 保留は、スーパーバイザー待ちのまま残る。
- [ ] `defer` → 同じサイクルの後の回りで、その保留についてスーパーバイザーの判断点は呼ばれない。
- [ ] `defer` → 次のサイクルで、その保留についてスーパーバイザーの判断点が呼ばれる。
- [ ] 同じ保留に `defer` が 3 サイクル続いた → 4 回目のサイクルでは、判断点を呼ばず、保留が「上げた」（`escalated`）になる。
