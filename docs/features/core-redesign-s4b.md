# core の見直し 区切り S4b — スーパーバイザーのその場の対処

## 概要

`docs/features/core-redesign.md` の区切り S4b の仕様。S4a（長く走るサイクル）の実装の間に書くので、その間だけ別の文書に書き、main に入れた後に `core-redesign.md` へ畳む（S3d・S4d と同じ進め方。オーナーの決定 2026-11-22）。

S4b は、設計書 §21.5 のスーパーバイザーの出番のうち「その場の対処」を入れる。サイクルの途中でタスクが想定外に止まったとき、いまは保留にしてオーナーへ上げる。S4b からは、スーパーバイザー（読み取りの道具だけを持つ判断点）が先に調べ、core が用意した手の一覧から 1 つ選ぶ。選んだ手を実行するのは core。委譲先からの問い（子の問い）も、スーパーバイザーが受ける（子の問いに答える判断点〔J4〕を、スーパーバイザーにまとめる。設計書 §21.6）。

サイクルの終わりの振り返り（出番 2）は S5。

> **仮の決定の印**: 本文で「（仮）」と書いた所は、オーナーに伺う前の推奨案で書いている。伺う点は、PR の説明に並べる。
>
> **「最初の Issue で確かめる」の印**: 仕様を書くときに実物のコードで確かめ切れなかった点。最初の実装の Issue で確かめ、食い違えば、仕様を変えずに PR の説明へ「仕様への指摘」として書く。

## 背景・目的

- 測った期間に、サイクルの途中でオーナーへ上がった問い 117 件のうち、スーパーバイザーが引き受けられるものが約 45 件あった（委譲先の失敗・中止 18、自己レビューが不明 15、成果物の中身を読めない 9、成果物が見つからない 3。設計書 §21.5）。いまは、想定外のことが起きると「同じことをやり直す」か「オーナーへ上げる」しか無い。
- 子の問いに答える判断点（J4）は、実行の記録が 0 回だった（設計書 §21.6）。オーナーへの問い（保留）は 470 件で、回答待ちは、委譲で完了した課題の時間の 40% だった（設計書 §21.0）。
- S4a で、サイクルは、進められるものが無くなるまで回りを繰り返す。保留がオーナーへ上がると、その課題はオーナーの回答まで止まる。スーパーバイザーが先に受ければ、同じサイクルの中で続きを進められる。

## ユーザーストーリー

オーナーとして、委譲先の一時的な失敗や、調べれば分かる食い違いのたびに呼ばれたくない。自分に上がってくる問いには、何が起きたか・何を調べたか・どうするのがよいかが、付いていてほしい。スーパーバイザーが自分の代わりに決めたことは、後から全部見たい。

## 機能要件

語は `docs/glossary.md` に合わせる。この文書では、次の語を使う。

- **止まり方**: スーパーバイザーを呼ぶきっかけの種類。下の「対象の止まり方」の閉じた一覧。
- **対処**: スーパーバイザーの判断 1 回と、core がその手を実行した結果。1 件ずつ記録する（対処の記録）。
- **スーパーバイザー待ちの保留**: core が作った保留のうち、オーナーより先にスーパーバイザーが見るもの。
- **オーナーへ上げる**: 保留を、オーナーの回答を待つ保留にする（スーパーバイザー待ちだった保留は、`supervisor_state` を `escalated` にする）。
- **最後のオーナーの回答**: その課題の、回答した者が `supervisor` でない回答済みの保留の、最大の回答時刻。回数の数えは、これより後の対処の記録だけを数える。

### スーパーバイザーを呼ぶとき

- [ ] サイクルの進める段の最後に、スーパーバイザーの段（`supervise`）を足す。回りごとに 1 回通る（S4a の回りの中。完了の検証の段の後）。
- [ ] 止まり方（`stop_kind`）は、保留の理由から導かず、保留を作る呼び出し元が渡す。保留を作る共通の関数（`insertHoldKindFromTask`）が、止まり方を受け取り、下の「回数の上限」の判定と、スーパーバイザー待ちの印と、問いの冒頭への付け足しを、1 か所で行う。
- [ ] core が、サイクルの中で、対象の止まり方を渡して保留を作るとき、その保留を「スーパーバイザー待ち」にする（保留の行の `supervisor_state` を `pending` にする。課題の状態の遷移は、いまの保留と同じ）。
- [ ] 対象の止まり方（閉じた一覧）と、止まり方を渡す呼び出し元は、次のとおり。「いまの保留の理由」は参考の列（理由の値は、止まり方の判定に使わない。保留の行に理由を書かない理由もある）。

| 止まり方 | 起きること | 止まり方を渡す呼び出し元 | いまの保留の理由（参考） |
|---|---|---|---|
| `verify_uncertain` | 完了の検証・タスクの検証が「判断できない」を返した | 完了の検証の「判断できない」の保留（`judgment_j5.go`）、タスクの検証の「判断できない」の保留（`judgment_j5_task.go`） | なし |
| `artifact_missing` | 成果物が見つからない | 委譲の報告の照合で、成果物が見つからない保留（`delegate_reconcile.go`・`delegate_reconcile_retry.go`） | `artifact_missing` |
| `delegate_stopped` | 委譲先の実行が失敗・中止で終わった、委譲の連続の失敗が上限に達した | 契約の実行の終わり・回収の保留（`holdContractWithReason` に `contract_stopped` を渡す所）、委譲の連続失敗の保留（`holdForFailureLimit`） | `contract_stopped`・`failure_limit` |
| `facts_unmet` | 委譲先が返す値が、宣言の求める値を満たさないレビュー待ちが 2 回続いた | レビュー待ちの受け取り（`contract_review_intake.go`） | `facts_unmet` |
| `rework_limit` | 差し戻しが上限に達した。タスクの検証の連続の「満たしていない」が上限に達した（下の「S3b で残した点」） | 委譲の差し戻しの上限の保留（`holdForReworkLimit`・レビュー待ちへの返しの上限）、タスクの検証の連続の上限の保留（新設） | `rework_limit` |
| `checks_failed` | 検証した中身の確かめに失敗がある | 統合先へ入れる処理（`integration_land.go`） | `checks_failed` |
| `judgment_failed` | 判断点（分類・計画・完了の検証）の失敗・不正な出力が、連続の上限に達した | 判断点の連続失敗の保留（`holdForJudgmentFailureLimit`） | `failure_limit` |
| `intake_unverified` | 統合先を使う課題で、タスクの成果を受け取れない（成果物が統合先へ入らないまま実行が終わった・検証を経ずに入っていた・統合先の識別が合わない） | 統合先のタスクの受け取り（`contract_delegate_after.go`・`contract_review_intake.go` の、理由 `delegate_ended`・`merged_unverified`・`integration_ref_invalid` を渡す所） | `delegate_ended`・`merged_unverified`・`integration_ref_invalid` |
| `upstream_unreadable` | 「入れてよい」を返した後、上流を読めない回りが 3 回続いた（下の「S3b で残した点」） | 新設 | （新設） |
| `child_question` | 委譲先からの問い（下の「子の問い」。答えたときは保留を作らない。上げるときだけ、この止まり方の保留を作る） | 委譲の報告の問い（`delegate_reconcile.go`）、契約の判断待ち（`contract_delegate_after.go`） | `questions`・`contract_stopped` |

- [ ] 止まり方を渡さない保留は、対象にしない（はじめからオーナーへ上がる。`supervisor_state` は NULL）。対象にしない保留を作る呼び出し元は、次のとおり。
  - 分類の判断点・計画の判断点が作る保留（`judgment_j1.go`・`judgment_j2.go` の問い。計画の判断点が立てる、対話のセッションが引き取る保留〔`parent_direct`〕を含む）
  - 完了の検証が、実物の食い違いで作る保留、人の操作の後でしか満たせない条件・反映が無くて満たせない条件で作る保留（`judgment_j5.go`）
  - 課題の単位の確かめが「満たしていない」だった保留（`challenge_check_not_met`）
  - 予算の上限を超えた保留（（仮）下の「やらないこと」）
  - 承認していない反映の検知（`unapproved_merge`）
  - 反映・上げる依頼に関わる保留（`land_unavailable`・`content_ref_invalid`・`land_refused`・`reflect_unavailable`・`reflect_failed`。「入れてよい」の後に実行が終わった・止まった保留〔`integration_land.go` の `holdLandedEnd`〕を含む）
  - 前提のタスクの取りやめで進めようが無い保留（`tasks_blocked`）
  - 委譲先が「進められない」と返した保留（`blocked`）
  - 契約の判断待ちのうち、承認の待ち（`approve`）、ターミナルで人が解く待ち（`resolvable_by` が `terminal`）、成果物の無いレビューの待ち
  - 保留の間に成功した、統合先を使う課題の実行の保留（`holdIntegrationSucceeded`。最初の Issue で、中身を確かめる）
  - オーナーが自分で作った保留（`flywheel hold`）、差し戻しのときに立つ、対話のセッションが引き取る保留（`parent_direct`）
- [ ] 最初の Issue で、サイクルの中で保留を作る所（`insertHold`・`insertHoldKind`・`insertHoldWithOccurrence` の系の呼び出し元）を全部一覧にし、上の 2 つの一覧のどちらにも無い呼び出し元は、対象にしない側に置く（止まり方を渡さない）。

#### 回数の上限

- [ ] 同じタスク（タスクの無い保留は、同じ課題）の、同じ止まり方への対処は、2 回まで。数えるのは、その課題の、最後のオーナーの回答より後の、手が `defer`・`escalate`・`answer` でなく、結果が `executed` の対処の記録。
- [ ] 上の数えが 2 件ある止まり方の、次の保留は、スーパーバイザー待ちにしない（`supervisor_state` は NULL。`stop_kind` は記録する）。問いの冒頭に「スーパーバイザーが 2 回対処したが、進まなかった」旨と、その 2 回の手の名前を付けて、オーナーへ上げる。
- [ ] 子の問い（`child_question`）は、2 回の上限の対象にしない（別々の問いは「同じ止まり方」ではないため）。子の問いは、下の「答えによる再開は 3 回まで」だけで止める。

#### スーパーバイザーの段

- [ ] スーパーバイザーの段は、スーパーバイザー待ちの保留を、古い順に 1 件ずつ処理する。1 件ごとに、スーパーバイザーの判断点を 1 回呼ぶ。
- [ ] オーナーは、スーパーバイザー待ちの保留にも、いまと同じ操作（`flywheel answer`）で回答できる。回答済みの保留を、スーパーバイザーの段は処理しない。
- [ ] 宣言（`agent.json`）の `supervisor`（真偽。既定は真）が偽のとき、保留をスーパーバイザー待ちにしない（S4a までと同じ動き。子の問いは、下の「子の問い」の「偽のとき」）。（仮: 切る設定を置くこと）
- [ ] 段の差し込み位置（回りの中の、完了の検証の段の後）は、S4a が main に入った後で、実物の段の一覧に合わせて確かめ直す。

### スーパーバイザーの判断点

- [ ] スーパーバイザーの判断点（記録上の名前は `SV`）は、ほかの判断点と同じ呼び出し（`internal/invoker`。読み取りの道具〔`Read`・`Grep`・`Glob`〕だけ。作業ディレクトリはワークスペース）で呼ぶ。コマンドを実行する道具を持たない。
- [ ] 入力に渡すもの: 止まり方、保留の問い、課題とタスクの題名、タスクの完了条件（1 から始まる番号つき）、計画の方針、そのタスクの実行の記録（状態・要約・委譲先が返した値・成果物の識別。直近 5 件）、そのタスクへのこれまでの対処の記録、選べる手の一覧、記憶の索引の場所。
- [ ] 選べる手の一覧は、下の「止まり方ごとに選べる手」の表から、いまの状態では実行できない手を core が外したもの（下の「事前に外す手」）。
- [ ] 出力（型つき）: `hand`（選べる手の 1 つ）、`findings`（調べたこと。必須）、`note`（手に添える文。手ごとの必須は下）、`basis`（根拠の場所の配列。要素は `path` と `locator`〔節や行の手がかり〕）、`recommendation`（オーナーへ上げるときの推奨。`escalate` のとき必須）、`conditions`（フォローアップへ回す完了条件の番号の配列。`split_followup` のとき 1 件以上）、`answers`（子の問いへの答えの配列。`answer` のとき、問いの数と同じ件数）。
- [ ] 費用の上限は、宣言の `judgment_budget_usd.SV`（（仮）既定 3 USD）。時間の上限は、ほかの判断点と同じ（`timeout_sec.judgment`）。
- [ ] スーパーバイザーの判断点の費用は、判断点の費用として、課題の費用に入る。
- [ ] スーパーバイザーの判断点の費用は、サイクルの費用に入る。
- [ ] 指示文 `sv.md` を足す。書くこと: できないこと（承認・反映・取り下げ・予算の増額・範囲の変更・成果物の手直し）、手の選び方、根拠を示せないときは上げること、調べる範囲（ワークスペースの中の文書・記憶・コード。成果物の中身は、入力に渡した識別と要約まで）、子の問いの歯止め（下の「子の問い」）。開発に固有の語を書かない（禁止語の照合を通す）。

### 手の一覧

- [ ] 手は、次の 8 つ（閉じた一覧）。設計書 §21.5 の手 4（委譲先に片付けを頼んで、起動し直す）は、入れない（オーナーの決定 2026-11-22。下の「やらないこと」）。

| `hand` | 手 | core がすること | 必須の出力 |
|---|---|---|---|
| `reverify` | 調べた結果を添えて、検証（受け取り）をやり直す | 保留を閉じ、保留の直前の状態へ戻す。保留の回答の文に、`findings` と `note` を「スーパーバイザーが調べた結果」として書く | `note` |
| `send_back` | 添え書きを付けて、委譲先へ差し戻す | 保留を閉じ、`note` を指摘として、いまある差し戻しの道へ渡す。差し戻しの回数に数える | `note` |
| `retry` | 同じ入力でやり直す | 保留を閉じ、保留の直前の状態へ戻す。連続の失敗の数えを、あと 1 回だけ起動できる値（上限 − 1）に戻す。委譲先の実行が終わっていれば、次の回りで、同じタスクを起動し直す | なし |
| `split_followup` | 残った条件をフォローアップへ回して、ほかの条件で判定する | `conditions` の番号 1 件ごとに、そのタスクにぶら下がるフォローアップを作る（出どころは `supervisor`。題名は、その番号の完了条件の文）。保留を閉じ、保留の直前の状態へ戻す。次の検証の入力に「フォローアップへ回した条件（判定から外す）」として渡す | `note`・`conditions` |
| `replan` | 計画を作り直す | 保留を、計画を作り直す回答（`--replan`）と同じ印で閉じる（次の回りで計画の判断点が作り直し、計画の承認待ちへ戻る。承認するのはオーナー）。保留の回答の文に `note` を書く | `note`（作り直す理由） |
| `defer` | このサイクルでは見送る | 保留は、スーパーバイザー待ちのまま残す。このサイクルでは、もう処理しない | `note`（何を待つか） |
| `escalate` | 調べた内容と推奨を付けて、オーナーへ上げる | 保留を「オーナーへ上げた」（`escalated`）にし、`findings` と `recommendation` を保留に残す | `recommendation` |
| `answer` | 根拠を示して、子の問いに答える | 下の「子の問い」 | `answers`（問いごとに `basis` 1 件以上） |

#### 事前に外す手

- [ ] `retry` は、同じタスクの同じ止まり方に、1 回まで。最後のオーナーの回答より後に、結果が `executed` の `retry` の対処の記録が 1 件あれば、選べる手の一覧から `retry` を外して渡す。
- [ ] `replan` は、いまの状態では受けられないとき、選べる手の一覧から外して渡す。外す条件は、いまの「計画を作り直す回答」が断る条件と同じ: 作業している契約の実行がある（開いていて、最後に読んだ状態が実行中のタスクの実行・「入れてよい」を返そうとして届いたか分からない実行・保留の間の成功が未処理の実行）、または、保留の直前の状態が着手中・検証中でない。
- [ ] `rework_limit` の `send_back` は、上限の後の 1 回だけの差し戻しになる（対処の上限 2 回のうちの 1 回）。

#### 手の実行（戻す先と、文が渡る入口）

- [ ] 保留を閉じる手（`reverify`・`send_back`・`retry`・`split_followup`・`replan`）は、いまの保留の回答の処理の中身（保留を読む・回答の列を書く・`facts_unmet` の数えを戻す・統合先のタスクの再開・作り直しのときの検査）を、本人確認を取らない内部の関数へ切り出したものを、判断点の行為者の遷移（`transitionAsInvoker`）で呼ぶ。オーナーの回答（`ExecuteAnswer`）は、本人確認の検査の後に、同じ内部の関数を呼ぶ。本人確認の登録簿（`verificationRegistry`）は変えない。
- [ ] 閉じた保留の回答の文は、core が、手の名前・`findings`・`note` から組み立てる（スーパーバイザーの出力を、そのまま保留の回答にしない）。
- [ ] 手ごとの、戻す先・次に呼ばれるもの・文が渡る入口は、次のとおり。

| 手 | 戻す先の状態 | 次に呼ばれるもの | `findings`・`note`・条件の番号が渡る入口 |
|---|---|---|---|
| `reverify` | 保留の直前の状態（`hold.from_status`）。`verify_uncertain` は検証中、`artifact_missing`・`intake_unverified` は着手中 | オーナーが回答したときと同じ処理。検証中へ戻れば、次の回りの検証の判断点。着手中へ戻れば、次の回りの成果物の照合・統合先のタスクの受け取り直し（`resumeIntegrationTaskAfterAnswer`） | 保留の回答の文。判断点の入力の「保留の記録」の区画（`formatHoldsSection`。完了の検証・計画・分類・委譲の入力が読む）が、問いと回答を渡す。タスクの検証の入力がこの区画を読むかは、最初の Issue で確かめ、読まなければ足す |
| `send_back` | 着手中 | 検証の判断点が「満たしていない」を返したときと同じ差し戻しの道。契約のレビュー待ちの実行には、レビュー待ちへの返し（`pendingReviewReply`・`respondToReview`）が、指摘を返す。委譲の報告の形の実行には、次の起動の入力が渡す | `note` を、差し戻しの指摘として、差し戻しの道が読む所へ書く（指摘の置き場と、実行がすでに終わっているときの入口は、最初の Issue で確かめる。入口が無い止まり方では、`send_back` を事前に外す） |
| `retry` | 保留の直前の状態 | オーナーが回答したときと同じ処理。委譲先の実行が終わっていれば、次の回りの委譲の段が、同じタスクを起動する。`judgment_failed` は、次の回りで、同じ判断点 | 渡さない（保留の回答の文には、`findings` が残る） |
| `split_followup` | 保留の直前の状態（検証中） | 次の回りの検証の判断点 | 保留の回答の文と、対処の記録の `conditions`。検証の判断点の入力を作る所が、そのタスクの、最後のオーナーの回答より後の、結果が `executed` の `split_followup` の対処の記録を引き、「フォローアップへ回した条件（判定から外す）」の区画として渡す |
| `replan` | いまの `--replan` の回答と同じ（計画の作り直しへ） | 次の回りの計画の判断点 | 保留の回答の文（計画の判断点の入力の「保留の記録」の区画） |

- [ ] 保留の行は、その保留を閉じた・上げた対処の記録を指す（`hold.supervisor_action_id`）。

#### 出力の不備と、実行できない状態

- [ ] 出力が、型・規則に反するときは、手を実行せず、「スーパーバイザーが判断できなかった」旨を付けて、オーナーへ上げる（やり直さない）。対処の記録の結果は `failed`。当たるのは: 判断点の失敗、不正な出力、費用の上限、時間の上限、閉じた一覧に無い `hand`、入力に渡した一覧に無い `hand`、`findings` が空、手ごとの必須の出力（`note`・`recommendation`・`answers`・`basis`）の欠け、`conditions` の不正（空・範囲外の番号・完了条件の全部）、`answers` の不正（件数が合わない・選択肢に無い値・根拠の検査に落ちた）。
- [ ] 出力は正しいが、手を実行する時点の状態では実行できないとき（判断の間に、状態が変わった）は、手を実行せず、`findings` を付けて、オーナーへ上げる。対処の記録の結果は `rejected`。
- [ ] 利用上限・サイクルの費用の上限で、スーパーバイザーの判断点を起動できなかった保留は、スーパーバイザー待ちのまま残す（対処の記録を作らない）。

#### 閉じた保留の記録

- [ ] スーパーバイザーが閉じた保留の、回答した者（`answered_by`）は `supervisor`。
- [ ] スーパーバイザーが閉じた保留の、経路（`answered_channel`）は `invoker`。
- [ ] スーパーバイザーが閉じた保留の、本人確認（`answered_verification`）は `none`。
- [ ] スーパーバイザーが閉じた保留は、オーナーの回答として数えない: 「最後のオーナーの回答」に入らない。計画の承認・完了の承認・不可逆操作の承認の記録を作らない。

### 子の問い

- [ ] 委譲先からの問いは、子の問いに答える判断点（J4）ではなく、スーパーバイザーが受ける。J4 の新しい呼び出しと、指示文 `j4.md` は外す。J4 の定数と、過去の J4 の実行の記録の読み取りは残す。
- [ ] 子の問いは、保留を作る前に、スーパーバイザーの判断点を呼ぶ（いまの J4 と同じ位置。段の中で呼び、スーパーバイザーの段を待たない）。止まり方は `child_question`。記録・費用の決まりは、ほかの止まり方と同じ。回数は、下の「答えによる再開」だけで止める。
- [ ] 呼び出し元は 2 か所で、それぞれ次のとおり。

| | 委譲の報告の問い（結末が「問い」の報告。`routeQuestionsToJ4` の位置） | 契約の判断待ち（`answerParentWait` の位置） |
|---|---|---|
| 問いの数 | 1 件以上 | 1 件 |
| スーパーバイザーへ回す条件 | 問いの種類が、接続の宣言の「人に聞く種類」（`human_question_kinds`）に 1 件も当たらない。委譲の意思決定者が「人」でも、回す（オーナーの決定 2026-11-22） | 求めが「回答」（`answer`）で、ターミナルで人が解く待ちでない。答える者が「親」でも「人」でも「どちらでも」でも、回す（「人」も回すのは、オーナーの決定 2026-11-22）。（仮）契約の求めは、問いの種類の値を持たないので、「人に聞く種類」の照合は行えない。歯止めは、指示文と、根拠の検査 |
| 回さないもの | 「人に聞く種類」に当たる問いを 1 件でも含む報告（全部の問いを、いまと同じ保留にして、オーナーへ上げる） | 承認の待ち・ターミナルで人が解く待ち・成果物の無いレビューの待ち（いまと同じ保留。対象外） |
| 答えたとき | いまの J4 と同じ返し方（保留を作らず、次の起動が答えを渡して再開する） | 宣言の `resume` で答えを返す（選択肢があれば選んだ選択肢、無ければ文）。保留を作らない |
| 再開の引数を埋められなかったとき | （当たらない） | 委譲先へ返さず、理由を問いの冒頭に付けて、オーナーへ上げる。対処の記録の結果は `failed` |
| いまの旗 | J4 の環境（`j4Env`）を、スーパーバイザーの環境に替える | `contractReleaseSource` の旗 `J4` を、「スーパーバイザーへ回せるか」（判断の呼び出しが渡されていて、宣言の `supervisor` が真）に読み替える。偽なら、いまと同じくオーナーの保留 |

- [ ] `answer` の出力の `answers` は、問いごとに、選んだ選択肢（選択肢がある問い）か回答の文（無い問い）と、`basis`（1 件以上）を持つ。
- [ ] 根拠の検査: core は、`basis` の各 `path` について、リンクを解決した後の場所が、ワークスペースの根の下の通常のファイルであることを確かめる。ワークスペースの外・ディレクトリ・ストアの置き場（`.flywheel/`）の下・存在しない場所は、根拠として数えない。根拠として数えられる `basis` が 1 件も無い問いがあれば、出力の不備（`failed`）として、その報告の問い全部を、オーナーへ上げる。
- [ ] 全部の問いに答えたときだけ、委譲先へ答えを返して再開する。スーパーバイザーが `escalate` を選んだときは、全部の問いを 1 つの保留にして、オーナーへ上げる（答えられる問いの答えの案と根拠は、`findings` に書かせ、保留に残す）。
- [ ] 答えによる再開は、1 つの課題で、最後のオーナーの回答より後に、3 回まで（いまの J4 の上限のまま）。数えるのは、その課題の、手が `answer` で結果が `executed` の対処の記録。過去の J4 の実行は数えない。
- [ ] 上の数えが 3 件あるときの子の問いは、スーパーバイザーの判断点を呼ばず、問いの冒頭に「スーパーバイザーが答えて再開できる回数の上限（3 回）に達した」旨を付けた保留にして、オーナーへ上げる（対処の記録は作らない）。
- [ ] 上げるときに作る保留は、止まり方が `child_question`、`supervisor_state` が `escalated`（判断点を呼ばずに上げたときは NULL）。
- [ ] 指示文に書く歯止め: 範囲・完了条件・予算を変える問い、好みを問う問い、取り消せない操作に関わる問いは、必ず上げる。
- [ ] 宣言の `supervisor` が偽のとき、子の問いは、すべて保留にして、オーナーへ上げる（J4 は戻さない）。

### オーナーへ上げるとき

- [ ] スーパーバイザーが上げた保留には、調べたこと（`findings`）と推奨（`recommendation`）が付く。`flywheel show <課題>`・`flywheel status` の保留の表示に出す。
- [ ] API の保留の値に、`stop_kind`・`supervisor_state`・`findings`・`recommendation` を出す。
- [ ] 上げた保留は、いまの保留と同じ操作で回答できる。回答の後の動きは、いまと同じ。
- [ ] （仮）スーパーバイザー待ち（`pending`）の保留だけを持つ課題は、オーナー待ちに数えない。
- [ ] （仮）`flywheel status` は、「スーパーバイザーが確認中」として、件数と課題を、オーナー待ちと別に出す。
- [ ] （仮）状況の API の値も、スーパーバイザーが確認中の課題を、オーナー待ちと別に持つ。
- [ ] サイクルが走っていない間に残っているスーパーバイザー待ちの保留（見送り・起動できなかったもの）は、S4a の「いま始められるもの」に数える（次のサイクルで処理できる）。
- [ ] 見送った保留は、見送ったサイクル（`deferred_cycle_id`）が、いまのサイクルと同じ間、処理しない。そのサイクルの回りの終わりの数えにも入れない（見送りだけで回りを続けない）。
- [ ] 見送り（`defer`）が、同じ保留に 3 サイクル続いたら（`deferred_count` が 3）、次のサイクルでは、スーパーバイザーを呼ばず、オーナーへ上げる。連続の数えは、見送ったサイクルごとに 1 増える（サイクルが走らない間は、進まない）。

### 記録と表示

- [ ] 対処は、1 件ずつ記録する（対処の記録）。持つ値: サイクル、課題、タスク（あれば）、保留（子の問いに答えて保留を作らなかったときは無し）、スーパーバイザーの判断の実行、止まり方、手、調べたこと、添えた文、根拠、条件の番号、結果（`executed`・`rejected`・`failed`）、時刻。子の問いのときは、問いと答えも持つ。
- [ ] 作業ログに、対処を 1 行で残す（行為者は `invoker`。操作の種類は `supervise`）。
- [ ] `flywheel show <課題>`（テキストと `--json`）と、課題の詳細の API に、その課題の対処の記録（`supervisor_actions[]`）を、古い順に出す。
- [ ] 完了の承認待ちの課題の要約（`flywheel show`・承認待ちの API）に、「スーパーバイザーが答えた子の問い」（問い・答え・根拠）を出す。
- [ ] 完了の承認待ちの課題の要約に、「打った手」の件数を出す。
- [ ] `flywheel cycle` の出力の段（`phases`）に `supervise` を足し、処理した件数・手ごとの件数を出す。
- [ ] 画面の表示は、S4d-2（この区切りでは、型と偽のデータの追従だけ）。

### S3b で残した点

`core-redesign.md` が「S4b で、スーパーバイザーの手と一緒に決める」とした 4 点。

- [ ] **タスクの検証の、連続の「満たしていない」の上限**: タスクに、検証の連続の「満たしていない」の数え（`task.verify_not_met_streak`）を持つ。タスクの検証が「満たしていない」を返すたびに 1 増やし、「満たした」で 0 に戻す。数えが、宣言の差し戻しの上限（`rework_limit`。既定 3）に達したら、差し戻さず、止まり方 `rework_limit` の保留にする（スーパーバイザー待ち）。いまある委譲の差し戻しの回数とは、別の数え。
- [ ] スーパーバイザーの `send_back` は、いまある委譲の差し戻しの回数に数える（タスクの検証の連続の数えには、数えない）。
- [ ] **「入れてよい」の後、上流を読めない状態が続く**: 「入れてよい」を返した実行について、上流を読めなかった回りを数える（契約の実行の記録の列）。3 回続いたら、止まり方 `upstream_unreadable` の保留にする（スーパーバイザー待ち）。読めた回りで、0 に戻す。実行は取り消さない。いまある、読めなかった回数の数えとの関係は、最初の Issue で確かめる。
- [ ] **統合先へ入ったかの確かめが、成果物の形に頼る**: 確かめの作りは、変えない（開発に固有の知識を、core に足さない）。確かめられずに保留になるとき（`intake_unverified`）、スーパーバイザーが調べて、受け取りのやり直しか、見送りか、上げるかを選ぶ。
- [ ] **終わりを記録した実行があるときの、計画の作り直し**: この区切りでは、スーパーバイザーの `replan` を、いまの「計画を作り直す回答」と同じ動きにする（動きは変えない）。作り直しのときに、終わった実行を持つタスクをどう残すかは、S4c（計画の後にタスクを足す）で決める。

## クリティカル設計決定

### 承認の真正性: スーパーバイザーは、保留を「閉じる」ことはできるが、承認はできない

- **採用案**: スーパーバイザーが閉じられるのは、core がサイクルの中で、対象の止まり方を渡して作った保留だけ。保留を閉じる手は 5 つ（`reverify`・`send_back`・`retry`・`split_followup`・`replan`）。`answer` だけは、保留を作る前の委譲先の問いに答える（閉じる保留は無く、動きは、いまの J4 の再開と同じ）。どの手も、計画の承認・完了の承認・不可逆操作の承認・予算の増額・取り下げを、通らない。`replan` は、計画の承認待ちへ戻るので、作り直した計画を承認するのはオーナー。閉じた者は `supervisor` と記録し、オーナーの回答（本人確認つき）と区別する。
- **実装の形**: 保留の回答の処理の中身を、本人確認を取らない内部の関数へ切り出し、スーパーバイザーの手は、それを判断点の行為者の遷移で呼ぶ。本人確認の登録簿に、（判断点・本人確認なし）の組を足さない（人の本人確認つきの操作の入口に、人でない行為者を通さない。D11 を変えない）。
- **理由**: 設計書 D27・§21.5 の「できないこと」。保留の回答は、いまは本人確認つきの操作（D11）だが、対象の保留は、core が自分で作った「進め方」の保留で、回答で起きることは、いまもサイクルの中で core が自分で行っている動き（検証・差し戻し・起動）に限られる。
- **代替案**: (a) 本人確認の登録簿に（判断点・本人確認なし）を足して、`ExecuteAnswer` をそのまま呼ぶ。D11 の変更になるので採らない。(b) スーパーバイザーの手を、保留を作る前に呼ぶ（保留を作らない）。止まる所ごとに、呼び出しと戻り先を作ることになり、遷移が増える。保留を経由すれば、いまの遷移と、オーナーが割り込む口（回答）を、そのまま使える（子の問いだけは、いまの J4 が保留の前に呼ばれているので、その位置を引き継ぐ）。

### 子の問いに答える範囲

- **採用案**: 必ず上げる種類（接続の宣言の一覧）に当たる問いは、スーパーバイザーを呼ばない。ほかの問いは、答える者が「人」と指定されていても、スーパーバイザーが先に受け（オーナーの決定 2026-11-22）、根拠の場所（ワークスペースの根の下の通常のファイル）を示せた問いだけ答える。1 問でも示せなければ、全部を上げる。（仮）契約の判断待ちは、問いの種類の値を持たないので、種類の照合なしで受ける。
- **理由**: 設計書 §21.5 の歯止め。根拠の実在は、core が LLM なしで確かめられる。中身が合っているかは確かめられないので、答えた問いと根拠を記録し、完了の承認のときにオーナーへ見せる。
- **代替案**: 答えるのが「人」と指定された問いは、いまのまま、全部オーナーへ上げる。守りは強いが、J4 の実行が 0 回だった形が、そのまま残る見込みがある。契約の判断待ちについては、答える者が「人」のものだけは受けない形もある（種類を照合できない分を、指定で補う）。

### 条件をフォローアップへ回す（`split_followup`）

- **採用案**: 回す条件は、入力に付けた完了条件の番号で返させる。番号が範囲外・空・全部のときは、実行しない。回した条件は、タスクにぶら下がるフォローアップ（題名は、core が番号から引いた条件の文）として残り、課題の完了の承認のときに、オーナーに見える。
- **理由**: 設計書 §21.5 は、この手を「オーナーに聞かずに使ってよい。条件は消えずに残るので、範囲の変更には当たらない」としている。番号で返させることで、スーパーバイザーが条件を書き換える・作ることを防ぎ、文の言い換えによる照合のぶれも無くす。
- **代替案**: (a) 条件の文を返させて、core が文の一致で照合する。言い換えで落ちる。(b) 回す前に、オーナーへ問う。反映の後でしか満たせない条件のたびに、保留が 1 回増える。

### DB スキーマ（S4a・対話の欄の次の版）

- 保留の表 `hold` に足す列: `stop_kind`（止まり方。渡されなければ NULL）、`supervisor_state`（NULL・`pending`〔スーパーバイザー待ち〕・`escalated`〔上げた〕・`handled`〔手を打って閉じた〕）、`supervisor_findings`、`supervisor_recommendation`、`supervisor_action_id`（その保留を閉じた・上げた対処の記録。無ければ NULL）、`deferred_cycle_id`（最後に見送ったサイクル）、`deferred_count`（見送りの連続の数え。既定 0）。
- 対処の記録の表 `supervisor_action`: `id`・`cycle_id`・`challenge_id`・`task_id`（NULL 可）・`hold_id`（NULL 可）・`run_id`（スーパーバイザーの判断の実行。起動できたとき）・`stop_kind`・`hand`（判断できなかったときは NULL）・`findings`・`note`・`basis`（JSON）・`conditions`（回した完了条件の番号と文。JSON。無ければ NULL）・`questions`（子の問いと答え。JSON。無ければ NULL）・`result`・`created_at`。
- フォローアップの表 `followup` に足す列: `task_id`（ぶら下がるタスク。NULL 可）。出どころ（`source`）の値に `supervisor` を足す。
- タスクの表 `task` に足す列: `verify_not_met_streak`（タスクの検証の連続の「満たしていない」の数え。既定 0）。
- 上流を読めなかった回りの数は、契約の実行の記録に足す（列 1 つ。既定 0）。
- 検証の入力へ結ぶ持ち方: `reverify`・`replan` の文は、保留の回答の文（いまの「保留の記録」の区画）。`split_followup` の判定から外す条件は、対処の記録の `conditions`（タスクと、最後のオーナーの回答より後で引く）。
- 過去の行は、書き換えない（新しい列は NULL・0）。書き出しと再構築（export・import）の対象に、新しい表と列を含める。

## 機能全体の設計

### S4c との境目

- フォローアップの列 `task_id` と、出どころ `supervisor` は、S4b が足す。S4b が書くのは、`split_followup` のフォローアップだけ。
- フォローアップを、開いている課題のタスクに上げること・計画の後にタスクを足すこと・保留中の課題のほかのタスクを進めることは、S4c。S4b の保留は、いまと同じく、課題を単位に止める。
- `replan` の動きは、S4b では変えない。S4c が、計画の作り直しと、承認なしで足すタスクの形を決めたら、スーパーバイザーの手に「タスクを足す」を足すかは、S4c の仕様で決める。
- 委譲先の軽い指摘から出るフォローアップは、S4c か S5（S4b は書かない）。

### 実装計画（チケット分解の見通し）

1. 土台: マイグレーション、止まり方と手の閉じた一覧、対処の記録の API、宣言の項目、判断点 `SV` の登録（上の「`SV` を足す一覧」）と入出力の型、指示文。サイクルの中で保留を作る所の一覧と、「最初の Issue で確かめる」とした点の確かめ。
2. スーパーバイザー待ちの印: 保留を作る共通の関数で、止まり方と回数の上限を見て、印を付ける。表示の区別（`status`・API）。「いま始められるもの」の数え。
3. 保留の回答の処理の切り出しと、スーパーバイザーの段、手の実行（`reverify`・`send_back`・`retry`・`replan`・`defer`・`escalate`）。
4. `split_followup`（検証の入力の追加を含む）。
5. 子の問い（J4 の付け替え・`answer`・根拠の検査）。
6. S3b で残した点（タスクの検証の上限・上流を読めない回りの数え）。
7. 表示（`show`・`cycle` の出力・承認待ちの要約・API の型）と文書。

順は、1 → 2 → 3 →（4・5・6 は並べられる）→ 7。

費用の見込み（実装の分）: 3・5 が各 20〜30 USD、2・4・6・7 が各 10〜18 USD、1 が 8〜14 USD。合計は約 90〜140 USD。

## やらないこと

- 手 4「委譲先に片付けを頼んで、起動し直す」（理由: 委譲先との契約に、片付ける口が無い。オーナーの決定 2026-11-22。作業場所のぶつかりで止まったときは、ほかの止まり方と同じく、調べた内容と推奨を付けてオーナーへ上げる。claude-harness に Issue を作る）
- サイクルの終わりの振り返り、事例の記憶、改善の候補、対処の後に「進んだか」の判定、時間の集計（理由: S5）
- （仮）予算の上限を超えた保留を、スーパーバイザーが受けること（理由: 打てる手が「上げる」だけで、数字は core が出せる。判断の費用に見合わない）
- 反映・上げる依頼・承認していない反映の検知に関わる保留を、スーパーバイザーが受けること（理由: 取り消せない操作に関わる）
- 分類・計画の判断点の問い、完了の検証の実物の食い違い、人の操作の後でしか満たせない条件の保留、対話のセッションが引き取る保留を、スーパーバイザーが受けること（理由: オーナーか、オーケストレーターが答える問い）
- 契約の判断待ちのうち、承認の待ち・ターミナルで人が解く待ちを、スーパーバイザーが受けること（理由: 承認はできない。ターミナルの操作はできない）
- 「同じ場所で 2 回止まる」を、止まり方をまたいで検知すること（理由: 止まり方ごとの上限〔対処 2 回〕で足りる。いまある個別の上限は残す）
- スーパーバイザーに、コマンドを実行する道具や、成果物の中身を取りに行く道具を持たせること（理由: 設計書 D5・§21.5）
- 保留を、タスクの単位に下げること、保留中の課題のほかのタスクを進めること（理由: S4c）
- 計画の後に、承認なしでタスクを足すこと（理由: S4c）
- 画面の表示（スーパーバイザーが確認中の札・打った手・答えた問い）（理由: S4d-2）
- スーパーバイザーの手の一覧・止まり方・できないことを、宣言で変えられるようにすること（理由: 設計書 §21.5。変更は、課題としてオーナーの承認を通す）
- 開発に固有の知識を、core に新しく足すこと（理由: flywheel#981）

## 受入基準

特に断らない限り、テスト用の判断点（決めた出力を返す）とテスト用の委譲先で、宣言の `supervisor` は真（既定）で確かめる。「スーパーバイザー待ち」は、保留の `supervisor_state` が `pending` であること。「オーナーへ上がる」は、保留が開いたままで、`supervisor_state` が `pending` でないこと。

### 回数の上限

- [ ] 同じタスクの同じ止まり方に、最後のオーナーの回答より後の、結果が `executed` の `reverify` の対処の記録が 2 件あるとき、その止まり方の次の保留は、スーパーバイザー待ちにならない。
- [ ] 上限に当たってスーパーバイザー待ちにならなかった保留の問いの冒頭に、スーパーバイザーが 2 回対処した旨がある。
- [ ] 上限に当たってスーパーバイザー待ちにならなかった保留の問いに、その 2 回の手の名前がある。
- [ ] 上限に当たってスーパーバイザー待ちにならなかった保留の `stop_kind` は、その止まり方である。
- [ ] 同じタスクの、別の止まり方の対処の記録が 2 件あっても、その止まり方でない新しい保留は、スーパーバイザー待ちになる。
- [ ] オーナーが保留に回答した後は、回答より前の対処の記録を数えない（同じ止まり方の新しい保留は、スーパーバイザー待ちになる）。
- [ ] スーパーバイザーが保留を閉じても、「最後のオーナーの回答」は進まない（スーパーバイザーが 2 回閉じた後の 3 回目の保留は、スーパーバイザー待ちにならない）。
- [ ] 手が `defer` の対処の記録は、2 回の上限に数えない。
- [ ] 手が `escalate` の対処の記録は、2 回の上限に数えない。
- [ ] 結果が `failed` の対処の記録は、2 回の上限に数えない。
- [ ] 結果が `rejected` の対処の記録は、2 回の上限に数えない。
- [ ] タスクの無い保留は、課題の単位で数える（同じ課題の、タスクの無い同じ止まり方の対処の記録が 2 件あるとき、次の保留は、スーパーバイザー待ちにならない）。
