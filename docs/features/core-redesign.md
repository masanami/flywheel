# core の見直し（課題 ＞ タスク ＞ フォローアップ・サイクル・スーパーバイザー）

## 概要

2026-11-17 の設計の見直し（`docs/architecture.md` §21。決定 D22〜D34）を、core・CLI・画面に実装する。全体を区切り（スライス）に分け、この文書の受入基準は、いま実装する区切りの分だけを持つ。後の区切りは、その番が来たときにこの文書へ書き足す。

区切り S1（外す）は出荷済み（flywheel#732・PR #747）。区切り S2（土台）は、S2a（ストアと計画。flywheel#749・PR #767）・S2b（入口と出口。flywheel#770・PR #795）・S2c（画面。flywheel#798・PR #835）の 3 つに分けて入れ、どれも出荷済み。

区切り S3（委譲先との境界）も大きいので、S3a（反映を委譲先に任せる）・S3b（複数のタスクと統合先）・S3c（衝突の解消を、承認し直さずに通す）・S3d（画面）の 4 つに分けて入れる（下の「スライス」）。S3a（flywheel#842・PR #876）と S3b（flywheel#878・PR #917）は出荷済み。S3c と S3d は、並べて進める（オーナーの決定 2026-11-21。S3d の仕様は、別の文書に書く）。

いまの実装対象は S3c（衝突の解消を、承認し直さずに通す）で、次を行う。

- 宛先（統合先か反映先）が動いて、委譲先が宛先の最新を取り込み、衝突を直したとき、完了の検証の判断点（J5）が、「通した中身からの、直した差分」だけを確かめる（衝突の解消の確かめ）。
- 確かめが「満たしたまま」で、チェックがすべて通っていれば、承認し直さずに（統合先宛てなら、検証し直さずに）「入れてよい」を返す。
- 通したことと、直した差分を記録し、課題の詳細に出す。
- 確かめが「問題あり」「判断できない」のとき、取り込みと関係のない変更が足されたときは、S3b までと同じに、検証（と承認）をやり直す。

フォローアップを、開いている課題のタスクに上げることは、S4 へ送る（オーナーの決定 2026-11-21。下の「クリティカル設計決定」）。

## 背景・目的

2026-11-01〜11-16 の 16 日間を測った結果（`docs/architecture.md` §21.0）、課題の時間の大半がオーナー待ちで、費用の約半分が判断点に出ていた。設計の見直しで、次を決めた。

- 課題の下にタスクのツリーとフォローアップを持ち、承認は課題ごとに 1 回にする（D22・D23）。
- 反映・統合先・作業ツリーは委譲先に任せる（D24・D25・D31〜D33）。
- サイクルは、走っているタスクを見ながら進める。想定外のことはスーパーバイザーが受ける（D26・D27）。
- 課題どうしを、同じ場所を触る見込みを理由には直列にしない（D29）。

S3c は、宛先が動いたときのやり直しを減らす。S3b までは、委譲先が宛先の最新を取り込むときに衝突を直すと、直したのが 1 ファイルでも、取り込みと関係のない変更と同じに扱い、反映先宛てなら反映の承認を取り消して検証と承認をやり直し、統合先宛てならタスクの検証を最初からやり直していた。同時に走るタスクが増える（S3b）と、宛先が動く回数も増える。変わり方の見分け（取り込みだけ・衝突の解消あり・関係のない変更あり・判定できない）と、直した差分の読み取りは、S3a で core に入っている（上流のアダプタの比較の口）。S3c は、「衝突の解消あり」のときに、J5 を差分で呼ぶ道と、その結果の記録を足す（設計書 §21.3。決定 D31）。

S3b は、タスクが複数の課題を進められるようにした。S3a までは、起動するのが「統合先を使わない、タスクが 1 個の課題」だけで、計画がタスクを 2 個以上に分けた課題（統合先を使う課題）は、起動しないで止まっていた。実行の重なりを止める一意の制約・同時に走らせる数・予算・完了の検証は、どれも課題の単位で、タスクの前提（順番）は、記録するだけで、起動の判定に使っていなかった。委譲先の側の受け口（統合先を作る・統合先の成果物の印・統合先を反映先へ上げる依頼）は、claude-harness の 5.2.0 には無く、claude-harness の側で先に足す（下の「委譲先との契約」の「claude-harness の側で要るもの（S3b）」）。

S3a は、反映を委譲先に任せた。見直し前は、完了の承認の後、flywheel が自分で反映先へ入れていた（開発では、PR のマージと、反映先の最新の取り込みの依頼）。入れられないときは課題を着手中へ戻して委譲先へ差し戻し、委譲先の実行には、入れ終えた後で「反映まで済ませた」を返して終わらせていた。この形では、ブランチ・PR・マージという開発に固有の操作を core が持ち、差し戻しを返す・入れる・終わりを読むのそれぞれに 1 サイクルかかる（設計書 §21.3・§21.4）。委譲先の指示は、契約の形ではタスクの文面を渡す道が無く、取り込み元（Issue）の本文だけが委譲先に届いていた。S3a は、契約に足した受け口（下の「委譲先との契約（S3 で使う受け口）」。claude-harness 側の実装は claude-harness#388）を、flywheel の側で使う。

決定の正本は、flywheel#724・#725・#726 の「設計の見直しで決めたこと」の節と、`docs/architecture.md` §21、`docs/glossary.md`。この文書は、それらを写さずに参照する。

## ユーザーストーリー

オーナーとして、完了と反映を承認した後に反映先が動き、委譲先が衝突を直したとき、直した差分が承認した中身の意図を変えていないことを判断点が確かめたなら、もう一度承認を求められずに反映先へ入ってほしい。何を通したか（直したファイルと差分）は、後から課題の詳細で読みたい。取り込みと関係のない変更が足されたとき、判断点が確かめられないときは、これまでどおり、検証と承認をやり直してほしい。

## 機能要件

S3c（衝突の解消を、承認し直さずに通す）の要件。S3b の要件は、下の「S3b で入れた要件（出荷済み）」に（受入基準は flywheel#878）、S3a の要件は、「S3a で入れた要件（出荷済み）」に残してある（受入基準は flywheel#842）。S2c の要件と受入基準は flywheel#798（S2b は flywheel#770、S2a は flywheel#749、S1 は flywheel#732）。

語は `docs/glossary.md` に合わせる。「契約の実行」「反映の操作」「反映の試行」「承認した中身」「中身の識別」の意味は S3a の要件と、「統合先を使う課題」「タスクの検証」「検証した中身」「上げる依頼」の意味は S3b の要件と同じ。この節では、さらに次の語を使う。

| 語 | 意味 |
|---|---|
| 通した中身 | 宛先へ入れてよいと、すでに確かめてある中身の識別。統合先宛て（タスクの実行）では、検証した中身（`contract_run.verified_ref`）。反映先宛て（反映の依頼と、統合先を使わない課題のタスクの実行）では、承認した中身。反映先宛てで、衝突の解消の確かめを通した後は、その確かめで通した中身（`contract_run.fix_verified_ref`）。統合先宛てでは、確かめを通すと検証した中身そのものを改めるので、別の列は持たない。 |
| 変わり方 | 通した中身から、いまの中身への動きを、core が上流のアダプタの比較の口で見分けた結果。取り込みだけ・衝突の解消あり・関係のない変更あり・判定できない、の 4 つ（S3a で入れた見分け。変えない）。 |
| 衝突の解消あり | 動きが、宛先の最新の取り込み（マージのコミット）だけで、そのうち 1 つ以上で、両方の親と違う形になったファイルがあること。取り込みのほかにコミットが 1 つでもあれば、これにならない（関係のない変更あり）。 |
| 直した差分 | 衝突の解消ありのときの、取り込みのマージのコミットごとの、両方の親と違う形になったファイルと、その差分（通した中身の側の親からの差分）。core が比較の口から読む（委譲先の申告は使わない）。 |
| 衝突の解消の確かめ | J5 が、直した差分だけを、完了条件に照らして確かめること。J5 の 3 つ目の動き方（1 つ目は完了の検証とタスクの検証、2 つ目は課題の単位の確かめ）。 |
| 確かめ待ちの中身 | 衝突の解消の確かめを待っている、いまの中身の識別（`contract_run.fix_pending_ref`）。 |

### 衝突の解消の確かめ（J5 の動き方）

対象と、実行の記録。

- [ ] J5 の段は、見直し前の対象（検証中の課題・検証中のタスク・課題の単位の確かめ）を先に処理し、その後に、衝突の解消の確かめの対象を処理する。対象選びは、見直し前の対象選びと別にする。
- [ ] 確かめの対象は、確かめ待ちの中身を持ち、終わっていない契約の実行。統合先宛てでは、着手中の課題の、検証中のタスクの実行。反映先宛てでは、完了の課題の、終わっていない反映の操作に対応する実行（上げる依頼・統合先を使わない課題のタスクの実行・委譲先のフローを通らない成果物の反映の依頼）。
- [ ] 保留中の課題の実行は、対象にしない。取り込み元の食い違いで、自動の対象から外す決まり（見直し前の J5 と同じ）は、確かめにも当てる。
- [ ] 確かめの実行の記録（`run`）は、統合先宛てでは、そのタスクの実行として作る（`task_id` を付ける）。反映先宛てでは、課題の実行として作る（`task_id` を付けない）。同じ単位に、終わっていない実行があるときは、確かめを始めない（見直し前の、実行の重なりの決まりのまま）。
- [ ] 費用は、見直し前の J5 と同じに、その課題の判断点の費用として記録する（完了の課題でも同じ）。タスクの枠の使った額には数えない。

入力。

- [ ] 入力を組み立てるとき、通した中身から確かめ待ちの中身への変わり方を、比較の口で読み直す。結果が衝突の解消ありでなければ、確かめを始めない（実行の記録を作らない。次の状態の確認か反映の段が、見分け直して扱う）。
- [ ] 入力は、次のもの。完了条件（統合先宛てなら、タスクの完了条件と、対応する取り込み元があればその本文。反映先宛てなら、計画の「完了したら見えるもの」）。通した中身と、確かめ待ちの中身の識別。取り込みのマージのコミットごとの、直したファイルと、その差分（通した中身の側の親からの差分）。差分を上流が返さなかったファイルがあれば、そのファイルの名前と、差分を読めなかった旨。
- [ ] 作業ディレクトリは、確かめ待ちの中身を取り出した一時の作業ツリー（S3a の、成果物の中身を読む作りと同じ）。
- [ ] J5 の指示文に、衝突の解消の確かめの節を足し、次の 3 つを書く。直した差分が、通した中身の意図を保ったまま、宛先の変更と両立させているかだけを確かめる（全体を検証し直さない）。差分が、衝突の解消の範囲を超えて、振る舞いを足している・消しているなら「満たしていない」を返す。差分を読めないファイルがあって確かめられないなら「判断できない」を返す。

結果。

- [ ] J5 の出力の形は変えない。「満たした」を満たしたまま、「満たしていない」を問題あり、「判断できない」を判断できない、と読む。
- [ ] 結果を書く直前に、契約の実行の中身の識別が、確かめを始めたときの確かめ待ちの中身と同じことを確かめる。違えば、結果を捨てる（列は何も変えない。次の状態の確認か反映の段が、新しい中身で見分け直す）。
- [ ] 結果を書く直前に、課題が保留中になっていたら、結果を捨てる（列は何も変えない）。
- [ ] J5 の呼び出しが、連続の失敗の上限（見直し前のまま）に達したら、判断できないと同じに扱う。
- [ ] 確かめに、回数の上限は足さない（問題あり・判断できないは、どちらも検証か承認のやり直しへ落ちるので、同じ中身で繰り返さない）。

### 統合先へ入れるとき（タスクの実行）

S3b の「レビュー待ちで、中身の識別が検証した中身と違う」ときの分けを、次に改める。状態の確認は、確かめ待ちの中身がある間も、毎回、検証した中身からいまの中身への変わり方を見分ける。

- [ ] 変わり方が取り込みだけ → S3b のまま（検証した中身を新しい中身に改め、チェックを確かめて「入れてよい」を返す）。
- [ ] 変わり方が衝突の解消あり → 検証した中身は消さず、いまの中身を、確かめ待ちの中身として記録する（すでに確かめ待ちの中身があれば、いまの中身に改める）。`land_ref` は消し、`land_delivered` は偽にする。タスクは検証中のまま。「入れてよい」は返さない。
- [ ] 確かめ待ちの中身がある間、そのタスクは、タスクの検証（1 つ目の動き方）の対象にしない。
- [ ] 確かめが満たしたまま → 検証した中身を、確かめ待ちだった中身に改め、確かめ待ちの中身を消す。次の状態の確認が、S3b の決まりで、チェックを確かめて「入れてよい」を返す。
- [ ] 確かめが問題あり → S3b の、タスクの検証の「満たしていない」と同じ（タスクを着手中へ戻し、J5 の指摘を、委譲先へ差し戻しで返す）。検証した中身と確かめ待ちの中身は消す。
- [ ] 確かめが判断できない → 検証した中身と確かめ待ちの中身を消す（タスクは検証中のまま。次の J5 が、タスクの検証を最初からやり直す。課題を保留にしない）。
- [ ] 変わり方が関係のない変更あり・判定できない（比較の口を持たない委譲先・上流を含む）→ S3b のまま（検証した中身を消して、検証し直す）。確かめ待ちの中身があれば、一緒に消す。
- [ ] 確かめ待ちの中身は、次のときにも消す。タスクが着手中へ戻ったとき。契約の実行が終わったとき（どの終わり方でも）。課題が保留になっても消さない（回答の後の状態の確認が、見分け直す）。

### 反映先へ入れるとき（反映の段）

S3a・S3b の、反映の段で「承認した中身と、いまの中身が違う」ときの分けを、次に改める。上げる依頼・統合先を使わない課題のタスクの実行・委譲先のフローを通らない成果物の反映の依頼の、どれも同じ。反映の段は、確かめ待ちの中身がある間も、毎回、起点からいまの中身への変わり方を見分ける。

- [ ] 見分けの起点は、通した中身（`fix_verified_ref` があればそれ。無ければ、承認した中身）。
- [ ] いまの中身が起点と同じ → S3a のまま（チェックを確かめて、いまの中身を付けて「入れてよい」を返す）。
- [ ] 変わり方が取り込みだけ → S3a のまま（チェックを確かめて、いまの中身を付けて「入れてよい」を返す）。`fix_verified_ref` は変えない。
- [ ] 変わり方が衝突の解消あり → 反映の承認を取り消さない。いまの中身を、確かめ待ちの中身として記録する（すでにあれば、いまの中身に改める）。「入れてよい」は返さない。課題は完了のまま。反映の試行の記録を 1 件残す（結果は、S3c で足す値 `waiting_fix_check`。見た中身に、いまの中身）。`waiting_fix_check` は、待つ種類の結果で、連続の失敗に数えない。直前の閉じた試行の結果が `waiting_fix_check` で、その見た中身が、いまの確かめ待ちの中身と同じなら、試行の記録を増やさない（S3a の `waiting_outside` と同じ決まり）。
- [ ] 確かめが満たしたまま → 確かめ待ちだった中身を `fix_verified_ref` に記録し、確かめ待ちの中身を消す。課題の状態は変えない。次の反映の段が、上の決まりで進める。
- [ ] 確かめが問題あり・判断できない → J5 の結果の書き込みは、確かめ待ちだった中身を、通らなかった中身（`fix_rejected_ref`）として記録し、確かめ待ちの中身を消すだけにする（反映の承認・反映の操作・課題の状態は、J5 が変えない）。
- [ ] 次の反映の段は、いまの中身が `fix_rejected_ref` と同じなら、S3a の、関係のない変更ありと同じ道を通す（結果 `head_changed`。反映の承認を取り消す。その後の検証と承認のやり直しは、S3a のまま）。試行の記録の詳細に、衝突の解消の確かめが通らなかった旨を書く。いまの中身が `fix_rejected_ref` と違えば、`fix_rejected_ref` を消して、起点から見分け直す。
- [ ] 変わり方が関係のない変更あり・判定できない（比較の口を持たない委譲先・上流を含む）→ S3a のまま。確かめ待ちの中身・`fix_verified_ref`・`fix_rejected_ref` は消す。
- [ ] 確かめを通した中身で入れたときの、反映の試行の記録は、承認した中身と、入れた中身の両方を持つ（S3a の列のまま）。
- [ ] チェックの確かめ（落ちたら S3a の扱い、まだなら待つ）と、承認した中身にチェックが無かったときの扱いは、S3a のまま。
- [ ] 確かめ待ちの中身・`fix_verified_ref`・`fix_rejected_ref` は、次のときにも消す。反映の承認を取り消したとき。課題が完了から戻ったとき。契約の実行が終わったとき（どの終わり方でも）。

### 記録と表示

- [ ] 確かめが満たしたままのとき、作業ログに 1 件残す。`action` は `conflict_fix_passed`（S3c で足す）。`entity` は、統合先宛てならタスク、反映先宛てなら反映の操作（どちらも、すでにある種類）。`before` は `{"ref": 通す前の中身}`、`after` は `{"ref": 通した中身, "files": 直したファイルの名前の配列, "run_id": 確かめの実行の ID}`。
- [ ] 問題あり・判断できないのとき、`conflict_fix_passed` は残さない。
- [ ] 確かめの結果は、どれでも、J5 の実行の記録（`run`）に残る（見直し前の J5 と同じ）。直した差分は、その実行の入力として保存する（見直し前の J5 の入力の保存と同じ）。

### S3b のレビューで残した 3 件の直し（flywheel#915）

S3b を main へ入れる前の全体のレビューで残した 3 件を、S3c の統合ブランチに、最初に入れる（オーナーの決定 2026-11-21）。受入基準は flywheel#915 が持ち、この文書の受入基準には入れない。下の「やらないこと」の、S4 へ送る「S3b で残した点」とは別のもの。

3 件は、計画の作り直しの入力が、統合先を使う課題で、使った費用を枠ごとに二重に含めさせること、計画のレビュー対応の枠に、上限の検査が無いこと、タスクが 1 個で枠を省いた計画の、承認の要約に、タスクの枠が出ないこと。

### S3b で入れた要件（出荷済み）

S3b（複数のタスクと統合先）の要件。受入基準は flywheel#878。この節と、下の「S3a で入れた要件（出荷済み）」は、出荷したときの記録として残す。中身が動いたときの分けのうち、「取り込みだけでなければ、検証した中身を消す」「衝突の解消ありは、`head_changed`」と書いている行は、S3c で、衝突の解消ありのときだけ、上の「統合先へ入れるとき」「反映先へ入れるとき」のとおりに改めた（取り込みだけ・関係のない変更あり・判定できないのときは、この節のまま）。

語は `docs/glossary.md` に合わせる。委譲先との契約（コマンド・出力のキー・答えの値）は、下の「委譲先との契約（S3 で使う受け口）」が正本で、この節は flywheel の側の動きを書く。「契約の実行」「反映の操作」「反映の試行」「承認した中身」「中身の識別」の意味は、S3a の要件と同じ。S3b の要件では、さらに次の語を使う。

| 語 | 意味 |
|---|---|
| 統合先を使う課題 | 課題に記録した `uses_integration` が真の課題。タスクの成果の宛先は統合先で、反映先へは、統合先をまとめて上げる。 |
| 統合先を使わない課題 | それ以外（タスクは 1 個。成果の宛先は反映先）。動きは S3a のまま変えない。 |
| タスクの検証 | 完了の検証の判断点（J5）が、1 つのタスクの成果を、そのタスクの完了条件で確かめること。 |
| 課題の単位の確かめ | J5 が、統合先に集まった全体を、課題の完了条件で確かめること。 |
| 検証した中身 | タスクの検証が「満たした」とした、タスクの成果の中身の識別（`contract_run.verified_ref`）。 |
| 上げる依頼 | 統合先を反映先へ上げるための反映の依頼（`contract_run.kind` が `reflect`）。完了の承認の前に始める。 |

#### 起動する課題とタスク

- [x] 統合先を使う課題（タスクが 1 個でも、2 個以上でも）のタスクを起動する。統合先を使わない課題は、S3a と同じに、起動できるタスクがちょうど 1 個のときだけ起動する。
- [x] 統合先を使う課題で、タスクのリポジトリが 2 つ以上にまたがるものは、計画の検査で不正にする（計画を作る判断点〔J2〕の出力の検査。済みのタスクのリポジトリと、計画のタスクのリポジトリを合わせて見る）。検査をすり抜けた課題（手で登録した計画・過去の計画）は、起動せず、保留の理由 `tasks_blocked` で保留にする（問いに、リポジトリが複数である旨と、計画を作り直す回答〔タスクのリポジトリを 1 つにそろえる〕か、課題の取り下げで進める旨）。数えるのは、取りやめでないタスク（済みを含む）のリポジトリ。
- [x] 統合先を使う課題のタスクは、委譲先が `form: cli` のときだけ起動する。`form: plugin`・`form: brief` の委譲先のタスクは、起動しない（理由 `integration_unavailable`。詳細に、委譲の形が契約の形でない旨）。`form: cli` の委譲先が統合先を受けられない版のとき（`commands.start` が失敗で返る）は、見直し前の、起動の失敗の扱いのまま（flywheel は、委譲先の版を見分けない）。
- [x] 手で検証へ出す・手で検証の結果を書く口（`flywheel submit`・`flywheel verify --result`）は、統合先を使う課題では使えない（検証の誤り `validation_failed`。タスクの指定を足すのは、要るときに行う）。
- [x] 起動できるタスクは、状態が未着手（`pending`）で、前提のタスク（`task_dependency`）がすべて済み（`done`）のもの。前提に、取りやめ（`cancelled`）のタスクがあるタスクは、起動しない。
- [x] 統合先を使う課題のタスクが済み（`done`）になるのは、その成果が統合先へ入ったことを確かめたとき（下の「統合先へ入れる」）。
- [x] 同じ課題の、起動できるタスクは、同時に走らせてよい（同時に走らせる数の上限まで）。
- [x] 委譲の計画の候補は、課題ではなく、タスクの単位にする。並べる順は、課題の優先度、課題の ID、タスクの ID の順。
- [x] 同時に走らせる数（`max_parallel_runs`）は、タスクの単位で数える: 作業している契約の実行（タスクの実行と反映の依頼。レビュー待ち・オーナー待ちは数えない）と、終わっていない委譲の実行の数。
- [x] タスクが対応する子の上流の状態で起動しない決まり（S2b）は、タスクごとに当てる（1 つのタスクが起動できなくても、同じ課題のほかのタスクは起動する）。
- [x] 保留中の課題では、新しいタスクを起動せず、上げる依頼も始めない。走っている契約の実行（ほかのタスクの実行と、上げる依頼）は、状態を読み続ける（状態・費用を記録する）。保留が解けるまで延ばすのは、レビュー待ちの受け取り・タスクの検証・「入れてよい」を返すことの 3 つだけ。終わりの状態（`succeeded`・`failed`・`cancelled`）の確かめと、タスクを済みにすること、取り消すと決まった上げる依頼の `commands.cancel` は、保留中でも行う（課題の状態は、保留のまま変えない）。
- [x] 「タスクが実行中」は、そのタスクに、終わっていない実行の記録があるか、作業している契約の実行（終わっていなくて、最後に読んだ状態が、レビュー待ち・オーナーへの問いの待ちでないもの）があること。レビュー待ちを数えない条件は、課題の状態によらない（見直し前は、課題が検証中より後のときだけ、数えなかった）。起動の判定・J5 の対象の選び方・保留の間の成功の扱い（`held_success`）は、タスクの単位のこの述語で絞る。
- [x] 課題の単位の判断点（分類・計画・学び）が見る「課題が実行中」は、その課題のどれかのタスクが実行中か、タスクに結び付かない、終わっていない実行の記録か、作業している契約の実行があること。
- [x] 同じタスク（か、同じ課題のタスクに結び付かない実行どうし）で、実行の記録が重なるとき（例: タスクの検証の実行が開いている間の、そのタスクの状態の確認）は、後から始めようとした側が、何も呼ばずに、その 1 件を飛ばす（次の機会にやり直す。見直し前の、課題の単位での扱いと同じ）。
- [x] 進めようが無くなった課題は、保留にする: 統合先を使う、着手中の課題で、実行中のタスクも、検証中のタスクも、終わっていない契約の実行も無く、未着手のタスクが、どれも「前提に取りやめのタスクがある」ために起動できないとき、または、未完のタスクも済みのタスクも無い（全部が取りやめ）とき（保留の理由 `tasks_blocked`。問いに、起動できないタスクと理由、計画を作り直す回答か、課題の取り下げで進める旨）。対応する子の上流の状態で起動できないタスクは、S2b のまま、起動しなかった理由に出すだけにする（flywheel#800）。統合先を使う課題で、取りやめでないタスク（済みを含む）のリポジトリが 2 つ以上にまたがるときも、同じ理由 `tasks_blocked` で保留にする。こちらも、作業している実行（実行中のタスクの実行）か検証中のタスクがある間は、起動しないだけで待ち、無くなって起動するタスクも無いときに立てる（動いている作業の結果を受け取る前に課題を止めない。問いに、リポジトリが複数である旨と、計画を作り直す回答〔タスクのリポジトリを 1 つにそろえる〕か、課題の取り下げで進める旨）。
- [x] 起動の履歴・連続の失敗の数・差し戻しの数・再開の対象の決め方（`delegate_resume.go`）は、タスクの単位にする（見直し前は、課題と計画の版の単位）。
- [x] 保留は、そのきっかけがタスクのもの（タスクの実行の待ち・失敗・予算・タスクの検証）なら、起動できるタスクの数によらず、そのタスクに結び付ける。

#### レビュー待ちの受け取り（統合先を使う課題のタスク）

課題が着手中のときに、統合先を使う課題のタスクの実行の、成果物つきのレビュー待ちを読んだら（最初のレビュー待ちも、差し戻しの後・取り込みの後の、中身の変わったレビュー待ちも、同じ）、S3a の確かめ（`options` に `land` が無い・中身の識別がちょうど 1 つでない・`required_facts`）に続けて、次を確かめる。S3a の「反映先宛ての成果物が 2 つ以上」の確かめは、次の 1 つ目に置き換える。

- [x] 成果物に、反映先宛てのもの（開発では、既定ブランチ宛ての PR）が 1 つでもある → 検証へ進めず、課題を保留にする（保留の理由 `integration_ref_invalid`。問いに、統合先を使うタスクの成果が反映先宛てになっている旨）。
- [x] 成果物に、統合先の識別（`role` が `integration` の `branch`）と、統合先の中身の識別（`role` が `integration` の `commit`）が、ちょうど 1 つずつ無い → 同じく保留（`integration_ref_invalid`。問いに、見つかった数）。
- [x] 統合先の識別が、課題に記録した統合先（`challenge.integration_ref`）と違う → 同じく保留（`integration_ref_invalid`。問いに、2 つの値）。記録が無ければ、この識別を課題に記録する。
- [x] どれにも当たらない → 成果物を取り込み、タスクを検証中（`verifying`）へ進める。課題は着手中のまま。反映の操作は作らない（統合先へ入れることは、反映先に届かない）。
- [x] 保留にするときは、S3a と同じに、成果物の取り込みを行わない。
- [x] 検証した中身を持つタスクの実行の、中身の変わったレビュー待ちも、先に、この節の確かめと成果物の取り込みを行い、その後で、下の「タスクの検証と、統合先へ入れる」の、検証した中身との見比べへ進む（J5 が検証し直すときに、新しい成果物を読めるようにする）。
- [x] 統合先を使う課題のタスクの実行が、レビュー待ちを経ずに終わった（`land_ref` が無いのに `succeeded` を読んだ）→ 検証へ進めず、課題を保留にする（上流の成果物が統合先へ入っていれば `merged_unverified`、入っていなければ `delegate_ended`）。保留の間の成功をまとめて検証へ出す処理（`SubmitHeldContractSuccesses`）は、統合先を使う課題を対象にしない。

#### タスクの検証と、統合先へ入れる

- [x] J5 の対象に、「統合先を使う、着手中の課題の、検証中のタスクで、契約の実行の中身の識別が、検証した中身と違う（か、検証した中身が無い）もの」を足す。対象は、課題とタスクの組で選ぶ（同じ課題に、検証中のタスクが 2 個以上あってよい）。判断点の実行の記録には、そのタスクを残す（`run.task_id`）。
- [x] タスクの検証の結果は、課題の遷移（T8〜T10）を使わずに書く。書く直前に、課題が着手中で、タスクが検証中で、契約の実行の中身の識別が、検証を始めたときと同じことを確かめ、違えば、結果を捨てる（何も書かない。次の J5 が、やり直す）。作業ログには、タスクの検証の結果として残す。
- [x] 課題の「実物」の記録・予想と実物の食い違いの保留・人の操作の後でしか満たせない条件の保留は、タスクの検証では行わない（課題の単位の確かめだけで行う）。
- [x] タスクの検証の結果:
  - 満たした → 契約の実行に、検証した中身（そのときの中身の識別）を記録する。タスクは検証中のまま（済みにするのは、統合先へ入った後）。課題の状態は変えない。オーナーの承認は求めない。
  - 満たしていない → タスクを着手中へ戻し、次の状態の確認で、そのタスクの実行へ `respond` で指摘を返す（S3a と同じ返し方。相手は、そのタスクの実行）。
  - 判断できない → 課題を保留にする（見直し前と同じ。保留は、そのタスクに結び付ける）。
- [x] J5 の指示文に、タスクの検証では、そのタスクの完了条件（と、対応する取り込み元）だけで判定し、ほかのタスクの範囲が済んでいないことを理由に「満たしていない」としない旨を足す。
- [x] 委譲の段の先頭の状態の確認で、検証した中身を持つタスクの実行を、次のように進める。
  - レビュー待ちで、中身の識別が検証した中身と同じで、まだ「入れてよい」を返していない（か、届いた記録が無い）→ 中身のチェックを、上流のアダプタの口で確かめる。終わっていないチェックがあれば、何も返さず待つ。失敗があれば、課題を保留にする（保留の理由 `checks_failed`）。すべて通っていれば（0 件の扱いは S3a と同じ）、`commands.resume` で「入れてよい」を返す（`{choice}` に `land`、`{approved_ref}` に検証した中身。`land_ref`・`land_delivered` の書き方は S3a と同じ）。
  - `running` → 待つ。
  - レビュー待ちで、中身の識別が検証した中身と同じで、「入れてよい」が届いた記録がある → 課題を保留にする（保留の理由 `land_refused`。問いに、委譲先の `summary` と `requested_action.text`）。
  - レビュー待ちで、中身の識別が検証した中身と違う → 上流のアダプタの比較の口で、成果物の宛先（統合先）に対して見分ける。統合先の最新の取り込みだけ（衝突の解消が無い）なら、検証した中身を新しい中身に改め、上の 1 つ目へ進む（検証し直さない）。そうでなければ、検証した中身と `land_ref` を消し、`land_delivered` を偽にする（タスクは検証中のままなので、次の J5 が検証し直す）。比較の口には、取り込み元のブランチとして、成果物の宛先（上流から読んだ、その成果物の宛先。統合先）を渡し、前の中身に検証した中身、後の中身に新しい中身を渡す。
  - `succeeded` → 成果物を上流から読んで確かめる。成果物が統合先へ入っていて、入った中身が、「入れてよい」で返した中身と同じ → タスクを済みにし、契約の実行を終わった記録にする。出力の成果物の、統合先の中身の識別（入れた後のもの）を、成果物の記録に残す。入っていない → 課題を保留にする（保留の理由 `delegate_ended`）。入った中身が違う → 課題を保留にする（保留の理由 `merged_unverified`）。上流から読めない → 何も書かず、次の状態の確認でやり直す。
  - `failed`・`cancelled` → 「入れてよい」を返していなければ、検証した中身を消し、検証中のタスクを着手中へ戻して、見直し前の、失敗の扱い（タスクの単位）へ進む。「入れてよい」を返した後なら、先に、成果物が統合先へ入ったかを上流から読んで確かめる。入っていて、入った中身が、「入れてよい」で返した中身と同じ → `succeeded` と同じに、タスクを済みにする。入った中身が違う → 課題を保留にする（保留の理由 `merged_unverified`）。入っていない → 検証した中身と `land_ref` を消し、`land_delivered` を偽にし、検証中のタスクを着手中へ戻して、見直し前の、失敗の扱いへ進む（課題が保留中なら、何も書かず、回答の後の状態の確認で同じ終わりを読み直す）。上流から読めない → 何も書かず、次の状態の確認でやり直す。
  - そのタスクに、J5 の実行の記録が開いている → 何も呼ばずに飛ばす。
- [x] 「入れてよい」を返すのは、検証した中身があるときだけ（J5 が「満たした」としていない中身を、統合先へ入れない）。
- [x] 保留の理由 `checks_failed`・`land_refused`・`delegate_ended`・`merged_unverified` の保留は、必ずタスクに結び付ける。回答で課題が着手中へ戻ったら、そのタスクの、終わっていないタスクの実行の `land_ref` を消し、`land_delivered` を偽にする（検証した中身は残す。次の状態の確認が、上の決まりで進め直す）。ほかのタスクの実行と、反映の依頼の記録は変えない。`delegate_ended`・`merged_unverified` で、契約の実行がもう終わっているときは、タスクを着手中へ戻す（次の委譲の段が、委譲し直す）。

#### 課題の単位の確かめと、反映先へ上げる

- [x] 統合先を使う、着手中の課題で、未着手・着手中・検証中のタスクが 1 個も無く、済みのタスクが 1 個以上あり、終わっていない契約の実行が無いとき、委譲の段が、上げる依頼を始める（課題に統合先の識別の記録が無ければ、始めずに、保留の理由 `integration_ref_invalid` で保留にする）: リポジトリの反映の依頼の口の `commands.reflect` を、`{artifact_ref}` に課題に記録した統合先の識別、`{challenge_id}` に課題の ID を入れて呼ぶ。契約の実行の記録は、`kind` を `reflect`、`operation_id` を空（NULL）にして作る。
- [x] 上げる依頼の、同時に走らせる数・サイクルの費用の上限・作業ディレクトリの決め方・費用の記録・予算の上限での中止をしないことは、S3a の反映の依頼と同じ。
- [x] リポジトリに反映の依頼の口が無い → 上げる依頼を始めず、課題を保留にする（保留の理由 `reflect_unavailable`。問いに、口を宣言に足してから回答するか、課題を取り下げる旨）。
- [x] `commands.reflect` が失敗した・終わった状態を返した → 課題を保留にする（保留の理由 `reflect_failed`）。
- [x] 完了でない課題の上げる依頼が、終わりの状態（`succeeded`・`failed`・`cancelled`）を返した（flywheel が取り消したときを除く）→ 契約の実行を終わった記録にし、反映の操作を作っていれば閉じ、課題を着手中へ戻して保留にする（保留の理由 `reflect_failed`。問いに、読んだ状態と委譲先の `summary`）。回答で保留が解けたら、次の委譲の段が、上げる依頼を始め直す（保留を挟まずに、自動では始め直さない）。
- [x] 契約の実行を読む段の分け方に、次を足す: 完了でない課題の反映の依頼（上げる依頼）は、委譲の段の先頭の状態の確認が読む。完了の課題の反映の依頼は、S3a と同じに、反映の段が読む。
- [x] 上げる依頼のレビュー待ちを読んだら、S3a の確かめ（`options` に `land`・中身の識別がちょうど 1 つ）と、反映先宛ての成果物（開発では、既定ブランチ宛ての PR）がちょうど 1 つであることを確かめる。当たらなければ、課題を保留にする（保留の理由は S3a と同じ `land_unavailable`・`content_ref_invalid`）。通れば、その成果物の反映の操作を作り（作り方は S3a と同じ）、契約の実行の `operation_id` に記録し、成果物を取り込み、課題を検証中へ進める（タスクは済みのまま）。
- [x] 検証中の、統合先を使う課題に対する J5 は、課題の単位の確かめとして動く。入力は、計画の背景（方針・完了したら見えるもの・やらないこと）、課題の取り込み元（見直し前と同じ読み方）、全部のタスクの題名と完了条件（済み・取りやめの別）、反映の操作の成果物（反映先へ上げる実物。開発では、統合ブランチから既定ブランチへの PR）、終わっていない上げる依頼があれば、その `facts`、直前の保留が `challenge_check_not_met` で、計画を作り直さない回答だったときは、その回答の文。成果物の中身の読み方（一時の作業ツリー）は、見直し前と同じ。結果の書き方（遷移・課題の「実物」の記録・食い違いの保留）は、見直し前と同じ。
- [x] J5 の指示文に、課題の単位の確かめでは、課題の完了条件（完了したら見えるもの）で全体を確かめ、タスクごとの検証をやり直さない旨を足す。
- [x] 課題の単位の確かめの結果:
  - 満たした → 見直し前と同じに、完了の承認待ちへ進める。
  - 満たしていない → 課題を着手中へ戻して、保留にする（保留の理由 `challenge_check_not_met`。問いに、J5 の指摘と、計画を作り直す回答〔`--replan`〕で直すタスクを足せる旨）。作った反映の操作は閉じ、上げる依頼は、次の状態の確認で `commands.cancel` で取り消す（保留中でも取り消す。取り消せるまで、新しい上げる依頼を始めない）。計画を作り直さない回答で保留が解けたら、次の委譲の段が、上げる依頼を始め直し、課題の単位の確かめをやり直す（オーナーが、回答の文で、J5 の読み違いを正す・flywheel の外で統合先を直した、ときの道）。
  - 判断できない → 見直し前と同じに、保留にする。
- [x] 完了の承認と、反映の操作の承認は、変えない。承認の後の反映の段は、S3a の「反映の依頼へ返す」の道で、上げる依頼へ「入れてよい」を返す。結果の読み方・取り消す結果の扱いも、S3a と同じ。
- [x] 統合先を使う課題の反映の操作について、反映の段が反映の依頼を始めるとき（上げる依頼が、取り消し・完了から戻す・失敗で、もう無いとき）は、`{artifact_ref}` に、反映の操作の参照ではなく、課題に記録した統合先の識別を入れる。
- [x] 統合先を使う課題を、完了から戻すとき（T18）は、課題だけを検証中へ戻し、タスクは済みのままにする。上げる依頼は、S3a と同じに、戻す前に取り消す。戻した後の J5 は、課題の単位の確かめで、反映の操作の成果物（置き換えた後の反映の操作の、同じ実物）を上流から読んで確かめる（上げる依頼の `facts` は無い）。もう一度承認された後、反映の段が、上げる依頼を始め直す（上の `{artifact_ref}` の決まり）。
- [x] 統合先を使う課題の、完了の差し戻し（T15）は、タスクを済みのまま残し（見直し前は、済みのタスクを着手中へ戻していた）、反映の操作を閉じ、課題を、計画を作り直す道へ送る（保留への `--replan` の回答の後と同じ扱い。次の J2 の入力に、差し戻しの理由を入れる）。上げる依頼は、次の状態の確認で取り消す。

#### 計画の作り直し

- [x] 統合先へ入ったタスク（済みのタスク）がある課題の計画は、`uses_integration` が真でなければ不正。

- [x] 作り直した計画の承認では、見直し前と同じに、未完のタスクを取りやめにして、新しい版のタスクを作る。済みのタスクは残す。取りやめにするタスクと、その課題の上げる依頼の、終わっていない契約の実行は、`commands.cancel` で取り消す（見直し前は、課題に 1 本の前提だった）。取り消せなかった実行は、終わっていない記録のまま残し、次の状態の確認が、取り消し直す（取りやめのタスクの実行は、レビュー待ちを受け取らない）。
- [x] 課題の取り下げも、その課題の、終わっていない契約の実行を、全部取り消す。

### S3a で入れた要件（出荷済み）

S3a（反映を委譲先に任せる）で入れた要件。S3b は、統合先を使わない課題の動きを変えない。統合先を使う課題で変える所は、上に書いた。

#### 宣言

- [x] `form: cli` の委譲先の `commands.start` に書ける差し込みに、`{task_file}`・`{task_id}`・`{uses_integration}` を足す。
- [x] `commands.resume` に書ける差し込みに、`{approved_ref}` を足す。
- [x] `form: cli` の委譲先の `commands` に、任意のキー `reflect`（反映の依頼を始めるコマンド。引数の配列）を足す。書ける差し込みは、`{artifact_ref}` と `{challenge_id}` の 2 つ。
- [x] コマンドごとに書ける差し込みは、次の表のとおり。

  | コマンド | 書ける差し込み |
  |---|---|
  | `start` | `{issue_number}`・`{issue_url}`・`{external_key}`・`{challenge_id}`・`{task_file}`・`{task_id}`・`{uses_integration}` |
  | `status`・`cancel` | `{issue_number}`・`{issue_url}`・`{external_key}`・`{challenge_id}`・`{run_id}` |
  | `resume` | `status` の 5 つと、`{answer}`・`{choice}`・`{note}`・`{approved_ref}` |
  | `reflect` | `{artifact_ref}`・`{challenge_id}` |

読んだ状態（2 で読んだとき）:

- [x] `running` → 結果 `waiting_delegate`（何も返さない。`land_ref` の有無によらない）。

## クリティカル設計決定

### DB スキーマ: 衝突の記録の表（S1）

- **採用案**: マイグレーションを 1 本足し、`challenge_conflict` の表と、その索引を消す（スキーマの版は 25 になる）。過去の衝突の記録は消える。
- **理由**: この表を読むのは、直列化グループと、グラフの衝突の線・「待っている理由」の衝突の欄（`graph.go`・`waiting.go`）だけで、どれも外す。過去の記録を読む用途が無い。残すと、全表を埋めるテストの支え（`coretest.FillAllTables`）と書き出しの検査に、使わない表の追従が残り続ける（オーナー 2026-11-17）。
- **代替案**: 表を残し、書き込みと読み取りだけをやめる。却下の理由は上のとおり。
- **影響範囲**: `internal/core/internal/store/migrations`、`internal/core/conflict.go`・`graph.go`・`waiting.go`・`delegate_plan.go`、`coretest.FillAllTables`、`internal/core/export_test.go` の表の一覧、スキーマの版を直に書いているテスト、表を直に読み書きしているテスト（`internal/server/graph_test.go`・`internal/core/graph_test.go`。`internal/core/internal/store/migrate_0018_test.go` は最新まで当てた後で表を読むので、当てる版を 18 までに絞る）。書き出しと再構築（`Export`・`Import`）は表を列挙する作りなので、コードの変更は要らない。版 24 の書き出しは、版 25 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### DB スキーマ: 過去の実行の記録（S1）

- **採用案**: `run.kind = 'predict'` と `run.judgment = 'J9'` を、読み取りで受け付ける値として残す。予測の run が持つ予算の枠の値（`run.budget_bucket = 'predict'`）も同じく残す。新しく作る経路は無くす。すでにある行を終わらせる更新（終わっていない run を、サイクルの後片付けが「中断」にする）は受け付けるままにする。
- **理由**: 2026-11-01〜11-16 に、予測の run が 58 本、J9 の run が 105 本ある。費用の集計と `flywheel runs` の表示の根拠を消さない（オーナー 2026-11-17）。
- **代替案**: 過去の行を消す、または別の値へ書き換える。費用の記録が失われるので採らない。
- **影響範囲**: `internal/core/run_store.go` の値の検査（読み取りと書き込みで受け付ける値を分ける）、`view` の run の表示。

### 宣言の互換: 無くした項目（S1）

- **採用案**: 無くした項目が残っている宣言は、設定の誤り（`config_invalid`）として止める。エラーの文に、項目の名前と、無くなった旨（決まった語 `removed`）を出す。知らないキーを拒む既存のエラーの文（`unknown key`）とは別の文にする。
- **理由**: 宣言は、知らないキーを拒む閉じた集合として検査している。黙って無視すると、設定が効いていると思い込んだまま動かすことになる（オーナー 2026-11-17）。
- **代替案**: 黙って無視して動かす。上の理由で採らない。
- **影響範囲**: `internal/core/connectors_declaration.go`・`internal/core/agent_declaration.go`。Tom のワークスペースの宣言の直しが、S1 を main に入れるときに要る。

### DB スキーマ: 課題 ＞ タスク ＞ フォローアップの持ち方（S2 で適用）

- **採用案**: いまの課題（`challenge`）を「課題」のまま残し、その下にタスク・タスクの前提・フォローアップの表を足す。委譲と完了の検証を、課題からタスクへ付け替える（`run`・`contract_run`・`hold` にタスクへの参照を足す）。計画・承認・反映は、課題の単位のまま残す。
- **理由**: 「承認の真正性」と「完了と反映を 1 回の操作で承認する」（D12）は変えないと決めている（§21.8）。この案は、承認と反映の処理に手を入れずに済む。過去の完了・取り下げの課題は、タスクが 0 個の課題としてそのまま読める。設計書と用語集も、課題を「いまの課題のまま」としている（§21.1）。
- **代替案**: いまの課題をタスクとして読み替え、その上に課題の表を足す。委譲と検証はそのまま使えるが、計画・承認・反映の処理を課題の単位へ上げ直すことになり、識別子の意味が用語集とずれる。
- **影響範囲**: 表と列は、使う区切りで足す。S2a の分は次の節。フォローアップの表と、取り込み元の子の Issue をタスクに対応づける持ち方は、S2b の節（下の「DB スキーマ: フォローアップ・取り込み元の子」）。進行中の課題を新しい形へ移す処理は作らない（開いている課題は 0 件）。

### DB スキーマ: タスク・タスクの前提・計画の問いへの答え（S2a）

- **採用案**: マイグレーションを 1 本足す（スキーマの版は 26 になる）。中身は次のとおり。
  - タスクの表 `task`: `id`（主キー。表示は `T-<番号>`）・`challenge_id`（課題への参照。必須）・`plan_version`（このタスクを作った計画の版。必須）・`key`（計画の中の識別子。計画から作ったタスクだけが持つ。NULL を許す）・`title`・`body`・`done_criteria`（どれも必須）・`non_goals`（JSON の配列。無ければ NULL）・`repo`・`operation`（必須）・`status`（必須。`pending`・`in_progress`・`verifying`・`done`・`cancelled`）・`created_at`・`updated_at`。同じ課題・同じ計画の版の中で、`key` は重ならない（一意の制約。`key` が NULL の行どうしは重なりと見ない）。
  - タスクの前提の表 `task_dependency`: `task_id`・`depends_on_id`（どちらもタスクへの参照。2 つの組が主キー）。
  - 計画の問いへの答えの表 `plan_answer`: `id`（主キー）・`challenge_id`（必須）・`plan_version`（必須）・`question_number`（必須。1 から）・`choice`（選んだ選択肢の番号。文の答えのときは NULL）・`text`（文の答え。選択肢の答えのときは NULL）・`recommended`（推奨と同じ答えなら 1）・`actor`・`channel`・`verification`（承認の記録と同じ意味の 3 つ）・`relay_session`・`relay_quote`（対話で受けたときだけ）・`answered_at`。別々のコマンドで同じ問いに答えが複数記録されたときは、後の行を使う（1 回のコマンドで同じ問いを 2 度は指定できない）。
  - 列の追加: `run.task_id`・`contract_run.task_id`・`hold.task_id`（タスクへの参照。NULL を許す）、`challenge.uses_integration`（1・0・NULL。NULL は、まだ決めていないか、過去の課題）。
  - 過去の行は書き換えない（`task_id` は NULL のまま）。索引と一意の制約は、足す表の分だけを作り、既存のものは変えない。
- **理由**:
  - タスクの行を計画の承認で作る形にすると、承認の前に計画を何度作り直しても、タスクの行の入れ替えが起きない。承認の前のツリーは、計画の構造化した出力（`task_plan.spec`）から読む。
  - 問いへの答えを、保留（`hold`）ではなく別の表に持つのは、答えが課題を止めないことと、問いごと（番号ごと）に「推奨と同じか」を機械的に判定するため。見直し前の論点への回答は、保留の 1 つの文で、問いごとの構造を持たなかった。
  - `task_id` に NULL を許すのは、課題の単位の実行（分類・計画・学び・改修提案の判断点）と過去の行があるため。SQLite は、既存の表へ、既定値の無い必須の列を足せない。
- **代替案**:
  - タスクの行を計画の登録で作り、作り直しのたびに入れ替える。承認の前のタスクに実行は付かないが、行の入れ替えと、古い版のタスクの扱いが増えるので採らない。
  - 問いへの答えを、承認の記録（`approval`）の 1 つの列に JSON で持つ。推奨と違う答えは、承認より前に記録する必要があり（承認されない版にも答えが付く）、承認の行に載せられないので採らない。
  - 既存の課題すべてに、タスクを 1 個ずつ作って埋める。過去の課題（450 件）に、計画に無いタスクを作ることになり、読むだけの用途に要らないので採らない。
- **影響範囲**: `internal/core/internal/store/migrations`、全表を埋めるテストの支え（`coretest.FillAllTables`）、`internal/core/export_test.go` の表の一覧、スキーマの版を直に書いているテスト。書き出しと再構築（`Export`・`Import`）は表と列を実行時に列挙する作りなので、コードの変更は要らない。版 25 の書き出しは、版 26 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### 承認の真正性: 問いへの答えの記録と、計画の作り直し（S2a）

- **採用案**: 計画の問いへの答えは、保留への回答と同じ本人確認（端末での本人確認か、対話で受けたことの記録〔`--relayed`〕）を通して記録する。本人確認の登録簿に、操作の種類 `answer_plan` を足す（端末の本人確認と、対話で受けた記録の組は受ける。画面・本人確認なしの組は受けない）。推奨と違う答え（か文の答え）が 1 件でも記録されたら、課題を計画の承認待ちから分類済へ戻す遷移（T19。操作の名前は `answer_plan`）を足し、次の計画の段に計画を作り直させる。計画の承認（T5）は、答えが記録されていない問いに、推奨の選択肢を、その承認と同じ人・経路・本人確認で記録する。
- **理由**: 計画の承認が「何を承認したか」は、計画の版と、問いごとの答えで決まる。答えを本人確認つきで記録し、推奨と違う答えの後は必ず新しい版の承認を通すことで、承認された計画と、オーナーの答えが食い違わない。差し戻し（T6）と同じ「分類済へ戻して作り直す」経路に乗せると、計画を作る判断点（J2）の対象の決め方と、計画の版の扱いを変えずに済む。
- **代替案**: 課題を計画の承認待ちのまま、作り直しの印だけを付ける。古い版の計画を承認できてしまう時間ができ、それを防ぐ検査が要るので採らない。
- **影響範囲**: `internal/core/transition.go`（遷移表）、`internal/core/verification.go`（登録簿と、遷移から操作の種類を引く対応）、`internal/core/approval.go`、`internal/cli/approval.go`・`commands.go`、`docs/features/m1-core.md` の遷移表と作業ログの一覧。画面のボタンで問いに答える口は、画面のボタンで受ける範囲を広げる決定（設計書 §9 の改訂。`ux.md` の未決は、S4 のクリティカル設計で決め、それまでは §9 の範囲で作るとしている）と一緒に入れる。入れるときは、この記録の口と、登録簿の `answer_plan` を通す。画面のボタンで受ける範囲と本人確認の決まり（設計書 §9）は、S2a では変えない。

### 一意の制約をタスクの単位に改める時期（S2a で決め直した）

- **採用案**: 「終わっていない実行は課題ごとに 1 本」の一意の制約は、S2a では変えず、複数のタスクを同時に走らせる S3 で改める。
- **理由**: この制約は、委譲の実行だけでなく、判断点の実行どうしの排他にも効いている。タスクの単位に改めると、課題の単位の排他が外れるので、別の形で残す設計が要る。S2a で起動するのはタスクが 1 個の課題だけで、いまの制約のままで足りる。S1 の時点のこの文書は「S2 で改める」としていたが、コードを調べたうえで時期を改めた（2026-11-18）。
- **代替案**: S2a で改める。動きを確かめられる場面（同じ課題の 2 つのタスクの同時の実行）が S3 まで無く、確かめられない変更を先に入れることになるので採らない。
- **影響範囲**: S3 の仕様で、`idx_run_active_challenge`・`idx_contract_run_active_challenge` の作り替えと、課題の単位の排他の残し方を決める。

### DB スキーマ: フォローアップ・取り込み元の子（S2b）

- **採用案**: マイグレーションを 1 本足す（スキーマの版は 27 になる）。中身は次のとおり。
  - フォローアップの表 `followup`: `id`（主キー。表示は `F-<番号>`）・`challenge_id`（ぶら下がる課題。課題に属さないものは NULL）・`title`（1 行。必須）・`detail`（説明。無ければ NULL）・`source`（出どころ。必須。S2b で書くのは `learn` だけ）・`status`（必須。`open`・`done`・`dropped`）・`note`（済みにしたときの、確かめた結果）・`reason`（捨てた理由）・`promoted_challenge_id`（上げた先の課題。上げていなければ NULL）・`created_at`・`updated_at`。
  - 取り込み元の子の表 `source_child`: `id`（主キー）・`challenge_id`（親の Issue から作った課題。必須）・`source_id`（取り込み元）・`external_key`（子の識別。一意）・`parent_external_key`（直の親の識別）・`url`・`title`・`body`・`upstream_state`（`open`・`closed`・`missing`。取り込み元との対応 `source_binding` と同じ値）・`created_at`・`updated_at`。
  - 列の追加: `task.source_key`（対応する子の `external_key`。NULL を許す）。
  - 過去の行は書き換えない。出どころが `followup` の過去の課題（295 件）を、フォローアップの行へ移すことはしない。
- **理由**:
  - フォローアップは、分類・計画・承認を通さない 1 行の項目で、課題の状態機械に乗せない（設計書 §21.1）。課題の表に種類を足して持つと、課題を対象にするすべての処理（分類・計画・一覧・状況）に、除外の条件が要る。
  - 上げた先は、フォローアップの側に持つ（`promoted_challenge_id`）。課題の側の `followup_of` は、見直し前から「派生元の課題」を指しており、意味を変えない。
  - 取り込み元の子を、取り込み元との対応（`source_binding`）の行にしないのは、その表が「課題 1 件に対応 1 件」（主キーが `challenge_id`）で、対応のある課題を対象にする処理（追従・除外・差し込み）が、その形に依っているため。子は課題ではないので、別の表に持つ。
  - タスクと子の対応を、タスクの側の列（`source_key`）に持つのは、タスクの行が計画の承認で作られ、承認の前の対応は計画の構造化した出力（`task_plan.spec` の `source`）から読めるため。
- **代替案**:
  - 過去の `followup` の課題を、フォローアップの行へ移す。完了・取り下げの課題に付いた実行・承認・作業ログの記録が宙に浮くので採らない（過去の課題は、読めれば足りる）。
  - 子の本文を記録せず、計画のたびに上流から読む。計画の段が上流の読み取りに依り、上流を読めないときに計画が止まるので採らない（追従は、取り込みの段でまとめて行う）。
  - フォローアップに、ぶら下がるタスク（`task_id`）の列も足す。S2b でフォローアップを書くのは、課題を単位にする学びの判断点だけで、タスクから出るフォローアップ（スーパーバイザーの手・委譲先の軽い指摘）は S4 から。列は、使う区切りで足す。
- **影響範囲**: `internal/core/internal/store/migrations`、全表を埋めるテストの支え（`coretest.FillAllTables`）、`internal/core/export_test.go` の表の一覧。版 26 の書き出しは、版 27 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### フォローアップを上げる先（S2b）

- **採用案**: S2b では、フォローアップを上げると、いつも新しい課題になる（課題に属するフォローアップは、その課題を派生元とする課題。属さないものは、取り込み元の無い課題）。「課題が開いていれば、その課題のタスクにする」（`ux.md` の決定 21）は、複数のタスクを走らせる S3 で入れる。
- **理由**: 開いている課題にタスクを 1 個足すと、起動できるタスクが 2 個になる。S2a・S2b の core は、起動できるタスクがちょうど 1 個の課題だけを進めるので、足した課題は、S3 まで止まる。完了の承認待ちの課題に足した未着手のタスクは、完了の承認で取りやめになり、上げた作業が消える。新しい課題にすれば、タスクが 1 個の課題として、いまの core で最後まで進む。
- **代替案**:
  - S2b で、開いている課題のタスクとして足す（設計のとおり）。上の理由で、足した課題が S3 まで進まない。
  - 上げる操作そのものを S3 へ送る。フォローアップが、一覧に溜まるだけで作業にできなくなるので採らない。
- **影響範囲**: `ux.md` の決定 21 との差は、S3 の仕様で埋める（そのとき、上げた先のタスクの記録の列を足す）。設計書 §21.1 の「上げたものは、その課題の中の派生のタスクになる」も、S3 から。core が済みにするきっかけも、S2b では「上げた先の課題の完了」で、設計書の「上げた先のタスクの完了」になるのは S3 から。

### 承認の真正性: フォローアップを捨てる・上げる（S2b）

- **採用案**: 捨てる（`followup_drop`）と上げる（`followup_promote`）は、保留への回答と同じ本人確認（端末での本人確認か、対話で受けたことの記録〔`--relayed`〕）を通す。本人確認の登録簿に、この 2 つの操作の種類を足す（画面・本人確認なしの組は受けない）。済みにする操作は、本人確認を通さない。
- **理由**: 設計書 §21.1 が、上げるのと捨てるのは「オーナーか、オーナーの指示を受けたオーケストレーター」、済みにするのは「オーナーとオーケストレーター（確かめた結果を書く）」と分けている。上げる操作は作業（費用）を増やし、捨てる操作は項目を消すので、オーナーの指示の記録を残す（上げる操作の記録の形は、設計書 §21.9 の U13）。
- **代替案**: 3 つとも本人確認なしにする。オーナーの指示の無い、作業の追加と項目の削除を、記録の上で見分けられなくなるので採らない。
- **影響範囲**: `internal/core/verification.go`（登録簿）、`internal/cli`（`relayedFlags` を付けるコマンド）。画面のボタンで済みにする・捨てる口（`ux.md` の決定 20）は、画面のボタンで受ける範囲を広げる決定（設計書 §9 の改訂。S4）と一緒に入れる。

### 取り込みを選ぶ形と、取り込み元の親子（S2b）

- **採用案**:
  - 新しい課題を作るのは、オーナーが選んだ Issue だけにする（`flywheel ingest <指定>...`）。サイクルの取り込みの段と、引数の無い `flywheel ingest` は、取り込み済みのものの追従だけを行う。
  - 選んだ Issue の子孫は、深さを問わず、その課題の「取り込み元の子」として平らに記録する。子は課題にしない。タスクにするかは、計画を作る判断点（J2）が決める（子は、ツリーの初期値）。
  - 親を持つ Issue も、単独で選べば、独立した課題になる。
  - 取り込みの後に上流で足された子は、自動では記録しない。
  - 子の記録は、課題を取り下げても残し、取り込み元との対応を外す操作（`flywheel unbind`）で消す。
- **理由**:
  - 課題の出どころを測ると（設計書 §21.0）、取り込みの 96 件に対し、オーナーの番を待つ時間が課題の時間の大半だった。取り込むものをオーナーが選ぶ形にして、選んでいないものが分類・計画・承認待ちに並ばないようにする（`ux.md` の決定 8）。
  - 子を課題にせず、課題の下の記録にするのは、設計書 §21.1 の「親の Issue を課題にし、子の Issue はそのタスクとして取り込む。読むのはツリーの初期値としてで、正本は flywheel」のとおり。
  - 子を単独で選べるようにするのは、複数のタスクの課題が S3 まで進まないため。親ごと取り込むと止まる間も、親を取り込まずに、子を 1 件ずつ、タスクが 1 個の課題として進められる（親を取り込んだ後は、対応を外してから選び直す）。
  - 平らに記録するのは、core が持つ層が「課題 ＞ タスク」の 2 つで、取り込み元の深さを写す層が無いため。直の親は、計画を作る判断点（J2）が前提の線を引く材料として渡す。
  - 取り下げた課題の子を残すのは、取り下げた課題の Issue そのものが、対応を外すまで取り込み直せない、いまの作りに合わせるため（取り下げたものが、取り込めるものに戻って並ぶのを避ける。戻したいときは、対応を外す）。
- **代替案**:
  - 親を選んだら、子は必ずタスクにする（計画を作る判断点に任せない）。子に無い作業（設計・結合の確かめ）を足せず、粒の合わない子をまとめられないので採らない。
  - 子を単独では選べないようにする。上の理由（S3 までの間、進める道が無くなる）で採らない。
  - 取り込みの後に足された子も、追従で記録する。承認済みの計画に無い子が増え、計画との食い違いをどう扱うかの決まりが要る。計画の後にタスクを足す形（S4）と一緒に決める。
- **影響範囲**: `internal/core/ingest.go`、`internal/cli/ingest.go`、`docs/features/m2-github-issue-ingest.md`。Tom の運用では、取り込みが自動で課題を作らなくなる（切り替えのときに、対話のセッションの進め方を合わせる）。

### 取り込み元とタスクの対応と、委譲先へ渡す取り込み元（S2b）

- **採用案**: タスクは、対応する子を 0 件か 1 件持つ（`source_key`）。1 件の子に対応するタスクは 1 個まで。委譲先へ渡す取り込み元（差し込み `{issue_number}`・`{issue_url}`・`{external_key}`）は、次の順で決める。
  1. タスクが対応する子を持つ → その子。
  2. 持たず、承認済みの計画のタスクが 1 個 → 課題の取り込み元（あれば）。
  3. 持たず、承認済みの計画のタスクが 2 個以上 → 渡さない（取り込み元の無いタスク）。
- **理由**: 委譲先は、取り込み元を、成果物からの参照（開発では、PR が Issue を閉じる書き方）に使う。子に対応するタスクの成果は、その子を閉じる。タスクが 1 個の課題では、タスクの成果が課題の成果なので、課題の取り込み元を閉じる（見直し前と同じ）。タスクが複数の課題で、子に対応しないタスクに課題の取り込み元を渡すと、最初のタスクの成果が、親の Issue を閉じてしまう。
- **代替案**: 子に対応しないタスクには、いつも課題の取り込み元を渡す。上の理由（親の Issue が早く閉じる）で採らない。
- **影響範囲**: S2b で効くのは 1 と 2（起動するのが、統合先を使わない課題だけで、その計画のタスクは 1 個のため）。3 は、複数のタスクを走らせ、タスクを文面で渡す S3 から効く（「委譲先との契約」の、足すもの 1）。計画を登録するときの、操作の検査（取り込み元の差し込みを要する操作を選べるか）を、タスクの単位でこの順に合わせるのも、S3。

### 状況の出力の互換と、上流の読み取り（S2b）

- **採用案**: `flywheel status --json` と状況の API は、いまあるキーと形を変えず、キーを足す（`ingestable`・`followups`・`cycle_work`）。文の出力は、並びと見出しを改める。状況の API が上流の Issue の一覧を読むのは、問い合わせに `ingestable=true` が付いたときだけにする。
- **理由**: いまの形は、画面（ボードと帯）と、仕様の文書に照らすテストが読んでいる（`ux.md` の未決「`--json` の利用への影響」を調べた結果。指示文とスクリプトからの読み取りは無い）。画面は S2c で作り替えるので、それまで、いまの画面を動くままにする。状況の API は画面が定期的に読むので、読むたびに上流の一覧（リポジトリごとに 1 回以上の呼び出し）を読ませない。
- **代替案**:
  - 根の形を「いま進められること」に合わせて作り直す。画面と文書とテストの追従が、S2c の前に二度手間になるので採らない。
  - 取り込めるものを、別のコマンドと別の API にする。`ux.md` の決定 24（新しいコマンドを足さず、`flywheel status` に出す）と食い違うので採らない。
- **影響範囲**: `internal/view`（`StatusResponse`）、`internal/server/status.go`、CLI と API の応答が同じであることを確かめるテスト（`ingestable=true` を付けた応答と比べる形に改める）、`docs/features/m1-core.md`・`m4-ui-server.md`。「回した場合の費用の見込み」（設計書 §21.4）は、費用の集計を入れる S5 で足す。

### 改修提案の判断点（J8）を変えない（S2b）

- **採用案**: S2b で、課題を起票しなくなるのは、学びの判断点（J6）だけにする。改修提案の判断点（J8）は、改修の課題を起票する形のまま残す。
- **理由**: 改修の課題は、改修の鍵（層と対象）で、発生の記録と結び付いており、同じ鍵の終わっていない課題があれば、起票せずにそれへ紐づける作りになっている。フォローアップへ移すには、この結び付きの持ち方を決め直す必要がある。設計書 §21.6 は、学びと改修提案の判断点を、スーパーバイザーの振り返りにまとめる（S5）としており、結び付きは、そのときに決め直す。件数は、学びの判断点のフォローアップが 295 件、改修提案の課題が 46 件（設計書 §21.0）で、先に効くのは学びの側。
- **代替案**: S2b で、改修提案も、課題に属さないフォローアップとして書く。上の理由（結び付きの決め直しが、S5 と二度手間になる）で採らない。
- **影響範囲**: S5 までは、改修提案の判断点が起票した課題が、分類の対象になる（見直し前と同じ）。

### 本文を Markdown として整える部品（S2c）

- **採用案**: `marked` の字句解析（本文を、見出し・段落・表などの部分の並びに分ける所）だけを使い、その並びから、画面の部品（React の要素）を自前で組み立てる。HTML の文字列は作らず、要素に HTML の文字列を差し込む口（`dangerouslySetInnerHTML`）も使わない。字句解析が「生の HTML」と判定した部分は、書いてある文字のまま出す。リンクは、行き先が `http:`・`https:` のものだけをリンクにする。画像は読み込まず、代わりの文字（と、行き先へのリンク）を出す。`marked` は、いま `mermaid` を通して入っている版を、`web/package.json` の直接の依存に書いて固定する。
- **理由**: 本文（計画・説明・完了条件・問い）は、判断点・委譲先・上流の Issue から来る、外の文字で、そのまま HTML にすると、画面の中でスクリプトが動きうる。画面は、承認の口（計画の承認・反映を保留にした完了の承認）を、ボタンを押すだけで呼べるので、画面の中でスクリプトが動くと、承認まで届く。HTML の文字列を作らない形にすれば、無害にする処理の抜けに頼らずに、この道を構造で閉じられる。画像を読み込まないのは、本文を開いただけで外へ通信が出る（どの課題をいつ見たかが、外に伝わる）のを避けるため。字句解析に `marked` を使うのは、表や入れ子の箇条書きの読み取りを自作すると、誤りが出やすいため（新しく入る物は無く、いま入っている物を直接使うだけ）。
- **代替案**:
  - `marked` で HTML の文字列にし、`DOMPurify` で無害にして、要素に差し込む。どちらもいま入っているが、無害にする設定の誤りや抜けが、そのまま承認の口へ届く道になるので採らない。
  - `react-markdown`（と表のための追加）を足す。要素を組み立てる形で、生の HTML も通さないが、数十の物が新しく入る。いま入っている `marked` で同じ形が作れるので採らない。
  - 字句解析から自作する。依存は増えないが、表・入れ子・コードのブロックの読み取りの誤りが出やすいので採らない。
- **影響範囲**: `web/package.json`（`marked` を直接の依存に）、Markdown の部品（新しいファイル）、本文を出す所（課題の詳細・タスクの詳細・計画の承認）。図（`FigureView`。Mermaid）は、見直し前と同じ部品のまま。flywheel#682 の決定「生の HTML を通さない Markdown の部品を 1 つ入れて、部品の選定まで決める」の持ち越し分。

### 画面のボタンで受ける範囲を広げない（S2c）

- **採用案**: S2c の画面のボタンで受ける書き込みは、見直し前と同じ 3 つ（計画の承認・反映を保留にした完了の承認・サイクルを回す）のままにする。試作にある、問いに答えるボタン・取り込みのチェックとボタン・フォローアップを済みにする・捨てるボタン・計画を作り直すボタンは作らず、その場所に、端末のコマンドの案内を出す。計画の承認の画面の問いの選択肢は、見せるだけで、選べない。
- **理由**: 設計書 §9 は、画面のボタンで受ける範囲を、計画の承認と、反映を保留にした完了の承認に限っている（画面の口には、委譲の子からも届きうるため）。範囲を広げる決定（`ux.md` の決定 26・27）は、子から届かないことの守り方と一緒に、対話の欄を作る S4 で、設計書の決定として足すと決めてある（`ux.md` の未決）。S2c で一部だけ先に広げると、守り方を決める前に口が増える。
- **代替案**: 選ぶだけの回答と、フォローアップを済みにする口だけを、S2c で先に足す。上の理由で採らない（S4 でまとめて決める）。
- **影響範囲**: `internal/server` に `POST` の口は増えない。画面の承認の経路（経路 `ui`・本人確認の方式 `none`）と、core が強制する範囲は変わらない。

### 表示の区分と件数を core が決める（S2c）

- **採用案**: タスクの表示の区分（走っている・あなたを待っている・次に走る・前提を待っている・済み・取りやめ）、課題のタスクの進み、費用の合計、未のフォローアップの件数は、core が決めて、課題のツリーの API が返す。画面は、返ってきた値を出すだけにする。計画の承認の画面のツリーの区分も、承認の要約の API が返す。
- **理由**: 表示の区分は、タスクの状態・前提・保留の 3 つから決まる。画面の側で決めると、同じ決まりを、端末の表示（S4 で作る `flywheel cycle status` など）と二重に持つことになり、食い違う。件数も同じ（未のフォローアップの数え方は、状況の `followups.open` と同じ決まりを使う）。課題の画面は、開いている課題の全部のツリーを 1 回で出すので、課題ごとに詳細を読むと、課題の数だけ呼び出しが増える。
- **代替案**:
  - 画面が、課題ごとに課題の詳細の API を読んで、区分と件数を導く。呼び出しが課題の数だけ増え、決まりが画面に入るので採らない。
  - 課題の一覧の API（`GET …/challenges`）の要素に、タスクと件数を足す。この API は、60 秒ごとと変化の合図のたびに、全部のエージェントの分を読んでいる。ツリーの中身まで毎回運ぶと重くなるので、課題の画面を開いている間だけ読む、別の口にする。
- **影響範囲**: `internal/core`（新しい読み取りの口）、`internal/view`、`internal/server`、型の生成。

### グラフの API を外す（S2c）

- **採用案**: グラフの画面と一緒に、グラフの API（`GET …/graph`）・型・core の口・テスト・照合用の見本・グラフ専用の種・本物のサーバを相手にしたグラフの試験を外す。課題どうしの関係のうち、記録した前提は、課題のツリーの API の `dependencies` と、課題の詳細の `challenge.dependencies`・`dependents` で出す。課題の親子（見直し前の、親の大枠）は、課題のツリーの要素の `parent`・`children` で返し、課題の詳細に、文字で出す。
- **理由**: グラフの API を読むのは、グラフの画面だけ（端末のコマンドには無い）。画面を外した後に API とテストを残すと、使われない形を、型の生成・照合用の見本・種のテストと一緒に、保ち続けることになる。課題の親子は、見直しで、取り込み元の親子を「課題と、そのタスクの初期値」にする形に改めた（S2b）ので、新しく作られる課題どうしの親子は、増えない。
- **代替案**: API は残し、画面だけ外す。上の理由で採らない（課題の親子を返す口が、グラフの API だけだったので、その分は、課題のツリーの要素へ移す）。
- **影響範囲**: `internal/core`（グラフの口と値の集合）・`internal/view`・`internal/server`・`web/src/testing/relation-api.golden.json`・`web/e2e-real`・`Makefile` の `e2e-real`（筋書きを作り替える）・`docs/features/ui-relation-graph.md`（外した旨の注記）。

### 反映の記録は変えず、実行だけを委譲先へ移す（S3a）

- **採用案**: 反映の操作（`operation.kind = release`）・その承認（承認した中身つき）・反映の試行（`operation_execution`）の持ち方と、課題が完了の承認で完了になる順は、見直し前のまま残す。変えるのは、承認済みの反映の操作を実行する所だけで、flywheel が自分で入れる代わりに、委譲先へ「入れてよい」を返す（か、反映の依頼を始める）。委譲先が入れ終えたのを読んだら、反映の操作を実行済みにする。
- **理由**: 完了と反映を 1 回の操作で承認し、記録を分けること（D12）と、反映先に入るものを承認で縛ることは、変えないと決めている（設計書 §21.8）。S2 の決定（「課題 ＞ タスク ＞ フォローアップの持ち方」）も、計画・承認・反映を課題の単位のまま残すとしている。承認の口（端末・対話・画面）と、承認の時点の中身の記録は、反映を誰が実行するかに依らない。
- **代替案**:
  - 課題に「反映待ち」の状態を足し、委譲先が入れ終えてから完了にする。「課題の完了は、成果が反映先へ入ること」（設計書 §21.1）に、状態の名前が近づく。ただし、画面のボタンの完了の承認（反映を保留にする）・反映の操作だけの承認・承認の取り消しと承認し直し、のすべてに新しい状態からの遷移が要り、承認の処理を作り替えることになるので採らない。
  - 反映の操作の表をやめ、契約の実行の記録に承認を結び付ける。委譲先のフローを通らない成果物と、flywheel の外での反映に、結び付ける先が無いので採らない。
- **影響範囲**: `internal/core` の反映の実行（`release_exec.go`・`release_exec_write.go`）を作り替える。承認（`approval.go`・`operation.go`）と、承認待ちの反映の操作の片付け（`release_tidy.go`）は、戻り先（次の節）を除いて変えない。

### 完了から戻す先を、検証中にする（S3a）

- **採用案**: 完了の課題を戻す遷移（T18）の戻り先を、着手中から検証中に改める。「反映先へ入れられない」を理由に戻す場面は無くす。
- **理由**: 見直し前は、flywheel が入れようとして入れられないとき（衝突）に、課題を着手中へ戻し、委譲先に「追従して衝突を解消する」よう差し戻していた。S3 では、反映先とのずれは、委譲先が「入れてよい」を受けたときに自分で取り込んで解き、新しい中身を返す。flywheel に残るのは「中身が、取り込みだけではない形で変わった」ときで、要るのは作り直しではなく、変わった中身の検証と承認のやり直し（設計書 §21.3 の D31）。検証で直しが要ると分かったときは、見直し前と同じに、着手中へ戻って差し戻す。
- **代替案**: 戻り先を着手中のままにし、委譲先へ差し戻してから検証する。中身はすでに変わっていて、委譲先に頼むことが無いのに、差し戻しが 1 回入るので採らない。
- **影響範囲**: `internal/core/transition.go`（T18）、`internal/core/release_reopen.go`（戻すときのタスクの状態・添え書きの処理を外す）、`internal/core/contract_delegate_review.go`、`docs/features/m1-core.md` の遷移表。過去の作業ログの T18 の行（戻り先が着手中）は、そのまま読める。

### 外部システム連携: 「入れてよい」を返せない委譲先は、レビュー待ちを受け取った時点で止める（S3a）

- **採用案**: タスクの実行のレビュー待ちを受け取ったとき、`options` に `land` が無い・中身の識別がちょうど 1 つでない、のどちらかなら、検証中へ進めずに、課題を保留にする。
- **理由**: S3 の flywheel は、自分で反映する処理を持たない。「入れてよい」を返せない相手の成果は、検証と承認を通しても、反映先へ入れる道が無い。完了の検証（費用）とオーナーの完了の承認の後で止まるより、受け取った時点で止めて知らせるほうが、無駄が無い（契約の節の「黙って待たせず、課題を保留にして、オーナーへ知らせる」）。
- **代替案**: 検証と承認は通し、反映の段で止める。承認した後に入れられないと分かるので採らない。
- **影響範囲**: `internal/core/contract_delegate_after.go`・`contract_delegate_review.go`、保留の理由の値の集合。古い版の委譲先との組は、起動はできるが、レビュー待ちで必ず保留になる（S3a を main に入れるのは、claude-harness 側の出荷の後）。

### 外部システム連携: 委譲先が入れられなかったときは、反映の承認を取り消して見せる（S3a）

- **採用案**: 「入れてよい」を返した後に、同じ中身のままレビュー待ちが戻ってきたとき（委譲先が、宛先が動いた以外の理由で入れられなかった）は、反映の承認を取り消して、反映の操作を未承認へ戻す（結果 `land_refused`）。委譲先の書いた理由は、試行の記録に残し、課題の詳細（`flywheel show`）に出す（状況〔`flywheel status`〕に出すのは、結果の語）。オーナーが原因を直して、反映の操作を承認し直すと、次の反映の段が、もう一度「入れてよい」を返す。
- **理由**: このとき、課題はすでに完了で、保留（課題を人間対応待ちにする）は使えない。見直し前から、反映できない理由があるときは、承認を取り消して未承認へ戻し、「あなたの承認を待っているもの」に理由つきで出す形がある（結果が `head_changed`・`limit_reached`・`base_changed` のとき）。同じ形に乗せると、同じ「入れてよい」を自動で返し続けることも無い。契約の節の「課題を保留にして、委譲先の書いた理由をオーナーへ見せる」は、この形で満たす（契約の節の文を、この決定に合わせて直す）。
- **代替案**: 完了の課題にも保留を作れるようにする。保留は、課題の状態を人間対応待ちへ移し、戻り先を持つ作りで、完了の課題に広げると、承認の処理に波及するので採らない。
- **影響範囲**: 反映の試行の結果の値の集合、`internal/view`・画面の文言の表。

### 外部システム連携: 反映の依頼の口と、口が無いリポジトリ（S3a）

- **採用案**: 反映の依頼は、`form: cli` の委譲先の `commands.reflect`（始めるコマンド）で宣言し、状態の確認・答え・取り消しは、その委譲先の `status`・`resume`・`cancel` を共有する。リポジトリごとに、どの委譲先へ頼むかを `reflect_connector` で選べる（省略時は、リポジトリの委譲先が口を持てば、それ）。口が無いリポジトリの、承認済みの反映の操作は、flywheel の外で反映先へ入るのを待ち、入ったのを読んで、実行済みにする（承認した中身と照らすのは、見直し前の「すでに反映先へ入っている」の判定と同じ）。反映の依頼を始めるコマンドが失敗したときは、委譲先の側に実行が残っているかもしれないので、自動では始め直さず、反映の承認を取り消して見せる（見直し前の、契約の `start` の失敗を保留にする扱いと同じ考え方）。
- **理由**: 設計書 §21.3（D32）は、反映を「委譲先の宣言にある 1 つの操作」とし、オーケストレーターが直接作った成果物は「flywheel の外で、オーナーの指示を受けてオーケストレーターが反映先へ入れる」としている。口が無いリポジトリの成果物を、後者と同じ扱いにすれば、スキルを直接呼ぶ形・指示文を直接渡す形だけの宣言でも、課題を最後まで進められる。状況には「flywheel の外での反映を待っている」と出るので、黙って待たせない（契約の節の未決の 2 つ目）。
- **代替案**:
  - 口が無いリポジトリを持つ宣言を、読み込みで止める。契約の形の委譲先を持たないワークスペースが、S3 の flywheel を使えなくなるので採らない。
  - 口が無いリポジトリの分だけ、flywheel が自分で入れる処理を残す。反映の道が 2 本残り、「flywheel はマージを持たない」（設計書 §21.3）に反するので採らない。
- **影響範囲**: `internal/core/connectors_declaration.go`、反映の実行。Tom の宣言の直し（委譲先 `harness-cli` に `reflect` を足し、指示文を直接渡す形のリポジトリに `reflect_connector` を足すか、外での反映にするかを決める）は、S3a を main に入れた後の、ワークスペースの切り替えで行う。

### 承認の真正性: 「入れてよい」を返す条件（S3a）

- **採用案**: flywheel が `land` を返すのは、反映の段だけで、対象の反映の操作が承認済みで、通す中身が、承認した中身か、それに反映先の最新の取り込みだけを足したもので、そのチェックがすべて通っているときだけにする。`{approved_ref}` に入れるのは、その通す中身。オーナーの保留への回答・子の問いを振り分ける判断点（J4）の答えを返す `resume` では、`{approved_ref}` は空の文字列になる。
- **理由**: 見直し前に、flywheel が自分で入れる前に確かめていたこと（承認の有無・承認した中身との一致・チェック）を、そのまま「入れてよい」を返す前の条件にする。反映先に入るものを承認で縛る保証（設計書 §21.8）は、flywheel の側の条件と、委譲先の側の一致の確かめ（契約の節の「足すもの 3」）の 2 つで保つ。契約は、`{approved_ref}` が空の `land` を、委譲先が入れないと決めているので、回答の文がたまたま `land` でも、反映先へは入らない。
- **代替案**: 中身の一致を、委譲先の確かめだけに任せる。変わった中身の判定を委譲先の申告に頼ることになり、設計書 §21.3（D31）の「判定は core が持つ」に反するので採らない。
- **影響範囲**: 反映の実行、`internal/core/contract_delegate.go`（差し込み）。

### 委譲先が値で返したことを、core が照らす（S3a）

- **採用案**: 委譲先の宣言の `required_facts` を満たさないレビュー待ちには、完了の検証（J5）を起動せず、core が、決まった形の添え書きで `respond` を返す。同じ契約の実行で 2 回続いたら、保留にする。
- **理由**: 設計書 §21.3 は、機械的に確かめられることを「委譲先が契約の結果に値で返し、core が LLM なしで確かめる」としている。測った期間に、「自己レビューが不明」でオーナーへ上がった問いが 15 件あった（設計書 §21.5）。満たしていない値は、判断ではなく事実なので、判断点の費用を使わずに差し戻せる。2 回で止めるのは、同じ差し戻しを繰り返さないため（スーパーバイザーが入る S4 で、止めた先を、スーパーバイザーに改める）。
- **代替案**:
  - 満たさないときは、すぐ保留にする。委譲先が自分で直せること（自己レビューをやり直す）を、オーナーに上げることになるので採らない。
  - J5 の入力に値を渡すだけにして、判断は J5 に任せる。機械的に決まることに判断点を使い、見直し前の「判断できない」が残るので採らない。
- **影響範囲**: `internal/core/connectors_declaration.go`、`internal/core/contract_delegate_after.go`、J5 の入力と指示文（`internal/invoker/prompts/j5.md`）。

### DB スキーマ: 契約の実行と成果物に足す列（S3a）

- **採用案**: マイグレーションを 1 本足す（スキーマの版は 28 になる）。
  - `run_artifact.role`（文字列。無ければ NULL）。
  - `run.operation_id`（反映の操作のために呼んだ契約のコマンドの実行〔反映の段・完了から戻す前の読み・片付けが作る実行〕の印。NULL は委譲の段の実行と過去の行。印の付いた実行は成果物を持たず、課題の最後の委譲の実行・最後の契約のコマンドを読む所〔完了の検証の入力・回収された start の保留・指摘を届けたかの判定〕から外す）。
  - `hold.reason`（保留の理由。NULL 可。値は `land_unavailable`・`content_ref_invalid`・`facts_unmet`、S3b で足す `integration_ref_invalid`・`delegate_ended`・`merged_unverified` など。ほかの保留と過去の行は NULL。保留の理由の見分けと、`facts_unmet` の保留への回答で回数を戻す対象の絞り込みは、問いの文でなくこの列で行う。状況や課題の詳細の出力には、S3a では出さない）。
  - `contract_run.kind`（必須。`task` か `reflect`。既定は `task`）・`operation_id`（反映の依頼が対象にする反映の操作。タスクの実行では NULL）・`requested_options`（JSON の配列。無ければ NULL）・`content_ref`（レビュー待ちの中身の識別。無ければ NULL）・`facts`（JSON の対応。無ければ NULL）・`facts_unmet_count`（必須。既定 0）・`land_ref`（最後に返した「入れてよい」の中身。返していなければ NULL）・`land_delivered`（必須。既定 0。`land_ref` の「入れてよい」を、委譲先が受け取ったと分かっているか）。
  - 過去の行は書き換えない（`kind` は既定の `task` になる）。索引と一意の制約は変えない（「終わっていない契約の実行は課題ごとに 1 本」のまま。タスクの単位に改めるのは S3b）。反映の依頼は、完了の課題に対して始めるので、同じ課題のタスクの実行とは重ならない（待っている実行があれば、反映の依頼は始めない）。
  - `land_ref` は、「入れてよい」を返す前に書き、取り消す結果になったときと、完了から戻すときに消す（NULL は、いまの承認では、まだ返していないことを表す）。
  - 反映の試行の表（`operation_execution`）は変えない。結果の値の集合だけが変わる（列に制約は無く、値は core が検査する）。
- **理由**: 「入れてよい」を返してよい相手か（`requested_options`）・何を通したか（`land_ref`）・戻ってきた中身（`content_ref`）は、次のサイクルの反映の段が、委譲先を読む前に要る。読むたびに決め直せないので、記録に持つ。承認し直さずに通した記録（契約の節の未決の 1 つ目）は、反映の試行の `approved_head`（承認した中身）と `observed_head`（通した中身）で、見直し前から残る形になっているので、列を足さない。
- **代替案**: 反映の依頼を、契約の実行とは別の表に持つ。状態の確認・費用の差分・取り消しの処理が、契約の実行と同じなので、表を分けると同じ処理が 2 つになる。採らない。
- **影響範囲**: `internal/core/internal/store/migrations`、全表を埋めるテストの支え（`coretest.FillAllTables`）、スキーマの版を直に書いているテスト。版 27 の書き出しは、版 28 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### 作業ツリーの持ち主のキーを足さない（S3a）

- **採用案**: 作業ツリーの持ち主は、見直し前と同じに、委譲の形で決まるままにする（`form: cli` は委譲先が作って片付け、`form: plugin`・`brief` は flywheel が払い出す）。宣言にキー（`slot_owner`）は足さない。
- **理由**: 設計書 §21.3 は「持ち主は委譲先の宣言ごとに選ぶ（`slot_owner` を足す）」としているが、いまの 3 つの形は、形と持ち主が 1 対 1 に決まっていて、選ぶ余地が無い。使わないキーを足すと、宣言の検査と文書だけが増える。形と持ち主が食い違う委譲先が出てきたら、そのとき足す。
- **代替案**: 設計書のとおりにキーを足し、既定を形から決める。上の理由で採らない（設計書 §21.3 に、S3a では足さなかった旨を注記する）。
- **影響範囲**: 無し（設計書の注記だけ）。

### 衝突の解消を、承認し直さずに通す形は S3b で入れる（S3a）

- **採用案**: S3a では、承認した中身からの変わり方が「反映先の最新の取り込みだけ」のときだけ、承認し直さずに通す（見直し前と同じ）。衝突の解消を含む変わり方は、関係のない変更と同じに、検証と承認をやり直す。衝突の解消を、完了の検証の判断点（J5）が差分で確かめて、承認し直さずに通す形（設計書 §21.3 の D31）は、S3b で入れる。
- **理由**: 衝突の解消を通す形は、判断点に「承認した中身からの差分」を渡す新しい入力と、通した記録・オーナーへの知らせが要る。効くのは、統合先に集めた課題を反映先へ上げるとき（タスクの成果が集まった後で、反映先とのずれが大きい）で、統合先を入れる S3b と一緒に作るほうが、確かめる場面がある。S3a は、タスクが 1 個の課題だけを進め、動きを見直し前とそろえる。
- **代替案**: S3a で入れる。確かめる場面（統合先から上げるときの衝突）が S3b まで無いので採らない。
- **影響範囲**: 設計書 §21.3 の保証の文言（「検証を通った衝突の解消」）は、S3b が入るまで、S3a の動き（取り込みだけ）より広い。用語集の「反映」の行に、その旨を書く。

### DB スキーマ: タスクの単位の一意の制約と、足す列（S3b）

- **採用案**: マイグレーションを 1 本足す（版 29）。
  - 「終わっていない実行は課題ごとに 1 本」の一意の索引（`idx_run_active_challenge`）を、「課題とタスクの組ごとに 1 本」に作り直す（`run (challenge_id, COALESCE(task_id, 0)) WHERE result IS NULL`）。タスクに結び付かない実行（計画・学び・課題の単位の確かめ・反映の依頼のコマンド）は、見直し前と同じに、課題ごとに 1 本。
  - 「終わっていない契約の実行は課題ごとに 1 本」の一意の索引（`idx_contract_run_active_challenge`）も、同じ形に作り直す（`contract_run (challenge_id, COALESCE(task_id, 0)) WHERE ended_at IS NULL`）。反映の依頼（`task_id` が空）は、課題ごとに 1 本のまま。
  - `task` に `budget_impl_micros`・`budget_review_micros`（整数。空を許す）を足す。
  - `challenge` に `integration_ref`（文字列。空を許す）を足す。
  - `contract_run` に `verified_ref`（文字列。空を許す）を足す。
  - `approval` に `task_id`（タスクへの参照。空を許す）を足す。
  - `run` に `reflect`（0 か 1。既定は 0）を足す。過去の行のうち、反映の操作を持つ行（`operation_id` がある）は、1 にする。
  - ほかに、過去の行は書き換えない。
- **理由**: 同じ課題のタスクを同時に走らせるには、実行の重なりを止める単位を、課題からタスクに改める必要がある（S2a の「一意の制約をタスクの単位に改める時期」で、ここまで延ばした）。タスクに結び付かない実行を課題ごとに 1 本のままにするのは、計画の作り直しや学びが、同じ課題で重ならない保証を残すため。
- **代替案**: 一意の索引を外して、コードの読みだけで確かめる。同時に始めた 2 つの書き込みを止められないので採らない。タスクの状態に「統合先へ入れている」を足す。値の集合・表示・型の追従が広がるわりに、契約の実行の記録（検証した中身）で同じことが読めるので採らない（画面での見せ方は S3d）。
- **影響範囲**: 課題に 1 本と決め打ちして契約の実行を読む所（反映の段の対応づけ・完了から戻す前の読み・取り下げ・計画の作り直し・子の上流の状態・取り消し）を、タスクか操作で絞る読みに改める。同じタスクの、判断点の実行（タスクの検証）と、契約のコマンドの実行は、同じ索引に載るので、同時には 1 本だけになる（後から始めようとした側が、飛ばす）。サイクルの中では段が順に動くので、重なるのは、別のプロセス（手の操作）が同時に動いたときだけ。書き出しと再構築（`Export`/`Import`）に、足した列を通す。

### 統合先へ入れる関所は、タスクの検証。反映の操作は作らない（S3b）

- **採用案**: 統合先を使う課題のタスクの成果は、J5 が「満たした」とした中身（検証した中身）だけを、「入れてよい」で統合先へ入れる。オーナーの承認は求めず、反映の操作（不可逆操作）も作らない。検証の後に中身が変わったときは、統合先の最新の取り込みだけ（衝突の解消が無い）なら検証し直さずに通し、それ以外は検証し直す。
- **理由**: 設計書 §21.2（統合先へ入れる関所は、人の承認ではなく完了の検証）。統合先は反映先に届かないので、不可逆操作の承認の仕組み（本人確認・承認した中身の固定）に載せない。それでも「検証していない中身が統合先へ入らない」ことは、反映先と同じ形（中身の識別を付けた `land` と、core による変わり方の判定）で保つ。
- **代替案**: 統合先へ入れることも反映の操作にして、自動で承認する。承認の記録が「人が承認した」の意味でなくなるので採らない。
- **影響範囲**: 反映の段は、統合先を使う課題のタスクの実行を扱わない（委譲の段の先頭の状態の確認が進める）。統合先へ入れた記録は、契約の実行の記録（検証した中身・返した中身）と、成果物の記録（入れた後の統合先の中身）で読む。

### 課題の単位の確かめは、上げる依頼が用意した実物で行う（S3b）

- **採用案**: 全部のタスクが統合先へ入ったら、完了の承認の前に、上げる依頼を始める。委譲先が用意した実物（開発では、統合ブランチから既定ブランチへの PR）とその中身を、課題の単位の確かめ（J5）と、オーナーの完了の承認・反映の操作の承認に使う。承認の後、承認した中身を付けて「入れてよい」を返す。
- **理由**: 契約の節の「足すもの 4」のとおり。オーナーが承認の前に見る実物と、承認する中身を、委譲先が用意する形にすると、反映の操作・承認・反映の段を、S3a の形（成果物 1 つに、反映の操作 1 つ）のまま使える。
- **代替案**: 統合先の中身の識別を直接、承認の対象にして、承認の後に上げる依頼を始める。承認の時点で、反映先の最新の取り込みと、上げる前の検証が済んでいないので採らない。
- **影響範囲**: 反映の依頼に、反映の操作がまだ無い時期ができる（`operation_id` が空）。完了でない課題の反映の依頼を、委譲の段が読む。

### 課題の単位の確かめが満たしていないときは、保留にして、計画の作り直しで直す（S3b）

- **採用案**: 課題の単位の確かめが「満たしていない」のとき、課題を着手中へ戻して保留にする。オーナーは、計画を作り直す回答（`--replan`）で、直すタスクを足せる（済みのタスクは残る。同じ統合先に続けて集まる）。
- **理由**: この時点では、全部のタスクの実行が終わっていて、指摘を返す相手がいない。直すには新しいタスクが要り、タスクを足すのは計画の承認の範囲。承認なしでタスクを足す形（設計書 §21.2 の「計画の後にタスクを足す」）と、スーパーバイザーが受ける形は S4。
- **代替案**: J5 が、直すタスクを自分で足す。判断点の役割（確かめる）を超えるので採らない。
- **影響範囲**: 保留の理由の値が 1 つ増える。J2 の入力に、済みのタスクと J5 の指摘が要る。完了の差し戻し（T15）も、同じ理由で、統合先を使う課題では、計画を作り直す道へ送る。タスクが 1 個で統合先を使う課題は、タスクの検証と、課題の単位の確かめの 2 回、J5 が走る（設計書 §21.3 の、タスクが 1 個でも統合先を使う例外の形。費用は増えるが、流れを分けない）。保留は課題の状態なので、1 つのタスクの保留が、同じ課題のほかのタスクの検証と「入れてよい」を、回答まで止める（保留をタスクに結び付けるのは、回答の後に記録を直す相手を決めるため。タスクごとに止める形は S4）。

### 統合先を使う課題は、リポジトリを 1 つに限る（S3b）

- **採用案**: 統合先を使う課題で、タスクのリポジトリが 2 つ以上にまたがるものは、計画の検査で不正にする。検査をすり抜けた課題は、保留の理由 `tasks_blocked` で保留にする。数えるのは、取りやめでないタスク（済みを含む）。
- **理由**: 統合先はリポジトリごとにでき、上げる依頼・反映の操作・完了の承認の対象が、リポジトリの数だけ要る。課題に記録する統合先の識別と、課題の単位の確かめの入力を、1 つに保つ。Tom の課題は、いま、どれも 1 つのリポジトリで閉じている。
- **代替案**: リポジトリごとに統合先と上げる依頼を持つ。必要になったら足す（flywheel の Issue にする）。
- **影響範囲**: 複数のリポジトリにまたがる変更は、リポジトリごとに課題を分ける。

### 予算は、タスクごとの見込みを持ち、合計を課題の上限にする（S3b）

- **採用案**: J2 が、タスクごとに実装の枠とレビュー対応の枠を出す。課題の上限は、その合計。計画の承認で、合計（とタスクごとの額）を承認する。各タスクの実行は、自分の枠が上限で、超えたら、そのタスクだけを止めて保留にする。増額は、タスクを指定して承認する（オーナーの決定 2026-11-20）。
- **理由**: 課題に 1 つの枠を分け合うと、先のタスクが使い切って、後のタスクが起動できなくなる。設計書 §21.2 の「足した後の予算の合計が、承認した上限を超えるなら、必ずオーナーへ問う」（S4）に、そのままつながる。
- **代替案**: 課題に 1 つの枠のまま。上のとおり採らない。
- **影響範囲**: J2 の出力の形・検査、タスクの記録、使った額の数え方、`flywheel budget` の引数、増額の承認の記録。タスクが 1 個の課題の動きは、変えない（タスクが値を持たなければ、見直し前の決め方の値になる）。

### 子に対応するタスクは、子の本文を、文面と検証の入力に入れる（S3b。flywheel#801）

- **採用案**: タスクが取り込み元の子に対応するとき、取り込みのときに記録した子の題名・URL・本文を、タスクの文面と、タスクの検証の入力に入れる。上流を読み直さない。
- **理由**: 複数のタスクを走らせると、親の本文だけでは、タスクごとの指示と確かめができない。記録した値を使うのは、タスクの文面を、core が LLM も上流の読みも使わずに組み立てる決まり（S3a）を保つため。計画（J2）も、同じ記録を読んでタスクを作っている。
- **代替案**: 起動と検証のたびに、子を上流から読む。読めないときの扱いが増えるので採らない（子が閉じた・無くなったことの見せ方は flywheel#800）。
- **影響範囲**: 取り込みの後に子の本文が上流で変わっても、文面には、記録した時点の本文が入る。

### 衝突の解消を通す形と、フォローアップをタスクに上げる形は、S3c に分ける（S3b）

- **採用案**: S3b は、切り離せない部分（複数のタスク・統合先・課題の単位の確かめ・上げる依頼・予算・子に対応するタスク）だけにする。衝突の解消を、J5 が差分で確かめて承認し直さずに通す形と、フォローアップを開いている課題のタスクに上げる形は、次の区切り（S3c）にする。画面は、その次（S3d）にする（オーナーの決定 2026-11-20）。
- **理由**: 切り離せない部分だけで、S3a と同じくらいの大きさになる。動く最小の形を先に Tom で試す。
- **代替案**: 1 回で入れる。確かめる量が大きくなるので採らない。
- **影響範囲**: S3c が入るまで、衝突を直した中身は、S3a と同じに、検証と承認をやり直す（統合先へ入れるときも、検証し直す）。フォローアップは、新しい課題に上げる道だけ。

### 承認の真正性: 承認していない差分を、判断点の確かめだけで反映先へ入れる（S3c）

- **採用案**: 設計書 §21.3（決定 D31。2026-11-17 のオーナーの決定）のとおり。承認し直さずに通すのは、変わり方が「衝突の解消あり」のときだけで、その見分けと、直した差分は、core が上流のアダプタの比較の口から自分で読む（委譲先の申告は使わない）。取り込みのほかにコミットが 1 つでも足されていれば、この道に入らない。J5 が確かめた中身と、「入れてよい」に付ける中身が同じことを、返す直前に確かめる。
- **保証の文言**: 「反映先に入るのは、承認した中身か、それに反映先の最新の取り込みと、検証を通った衝突の解消だけを足したもの」（設計書の文言が、S3c で、実際の動きと一致する）。
- **残る危うさ**: J5 が、振る舞いを変える差分を、衝突の解消として通すこと。備えは、チェックがすべて通っていること・通したことと直した差分の記録（後から読める）・課題の詳細への表示。
- **設計書との差**: 決定 D31 は「記録して、オーナーへ知らせる」と書く。S3c は、記録と、課題の詳細（`show`・API）への表示までを作り、画面での表示は S3d、対話の欄での知らせ（`ux.md` の決定 25）は S4 で作る。それまで、通したことは、オーナーが課題の詳細を開いて読む。
- **代替案**: 衝突の解消ありでも、常に承認し直す（S3b まで）。同時に走るタスクが増えると、やり直しが増えるので採らない。スーパーバイザーかオーケストレーターが確かめる。設計書 §21.3 で採らないと決めている。
- **影響範囲**: 反映の段、統合先へ入れる所、J5。

### DB スキーマ: 確かめ待ちの中身と、通した中身（S3c。版 30）

- **採用案**: `contract_run` に、`fix_pending_ref`（確かめ待ちの中身）・`fix_verified_ref`（反映先宛てで、衝突の解消の確かめを通した中身）・`fix_rejected_ref`（反映先宛てで、確かめが通らなかった中身）を足す（どれも NULL 可。過去の行は書き換えない）。確かめが通らなかったとき、J5 は `fix_rejected_ref` を書くだけで、反映の承認の取り消しは、次の反映の段が、S3a の道（結果 `head_changed`）で行う（反映の試行の記録と、反映の操作の状態を書くのを、反映の段だけにする）。統合先宛てでは、通した後に `verified_ref` を改めるので、`fix_verified_ref` は使わない。通した履歴（一覧）は、表を足さず、作業ログの記録（`conflict_fix_passed`）から読む。反映先宛ての確かめ待ちは、反映の試行の結果の値 `waiting_fix_check` を足して記録する（`waiting_delegate` は「委譲先の実行を待つ」の意味なので、使い回さない）。
- **理由**: 確かめは、「入れてよい」を返す前に要る。反映の試行の記録は、返すとき・待つときに作るので、確かめの状態を持つ場所にならない。承認した中身（反映の承認の記録）は、書き換えない（何を承認したかの記録を保つ）。
- **代替案**: 反映の試行の表に結果を足す（上の理由で採らない）。通した衝突の解消の表を足す（作業ログで足りるので採らない）。
- **影響範囲**: マイグレーション 1 本、書き出しと再構築。

### フォローアップを、開いている課題のタスクに上げる形は、S4 へ送る（S3c）

- **採用案**: S3c は、衝突の解消だけにする。フォローアップを、開いている課題のタスクに上げる形は、S4（計画の後にタスクを足す）で一緒に決める（オーナーの決定 2026-11-21）。
- **理由**: いまフォローアップを書くのは、学びの判断点（J6）だけで、J6 の対象は、完了・取り下げ・保留中の課題。フォローアップが付いた課題が開いているのは、保留中の課題に J6 が書いたときだけになる。走っているタスクから出るフォローアップ（スーパーバイザーの手・委譲先の軽い指摘）は S4 から。着手中の課題にタスクを足すには、足すタスクの完了条件と枠を誰が書くか・課題の上限が増えることの承認の形・上げる依頼が始まった後の戻し方を決める必要があり、どれも S4 の「計画の後にタスクを足す」と同じ論点。
- **影響範囲**: S4 が入るまで、フォローアップは、新しい課題に上げる道だけ（S2b のまま）。

### S3c と S3d を、並べて進める（S3c）

- **採用案**: S3c（core）と S3d（画面）は、S3b が main に入った後、統合ブランチを 2 本立てて、並べて実装する。main へは、S3c、S3d の順に入れ、S3d の側で、S3c を取り込み直す（オーナーの決定 2026-11-21）。S3d の仕様は、この文書と別の文書（`docs/features/core-redesign-s3d.md`）に書き、S3d を main に入れるときに、この文書へ畳む。
- **理由**: S3c は core と J5、S3d は画面と API の値で、触るファイルがほぼ重ならない。重なるのは、S3c が足す API の値（`conflict_fixes[]`・`fix_pending_ref`）を S3d が画面に出す所だけで、S3d の側で、後から足せる。この文書を 2 本のブランチで同時に書き換えると、文書の全体が衝突するので、S3d の仕様は別の文書にする。
- **影響範囲**: スライスの表の出荷条件。

## 機能全体の設計

### アーキテクチャ決定

- 区切りの順は、外す → 土台 → 委譲先との境界 → 長く走るサイクルとスーパーバイザー → 仕上げ、とする。先に外すのは、ストアの形を変えるときに運ぶコードを減らすため。土台を次に置くのは、後の区切りがどれも「タスク」を単位にするため。
- 土台（S2）は、ストアと計画（S2a）→ 入口と出口（S2b）→ 画面（S2c）の順に分けて入れる。S2b と S2c は S2a のストアを使い、S2c は S2b の API を使う。1 回に入れる量を、全体を確かめられる大きさ（S1 は 135 ファイル・受入基準 68 件）に近づけるために分ける。
- 委譲先との境界（S3）は、反映を委譲先に任せる（S3a）→ 複数のタスクと統合先（S3b）の順に入れ、その後、衝突の解消（S3c）と画面（S3d）を並べて進める（フォローアップをタスクに上げる形は S4 へ送った）。S3a は、進める課題の形（タスクが 1 個）を変えずに、反映を誰が実行するかだけを変える。先に core の反映の処理を外しておくと、S3b でタスクの単位に付け替えるコードが減る（S1 を先に置いたのと同じ理由）。
- サイクルの構造は、flywheel に決まった形として持つ。YAML の定義から描いて調整できるようにするのは、この機能の範囲外（flywheel#265・#266）。
- claude-harness 側の受け口（Issue の無い入力・統合ブランチを作る口・承認した中身つきで既定ブランチへ入れる口・統合ブランチから上げるフロー・任意の成果物を上げる口・取り込んで新しい中身を返して待つ口・自己レビューの値の返却）は、別のリポジトリなので、この文書に契約（flywheel が渡すもの・受け取るもの）を書き、実装は claude-harness 側の Issue にする。契約は、S3 を待たず、S2a の実装と並行して先に書いた（S3 の出荷条件が claude-harness 側の出荷なので、先に始める）。下の「委譲先との契約（S3 で使う受け口）」。契約の既存の値の意味は変えない（レビュー待ちへの答え `ready` は「flywheel が反映まで済ませた」の意味のまま残し、新しい意味には新しい値を足す）。
- 画面の行き先は、URL のハッシュに持つ（S2c）。サーバは、`/` で画面を返すだけのままにし、画面の中の行き来のための受け口を増やさない。ルーティングのライブラリは足さず、ハッシュを読んで画面を選ぶ小さな部品を持つ。
- 画面ごとに要るデータ（課題のツリー・課題の詳細・承認の要約・フォローアップ・作業ログ）は、その画面を開いている間だけ読む（S2c）。全部のエージェントについて常に持つのは、見直し前と同じく、状況・課題の一覧・サイクル・あなたを待っているものの横断だけにする。
- S1 で委譲の計画の処理（`planDelegation`・`executePlan`）を単純にするとき、S2 でタスクの単位に付け替えることを見越して、候補 1 件を 1 つの単位として扱う形にとどめる（タスクの概念は S1 に持ち込まない）。

### 実装計画（チケット分解の見通し）

S3c の分け方の案（最終の分解は `/create-ticket` で行う）。

0. S3b の全体のレビューで残した 3 件の直し（flywheel#915。S3c の統合ブランチに、最初に入れる。受入基準は、その Issue が持つ）。
1. ストア: マイグレーション（版 30）。足す 3 列、結果の値と `action` の値、書き出しと再構築。
2. 衝突の解消の確かめ: J5 の対象（確かめ待ちの中身を持つ実行。完了の課題を含む）、入力（直した差分）、指示文、結果の書き方（統合先宛て・反映先宛て）、書く直前の確かめ。
3. 統合先へ入れる所: 変わり方の分けを 2 つ（取り込みだけか、それ以外か）から 4 つに改める（`settleMovedContent` の返しを、変わり方の値にする）。衝突の解消ありのときに確かめ待ちにする、タスクの検証の対象選びの条件に「確かめ待ちの中身が無い」を足す、中身がさらに動いたときの見分け直し、消す所。
4. 反映の段: 起点を通した中身にする、衝突の解消ありのときに確かめ待ちにする（承認を取り消さない。結果 `waiting_fix_check`）、通した中身で「入れてよい」を返す、通らなかった中身なら S3a の `head_changed` の道を通す、消す所。
5. 記録と表示: 作業ログ、`conflict_fixes[]`・`fix_pending_ref`、`show` の文の出力、型の生成。
6. 文書。

順は、0 → 1 → 2 → 3・4（並行にできる。3 は `integration_land.go`、4 は `release_exec.go`・`release_contract.go`）→ 5 → 6。

費用の見込み（実装の分）: 2・4 が各 15〜25 USD、3・5 が各 10〜18 USD、0・1・6 が各 6〜12 USD。合計は約 70〜120 USD。

## 委譲先との契約（S3 で使う受け口）

区切り S3（委譲先との境界）で flywheel が委譲先へ渡すもの・受け取るものを、ここに決める。S3 の出荷条件が委譲先（claude-harness）の側の出荷なので、S3 の仕様より先に書く（オーナー 2026-11-18）。この節は、契約（外から見える形）だけを決める。flywheel の側の実装（宣言のキー・記録の持ち方・受入基準）のうち、S3a の分は、上の「機能要件」と「クリティカル設計決定」に書いた。統合先を使う分（S3b）も、同じ 2 つの節に書いた。claude-harness の側の作り（ワークフローの段・入力の名前・ブランチの名前）は、claude-harness の側で決める。

調べた時点: flywheel は main b2675f2、claude-harness は main c21a1fc（2026-11-18）。

### いまの契約（版 1）と、変えないもの

- 契約のコマンドは、始める（`start`）・状態を読む（`status`）・答えて再開する（`resume`）・取り消す（`cancel`）の 4 つ。出力は JSON 1 つで、形は `docs/features/m3-invoker-delegation.md` の「接続ツールとの契約」が正本。
- 出力のキー（`contract_version`・`run_id`・`state`・`summary`・`requested_action`・`artifacts`・`cost_usd`）と、値の集合（`state` の 5 つ・`requested_action.kind` の 4 つ・`requested_action.decider` の 3 つ・`artifacts[].kind` の 4 つ）は変えない。
- レビュー待ち（`requested_action.kind` が `review`）への、いまの 2 つの答えの意味は変えない。`respond` は「直してほしい（理由は `note`）」、`ready` は「flywheel の側で反映まで済ませた」。
- 契約の版は 1 のままにする。下に足すものは、どれも「知らない側が読み飛ばせる」か「使う側が、相手が受けると分かったときだけ使う」形にする。
- 出力の、知らないキーは読み飛ばす（いまの flywheel の作りがそうなっている。これを契約の決まりにする）。
- 版を上げるのは、次のどれかをするとき（これまで文になっていなかったので、ここに書く）: すでにあるキーや値の意味を変える。値の集合の外の値を、呼ぶ側が受けると宣言していないのに出す。必須のキーを足す・消す。`requested_action` を複数にする。
- 新旧の組み合わせごとの動き:
  - 新しい委譲先と、いまの flywheel: flywheel は、新しい入力を渡さず、`land` も返さない。委譲先は、いまと同じに動く（`respond`・`ready` の動きを変えない。新しい入力を受けていない実行では、統合先を使わず、`role` の付いた成果物も出さない。`facts` は、知らない側が読み飛ばせる任意のキーなので、出してよい）。
  - いまの委譲先と、S3 の flywheel: 支えない。S3 の flywheel は、自分で反映する処理を持たないので、レビュー待ちの `options` に `land` が無い委譲先の成果を、宛先へ入れる道が無い。黙って待たせず、課題を保留にして、委譲先が `land` を受けられないことをオーナーへ知らせる。S3 を main に入れるのは、claude-harness の側の出荷の後（スライスの表の出荷条件）。
  - 宣言の差し込みの集合は、flywheel の版で決まる（契約の版は、出力の形の版）。いまの flywheel は、知らない差し込みを宣言の誤りとして止める。宣言に新しい差し込みを書くのは、そのワークスペースを S3 の flywheel に切り替えるときにする。

### 足すもの 1: 取り込み元の無いタスクを渡す（始めるときの入力）

- flywheel は、タスクの文面を 1 つのファイルに書き、その場所を渡す。宣言の `start` に書ける差し込みに、次の 4 つを足す。
  - `{task_file}`: タスクの文面のファイルの絶対パス。UTF-8 の Markdown。中身は、core が LLM を使わずに組み立てる（背景〔方針・論点の決定・完了したら見えるもの・やらないこと〕、指定のタスク〔題名・何をするか・完了条件・やらないこと〕、ツリーのほかのタスクの題名の一覧と「ほかのタスクは範囲外」の明記）。ファイルは、その実行が終わるまで消さない。
  - `{task_id}`: タスクの ID（`T-<番号>`）。これを受けた委譲先は、作業ツリーやブランチの名前を、タスクごとに重ならないように、この ID から決める（取り込み元の番号からは決めない。同じ取り込み元を持つタスクが、同時に走りうるため）。
  - `{uses_integration}`: この課題が統合先を使うか（`true` か `false`）。
  - `{challenge_id}`（いまもある）: 課題の識別。統合先を使うとき、同じ課題のタスクを同じ統合先へ集める鍵にする。
- 取り込み元（Issue）があるタスクでは、いまの差し込み（`{issue_number}`・`{issue_url}`・`{external_key}`）も一緒に渡せる。委譲先は、文面のファイルと取り込み元の、少なくとも片方があれば始められるようにする。両方あるときは、文面のファイルを作業の範囲の正本とし、取り込み元は成果物からの参照（開発では、PR が Issue を閉じる書き方）に使う。
- 委譲先は、文面のファイルを解釈して分岐しない（作業する側へ、要件の文面としてそのまま渡す）。
- 値の無い差し込みは、空の文字列で渡る（引数の数は変えない）。委譲先は、空の文字列を「無い」と読む。S3 の flywheel は、`{task_file}` を書いた宣言では、取り込み元の無いタスクにも、取り込み元の差し込みを空の文字列にして起動する。
- どのタスクにどの取り込み元を渡すかは、「クリティカル設計決定」の「取り込み元とタスクの対応と、委譲先へ渡す取り込み元（S2b）」で決めた（対応する子を持つタスクには、その子。持たないタスクには、承認済みの計画のタスクが 1 個なら課題の取り込み元、2 個以上なら渡さない）。

### 足すもの 2: 統合先

- 統合先の名前と作り方は、委譲先が決める。`{uses_integration}` が `true` のとき、委譲先は、`{challenge_id}` から決めた統合先を使い、無ければ作る。flywheel は、統合先を作らず、名前も決めない。
- 成果を入れる先を、宛先と呼ぶ。統合先を使うタスクの成果の宛先は統合先、使わないタスクの成果の宛先は反映先（開発では既定ブランチ）にする。
- 委譲先は、統合先を使う実行の成果物に、統合先の識別と、その時点の中身の識別を足して返す。成果物の要素に、任意のキー `role` を足し、値 `integration` で印を付ける（開発では、`{"kind": "branch", "ref": <統合ブランチの名前>, "role": "integration"}` と `{"kind": "commit", "ref": <統合ブランチの先頭のコミット>, "role": "integration"}`）。`role` の無い要素は、いまと同じく、そのタスクの成果物。
- `role` が `integration` の要素を出すのは、`{uses_integration}` に `true` を受けた実行だけにする（この入力を渡さない、いまの flywheel へは出さない）。出すときは、統合先の識別（`branch`）と中身の識別（`commit`）を、1 つずつ出す。
- 成果を統合先へ入れて終えた実行（`succeeded`）の成果物には、入れた後の統合先の中身の識別を出す（flywheel は、課題の全体の検証と、完了の承認の対象の中身に、これを使う）。

### 足すもの 3: 「入れてよい」の答え（`land`）と、宛先が動いたときのやりとり

レビュー待ちへの答えに、新しい値 `land` を足す。意味は「検証（と、要るときは承認）を通ったので、この中身を宛先へ入れてよい」。

- flywheel は、`land` と一緒に、通した中身の識別を渡す。宣言の `resume` に書ける差し込みに、`{approved_ref}`（開発では、通した先頭のコミット）を足す。
- 委譲先は、`options` に `land` を入れたレビュー待ちの成果物に、そのタスクの成果のいまの中身の識別（`kind` が `commit` で、`role` の無い要素）を、ちょうど 1 つ出す。flywheel は、これを検証と承認の対象の中身として記録し、`{approved_ref}` に使う。この要素が無い・2 つ以上あるレビュー待ちには、flywheel は `land` を返さず、課題を保留にする。
- 委譲先は、レビュー待ちで `land` を受けられるとき、`requested_action.options` に `land` を入れる。flywheel は、`options` に `land` があるときだけ `land` を返す（無い相手との組は、上の「新旧の組み合わせごとの動き」）。
- `land` は、flywheel が、通した中身を付けて自分で返す答えにする。オーナーへの問いの選択肢や、子の問いを振り分ける判断点（J4）の選択肢には出さない。委譲先は、`{approved_ref}` が空の `land` を、下の 3（一致しない）として扱い、宛先へ入れない。
- `land` を受けた委譲先の動き:
  1. 成果物のいまの中身が `{approved_ref}` と一致し、宛先の最新を含んでいる → 宛先へ入れる（入れる操作にも、中身の一致の条件を付ける。開発では、先頭のコミットが一致するときだけ通るマージ）。その後、片付けて、実行を終える（`succeeded`）。
  2. 一致するが、宛先が動いていて、成果物が宛先の最新を含んでいない（衝突が無くても同じ） → 宛先の最新を成果物へ取り込み、宛先へは入れずに、新しい中身を成果物に出して、もう一度レビュー待ちで待つ。
  3. 一致しない → 宛先へ入れずに、いまの中身を成果物に出して、もう一度レビュー待ちで待つ。
  4. 宛先が動いた以外の理由で入れられない（チェックが通っていない・宛先の保護の決まり） → 宛先へ入れずに、理由を `summary` と `requested_action.text` に書いて、もう一度レビュー待ちで待つ（中身は変えない）。続けられないときは、失敗で終える。
- 委譲先は、`land` を受け付けたら、`resume` の応答と、その後の `status` で、処理が終わる（宛先へ入れて終える・上の 2〜4 でレビュー待ちへ戻る）まで、`running` を返す。受け付ける前のレビュー待ちを、そのまま返さない（flywheel は、`land` を返した後に、同じ中身のレビュー待ちを読んだら、上の 4 と読む。2026-11-20 に足した）。
- 委譲先は、`land` を受けた後、上の 2・3・4 のほかの理由では、レビュー待ちへ戻らない。別の種類の待ちへも移らない（宛先へ入れる道は、中身の識別を付けた `land` だけにする）。
- `land` の後のレビュー待ちと、最初のレビュー待ちは、出力の形が同じ。flywheel は、自分の記録（最後に返した答えと、そのときの `{approved_ref}`）で見分ける。中身が `{approved_ref}` と同じまま戻ってきたとき（上の 4）は、すぐには `land` を返し直さず、反映の承認を取り消して、委譲先の書いた理由をオーナーへ見せる（このとき、課題はすでに完了で、保留にはできない。上の「クリティカル設計決定」の「委譲先が入れられなかったときは、反映の承認を取り消して見せる（S3a）」）。
- 同じ `{approved_ref}` の `land` を 2 度受けても、委譲先は、宛先へ 2 度入れない。終わった実行への `resume` には、終わりの状態をそのまま返す。flywheel は、`resume` が失敗したとき、次の機会に同じ `land` を返し直してよい。
- 取り込みの形: 委譲先は、宛先の最新を「取り込みだけ」と機械的に見分けられる形で取り込む（開発では、宛先の最新をマージのコミットとして取り込む。履歴の書き換え〔rebase・強制の push〕をしない）。衝突を直すときは、その取り込みのコミットの中だけで直し、関係のない変更を足さない。
- 委譲先は、最初にレビュー待ちへ出す前にも、宛先の最新を取り込む。
- 委譲先は、宛先が動いていないかを、宛先へ入れる直前に確かめる。確かめてから入れるまでの間に宛先が動く隙間は残る（いまの flywheel の反映の処理と同じ）。
- 取り込んだ後、委譲先は、新しい中身のチェックの完了を待たずに、レビュー待ちへ戻ってよい。チェックの完了は、flywheel が待つ（下）。
- flywheel は、`land` を返す前に、通す中身のチェックがすべて通っていることを、上流のアダプタの口で自分で確かめる（いまの反映の処理と同じ。最初の `land` でも、宛先が動いた後の `land` でも行う。チェックがまだ走っている間は、`land` を返さずに待つ）。委譲先の側の検査（上の 4）は、それに足す安全側の確かめで、flywheel の確かめの代わりにはしない。
- 変わった中身の判定は flywheel が持つ（委譲先の申告は使わない）。flywheel は、レビュー待ちの成果物の中身が、通した中身と違うとき、上流のアダプタの比較の口で「取り込みだけ・衝突の解消あり・関係のない変更あり・判定できない」を見分け、通すときは、新しい中身を `{approved_ref}` にして、もう一度 `land` を返す。通さないときは、検証と承認へ戻す（設計書 §21.3 の「完了を承認した後に反映先が動いたとき」）。その間、タスクの実行はレビュー待ちのまま残し、やり直した検証で直しが要るときは `respond` を、通ったときは新しい中身の `land` を返す。
- `land` を返す時期は、宛先で違う。宛先が統合先の実行には、完了の検証の判断点（J5）がタスクを「満たした」とした後に返す（オーナーの承認は要らない）。宛先が反映先の実行には、オーナーの完了の承認の後に返す。委譲先から見た動きは、どちらも同じ。
- `ready`（flywheel の側で反映まで済ませた）は残す。flywheel が自分で反映する処理を外した後は、flywheel は `ready` を返さない。

### 足すもの 4: 課題を反映先へ上げる（新しい依頼）

待っている実行が無いときの反映は、新しい依頼として始める。使うのは、統合先に集めた課題を反映先へ上げるときと、委譲先のフローを通らずに作られた成果物（スキルを直接呼ぶ形・指示文を直接渡す形の委譲の成果物）を反映先へ上げるとき。

- 宣言の操作として、タスクの実行とは別に、反映の操作を 1 つ書けるようにする（flywheel の側の宣言の形は、`commands.reflect` と `repos[].reflect_connector`。S3a の機能要件の「宣言」）。反映の `start` に書ける差し込みに、`{artifact_ref}`（上げる成果物の参照）を足す。統合先を上げるときは、委譲先が返した統合先の識別（`role` が `integration` の `branch` の `ref`）。それ以外は、成果物の参照（開発では PR の URL。flywheel の側では、反映の操作の参照が、これに当たる）。
- 委譲先の動き:
  1. 用意する。統合先を上げるときは、反映先へ上げるための実物を作る（開発では、統合ブランチから既定ブランチへの PR。すでにあれば、それを使う）。反映先の最新を取り込み、上げる前の検証（委譲先の決まりの検査）を行う。
  2. 成果物に、実物（開発では PR）と、その中身の識別（`kind` が `commit` で、`role` の無い要素を、ちょうど 1 つ）を出して、レビュー待ち（`options` に `land`）で待つ。この依頼は、`land` を受けるまで、反映先へ入れない。
  3. `land` と `{approved_ref}` を受けた後は、足すもの 3 と同じに動く（一致して、反映先の最新を含んでいれば、反映先へ入れる。そうでなければ、入れずにレビュー待ちへ戻る）。
  4. 反映先へ入れた後、統合先と作業ツリーを片付けて、実行を終える（`succeeded`）。成果物には、反映先へ入れたもの（開発では PR）と、入れた後の中身の識別を出す。
- 統合先に集めた課題では、flywheel は、課題のタスクがすべて統合先へ入った後、オーナーの完了の承認の前に、この依頼を始める。委譲先が用意した実物とその中身を、課題の全体の検証（完了の検証の判断点〔J5〕）と、オーナーの完了の承認に使う。承認の後、承認した中身を `{approved_ref}` にして `land` を返す。
- 委譲先のフローを通らずに作られた成果物では、flywheel は、オーナーの完了の承認の後に、この依頼を始める。レビュー待ちの中身が、承認した中身と同じか、足すもの 3 の判定で通せる違いだけのとき、`land` を返す。
- flywheel が通さないとき（関係のない変更あり・判定できない・オーナーの差し戻し）は、その依頼を取り消す（`cancel`）。取り消された委譲先は、反映先へ入れず、統合先も消さない（自分の作業ツリーだけを片付ける。用意した実物を閉じるかは、委譲先が決める）。直しが済んで、検証と承認をやり直せる状態になったら、flywheel は、新しい依頼を出す。
- 設計書 §21.3 の表は、この依頼で flywheel が渡すものを「承認した中身」としている。この節では、依頼を承認の前にも始められる形にし、承認した中身は `land` で渡す（オーナーが完了の承認の前に見る実物を、委譲先が用意するため）。承認していない中身が反映先へ入らないことは変わらない。

### 足すもの 5: 委譲先が値で返すもの（`facts`）

- 出力に、任意のキー `facts` を足す。名前から値への対応（どちらも文字列）で、機械的に確かめられることを委譲先が返す。
- claude-harness は、自己レビューを実行したかを `self_review`（`complete`・`incomplete`・`not_run`）で返す。値は、委譲先が最後に作業した時点（実装か、レビューの指摘を受けた直し）のものにする。宛先の最新の取り込みでは、値を変えない。
- `facts` の形が合わないとき（値が文字列でない）は、flywheel は、`facts` が無いものとして扱う（出力の全体を誤りにしない）。
- 委譲先は、レビュー待ちの出力に、毎回 `facts` を出す。flywheel は、出力を読むたびに読み替え、`facts` の無い出力では、前の値を引き継がない（無いものとして扱う）。
- flywheel は、名前と値の意味を持たない。どの名前がどの値であることを求めるかは、宣言に書き、core が LLM を使わずに照らす（宣言の形は、委譲先ごとの `required_facts`。S3a の機能要件の「宣言」）。

### 契約に入れないもの

- 作業ツリーの持ち主は、flywheel の側の宣言で選ぶ（設計書 §21.3）。claude-harness は、いまも自分で作って片付けるので、契約に足すものは無い。
- 失敗した委譲の成果物を引き継いで続ける入力（claude-harness#383・flywheel#681）は、この節では決めない。
- 複数の課題を 1 回の依頼に束ねること。

### 未決だった点（S3a の仕様で決めた）

- `land` の後、委譲先が宛先へ入れるまでの間の、flywheel の側の記録: 反映の試行の記録に、承認した中身と、通した中身の両方を残す（見直し前からある 2 つの列を使う）。返した中身は、契約の実行の記録にも残す。「クリティカル設計決定」の「DB スキーマ: 契約の実行と成果物に足す列（S3a）」。
- 反映の依頼の口を持たないリポジトリの課題の扱い: 宣言の検査では止めず、flywheel の外での反映を待つ（状況に、その旨を出す）。「クリティカル設計決定」の「反映の依頼の口と、口が無いリポジトリ（S3a）」。
- レビュー待ちの読み方の決まりとの突き合わせ: 検証中と完了の承認待ちの間は、見直し前と同じに、状態を読まない。完了の課題の契約の実行は、反映の段だけが読む。「直前と同じレビュー待ちは取り込み直さない」の決まりは、「入れてよい」を返した後のレビュー待ちには使わず、中身の識別で見分ける。S3a の機能要件の「反映の段」。
- 統合先に集めた課題を上げるときの、宣言と記録の形（S3b の仕様で決めた）: 宣言は足さない（S3a の `commands.reflect` と `reflect_connector` を、そのまま使う）。課題に、統合先の識別を記録する（`challenge.integration_ref`）。上げる依頼は、反映の操作がまだ無いうちに始め、レビュー待ちを読んだときに、反映の操作を作って結び付ける。

### claude-harness の側で要るもの（S3b）

claude-harness の 5.2.0（main 9911091。2026-11-20 に調べた）に無いもの。claude-harness の側の Issue にする。契約の形は、上の「足すもの 2」「足すもの 4」のとおりで、変えない。

| 口 | いま（5.2.0） | 要るもの |
|---|---|---|
| 統合先を作る | 無い（`uses_integration` に `true` を受けると、失敗 `integration_unsupported` で止まる） | `uses_integration` と `challenge_id` から統合先を決め、無ければ作る。タスクの成果の宛先を統合先にする。同じ課題の実行が同時に始まっても、同じ統合先になる（どちらが作っても、片方が失敗しない） |
| 統合先の成果物の印 | 無い（成果物の要素に `role` が無い） | 統合先を使う実行の出力に、統合先の識別と、統合先の中身の識別を、`role` が `integration` の要素で 1 つずつ出す。統合先へ入れて終えた実行では、入れた後の中身を出す |
| 統合先宛ての `land` と取り込み | 作りはある（宛先を問わない）が、統合先宛てで通した試験が無い | 統合先宛てで、中身の一致・統合先の最新の取り込み（マージのコミット）・入れずにレビュー待ちへ戻る、を試験で確かめる |
| 統合先を反映先へ上げる | 無い（反映の依頼は、PR の URL だけを受け、ブランチの名前は `integration_reflect_unsupported` で止まる） | `artifact_ref` に統合先の識別を受けて、反映先へ上げる実物を用意し（あれば使う）、反映先の最新を取り込み、上げる前の検証をして、レビュー待ちで待つ。`land` で反映先へ入れた後に、統合先を片付ける。取り消しでは、統合先を消さない |

実装対象: S3c

S3 は、1 回に確かめられる大きさを超えるので、4 つに分ける（S3a・S3b・S3d は 2026-11-20 に分けた。S3b から S3c を分けたのも同じ日。オーナーの決定）。S3b は、切り離せない部分（複数のタスク・統合先・課題の単位の確かめ・上げる依頼）と、それに要る予算・子に対応するタスクだけにした。S3c は、衝突の解消だけにし、フォローアップを開いている課題のタスクに上げる形は S4 へ送った（オーナーの決定 2026-11-21）。S3c と S3d は、並べて進める（オーナーの決定 2026-11-21）。

手触りと見た目の作り込み（配色・余白・動き）は、どの区切りにも入れず、S5 より後に行う（オーナーの決定 2026-11-20）。

claude-harness 側の受け口の契約（flywheel が渡すもの・受け取るもの）は、上の「委譲先との契約（S3 で使う受け口）」に書いた。claude-harness 側の実装は、S3a の分が claude-harness#388（出荷済み。5.2.0）、S3b の分が claude-harness#409（出荷済み。5.3.0）。S3c で、claude-harness の側に要るものは無い。

## やらないこと

- 取り込みと関係のない変更が足された中身を、差分で確かめて通すこと（理由: 設計書 §21.3。検証と承認をやり直す）
- 履歴を書き換えた取り込み（rebase・強制の push）を通すこと（理由: 契約のまま。判定できないものとして扱う）
- 衝突の解消を、スーパーバイザーやオーケストレーターが確かめること（理由: 設計書 §21.3）
- 衝突の解消の確かめに、回数の上限や、オーナーへ上げる道を足すこと（理由: 問題あり・判断できないは、検証か承認のやり直しへ落ちる。判断点が止まったときにスーパーバイザーが上げる形は S4）
- 通した衝突の解消を、画面に出すこと（理由: S3d。S3c は API の値まで）。`flywheel status` の出力に出すこと（理由: 課題の詳細で読む。状況の出力は変えない）。通したことを、対話の欄や通知で、オーナーへ自分から知らせること（理由: S4。対話の欄と一緒に作る）
- フォローアップを、開いている課題のタスクに上げること（理由: S4 へ送った。上の「クリティカル設計決定」）
- 比較の口を持たない委譲先・上流で、衝突の解消を通すこと（理由: 判定できないので、検証と承認へ戻す。設計書 §21.3）
- 委譲先との契約を変えること、claude-harness の側の実装（理由: S3c では要らない）
- 取り込み元の Issue を、反映先へ入れたときに閉じる行を、上げる依頼に渡すこと（理由: claude-harness#419 と、flywheel の側の Issue で行う）
- 完了の承認の画面を作り替えること、タスクの詳細に、委譲先の実行がいまいる段・成果物・枠と使った額を出すこと（理由: S3d）
- 統合先を使う課題で、タスクのリポジトリが 2 つ以上にまたがるものを進めること、統合先を使う課題を `form: plugin`・`form: brief` の委譲先で進めること（理由: S3b の「やらないこと」のまま）
- 走っているタスクを見ながら進めること、承認・回答がサイクルを始めること、計画の後にタスクを足すこと、保留中の課題のほかのタスクを進めること（理由: S4）
- S3b で残した点（統合先へ入ったかの確かめが、成果物の形に頼る・「入れてよい」の後の失敗で上流を読めない状態が続くと、実行が開いたまま残る・タスクの検証に連続の「満たしていない」の上限が無い・終わりを記録した実行があるときの、計画の作り直し）（理由: S4 で、スーパーバイザーの手と一緒に決める。S3c の範囲を広げない）
- S3a で残した点（理由: flywheel#875・claude-harness#406）、S2c の画面に残した点（理由: flywheel#836〜#840）
- 手触りと見た目の作り込み（理由: S5 より後。オーナーの決定 2026-11-20）
- サイクルの構造を YAML で定義・調整すること（理由: flywheel#265・#266）
- Tom のワークスペースの切り替え（理由: S3c が main に入った後に、オーナーの了承を得て、オーケストレーターが行う）

## 受入基準

S3c（衝突の解消を、承認し直さずに通す）の受入基準。特に断らない限り、実ストアを使う Go のテストで確かめる。委譲先は、契約の出力を決めたとおりに返す、テスト用の実行で作る。上流（成果物・チェック・比較の口）は、テスト用の差し替えで作り、変わり方（取り込みだけ・衝突の解消あり・関係のない変更あり・判定できない）と、直した差分を、決めたとおりに返させる。J5 は、結果を決めたとおりに返す、テスト用の判断の呼び出しで作る。S3b の受入基準は flywheel#878、S3a は flywheel#842。

### 統合先へ入れるとき

- [ ] レビュー待ちのタスクの実行の中身の識別が、検証した中身と違い、変わり方が衝突の解消あり → 契約の実行の `fix_pending_ref` は、いまの中身になる。
- [ ] そのとき、`verified_ref` は、変わらない。
- [ ] そのとき、`land_ref` は NULL になる。
- [ ] そのとき、`land_delivered` は偽になる。
- [ ] そのとき、`commands.resume` は呼ばれない。
- [ ] そのとき、タスクは `verifying` のままである。
- [ ] `fix_pending_ref` があるタスクは、タスクの検証（1 つ目の動き方）の対象にならない。
- [ ] `fix_pending_ref` があるタスクの実行は、衝突の解消の確かめの対象になる。
- [ ] 保留中の課題の、`fix_pending_ref` があるタスクの実行は、確かめの対象にならない。
- [ ] 統合先宛ての確かめの実行の記録（`run`）は、そのタスクの `task_id` を持つ。
- [ ] 確かめが「満たした」→ `verified_ref` は、確かめ待ちだった中身になる。
- [ ] そのとき、`fix_pending_ref` は NULL になる。
- [ ] その次の状態の確認で、チェックがすべて通っていれば、`commands.resume` が、確かめを通した中身を付けた `land` で呼ばれる。
- [ ] 確かめが「満たしていない」→ タスクは `in_progress` になる。
- [ ] そのとき、`verified_ref` は NULL になる。
- [ ] そのとき、`fix_pending_ref` は NULL になる。
- [ ] そのとき、J5 の指摘が、委譲先への差し戻し（`respond`）に入る。
- [ ] 確かめが「判断できない」→ `verified_ref` は NULL になる。
- [ ] そのとき、`fix_pending_ref` は NULL になる。
- [ ] そのとき、タスクは `verifying` のままである。
- [ ] そのとき、課題は保留にならない。
- [ ] その次の J5 で、そのタスクは、タスクの検証（1 つ目の動き方）の対象になる。
- [ ] J5 の呼び出しが、連続の失敗の上限まで失敗した → `verified_ref` と `fix_pending_ref` は NULL になる。
- [ ] 変わり方が取り込みだけ → `fix_pending_ref` は NULL のままである。
- [ ] 変わり方が関係のない変更あり → `fix_pending_ref` は NULL のままで、`verified_ref` は NULL になる。
- [ ] 比較の口が無い（判定できない）→ `fix_pending_ref` は NULL のままで、`verified_ref` は NULL になる。
- [ ] `fix_pending_ref` がある間に、中身の識別がさらに動き、検証した中身からの変わり方が衝突の解消あり → `fix_pending_ref` は、いまの中身になる。
- [ ] `fix_pending_ref` がある間に、中身の識別がさらに動き、検証した中身からの変わり方が関係のない変更あり → `fix_pending_ref` と `verified_ref` は NULL になる。
- [ ] 確かめの結果を書く直前に、契約の実行の中身の識別が `fix_pending_ref` と違っていたら、`verified_ref` も `fix_pending_ref` も変わらない。
- [ ] 確かめの結果を書く直前に、課題が `awaiting_human` になっていたら、`verified_ref` も `fix_pending_ref` も変わらない。
- [ ] `fix_pending_ref` があるタスクの契約の実行が終わった（`failed`）→ `fix_pending_ref` は NULL になる。
- [ ] 課題が保留になっても、`fix_pending_ref` は変わらない。
- [ ] 入力を組み立てるときに読み直した変わり方が、衝突の解消ありでない → 確かめの実行の記録（`run`）は作られない。

### 衝突の解消の確かめの入力

- [ ] 入力に、通した中身の識別が入る。
- [ ] 入力に、確かめ待ちの中身の識別が入る。
- [ ] 入力に、取り込みのマージのコミットごとに、両方の親と違う形になったファイルの名前が入る。
- [ ] 入力に、そのファイルの、通した中身の側の親からの差分が入る。
- [ ] 差分を上流が返さなかったファイルは、入力に、ファイルの名前と、差分を読めなかった旨が入る。
- [ ] 統合先宛ての確かめの入力に、タスクの完了条件が入る。
- [ ] 統合先宛てで、タスクが取り込み元の子に対応するとき、入力に、その子の本文が入る。
- [ ] 反映先宛ての確かめの入力に、計画の「完了したら見えるもの」が入る。
- [ ] 作業ディレクトリは、確かめ待ちの中身を取り出した一時の作業ツリーである。
- [ ] J5 の指示文に、直した差分だけを確かめる（全体を検証し直さない）旨がある。
- [ ] J5 の指示文に、差分が衝突の解消の範囲を超えていれば「満たしていない」を返す旨がある。
- [ ] J5 の指示文に、差分を読めないファイルがあって確かめられなければ「判断できない」を返す旨がある。
- [ ] 統合先宛ての確かめの費用は、タスクの使った額（`spent_usd`）に数えられない。
- [ ] 確かめの費用は、その課題の判断点の費用に数えられる。
- [ ] J5 の段で、同じ課題に、検証中のタスクと、確かめ待ちの中身を持つ別のタスクがあるとき、両方が処理される。
- [ ] 統合先宛てで、同じタスクに、終わっていない実行（`run`）があるとき、確かめの実行の記録は作られず、`fix_pending_ref` は変わらない。
- [ ] 反映先宛てで、同じ課題に、`task_id` を持たない終わっていない実行（`run`）があるとき、確かめの実行の記録は作られず、`fix_pending_ref` は変わらない。
