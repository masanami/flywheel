# core の見直し（課題 ＞ タスク ＞ フォローアップ・サイクル・スーパーバイザー）

## 概要

2026-11-17 の設計の見直し（`docs/architecture.md` §21。決定 D22〜D34）を、core・CLI・画面に実装する。全体を区切り（スライス）に分け、この文書の受入基準は、いま実装する区切りの分だけを持つ。後の区切りは、その番が来たときにこの文書へ書き足す。

区切り S1（外す）は出荷済み（flywheel#732・PR #747）。区切り S2（土台）は大きいので、S2a（ストアと計画）・S2b（入口と出口）・S2c（画面）の 3 つに分けて順に入れる（オーナー 2026-11-18）。S2a は出荷済み（flywheel#749・PR #767）。S2b も出荷済み（flywheel#770・PR #795）。

いまの実装対象は S2c（画面）で、次を行う。

- 画面の枠を作り替える。左の列でエージェントを切り替え、上の帯で「いま進められること・課題・フォローアップ・サイクル」を切り替える。
- 「いま進められること」（あなたを待っているもの・取り込めるもの・サイクルを回すと進むもの）、課題ごとのタスクのツリー、課題の詳細、タスクの詳細、計画の承認、フォローアップの一覧、サイクル、すべてのエージェント（あなたを待っているものの横断）の画面を作る。
- 計画・説明・完了条件・問いの本文を、Markdown として整えて出す（生の HTML は通さない）。
- いまのボードとグラフの画面を外す。グラフのための API も外す。

## 背景・目的

2026-11-01〜11-16 の 16 日間を測った結果（`docs/architecture.md` §21.0）、課題の時間の大半がオーナー待ちで、費用の約半分が判断点に出ていた。設計の見直しで、次を決めた。

- 課題の下にタスクのツリーとフォローアップを持ち、承認は課題ごとに 1 回にする（D22・D23）。
- 反映・統合先・作業ツリーは委譲先に任せる（D24・D25・D31〜D33）。
- サイクルは、走っているタスクを見ながら進める。想定外のことはスーパーバイザーが受ける（D26・D27）。
- 課題どうしを、同じ場所を触る見込みを理由には直列にしない（D29）。

S2c は、S2a・S2b で core と端末のコマンドに入れた形（タスクのツリー・計画の問いと推奨・フォローアップ・取り込めるもの・サイクルを回すと進むもの）を、画面で見られるようにする。いまの画面は、課題を 1 枚のカードとして並べるボードと、課題どうしの関係のグラフで、タスクもフォローアップも取り込めるものも出ない。計画の承認の画面は、問いと推奨を論点ごとに見せず、計画の本文は整えずにそのままの文字で出ている。オーナーが「いま自分は何をすればよいか」を見る最初の画面も無い（端末の `flywheel status` にはある）。画面の形は、試作をオーナーが触って決めた（`docs/features/core-redesign/ux.md`。2026-11-17）。

決定の正本は、flywheel#724・#725・#726 の「設計の見直しで決めたこと」の節と、`docs/architecture.md` §21、`docs/glossary.md`。この文書は、それらを写さずに参照する。

## ユーザーストーリー

オーナーとして、画面を開いたら、いま自分を待っているもの・取り込めるもの・サイクルを回すと進むものを 1 か所で見たい。課題は、タスクのツリーで、どこまで進み、どこで誰を待っているかを見たい。計画の承認では、方針・問いと推奨・タスクのツリー・予算の上限を 1 画面で見て、推奨のままでよければ、そのまま承認したい。

## 機能要件

S2c（画面）の要件。S2b の要件と受入基準は、flywheel#770 に残してある（S2a は flywheel#749、S1 は flywheel#732）。

画面の語は `docs/glossary.md` に合わせる。画面では、ワークスペースを「エージェント」、オーナーを「あなた」と書く。画面の文言は、下で「」に入れて書いたものだけを固定し、ほかは実装に任せる。API のパスとキーの名前（`workspaces` など）は変えない。

### 読み取りの API

- [ ] 課題のツリーの API（`GET /api/v1/workspaces/{name}/tree`）を足す。応答の根は、`challenges`（開いている課題＝状態が完了でも取り下げでもない課題の全部。並びは課題の ID の小さい順）と、`recent_done`（完了した課題を、更新が新しい順に 10 件まで。更新が同じ時刻のものは、ID の大きい順。取り下げた課題は入れない）。要素は、下の「課題のツリーの要素」。
- [ ] 課題のツリーの要素は、次のキーを持つ: `id`・`title`・`status`・`status_label`・`updated_at`・`next_human_actions`（課題の一覧の `card.next_human_actions` と同じ値）・`uses_integration`（真・偽・null）・`tasks`・`tasks_total`・`tasks_done`・`cost_usd`・`budget_usd`・`followups_open`・`dependencies`・`parent`・`children`。
- [ ] `tasks` は、最新の計画のタスク（`flywheel show <課題の ID> --plan` と同じ出どころ。計画の承認の前は計画の中のタスク、承認の後は、その計画から作ったタスクの行）。要素は、`key`（計画の中の識別子。最新の計画のタスクなので、いつもある）・`id`（タスクの ID。計画の承認の前は null）・`title`・`depends_on`（前提のタスクの `key` の配列。計画の承認の後でも、タスクの ID ではなく `key` で返す）・`status`（タスクの状態。計画の承認の前は null）・`phase`（下の表示の区分）・`cost_usd`（そのタスクの行に付いた実行の記録の費用の合計。計画の承認の前は 0）。前の版の計画のタスク（作り直した計画の承認で、取りやめになったもの）は入れない。最新の計画が、タスクを持つ形でない（過去の形）か、計画が無い課題では、空の配列。計画から作っていないタスクは、S2c の時点では作られない（計画の後にタスクを足す S4 で、要素の形を決め直す）。
- [ ] `phase`（表示の区分）は、次の 6 つのどれか。上から順に当てはめ、最初に当たったものにする。
  - `cancelled`: タスクの状態が取りやめ（最新の計画のタスクが取りやめになるのは、課題を取り下げたとき）。
  - `done`: タスクの状態が済み。
  - `waiting`: そのタスクの行に、答えていない、オーナー宛ての保留がある（保留の種類が、オーケストレーターが直接行うもの〔`parent_direct`〕のときは、当たらない）。
  - `running`: タスクの状態が作業中か検証中。
  - `next`: タスクの状態が未着手（計画の承認の前を含む）で、前提のタスクが全部済みか、前提が無い。
  - `blocked`: タスクの状態が未着手（計画の承認の前を含む）で、済みでない前提がある（取りやめの前提は、済みでないものとして扱う）。
- [ ] `tasks_total` は `tasks` の件数、`tasks_done` は、そのうち `phase` が `done` の件数。
- [ ] 課題の `cost_usd` は、その課題の実行の記録（判断点と委譲。課題の詳細の API の `runs`。前の版の計画のタスクに付いた実行も含む）の費用の合計。費用の記録が無い実行は、0 として足す。
- [ ] `budget_usd` は、予算の上限。`flywheel show <課題の ID> --plan --json` の `plan.budget_usd` と同じ規則で決める（決められないとき・計画が無いときは null）。
- [ ] `uses_integration` は、計画の承認の前は、最新の計画の値（計画が無いか、過去の形のときは null）。計画の承認の後は、課題に記録した値。
- [ ] `followups_open` は、その課題の未のフォローアップの件数。数え方は、状況の `followups.open` と同じ（上げてあって、上げた先の課題が取り下げでないものは、数えない）。
- [ ] `dependencies` は、記録した前提の課題。要素は、`challenge_id`・`title`・`status`・`status_label`・`satisfied`（前提が満たされているか）。
- [ ] `parent` は、親の課題（`challenge_id`・`title`・`status`・`status_label`。親が無ければ null）。`children` は、子の課題（同じ形の配列。無ければ空）。見直し前は、グラフの API だけが返していた関係。
- [ ] 課題の詳細の API（`GET /api/v1/workspaces/{name}/challenges/{id}`）の根に、`tree`（課題のツリーの要素と同じ形）を足す。完了・取り下げの課題でも出す。`flywheel show <課題の ID> --json` には足さない（`card`・`waiting` と同じく、API だけのキー）。
- [ ] 承認の要約の API（`GET …/challenges/{id}/approval`）の `approval.plan` に、`summary`（方針。無ければ null）と `budget_usd`（予算の上限。決められなければ null）を足す。値は、`flywheel show <課題の ID> --plan --json` の `plan.summary`・`plan.budget_usd` と同じ（予算の上限は、宣言のサイズごとの既定も使う、同じ規則で決める）。端末の `flywheel approve` の要約と `--json` の形は変えない。
- [ ] 承認の要約の API の `approval.plan.tasks` の要素に、`phase` を足す（課題のツリーの要素と同じ決まり。計画の承認の前なので、`next` か `blocked`）。
- [ ] 問いの一覧の API（`GET /api/v1/questions`）の要素に、`task_id`（保留が付いているタスクの ID。付いていなければ null）を足す。画面は、あなたを待っているものの回答の行の、問いの文と行き先を、この API から取る。
- [ ] 表示の区分・進み・費用の合計・未のフォローアップの件数は、core が決めて API が返す。画面は、これらを自分で数え直さない。
- [ ] 画面のボタンで受ける書き込みの口（`POST`）は足さない。画面から出す書き込みは、見直し前と同じ 3 つ（計画の承認・反映を保留にした完了の承認・サイクルを回す）だけにする。

### 画面の枠と URL

- [ ] 画面は、左の列（エージェントの切り替え）・上の帯・本文の 3 つで作る。右の対話の欄は作らない（S4）。
- [ ] エージェントが 1 つも無いとき（ワークスペースの一覧が空）は、「エージェントがありません。」を出す。
- [ ] 左の列に、`flywheel serve` が知っているエージェント（ワークスペースの一覧の API の順）を並べる。エージェントごとに、頭文字（名前の先頭の 1 字。英字は大文字にする）・名前・あなたを待っているものの件数を出す。件数が 0 のときは、数字を出さない。
- [ ] エージェントが 2 つ以上あるときは、左の列の一番上に「すべて」を置く。エージェントが 1 つだけのときは、「すべて」を置かない。
- [ ] 選んでいるエージェント（か「すべて」）に、選んでいる印を付ける（色だけでなく、支援技術にも伝わる形で）。
- [ ] ストアを読めないエージェント（ワークスペースの一覧の `state` が `ok` でない）は、左の列に、読めない印を付けて出す。選ぶと、本文に、読めない理由（`error`）を出す。
- [ ] あなたを待っているものの件数は、見直し前の人間待ちの帯の区分の件数の合計と同じ数え方にする（`docs/features/m4-ui-server.md` の区分の表。数え方は変えない）。見直し前の区分と、S2c の種類の語の対応は、承認待ち＝「計画の承認」と「完了の承認」（課題の状態で分ける）、未回答の問い＝「回答」、不可逆操作の承認＝「不可逆操作の承認」、食い違い＝「食い違い」（同じ課題に要素が複数あっても、課題ごとに 1 件）、予算の使い切り＝「予算の増額」、トリアージ＝「トリアージ」、片付け待ちのスロット＝「スロットの片付け」。
- [ ] 上の帯に、選んでいるエージェントの名前と、4 つの項目「いま進められること」「課題」「フォローアップ」「サイクル」を、この順に出す。選んでいる項目に印を付ける。課題の詳細・タスクの詳細・計画の承認の画面では、「課題」を選んでいることにする。
- [ ] 上の帯の右に、選んでいるエージェントのサイクルの状態を出す（サイクルの API の `state`。「サイクル: 走っている」「サイクル: 走っていない」「サイクル: 止まっているかもしれない」〔`stale`〕）。サーバとの接続が切れているときは、「切断中」を出す（見直し前と同じ）。
- [ ] 「すべて」を選んでいるときは、上の帯の 4 つの項目とサイクルの状態を出さない。
- [ ] 最初の画面（URL が画面を指していないとき）は、一覧の先頭のエージェントの「いま進められること」にする。
- [ ] どの画面を見ているかを、URL のハッシュ（`#` の後ろ）に持つ。形は、下の「画面・API設計」。再読み込みしても、同じ画面に戻る。ブラウザの「戻る」で、前の画面に戻る。
- [ ] URL が、無いエージェント・無い課題・無いタスクを指しているときは、「見つかりません」と、「いま進められること」へのリンクを出す。読み込みが終わるまでは、「見つかりません」を出さず、「読み込んでいます」を出す。
- [ ] サーバから変化の合図（`workspace_changed`）を受けたら、そのエージェントの、開いている画面のデータを読み直す（ほかのエージェントの合図では、読み直さない）。60 秒ごとにも、開いている画面のデータを読み直す（画面が裏に回っている間は、見直し前と同じく、読み直さない）。取り込めるものは、どちらの契機でも読み直さない（下の「いま進められること」）。
- [ ] エージェントを足す口（左の列の「足す」）は置かない。

### いま進められること

- [ ] 見出しは「いま進められること」。その下に、件数の行（あなたを待っているもの・取り込めるもの・サイクルを回すと進むもの・未のフォローアップ）を出す。
- [ ] 区分「あなたを待っている（N 件）」に、あなたを待っているものを 1 件ずつ並べる（数え方の 1 件が、1 行。食い違いは、課題ごとに 1 行）。1 件ごとに、種類・題名（課題に結び付かないものは、何が待っているかの文）・行き先を出す。
- [ ] 種類の語は、次の 8 つ: 「計画の承認」「完了の承認」「回答」「不可逆操作の承認」「食い違い」「予算の増額」「トリアージ」「スロットの片付け」。並びは、この順。
- [ ] 計画の承認の行の行き先は、その課題の計画の承認の画面。完了の承認・不可逆操作の承認・食い違い・予算の増額・トリアージの行の行き先は、その課題の詳細。
- [ ] 回答の行には、問いの文を出す。行き先は、保留がタスクに付いていればタスクの詳細、付いていなければ課題の詳細（問いの文とタスクは、問いの一覧の API から取る。その課題の問いが、問いの一覧に無いときは、課題の題名を出し、行き先は課題の詳細）。
- [ ] スロットの片付けの行には、片付ける対象（スロットの ID とリポジトリ）と、端末のコマンドの案内を出す（行き先は無い）。
- [ ] あなたを待っているものが 0 件のときは、この区分に「あなたを待っているものはありません。」を出す。
- [ ] 区分「取り込めるもの（N 件）」に、状況の API の `ingestable.items` を並べる。1 件ごとに、番号・題名（上流へのリンク）・子の件数（子があるとき）・取り込むコマンド（`flywheel ingest <external_key>`）を出す。子は、親の下に、字下げして題名を並べる。
- [ ] 取り込めるものの親が、すでに課題になっているとき（`parent_challenge_id` がある）は、その課題の題名を添える。
- [ ] 「取り込めるもの」の区分に、ボタン「読み直す」を置く。取り込めるものは、この画面を開いたときと、「読み直す」を押したときだけ、状況の API に `ingestable=true` を付けて読む（上流を読むので、変化の合図と 60 秒ごとの読み直しでは読まない）。読んでいる間は、「読んでいます」を出す。読んだ結果は、この画面の中だけで持つ（全部のエージェントについて持つ状況には混ぜない）。
- [ ] 上流を読めなかったとき（`ingestable.error` がある）は、その文と、読めた分の一覧を出す。
- [ ] 取り込めるものを、画面のボタンでは取り込まない。この区分に「取り込みは、端末か対話で行います。」と出す。
- [ ] 区分「サイクルを回すと進むもの（N 件）」に、状況の `cycle_work` の合計と、段ごとの件数（0 件の段は出さない）を出す。段の語は、「反映」「分類」「計画」「委譲」「完了の検証」「学び」「改修の提案」「片付け」。
- [ ] この区分に、ボタン「サイクルを回す」を置く（見直し前の「1 周を起動」のボタンの置き換え。口は同じ `POST …/cycle`）。押せるのは、合計が 1 件以上で、サイクルの状態が走っていない（`idle`）ときだけ。
- [ ] サイクルの状態が、止まっているかもしれない（`stale`）ときは、ボタンを押せなくし、端末で `flywheel cycle` を実行すると、止まったサイクルを片付けてから始める旨を出す（画面の口は、止まったサイクルの片付けをしないので、押しても始まらない）。
- [ ] 合計が 0 件のときは、「進められるものが無いので、サイクルは始めません。」を出す。
- [ ] 「サイクルを回す」を押して、始まった（`started` が真）ら「サイクルを始めました。」、始まらなかった（`started` が偽）ら「進められるものが無かったので、始めませんでした。」を出す。ほかのサイクルが走っていて始められなかった（`locked`）ときは、その旨を出す。
- [ ] 未のフォローアップの件数（状況の `followups.open`）と、フォローアップの一覧へのリンクを出す。
- [ ] あなたを待っているもの・取り込めるもの・サイクルを回すと進むものが、どれも 0 件のときは、「いま進められるものはありません。」を出す（取り込めるものを読み終えるまでは出さない）。

### 課題（タスクのツリーの一覧）

- [ ] 見出しは「課題」。課題のツリーの API の `challenges` を、課題ごとの枠にして、その順に縦に並べる。表の一覧とボードは作らない。
- [ ] 枠の見出しに、題名（課題の詳細へのリンク）・状態（`status_label`）・あなたを待っているときはその種類（`next_human_actions`。語は「いま進められること」の種類と同じ）を出す。
- [ ] 枠に、タスクの進み（「タスク 済みの件数 / 全体の件数」）・費用（`cost_usd`）・予算の上限（`budget_usd`。null のときは出さない）・未のフォローアップの件数・統合先（「使う」「使わない」。null のときは出さない）を出す。
- [ ] 計画の承認待ちの課題の枠には、計画の承認の画面へのリンクを出す。
- [ ] 記録した前提の課題があるときは、枠に「前提:」に続けて、前提の課題の題名と状態を出す。満たされていない前提には、「未完了」を添える。
- [ ] 枠の中に、タスクのツリーを出す（下の「タスクのツリー」）。`tasks` が空の課題は、ツリーの代わりに「タスクはまだありません。」を出す。
- [ ] 開いている課題が 0 件のときは、「開いている課題はありません。」と、「いま進められること」へのリンクを出す。
- [ ] 完了した課題（`recent_done`）は、「完了した課題を開く（最近の N 件）」を押すと出る（はじめは閉じている。N は `recent_done` の件数）。0 件のときは、この口を出さない。
- [ ] 画面の上に、色の凡例を出す: 「走っている」「あなたを待っている」「次に走る（前提は済み）」「前提を待っている」「済み」と、「線は前提です（左が終わると、右が走れます）。」

### タスクのツリー

- [ ] タスクを箱にして、前提の深さ（そのタスクまでの、いちばん長い前提の連鎖の長さ）ごとの列に、左から並べる。前提の無いタスクが、いちばん左の列。
- [ ] 前提のタスクの箱から、後のタスクの箱へ、前提 1 つにつき線を 1 本引く。
- [ ] 箱に、タスクの題名と、表示の区分の語（「走っている」「あなたを待っている」「次に走る」「前提を待っている」「済み」「取りやめ」）を出し、区分ごとに色を変える。区分は、色だけでなく、文字でも分かる。箱は、表示の区分の値を、属性（`data-phase`）に持つ。
- [ ] `depends_on` に、その課題の `tasks` に無い `key` があるときは、その前提を無いものとして並べる（線も引かない）。
- [ ] タスクの ID がある箱（計画の承認の後）は、押すと、タスクの詳細へ移る。計画の承認の前の箱は、押せない。
- [ ] ツリーが枠の幅より広いときは、枠の中で横にスクロールできる（ページ全体は、横にスクロールしない）。
- [ ] 同じツリーの部品を、課題の画面・課題の詳細・計画の承認の画面で使う。

### 課題の詳細

- [ ] 上から、題名 → 課題の項目 → あなたを待っているもの → 切り替え（「ツリー」「経緯」「計画の本文」）→ 切り替えで選んだ中身、の順に出す。はじめは「ツリー」。
- [ ] 課題の項目に、状態・取り込み元（対応があるとき。上流へのリンクと、取り込み元の子の件数）・統合先（「使う」「使わない」。null のときは出さない）・タスクの進み・費用・予算の上限（null のときは出さない）を出す。
- [ ] あなたを待っているものの区画に、その課題の `next_human_actions` ごとに、次を出す。
  - 計画の承認: 計画の承認の画面へのリンク。
  - 完了の承認: 完了の承認の要約とボタン（見直し前の詳細にあったものを、そのままここに置く。反映は保留にする。作り替えは S3）。
  - 回答: 問いの文（課題の詳細の `holds` の、答えていない保留）と、保留がタスクに付いていれば、そのタスクの題名とタスクの詳細へのリンク。答える欄は置かず、端末のコマンドの案内を出す。
  - そのほか（不可逆操作の承認・食い違い・予算の増額・トリアージ）: 見直し前の詳細と同じ案内（端末のコマンド・対話での伝え方）。
- [ ] あなたを待っているものが無いときは、「あなたを待っているものはありません。」を出す。オーケストレーターが直接行う保留（`parent_direct`）で止まっている課題では、オーナーが答える問いではない旨を出す（見直し前と同じ）。
- [ ] 「ツリー」には、タスクのツリー・フォローアップ・取り込み元の子・関係する課題・不可逆操作を出す。
- [ ] フォローアップの区画に、その課題の未・済み・捨てたの件数と、未のフォローアップの題名と出どころを出す。フォローアップの一覧（その課題で絞った形）へのリンクを置く。フォローアップが 1 件も無い課題では、区画を出さない。
- [ ] 取り込み元の子の区画に、子ごとに、題名（上流へのリンク）・上流の状態・対応するタスクの題名（対応するタスクがあるとき）を出す。子が無い課題では、区画を出さない。
- [ ] 関係する課題の区画に、前提の課題（題名・状態・満たされているか）・この課題を前提にしている課題・親の課題・子の課題を出す。題名は、その課題の詳細へのリンクにする。どれも無い課題では、区画を出さない。
- [ ] 不可逆操作の区画に、その課題の不可逆操作（種類・状態・参照）を出す。無い課題では、区画を出さない。
- [ ] 「経緯」には、その課題の出来事を、新しい順に 1 本の時系列で並べる。出来事は、作業ログ（`GET …/log?challenge=<課題の ID>`）の記録（記録の時刻 `at` で並べる）と、実行の記録（課題の詳細の `runs`。始まった時刻で並べる）。
- [ ] 経緯の 1 行に、いつ・タスク（`entity` が `task` の記録のとき、`entity_id` のタスクの題名）・誰が・何が起きたか、を出す。
- [ ] 「誰が」は、作業ログの記録の、本人確認の方式と経路から決める: 方式が `relayed` なら「あなた（対話）」、経路が `ui` なら「あなた（画面）」、経路が `cli` で方式が `tty_confirm` なら「あなた（端末）」。どれにも当たらない記録は、経路の値をそのまま出す。方式が `relayed` の記録には、発言の要旨（記録の `after` の `relay_quote`）を出す。
- [ ] 経緯を、種類で絞れる: 「すべて」「計画と承認」「問いと回答」「完了の検証」「実行」。作業ログの記録（`entity` と `action`）と種類の対応は、下の表のとおり。表に無い記録は、「すべて」のときだけ出す。「何が起きたか」の語は、画面が、知っている `action` の値ごとに持つ。画面の知らない値は、値をそのまま出す。

  | 種類 | 作業ログの記録 |
  |---|---|
  | 計画と承認 | `entity` が `challenge` の `plan`・`approve`・`approve_hold_release`・`reject`、`entity` が `operation` の `approve`・`reject` |
  | 問いと回答 | `entity` が `challenge` の `hold`・`answer`・`answer_plan` |
  | 完了の検証 | `entity` が `challenge` の `submit`・`verify_met`・`verify_not_met`・`verify_uncertain` |
  | 実行 | 実行の記録（作業ログの記録ではない） |

- [ ] 実行の記録の行には、何の実行か（判断点の名前か、委譲）・結果・費用を出す。
- [ ] 「計画の本文」には、最新の計画の本文（Markdown として整えて出す）・課題の説明・完了条件（どちらも Markdown として整えて出す）・完了したら見えるもの（予想と、実物があれば実物。見直し前の詳細にあった段階の欄を、そのまま置く）・図（あるとき）を出す。計画が複数の版を持つときは、版を選んで前の版の本文を読める。計画が無い課題では、説明と完了条件だけを出す。
- [ ] 「この課題について相談する」の口と、スーパーバイザーの記録の区画は出さない（S4）。

### タスクの詳細

- [ ] 上に、課題の画面と課題の詳細へ戻るリンク（「課題」› 課題の題名）を出す。
- [ ] 上から、タスクの題名 → タスクの項目（表示の区分・前提のタスク・この後のタスク・費用）→ あなたを待っているもの（あるとき）→ このタスクでやること・完了条件・やらないこと → 問いと回答 → 実行の記録、の順に出す。
- [ ] タスクの詳細は、課題の詳細の API の応答から作る（タスクの本文は `tasks`、表示の区分・前提・費用は `tree.tasks`。2 つは、タスクの ID で結ぶ）。
- [ ] 前提のタスクと、この後のタスク（このタスクを前提にしているタスク）は、題名と表示の区分を出し、押すと、そのタスクの詳細へ移る。
- [ ] このタスクでやること（`body`）・完了条件（`done_criteria`）は、Markdown として整えて出す。やらないこと（`non_goals`）は、箇条書きで出す。
- [ ] そのタスクに、答えていない、オーナー宛ての保留があるときは、あなたを待っているものの区画に、問いの文と、端末のコマンドの案内を出す。答える欄とボタンは置かない（S4）。
- [ ] 問いと回答の区画に、そのタスクの保留（課題の詳細の `holds` のうち、`task_id` がそのタスク）を、古い順に出す。1 件ごとに、問い・回答（あるとき）・誰が答えたか（経路と、対話のときは発言の要旨）・計画の作り直しへ回したか、を出す。1 件も無いタスクでは、区画を出さない。
- [ ] 実行の記録の区画に、そのタスクの実行の記録（課題の詳細の `runs` のうち、`task_id` がそのタスク）を、新しい順に出す。1 件ごとに、種類・始まった時刻・終わった時刻（終わっていれば）・結果・費用を出す。委譲先の報告（仮定 `assumptions`・確かめていないこと `unverified`。`GET …/runs/{id}/report`）は、そのタスクの、いちばん新しい委譲の実行の分だけを読んで出す。
- [ ] 取り込み元の子に対応するタスク（`source_key` がある）は、タスクの項目に、その子の題名（上流へのリンク）と上流の状態を出す。
- [ ] 委譲先の実行がいまいる段・成果物・タスクごとの完了の検証の結果・スーパーバイザーの記録は出さない（S3・S4）。

### 計画の承認

- [ ] 計画の承認の画面の、計画の中身（方針・完了したら見えるもの・やらないこと・ツリー・問いと推奨・予算の上限・統合先）は、承認の要約の API（`GET …/challenges/{id}/approval`）の応答から作る。承認の口へ送る版は、同じ応答の `approval.version` にする（見せた中身と、承認する版を、同じ応答から取る）。
- [ ] 見出しは「計画の承認: 」に続けて課題の題名。その下に、予算の上限（`approval.plan.budget_usd`。null のときは「未設定」）と、統合先を使うか（`approval.plan.uses_integration`。「使う」「使わない」。null のときは出さない）を出す。
- [ ] 左に、方針（`approval.plan.summary`）・完了したら見えるもの（`approval.stages.expected`。場面・いま・終わった後）・やらないこと（`approval.stages.non_goals`）・タスクのツリー（`approval.plan.tasks`。件数つき）・図（`approval.stages.figure`。あるとき）を出す。
- [ ] 計画の承認の画面のツリーは、`approval.plan.tasks` の `phase` のとおりに出す（前提の無いタスクが「次に走る」、ほかが「前提を待っている」になる）。箱は押せない。
- [ ] 右に、「問いと推奨」を、論点（`approval.plan.topics`）ごとにまとめて出す。論点ごとに、題名・どう決めたか（`decision`）・問いを出す。問いごとに、問いの文・選択肢・どれが推奨か・いま記録されている答え（あるとき）を出す。
- [ ] 問いの選択肢は、画面では選べない（見せるだけ）。推奨の選択肢に「推奨」の印を付ける。
- [ ] 問いが 1 件以上あるときは、「推奨のままでよければ、そのまま承認できます。」と、推奨と違う答えにしたいときの端末のコマンドの案内（`flywheel answer <課題の ID> --choice <問いの番号>=<選択肢の番号>`）を出す。
- [ ] 問いが 0 件のときは、「問いと推奨」に「問いはありません。」を出す。
- [ ] ボタン「この計画を承認する」を置く。押すと、見ている版を付けて承認の口（`POST …/challenges/{id}/approve`）を呼ぶ（見直し前と同じ口・同じ本文）。
- [ ] 承認が通ったら、「承認しました。」と、「続きは、次のサイクルで進みます。」と、課題の詳細へのリンクと、ボタン「サイクルを回す」を出す（承認がサイクルを始めるのは S4）。このボタンは、「いま進められること」のものと同じ部品で、押せる条件も同じ（状況の `cycle_work` と、サイクルの状態から決める）。
- [ ] 版が食い違って承認が通らなかった（`conflict`）ときは、計画が変わった旨を出し、要約を読み直す。ほかの失敗は、エラーの文を出す。
- [ ] 計画の本文の全文は、課題の詳細の「計画の本文」へのリンクで読めるようにする。
- [ ] 差し戻しのボタンは置かない。差し戻しは、端末か対話で行う旨と、端末のコマンドの案内を出す。
- [ ] 計画の承認待ちでない課題（承認の要約が完了の承認のもの・承認の要約の API が、承認できる状態でない旨のエラー〔`invalid_transition`〕を返すもの）で、この画面を開いたときは、「この課題は、計画の承認待ちではありません。」と、課題の詳細へのリンクを出す。
- [ ] 計画が、タスクを持つ形でない（過去の形の）ときは、方針・ツリー・問いと推奨の代わりに、計画の本文（Markdown として整えて出す）を出す。承認のボタンは置く。

### フォローアップの一覧

- [ ] 見出しは「フォローアップ」。「未（N）」「済み（N）」「捨てた（N）」で切り替える（はじめは未。選んでいる状態は、URL の `status` に持つ。切り替えは、ブラウザの履歴を増やさない）。件数は、フォローアップの一覧の API（`GET …/followups?status=all`）の応答から、状態ごとに数える。
- [ ] 一覧は、課題ごとにまとめ、まとまりの見出しに、課題の題名（課題の詳細へのリンク）と状態を出す。課題に属さないフォローアップは、最後に「課題に属さないもの」としてまとめる。
- [ ] 1 件ごとに、題名・説明（あるとき）・出どころ（`source`）・できた日時を出す。済みのものには確かめた結果（`note`）、捨てたものには理由（`reason`）を出す。
- [ ] 課題へ上げてあるフォローアップ（`promoted_challenge_id` がある）には、上げた先の課題の題名（課題の詳細へのリンク）を出す。
- [ ] URL で課題を指定して開いたときは、その課題のフォローアップだけを出し、絞っている旨と、絞りを外すリンクを出す。
- [ ] 選んでいる状態のフォローアップが 0 件のときは、その旨を出す（未のときは「未のフォローアップはありません。」）。
- [ ] 済みにする・捨てる・課題へ上げるのボタンと、選ぶためのチェックは置かない（S4）。未の一覧の下に、端末のコマンドの案内（`flywheel followup done`・`drop`・`promote`）を出す。

### サイクル

- [ ] 見出しは「サイクル」。サイクルの状態（走っている・走っていない・止まっているかもしれない）と、最後のサイクルの始まった時刻・終わった時刻・結果（サイクルの API の値）を出す。
- [ ] サイクルを回すと進むもの（合計と、段ごとの件数）と、ボタン「サイクルを回す」を出す（「いま進められること」の区分と同じ部品）。
- [ ] サイクルの構造の図・見ているタスク・スーパーバイザーの記録・費用の内訳・サイクルを止めるボタンは出さない（S4）。

### すべて

- [ ] 「すべて」の見出しは「すべてのエージェント」。区分「あなたを待っている（N 件）」に、全部のエージェントのあなたを待っているものを、エージェントの名前つきで並べる（横断の API `GET /api/v1/needs-human`）。1 件ごとの種類・題名・行き先は、「いま進められること」と同じ（行き先は、そのエージェントの画面）。
- [ ] 区分「エージェント」に、エージェントごとに、サイクルの状態と、あなたを待っているものの件数を出す。名前を押すと、そのエージェントの「いま進められること」へ移る。
- [ ] ストアを読めないエージェントは、読めない旨と理由を、区分「エージェント」の行に出す。

### 本文の Markdown

- [ ] 計画の本文・課題の説明・課題の完了条件・タスクのやることと完了条件・保留の問いと回答・論点の決め方（`decision`）は、Markdown として整えて出す（下の「Markdown として整える」を、1 つの部品にして使う）。
- [ ] 整えるもの: 見出し・段落・強調（太字と斜体）・箇条書き・番号つきの箇条書き（入れ子を含む）・行の中のコード・コードのブロック・表・引用・区切りの線・改行・リンク。それ以外の書き方（打ち消し線・チェックつきの箇条書き・脚注など、部品が組み立て方を持たないもの）は、書いてある文字のまま出す。
- [ ] 本文の `&`・`<`・`>` は、文字のまま出る（`&amp;` のような、置き換えた後の形を出さない）。
- [ ] 本文の中の生の HTML は、HTML として解釈せず、書いてある文字のまま出す。
- [ ] リンクは、行き先が `http:` か `https:` のものだけをリンクにする（`<https://…>` の形と、行き先を別の行に書く形のリンクも同じ）。それ以外（`javascript:` など）は、リンクにせず、文字として出す。リンクは、新しいタブで開き、開いた先から元の画面を操作できないようにする（`rel="noopener noreferrer"`）。
- [ ] 画像は読み込まない。代わりの文字を出し、行き先が `http:` か `https:` なら、リンクにする。
- [ ] 見出しは、画面の見出しの段より下の段にそろえる（本文の `#` が、画面の題名と同じ大きさにならない）。
- [ ] 長い本文は、見直し前と同じく、はじめは途中までを出し、「全文を開く」で全部を出す。そのために、長い本文の部品（`ClampedText`）を、整えた本文（要素の並び）も包める形に広げる（文字だけを渡す、見直し前の使い方の動きは変えない）。

### 外すもの

- [ ] ボードの画面（エージェントごとの列・カード・人間待ちの帯・絞り込み）と、グラフの画面（関係のグラフ・狭い画面の一覧・「グラフ／ボード」の切り替え）を外す。課題の詳細のモーダルは、課題の詳細の画面に置き換える。
- [ ] グラフの API（`GET /api/v1/workspaces/{name}/graph`）と、その型・core の口・テスト・照合用の見本・グラフ専用の種を外す。課題の詳細の API の `waiting` は残す。
- [ ] 本物の `flywheel serve` を相手にしたブラウザの試験（`make e2e-real`）は、グラフの筋書きをやめ、新しい画面の筋書きに作り替える。種のストアは、見直し前と同じ形（Go のテストが、環境の変数で渡された置き場所に作る。渡されなければ、一時の置き場所に作って中身だけを確かめる）で、新しい種のテストが作る。種の中身は、計画承認待ちの課題（タスク 2 件・問い 1 件）・着手中の課題（タスク 3 件。済み・作業中・未着手）・タスクに保留が付いた人間対応待ちの課題・完了の課題・未と済みと捨てたのフォローアップ（各 1 件）。取り込めるものは、上流を読むので、この試験では扱わない。
- [ ] ボード・グラフ・課題の詳細のモーダルを前提にした、画面のテストとブラウザの試験は、その部品を外す課題の中で外し、新しい画面のテストに置き換える（途中の課題でも、全体の検査 `make gate` が通るようにする）。

## 技術的な制約・方針

- 使用技術: 既存のまま（Go・SQLite・React・TypeScript・Vite・Vitest・Biome・Playwright）。Go の本番の依存は増やさない。画面（`web`）の依存は、`marked` を直接の依存に足すだけにする（いまは `mermaid` を通して入っている。下の「クリティカル設計決定」）。ルーティングのライブラリ・Markdown を HTML にするライブラリ・HTML を無害にするライブラリは足さない。
- 変更対象（S2c）:
  - `internal/core`: 課題のツリー（表示の区分・進み・費用の合計・未のフォローアップの件数）を返す、新しい読み取りの口。計画の表示（`show --plan` と同じ出どころ）を使う。グラフの口（`ChallengeGraph` と、グラフの区分・依存の種類・登録の経路の値の集合）と、そのテスト（`graph_test.go` と、`parent_direct_test.go` の中のグラフの分）、グラフ専用の種のテスト（`relation_graph_seed_test.go`）は外す。課題の親子と前提を読む所（いまは `graph.go` の中）は、課題のツリーの口を作る課題で、別のファイルへ移して使う。承認の要約を作る所（`approval.go`）は、API の側でだけ、宣言を渡して予算の上限を決める（端末の要約は変えない）。
  - `internal/view`: 課題のツリーの型、課題の詳細の `tree`、承認の要約の `summary`・`budget_usd` と、タスクの `phase`、問いの一覧の `task_id`。グラフの型（`graph.go`）と、画面と共有する値の集合（`closedsets.go`）のうちグラフの分を外し、表示の区分（`phase`）の値の集合を足す。型の生成（`web/src/api/types.gen.ts`）。
  - `internal/server`: 課題のツリーの API。グラフの API とそのテスト（`graph_test.go`）を外す。画面の配信（`ui.go`）は変えない（URL はハッシュで持つので、サーバ側の受け口は増えない）。
  - `web/src`: 入口（`App.tsx`・`screens.tsx`・`nav.tsx`）、読み込み（`live/useLive.ts`・`api/client.ts`）、ボード（`board/` のうち、ボード・列・カード・帯・絞り込み）とグラフ（`graph/` の全部）を外し、新しい画面の部品を足す。課題の詳細のモーダル（`board/CardDetailModal.tsx`）は、課題の詳細の画面に作り替える。承認の要約とボタン（`board/ApprovalPanel.tsx`）は、完了の承認の分を残し、計画の承認の分を新しい画面へ移す。端末のコマンドの案内（`guidance.json`・`guidance.ts`）・文言の表（`labels.ts`）・長い本文の部品（`ClampedText`）・図の部品（`FigureView`）は残して使う。見た目（`styles.css`。`graph/graph.css` は外す）。偽のデータ（`mock/`）。
  - `web/e2e`・`web/e2e-real`: ブラウザの試験を、新しい画面の筋書きに作り替える。
  - 文書: `docs/features/m4-ui-server.md`・`docs/features/ui-relation-graph.md`・`docs/architecture.md`・`docs/glossary.md`。
- 既存コードとの関係:
  - いまの画面は、URL に状態を持たず、画面の切り替えを部品の中の状態で持つ（`App.tsx`・`graph/RelationScreen.tsx`）。サーバは、`/` だけで画面を返し、ほかの無いパスには JSON の 404 を返す（`internal/server/ui.go`）。S2c は、画面の行き先を URL のハッシュに持たせ、サーバのこの動きを変えない。
  - いまの読み込み（`live/useLive.ts`）は、全部のワークスペースの状況・課題の一覧・サイクルを持ち、変化の合図でそのワークスペースだけを読み直す。S2c は、この仕組みを残し、画面ごとに要るもの（課題のツリー・課題の詳細・承認の要約・フォローアップ・作業ログ）を、その画面を開いている間だけ読む形を足す。そのために、読み込みの仕組みが、エージェントごとの変化の通し番号（変化の合図と、60 秒ごとの読み直しで進める）を外へ出し、画面ごとの読み込みは、通し番号が進んだら読み直す。全部のエージェントについて持つものに、問いの一覧（`GET /api/v1/questions`）を足す（いまは読んでいない）。状況の API に `ingestable=true` を付けて読む口は、別に持ち、結果は「いま進められること」の画面の中だけで持つ。この土台（通し番号・画面ごとの読み込みの形・API を呼ぶ口と、偽のデータの側の受け口）は、画面の土台の課題が作る。
  - 画面の文言と、core の値の集合の対応は、`labels.ts` が持ち、集合の全部の値に文言があることを型とテストで確かめている。表示の区分（`phase`）の語も、同じ形で持つ。
  - 端末のコマンドの案内（`guidance.json`）は、Go の側のテスト（`internal/cli/ui_guidance_test.go`）が、書いてあるコマンドとフラグが実在することを確かめている。S2c で足す案内（`flywheel ingest`・`flywheel answer --choice`・`flywheel followup done`・`drop`・`promote`）も、この JSON に書き、同じテストで確かめる。雛形は、見直し前と同じく `--workspace <パス>` を付け、必須のフラグ（`followup done` の `--note`、`followup drop` の `--reason`）を含める。いまの雛形は、出す場面を課題の操作（`next_human_actions`）で決めているので、課題の操作に結び付かない案内（取り込み・フォローアップ）のために、出す場面の書き方を広げる（画面の土台の課題が形を広げ、案内そのものは、それを使う画面の課題が足す）。
  - 本番のビルドに偽のデータが入らないことは、`web/src/build.test.ts` が、偽のデータに固有の文言が成果物に無いことで確かめている。偽のデータを作り替えると、いまの目印が偽のデータから消えて、検査が空になるので、目印を、新しい偽のデータの文言に差し替える。
  - 長い本文の部品（`ClampedText`）は、文字を受け取って、3 行で切る作りになっている。整えた本文（表や箇条書きの要素）は、そのままでは包めないので、要素の並びも包める形に広げる（Markdown の部品の課題が行う）。
  - 承認の要約を作る core の口は、端末の `flywheel approve`・`reject` と共有していて、宣言を読まずに計画の表示を作っている（予算の上限は、計画の本文で出すため）。宣言のサイズごとの既定で決まる予算の上限は、このままでは null になるので、API の側でだけ、宣言を渡して決める。
  - `docs/features/m4-ui-server.md` の、エラーコードの表（`#### エラーコードと HTTP の状態コード`・`#### エラーコードの追加`）と、API の表のフォローアップの行は、Go の側のテストが読んでいる（`internal/server/status_test.go`・`internal/cli/errors_test.go`・`internal/server/followups_test.go`）。状況の API の行の `ingestable=true` の説明（`internal/cli/status_ingestable_test.go`）と、`show --json` のキーを書いた節（`internal/cli/jsondoc_test.go`）も読んでいる。見出しと表の形と、これらの文言を変えない。
  - `docs/glossary.md` と `docs/architecture.md` §21 の冒頭の注記は、S2b の文書のテスト（`internal/cli/docs_s2b_test.go`）が読んでいる。S2b で入れた文言を消さない。
- S2a・S2b で決めて、後の区切りにも効くこと:
  - タスクの行は、計画の版（`plan_version`）と計画の中の識別子（`key`）を「作った出どころ」として持つ。どのタスクを起動・検証するかは、版ではなく、タスクの状態で決める。
  - 起動するのは、統合先を使わない、起動できるタスクがちょうど 1 個の課題だけ（それ以外は、理由 `integration_unavailable`・`no_tasks` で起動しない）。S2c でも変えない。
  - 状況の API が上流を読むのは、問い合わせに `ingestable=true` が付いたときだけ。
  - 画面のボタンで受ける書き込みは、計画の承認・反映を保留にした完了の承認・サイクルを回す、の 3 つ。広げるのは S4（設計書 §9 の改訂と一緒）。
  - 受入基準・決定を変える必要に気付いたら、変えずに PR の説明へ「仕様への指摘」として書く（`CLAUDE.md`）。
- 既定ブランチが一時的に動かなくなることを許す（オーナー 2026-11-17）。サイクルは、core の改修が終わるまで凍結している。
- Tom のワークスペースのバイナリとストアの切り替えは、S2a・S2b・S2c が全部入ってから 1 回行う（オーナー 2026-11-18）。main へ入れる前に、Tom のストアの写しで新しいバイナリを起動し、新しい画面を開いて確かめる。

## 画面・API設計

- UX の決定: `docs/features/core-redesign/ux.md`（決定 28 件・シナリオ 19 件）
- 試作: `docs/features/core-redesign/prototype/`（`web/`・`cli/`・`chat/`）

S2c で作る画面と、試作の対応は次のとおり。配置と見た目は、試作を参照する（受入基準にはしない）。試作は、後の区切りのもの（右の対話の欄・問いに答えるボタン・取り込みのチェックとボタン・スーパーバイザーの記録・計画の後に足したタスクの点線・委譲先の段・費用の見込み）も描いている。S2c では、それらを出さない（下の「やらないこと」）。

| 画面 | 試作のファイル |
|---|---|
| 枠（左の列・上の帯） | 全部の画面 |
| いま進められること | `web/w8-now.html`・`web/w8-now-empty.html` |
| 課題（タスクのツリーの一覧） | `web/w1-issues.html`・`web/w1-issues-empty.html` |
| 課題の詳細（ツリー・経緯・計画の本文） | `web/w2-issue-running.html`・`web/w2-issue-article.html`・`web/w2-issue-alldone.html`（完了の承認を待つ課題。S2c では、あなたを待っているものの区画に、見直し前の完了の承認の要約とボタンを置く）・`web/w10-history.html`・`web/w10-markdown.html` |
| タスクの詳細 | `web/w3-task-running.html`・`web/w3-task-done.html`・`web/w3-task-article.html` |
| 計画の承認 | `web/w4-plan-approval.html`・`web/w4-plan-approved.html` |
| フォローアップの一覧 | `web/w7-followups.html`・`web/w7-followups-empty.html` |
| すべて | `web/w10-all.html` |

試作と変える点:

- 「いま進められること」の「あなたを待っている」に、承認と回答のほか、見直し前の人間待ちの帯にあった区分（不可逆操作の承認・食い違い・予算の増額・トリアージ・スロットの片付け）も出す（試作は、承認と回答だけ。出さないと、いまの画面で見えているものが見えなくなる）。
- 「サイクルを回す」のボタンを、「いま進められること」と「サイクル」の画面と、計画の承認が通った後の表示に置く（試作には無い。承認・回答・取り込みがサイクルを始めるのは S4 で、それまでは、オーナーが始める口が画面に要る）。
- 費用は、使った額と予算の上限を並べて出し、割合の棒は出さない（使った額は判断点と委譲の合計、予算の上限は委譲の枠で、同じ範囲の数字ではないため）。
- 課題の画面の、計画の承認待ちの課題の題名は、ほかの課題と同じく、課題の詳細へ移る（試作は、計画の承認の画面へ移る）。計画の承認の画面へは、枠の中のリンクから移る。
- タスクの番号（① ② …）は付けない（タスクは題名と ID で指す）。
- 上の帯の 4 つの項目とサイクルの状態は、「すべて」では出さない（試作は、選んでいない形で出している）。
- 左の列の「足す」は出さない（押しても何も起きないものを置かない。エージェントを足す流れは flywheel#535）。

URL のハッシュの形（`<名前>` はエージェントの名前、`<C>` は課題の ID、`<T>` はタスクの ID）:

| ハッシュ | 画面 |
|---|---|
| （無し）・`#/` | 一覧の先頭のエージェントの「いま進められること」 |
| `#/all` | すべて |
| `#/a/<名前>/now` | いま進められること |
| `#/a/<名前>/challenges` | 課題 |
| `#/a/<名前>/challenges/<C>` | 課題の詳細（ツリー） |
| `#/a/<名前>/challenges/<C>/history` | 課題の詳細（経緯） |
| `#/a/<名前>/challenges/<C>/plan` | 課題の詳細（計画の本文） |
| `#/a/<名前>/challenges/<C>/approve-plan` | 計画の承認 |
| `#/a/<名前>/challenges/<C>/tasks/<T>` | タスクの詳細 |
| `#/a/<名前>/followups` | フォローアップの一覧（`?status=open\|done\|dropped`・`?challenge=<C>` を付けられる） |
| `#/a/<名前>/cycle` | サイクル |

ハッシュは、`#` の後ろを、最初の `?` で、道と問い合わせに分けて読む。エージェントの名前は、パーセントエンコードして書く。フォローアップの一覧の `status` が、3 つの値のどれでもないときは、`open` として扱う。画面の中の切り替え（フォローアップの状態）は、ブラウザの履歴を増やさずに URL を書き換える。画面から画面への移動は、履歴を増やす。

API の形（S2c で足す・外すもの）:

- `GET /api/v1/workspaces/{name}/tree`: 根は `challenges`・`recent_done`（どちらも配列。要素は、課題のツリーの要素）。課題のツリーの要素は、`budget_usd`（数か null）・`cost_usd`（数）・`dependencies`（配列。要素は `challenge_id`・`satisfied`・`status`・`status_label`・`title`）・`followups_open`（数）・`id`・`next_human_actions`（配列）・`parent`（`challenge_id`・`status`・`status_label`・`title` を持つか、null）・`children`（配列。要素は `parent` と同じ形）・`status`・`status_label`・`tasks`（配列。要素は `cost_usd`・`depends_on`〔`key` の配列〕・`id`〔文字列か null〕・`key`・`phase`・`status`〔文字列か null〕・`title`）・`tasks_done`・`tasks_total`・`title`・`updated_at`・`uses_integration`（真・偽・null）。エラーは、ほかの閲覧の API と同じ（ストアを読めないワークスペースは、いまのコードと状態コード）。
- `GET /api/v1/workspaces/{name}/challenges/{id}`: 根に `tree`（課題のツリーの要素）を足す。
- `GET /api/v1/workspaces/{name}/challenges/{id}/approval`: `approval.plan` に `summary`（文字列か null）・`budget_usd`（数か null）を足す。`approval.plan.tasks` の要素に `phase` を足す。
- `GET /api/v1/questions`: `questions` の要素に `task_id`（文字列か null）を足す。
- `GET /api/v1/workspaces/{name}/graph`: 外す（ほかの無いパスと同じく、404 `not_found`）。
- 画面と共有する値の集合（`view.ClosedSets`）に、表示の区分（`running`・`waiting`・`next`・`blocked`・`done`・`cancelled`）を足し、グラフの区分・依存の種類・登録の経路を外す。
- `flywheel` の端末のコマンドと、その `--json` の形は変えない。

S2b で足した形（変えない）:

- `flywheel followup list [--status open|done|dropped|all] [--challenge <課題の ID>]`。`--json` の根は `followups`（配列。要素は `id`〔`F-<番号>`〕・`challenge_id`〔課題の ID か null〕・`title`・`detail`・`source`・`status`・`note`・`reason`・`promoted_challenge_id`・`created_at`・`updated_at`）。試作（C4）の `--issue` は、課題を指すフラグの名前を、ほかのコマンドの語に合わせて `--challenge` にした（試作のフラグは案）。
- `flywheel followup done <フォローアップの ID>... --note <確かめた結果>`。
- `flywheel followup drop <フォローアップの ID>... --reason <理由> [--relayed --session <会話の識別> --quote <発言の要旨>]`。

## クリティカル設計決定

### DB スキーマ: 衝突の記録の表（S1）

- **採用案**: マイグレーションを 1 本足し、`challenge_conflict` の表と、その索引を消す（スキーマの版は 25 になる）。過去の衝突の記録は消える。
- **理由**: この表を読むのは、直列化グループと、グラフの衝突の線・「待っている理由」の衝突の欄（`graph.go`・`waiting.go`）だけで、どれも外す。過去の記録を読む用途が無い。残すと、全表を埋めるテストの支え（`coretest.FillAllTables`）と書き出しの検査に、使わない表の追従が残り続ける（オーナー 2026-11-17）。
- **代替案**: 表を残し、書き込みと読み取りだけをやめる。却下の理由は上のとおり。
- **影響範囲**: `internal/core/internal/store/migrations`、`internal/core/conflict.go`・`graph.go`・`waiting.go`・`delegate_plan.go`、`coretest.FillAllTables`、`internal/core/export_test.go` の表の一覧、スキーマの版を直に書いているテスト、表を直に読み書きしているテスト（`internal/server/graph_test.go`・`internal/core/graph_test.go`。`internal/core/internal/store/migrate_0018_test.go` は最新まで当てた後で表を読むので、当てる版を 18 までに絞る）。書き出しと再構築（`Export`・`Import`）は表を列挙する作りなので、コードの変更は要らない。版 24 の書き出しは、版 25 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### DB スキーマ: 過去の実行の記録（S1）

- **採用案**: `run.kind = 'predict'` と `run.judgment = 'J9'` を、読み取りで受け付ける値として残す。予測の run が持つ予算の枠の値（`run.budget_bucket = 'predict'`）も同じく残す。新しく作る経路は無くす。すでにある行を終わらせる更新（終わっていない run を、サイクルの後片付けが「中断」にする）は受け付けるままにする。
- **理由**: 2026-11-01〜11-16 に、予測の run が 58 本、J9 の run が 105 本ある。費用の集計と `flywheel runs` の表示の根拠を消さない（オーナー 2026-11-17）。
- **代替案**: 過去の行を消す、または別の値へ書き換える。費用の記録が失われるので採らない。
- **影響範囲**: `internal/core/run_store.go` の値の検査（読み取りと書き込みで受け付ける値を分ける）、`view` の run の表示。

### 宣言の互換: 無くした項目（S1）

- **採用案**: 無くした項目が残っている宣言は、設定の誤り（`config_invalid`）として止める。エラーの文に、項目の名前と、無くなった旨（決まった語 `removed`）を出す。知らないキーを拒む既存のエラーの文（`unknown key`）とは別の文にする。
- **理由**: 宣言は、知らないキーを拒む閉じた集合として検査している。黙って無視すると、設定が効いていると思い込んだまま動かすことになる（オーナー 2026-11-17）。
- **代替案**: 黙って無視して動かす。上の理由で採らない。
- **影響範囲**: `internal/core/connectors_declaration.go`・`internal/core/agent_declaration.go`。Tom のワークスペースの宣言の直しが、S1 を main に入れるときに要る。

### DB スキーマ: 課題 ＞ タスク ＞ フォローアップの持ち方（S2 で適用）

- **採用案**: いまの課題（`challenge`）を「課題」のまま残し、その下にタスク・タスクの前提・フォローアップの表を足す。委譲と完了の検証を、課題からタスクへ付け替える（`run`・`contract_run`・`hold` にタスクへの参照を足す）。計画・承認・反映は、課題の単位のまま残す。
- **理由**: 「承認の真正性」と「完了と反映を 1 回の操作で承認する」（D12）は変えないと決めている（§21.8）。この案は、承認と反映の処理に手を入れずに済む。過去の完了・取り下げの課題は、タスクが 0 個の課題としてそのまま読める。設計書と用語集も、課題を「いまの課題のまま」としている（§21.1）。
- **代替案**: いまの課題をタスクとして読み替え、その上に課題の表を足す。委譲と検証はそのまま使えるが、計画・承認・反映の処理を課題の単位へ上げ直すことになり、識別子の意味が用語集とずれる。
- **影響範囲**: 表と列は、使う区切りで足す。S2a の分は次の節。フォローアップの表と、取り込み元の子の Issue をタスクに対応づける持ち方は、S2b の節（下の「DB スキーマ: フォローアップ・取り込み元の子」）。進行中の課題を新しい形へ移す処理は作らない（開いている課題は 0 件）。

### DB スキーマ: タスク・タスクの前提・計画の問いへの答え（S2a）

- **採用案**: マイグレーションを 1 本足す（スキーマの版は 26 になる）。中身は次のとおり。
  - タスクの表 `task`: `id`（主キー。表示は `T-<番号>`）・`challenge_id`（課題への参照。必須）・`plan_version`（このタスクを作った計画の版。必須）・`key`（計画の中の識別子。計画から作ったタスクだけが持つ。NULL を許す）・`title`・`body`・`done_criteria`（どれも必須）・`non_goals`（JSON の配列。無ければ NULL）・`repo`・`operation`（必須）・`status`（必須。`pending`・`in_progress`・`verifying`・`done`・`cancelled`）・`created_at`・`updated_at`。同じ課題・同じ計画の版の中で、`key` は重ならない（一意の制約。`key` が NULL の行どうしは重なりと見ない）。
  - タスクの前提の表 `task_dependency`: `task_id`・`depends_on_id`（どちらもタスクへの参照。2 つの組が主キー）。
  - 計画の問いへの答えの表 `plan_answer`: `id`（主キー）・`challenge_id`（必須）・`plan_version`（必須）・`question_number`（必須。1 から）・`choice`（選んだ選択肢の番号。文の答えのときは NULL）・`text`（文の答え。選択肢の答えのときは NULL）・`recommended`（推奨と同じ答えなら 1）・`actor`・`channel`・`verification`（承認の記録と同じ意味の 3 つ）・`relay_session`・`relay_quote`（対話で受けたときだけ）・`answered_at`。別々のコマンドで同じ問いに答えが複数記録されたときは、後の行を使う（1 回のコマンドで同じ問いを 2 度は指定できない）。
  - 列の追加: `run.task_id`・`contract_run.task_id`・`hold.task_id`（タスクへの参照。NULL を許す）、`challenge.uses_integration`（1・0・NULL。NULL は、まだ決めていないか、過去の課題）。
  - 過去の行は書き換えない（`task_id` は NULL のまま）。索引と一意の制約は、足す表の分だけを作り、既存のものは変えない。
- **理由**:
  - タスクの行を計画の承認で作る形にすると、承認の前に計画を何度作り直しても、タスクの行の入れ替えが起きない。承認の前のツリーは、計画の構造化した出力（`task_plan.spec`）から読む。
  - 問いへの答えを、保留（`hold`）ではなく別の表に持つのは、答えが課題を止めないことと、問いごと（番号ごと）に「推奨と同じか」を機械的に判定するため。見直し前の論点への回答は、保留の 1 つの文で、問いごとの構造を持たなかった。
  - `task_id` に NULL を許すのは、課題の単位の実行（分類・計画・学び・改修提案の判断点）と過去の行があるため。SQLite は、既存の表へ、既定値の無い必須の列を足せない。
- **代替案**:
  - タスクの行を計画の登録で作り、作り直しのたびに入れ替える。承認の前のタスクに実行は付かないが、行の入れ替えと、古い版のタスクの扱いが増えるので採らない。
  - 問いへの答えを、承認の記録（`approval`）の 1 つの列に JSON で持つ。推奨と違う答えは、承認より前に記録する必要があり（承認されない版にも答えが付く）、承認の行に載せられないので採らない。
  - 既存の課題すべてに、タスクを 1 個ずつ作って埋める。過去の課題（450 件）に、計画に無いタスクを作ることになり、読むだけの用途に要らないので採らない。
- **影響範囲**: `internal/core/internal/store/migrations`、全表を埋めるテストの支え（`coretest.FillAllTables`）、`internal/core/export_test.go` の表の一覧、スキーマの版を直に書いているテスト。書き出しと再構築（`Export`・`Import`）は表と列を実行時に列挙する作りなので、コードの変更は要らない。版 25 の書き出しは、版 26 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### 承認の真正性: 問いへの答えの記録と、計画の作り直し（S2a）

- **採用案**: 計画の問いへの答えは、保留への回答と同じ本人確認（端末での本人確認か、対話で受けたことの記録〔`--relayed`〕）を通して記録する。本人確認の登録簿に、操作の種類 `answer_plan` を足す（端末の本人確認と、対話で受けた記録の組は受ける。画面・本人確認なしの組は受けない）。推奨と違う答え（か文の答え）が 1 件でも記録されたら、課題を計画の承認待ちから分類済へ戻す遷移（T19。操作の名前は `answer_plan`）を足し、次の計画の段に計画を作り直させる。計画の承認（T5）は、答えが記録されていない問いに、推奨の選択肢を、その承認と同じ人・経路・本人確認で記録する。
- **理由**: 計画の承認が「何を承認したか」は、計画の版と、問いごとの答えで決まる。答えを本人確認つきで記録し、推奨と違う答えの後は必ず新しい版の承認を通すことで、承認された計画と、オーナーの答えが食い違わない。差し戻し（T6）と同じ「分類済へ戻して作り直す」経路に乗せると、計画を作る判断点（J2）の対象の決め方と、計画の版の扱いを変えずに済む。
- **代替案**: 課題を計画の承認待ちのまま、作り直しの印だけを付ける。古い版の計画を承認できてしまう時間ができ、それを防ぐ検査が要るので採らない。
- **影響範囲**: `internal/core/transition.go`（遷移表）、`internal/core/verification.go`（登録簿と、遷移から操作の種類を引く対応）、`internal/core/approval.go`、`internal/cli/approval.go`・`commands.go`、`docs/features/m1-core.md` の遷移表と作業ログの一覧。画面のボタンで問いに答える口は、画面のボタンで受ける範囲を広げる決定（設計書 §9 の改訂。`ux.md` の未決は、S4 のクリティカル設計で決め、それまでは §9 の範囲で作るとしている）と一緒に入れる。入れるときは、この記録の口と、登録簿の `answer_plan` を通す。画面のボタンで受ける範囲と本人確認の決まり（設計書 §9）は、S2a では変えない。

### 一意の制約をタスクの単位に改める時期（S2a で決め直した）

- **採用案**: 「終わっていない実行は課題ごとに 1 本」の一意の制約は、S2a では変えず、複数のタスクを同時に走らせる S3 で改める。
- **理由**: この制約は、委譲の実行だけでなく、判断点の実行どうしの排他にも効いている。タスクの単位に改めると、課題の単位の排他が外れるので、別の形で残す設計が要る。S2a で起動するのはタスクが 1 個の課題だけで、いまの制約のままで足りる。S1 の時点のこの文書は「S2 で改める」としていたが、コードを調べたうえで時期を改めた（2026-11-18）。
- **代替案**: S2a で改める。動きを確かめられる場面（同じ課題の 2 つのタスクの同時の実行）が S3 まで無く、確かめられない変更を先に入れることになるので採らない。
- **影響範囲**: S3 の仕様で、`idx_run_active_challenge`・`idx_contract_run_active_challenge` の作り替えと、課題の単位の排他の残し方を決める。

### DB スキーマ: フォローアップ・取り込み元の子（S2b）

- **採用案**: マイグレーションを 1 本足す（スキーマの版は 27 になる）。中身は次のとおり。
  - フォローアップの表 `followup`: `id`（主キー。表示は `F-<番号>`）・`challenge_id`（ぶら下がる課題。課題に属さないものは NULL）・`title`（1 行。必須）・`detail`（説明。無ければ NULL）・`source`（出どころ。必須。S2b で書くのは `learn` だけ）・`status`（必須。`open`・`done`・`dropped`）・`note`（済みにしたときの、確かめた結果）・`reason`（捨てた理由）・`promoted_challenge_id`（上げた先の課題。上げていなければ NULL）・`created_at`・`updated_at`。
  - 取り込み元の子の表 `source_child`: `id`（主キー）・`challenge_id`（親の Issue から作った課題。必須）・`source_id`（取り込み元）・`external_key`（子の識別。一意）・`parent_external_key`（直の親の識別）・`url`・`title`・`body`・`upstream_state`（`open`・`closed`・`missing`。取り込み元との対応 `source_binding` と同じ値）・`created_at`・`updated_at`。
  - 列の追加: `task.source_key`（対応する子の `external_key`。NULL を許す）。
  - 過去の行は書き換えない。出どころが `followup` の過去の課題（295 件）を、フォローアップの行へ移すことはしない。
- **理由**:
  - フォローアップは、分類・計画・承認を通さない 1 行の項目で、課題の状態機械に乗せない（設計書 §21.1）。課題の表に種類を足して持つと、課題を対象にするすべての処理（分類・計画・一覧・状況）に、除外の条件が要る。
  - 上げた先は、フォローアップの側に持つ（`promoted_challenge_id`）。課題の側の `followup_of` は、見直し前から「派生元の課題」を指しており、意味を変えない。
  - 取り込み元の子を、取り込み元との対応（`source_binding`）の行にしないのは、その表が「課題 1 件に対応 1 件」（主キーが `challenge_id`）で、対応のある課題を対象にする処理（追従・除外・差し込み）が、その形に依っているため。子は課題ではないので、別の表に持つ。
  - タスクと子の対応を、タスクの側の列（`source_key`）に持つのは、タスクの行が計画の承認で作られ、承認の前の対応は計画の構造化した出力（`task_plan.spec` の `source`）から読めるため。
- **代替案**:
  - 過去の `followup` の課題を、フォローアップの行へ移す。完了・取り下げの課題に付いた実行・承認・作業ログの記録が宙に浮くので採らない（過去の課題は、読めれば足りる）。
  - 子の本文を記録せず、計画のたびに上流から読む。計画の段が上流の読み取りに依り、上流を読めないときに計画が止まるので採らない（追従は、取り込みの段でまとめて行う）。
  - フォローアップに、ぶら下がるタスク（`task_id`）の列も足す。S2b でフォローアップを書くのは、課題を単位にする学びの判断点だけで、タスクから出るフォローアップ（スーパーバイザーの手・委譲先の軽い指摘）は S4 から。列は、使う区切りで足す。
- **影響範囲**: `internal/core/internal/store/migrations`、全表を埋めるテストの支え（`coretest.FillAllTables`）、`internal/core/export_test.go` の表の一覧。版 26 の書き出しは、版 27 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### フォローアップを上げる先（S2b）

- **採用案**: S2b では、フォローアップを上げると、いつも新しい課題になる（課題に属するフォローアップは、その課題を派生元とする課題。属さないものは、取り込み元の無い課題）。「課題が開いていれば、その課題のタスクにする」（`ux.md` の決定 21）は、複数のタスクを走らせる S3 で入れる。
- **理由**: 開いている課題にタスクを 1 個足すと、起動できるタスクが 2 個になる。S2a・S2b の core は、起動できるタスクがちょうど 1 個の課題だけを進めるので、足した課題は、S3 まで止まる。完了の承認待ちの課題に足した未着手のタスクは、完了の承認で取りやめになり、上げた作業が消える。新しい課題にすれば、タスクが 1 個の課題として、いまの core で最後まで進む。
- **代替案**:
  - S2b で、開いている課題のタスクとして足す（設計のとおり）。上の理由で、足した課題が S3 まで進まない。
  - 上げる操作そのものを S3 へ送る。フォローアップが、一覧に溜まるだけで作業にできなくなるので採らない。
- **影響範囲**: `ux.md` の決定 21 との差は、S3 の仕様で埋める（そのとき、上げた先のタスクの記録の列を足す）。設計書 §21.1 の「上げたものは、その課題の中の派生のタスクになる」も、S3 から。core が済みにするきっかけも、S2b では「上げた先の課題の完了」で、設計書の「上げた先のタスクの完了」になるのは S3 から。

### 承認の真正性: フォローアップを捨てる・上げる（S2b）

- **採用案**: 捨てる（`followup_drop`）と上げる（`followup_promote`）は、保留への回答と同じ本人確認（端末での本人確認か、対話で受けたことの記録〔`--relayed`〕）を通す。本人確認の登録簿に、この 2 つの操作の種類を足す（画面・本人確認なしの組は受けない）。済みにする操作は、本人確認を通さない。
- **理由**: 設計書 §21.1 が、上げるのと捨てるのは「オーナーか、オーナーの指示を受けたオーケストレーター」、済みにするのは「オーナーとオーケストレーター（確かめた結果を書く）」と分けている。上げる操作は作業（費用）を増やし、捨てる操作は項目を消すので、オーナーの指示の記録を残す（上げる操作の記録の形は、設計書 §21.9 の U13）。
- **代替案**: 3 つとも本人確認なしにする。オーナーの指示の無い、作業の追加と項目の削除を、記録の上で見分けられなくなるので採らない。
- **影響範囲**: `internal/core/verification.go`（登録簿）、`internal/cli`（`relayedFlags` を付けるコマンド）。画面のボタンで済みにする・捨てる口（`ux.md` の決定 20）は、画面のボタンで受ける範囲を広げる決定（設計書 §9 の改訂。S4）と一緒に入れる。

### 取り込みを選ぶ形と、取り込み元の親子（S2b）

- **採用案**:
  - 新しい課題を作るのは、オーナーが選んだ Issue だけにする（`flywheel ingest <指定>...`）。サイクルの取り込みの段と、引数の無い `flywheel ingest` は、取り込み済みのものの追従だけを行う。
  - 選んだ Issue の子孫は、深さを問わず、その課題の「取り込み元の子」として平らに記録する。子は課題にしない。タスクにするかは、計画を作る判断点（J2）が決める（子は、ツリーの初期値）。
  - 親を持つ Issue も、単独で選べば、独立した課題になる。
  - 取り込みの後に上流で足された子は、自動では記録しない。
  - 子の記録は、課題を取り下げても残し、取り込み元との対応を外す操作（`flywheel unbind`）で消す。
- **理由**:
  - 課題の出どころを測ると（設計書 §21.0）、取り込みの 96 件に対し、オーナーの番を待つ時間が課題の時間の大半だった。取り込むものをオーナーが選ぶ形にして、選んでいないものが分類・計画・承認待ちに並ばないようにする（`ux.md` の決定 8）。
  - 子を課題にせず、課題の下の記録にするのは、設計書 §21.1 の「親の Issue を課題にし、子の Issue はそのタスクとして取り込む。読むのはツリーの初期値としてで、正本は flywheel」のとおり。
  - 子を単独で選べるようにするのは、複数のタスクの課題が S3 まで進まないため。親ごと取り込むと止まる間も、親を取り込まずに、子を 1 件ずつ、タスクが 1 個の課題として進められる（親を取り込んだ後は、対応を外してから選び直す）。
  - 平らに記録するのは、core が持つ層が「課題 ＞ タスク」の 2 つで、取り込み元の深さを写す層が無いため。直の親は、計画を作る判断点（J2）が前提の線を引く材料として渡す。
  - 取り下げた課題の子を残すのは、取り下げた課題の Issue そのものが、対応を外すまで取り込み直せない、いまの作りに合わせるため（取り下げたものが、取り込めるものに戻って並ぶのを避ける。戻したいときは、対応を外す）。
- **代替案**:
  - 親を選んだら、子は必ずタスクにする（計画を作る判断点に任せない）。子に無い作業（設計・結合の確かめ）を足せず、粒の合わない子をまとめられないので採らない。
  - 子を単独では選べないようにする。上の理由（S3 までの間、進める道が無くなる）で採らない。
  - 取り込みの後に足された子も、追従で記録する。承認済みの計画に無い子が増え、計画との食い違いをどう扱うかの決まりが要る。計画の後にタスクを足す形（S4）と一緒に決める。
- **影響範囲**: `internal/core/ingest.go`、`internal/cli/ingest.go`、`docs/features/m2-github-issue-ingest.md`。Tom の運用では、取り込みが自動で課題を作らなくなる（切り替えのときに、対話のセッションの進め方を合わせる）。

### 取り込み元とタスクの対応と、委譲先へ渡す取り込み元（S2b）

- **採用案**: タスクは、対応する子を 0 件か 1 件持つ（`source_key`）。1 件の子に対応するタスクは 1 個まで。委譲先へ渡す取り込み元（差し込み `{issue_number}`・`{issue_url}`・`{external_key}`）は、次の順で決める。
  1. タスクが対応する子を持つ → その子。
  2. 持たず、承認済みの計画のタスクが 1 個 → 課題の取り込み元（あれば）。
  3. 持たず、承認済みの計画のタスクが 2 個以上 → 渡さない（取り込み元の無いタスク）。
- **理由**: 委譲先は、取り込み元を、成果物からの参照（開発では、PR が Issue を閉じる書き方）に使う。子に対応するタスクの成果は、その子を閉じる。タスクが 1 個の課題では、タスクの成果が課題の成果なので、課題の取り込み元を閉じる（見直し前と同じ）。タスクが複数の課題で、子に対応しないタスクに課題の取り込み元を渡すと、最初のタスクの成果が、親の Issue を閉じてしまう。
- **代替案**: 子に対応しないタスクには、いつも課題の取り込み元を渡す。上の理由（親の Issue が早く閉じる）で採らない。
- **影響範囲**: S2b で効くのは 1 と 2（起動するのが、統合先を使わない課題だけで、その計画のタスクは 1 個のため）。3 は、複数のタスクを走らせ、タスクを文面で渡す S3 から効く（「委譲先との契約」の、足すもの 1）。計画を登録するときの、操作の検査（取り込み元の差し込みを要する操作を選べるか）を、タスクの単位でこの順に合わせるのも、S3。

### 状況の出力の互換と、上流の読み取り（S2b）

- **採用案**: `flywheel status --json` と状況の API は、いまあるキーと形を変えず、キーを足す（`ingestable`・`followups`・`cycle_work`）。文の出力は、並びと見出しを改める。状況の API が上流の Issue の一覧を読むのは、問い合わせに `ingestable=true` が付いたときだけにする。
- **理由**: いまの形は、画面（ボードと帯）と、仕様の文書に照らすテストが読んでいる（`ux.md` の未決「`--json` の利用への影響」を調べた結果。指示文とスクリプトからの読み取りは無い）。画面は S2c で作り替えるので、それまで、いまの画面を動くままにする。状況の API は画面が定期的に読むので、読むたびに上流の一覧（リポジトリごとに 1 回以上の呼び出し）を読ませない。
- **代替案**:
  - 根の形を「いま進められること」に合わせて作り直す。画面と文書とテストの追従が、S2c の前に二度手間になるので採らない。
  - 取り込めるものを、別のコマンドと別の API にする。`ux.md` の決定 24（新しいコマンドを足さず、`flywheel status` に出す）と食い違うので採らない。
- **影響範囲**: `internal/view`（`StatusResponse`）、`internal/server/status.go`、CLI と API の応答が同じであることを確かめるテスト（`ingestable=true` を付けた応答と比べる形に改める）、`docs/features/m1-core.md`・`m4-ui-server.md`。「回した場合の費用の見込み」（設計書 §21.4）は、費用の集計を入れる S5 で足す。

### 改修提案の判断点（J8）を変えない（S2b）

- **採用案**: S2b で、課題を起票しなくなるのは、学びの判断点（J6）だけにする。改修提案の判断点（J8）は、改修の課題を起票する形のまま残す。
- **理由**: 改修の課題は、改修の鍵（層と対象）で、発生の記録と結び付いており、同じ鍵の終わっていない課題があれば、起票せずにそれへ紐づける作りになっている。フォローアップへ移すには、この結び付きの持ち方を決め直す必要がある。設計書 §21.6 は、学びと改修提案の判断点を、スーパーバイザーの振り返りにまとめる（S5）としており、結び付きは、そのときに決め直す。件数は、学びの判断点のフォローアップが 295 件、改修提案の課題が 46 件（設計書 §21.0）で、先に効くのは学びの側。
- **代替案**: S2b で、改修提案も、課題に属さないフォローアップとして書く。上の理由（結び付きの決め直しが、S5 と二度手間になる）で採らない。
- **影響範囲**: S5 までは、改修提案の判断点が起票した課題が、分類の対象になる（見直し前と同じ）。

### 本文を Markdown として整える部品（S2c）

- **採用案**: `marked` の字句解析（本文を、見出し・段落・表などの部分の並びに分ける所）だけを使い、その並びから、画面の部品（React の要素）を自前で組み立てる。HTML の文字列は作らず、要素に HTML の文字列を差し込む口（`dangerouslySetInnerHTML`）も使わない。字句解析が「生の HTML」と判定した部分は、書いてある文字のまま出す。リンクは、行き先が `http:`・`https:` のものだけをリンクにする。画像は読み込まず、代わりの文字（と、行き先へのリンク）を出す。`marked` は、いま `mermaid` を通して入っている版を、`web/package.json` の直接の依存に書いて固定する。
- **理由**: 本文（計画・説明・完了条件・問い）は、判断点・委譲先・上流の Issue から来る、外の文字で、そのまま HTML にすると、画面の中でスクリプトが動きうる。画面は、承認の口（計画の承認・反映を保留にした完了の承認）を、ボタンを押すだけで呼べるので、画面の中でスクリプトが動くと、承認まで届く。HTML の文字列を作らない形にすれば、無害にする処理の抜けに頼らずに、この道を構造で閉じられる。画像を読み込まないのは、本文を開いただけで外へ通信が出る（どの課題をいつ見たかが、外に伝わる）のを避けるため。字句解析に `marked` を使うのは、表や入れ子の箇条書きの読み取りを自作すると、誤りが出やすいため（新しく入る物は無く、いま入っている物を直接使うだけ）。
- **代替案**:
  - `marked` で HTML の文字列にし、`DOMPurify` で無害にして、要素に差し込む。どちらもいま入っているが、無害にする設定の誤りや抜けが、そのまま承認の口へ届く道になるので採らない。
  - `react-markdown`（と表のための追加）を足す。要素を組み立てる形で、生の HTML も通さないが、数十の物が新しく入る。いま入っている `marked` で同じ形が作れるので採らない。
  - 字句解析から自作する。依存は増えないが、表・入れ子・コードのブロックの読み取りの誤りが出やすいので採らない。
- **影響範囲**: `web/package.json`（`marked` を直接の依存に）、Markdown の部品（新しいファイル）、本文を出す所（課題の詳細・タスクの詳細・計画の承認）。図（`FigureView`。Mermaid）は、見直し前と同じ部品のまま。flywheel#682 の決定「生の HTML を通さない Markdown の部品を 1 つ入れて、部品の選定まで決める」の持ち越し分。

### 画面のボタンで受ける範囲を広げない（S2c）

- **採用案**: S2c の画面のボタンで受ける書き込みは、見直し前と同じ 3 つ（計画の承認・反映を保留にした完了の承認・サイクルを回す）のままにする。試作にある、問いに答えるボタン・取り込みのチェックとボタン・フォローアップを済みにする・捨てるボタン・計画を作り直すボタンは作らず、その場所に、端末のコマンドの案内を出す。計画の承認の画面の問いの選択肢は、見せるだけで、選べない。
- **理由**: 設計書 §9 は、画面のボタンで受ける範囲を、計画の承認と、反映を保留にした完了の承認に限っている（画面の口には、委譲の子からも届きうるため）。範囲を広げる決定（`ux.md` の決定 26・27）は、子から届かないことの守り方と一緒に、対話の欄を作る S4 で、設計書の決定として足すと決めてある（`ux.md` の未決）。S2c で一部だけ先に広げると、守り方を決める前に口が増える。
- **代替案**: 選ぶだけの回答と、フォローアップを済みにする口だけを、S2c で先に足す。上の理由で採らない（S4 でまとめて決める）。
- **影響範囲**: `internal/server` に `POST` の口は増えない。画面の承認の経路（経路 `ui`・本人確認の方式 `none`）と、core が強制する範囲は変わらない。

### 表示の区分と件数を core が決める（S2c）

- **採用案**: タスクの表示の区分（走っている・あなたを待っている・次に走る・前提を待っている・済み・取りやめ）、課題のタスクの進み、費用の合計、未のフォローアップの件数は、core が決めて、課題のツリーの API が返す。画面は、返ってきた値を出すだけにする。計画の承認の画面のツリーの区分も、承認の要約の API が返す。
- **理由**: 表示の区分は、タスクの状態・前提・保留の 3 つから決まる。画面の側で決めると、同じ決まりを、端末の表示（S4 で作る `flywheel cycle status` など）と二重に持つことになり、食い違う。件数も同じ（未のフォローアップの数え方は、状況の `followups.open` と同じ決まりを使う）。課題の画面は、開いている課題の全部のツリーを 1 回で出すので、課題ごとに詳細を読むと、課題の数だけ呼び出しが増える。
- **代替案**:
  - 画面が、課題ごとに課題の詳細の API を読んで、区分と件数を導く。呼び出しが課題の数だけ増え、決まりが画面に入るので採らない。
  - 課題の一覧の API（`GET …/challenges`）の要素に、タスクと件数を足す。この API は、60 秒ごとと変化の合図のたびに、全部のエージェントの分を読んでいる。ツリーの中身まで毎回運ぶと重くなるので、課題の画面を開いている間だけ読む、別の口にする。
- **影響範囲**: `internal/core`（新しい読み取りの口）、`internal/view`、`internal/server`、型の生成。

### グラフの API を外す（S2c）

- **採用案**: グラフの画面と一緒に、グラフの API（`GET …/graph`）・型・core の口・テスト・照合用の見本・グラフ専用の種・本物のサーバを相手にしたグラフの試験を外す。課題どうしの関係のうち、記録した前提は、課題のツリーの API の `dependencies` と、課題の詳細の `challenge.dependencies`・`dependents` で出す。課題の親子（見直し前の、親の大枠）は、課題のツリーの要素の `parent`・`children` で返し、課題の詳細に、文字で出す。
- **理由**: グラフの API を読むのは、グラフの画面だけ（端末のコマンドには無い）。画面を外した後に API とテストを残すと、使われない形を、型の生成・照合用の見本・種のテストと一緒に、保ち続けることになる。課題の親子は、見直しで、取り込み元の親子を「課題と、そのタスクの初期値」にする形に改めた（S2b）ので、新しく作られる課題どうしの親子は、増えない。
- **代替案**: API は残し、画面だけ外す。上の理由で採らない（課題の親子を返す口が、グラフの API だけだったので、その分は、課題のツリーの要素へ移す）。
- **影響範囲**: `internal/core`（グラフの口と値の集合）・`internal/view`・`internal/server`・`web/src/testing/relation-api.golden.json`・`web/e2e-real`・`Makefile` の `e2e-real`（筋書きを作り替える）・`docs/features/ui-relation-graph.md`（外した旨の注記）。

## 機能全体の設計

### アーキテクチャ決定

- 区切りの順は、外す → 土台 → 委譲先との境界 → 長く走るサイクルとスーパーバイザー → 仕上げ、とする。先に外すのは、ストアの形を変えるときに運ぶコードを減らすため。土台を次に置くのは、後の区切りがどれも「タスク」を単位にするため。
- 土台（S2）は、ストアと計画（S2a）→ 入口と出口（S2b）→ 画面（S2c）の順に分けて入れる。S2b と S2c は S2a のストアを使い、S2c は S2b の API を使う。1 回に入れる量を、全体を確かめられる大きさ（S1 は 135 ファイル・受入基準 68 件）に近づけるために分ける。
- サイクルの構造は、flywheel に決まった形として持つ。YAML の定義から描いて調整できるようにするのは、この機能の範囲外（flywheel#265・#266）。
- claude-harness 側の受け口（Issue の無い入力・統合ブランチを作る口・承認した中身つきで既定ブランチへ入れる口・統合ブランチから上げるフロー・任意の成果物を上げる口・取り込んで新しい中身を返して待つ口・自己レビューの値の返却）は、別のリポジトリなので、この文書に契約（flywheel が渡すもの・受け取るもの）を書き、実装は claude-harness 側の Issue にする。契約は、S3 を待たず、S2a の実装と並行して先に書いた（S3 の出荷条件が claude-harness 側の出荷なので、先に始める）。下の「委譲先との契約（S3 で使う受け口）」。契約の既存の値の意味は変えない（レビュー待ちへの答え `ready` は「flywheel が反映まで済ませた」の意味のまま残し、新しい意味には新しい値を足す）。
- 画面の行き先は、URL のハッシュに持つ（S2c）。サーバは、`/` で画面を返すだけのままにし、画面の中の行き来のための受け口を増やさない。ルーティングのライブラリは足さず、ハッシュを読んで画面を選ぶ小さな部品を持つ。
- 画面ごとに要るデータ（課題のツリー・課題の詳細・承認の要約・フォローアップ・作業ログ）は、その画面を開いている間だけ読む（S2c）。全部のエージェントについて常に持つのは、見直し前と同じく、状況・課題の一覧・サイクル・あなたを待っているものの横断だけにする。
- S1 で委譲の計画の処理（`planDelegation`・`executePlan`）を単純にするとき、S2 でタスクの単位に付け替えることを見越して、候補 1 件を 1 つの単位として扱う形にとどめる（タスクの概念は S1 に持ち込まない）。

## 委譲先との契約（S3 で使う受け口）

区切り S3（委譲先との境界）で flywheel が委譲先へ渡すもの・受け取るものを、ここに決める。S3 の出荷条件が委譲先（claude-harness）の側の出荷なので、S3 の仕様より先に書く（オーナー 2026-11-18）。この節は、契約（外から見える形）だけを決める。flywheel の側の実装（宣言のキー・記録の持ち方・受入基準）は、S3 を実装対象にするときに書く。claude-harness の側の作り（ワークフローの段・入力の名前・ブランチの名前）は、claude-harness の側で決める。

調べた時点: flywheel は main b2675f2、claude-harness は main c21a1fc（2026-11-18）。

### いまの契約（版 1）と、変えないもの

- 契約のコマンドは、始める（`start`）・状態を読む（`status`）・答えて再開する（`resume`）・取り消す（`cancel`）の 4 つ。出力は JSON 1 つで、形は `docs/features/m3-invoker-delegation.md` の「接続ツールとの契約」が正本。
- 出力のキー（`contract_version`・`run_id`・`state`・`summary`・`requested_action`・`artifacts`・`cost_usd`）と、値の集合（`state` の 5 つ・`requested_action.kind` の 4 つ・`requested_action.decider` の 3 つ・`artifacts[].kind` の 4 つ）は変えない。
- レビュー待ち（`requested_action.kind` が `review`）への、いまの 2 つの答えの意味は変えない。`respond` は「直してほしい（理由は `note`）」、`ready` は「flywheel の側で反映まで済ませた」。
- 契約の版は 1 のままにする。下に足すものは、どれも「知らない側が読み飛ばせる」か「使う側が、相手が受けると分かったときだけ使う」形にする。
- 出力の、知らないキーは読み飛ばす（いまの flywheel の作りがそうなっている。これを契約の決まりにする）。
- 版を上げるのは、次のどれかをするとき（これまで文になっていなかったので、ここに書く）: すでにあるキーや値の意味を変える。値の集合の外の値を、呼ぶ側が受けると宣言していないのに出す。必須のキーを足す・消す。`requested_action` を複数にする。
- 新旧の組み合わせごとの動き:
  - 新しい委譲先と、いまの flywheel: flywheel は、新しい入力を渡さず、`land` も返さない。委譲先は、いまと同じに動く（`respond`・`ready` の動きを変えない。新しい入力を受けていない実行では、統合先を使わず、`role` の付いた成果物も出さない。`facts` は、知らない側が読み飛ばせる任意のキーなので、出してよい）。
  - いまの委譲先と、S3 の flywheel: 支えない。S3 の flywheel は、自分で反映する処理を持たないので、レビュー待ちの `options` に `land` が無い委譲先の成果を、宛先へ入れる道が無い。黙って待たせず、課題を保留にして、委譲先が `land` を受けられないことをオーナーへ知らせる。S3 を main に入れるのは、claude-harness の側の出荷の後（スライスの表の出荷条件）。
  - 宣言の差し込みの集合は、flywheel の版で決まる（契約の版は、出力の形の版）。いまの flywheel は、知らない差し込みを宣言の誤りとして止める。宣言に新しい差し込みを書くのは、そのワークスペースを S3 の flywheel に切り替えるときにする。

### 足すもの 1: 取り込み元の無いタスクを渡す（始めるときの入力）

- flywheel は、タスクの文面を 1 つのファイルに書き、その場所を渡す。宣言の `start` に書ける差し込みに、次の 4 つを足す。
  - `{task_file}`: タスクの文面のファイルの絶対パス。UTF-8 の Markdown。中身は、core が LLM を使わずに組み立てる（背景〔方針・論点の決定・完了したら見えるもの・やらないこと〕、指定のタスク〔題名・何をするか・完了条件・やらないこと〕、ツリーのほかのタスクの題名の一覧と「ほかのタスクは範囲外」の明記）。ファイルは、その実行が終わるまで消さない。
  - `{task_id}`: タスクの ID（`T-<番号>`）。これを受けた委譲先は、作業ツリーやブランチの名前を、タスクごとに重ならないように、この ID から決める（取り込み元の番号からは決めない。同じ取り込み元を持つタスクが、同時に走りうるため）。
  - `{uses_integration}`: この課題が統合先を使うか（`true` か `false`）。
  - `{challenge_id}`（いまもある）: 課題の識別。統合先を使うとき、同じ課題のタスクを同じ統合先へ集める鍵にする。
- 取り込み元（Issue）があるタスクでは、いまの差し込み（`{issue_number}`・`{issue_url}`・`{external_key}`）も一緒に渡せる。委譲先は、文面のファイルと取り込み元の、少なくとも片方があれば始められるようにする。両方あるときは、文面のファイルを作業の範囲の正本とし、取り込み元は成果物からの参照（開発では、PR が Issue を閉じる書き方）に使う。
- 委譲先は、文面のファイルを解釈して分岐しない（作業する側へ、要件の文面としてそのまま渡す）。
- 値の無い差し込みは、空の文字列で渡る（引数の数は変えない）。委譲先は、空の文字列を「無い」と読む。S3 の flywheel は、`{task_file}` を書いた宣言では、取り込み元の無いタスクにも、取り込み元の差し込みを空の文字列にして起動する。
- どのタスクにどの取り込み元を渡すかは、「クリティカル設計決定」の「取り込み元とタスクの対応と、委譲先へ渡す取り込み元（S2b）」で決めた（対応する子を持つタスクには、その子。持たないタスクには、承認済みの計画のタスクが 1 個なら課題の取り込み元、2 個以上なら渡さない）。

### 足すもの 2: 統合先

- 統合先の名前と作り方は、委譲先が決める。`{uses_integration}` が `true` のとき、委譲先は、`{challenge_id}` から決めた統合先を使い、無ければ作る。flywheel は、統合先を作らず、名前も決めない。
- 成果を入れる先を、宛先と呼ぶ。統合先を使うタスクの成果の宛先は統合先、使わないタスクの成果の宛先は反映先（開発では既定ブランチ）にする。
- 委譲先は、統合先を使う実行の成果物に、統合先の識別と、その時点の中身の識別を足して返す。成果物の要素に、任意のキー `role` を足し、値 `integration` で印を付ける（開発では、`{"kind": "branch", "ref": <統合ブランチの名前>, "role": "integration"}` と `{"kind": "commit", "ref": <統合ブランチの先頭のコミット>, "role": "integration"}`）。`role` の無い要素は、いまと同じく、そのタスクの成果物。
- `role` が `integration` の要素を出すのは、`{uses_integration}` に `true` を受けた実行だけにする（この入力を渡さない、いまの flywheel へは出さない）。出すときは、統合先の識別（`branch`）と中身の識別（`commit`）を、1 つずつ出す。
- 成果を統合先へ入れて終えた実行（`succeeded`）の成果物には、入れた後の統合先の中身の識別を出す（flywheel は、課題の全体の検証と、完了の承認の対象の中身に、これを使う）。

### 足すもの 3: 「入れてよい」の答え（`land`）と、宛先が動いたときのやりとり

レビュー待ちへの答えに、新しい値 `land` を足す。意味は「検証（と、要るときは承認）を通ったので、この中身を宛先へ入れてよい」。

- flywheel は、`land` と一緒に、通した中身の識別を渡す。宣言の `resume` に書ける差し込みに、`{approved_ref}`（開発では、通した先頭のコミット）を足す。
- 委譲先は、`options` に `land` を入れたレビュー待ちの成果物に、そのタスクの成果のいまの中身の識別（`kind` が `commit` で、`role` の無い要素）を、ちょうど 1 つ出す。flywheel は、これを検証と承認の対象の中身として記録し、`{approved_ref}` に使う。この要素が無い・2 つ以上あるレビュー待ちには、flywheel は `land` を返さず、課題を保留にする。
- 委譲先は、レビュー待ちで `land` を受けられるとき、`requested_action.options` に `land` を入れる。flywheel は、`options` に `land` があるときだけ `land` を返す（無い相手との組は、上の「新旧の組み合わせごとの動き」）。
- `land` は、flywheel が、通した中身を付けて自分で返す答えにする。オーナーへの問いの選択肢や、子の問いを振り分ける判断点（J4）の選択肢には出さない。委譲先は、`{approved_ref}` が空の `land` を、下の 3（一致しない）として扱い、宛先へ入れない。
- `land` を受けた委譲先の動き:
  1. 成果物のいまの中身が `{approved_ref}` と一致し、宛先の最新を含んでいる → 宛先へ入れる（入れる操作にも、中身の一致の条件を付ける。開発では、先頭のコミットが一致するときだけ通るマージ）。その後、片付けて、実行を終える（`succeeded`）。
  2. 一致するが、宛先が動いていて、成果物が宛先の最新を含んでいない（衝突が無くても同じ） → 宛先の最新を成果物へ取り込み、宛先へは入れずに、新しい中身を成果物に出して、もう一度レビュー待ちで待つ。
  3. 一致しない → 宛先へ入れずに、いまの中身を成果物に出して、もう一度レビュー待ちで待つ。
  4. 宛先が動いた以外の理由で入れられない（チェックが通っていない・宛先の保護の決まり） → 宛先へ入れずに、理由を `summary` と `requested_action.text` に書いて、もう一度レビュー待ちで待つ（中身は変えない）。続けられないときは、失敗で終える。
- 委譲先は、`land` を受けた後、上の 2・3・4 のほかの理由では、レビュー待ちへ戻らない。別の種類の待ちへも移らない（宛先へ入れる道は、中身の識別を付けた `land` だけにする）。
- `land` の後のレビュー待ちと、最初のレビュー待ちは、出力の形が同じ。flywheel は、自分の記録（最後に返した答えと、そのときの `{approved_ref}`）で見分ける。中身が `{approved_ref}` と同じまま戻ってきたとき（上の 4）は、すぐには `land` を返し直さず、課題を保留にして、委譲先の書いた理由をオーナーへ見せる。
- 同じ `{approved_ref}` の `land` を 2 度受けても、委譲先は、宛先へ 2 度入れない。終わった実行への `resume` には、終わりの状態をそのまま返す。flywheel は、`resume` が失敗したとき、次の機会に同じ `land` を返し直してよい。
- 取り込みの形: 委譲先は、宛先の最新を「取り込みだけ」と機械的に見分けられる形で取り込む（開発では、宛先の最新をマージのコミットとして取り込む。履歴の書き換え〔rebase・強制の push〕をしない）。衝突を直すときは、その取り込みのコミットの中だけで直し、関係のない変更を足さない。
- 委譲先は、最初にレビュー待ちへ出す前にも、宛先の最新を取り込む。
- 委譲先は、宛先が動いていないかを、宛先へ入れる直前に確かめる。確かめてから入れるまでの間に宛先が動く隙間は残る（いまの flywheel の反映の処理と同じ）。
- 取り込んだ後、委譲先は、新しい中身のチェックの完了を待たずに、レビュー待ちへ戻ってよい。チェックの完了は、flywheel が待つ（下）。
- flywheel は、`land` を返す前に、通す中身のチェックがすべて通っていることを、上流のアダプタの口で自分で確かめる（いまの反映の処理と同じ。最初の `land` でも、宛先が動いた後の `land` でも行う。チェックがまだ走っている間は、`land` を返さずに待つ）。委譲先の側の検査（上の 4）は、それに足す安全側の確かめで、flywheel の確かめの代わりにはしない。
- 変わった中身の判定は flywheel が持つ（委譲先の申告は使わない）。flywheel は、レビュー待ちの成果物の中身が、通した中身と違うとき、上流のアダプタの比較の口で「取り込みだけ・衝突の解消あり・関係のない変更あり・判定できない」を見分け、通すときは、新しい中身を `{approved_ref}` にして、もう一度 `land` を返す。通さないときは、検証と承認へ戻す（設計書 §21.3 の「完了を承認した後に反映先が動いたとき」）。その間、タスクの実行はレビュー待ちのまま残し、やり直した検証で直しが要るときは `respond` を、通ったときは新しい中身の `land` を返す。
- `land` を返す時期は、宛先で違う。宛先が統合先の実行には、完了の検証の判断点（J5）がタスクを「満たした」とした後に返す（オーナーの承認は要らない）。宛先が反映先の実行には、オーナーの完了の承認の後に返す。委譲先から見た動きは、どちらも同じ。
- `ready`（flywheel の側で反映まで済ませた）は残す。flywheel が自分で反映する処理を外した後は、flywheel は `ready` を返さない。

### 足すもの 4: 課題を反映先へ上げる（新しい依頼）

待っている実行が無いときの反映は、新しい依頼として始める。使うのは、統合先に集めた課題を反映先へ上げるときと、委譲先のフローを通らずに作られた成果物（スキルを直接呼ぶ形・指示文を直接渡す形の委譲の成果物）を反映先へ上げるとき。

- 宣言の操作として、タスクの実行とは別に、反映の操作を 1 つ書けるようにする（flywheel の側の宣言の形は、S3 の仕様で決める）。反映の `start` に書ける差し込みに、`{artifact_ref}`（上げる成果物の参照）を足す。統合先を上げるときは、委譲先が返した統合先の識別（`role` が `integration` の `branch` の `ref`）。それ以外は、成果物の参照（開発では PR の URL）。
- 委譲先の動き:
  1. 用意する。統合先を上げるときは、反映先へ上げるための実物を作る（開発では、統合ブランチから既定ブランチへの PR。すでにあれば、それを使う）。反映先の最新を取り込み、上げる前の検証（委譲先の決まりの検査）を行う。
  2. 成果物に、実物（開発では PR）と、その中身の識別（`kind` が `commit` で、`role` の無い要素を、ちょうど 1 つ）を出して、レビュー待ち（`options` に `land`）で待つ。この依頼は、`land` を受けるまで、反映先へ入れない。
  3. `land` と `{approved_ref}` を受けた後は、足すもの 3 と同じに動く（一致して、反映先の最新を含んでいれば、反映先へ入れる。そうでなければ、入れずにレビュー待ちへ戻る）。
  4. 反映先へ入れた後、統合先と作業ツリーを片付けて、実行を終える（`succeeded`）。成果物には、反映先へ入れたもの（開発では PR）と、入れた後の中身の識別を出す。
- 統合先に集めた課題では、flywheel は、課題のタスクがすべて統合先へ入った後、オーナーの完了の承認の前に、この依頼を始める。委譲先が用意した実物とその中身を、課題の全体の検証（完了の検証の判断点〔J5〕）と、オーナーの完了の承認に使う。承認の後、承認した中身を `{approved_ref}` にして `land` を返す。
- 委譲先のフローを通らずに作られた成果物では、flywheel は、オーナーの完了の承認の後に、この依頼を始める。レビュー待ちの中身が、承認した中身と同じか、足すもの 3 の判定で通せる違いだけのとき、`land` を返す。
- flywheel が通さないとき（関係のない変更あり・判定できない・オーナーの差し戻し）は、その依頼を取り消す（`cancel`）。取り消された委譲先は、反映先へ入れず、統合先も消さない（自分の作業ツリーだけを片付ける。用意した実物を閉じるかは、委譲先が決める）。直しが済んで、検証と承認をやり直せる状態になったら、flywheel は、新しい依頼を出す。
- 設計書 §21.3 の表は、この依頼で flywheel が渡すものを「承認した中身」としている。この節では、依頼を承認の前にも始められる形にし、承認した中身は `land` で渡す（オーナーが完了の承認の前に見る実物を、委譲先が用意するため）。承認していない中身が反映先へ入らないことは変わらない。

### 足すもの 5: 委譲先が値で返すもの（`facts`）

- 出力に、任意のキー `facts` を足す。名前から値への対応（どちらも文字列）で、機械的に確かめられることを委譲先が返す。
- claude-harness は、自己レビューを実行したかを `self_review`（`complete`・`incomplete`・`not_run`）で返す。値は、委譲先が最後に作業した時点（実装か、レビューの指摘を受けた直し）のものにする。宛先の最新の取り込みでは、値を変えない。
- `facts` の形が合わないとき（値が文字列でない）は、flywheel は、`facts` が無いものとして扱う（出力の全体を誤りにしない）。
- flywheel は、名前と値の意味を持たない。どの名前がどの値であることを求めるかは、宣言に書き、core が LLM を使わずに照らす（宣言の形は、S3 の仕様で決める）。

### 契約に入れないもの

- 作業ツリーの持ち主は、flywheel の側の宣言で選ぶ（設計書 §21.3）。claude-harness は、いまも自分で作って片付けるので、契約に足すものは無い。
- 失敗した委譲の成果物を引き継いで続ける入力（claude-harness#383・flywheel#681）は、この節では決めない。
- 複数の課題を 1 回の依頼に束ねること。

### claude-harness の側で要るもの

いまの claude-harness（main c21a1fc）に無いもの。claude-harness の側の Issue にする。

| 口 | いま | 要るもの |
|---|---|---|
| 取り込み元の無い入力 | 無い（`ticket` の入力 `issue` が必須。ブランチの名前と作業ツリーの場所も Issue の番号から作る） | 文面のファイルとタスクの ID で始められる。名前と場所を、Issue の番号に頼らずに決める |
| 統合先を作る | 無い（統合ブランチが無いと、失敗 `base_missing` で止まる） | 「統合先を使う」と課題の識別を受けて、統合先を決め、無ければ作る。成果物に `role: integration` の要素を返す |

| `facts` | 一部ある（実装の段の出力に `self_review` があるが、契約の出力に出ない。指摘を受けて直す段では記録しない） | 契約の出力に `facts.self_review` を出す。直す段でも記録する |

### 未決（S3 の仕様で決める）

- `land` の後、委譲先が宛先へ入れるまでの間の、flywheel の側の記録（承認の記録に、元の中身と通した後の中身の両方を残す形）。
- 反映の操作を持たないリポジトリ（スキルを直接呼ぶ形・指示文を直接渡す形だけの宣言）の課題の扱い。宣言の検査で止めるか、反映を flywheel の外で行う課題として扱うか（オーケストレーターが直接作った成果物と同じ）。どちらでも、黙って待たせない。
- いまの flywheel の、レビュー待ちの読み方の決まり（検証中と完了の承認待ちの間は状態を読まない・直前と同じレビュー待ちは取り込み直さない。`docs/features/m3-invoker-delegation.md` の「後半の流れ」）と、足すもの 3 のやりとりの突き合わせ。

## やらないこと

- 右の対話の欄（オーケストレーターとの対話・「いま見ているもの」・「この課題について相談する」）（理由: S4 で作る。画面の中の対話の欄で承認を受ける形は、設計書 §9 の改訂と一緒に決める）
- 問いに、画面のボタンで答えること。計画の承認の画面で、推奨と違う答えを選んで計画を作り直すこと（理由: 画面のボタンで受ける範囲を広げる決定と一緒に、S4 で入れる。それまでは、端末か対話で行い、画面は、端末のコマンドの案内を出す）
- 取り込めるものを、画面で選んで取り込むこと。フォローアップを、画面で選んで済みにする・捨てること（理由: 同上。S4）
- 計画と完了の差し戻しを、画面で受けること（理由: `ux.md` の決定 26。対話か端末に寄せる）
- 完了の承認の画面を作り替えること（課題の単位の確かめの結果・反映するもの・フォローアップを 1 画面で見る形。試作の `web/w5-completion.html`）（理由: 反映を委譲先に任せる形と一緒に、S3 で作る。S2c は、見直し前の完了の承認の要約とボタンを、課題の詳細に置くだけ）

## 受入基準

S2c（画面）の受入基準。API の基準は、実ストアを使う Go のテストで確かめる。画面の基準は、特に断らない限り、偽の API（`fetch` と変化の合図の差し替え）を相手にした画面のテスト（Vitest）で確かめる。「ブラウザの試験」と書いた基準は Playwright で確かめる（「偽のデータ」は `make e2e`、「本物のサーバ」は `make e2e-real`）。状態と値は、コードでの名前で書く（計画承認待ち＝`awaiting_plan_approval`・着手中＝`in_progress`・完了確認待ち＝`awaiting_completion_approval`・人間対応待ち＝`awaiting_human`・完了＝`done`・取り下げ＝`withdrawn`。タスクの未着手＝`pending`・作業中＝`in_progress`・検証中＝`verifying`・済み＝`done`）。「エージェント」は、API のワークスペースを指す。「課題のツリーの API」は `GET /api/v1/workspaces/{name}/tree`、「課題の詳細の API」は `GET …/challenges/{id}`、「承認の要約の API」は `GET …/challenges/{id}/approval`、「状況の API」は `GET …/status`、「問いの一覧の API」は `GET /api/v1/questions`。

文言を「」で固定していない表示（「〜の旨が出る」「印が付く」）は、画面のテストが、要素の目印（`data-` の属性か、支援技術向けの名前）で確かめる。目印の名前は、実装が決める。ソースの中身と、ファイルの有無の基準は、画面のテスト（Vitest が、ファイルを読む）か、Go のテストで確かめる。

### 課題のツリーの API

- [ ] 課題のツリーの API は、HTTP の状態 200 で、根に `challenges` と `recent_done` の 2 つの配列を持つ本文を返す。
- [ ] 状態が `in_progress` の課題は、`challenges` に含まれる。
- [ ] 状態が `done` の課題は、`challenges` に含まれない。
- [ ] 状態が `withdrawn` の課題は、`challenges` に含まれない。
- [ ] 状態が `done` の課題は、`recent_done` に含まれる。
- [ ] 状態が `withdrawn` の課題は、`recent_done` に含まれない。
- [ ] 状態が `done` の課題が 11 件あるとき、`recent_done` は 10 件である。
- [ ] `recent_done` は、`updated_at` が新しい順に並ぶ。
- [ ] `updated_at` が同じ時刻の課題は、`recent_done` で、ID の大きい方が先に並ぶ。
- [ ] `challenges` は、課題の ID の小さい順に並ぶ。
- [ ] タスクが 3 件の計画を承認した課題の `tasks` は 3 件で、各要素の `id` は、そのタスクの ID である。
- [ ] タスクが 2 件の計画を持つ、計画承認待ちの課題の `tasks` は 2 件である。
- [ ] 計画承認待ちの課題の `tasks` の要素の `id` は null である。
- [ ] 計画承認待ちの課題の `tasks` の要素の `status` は null である。
- [ ] `tasks` の要素の `depends_on` は、前提のタスクの `key` の配列である。
- [ ] 計画を承認した後の課題でも、`tasks` の要素の `depends_on` は、前提のタスクの `key` である（タスクの ID ではない）。
- [ ] 計画が無い課題の `tasks` は、空の配列である。
- [ ] 最新の計画がタスクを持つ形でない（過去の形の）課題の `tasks` は、空の配列である。
- [ ] 作り直した計画を承認して、前の版のタスクが取りやめになった課題の `tasks` に、前の版のタスクは含まれない。
- [ ] 取り下げた課題の、課題の詳細の API の `tree.tasks` の、状態が `cancelled` のタスクの `phase` は `cancelled` である。
- [ ] 状態が `pending` で、前提のタスクが `cancelled` のタスクの `phase` は `blocked` である。
- [ ] 状態が `done` のタスクの `phase` は `done` である。
- [ ] 状態が `in_progress` のタスクの `phase` は `running` である。
- [ ] 状態が `verifying` のタスクの `phase` は `running` である。
- [ ] 状態が `in_progress` のタスクに、答えていない、オーナー宛ての保留があるとき、そのタスクの `phase` は `waiting` である。
- [ ] そのタスクの保留が答え済みのとき、`phase` は `waiting` でない。
- [ ] そのタスクの保留の種類が `parent_direct` のとき、`phase` は `waiting` でない。
- [ ] 状態が `pending` で、前提の無いタスクの `phase` は `next` である。
- [ ] 状態が `pending` で、前提のタスクが全部 `done` のタスクの `phase` は `next` である。
- [ ] 状態が `pending` で、`done` でない前提があるタスクの `phase` は `blocked` である。
- [ ] 計画承認待ちの課題の、前提の無いタスクの `phase` は `next` である。
- [ ] 計画承認待ちの課題の、前提のあるタスクの `phase` は `blocked` である。
- [ ] `tasks_total` は、`tasks` の件数と同じである。
- [ ] `tasks_done` は、`tasks` のうち `phase` が `done` の件数と同じである。
- [ ] 課題の `cost_usd` は、その課題の実行の記録（判断点の実行と、委譲の実行の両方）の費用の合計と同じである。
- [ ] 費用の記録が無い実行だけを持つ課題の `cost_usd` は 0 である。
- [ ] 前の版の計画のタスクに付いた実行の費用は、課題の `cost_usd` に含まれる。
- [ ] タスクの `cost_usd` は、そのタスクの実行の記録の費用の合計と同じである。
- [ ] `budget_usd` は、`flywheel show <課題の ID> --plan --json` の `plan.budget_usd` と同じ値である。
- [ ] 計画が無い課題の `budget_usd` は null である。

- [ ] 課題へ上げてあるフォローアップ（上げた先の課題が取り下げでない）は、`followups_open` に数えない。
- [ ] 前提の課題を記録した課題の `dependencies` に、前提の課題の `challenge_id` と `title` を持つ要素がある。
- [ ] 前提の課題が完了していないとき、その要素の `satisfied` は偽である。

- [ ] 親の課題が無い課題の `parent` は null である。

- [ ] ストアが無いワークスペースへの課題のツリーの API は、ほかの閲覧の API と同じエラー（`store_not_found`）を返す。
- [ ] 課題のツリーの API を呼んでも、作業ログの件数は変わらない。
