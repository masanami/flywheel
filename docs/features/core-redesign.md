# core の見直し（課題 ＞ タスク ＞ フォローアップ・サイクル・スーパーバイザー）

## 概要

2026-11-17 の設計の見直し（`docs/architecture.md` §21。決定 D22〜D34）を、core・CLI・画面に実装する。全体を区切り（スライス）に分け、この文書の受入基準は、いま実装する区切りの分だけを持つ。後の区切りは、その番が来たときにこの文書へ書き足す。

区切り S1（外す）は出荷済み（flywheel#732・PR #747）。区切り S2（土台）は大きいので、S2a（ストアと計画）・S2b（入口と出口）・S2c（画面）の 3 つに分けて順に入れる（オーナー 2026-11-18）。

いまの実装対象は S2a（ストアと計画）で、次を行う。

- 課題の下に、タスクとタスクの前提を持てるストアにする。
- 計画を作る判断点（J2）が、方針・論点と問い・タスクのツリーを 1 回で出す。計画の前に論点だけをオーナーへ問う段は外す。
- 計画の承認は課題ごとに 1 回にする。問いには推奨を選んでおき、推奨と違う答えが記録されたら計画を作り直す。
- 委譲と完了の検証の対象を、課題からタスクへ付け替える。

## 背景・目的

2026-11-01〜11-16 の 16 日間を測った結果（`docs/architecture.md` §21.0）、課題の時間の大半がオーナー待ちで、費用の約半分が判断点に出ていた。設計の見直しで、次を決めた。

- 課題の下にタスクのツリーとフォローアップを持ち、承認は課題ごとに 1 回にする（D22・D23）。
- 反映・統合先・作業ツリーは委譲先に任せる（D24・D25・D31〜D33）。
- サイクルは、走っているタスクを見ながら進める。想定外のことはスーパーバイザーが受ける（D26・D27）。
- 課題どうしを、同じ場所を触る見込みを理由には直列にしない（D29）。

S2a は、このうち D22 のタスクの層と、D23 の「論点と計画を同時に出す」「計画の承認は課題ごとに 1 回」を入れる。見直し前は、サイズが中以上の課題で、計画の前に論点だけを問う段（保留 → 回答 → 次のサイクルで計画）があり、計画の承認までにオーナーの番が 2 回あった。後の区切り（統合先・長く走るサイクル・スーパーバイザー）は、どれもタスクを単位にするので、タスクの層を先に入れる。

決定の正本は、flywheel#724・#725・#726 の「設計の見直しで決めたこと」の節と、`docs/architecture.md` §21、`docs/glossary.md`。この文書は、それらを写さずに参照する。

## ユーザーストーリー

オーナーとして、課題ごとに、方針・問いと推奨・タスクのツリーを 1 回で見て、推奨のままなら 1 回の承認で進め、推奨と違う答えを選んだときは、その答えで計画を作り直してもらいたい。

## 機能要件

S2a（ストアと計画）の要件。

### ストア

- [ ] スキーマの版を 26 にし、タスク（`task`）・タスクの前提（`task_dependency`）・計画の問いへの答え（`plan_answer`）の表を足す。表と列は「クリティカル設計決定」のとおり。
- [ ] 実行（`run`）・契約の実行（`contract_run`）・保留（`hold`）に、タスクへの参照（`task_id`）を足す。課題（`challenge`）に、統合先を使うかの記録（`uses_integration`）を足す。
- [ ] 過去の課題（完了・取り下げ）は、タスクが 0 個の課題として、そのまま読める。過去の行の `task_id` は埋めない。
- [ ] 書き出しと再構築（`flywheel export`・`flywheel import`）は、足した表と列を含めて往復する。

### 計画を作る判断点（J2）

- [ ] 判定（`verdict`）は、計画を立てられる（`plan`）・判断できない（`uncertain`）・オーケストレーターが直接行う（`parent_direct`）の 3 つにする。論点を先に問う判定（`issues`）は無くす。
- [ ] `plan` の出力の根は、方針（`summary`）・論点と問い（`topics`）・課題の完了条件（`done_criteria`）・完了したら見えるもの（`expected`）・やらないこと（`non_goals`）・図（`figure`）・課題の前提（`depends_on`）・タスク（`tasks`）・統合先を使うか（`uses_integration`）・サイズ（`size`）・予算の額（`budget_impl_usd`・`budget_review_usd`）・複数のリポジトリにまたがるか（`cross_repo`・`related_repos`）を持つ。`uncertain` は問い（`question`）を、`parent_direct` は問い（`question`）とオーケストレーターの完了条件（`done_criteria`）を使う（見直し前と同じ）。根の対象リポジトリ（`repo`）・操作（`operation`）・手順（`steps`）・論点（`issues`）・論点を不要とした根拠（`no_issues_needed`）は無くす。`uses_integration` は、`plan` では必須（欠けたら不正な出力。`cross_repo` と同じ扱い）。`cross_repo` と `related_repos` は、課題の全体について書く（どのタスクの対象リポジトリから見ても、それ以外に関係するリポジトリ）。委譲の判断者の決め方（`DecideDecider`）は、対象のタスクの `repo` と、この 2 つを使う。
- [ ] タスクは 1〜12 件。タスクごとに、計画の中の識別子（`key`）・題名（`title`）・何をするか（`body`）・完了条件（`done_criteria`）・やらないこと（`non_goals`）・前提のタスク（`depends_on`。`key` の配列）・対象リポジトリ（`repo`）・操作（`operation`）を持つ。見直し前に計画が 1 つずつ持っていた対象リポジトリと操作は、タスクごとに持つ（委譲は、対象のタスクの `repo`・`operation` を使う）。タスクが 1 件の計画では、課題の完了条件とタスクの完了条件が食い違わないように書かせる（指示文に書く）。
- [ ] 論点は 0〜5 件。論点ごとに、題名（`title`）・どう決めたか（`decision`）・問い（`questions`。0〜3 件）を持つ。問いは、問いの文・選択肢 2〜5 個（ラベルと、あれば例）・推奨（選択肢の位置を 1 から数えた番号）を持つ。問いには、論点の並びと問いの並びの順に、1 から番号を振る（`Q1`・`Q2`…）。
- [ ] 問いが 0 件の計画も受ける。サイズが中以上の計画に論点の記録を求める検査と、その問い直しは無くす。
- [ ] タスクが 2 件以上の計画は、統合先を使う（`uses_integration` が真）ものだけを受ける。タスクが 1 件の計画は、どちらでも受ける（タスクが 1 個でも、反映先へ一定の期間入れられないときは統合先を使う。設計書 §21.3）。S2a では、オーナーがこの値を承認のときに変える口は持たない。変えたいときは、計画の差し戻し（理由に書く）で作り直す。オーナーが承認のときに選ぶ口は、値が効く S3 で足す（設計書の「計画の判断点が案を出し、オーナーが決める」との差）。
- [ ] タスクの対象リポジトリと操作の検査は、見直し前に計画の対象リポジトリと操作へ掛けていた検査の全部（`findConnectorRepo` と `checkOperationLaunchable`。宣言にあるか・差し込みが決まった集合に収まるか・取り込み元の無い課題が、取り込み元の差し込み〔`{issue_number}`・`{issue_url}`・`{external_key}`〕を要する操作を選んでいないか）を、タスクごとに掛ける。取り込み元の有無は、S2a では課題の単位で見る（タスクが 2 件以上の計画でも同じ。S2a では実行しないので、差し込みは起きない）。子の Issue とタスクの対応と、それに合わせた検査は、S2b で決める。
- [ ] 問いを持つ計画を登録しても、保留は作らない。課題は計画の承認待ちになる。
- [ ] 計画の本文（`task_plan.body`）に、方針・サイズと予算の額・論点（題名・どう決めたか）・問い（番号・文・選択肢・推奨）・タスクのツリー（題名・前提・対象リポジトリ・操作）・統合先を使うかを書く。
- [ ] タスクの行は、計画を登録した時点では作らず、計画の承認で作る。
- [ ] サイズが中以上で「完了したら見えるもの」が空の計画を保留にする決まりは、変えない。予算の額の検査も変えない（予算は課題の単位のまま。タスクごとの配分は S3）。

### 問いへの回答と、計画の作り直し

- [ ] 計画の承認待ちの課題の問いへ、`flywheel answer <課題の ID> --choice <問いの番号>=<選択肢の番号>`、または `--text <問いの番号>=<文>`（選択肢に無い答え）で答えられる。`--choice` と `--text` は、1 回のコマンドに複数並べられる（どちらも繰り返せる）。同じ問いの番号を 1 回のコマンドで 2 度指定することはできない。
- [ ] 答えは `plan_answer` に、計画の版・問いの番号・選んだ選択肢（か文）・推奨と同じか・答えた人と経路（本人確認の方式・対話で受けたときは会話の識別と発言の要旨）とともに記録する。
- [ ] 推奨と違う選択肢、または文の答えが 1 件でも記録されたら、課題を分類済へ戻す（遷移 T19 を足す）。次の計画の段で、計画を作る判断点（J2）が、問いと答えを入力に計画を作り直し、課題は新しい版の計画で、計画の承認待ちに戻る。
- [ ] 推奨と同じ選択肢だけを答えたときは、記録だけを行い、課題の状態は変えない（課題の版は 1 つ上げる）。
- [ ] 本人確認の扱いは、保留への回答（`flywheel answer --answer`）と同じにする（端末での本人確認か、`--relayed` の記録）。本人確認の登録簿（`internal/core/verification.go`）に、操作の種類 `answer_plan` を足し、分類済へ戻る答えも、記録だけの答えも、書き込みの前にこの種類で登録簿に照らす。画面の経路（本人確認なし）は、この種類を受けない。
- [ ] 問いへの答えは、作業ログに、課題の記録（`entity = challenge`・`action = answer_plan`）として残す。`after` に、課題の版と、答えた問いの番号と答え（`answers`）を載せ、分類済へ戻るときは状態も載せる。
- [ ] 計画を作る判断点（J2）の入力に、区画「問いと回答」を足す。これまでの版の計画の問いと、記録された答えを渡す。見直し前の区画「論点と回答」は無くす。

### 計画の承認

- [ ] 計画を承認すると、承認した版の計画の問いのうち、答えが記録されていないものに、推奨の選択肢を答えとして記録する。
- [ ] 計画を承認すると、承認した版の計画のタスクから、タスクの行と前提の行を作る。作ったタスクの状態は、未着手（`pending`）。
- [ ] 計画を承認すると、統合先を使うか（`uses_integration`）を課題に記録する。
- [ ] 計画を承認するたびに、同じ課題の、ほかの版の計画のタスクのうち、済み（`done`）でも取りやめ（`cancelled`）でもないものを、取りやめにする（着手の後に計画を作り直して承認し直したときに当たる。経路では分けない）。
- [ ] 構造化した出力を持たない計画（人が登録した計画）と、タスクを持たない過去の形の計画の承認は、タスクの行を作らずに成功する。
- [ ] 承認の経路（端末・対話で受けた承認の記録・画面のボタン）と本人確認の決まりは変えない。画面のボタンでの計画の承認は、問いをすべて推奨のままにした承認になる。
- [ ] 完了を承認して課題が完了になるとき、済みでも取りやめでもないタスクが残っていれば、取りやめにする（オーケストレーターが直接行った完了を承認したときに当たる）。
- [ ] タスクの作成と状態の変化は、作業ログに、タスクの記録（`entity = task`・`entity_id` は `T-<番号>`・`action` は `create` か `task_status`）として、原因の操作と同じトランザクションで残す。`after` には状態（`status`）を載せ、版（`version`）は載せない（タスクは版を持たない）。`flywheel log <課題の ID>` は、その課題のタスクの記録も含める（不可逆操作の記録と同じ扱い）。

### 委譲と完了の検証

- [ ] 委譲の段は、着手中の課題の、起動できるタスクを対象にする。起動できるタスクは、課題のタスクの行（`task`）のうち、状態が未着手（`pending`）か作業中（`in_progress`）のもの（計画の構造化した出力ではなく、行で数える）。判定は次の順に行う。見直し前からある除外（取り込み元が閉じた・無い・方針の外）と、①と、記録した課題の前提の判定は、見直し前の順のまま先に行い、その後に②③④を行う。①承認済みの計画が引けない、または構造化した出力を持たない → 見直し前と同じ（ID を省いた委譲の段は理由 `plan_unavailable`、`flywheel run <課題の ID>` は `validation_failed` のエラー）。②起動できるタスクが 0 個 → 起動せず、理由 `no_tasks`（過去の形の課題が着手中へ戻ったとき。計画の検査は掛けない）。③課題が統合先を使う（`challenge.uses_integration` が 1）、または起動できるタスクが 2 個以上 → 起動せず、理由 `integration_unavailable`（統合先と、複数のタスクの実行は S3 で入れる。タスクが 2 件以上の計画は必ず統合先を使うので、複数のタスクの課題はここで止まる）。④起動できるタスクがちょうど 1 個 → 見直し前と同じ計画の検査（`validateJ2Output`。落ちたときは見直し前と同じで、ID を省いた委譲の段は `plan_unavailable`、`flywheel run <課題の ID>` は `validation_failed`）と、予算・スロット・同時に走らせる数の判定へ進む。②と③は、`flywheel run <課題の ID>` でも、起動しなかった理由として返す（記録した前提が終わっていないときと同じ形）。
- [ ] 委譲に使う対象リポジトリと操作は、タスクのものを使う。
- [ ] 委譲の実行（`run`・`contract_run`）、委譲の指示文の判断点（J3）の実行、完了の検証の判断点（J5）の実行、それらから作る保留（`hold`）に、タスクの ID を記録する。
- [ ] 委譲の指示文の判断点（J3）と完了の検証の判断点（J5）の入力に、区画「タスク」（題名・何をするか・完了条件・やらないこと）を足す。
- [ ] タスクの状態は、未着手（`pending`）・作業中（`in_progress`）・検証中（`verifying`）・済み（`done`）・取りやめ（`cancelled`）の 5 つ。課題の遷移に合わせて core が進める（委譲の起動で、未着手なら作業中。検証へ出したら検証中。検証が「満たした」で、課題が完了の承認待ちへ進んだときに済み〔「満たした」でも課題が保留へ回るときは、検証中のまま〕。検証が「満たさない」のときは、検証中だったタスクを作業中。完了の差し戻しで着手中へ戻るときと、反映のやり直しで着手中へ戻るときは、承認済みの計画の版のタスクのうち、済みのものだけを作業中〔前の版の計画の済みのタスクは、済みのまま〕。取り下げと、完了の承認で課題が完了になるときに、済みでも取りやめでもないものを取りやめ）。すでに作業中のタスクの再開・やり直しでは、状態を変えない。
- [ ] 上に挙げていない遷移（保留・保留への回答・計画の差し戻し・問いへの答えで分類済へ戻る・オーケストレーターの直接の完了の記録・その完了を差し戻して保留へ戻る）では、タスクの状態を変えない。計画を作り直すために分類済へ戻った課題のタスクは、次の計画の承認まで、そのままの状態で残る。オーケストレーターの直接の完了が差し戻され、保留への回答で着手中へ戻った課題は、残っているタスクの委譲を続けられる。
- [ ] 委譲の指示文の判断点（J3）の対象のタスクは、起動する 1 個のタスク。完了の検証の判断点（J5）の対象のタスクは、課題のタスクのうち状態が検証中（`verifying`）のもので、ちょうど 1 個のときだけ、`task_id` の記録と区画「タスク」を入れる（それ以外は、`task_id` は NULL で、区画は入れない）。
- [ ] 完了の検証の判断点（J5）は、区画「タスク」があるとき、見直し前の完了条件（課題の完了条件。空なら計画の根の完了条件）と、タスクの完了条件の両方を満たしたときに「満たした」とする（指示文 `j5.md` に書く）。
- [ ] 課題の状態と、いまある遷移（T1〜T18）は変えない（足すのは T19 だけ）。タスクが 1 個の課題では、タスクの検証がそのまま課題の検証になる。
- [ ] 手で課題を進める口も、同じ結果にする（判断点を通らないときに、課題とタスクの状態が食い違って委譲が止まらないようにするため。全体の確かめで足した）。`flywheel submit`（着手中 → 検証中）は、起動できるタスク（`pending`・`in_progress`）がちょうど 1 個のときだけ、そのタスクを検証中にする。`flywheel verify --result` は、検証中のタスクがちょうど 1 個のときだけ、完了の検証の判断点（J5）と同じにする（`met` は済み、`not_met` は作業中、`uncertain` は検証中のままで、作る保留へタスクの ID を記録する）。それ以外（0 個・2 個以上）では、タスクの状態を変えず、保留もタスクに結び付けない。
- [ ] 契約の形（`form: cli`）の委譲は、コマンド 1 回ごとの実行（`run`。`kind = contract`）にも、タスクの ID と、タスクの対象リポジトリ（`repo`）を記録する（開始は起動するタスク、その後の読み直し・再開・中止は、契約の実行〔`contract_run`〕が結び付くタスク。全体の確かめで足した）。

### 表示

- [ ] `flywheel show <課題の ID> --json` と、課題の詳細の API に、タスクの一覧（`tasks`）を足す。実行と保留の要素に、タスクの ID（`task_id`）を足す。
- [ ] `flywheel show <課題の ID> --plan` を足し、最新の計画の方針・完了したら見えるもの・やらないこと・問いと推奨（答えがあれば答え）・タスクのツリー・予算の上限・統合先を使うかを、文で出す。
- [ ] 承認の要約（端末の `flywheel approve` の確認の文と、API の `GET …/challenges/{id}/approval`）に、計画の論点と問い・タスク・統合先を使うかを足す。
- [ ] 画面（Web）は、型の生成し直しと、いまの画面が動くままにする追従だけを行う。新しい画面は S2c で作る。

### 外すもの

- [ ] 論点を先に問う段（判定 `issues`・論点の保留・区画「論点と回答」）、論点を不要とした根拠（`no_issues_needed`）、サイズが中以上で論点の記録が無い計画の問い直しを外す。
- [ ] `flywheel edit --issues` を外す。

## 技術的な制約・方針

- 使用技術: 既存のまま（Go・SQLite・React）。本番の依存は増やさない。
- 変更対象（S2a）:
  - `internal/core/internal/store`（マイグレーション `0026`）、`internal/core/coretest`（全表を埋めるテストの支え）、`internal/core/export_test.go` の表の一覧。

- 既存コードとの関係:
  - 承認済みの計画の構造化した出力（`task_plan.spec`）は、委譲のたびに計画の検査（`validateJ2Output`）へ掛け直している。新しい形の検査は、起動できるタスクがちょうど 1 個の課題だけに掛かる（判定の順は、機能要件の「委譲と完了の検証」）。過去の形の計画（タスクを持たない）の課題は、起動できるタスクが 0 個なので、検査の前に `no_tasks` で外れる。
  - 委譲の履歴・再開・やり直しの数え・連続失敗の数え・予算の枠・照合のやり直しは、課題と計画の版の単位で引いている（`loadLaunchHistory`・`loadBucketSpend`・`decideRework`・`challenge.reconcile_fetch_*` の列）。S2a では、この引き方を変えない（タスクが 1 個の間は、同じ結果になる）。タスクの単位に分けるのは、複数のタスクを走らせる S3。
  - 「終わっていない実行は課題ごとに 1 本」の一意の制約（`idx_run_active_challenge`・`idx_contract_run_active_challenge`）も、S2a では変えない。この制約は、判断点の実行どうしの排他にも効いており、タスクの単位に改めるには、課題の単位の排他を別の形で残す必要がある。複数のタスクを同時に走らせる S3 で、その形と一緒に改める。
  - 人が登録した計画（`flywheel plan --file`・`--stdin`。構造化した出力を持たない）の課題は、いまと同じ扱いのまま（ID を省いた委譲の段は理由 `plan_unavailable`、`flywheel run <課題の ID>` は `validation_failed`）。この判定は、タスクの数の判定より先に行う。
  - タスクの行は、計画の版（`plan_version`）と計画の中の識別子（`key`）を「作った出どころ」として持つ。どのタスクを起動・検証するかは、版ではなく、タスクの状態で決める。計画の承認を通らずに足すタスク（S2b のフォローアップを上げたタスク・S4 の計画の後に足すタスク）は、`key` を持たないタスクとして、同じ表に足せる（`plan_version` には、足した時点の承認済みの計画の版を入れる）。派生元の参照の列は、それを使う S2b で足す（列の追加で、表の作り直しにはならない）。
  - 着手の後に計画を作り直したとき、新しい版の計画のタスクは、前の版の済みのタスクを前提に指せない（`depends_on` は、同じ計画の中の `key` だけ）。済んだ作業を踏まえた作り直しは、計画を作る判断点（J2）の入力（前の計画の本文と、区画「計画の作り直し」）で伝える。前の版の済みのタスクをツリーにつなぐ形は、複数のタスクを走らせる S3 で決める。
  - 計画の作り直しは、差し戻し（T6）と同じく、課題を分類済へ戻して、次の計画の段に作らせる。計画を作る判断点（J2）の対象の決め方（分類済だけ）は変えない。
  - 指示文 `j2.md` の分量の上限（12,288 バイト）は、変えないことを目指す。収まらないときに限り 16,384 バイトまで上げてよく、上げたときは PR の説明に理由を書く。全体の確かめで 12,482 バイトへ上げた（「読むもの」に区画「問いと回答」の説明の 194 バイトを足すと、上限より 300 バイト以上小さく保つ検査に当たるため、足した分だけ上げた）。
  - スキーマの版の数字だけを書いているテスト（約 20 ファイル）は、最新の版を返す 1 つの定義を見る形に改める（S2b でも版を上げるため）。
  - 受入基準・決定を変える必要に気付いたら、変えずに PR の説明へ「仕様への指摘」として書く（`CLAUDE.md`）。
- 既定ブランチが一時的に動かなくなることを許す（オーナー 2026-11-17）。S2a を main に入れた時点では、統合先を使わない、タスクが 1 個の課題は最後まで進み、統合先を使う課題（タスクが 2 個以上の課題を含む）は、計画・承認・表示までで止まる。サイクルは、core の改修が終わるまで凍結している（オーナー 2026-11-17）ので、止まった課題が運用に残ることは無い。
- Tom のワークスペースのバイナリとストアの切り替えは、S2a・S2b・S2c が全部入ってから 1 回行う（オーナー 2026-11-18）。main へ入れる前に、Tom のストアの写しで新しいバイナリを試す。

## クリティカル設計決定

### DB スキーマ: 衝突の記録の表（S1）

- **採用案**: マイグレーションを 1 本足し、`challenge_conflict` の表と、その索引を消す（スキーマの版は 25 になる）。過去の衝突の記録は消える。
- **理由**: この表を読むのは、直列化グループと、グラフの衝突の線・「待っている理由」の衝突の欄（`graph.go`・`waiting.go`）だけで、どれも外す。過去の記録を読む用途が無い。残すと、全表を埋めるテストの支え（`coretest.FillAllTables`）と書き出しの検査に、使わない表の追従が残り続ける（オーナー 2026-11-17）。
- **代替案**: 表を残し、書き込みと読み取りだけをやめる。却下の理由は上のとおり。
- **影響範囲**: `internal/core/internal/store/migrations`、`internal/core/conflict.go`・`graph.go`・`waiting.go`・`delegate_plan.go`、`coretest.FillAllTables`、`internal/core/export_test.go` の表の一覧、スキーマの版を直に書いているテスト、表を直に読み書きしているテスト（`internal/server/graph_test.go`・`internal/core/graph_test.go`。`internal/core/internal/store/migrate_0018_test.go` は最新まで当てた後で表を読むので、当てる版を 18 までに絞る）。書き出しと再構築（`Export`・`Import`）は表を列挙する作りなので、コードの変更は要らない。版 24 の書き出しは、版 25 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### DB スキーマ: 過去の実行の記録（S1）

- **採用案**: `run.kind = 'predict'` と `run.judgment = 'J9'` を、読み取りで受け付ける値として残す。予測の run が持つ予算の枠の値（`run.budget_bucket = 'predict'`）も同じく残す。新しく作る経路は無くす。すでにある行を終わらせる更新（終わっていない run を、サイクルの後片付けが「中断」にする）は受け付けるままにする。
- **理由**: 2026-11-01〜11-16 に、予測の run が 58 本、J9 の run が 105 本ある。費用の集計と `flywheel runs` の表示の根拠を消さない（オーナー 2026-11-17）。
- **代替案**: 過去の行を消す、または別の値へ書き換える。費用の記録が失われるので採らない。
- **影響範囲**: `internal/core/run_store.go` の値の検査（読み取りと書き込みで受け付ける値を分ける）、`view` の run の表示。

### 宣言の互換: 無くした項目（S1）

- **採用案**: 無くした項目が残っている宣言は、設定の誤り（`config_invalid`）として止める。エラーの文に、項目の名前と、無くなった旨（決まった語 `removed`）を出す。知らないキーを拒む既存のエラーの文（`unknown key`）とは別の文にする。
- **理由**: 宣言は、知らないキーを拒む閉じた集合として検査している。黙って無視すると、設定が効いていると思い込んだまま動かすことになる（オーナー 2026-11-17）。
- **代替案**: 黙って無視して動かす。上の理由で採らない。
- **影響範囲**: `internal/core/connectors_declaration.go`・`internal/core/agent_declaration.go`。Tom のワークスペースの宣言の直しが、S1 を main に入れるときに要る。

### DB スキーマ: 課題 ＞ タスク ＞ フォローアップの持ち方（S2 で適用）

- **採用案**: いまの課題（`challenge`）を「課題」のまま残し、その下にタスク・タスクの前提・フォローアップの表を足す。委譲と完了の検証を、課題からタスクへ付け替える（`run`・`contract_run`・`hold` にタスクへの参照を足す）。計画・承認・反映は、課題の単位のまま残す。
- **理由**: 「承認の真正性」と「完了と反映を 1 回の操作で承認する」（D12）は変えないと決めている（§21.8）。この案は、承認と反映の処理に手を入れずに済む。過去の完了・取り下げの課題は、タスクが 0 個の課題としてそのまま読める。設計書と用語集も、課題を「いまの課題のまま」としている（§21.1）。
- **代替案**: いまの課題をタスクとして読み替え、その上に課題の表を足す。委譲と検証はそのまま使えるが、計画・承認・反映の処理を課題の単位へ上げ直すことになり、識別子の意味が用語集とずれる。
- **影響範囲**: 表と列は、使う区切りで足す。S2a の分は次の節。フォローアップの表と、取り込み元の子の Issue をタスクに対応づける持ち方（`source_binding`）は、それを使う S2b で、この節に書き足す。進行中の課題を新しい形へ移す処理は作らない（開いている課題は 0 件）。

### DB スキーマ: タスク・タスクの前提・計画の問いへの答え（S2a）

- **採用案**: マイグレーションを 1 本足す（スキーマの版は 26 になる）。中身は次のとおり。
  - タスクの表 `task`: `id`（主キー。表示は `T-<番号>`）・`challenge_id`（課題への参照。必須）・`plan_version`（このタスクを作った計画の版。必須）・`key`（計画の中の識別子。計画から作ったタスクだけが持つ。NULL を許す）・`title`・`body`・`done_criteria`（どれも必須）・`non_goals`（JSON の配列。無ければ NULL）・`repo`・`operation`（必須）・`status`（必須。`pending`・`in_progress`・`verifying`・`done`・`cancelled`）・`created_at`・`updated_at`。同じ課題・同じ計画の版の中で、`key` は重ならない（一意の制約。`key` が NULL の行どうしは重なりと見ない）。
  - タスクの前提の表 `task_dependency`: `task_id`・`depends_on_id`（どちらもタスクへの参照。2 つの組が主キー）。
  - 計画の問いへの答えの表 `plan_answer`: `id`（主キー）・`challenge_id`（必須）・`plan_version`（必須）・`question_number`（必須。1 から）・`choice`（選んだ選択肢の番号。文の答えのときは NULL）・`text`（文の答え。選択肢の答えのときは NULL）・`recommended`（推奨と同じ答えなら 1）・`actor`・`channel`・`verification`（承認の記録と同じ意味の 3 つ）・`relay_session`・`relay_quote`（対話で受けたときだけ）・`answered_at`。別々のコマンドで同じ問いに答えが複数記録されたときは、後の行を使う（1 回のコマンドで同じ問いを 2 度は指定できない）。
  - 列の追加: `run.task_id`・`contract_run.task_id`・`hold.task_id`（タスクへの参照。NULL を許す）、`challenge.uses_integration`（1・0・NULL。NULL は、まだ決めていないか、過去の課題）。
  - 過去の行は書き換えない（`task_id` は NULL のまま）。索引と一意の制約は、足す表の分だけを作り、既存のものは変えない。
- **理由**:
  - タスクの行を計画の承認で作る形にすると、承認の前に計画を何度作り直しても、タスクの行の入れ替えが起きない。承認の前のツリーは、計画の構造化した出力（`task_plan.spec`）から読む。
  - 問いへの答えを、保留（`hold`）ではなく別の表に持つのは、答えが課題を止めないことと、問いごと（番号ごと）に「推奨と同じか」を機械的に判定するため。見直し前の論点への回答は、保留の 1 つの文で、問いごとの構造を持たなかった。
  - `task_id` に NULL を許すのは、課題の単位の実行（分類・計画・学び・改修提案の判断点）と過去の行があるため。SQLite は、既存の表へ、既定値の無い必須の列を足せない。
- **代替案**:
  - タスクの行を計画の登録で作り、作り直しのたびに入れ替える。承認の前のタスクに実行は付かないが、行の入れ替えと、古い版のタスクの扱いが増えるので採らない。
  - 問いへの答えを、承認の記録（`approval`）の 1 つの列に JSON で持つ。推奨と違う答えは、承認より前に記録する必要があり（承認されない版にも答えが付く）、承認の行に載せられないので採らない。
  - 既存の課題すべてに、タスクを 1 個ずつ作って埋める。過去の課題（450 件）に、計画に無いタスクを作ることになり、読むだけの用途に要らないので採らない。
- **影響範囲**: `internal/core/internal/store/migrations`、全表を埋めるテストの支え（`coretest.FillAllTables`）、`internal/core/export_test.go` の表の一覧、スキーマの版を直に書いているテスト。書き出しと再構築（`Export`・`Import`）は表と列を実行時に列挙する作りなので、コードの変更は要らない。版 25 の書き出しは、版 26 のバイナリでは再構築できない（版の一致を求める既存の作りのまま）。

### 承認の真正性: 問いへの答えの記録と、計画の作り直し（S2a）

- **採用案**: 計画の問いへの答えは、保留への回答と同じ本人確認（端末での本人確認か、対話で受けたことの記録〔`--relayed`〕）を通して記録する。本人確認の登録簿に、操作の種類 `answer_plan` を足す（端末の本人確認と、対話で受けた記録の組は受ける。画面・本人確認なしの組は受けない）。推奨と違う答え（か文の答え）が 1 件でも記録されたら、課題を計画の承認待ちから分類済へ戻す遷移（T19。操作の名前は `answer_plan`）を足し、次の計画の段に計画を作り直させる。計画の承認（T5）は、答えが記録されていない問いに、推奨の選択肢を、その承認と同じ人・経路・本人確認で記録する。
- **理由**: 計画の承認が「何を承認したか」は、計画の版と、問いごとの答えで決まる。答えを本人確認つきで記録し、推奨と違う答えの後は必ず新しい版の承認を通すことで、承認された計画と、オーナーの答えが食い違わない。差し戻し（T6）と同じ「分類済へ戻して作り直す」経路に乗せると、計画を作る判断点（J2）の対象の決め方と、計画の版の扱いを変えずに済む。
- **代替案**: 課題を計画の承認待ちのまま、作り直しの印だけを付ける。古い版の計画を承認できてしまう時間ができ、それを防ぐ検査が要るので採らない。
- **影響範囲**: `internal/core/transition.go`（遷移表）、`internal/core/verification.go`（登録簿と、遷移から操作の種類を引く対応）、`internal/core/approval.go`、`internal/cli/approval.go`・`commands.go`、`docs/features/m1-core.md` の遷移表と作業ログの一覧。画面のボタンで問いに答える口は、画面のボタンで受ける範囲を広げる決定（設計書 §9 の改訂。`ux.md` の未決は、S4 のクリティカル設計で決め、それまでは §9 の範囲で作るとしている）と一緒に入れる。入れるときは、この記録の口と、登録簿の `answer_plan` を通す。画面のボタンで受ける範囲と本人確認の決まり（設計書 §9）は、S2a では変えない。

### 一意の制約をタスクの単位に改める時期（S2a で決め直した）

- **採用案**: 「終わっていない実行は課題ごとに 1 本」の一意の制約は、S2a では変えず、複数のタスクを同時に走らせる S3 で改める。
- **理由**: この制約は、委譲の実行だけでなく、判断点の実行どうしの排他にも効いている。タスクの単位に改めると、課題の単位の排他が外れるので、別の形で残す設計が要る。S2a で起動するのはタスクが 1 個の課題だけで、いまの制約のままで足りる。S1 の時点のこの文書は「S2 で改める」としていたが、コードを調べたうえで時期を改めた（2026-11-18）。
- **代替案**: S2a で改める。動きを確かめられる場面（同じ課題の 2 つのタスクの同時の実行）が S3 まで無く、確かめられない変更を先に入れることになるので採らない。
- **影響範囲**: S3 の仕様で、`idx_run_active_challenge`・`idx_contract_run_active_challenge` の作り替えと、課題の単位の排他の残し方を決める。

## 機能全体の設計

### アーキテクチャ決定

- 区切りの順は、外す → 土台 → 委譲先との境界 → 長く走るサイクルとスーパーバイザー → 仕上げ、とする。先に外すのは、ストアの形を変えるときに運ぶコードを減らすため。土台を次に置くのは、後の区切りがどれも「タスク」を単位にするため。
- 土台（S2）は、ストアと計画（S2a）→ 入口と出口（S2b）→ 画面（S2c）の順に分けて入れる。S2b と S2c は S2a のストアを使い、S2c は S2b の API を使う。1 回に入れる量を、全体を確かめられる大きさ（S1 は 135 ファイル・受入基準 68 件）に近づけるために分ける。
- サイクルの構造は、flywheel に決まった形として持つ。YAML の定義から描いて調整できるようにするのは、この機能の範囲外（flywheel#265・#266）。
- claude-harness 側の受け口（Issue の無い入力・統合ブランチを作る口・承認した中身つきで既定ブランチへ入れる口・統合ブランチから上げるフロー・任意の成果物を上げる口・取り込んで新しい中身を返して待つ口・自己レビューの値の返却）は、別のリポジトリなので、この文書に契約（flywheel が渡すもの・受け取るもの）を書き、実装は claude-harness 側の Issue にする。契約は、S3 を待たず、S2a の実装と並行して先に書く（S3 の出荷条件が claude-harness 側の出荷なので、先に始める）。契約の既存の値の意味は変えない（レビュー待ちへの答え `ready` は「flywheel が反映まで済ませた」の意味のまま残し、新しい意味には新しい値を足す）。
- S1 で委譲の計画の処理（`planDelegation`・`executePlan`）を単純にするとき、S2 でタスクの単位に付け替えることを見越して、候補 1 件を 1 つの単位として扱う形にとどめる（タスクの概念は S1 に持ち込まない）。

### 実装計画（チケット分解の見通し）

S2a の分け方の案（最終の分解は `/create-ticket` で行う）。

1. store と core の土台: スキーマの版 26（タスク・タスクの前提・計画の問いへの答えの表、`task_id` と `uses_integration` の列）。タスクを読み書きする core の口。書き出しと再構築・全表を埋めるテストの支えの追従。版の数字だけを書いているテストを、最新の版の定義を見る形に改める。
2. 計画を作る判断点（J2）の出力の形: タスク・論点と問い・統合先を使うか。出力の検査と計画の本文。指示文 `j2.md`。論点を先に問う段・問い直し・論点を不要とした根拠・`flywheel edit --issues` を外す。
3. 問いへの回答と計画の承認: `flywheel answer --choice`・`--text`、遷移 T19 と本人確認の登録簿、作業ログの記録、計画を作る判断点（J2）の入力の区画「問いと回答」。承認で、推奨の答えを記録し、タスクの行を作り、統合先を使うかを記録する。作り直しの後の承認で、前の版のタスクを取りやめにする。
4. 委譲をタスクの単位にする: 対象の決め方（`integration_unavailable`・`no_tasks`）、タスクの対象リポジトリと操作、`task_id` の記録、タスクの状態、委譲の指示文の判断点（J3）の区画「タスク」。
5. 完了の検証をタスクの単位にする: 完了の検証の判断点（J5）の `task_id` と区画「タスク」、検証の結果とタスクの状態。完了の差し戻し・取り下げ・完了の承認・反映のやり直しでのタスクの状態。
6. 表示: `flywheel show`（`--json`・`--plan`・文の出力）、承認の要約（端末と API）、型の生成し直しと、画面の追従。
7. 文書: 外した段の仕様の節の注記、遷移表、用語集、設計書の注記。

1 を最初に行う。2 は 1 の後、3 と 4 は 2 の後なら並行にできる（3 は承認と計画、4 は委譲のファイルに触れる。4 のテストは、タスクの行を 1 の core の口で直に作る。承認から委譲までの通しの確かめは、3 と 4 の両方が入った後に行う）。5 は 4 の後、6 は 3 と 5 の後、7 はいつでもよい。

費用の見込み（実装の分。区切り S1 の実績は 6 件で約 44 USD・1 件 2.9〜8.4 USD で、削除が中心だった。新しい処理とテストを書く S2a は、1 件あたり 2〜3 倍と置く）: 2 と 3 が各 15〜25 USD、4 が 10〜20 USD、1・5・6 が各 8〜15 USD、7 が 3〜6 USD。合計は約 70〜130 USD（3 に、本人確認の登録簿と作業ログの記録が入る分を見込む）。全体の確かめ（セルフレビュー・Codex レビュー・受入基準の突き合わせ）は、対話のセッションの中で行うので、金額の記録が無い。

## やらないこと

- 統合先を使う課題（タスクが 2 個以上の課題を含む）のタスクを実行すること（理由: 後のタスクは、前のタスクの成果が統合先に入ってから始める。統合先は S3 で入れる。S2a では、計画・承認・表示までを行う）
- 計画の承認の後に、計画を作る判断点（J2）がタスクを足すこと（理由: 設計の後に実装のタスクを確定する流れは、走っているタスクを見ながら進めるサイクルと一緒に S4 で入れる）
- 統合先を使うかを、オーナーが承認のときに変える口（理由: 値が効くのは統合先を入れる S3 から。S2a では、計画を作る判断点の案をそのまま記録する）
- 新しい画面（理由: S2c で作る。S2a の画面は、いまの形が動くままにする追従だけ）
- 画面のボタンで問いに答えること（理由: 画面のボタンで受ける範囲を広げる決定〔設計書 §9 の改訂〕と一緒に、S4 で入れる。それまでは、端末か対話で答える）
- 承認と回答が、サイクルを始めること（理由: S4 で入れる。S2a では記録までを行い、続きはオーナーが始めた次のサイクルで進む）
- フォローアップ・取り込みをオーナーが選ぶ形・`flywheel status` の改め（理由: S2b で扱う）
- 委譲の履歴・再開・やり直しの数え・予算の枠を、タスクの単位に分けること（理由: タスクが 1 個の間は、課題の単位と同じ結果になる。複数のタスクを走らせる S3 で分ける）
- 過去の課題の論点の記録（`challenge.issues`・`issues_hold_id`）の列を消すこと（理由: 過去の課題の表示に使う。消す用途が出たら、そのとき決める）
- サイクルの構造を YAML で定義・調整すること（理由: flywheel#265・#266 で、Tom で安定を見た後に検討する）
- 自分から見回って通知すること（理由: flywheel#585 で後に扱う）
- エージェントを足す流れ（理由: flywheel#535 で扱う）
- ミッション（ゴール）から課題の案を出すこと（理由: 先の要望で、時期と形を決めていない）
- 進行中の課題を新しい形へ移す処理（理由: 開いている課題は 0 件で、過去の課題は読めれば足りる）
- 承認の単位を「タスクごと」にする設定（理由: 必須ではなく、要るときに足す）
- ボード（列にカードを並べる表示）の作り直し（理由: ほとんど使わない。`ux.md` の決定 2）
- スキルを直接呼ぶ形・指示文を直接渡す形の委譲で、委譲の指示文の判断点（J3）を外すこと（理由: D28 は、委譲先のフローを通る委譲で外すと決めており、その委譲ではすでに呼ばれていない）
- claude-harness の側の実装と、その契約をこの文書に書く作業（理由: 実装は別のリポジトリ。契約は S2a の実装と並行して書くが、S2a の実装の課題と受入基準には含めない）
- Tom のワークスペースの切り替え（理由: ワークスペースの側の作業で、S2c までが main に入った後に、オーケストレーターが行う）

## 受入基準

S2a（ストアと計画）の受入基準。状態と値は、コードでの名前で書く（計画の承認待ち＝`awaiting_plan_approval`・分類済＝`classified`・着手中＝`in_progress`・検証中＝`verifying`）。「計画の段」は `flywheel plan --auto`、「委譲の段」は `flywheel run`、「完了の検証」は `flywheel verify --auto` と、サイクルの中の同じ段を指す。

### ストア

- [ ] 新しく作ったストアのスキーマの版は 26 である。
- [ ] スキーマの版 25 のストアを開くと、版 26 になる。
- [ ] スキーマの版 25 のストアを開いた前後で、`challenge` の表の行数が変わらない。
- [ ] スキーマの版 25 のストアを開いた前後で、`run` の表の行数が変わらない。
- [ ] スキーマの版 25 のストアを開いた後、もとからあった `run` の行の `task_id` は NULL である。
- [ ] 新しく作ったストアに、`task` の表がある。
- [ ] 新しく作ったストアに、`task_dependency` の表がある。
- [ ] 新しく作ったストアに、`plan_answer` の表がある。
- [ ] 同じ課題・同じ計画の版で、`key` が同じ `task` の行を 2 つは作れない。
- [ ] `task` に行があるストアを `flywheel export` で書き出し、その書き出しから再構築すると、その行が再構築したストアにある。
- [ ] `task_dependency` に行があるストアを `flywheel export` で書き出し、その書き出しから再構築すると、その行が再構築したストアにある。
- [ ] `plan_answer` に行があるストアを `flywheel export` で書き出し、その書き出しから再構築すると、その行が再構築したストアにある。
- [ ] タスクが 0 個の完了の課題で、`flywheel show <課題の ID> --json` が終了コード 0 で終わる。

### 計画を作る判断点（J2）の出力

- [ ] 計画を作る判断点（J2）へ渡す出力の型（`--json-schema`）の `verdict` の値の集合は、`plan`・`uncertain`・`parent_direct` の 3 つである。
- [ ] 計画を作る判断点（J2）へ渡す出力の型に、`no_issues_needed` のキーが無い。
- [ ] 計画を作る判断点（J2）へ渡す出力の型に、`steps` のキーが無い。
- [ ] 計画を作る判断点（J2）へ渡す出力の型の根に、`repo` のキーが無い。
- [ ] 計画を作る判断点（J2）へ渡す出力の型の根に、`operation` のキーが無い。
