# フローの移植（claude-harness の実行の仕組みを flywheel へ）

## 概要

claude-harness が持っている「フロー（YAML）と、それを進める仕組み」を flywheel のリポジトリへ移し、flywheel が自分でフローを進められるようにする。最初の区切り（S1）では、いまの標準の実装フローと、統合ブランチを上げるフローを、中身を変えずに移し、フローの中のステップの進み・費用・使ったモデルを flywheel の記録と画面に出す（実装済み）。

2 つ目の区切り（S2。いまの実装対象）では、分析と懐疑のレビューを省いた簡略なフローを足し、計画を作る判断点がタスクごとにフローを選んで理由を計画に書くようにする。あわせて、Codex のレビューを委譲先の宣言で使えるようにし（セルフレビューと並べて走らせる）、claude の effort を、モデルと同じくフローの変数にする。

方針と決定の正本は flywheel#981 の本文（「移植の仕様で決めたこと」）。この文書は、その決定を実装できる形に書き下ろしたもの。

## 背景・目的

flywheel のコンセプトは「人を待たせず、人に待たされず、課題を最短で終わらせる。費用は、その範囲で抑える」（柱は自走・速さ・費用・可視化。品質の水準はフローで決める）。いまの作りでは、次の 3 つがこのコンセプトの邪魔をしている。

- **委譲の中が見えない**: flywheel は外部コマンド `harness` へタスクを渡し、返ってくるのは状態・要約・合計の費用だけ。いまどのステップにいるか、どのステップにいくら使ったか、どのモデルを使ったかが、flywheel の記録にも画面にも無い。
- **確かめが二重**: コードを読むレビュー・品質の検査・CI の待ちが、claude-harness のフローの中と flywheel の完了の検証の両方にある。フローが別の道具の中にある限り、flywheel の側から整理できない。
- **フローを選べない**: 小さな直しにも、標準の実装フローの全部のステップが走る。フローの定義が flywheel の外にあるので、計画の段階でフローを選ぶ形にできない。

この機能の全体（S1〜S4）で、フローの定義と進める仕組みを flywheel に持ち、上の 3 つを順に解く。S1 は土台で、1 つ目（見えない）を解く。2 つ目と 3 つ目は S2・S3 で解く。

## ユーザーストーリー

オーナーとして、タスクの詳細の画面で、委譲がいまどのステップにいて、どのステップにいくら・どのモデルを使ったかを見て、待つべきか手を打つべきかを判断したい。

flywheel の開発者として、フローの定義と進める仕組みを flywheel のリポジトリで直し、flywheel の検査（`make gate`）で確かめたい。

オーナーとして、文書だけの直しや小さな直しは、分析と懐疑のレビューを省いた簡略なフローで速く安く済ませ、どのタスクをどのフローで進めるかを、計画の承認のときに理由つきで見て認めたい（S2）。

オーナーとして、Codex のレビューを使うかと、claude の effort を、委譲先の宣言で決めたい（S2）。

## 機能要件

実装対象の S2 の要件。S1 の要件は、下の「機能要件（S1・実装済み）」に残す。

語: 「簡略なフロー」は、この区切りで足す簡略な実装フロー（識別子 `ticket-light`）のこと。「軽いセルフレビュー」は、プラグインのレビュアー 2 体を並べて呼び、直した箇所を 1 回だけ確かめ直す、懐疑者を呼ばないセルフレビューのこと（下の「簡略なフロー」で定める）。

### 簡略なフロー

- [ ] 組み込みのフローに、簡略なフロー `ticket-light` を足し、flywheel のバイナリへ埋め込む
- [ ] `ticket-light` のステップの並びは、下の「簡略なフローの定義」の表のとおり。標準の実装フロー（`ticket`）から、分析（`analyze`）・E2E の振り分けと E2E テスト（`e2e-route`・`e2e`）を外し、作業ブランチ名を決めるステップ（`branch`）を足し、実装（`implement`）と直し（`fix`）の指示文を簡略なフローの指示文に替えたもの。表に無いステップと遷移は `ticket` と同じ
- [ ] 簡略なフローの作業ブランチ名は、入力の確かめ（`resolve`）が返す名前の鍵（`task-<番号>` か `issue-<番号>`）から、`feature/<鍵>-light` に決める。決めるのは、フロー専用のつなぎのスクリプトを 1 本足して、種類が `command` のステップで行う（claude を呼ばない）
- [ ] 簡略なフローの実装のステップは、プラグインの実装エージェント（`feature-implementer`）を使わない。要件の正本（タスクの文面のファイル。無ければ Issue）を読んで実装し、テストを足すか直し、必須ゲート（`/quality-check`）を通し、軽いセルフレビューを行う
- [ ] 軽いセルフレビューは、プラグインのレビュアー 2 体（`claude-harness:code-reviewer`・`claude-harness:design-reviewer`）を並べて 1 回呼び、重さが中以上の指摘を直し、直した箇所だけを 1 回確かめ直す（確かめ直しは、同じ 2 体へ、直した指摘だけを渡して呼ぶ）
- [ ] 軽いセルフレビューは、懐疑者（`claude-harness:finding-verifier`・`claude-harness:design-deviation-verifier`）を呼ばない
- [ ] 軽いセルフレビューで直さなかった指摘と、確かめ直しで残った指摘は、実装の出力の残指摘（`residual_findings`）に全件載せる
- [ ] 軽いセルフレビューを最後まで行えたら、実装の出力の `self_review` を `complete` にする（`required_facts` の `self_review` の照合は、`ticket` と同じに効く）
- [ ] 簡略なフローの直しのステップは、実装のステップと同じ簡略なフローの指示文の決まり（実装エージェントを使わない・軽いセルフレビュー）で、渡された失敗を直す
- [ ] 簡略なフローの実装のステップは、簡略なフローの範囲を超える変更（ストアの版・承認・権限・クリティカル設計に触れる変更）が要ると分かったら、実装を止めて `outcome: deviation` を返し、`deviation_report` に理由を書く
- [ ] 簡略なフローのレビュー対応（`respond`）は、`ticket` と同じ指示文を使う

### フローを選ぶ（計画）

- [ ] 委譲先の宣言の、`flow` の形の委譲先の操作の `flow` に、`ticket` に加えて `ticket-light` を書ける。1 つの委譲先に、フローの違う操作を並べて書ける
- [ ] 計画を作る判断点の入力の、操作の一覧の行に、`flow` の形の委譲先の操作ではフローの名前（日本語の名前と識別子。例: 「簡略な実装（ticket-light）」）を出す
- [ ] 計画を作る判断点の出力のタスクに、欄 `flow_reason`（そのタスクのフローを選んだ理由）を足す
- [ ] `flow` の形の委譲先の操作を選んだタスクでは、`flow_reason` は必須（無い・`null`・空白だけは不正。2000 文字以内）
- [ ] `flow` の形でない委譲先の操作を選んだタスクでは、`flow_reason` を書かない（無い・`null`・空の文字列のどれか。それ以外は不正）
- [ ] 計画を作る判断点の指示文（`internal/invoker/prompts/j2.md`）に、簡略なフローを選んでよいタスクの基準（文書だけの変更・振る舞いを変えない小さな直し〔文言・設定の値・試験だけの直しなど〕・小さなコードの直し〔1〜2 ファイルの不具合の直しなど〕）と、除くもの（ストアの版・承認・権限・クリティカル設計に触れるもの）と、迷ったら標準を選ぶことを書く
- [ ] 計画を作る判断点は、モデル・effort・切り替え（Codex を使うか）を変えられない（出力の型に欄を足さない）
- [ ] 計画の本文のタスクの項に、`flow` の形の委譲先のタスクでは、フローの名前と理由の行を出す
- [ ] 計画の出力を検査するとき、`flow` の形の委譲先の操作を選んだタスクには、そのときの宣言の操作の `flow` の値（計画が選んだフロー）を、計画の版の中身（`task_plan.spec` の `tasks[]` の要素）に、core が欄 `planned_flow` として足す（`flow` の形でない委譲先のタスクでは欄ごと無し）。続きのタスクを足す経路も同じ。モデルの出力の型には足さない（`additionalProperties: false` のまま。モデルは `planned_flow` を書けない）。`flow_reason` は、モデルが書いたままを `spec` に残し、タスクの記録へ写すときに前後の空白を除く。「構造化出力と `spec` が等しい」ことを確かめている既存の試験は、この欄の分だけ直す
- [ ] 委譲を始めるとき、core は、タスクの記録の、計画が選んだフローを始める（計画の承認の後に宣言の操作の `flow` を変えても、承認したフローで走る）。計画が選んだフローが無いタスク（S2 より前に承認したもの）は、そのときの宣言の操作の `flow` を始める
- [ ] 計画の承認でタスクができるとき、計画が選んだフローと `flow_reason` をタスクの記録に持つ。`flow_reason` は前後の空白を除いた値。`flow` の形でない委譲先のタスクでは、どちらも無し（NULL）
- [ ] 計画の後から足すタスク（続きのタスクを足す判断・フォローアップをタスクとして上げる）も、計画のタスクと同じ型と検査（`flow_reason` を含む）を通る
- [ ] 計画の承認で、オーナーがフローを変えたいときは、いまの差し戻し（計画の作り直し）で受ける。新しい口は作らない

### Codex のレビュー

- [ ] `ticket` と `ticket-light` の定義に、切り替え `codex_review`（既定は偽）を定義する
- [ ] 切り替え `codex_review` が真の実行では、実装のステップの claude が、セルフレビュー（`ticket` では `/self-review`、`ticket-light` では軽いセルフレビュー）を始める前に、Codex のレビュー（`claude-harness-run codex-review-runner`）を裏で起動し、セルフレビューと並べて走らせる
- [ ] 実装のステップは、Codex のレビューが終わるまで値を返さない
- [ ] Codex の指摘のうち、重さが中以上で、Codex の中の確かめで棄却されていない（`refuted` でない）ものを、セルフレビューの指摘と同じに直す。直した後は `/quality-check` を通す
- [ ] 直さなかった Codex の指摘は、残指摘（`residual_findings`）に、`claim` の先頭に `[Codex] ` を付けて載せる
- [ ] Codex のレビューが完了しなかった（`result` が `partial`・`failed`、Codex が入っていない、ほかの起動の失敗）ときは、実装を止めずに進め、未検証の事項（`unverified`）に、完了しなかったことと理由（`errors[].message` があればそれ）を書く
- [ ] 実装の出力に、欄 `codex_review`（`off`・`complete`・`partial`・`failed`・`skipped`）を足す。切り替えが偽なら `off`。Codex を起動できなかったときは `failed`。戻された 2 回目は `skipped`
- [ ] 直しのステップとレビュー対応のステップでは、Codex のレビューを走らせない
- [ ] セルフレビューを実行しなかったために実装のステップへ戻された 2 回目（添付データの `harness.attempt` が 2 以上で、作業ツリーにこの要件の変更が既にある。いまの `ticket-implement.md` の「戻されたとき」と同じ条件）では、Codex のレビューを走らせず、`codex_review` を `skipped` にする（1 回目の結果は、実行の記録の 1 回目のステップの出力に残る）。作業ツリーに変更が無い 2 回目（落ちた実行を `rerun` でやり直した場合）は、1 回目と同じに扱う（Codex を走らせる）
- [ ] Codex のレビューが作った一時ファイルは、結果の成否に関わらず、`claude-harness-run cleanup-review-diff` で消す

### effort と切り替え（フローの変数）

- [ ] フローの YAML の最上位に、`efforts`（変数の名前 → 既定の effort）を定義できる。値は claude の `--effort` が受ける 5 つ（`low`・`medium`・`high`・`xhigh`・`max`）だけ
- [ ] 種類が `llm` のステップに、任意のキー `effort` を書け、値は変数の参照（`$efforts.<名前>`）だけ。指したステップは、解決した値を `--effort <値>` に付けて claude を起動する。指さないステップは、いまと同じ（指定しない）
- [ ] フローの YAML の最上位に、`switches`（変数の名前 → 既定の真偽）を定義できる。`$switches.<名前>` は、種類が `llm` のステップの `with` の値としてだけ書け（ほかの位置は定義の検査の誤り）、解決した値は、添付データへ JSON の真偽値（`true`・`false`）で入る
- [ ] effort と切り替えの値は、オーナーが、委譲先の宣言（`efforts`・`switches`）で差し替えられる。形と扱いは、S1 のモデル（`models`）と同じ（フローの名前 → 変数 → 値）
- [ ] ステップの記録に、書いた effort（解決した値。指さないステップは無し）を持つ
- [ ] `ticket` と `reflect` の定義は、`efforts` を定義しない（effort はいまと同じに指定しない）。`reflect` は `switches` も定義しない
- [ ] `ticket-light` の定義は、`efforts` に `main`（既定 `medium`）と `quick`（既定 `low`）を定義し、実装・直しのステップが `main` を、コミット・コンフリクトの解消のステップが `quick` を指す（値は試しで測って見直す）

- [ ] ステップの名前の表に、`branch`（作業ブランチ名の決定）を足す

## 機能要件（S1・実装済み）

語: フローの中の 1 つの処理を「ステップ」と呼ぶ（YAML の `steps` の 1 件）。「組み込みのフロー」は、flywheel が自分で進めるフローのこと。

### 写す

- [ ] claude-harness（main `b4d6154`）の runtime のうち、下の「写す範囲」の表の「写す」の部品を、試験と一緒に flywheel のリポジトリへ写す
- [ ] 標準の実装フロー（`ticket`）と、統合ブランチを上げるフロー（`reflect`）の定義・ステップの指示文・出力の型・フロー専用のつなぎのスクリプトを、中身を変えずに写し、flywheel のバイナリへ埋め込む
- [ ] 写した元（リポジトリ・コミット）と、写した後に変えた点を、写した先のディレクトリの文書に記録する
- [ ] 写さないものは、下の「写す範囲」の表の「写さない」のとおり

### 進める

- [ ] flywheel のバイナリに、組み込みのフローを始める・状態を読む・待ちに答えて続ける・取り消す、の 4 つのコマンド（`flywheel flow start|status|resume|cancel`）を足す。標準出力は、いまの契約（版 1）と同じ形の JSON
- [ ] フローは、始めたコマンドから切り離した flywheel 自身の別プロセスが進める。待ち（フローの定義の `gate` のステップ）に入るか、実行が終わると、そのプロセスは終わる
- [ ] フローを進めるプロセスが落ちたとき、次に状態を読むか続けるコマンドが、実行中だったステップを「中断」として記録し、やり直すか止めるかの待ちにする（写した仕組みのまま。自動ではやり直さない）
- [ ] フローの記録（1 行ずつ書き足す記録と、ステップごとのログ）は、ワークスペースの `.flywheel/flow/` の下の、実行ごとのフォルダに置く。`.flywheel/flow/` は Git で追跡しない
- [ ] 作業ツリーの作成と片付け・CI 待ち・CI の起動・品質の検査は、入っている claude-harness のプラグインのスクリプトを呼ぶ。場所は `claude-harness-run --plugin-root` で解決する
- [ ] フローを始めるとき、入っているプラグインの版が対応する範囲（4.9.0 以上 6.0.0 未満）に無ければ、始めずに、版と範囲を書いた誤りで終わる

### 宣言と委譲

- [ ] 委譲先の宣言（`connectors.json`）に、4 つ目の形 `flow`（組み込みのフロー）を足す。既存の形（`plugin`・`cli`・`brief`）の宣言と動きは変えない
- [ ] `flow` の形の委譲先は、起動のコマンドを宣言に書かない。操作ごとに、進めるフローの名前を書く（S1 で書けるのは `ticket` だけ）
- [ ] `flow` の形の委譲先へのタスクの委譲は、`cli` の形と同じ道筋（始める → 状態を読む → レビュー待ちを受ける → 完了の検証 → 承認 → 反映先へ入れる）で進む
- [ ] `flow` の形の委譲先の、反映の依頼（統合ブランチか PR を反映先へ上げる）は、組み込みの `reflect` のフローで進む
- [ ] `flow` の形の委譲先は、`cli` の形と同じに、スロットを使わず、同時に走らせる数だけに数える

### ステップの記録

- [ ] 契約（版 1）の出力に、任意の欄として、フローの名前と、ステップの一覧を足す。欄が無い出力（外部の委譲先）は、いまと同じに読む
- [ ] flywheel は、委譲の状態を読むたびに、ステップの一覧をストアへ写す。写すのは、ステップの名前・種類・何回目か・状態・結果・始まった時刻・終わった時刻・費用（額が上限額での計上かの印つき）・書いたモデル・使ったモデル
- [ ] ストアの書き出しと作り直し（`Export`・`Import`）に、ステップの記録を含める

### モデル

- [ ] フローの YAML の先頭に、そのフローで使うモデルを、変数（名前と既定の値）として定義できる
- [ ] claude を呼ぶステップは、使うモデルを、変数の名前で指せる（任意）。指したステップは、その変数の値のモデルを指定して claude を起動する。指さないステップは、いまと同じ（指定しない）。ステップにモデルの名前を直に書くことはできない

## クリティカル設計決定

S2 の分。S1 の分は、下の「クリティカル設計決定（S1・実装済み）」に残す。

### フローを選ぶ口: 計画は操作を選び、操作がフローを持つ

- **採用案**: 委譲先の宣言の操作ごとにフローを書き（S1 の `operations[].flow`）、1 つの委譲先に、フローの違う操作を並べられるようにする。計画を作る判断点は、いまと同じにタスクごとに操作（`operation`）を選び、それがフローを選ぶことになる。理由は、タスクの新しい欄 `flow_reason` に書く。core は、委譲を始めるとき、タスクの記録の、計画が選んだフロー（`planned_flow`）を始める。計画の承認の後に宣言の操作の `flow` を書き換えても、承認したフローで走る（承認していないフローで走らせない）。`planned_flow` が無いタスク（S2 より前に計画を承認したタスク）は、いまと同じに、そのときの宣言の操作の `flow` を始める【決定 2026-11-24 オーナー: フローは計画がタスクごとに選び、理由を添えて計画に出す。オーナーは計画の承認で認め、変えたければ差し戻す】
- **理由**: 計画のタスクは、もう「宣言のどの操作で進めるか」を選んでいて、その検査（宣言にある・起動できる）と、計画の本文・タスクの記録への写しが揃っている。フローを操作に結べば、新しく要るのは理由の欄だけで、どのフローを選べるかはオーナーが宣言で決める（宣言に簡略なフローの操作を書かなければ、計画は選べない）。`flow` の形でない委譲先には、フローを選ぶ口が無いまま
- **代替案**: タスクに欄 `flow` を足し、操作とは別に選ばせる（操作とフローの組み合わせの検査が要り、選べるフローの一覧の置き場をもう 1 つ作ることになる）／フローを選ぶのを core の決まり（変更の大きさなど）にする（決定 1 と合わない）
- **影響範囲**: `internal/core` の宣言の検査（`operations[].flow` の閉集合）・計画の出力の型と検査・計画の本文・計画の判断点の入力・タスクの記録・`internal/invoker/prompts/j2.md`・`internal/view`・`web`

### DB スキーマ: 版 40

- **採用案**: マイグレーション 1 本（版 40）で、次を足す。過去の行は書き換えない（どちらも NULL のまま）
  - `task` の列 `planned_flow`（計画が選んだフロー。文字列。無ければ NULL）
  - `task` の列 `flow_reason`（文字列。無ければ NULL）
  - `contract_run_step` の列 `effort`（文字列。無ければ NULL）
- **理由**: フローと理由はタスクごと、effort はステップの実行ごとの値で、いまの表の粒度に合う。フローを計画のときの値で持てば、画面のたびに宣言を引かずに済む
- **代替案**: 理由を計画の本文だけに持つ（タスクの詳細に出せず、計画の版が替わると引けなくなる）／フローを画面のたびに宣言から引く（core の読み取りの口の引数を変えることになり、宣言が読めないときの扱いも要る）
- **影響範囲**: `Export`・`Import`・`coretest.FillAllTables`・書き出しの表の一覧の試験。Tom の切り替えでは、S1 と同じに、入れ替える前のバイナリで書き出してから入れ替える

### 軽いセルフレビュー: flywheel の指示文で、プラグインのレビュアーを呼ぶ

- **採用案**: 簡略なフローの実装と直しのステップの指示文を flywheel の資材として新しく書き（`prompts/ticket-light-implement.md`・`prompts/ticket-light-fix.md`）、その中で、プラグインのレビュアー 2 体を直接呼ぶ。プラグインのセルフレビューのスキル（`/self-review`）と、実装エージェント（`feature-implementer`）は使わない。claude-harness のリポジトリは変えない【決定 2026-11-24 オーナー: セルフレビューは残し、懐疑のレビューは省く】
- **理由**: `/self-review` の手順（懐疑者・最大 3 周）は、スキルの中に固定で書かれていて、呼ぶ側から懐疑だけを外す口が無い。クリティカル設計の自己申告を疑う役（実装エージェントの手順）は、分析が抜き出したクリティカル設計を入力にしていて、分析を省く簡略なフローでは疑う対象が無い。レビュアー自体はプラグインのものを使うので、指示文の正本がプラグインにある、という決定（決定 7）と食い違わない
- **代替案**: claude-harness の `/self-review` に「懐疑なし」の引数を足す（手順の正本は 1 か所のままだが、claude-harness の直しと公開版の更新を先に済ませる必要がある）／懐疑も残す（簡略にする効き目が分析の分だけになる）
- **影響範囲**: `internal/flow/assets` の資材（新しい指示文・つなぎのスクリプト・出力の型・`ticket-light.yaml`）と、ハッシュの一覧。セルフレビューの手順が 2 か所（プラグインの `/self-review` と、簡略なフローの指示文）になる

### 外部システム連携: Codex のレビューを、実装のステップの中で並べる

- **採用案**: 切り替え `codex_review` が真の実行では、実装のステップの claude が、Codex のレビュー（プラグインの `claude-harness-run codex-review-runner`。中でコードと設計の 2 つの観点を読み、指摘の確かめまで済ませる）を、Bash の裏の実行で起動し、セルフレビューと並べて走らせる。差分は `claude-harness-run collect-review-diff`、要件の文脈はタスクの文面か Issue から作った一時ファイルで渡す（プラグインの `/codex-review` の手順 1〜4 と同じ）。フローを進める仕組みには、並列のステップを足さない【決定 2026-11-24 オーナー: Codex は宣言で使うかを決め、セルフレビューと並べて走らせる。作りは実装のステップの中で並べる】
- **理由**: フローを進める仕組みは、ステップを 1 つずつ順に進める作りで、並列のステップを足すと進める仕組みの直しが大きい。実装のステップの中なら、指示文と出力の型の変更だけで済み、Codex の指摘も同じステップの中で直せる
- **代替案**: フローに並列のステップを足す（Codex が独立したステップになり、画面でも分けて見えるが、別の区切りの大きさ）／実装の後に Codex のステップを続けて置く（素直だが、Codex の分だけ時間が延びる）
- **影響範囲**: `ticket` の定義（`workflows/ticket.yaml`。最上位の `switches: { codex_review: false }` と、実装のステップの `with` の `codex_review: $switches.codex_review`）・実装の指示文（`prompts/ticket-implement.md`）・出力の型（`schemas/implement-result.json`）を変える（S1 の「中身を変えない」は S1 の範囲の決まりで、S2 で変える。写した元と変えた点の文書〔`internal/flow/README.md`〕と、ハッシュの一覧〔`internal/flow/assets/SHA256SUMS`〕を直す）。Codex の費用は Claude とは別の枠で、ステップの費用にも、課題の費用にも数えない。Codex が使えないときは止めない（上の機能要件）。Codex のレビューの 3 つのスクリプト（`codex-review-runner`・`collect-review-diff`・`cleanup-review-diff`）は、手元の版 5.0.0〜5.3.0 のプラグインには入っている。対応する範囲の下限（4.9.0）に入っているかは確かめていない。入っていない版では `failed` として進む（止めない）ので、版の範囲は変えない
- **既知の点**: Codex のレビューの中にも、重く確信のない指摘を確かめる役がある（Codex の中の手順）。簡略なフローで懐疑を省く決定は、Claude の側の懐疑者についてのもので、Codex の中の手順は変えない

### フローの変数: effort と切り替えを、モデルと同じ形で足す

- **採用案**: S1 のモデルの変数（`models`・`$models.<名前>`・宣言の `models`・`flow start --model <変数>=<値>`）と同じ形で、effort（`efforts`・`$efforts.<名前>`・宣言の `efforts`・`--effort <変数>=<値>`）と、切り替え（`switches`・`$switches.<名前>`・宣言の `switches`・`--switch <変数>=<true か false>`）を足す。解決した値は、モデルと同じに、実行の始まりの記録に持ち、続けるコマンドの後も同じ値を使う（続けるコマンドは `--effort`・`--switch` を受けない）【決定 2026-11-24 オーナー: effort は、モデルと同じくフローの YAML の変数にし、オーナーが宣言で差し替える。計画の判断点は変えない】
- **理由**: 差し替えの口（宣言）・始めるときの検査・記録・続けるときの扱いが、モデルで揃っている。同じ形にすれば、宣言を書く人が覚えることが増えない
- **代替案**: Codex を使うかを、委譲先の宣言の 1 つの欄（フローに依らない）にする（フローごとに変えられず、フローの定義の側から使うかを読めない）
- **影響範囲**: `internal/flow/workflow`（定義の読み取りと検査。参照の種類に `$switches` を足し、型は真偽）・`internal/flow/engine`（`--effort` の付与と、`with` の `$switches` の参照を、実行の始まりの記録の値で解決する）・`internal/flow`（`flow start` の引数）・`internal/flow/runstate`（記録）・契約のステップの欄・core の宣言と引数の組み立て
- **実装の最初に確かめること**: `claude --effort <値>` が受け付けられ、実行に効くこと（入っている claude の版で）。受け付けられなければ、実装を止めて仕様への指摘にする。エージェントやスキルが effort を決めている場合にどちらが優先されるかは、「実物で確かめること」で記録する
- **定義の検査で誤りにするもの**: `effort` に値を直に書いた・定義していない変数を指した・`llm` 以外の種類のステップに `effort` を書いた・`efforts` の値が 5 つの値の外か文字列でない・`switches` の値が真偽でない・`with` の `$switches.<名前>` が定義していない変数を指した・`$switches.<名前>` を `llm` のステップの `with` の外（`command` の `with`・遷移の `with`・`select` の `value`・`add_dirs`）に書いた

### 契約: ステップの欄に `effort` を足す（版は 1 のまま）

- **採用案**: 契約の出力の `steps` の要素に、任意の欄 `effort`（文字列か `null`）を足す。欄が無い要素は `null` と読む（S1 の形の出力は、いまと同じに読む）。`effort` が文字列でも `null` でもない要素は、S1 と同じに `steps` の全体を「無い」として扱う
- **理由**: 外部の委譲先（`cli` の形）と、S1 の版の `flywheel flow` の出力は、この欄を持たない。任意にすれば、どちらも読める
- **影響範囲**: `internal/invoker` の契約の出力の読み取り・core のステップの記録・`docs/features/m3-invoker-delegation.md` の契約の節

## クリティカル設計決定（S1・実装済み）

### 移す形: 写して、内側の境界は残す

- **採用案**: claude-harness の runtime のうち、下の「写す範囲」の表の部品を flywheel のリポジトリへ写し、flywheel 自身の別プロセスとして進める。core とのやりとりは、いまの契約の状態の形のまま残す【決定 2026-11-24 オーナー】。写した後は、flywheel の側の写しを flywheel の正本とし、claude-harness の側の直しは、要るものを選んで手で取り込む（自動では追わない）。写した元のコミットと、変えた点を、写した先の文書に記録する
- **理由**: 進める仕組みが記録を呼ぶ口は狭く、写しやすい。PR まわり（約 2,000 行）と、落ちたときの回収は、実測で詰めた端の場合の塊で、書き直すと同じ不具合を踏み直す。core は、契約の状態を読む所が 36 ファイルあり、形を変えないことで、そこを触らずに済む
- **代替案**: core の作りに合わせて書き直す（境界は無くなるが、いちばん大きく、踏み直しのおそれがある）／実行は外部のまま、記録だけ先に受ける（小さいが、フローを flywheel が持つ所に届かない）
- **影響範囲**: 新しいパッケージ `internal/flow/`。claude-harness のリポジトリは変えない

### core との境界: 自分のバイナリを、契約のコマンドとして呼ぶ

- **採用案**: `flow` の形の委譲先では、core が、契約のコマンド（始める・状態を読む・続ける・取り消す・反映の依頼）の引数の配列を、自分の実行ファイルの `flow` のコマンドとして組み立てる。起動は、いまの契約のコマンドの起動の口（`ContractClient`）をそのまま使う。core は `internal/flow/` を import しない（`internal/cli` だけが、`flow` のコマンドのために import する）。実行ファイルのパスは、`internal/cli` が core へ渡す
- **理由**: 契約のコマンドの起動・結果の読み取り・状態の振り分けは、`cli` の形で通しの試しまで済んでいる。同じ口を通せば、core の振る舞いは `cli` の形と同じになり、突き合わせて確かめられる。core が進める仕組みを import しない形なら、「ストアを開くのは core だけ」「core は外部コマンドの起動を持たない」の決まりも変わらない
- **代替案**: core の中から進める仕組みを直接呼ぶ（プロセスが 1 つ減るが、サイクルが止まるとフローも止まり、落ちたときの回収を作り直すことになる）
- **影響範囲**: `internal/core` の宣言の検査と、契約のコマンドの引数の組み立て。実装の形は次のとおりに固定する
  - `flow` の形の委譲先の `commands` は、読み込んだ後も空のままにする（実行ファイルのパスは、宣言を読む時点では分からないため、合成しない）
  - 「契約のコマンドを使う形か」（`cli` か `flow`）を答える関数を 1 つ置き、いま `form` が `cli` かで分かれている箇所と、`commands` の有無で分かれている箇所（反映の依頼の口があるかの判定を含む）を、その関数と、下の引数の組み立ての関数を通す形に直す
  - 契約のコマンドの引数の配列を作る所を 1 つにまとめ、`cli` の形は宣言の `commands` の差し込み、`flow` の形は下の「core が組み立てるコマンド」の表から作る
  - `flow` の形の、始める・続ける・反映の依頼のコマンドの引数は、そのコマンドの run の行を作った後に完成させる（`--delegated-run` に、その run の ID を入れるため）。いまのコードは、続けると反映の依頼で、引数を作ってから run の行を作る順になっているので、`flow` の形では、run の行を作る所が、得た run の ID を引数へ入れてから起動する形に直す。`cli` の形の引数（宣言の差し込み）と、起動の順は変えない。状態を読む・取り消すコマンドは `--delegated-run` を受けないので、順は変えない
  - 宣言の型に、操作の `flow` と、委譲先の `challenge_id_prefix` を足す。`required_facts` を書ける形に `flow` を足す
  - `flow` の形の委譲先は、宣言に書かなくても、反映の依頼の口を持つ。リポジトリの `reflect_connector` は、`flow` の形の委譲先を指せる

### プロセスの形と、落ちたときの回収

- **採用案**: 写した仕組みのまま。始めるコマンドは、実行を作った後、自分の実行ファイルを切り離して起動し直し（新しいセッション・標準入力なし）、進める側が始まったことを記録するまで待って戻る。進める側は、待ちか終わりで終わる。生きているかは、記録した PID と、プロセスの開始時刻の一致で見る。死んでいれば、次の状態の読みか続けるコマンドが、実行中のステップを中断として記録し、やり直す（`rerun`）か止める（`abort`）かの待ちにする。残った子は、プロセスの組ごと止める。切り離して起動し直す内部の入口は `flywheel flow __run-detached <実行の識別>`（コマンドの一覧に出さない）。進める側が 30 秒のうちに引き継がなければ、始めるコマンドは誤りで終わる（写した仕組みの値）
- **理由**: flywheel のサイクルは、有限のプロセスで、常駐を必須にしない（設計書の原則 P6）。フローがサイクルのプロセスの外で進む形は、いまの外部コマンドの形と同じで、サイクルが止まってもフローは進み、次のサイクルが状態を読める
- **代替案**: サイクルのプロセスの中で進める（上の「core との境界」の代替案と同じ理由で採らない）
- **影響範囲**: `internal/flow/`。flywheel の run の表の PID・heartbeat の仕組み（スキルを直接呼ぶ形の委譲のもの）は使わない

### 記録の正本: ファイルが正本、ストアに写し

- **採用案**: 進める仕組みは、実行ごとのフォルダの、1 行ずつ書き足す記録を正本にする（写した仕組みのまま）。置き場は、ワークスペースの `.flywheel/flow/runs/<実行の識別>/`。flywheel は、委譲の状態を読むたびに、契約の出力のステップの一覧をストアへ写し、画面と集計はストアを読む【決定 2026-11-24 オーナー】。埋め込んだ資材（定義・指示文・型・スクリプト）は、版ごとの置き場（ワークスペースの `.flywheel/flow/runtime/<版>/`。版は flywheel のバイナリのコミット）へ展開し、中身の印で確かめる。置き場は、コマンドの `--workspace` の値から直接決め、写した元が読んでいた環境変数（`HARNESS_STATE_DIR`・`HARNESS_DATA_DIR`・`XDG_STATE_HOME`・`XDG_DATA_HOME`）は読まない
- **理由**: 記録の口と「読んでから書くまでの排他」を作り直さずに済み、落ちたときの回収がそのまま効く。ストアに写しがあるので、画面と書き出しは、ほかの記録と同じ扱いにできる
- **代替案**: ストアを正本にする（正本が 1 つになるが、記録の口を作り直すことになり、S1 が大きくなる。後の区切りで移す道は残る）
- **影響範囲**: ストアを作り直したとき（`Import`）、ステップの履歴は戻るが、走っている途中の実行の続きは、実行のフォルダが無いと進められない。`.flywheel/flow/` は、いまの `.flywheel/runs/` と同じに、Git で追跡しない: ワークスペースを作るとき（`flywheel init`）の `.flywheel/.gitignore` に `flow/` の行を入れ、`flywheel flow start` は、`.flywheel/.gitignore` が在って `flow/` の行が無ければ足す（無いファイルは作らない。`internal/flow` は core を import できず、core が持つ正本の中身で作れないため。ワークスペースは `flywheel init` で `.gitignore` を持つ前提）

### DB スキーマ: ステップの記録の表（版 39）

- **採用案**: マイグレーション 1 本（版 39）で、次を足す。過去の行は書き換えない
  - 表 `contract_run_step`: 委譲の実行（`contract_run`）にぶら下がる、ステップ 1 回ぶんの行。列は、委譲の実行の ID・実行の中の通し番号・ステップの識別子・種類・何回目か・状態（`running`・`finished`・`cancelled`・`interrupted`）・結果・始まった時刻・終わった時刻・費用（USD の 100 万分の 1 を単位にした整数。無ければ NULL。ほかの費用の列と同じ単位）・費用が上限額での計上かの印・書いたモデル（無ければ NULL）・使ったモデル（JSON の配列の文字列）。委譲の実行の ID と通し番号の組は重ならない
  - `contract_run` の列 `flow`: フローの名前（無ければ NULL）
- **理由**: ステップは、委譲の実行 1 件の中の出来事で、委譲のコマンド 1 回ごとの記録（`run`）とは粒度が違う。写すたびに同じ行を上書きできるよう、実行の中の通し番号を鍵にする
- **代替案**: `contract_run` に JSON の 1 列で持つ（表は増えないが、ステップごとの費用・モデルの集計を SQL で書けない）
- **影響範囲**: `Export`・`Import`・`coretest.FillAllTables`・書き出しの表の一覧の試験。バイナリより新しいストアを開かない決まりは変えない

### 契約: 任意の欄を足す（版は 1 のまま）

- **採用案**: 契約の出力に、任意の欄 `flow`（文字列）と `steps`（配列）を足す。版は 1 のまま。`steps` の要素は、画面の API の `steps` と同じ欄に、実行の中の通し番号（`seq`。1 以上の整数）を足したもの
  - 読み取りは、いまの `facts` と同じに、契約の出力を読む所（`internal/invoker`）が形を確かめ、core の契約の状態の型に `flow` と `steps` を足して渡す
  - `steps` が無い・配列でない・要素のどれか 1 つでも形が合わない（必須の欄が無い・型が違う・`state` が 4 つの値の外・`seq` が 1 未満か重なる・`attempt` が 1 未満）ときは、`steps` の全体を「無い」として扱う（出力の全体は不正にしない。ほかの欄は、いまと同じに読む）
  - core は、契約の状態を記録するいまの処理と同じトランザクションの中で、その委譲の実行のステップの行を、出力の `steps` と同じ中身にする（委譲の実行の ID と `seq` を鍵に、足すか上書きし、出力に無い `seq` の行は消す）。`steps` が「無い」ときは、ステップの行に触らない
  - `flywheel flow` が `steps` を作る決まり: 対象は、実行のただ 1 つの単位（写した仕組みの `main`。S1 の 2 つのフローは、単位が 1 つ）の、全部の回りのステップの実行。並びと `seq` は、ステップが始まった記録（`step_started`）の、記録の通し番号。`kind` は、フローの定義から引く。`attempt`・`state`・`outcome`・時刻は、写した仕組みの記録の値をそのまま出す。`cost_usd` は、ステップが終わった記録の「実行の累計へ加えた額」（終わっていない・claude を呼ばないステップは `null`）で、合計は、契約の `cost_usd` と一致する。`cost_unknown` は、費用を得られず、渡した上限額を使ったものとして数えたときに真（写した仕組みの決まり）
- **理由**: 欄を任意にすれば、外部の委譲先（`cli` の形）の動きは変わらない。外部の委譲先が同じ欄を返せば、同じ記録と画面に乗る
- **代替案**: 版を 2 に上げる（外部の委譲先の宣言と実装を同時に直すことになる）
- **影響範囲**: `internal/invoker` の契約の出力の読み取り・core の検査・`docs/features/m3-invoker-delegation.md` の契約の節

### 外部システム連携: 呼ぶコマンド

- **理由**: 機械の部品（作業ツリー・CI 待ち・CI の起動・品質の検査）は、後の区切り（S4）で Go に書き直すと決めてある【決定 2026-11-24 オーナー】。S1 では、同じに動くことを確かめる範囲に、書き直しを混ぜない
- **代替案**: スクリプトを flywheel に写して埋め込む（同じスクリプトが 2 か所になる）／S1 から Go に書き直す（確かめる範囲に、新しく書いた動きが混ざる）

### プラグインの版の確かめ

- **採用案**: フローを始めるとき、`claude-harness-run --plugin-root` が返した場所の、プラグインの宣言（`.claude-plugin/plugin.json`）の版を読み、4.9.0 以上 6.0.0 未満でなければ、始めずに誤りで終わる。範囲は、写した元と同じ値を、flywheel のコードに定数で持つ
- **理由**: ステップの中の claude は、入っているプラグインのエージェントとスキルを使う。範囲の外の版では、ステップの指示文と噛み合わない
- **代替案**: 確かめない（版がずれたとき、ステップの途中の分かりにくい失敗になる）
- **影響範囲**: `internal/flow/`

### セキュリティ: 権限モードと、子の目印

- **採用案**: (1) ステップが起動する claude には、宣言の `permission_mode` を `--permission-mode` で渡す。値の閉集合は変えない。Tom の切り替えでは、いまと同じ動きになる値（`auto`）を書く。いまの外部コマンドの形は、権限モードを渡していないが、渡さないときに効くのは、実行する人のユーザー設定の既定で、Tom を動かす環境では `auto`（Tom のいまの宣言の `permission_mode` も `auto`）。`default` を渡すと、ユーザー設定より引数が優先され、いまより厳しくなる（相手のいない実行で、確認の要る操作が拒否される）【訂正 2026-11-24 オーナー。初めは「同じになるのは `default`」と書いていた】(2) ステップが起動する claude の子の環境に `FLYWHEEL_DELEGATED_RUN` を付ける。`flywheel flow` のコマンドも、ほかのコマンドと同じに、この目印のある環境からは実行できない（いまの、コマンドの照合より前の検査を、そのまま使う）
  - 値の渡し方: core は、`flow start` と `flow resume` に、`--permission-mode <宣言の値>` と `--delegated-run <そのコマンドの run の ID>`（契約のコマンド 1 回ごとの run。例: `R-2494`）を必ず付ける。`flywheel flow` は、どちらかが無い・権限モードが 3 つの値の外のとき、使い方の誤りで終わる。状態を読む・取り消すコマンドは、claude を起動しないので、どちらも受けない
  - 切り離して進める側へは、権限モードを `HARNESS_CLAUDE_PERMISSION_MODE`、run の ID を flywheel の内部の環境変数で引き継ぐ。進める仕組みは、claude を起動するときだけ、子の環境に `FLYWHEEL_DELEGATED_RUN=<run の ID>` を足す。進める側のプロセス自身の環境と、つなぎのスクリプト・プラグインのスクリプトの環境には、目印を置かない（置くと、進める側が自分の起動で拒否される）
- **理由**: いまは、委譲先の子が `harness` を呼ぶことはできても、flywheel のコマンドは別の道具なので届かなかった。フローを flywheel のバイナリが進めるようになると、子が `flywheel flow resume` を呼べば、自分のレビュー待ちに自分で答えられてしまう。承認と回答の口へ子から届かない、という決まり（設計書 §9）を、組み込みのフローでも保つ
- **代替案**: 目印を付けない（子が、待ちへの答えと取り消しを自分で実行できる）
- **影響範囲**: `internal/flow/` の claude の起動。サイクルが `flywheel flow` を起動するときは、いまの契約のコマンドの起動と同じに、目印を外した環境で起動する

### モデル

- **採用案**: モデルは、フローの YAML の中の変数として定義し、値を差し替えられるのは宣言だけにする【決定 2026-11-24 オーナー】
  - 定義: YAML の最上位に `models`（変数の名前 → 既定の値。値は空でない文字列）。種類が `llm` のステップに、任意のキー `model` を足し、値は変数の参照（`$models.<名前>`）だけを書ける

    ```yaml
    models:
      main:  <モデルの名前>
      light: <モデルの名前>
    steps:
      analyze:   { kind: llm, model: $models.light }
      implement: { kind: llm, model: $models.main }
    ```

  - 定義の検査で誤りにするもの: `model` にモデルの名前を直に書いた・定義していない変数を指した・`llm` 以外の種類のステップに `model` を書いた・`models` の値が空か文字列でない
  - 差し替え: `flow` の形の委譲先の宣言に、任意の `models`（フローの名前 → 変数の名前 → 値）を書く。core は、フローを始めるとき（タスクの `ticket` と、反映の依頼の `reflect`）、そのフローの分を `--model <変数>=<値>` として渡す。`flywheel flow start` は、フローが定義していない変数を受けたら、実行を作らずに使い方の誤りで終わる。解決した値（既定の値に、宣言の値を重ねたもの）は、実行の始まりの記録に持ち、続けるコマンドの後も同じ値を使う（続けるコマンドは `--model` を受けない）
  - 起動と記録: 変数を指したステップは、解決した値を `--model <値>` に付けて claude を起動する。ステップの記録の「書いたモデル」は、解決した値。ステップが終わったとき、claude の結果の、モデルごとの使用の欄（`modelUsage`）の名前を、使ったモデルとして記録する
  - 計画を作る判断点の出力には、モデルの欄を足さない
- **理由**: エージェントが選ぶのはフローで、フローが品質の水準と費用の形を決める。モデルをステップに直に書くと、同じモデルを使う複数のステップを 1 か所で変えられず、宣言から差し替える口も、ステップの名前に結び付いてしまう。変数にすれば、「このフローは、どの役割のモデルを使うか」が定義の先頭で分かり、差し替えは変数の単位で済む。使ったモデルは、書いた値ではなく claude の報告から取ることで、指定しなかったステップ（既定のモデル）と、エージェントの定義が決めたモデルも記録できる
- **代替案**: ステップにモデルの名前を直に書く（変える所が散る）／計画を作る判断点がタスクごとにモデルを選ぶ（採らない。エージェントはモデルを変えない）／変数は定義だけで、差し替えの口は後の区切り（オーナーが、最初の区切りに差し替えまで入れると決めた）
- **影響範囲**: `internal/flow/` の定義の読み取りと検査・claude の起動・記録の型・`flow start` の引数。core の宣言の型と検査・始めるコマンドの引数の組み立て
- **実装の最初に確かめること**: エージェントの定義（`--agent`）がモデルを決めているステップで、`--model` がどちらを優先するかは未確認。実測して、変数の値のモデルが使われないなら、実装を止めて仕様への指摘にする

### 依存

### 簡略なフローの定義

`ticket-light` は、`ticket` の定義を元に、次の表の差分だけを持つ（表に無いステップ・遷移・上限・`facts` は `ticket` と同じ）。上書きの口（`overridable`）は持たない（S1 と同じに、組み込みのフローは上書きを読まない）。

| ステップ | `ticket` | `ticket-light` |
|---|---|---|
| `integration-route` | `none` → `analyze` | `none` → `branch` |
| `integration` | `created`・`existing` → `analyze` | `created`・`existing` → `branch` |
| `analyze` | 分析（claude） | 無い |
| `branch` | 無い | 種類 `command`。つなぎのスクリプト `ticket-light-branch` が、`resolve` の `key` から `feature/<鍵>-light` を返す（出力の型 `schemas/ticket-light-branch.json`。結果は `ok` だけで、`ok` → `workspace`） |
| `workspace` | `branch: $steps.analyze.branch` | `branch: $steps.branch.branch` |
| `implement` | 実装エージェント・`prompts/ticket-implement.md`・`with` に `critical_design` | エージェント無し・`prompts/ticket-light-implement.md`・`effort: $efforts.main`・`with` に `critical_design` は無い |
| `fix` | 実装エージェント・`prompts/ticket-fix.md` | エージェント無し・`prompts/ticket-light-fix.md`・`effort: $efforts.main` |
| `commit` | （effort 無し） | `effort: $efforts.quick` |
| `sync` | `current`・`synced` → `e2e-route` | `current`・`synced` → `quality` |
| `sync-resolve`・`land-sync-resolve` | （effort 無し） | `effort: $efforts.quick` |
| `e2e-route`・`e2e` | E2E の振り分けと E2E テスト | 無い |

- 実装の出力の型は、`ticket` と同じ `schemas/implement-result.json`（下の `codex_review` の欄を足したもの）を使う
- 実装のステップの `with` には、`ticket` と同じに `codex_review: $switches.codex_review` を渡す（直しのステップには渡さない）

### 実装の出力の型の変更

`schemas/implement-result.json` に、必須の欄 `codex_review`（`off`・`complete`・`partial`・`failed`・`skipped`）を足す。`ticket` と `ticket-light` の実装のステップの指示文は、どちらもこの欄を返す。

### IF / API

**委譲先の宣言（`flow` の形。S2 で足す欄）**:

```json
{
  "id": "flywheel-flow",
  "form": "flow",
  "permission_mode": "auto",
  "challenge_id_prefix": "tom-",
  "efforts": { "ticket-light": { "main": "medium" } },
  "switches": { "ticket": { "codex_review": true }, "ticket-light": { "codex_review": true } },
  "operations": [
    { "id": "impl", "flow": "ticket", "interactive": false, "child_may_decide": true, "artifacts": "pr" },
    { "id": "impl-light", "flow": "ticket-light", "interactive": false, "child_may_decide": true, "artifacts": "pr" }
  ],
  "required_facts": { "self_review": ["complete"] }
}
```

- `operations[].flow` に書けるのは `ticket` と `ticket-light`（ほかの値は設定の誤り）
- `models`（S1）・`efforts`・`switches` のフローの名前に書けるのは `ticket`・`ticket-light`・`reflect`（ほかの値は設定の誤り）
- `efforts` の値は 5 つの値（`low`・`medium`・`high`・`xhigh`・`max`）だけ。`switches` の値は真偽だけ（ほかは設定の誤り）
- `efforts`・`switches` を書いてよいのは、`flow` の形の委譲先だけ（ほかの形に書いたら設定の誤り）
- 変数がそのフローに定義されているかは、`models` と同じに、宣言を読むときには確かめず、`flywheel flow start` が確かめる

**core が組み立てるコマンド（S2 で足すもの）**: 始める・反映の依頼のコマンドに、S1 の `--model` に続けて、宣言の `efforts` のそのフローの分を `--effort <変数>=<値>`、`switches` の分を `--switch <変数>=<true か false>` として、それぞれ変数の名前の辞書順に、`--input` の前に足す（無ければ足さない）。並びは `--model`・`--effort`・`--switch`・`--input` の順。

**`flywheel flow start` の引数（S2 で足すもの）**: `--effort <変数>=<値>`（複数可）・`--switch <変数>=<true か false>`（複数可）。形が合わない（`=` が無い・変数の名前か値が空・同じ変数を 2 度）・フローが定義していない変数・effort の値が 5 つの外・切り替えの値が `true`・`false` の外のときは、実行のフォルダを作らずに、使い方の誤りで終わる。`flywheel flow resume` は、どちらも受けない。

**計画を作る判断点の出力（タスクの欄）**: `flow_reason`（文字列か `null`。型としては任意で、要否は上の機能要件の検査で決める）。計画の後から足すタスクの出力の型は、計画のタスクの型（`items`）を使っているので、同じ欄が入る。

**計画を作る判断点の入力（操作の一覧の行）**: `flow` の形の委譲先の操作の行の末尾に「｜フロー: <名前>（<識別子>）」を足す。名前は、上の「フローの名前」の表と同じ（core に同じ表を持つ。core はフローの定義を読まない）。

**計画の本文（タスクの項）**: `flow` の形の委譲先のタスクの「操作」の行の後に、「   - フロー: <名前>（<識別子>）」と「   - フローを選んだ理由: <理由>」の 2 行を足す。

**ステップの記録（契約の `steps` の要素・ストア・API）**: `effort`（文字列か `null`）を足す。`flywheel flow` の出力では、変数を指したステップは解決した値、指さないステップは `null`。

|---|---|---|
| `internal/flow/workflow` | フローの定義の読み取りと検査（写し） | 標準ライブラリ・yaml・jsonschema |
| `internal/flow/runstate` | 実行の記録の型・畳み込み・ファイルへの書き足しと排他（写し） | 標準ライブラリ |
| `internal/flow/engine` | ステップの実行・待ち・中断の回収（写し） | `workflow`・`runstate` |
| `internal/flow/assets` | 埋め込む資材（定義・指示文・型・つなぎのスクリプト）と、展開 | 標準ライブラリ |
| `internal/flow`（直下） | 始める・状態を読む・続ける・取り消す・切り離して進める、の入口と、契約の形の出力・プラグインの場所と版の確かめ | 上の 4 つ |

- `internal/flow/` の配下は、上の表に無い flywheel のパッケージ（`internal/core`・ストア・`internal/invoker`・`internal/server`・`internal/view`・`internal/adapters/*`・`internal/cli`）を import しない
- `internal/core`・`internal/invoker`・`internal/server`・`internal/view` は、`internal/flow/` を import しない
- `internal/cli` だけが `internal/flow` を import する（`flow` のコマンドの定義と、自分の実行ファイルのパスを core へ渡すこと）
- 依存の向きは、いまの検査（`go list` の依存関係の試験）に足して固定する

### IF / API

**委譲先の宣言（`flow` の形）**:

```json
{
  "id": "flywheel-flow",
  "form": "flow",
  "permission_mode": "auto",
  "challenge_id_prefix": "tom-",
  "models": { "ticket": { "main": "<モデルの名前>" } },
  "operations": [
    { "id": "impl", "flow": "ticket", "interactive": false, "child_may_decide": true, "artifacts": "pr" }
  ],
  "required_facts": { "self_review": ["complete"] }
}
```

- `commands` と `contract_version` は書けない（書いたら設定の誤り）
- `permission_mode` は、ほかの形と同じ 3 つの値（`default`・`acceptEdits`・`auto`）だけ
- `operations[].flow` は必須。S1 で書けるのは `ticket` だけ（ほかの値は設定の誤り）
- `challenge_id_prefix` は任意（既定は空）。書いてよいのは `flow` の形の委譲先だけ（ほかの形に書いたら設定の誤り）。フローへ渡す課題の識別の前に付く。統合ブランチの名前の鍵になるので、同じリポジトリを複数のワークスペースが使うときに、名前が重ならないようにするためのもの
- `required_facts` は、`cli` の形と同じ意味
- `models` は任意。フローの名前（S1 で書けるのは `ticket` と `reflect`）ごとに、差し替える変数の名前と値（空でない文字列）を書く。書いてよいのは `flow` の形の委譲先だけ。変数がそのフローに定義されているかは、宣言を読むときには確かめず（core はフローの定義を読まない）、フローを始めるときに `flywheel flow start` が確かめる
- `flow` を書いてよいのは、`flow` の形の委譲先の操作だけ

**core が組み立てるコマンド**（`<自分>` は、自分の実行ファイルの絶対パス）:

| 契約のコマンド | 引数 |
|---|---|
| 始める | `<自分> flow start --workspace <ワークスペース> --permission-mode <宣言の値> --delegated-run <run の ID> --input issue=<番号> --input task_file=<パス> --input task_id=<ID> --input uses_integration=<true か false> --input challenge_id=<前置き＋課題の ID> <フローの名前>` |
| 状態を読む | `<自分> flow status --workspace <ワークスペース> <実行の識別>` |
| 続ける | `<自分> flow resume --workspace <ワークスペース> --permission-mode <宣言の値> --delegated-run <run の ID> [--input <選んだもの>] [--note <添え書き>] [--approved-ref <通した中身>] <実行の識別>` |
| 取り消す | `<自分> flow cancel --workspace <ワークスペース> <実行の識別>` |
| 反映の依頼 | `<自分> flow start --workspace <ワークスペース> --permission-mode <宣言の値> --delegated-run <run の ID> --input artifact_ref=<成果物> --input challenge_id=<前置き＋課題の ID> reflect` |

- 宣言の `models` に、始めるフローの分があるときは、始める・反映の依頼のコマンドの `--input` の前に、変数ごとの `--model <変数>=<値>` を、変数の名前の辞書順に足す（無ければ足さない）
- `<run の ID>` は、そのコマンド 1 回の run の ID（flywheel の run。例: `R-2494`）。`<実行の識別>` は、`flow start` が返した契約の `run_id`（組み込みのフローの実行の識別）で、別のもの
- `challenge_id` は、前置きと課題の ID を、区切りを足さずにつないだもの（例: 前置き `tom-` と課題 `C-186` で `tom-C-186`）

- 値が空の入力（取り込み元の Issue が無い課題の `issue`）は、いまの外部コマンドの形と同じに、空のまま渡す
- 反映の依頼は、宣言に書かなくても、いつも組み込みの `reflect` のフローで進む（`flow` の形の委譲先は、どれも反映の依頼の口を持つ）
- コマンドの時間切れは、いまの契約のコマンドと同じ（`cli` の形と同じ値）
- レビュー待ち（`kind: review`）は、いつも受け付ける（外部コマンドの形の `--accept-kind review` に当たる）
- 作業ディレクトリは、`cli` の形と同じ（リポジトリの元のクローンか、作業用のクローン）

## やらないこと

- 外部の委譲先の形（`cli`・`plugin`）を外す（理由: 組み込みのフローに不具合が出たとき、宣言を戻すだけで元の形に帰れるようにする。外すかは、Tom で安定してから別の区切りで決める）
- フローを利用側で変える口（上書き）を、組み込みのフローで使えるようにする（理由: 写した仕組みには読み取りの処理が入っているが、どこに置いて誰が変えるかを決めていない。入口では受け付けない）
- 技術調査のフロー（理由: 後の区切り。フローを選ぶ仕組み〔S2〕の後に決める）
- 計画を作る判断点がコードを読めるようにする（flywheel#1212。理由: フローの移植とは別の点）
- 改修の提案の判断点が課題を自分で作ることの扱い（理由: 取り込みの決まりの話で、別に決める）
- 画面から、反映先へ入れる承認を受ける（理由: 承認の経路の決まり〔設計書 §9〕の話で、別に決める）
- 記録の正本をストアへ移す（理由: S1 は、写した仕組みを変えない。後の区切りで移す道は残る）
- 費用の集計の画面・コマンド（`flywheel metrics`）に、ステップごと・モデルごとの集計を足す（理由: 設計の見直しの区切り 5「時間と費用の集計」で作る。S1 は記録を持つ所まで）
- CLI のテキストの出力に、ステップの一覧を足す（理由: S1 で人が見る口は画面。`--json` の出力には、API と同じ型で出る）
- claude-harness のリポジトリの変更（理由: claude-harness は残す。写した後の追従は手で選ぶ）
- 写した仕組みの環境変数の名前（`HARNESS_*`）と、資材の中の語を、flywheel の語へ直す（理由: 同じに動くことを確かめる範囲に、名前の変更を混ぜない）
- 走っている途中の委譲を、外部コマンドの形から組み込みのフローへ移す（理由: 切り替えは、走っている委譲が 0 件のときに行う手順にする）
- （S2）フローを進める仕組みに、ステップを並べて走らせる作りを足す（理由: Codex は実装のステップの中で並べると決めた。並列のステップは、要るようになったら別の区切りで決める）
- （S2）claude-harness の `/self-review` に懐疑なしの口を足す（理由: claude-harness のリポジトリは変えない。軽いセルフレビューは flywheel の指示文で行う）
- （S2）計画を作る判断点が、モデル・effort・切り替え（Codex を使うか）を変える（理由: エージェントはフローを選ぶだけ。値はオーナーが宣言で決める）

- （S2）簡略なフローのレビュー対応（`respond`）を軽くする（理由: レビュー対応は PR への人の指摘が入口で、まれ。`ticket` と同じ指示文のまま）
- （S2）標準のフローの effort を変える（理由: `ticket` は、いまと同じに effort を指定しない。変えるなら宣言の `efforts` を使えるよう、変数を足すのは後で決める）

## Tom の切り替えと戻し方【切り替えそのものは、オーナーの了承を取って別に行う】

Tom の flywheel のリポジトリ（`repos[]` の `flywheel`。いまは `connector: harness-cli`＝`form: cli` の外部コマンド `harness` を呼ぶ形）を、組み込みのフローへ切り替える手順と、戻す手順。各段の前に、オーナーの了承を取る。走っている委譲を移す手順ではない（切り替えは、走っている委譲が 0 件のときだけ行う）。

### 前提

- claude-harness のプラグインと `claude-harness-run` が入っている（`claude-harness-run --plugin-root` が場所を返し、その `.claude-plugin/plugin.json` の版が 4.9.0 以上 6.0.0 未満）。入っていなければ、フローを始めるときの誤りで分かる。
- 切り替えるのは宣言（`.flywheel/connectors.json`）だけ。`repos[]` の `connector` の指し先を変えるか、指し先の宣言を書き換える。`harness-cli` の宣言は、戻すために消さずに残す。

### 切り替える手順（S1・実装済み）

1. **走っている委譲が 0 件であることを確かめる。** 着手中（`in_progress`）と検証中（`verifying`）の課題が 0 件（`flywheel list --status in_progress`・`flywheel list --status verifying`。`flywheel status` の一覧でも見る）で、反映の依頼も走っていない（`flywheel runs` と、各課題の `flywheel show` の委譲先の実行で、終わっていない実行が無い）こと。1 件でもあれば、終わるまで待つか、オーナーの判断で止めてから行う。サイクルは止めておく（切り替えの間に新しい委譲を始めない）。
2. **ストアを書き出しておく（入れ替える前の、古いバイナリで）。** `flywheel export --out <ファイル>` で書き出す。新しいバイナリでストアを開くと版 39 へ上がり、バイナリより新しいストアは古いバイナリで開けないので、戻すときのバックアップはこの時点でしか取れない。
3. **バイナリを入れ替える。** この機能を含む版（`flywheel flow` を持つもの）をビルドし（`make build`。成果物は `build/flywheel`）、Tom が使っている `flywheel` の実行ファイルを置き換える。置き換えた後、`flywheel help` に `flow`（内部向け）が出ることを確かめる。
4. **ストアの版を確かめる。** `flywheel version` の `schema_version`（このバイナリが扱える版）が 39 以上であること。この版のバイナリでストアを開くと、ストアは版 39（`contract_run_step` の表と `contract_run.flow` の列）へ上がる。
5. **宣言を `form: flow` へ書き換える。** `connectors.json` に `form: flow` の委譲先を足し、`repos[].connector` をそちらへ向ける（`harness-cli` の宣言は消さずに残す）。`form: flow` の委譲先には `commands`・`contract_version` を書けない。例:

    ```json
    {
      "id": "flywheel-flow",
      "form": "flow",
      "permission_mode": "auto",
      "challenge_id_prefix": "tom-",
      "operations": [
        {"id": "impl", "flow": "ticket", "interactive": false, "child_may_decide": true, "artifacts": "pr"}
      ],
      "required_facts": {"self_review": ["complete"]}
    }
    ```

    - `permission_mode` は **`auto`** を書く。いまの外部コマンドの形は権限モードを渡さず、効くのは実行する人のユーザー設定の既定（Tom の環境では `auto`）。`default` を書くと、ユーザー設定より引数が優先され、いまより厳しくなる（相手のいない実行で、確認の要る操作が拒否される）。
    - `challenge_id_prefix` は、いまの宣言の `--input challenge_id=tom-{challenge_id}` の `tom-` に合わせる。
    - モデルを差し替えたいときだけ、委譲先に `models`（フロー名 → 変数 → 値）を書く。S1 で移す 2 つのフローは変数を定義していないので、書くと始めるときの誤りになる（書かない）。
    - 反映の依頼の口は、宣言に書かなくても持つ。いまの `commands.reflect` の代わりは、`reflect_connector` を省くか `flow` の形の委譲先へ向ける。
    - `required_facts` は、いまの `harness-cli` と同じ値を写す（例は Tom のいまの値）。
6. **宣言を確かめる。** 次のサイクルの前に `flywheel status` が `config_invalid` にならないこと。1 件目の委譲は、状態（着手中→検証中→完了確認待ち→完了）が `cli` の形と同じ順で進み、タスクの詳細の画面の「委譲先の実行」にフローの名前とステップの一覧が出ることを、オーナーが見る。

### 戻す手順（S1・実装済み）

1. 走っている委譲が 0 件であることを、切り替えの手順の 1 と同じに確かめる（`flow` の形で走っている実行は、戻しても外部コマンドの形へは移らない）。
2. `connectors.json` の宣言を、元の形（`form: cli`・`harness-cli`）へ戻す。`repos[].connector` を `harness-cli` へ向け直す（宣言を消していたなら書き戻す）。バイナリとストアの版は戻さない（版 39 のストアは、版 39 以上のバイナリでだけ開く。外部コマンドの形は、ステップの欄を返さない出力と同じに読む）。
3. `flywheel status` が `config_invalid` にならず、次の委譲が `harness contract start` で始まることを確かめる。`.flywheel/flow/` は残してよい（Git で追跡しない。要らなければ、走っている実行が無いことを確かめてから消す）。

### 簡略なフローの操作を足す手順（S2。足すことそのものは、オーナーの了承を取って別に行う）

1. **走っている委譲が 0 件であることを、切り替えの手順の 1 と同じに確かめる。** サイクルは止めておく。
2. **ストアを書き出しておく（入れ替える前の、古いバイナリで）。** S2 を含むバイナリでストアを開くと版 40 へ上がる。S1 の手順の 2 と同じ理由で、戻すときのバックアップはこの時点でしか取れない。
3. **バイナリを入れ替え、`flywheel version` の `schema_version` が 40 以上であることを確かめる。**
4. **宣言に、簡略なフローの操作を足す。** `flow` の形の委譲先の `operations` に、`flow` が `ticket-light` の操作を、いまの `ticket` の操作と並べて足す（いまの操作は消さない。計画を作る判断点は、両方から選ぶ）。例: `{"id": "impl-light", "flow": "ticket-light", "interactive": false, "child_may_decide": true, "artifacts": "pr"}`。`required_facts` は委譲先ごとなので、そのまま両方の操作に効く。
5. **（Codex を使うときだけ。別に了承を取る）** 委譲先に `switches`（例: `{"ticket": {"codex_review": true}, "ticket-light": {"codex_review": true}}`）を書く。
6. **宣言を確かめる。** `flywheel status` が `config_invalid` にならないこと。次の計画で、計画の承認の画面のタスクにフローと理由が出ることを、オーナーが見る。

戻すときは、足した操作（と `switches`）を宣言から消す。簡略なフローの操作を選んだタスクが計画に残っていれば、委譲を始めるときに操作が宣言に無い誤りになるので、そのタスクが済むか、計画を作り直してから消す。

## 受入基準

> 実装対象の S2 の範囲。「実物で確かめること」のほかは、`make check` の中の試験で確かめる（試験の環境は「技術的な制約・方針」のとおり。偽の `claude` は、指示文に従う代わりに、試験が決めた出力を返す）。指示文の中身（軽いセルフレビューの手順・Codex の扱い）は、指示文のファイルに書かれていることを試験で確かめ、振る舞いは「実物で確かめること」で確かめる。指示文の基準の「〜の指示がある」は、基準に書いた名前・コマンド・値（例: `claude-harness:code-reviewer`・`cleanup-review-diff`・`refuted`）を含む文が、その指示文のファイルにあることを確かめる。「〜を呼ぶ指示が無い」は、その名前の文字列を、そのファイルが含まないことを確かめる（否定の文にも書かない）。S1 の受入基準は、下の「受入基準（S1・実装済み）」に残す。
