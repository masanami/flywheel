# フローの移植（claude-harness の実行の仕組みを flywheel へ）

## 概要

claude-harness が持っている「フロー（YAML）と、それを進める仕組み」を flywheel のリポジトリへ移し、flywheel が自分でフローを進められるようにする。最初の区切り（S1）では、いまの標準の実装フローと、統合ブランチを上げるフローを、中身を変えずに移し、フローの中のステップの進み・費用・使ったモデルを flywheel の記録と画面に出す。

方針と決定の正本は flywheel#981 の本文（「移植の仕様で決めたこと」）。この文書は、その決定を実装できる形に書き下ろしたもの。

## 背景・目的

flywheel のコンセプトは「人を待たせず、人に待たされず、課題を最短で終わらせる。費用は、その範囲で抑える」（柱は自走・速さ・費用・可視化。品質の水準はフローで決める）。いまの作りでは、次の 3 つがこのコンセプトの邪魔をしている。

- **委譲の中が見えない**: flywheel は外部コマンド `harness` へタスクを渡し、返ってくるのは状態・要約・合計の費用だけ。いまどのステップにいるか、どのステップにいくら使ったか、どのモデルを使ったかが、flywheel の記録にも画面にも無い。
- **確かめが二重**: コードを読むレビュー・品質の検査・CI の待ちが、claude-harness のフローの中と flywheel の完了の検証の両方にある。フローが別の道具の中にある限り、flywheel の側から整理できない。
- **フローを選べない**: 小さな直しにも、標準の実装フローの全部のステップが走る。フローの定義が flywheel の外にあるので、計画の段階でフローを選ぶ形にできない。

この機能の全体（S1〜S4）で、フローの定義と進める仕組みを flywheel に持ち、上の 3 つを順に解く。S1 は土台で、1 つ目（見えない）を解く。2 つ目と 3 つ目は S2・S3 で解く。

## ユーザーストーリー

オーナーとして、タスクの詳細の画面で、委譲がいまどのステップにいて、どのステップにいくら・どのモデルを使ったかを見て、待つべきか手を打つべきかを判断したい。

flywheel の開発者として、フローの定義と進める仕組みを flywheel のリポジトリで直し、flywheel の検査（`make gate`）で確かめたい。

## 機能要件

語: フローの中の 1 つの処理を「ステップ」と呼ぶ（YAML の `steps` の 1 件）。「組み込みのフロー」は、flywheel が自分で進めるフローのこと。

### 写す

- [ ] claude-harness（main `b4d6154`）の runtime のうち、下の「写す範囲」の表の「写す」の部品を、試験と一緒に flywheel のリポジトリへ写す
- [ ] 標準の実装フロー（`ticket`）と、統合ブランチを上げるフロー（`reflect`）の定義・ステップの指示文・出力の型・フロー専用のつなぎのスクリプトを、中身を変えずに写し、flywheel のバイナリへ埋め込む
- [ ] 写した元（リポジトリ・コミット）と、写した後に変えた点を、写した先のディレクトリの文書に記録する
- [ ] 写さないものは、下の「写す範囲」の表の「写さない」のとおり

### 進める

- [ ] flywheel のバイナリに、組み込みのフローを始める・状態を読む・待ちに答えて続ける・取り消す、の 4 つのコマンド（`flywheel flow start|status|resume|cancel`）を足す。標準出力は、いまの契約（版 1）と同じ形の JSON
- [ ] フローは、始めたコマンドから切り離した flywheel 自身の別プロセスが進める。待ち（フローの定義の `gate` のステップ）に入るか、実行が終わると、そのプロセスは終わる
- [ ] フローを進めるプロセスが落ちたとき、次に状態を読むか続けるコマンドが、実行中だったステップを「中断」として記録し、やり直すか止めるかの待ちにする（写した仕組みのまま。自動ではやり直さない）
- [ ] フローの記録（1 行ずつ書き足す記録と、ステップごとのログ）は、ワークスペースの `.flywheel/flow/` の下の、実行ごとのフォルダに置く。`.flywheel/flow/` は Git で追跡しない
- [ ] 作業ツリーの作成と片付け・CI 待ち・CI の起動・品質の検査は、入っている claude-harness のプラグインのスクリプトを呼ぶ。場所は `claude-harness-run --plugin-root` で解決する
- [ ] フローを始めるとき、入っているプラグインの版が対応する範囲（4.9.0 以上 6.0.0 未満）に無ければ、始めずに、版と範囲を書いた誤りで終わる

### 宣言と委譲

- [ ] 委譲先の宣言（`connectors.json`）に、4 つ目の形 `flow`（組み込みのフロー）を足す。既存の形（`plugin`・`cli`・`brief`）の宣言と動きは変えない
- [ ] `flow` の形の委譲先は、起動のコマンドを宣言に書かない。操作ごとに、進めるフローの名前を書く（S1 で書けるのは `ticket` だけ）
- [ ] `flow` の形の委譲先へのタスクの委譲は、`cli` の形と同じ道筋（始める → 状態を読む → レビュー待ちを受ける → 完了の検証 → 承認 → 反映先へ入れる）で進む
- [ ] `flow` の形の委譲先の、反映の依頼（統合ブランチか PR を反映先へ上げる）は、組み込みの `reflect` のフローで進む
- [ ] `flow` の形の委譲先は、`cli` の形と同じに、スロットを使わず、同時に走らせる数だけに数える

### ステップの記録

- [ ] 契約（版 1）の出力に、任意の欄として、フローの名前と、ステップの一覧を足す。欄が無い出力（外部の委譲先）は、いまと同じに読む
- [ ] flywheel は、委譲の状態を読むたびに、ステップの一覧をストアへ写す。写すのは、ステップの名前・種類・何回目か・状態・結果・始まった時刻・終わった時刻・費用（額が上限額での計上かの印つき）・書いたモデル・使ったモデル
- [ ] ストアの書き出しと作り直し（`Export`・`Import`）に、ステップの記録を含める

### モデル

- [ ] フローの YAML の、claude を呼ぶステップに、使うモデルを書ける（任意）。書いたステップは、そのモデルを指定して claude を起動する。書かないステップは、いまと同じ（指定しない）
- [ ] claude を呼ぶステップが終わったとき、claude の結果が報告した、使ったモデルの名前を記録する
- [ ] S1 で移す 2 つのフローの定義には、モデルを書かない（中身を変えない）

### 画面

- [ ] タスクの詳細の画面の「委譲先の実行」の区画に、フローの名前と、ステップの一覧（ステップ・結果・時間・費用・モデル）と、費用の合計を出す
- [ ] ステップの記録が無い委譲（外部の委譲先・記録を持たない過去の実行）では、ステップの一覧を出さない（いまの表示のまま）

### 守り

- [ ] ステップが起動する claude の子には、委譲の子と同じ目印（`FLYWHEEL_DELEGATED_RUN`）を付ける。子からは、flywheel のコマンド（`flow` を含む）を実行できない
- [ ] ステップが起動する claude には、宣言の権限モード（`permission_mode`）を渡す
- [ ] flywheel のコマンドの一覧（`flywheel help`）には、`flow` を「内部向け（サイクルが呼ぶ）」と添えて出す。切り離して進める内部の入口は、一覧に出さない

### 文書と切り替え

- [ ] 設計書 §10 と、契約の仕様（`docs/features/m3-invoker-delegation.md`）に、`flow` の形と、契約の任意の欄を書く
- [ ] リポジトリの決まり（`CLAUDE.md`）の、パッケージの表と、本番の依存の上限を、この機能に合わせて直す
- [ ] Tom の flywheel のリポジトリを、組み込みのフローへ切り替える手順と、戻す手順を、この文書に書き足す

設計書の決定（D7・原則 P5・コンセプト）の書き換えと、用語集の語（フロー・ステップ・組み込みのフロー）は、決定そのものなので、この仕様と同じ PR で済ませてある（実装の範囲に入れない）。

## 非機能要件

- 動作環境: macOS と Linux。写した試験も、両方で通す（OS の差で飛ばす試験は、その事実と理由を PR の説明に書く）
- 検査の時間: 写した試験を足した後も、`go test -race -timeout 20m ./...` の制限の中に収める。収まらないときは、制限を上げずに、仕様への指摘として止まる
- 安全: 権限モードの閉集合（`default`・`acceptEdits`・`auto`）は広げない。`bypassPermissions` は、組み込みのフローでも渡せない

## 技術的な制約・方針

- 使用技術: Go（バックエンド）・React と TypeScript（画面）。本番の依存に `gopkg.in/yaml.v3` と `github.com/santhosh-tekuri/jsonschema/v6` を足す【決定 2026-11-24 オーナー】
- 変更対象:
  - 新しいパッケージ `internal/flow/` の配下（写した `workflow`・`engine`・`runstate`、契約の形の出力と切り離しの起動、埋め込む資材）
  - `internal/cli`（`flow` のコマンドの定義）・`internal/core`（宣言の形・起動のコマンドの組み立て・契約の出力の欄・ステップの記録）・`internal/core/internal/store`（マイグレーション）・`internal/invoker`（契約の出力の読み取り）・`internal/view`（API の型）・`web`（タスクの詳細）
  - 文書: `docs/architecture.md`・`docs/glossary.md`・`docs/features/m3-invoker-delegation.md`（契約の欄）・`CLAUDE.md`
- 既存コードとの関係:
  - core は、委譲先を「契約の状態の形」（`ContractStatus`）で読んでいる。組み込みのフローも同じ形で返すので、契約の状態を読む core の処理（完了の検証・反映・スーパーバイザー・画面）は変えない
  - 写したコードは、flywheel の lint（`golangci-lint`）と整形の決まりに合わせてよい。振る舞いを変える直しは、この仕様に書いたもの（置き場・引数の受け方・上書きを読まないこと・プラグインの場所の解決と版の確かめ・モデル・ステップの一覧の出力〔記録の畳み込みに、ステップの実行ごとの通し番号・書いたモデル・使ったモデルを持たせることを含む〕・子の目印）だけにする
  - 写した仕組みが読む環境変数の名前（`HARNESS_*`）は、S1 では変えない（つなぎのスクリプトとプラグインのスクリプトが読むため）。誰が設定するかは、下の「環境変数」の表のとおり
- 試験の環境: `flywheel flow` と、写した仕組みの受入基準は、写した試験と同じ仕組み（偽の `claude`・`git`・`gh` を `HARNESS_CLAUDE_BIN`・`HARNESS_GIT_BIN`・`HARNESS_GH_BIN` で差し替える。`claude-harness-run` は、偽の実行ファイルを `PATH` の先頭に置く）で、`make check` の中で確かめる。実物の GitHub とプラグインを使う確かめは、「実物で確かめること」の節だけ

- 一覧に出すのは、種類が `llm`・`command`・`workspace`・`pull-request` のステップ。振り分けだけのステップ（`select`）と、待ち（`gate`）は出さない（待ちは、いまと同じに、状態と「求められていること」に出る）
- 並びは、始まった順。同じ識別子のステップが 2 回以上あるときは、回ごとに別の行にし、一覧の中で 2 回目からは「（2 回目）」のように、何回目かを名前に添える（数えるのは画面。`attempt` の値は使わない）
- ステップの名前は、下の「ステップの名前」の表にあるものは日本語の名前と識別子を並べ（例: 「実装 implement」）、無いものは識別子だけを出す。表は、画面の語の対応表（`web/src/labels.ts`）に足す
- 結果は、`state` が `finished` のステップは `outcome` の値をそのまま出す。`running` は「実行中…」、`interrupted` は「中断」、`cancelled` は「取り消し」
- 時間は、終わったステップは掛かった時間、実行中のステップは始まってからの経過（「経過」を添える）。60 秒未満は「N 秒」、60 秒以上は「N 分」（分は切り捨て）
- 費用は、`cost_usd` が数のステップに「N.NN USD」（小数 2 桁）で出し、`null` は「—」。`cost_unknown` が真のステップは、額の後ろに「（上限額で計上）」を添える
- モデルは、`models_used` の名前を「、」でつないで出す。空なら「—」
- 合計は、`cost_usd` が数のステップの額の合計（`null` は足さない）を「合計 N.NN USD」で出す

API: 課題の詳細の応答（`GET /api/v1/workspaces/{name}/challenges/{id}`）の、タスクごとの `delegate`（`internal/view` の `TaskDelegate`）に、次の 2 つを足す。同じ型を使う CLI の `--json` の出力にも、同じ欄が出る。型は `internal/view` に置き、`go generate ./internal/view` で画面の型（`web/src/api/types.gen.ts`）を作り直す。`steps` には、すべての種類のステップを返す（`select`・`gate` を除くのは画面）。

| 欄 | 型 | 中身 |
|---|---|---|
| `flow` | 文字列か `null` | フローの名前（委譲の実行の記録の値。ステップの記録の有無に依らない）。記録が無ければ `null` |

## クリティカル設計決定

### 移す形: 写して、内側の境界は残す

- **採用案**: claude-harness の runtime のうち、下の「写す範囲」の表の部品を flywheel のリポジトリへ写し、flywheel 自身の別プロセスとして進める。core とのやりとりは、いまの契約の状態の形のまま残す【決定 2026-11-24 オーナー】。写した後は、flywheel の側の写しを flywheel の正本とし、claude-harness の側の直しは、要るものを選んで手で取り込む（自動では追わない）。写した元のコミットと、変えた点を、写した先の文書に記録する
- **理由**: 進める仕組みが記録を呼ぶ口は狭く、写しやすい。PR まわり（約 2,000 行）と、落ちたときの回収は、実測で詰めた端の場合の塊で、書き直すと同じ不具合を踏み直す。core は、契約の状態を読む所が 36 ファイルあり、形を変えないことで、そこを触らずに済む
- **代替案**: core の作りに合わせて書き直す（境界は無くなるが、いちばん大きく、踏み直しのおそれがある）／実行は外部のまま、記録だけ先に受ける（小さいが、フローを flywheel が持つ所に届かない）
- **影響範囲**: 新しいパッケージ `internal/flow/`。claude-harness のリポジトリは変えない

### core との境界: 自分のバイナリを、契約のコマンドとして呼ぶ

- **採用案**: `flow` の形の委譲先では、core が、契約のコマンド（始める・状態を読む・続ける・取り消す・反映の依頼）の引数の配列を、自分の実行ファイルの `flow` のコマンドとして組み立てる。起動は、いまの契約のコマンドの起動の口（`ContractClient`）をそのまま使う。core は `internal/flow/` を import しない（`internal/cli` だけが、`flow` のコマンドのために import する）。実行ファイルのパスは、`internal/cli` が core へ渡す
- **理由**: 契約のコマンドの起動・結果の読み取り・状態の振り分けは、`cli` の形で通しの試しまで済んでいる。同じ口を通せば、core の振る舞いは `cli` の形と同じになり、突き合わせて確かめられる。core が進める仕組みを import しない形なら、「ストアを開くのは core だけ」「core は外部コマンドの起動を持たない」の決まりも変わらない
- **代替案**: core の中から進める仕組みを直接呼ぶ（プロセスが 1 つ減るが、サイクルが止まるとフローも止まり、落ちたときの回収を作り直すことになる）
- **影響範囲**: `internal/core` の宣言の検査と、契約のコマンドの引数の組み立て。実装の形は次のとおりに固定する
  - `flow` の形の委譲先の `commands` は、読み込んだ後も空のままにする（実行ファイルのパスは、宣言を読む時点では分からないため、合成しない）
  - 「契約のコマンドを使う形か」（`cli` か `flow`）を答える関数を 1 つ置き、いま `form` が `cli` かで分かれている箇所と、`commands` の有無で分かれている箇所（反映の依頼の口があるかの判定を含む）を、その関数と、下の引数の組み立ての関数を通す形に直す
  - 契約のコマンドの引数の配列を作る所を 1 つにまとめ、`cli` の形は宣言の `commands` の差し込み、`flow` の形は下の「core が組み立てるコマンド」の表から作る
  - `flow` の形の、始める・続ける・反映の依頼のコマンドの引数は、そのコマンドの run の行を作った後に完成させる（`--delegated-run` に、その run の ID を入れるため）。いまのコードは、続けると反映の依頼で、引数を作ってから run の行を作る順になっているので、`flow` の形では、run の行を作る所が、得た run の ID を引数へ入れてから起動する形に直す。`cli` の形の引数（宣言の差し込み）と、起動の順は変えない。状態を読む・取り消すコマンドは `--delegated-run` を受けないので、順は変えない
  - 宣言の型に、操作の `flow` と、委譲先の `challenge_id_prefix` を足す。`required_facts` を書ける形に `flow` を足す
  - `flow` の形の委譲先は、宣言に書かなくても、反映の依頼の口を持つ。リポジトリの `reflect_connector` は、`flow` の形の委譲先を指せる

### プロセスの形と、落ちたときの回収

- **採用案**: 写した仕組みのまま。始めるコマンドは、実行を作った後、自分の実行ファイルを切り離して起動し直し（新しいセッション・標準入力なし）、進める側が始まったことを記録するまで待って戻る。進める側は、待ちか終わりで終わる。生きているかは、記録した PID と、プロセスの開始時刻の一致で見る。死んでいれば、次の状態の読みか続けるコマンドが、実行中のステップを中断として記録し、やり直す（`rerun`）か止める（`abort`）かの待ちにする。残った子は、プロセスの組ごと止める。切り離して起動し直す内部の入口は `flywheel flow __run-detached <実行の識別>`（コマンドの一覧に出さない）。進める側が 30 秒のうちに引き継がなければ、始めるコマンドは誤りで終わる（写した仕組みの値）
- **理由**: flywheel のサイクルは、有限のプロセスで、常駐を必須にしない（設計書の原則 P6）。フローがサイクルのプロセスの外で進む形は、いまの外部コマンドの形と同じで、サイクルが止まってもフローは進み、次のサイクルが状態を読める
- **代替案**: サイクルのプロセスの中で進める（上の「core との境界」の代替案と同じ理由で採らない）
- **影響範囲**: `internal/flow/`。flywheel の run の表の PID・heartbeat の仕組み（スキルを直接呼ぶ形の委譲のもの）は使わない

### 記録の正本: ファイルが正本、ストアに写し

- **採用案**: 進める仕組みは、実行ごとのフォルダの、1 行ずつ書き足す記録を正本にする（写した仕組みのまま）。置き場は、ワークスペースの `.flywheel/flow/runs/<実行の識別>/`。flywheel は、委譲の状態を読むたびに、契約の出力のステップの一覧をストアへ写し、画面と集計はストアを読む【決定 2026-11-24 オーナー】。埋め込んだ資材（定義・指示文・型・スクリプト）は、版ごとの置き場（ワークスペースの `.flywheel/flow/runtime/<版>/`。版は flywheel のバイナリのコミット）へ展開し、中身の印で確かめる。置き場は、コマンドの `--workspace` の値から直接決め、写した元が読んでいた環境変数（`HARNESS_STATE_DIR`・`HARNESS_DATA_DIR`・`XDG_STATE_HOME`・`XDG_DATA_HOME`）は読まない
- **理由**: 記録の口と「読んでから書くまでの排他」を作り直さずに済み、落ちたときの回収がそのまま効く。ストアに写しがあるので、画面と書き出しは、ほかの記録と同じ扱いにできる
- **代替案**: ストアを正本にする（正本が 1 つになるが、記録の口を作り直すことになり、S1 が大きくなる。後の区切りで移す道は残る）
- **影響範囲**: ストアを作り直したとき（`Import`）、ステップの履歴は戻るが、走っている途中の実行の続きは、実行のフォルダが無いと進められない。`.flywheel/flow/` は、いまの `.flywheel/runs/` と同じに、Git で追跡しない: ワークスペースを作るとき（`flywheel init`）の `.flywheel/.gitignore` に `flow/` の行を入れ、`flywheel flow start` は、`.flywheel/.gitignore` が在って `flow/` の行が無ければ足す（無いファイルは作らない。`internal/flow` は core を import できず、core が持つ正本の中身で作れないため。ワークスペースは `flywheel init` で `.gitignore` を持つ前提）

### DB スキーマ: ステップの記録の表（版 39）

- **採用案**: マイグレーション 1 本（版 39）で、次を足す。過去の行は書き換えない
  - 表 `contract_run_step`: 委譲の実行（`contract_run`）にぶら下がる、ステップ 1 回ぶんの行。列は、委譲の実行の ID・実行の中の通し番号・ステップの識別子・種類・何回目か・状態（`running`・`finished`・`cancelled`・`interrupted`）・結果・始まった時刻・終わった時刻・費用（USD の 100 万分の 1 を単位にした整数。無ければ NULL。ほかの費用の列と同じ単位）・費用が上限額での計上かの印・書いたモデル（無ければ NULL）・使ったモデル（JSON の配列の文字列）。委譲の実行の ID と通し番号の組は重ならない
  - `contract_run` の列 `flow`: フローの名前（無ければ NULL）
- **理由**: ステップは、委譲の実行 1 件の中の出来事で、委譲のコマンド 1 回ごとの記録（`run`）とは粒度が違う。写すたびに同じ行を上書きできるよう、実行の中の通し番号を鍵にする
- **代替案**: `contract_run` に JSON の 1 列で持つ（表は増えないが、ステップごとの費用・モデルの集計を SQL で書けない）
- **影響範囲**: `Export`・`Import`・`coretest.FillAllTables`・書き出しの表の一覧の試験。バイナリより新しいストアを開かない決まりは変えない

### 契約: 任意の欄を足す（版は 1 のまま）

- **採用案**: 契約の出力に、任意の欄 `flow`（文字列）と `steps`（配列）を足す。版は 1 のまま。`steps` の要素は、画面の API の `steps` と同じ欄に、実行の中の通し番号（`seq`。1 以上の整数）を足したもの
  - 読み取りは、いまの `facts` と同じに、契約の出力を読む所（`internal/invoker`）が形を確かめ、core の契約の状態の型に `flow` と `steps` を足して渡す
  - `steps` が無い・配列でない・要素のどれか 1 つでも形が合わない（必須の欄が無い・型が違う・`state` が 4 つの値の外・`seq` が 1 未満か重なる・`attempt` が 1 未満）ときは、`steps` の全体を「無い」として扱う（出力の全体は不正にしない。ほかの欄は、いまと同じに読む）
  - core は、契約の状態を記録するいまの処理と同じトランザクションの中で、その委譲の実行のステップの行を、出力の `steps` と同じ中身にする（委譲の実行の ID と `seq` を鍵に、足すか上書きし、出力に無い `seq` の行は消す）。`steps` が「無い」ときは、ステップの行に触らない
  - `flywheel flow` が `steps` を作る決まり: 対象は、実行のただ 1 つの単位（写した仕組みの `main`。S1 の 2 つのフローは、単位が 1 つ）の、全部の回りのステップの実行。並びと `seq` は、ステップが始まった記録（`step_started`）の、記録の通し番号。`kind` は、フローの定義から引く。`attempt`・`state`・`outcome`・時刻は、写した仕組みの記録の値をそのまま出す。`cost_usd` は、ステップが終わった記録の「実行の累計へ加えた額」（終わっていない・claude を呼ばないステップは `null`）で、合計は、契約の `cost_usd` と一致する。`cost_unknown` は、費用を得られず、渡した上限額を使ったものとして数えたときに真（写した仕組みの決まり）
- **理由**: 欄を任意にすれば、外部の委譲先（`cli` の形）の動きは変わらない。外部の委譲先が同じ欄を返せば、同じ記録と画面に乗る
- **代替案**: 版を 2 に上げる（外部の委譲先の宣言と実装を同時に直すことになる）
- **影響範囲**: `internal/invoker` の契約の出力の読み取り・core の検査・`docs/features/m3-invoker-delegation.md` の契約の節

### 外部システム連携: 呼ぶコマンド

- **採用案**: 組み込みのフローが呼ぶ外部のコマンドは、`claude`・`git`・`gh`・`bash`・`ps`・`pgrep`・`claude-harness-run`。呼び方（引数・標準入力・時間切れ・やり直し）は、写した仕組みのまま。足すのは 2 つだけ: (1) プラグインの場所の解決に `claude-harness-run --plugin-root` を使う（スクリプトの置き場は、その下の `scripts`、エージェントの定義は `agents`）(2) claude を呼ぶステップに `--model` を渡せる
- **理由**: 機械の部品（作業ツリー・CI 待ち・CI の起動・品質の検査）は、後の区切り（S4）で Go に書き直すと決めてある【決定 2026-11-24 オーナー】。S1 では、同じに動くことを確かめる範囲に、書き直しを混ぜない
- **代替案**: スクリプトを flywheel に写して埋め込む（同じスクリプトが 2 か所になる）／S1 から Go に書き直す（確かめる範囲に、新しく書いた動きが混ざる）
- **影響範囲**: 組み込みのフローを使うワークスペースでは、claude-harness のプラグインと、`claude-harness-run` が入っていることが前提になる。入っていなければ、フローを始めるときの誤りで分かる
- **環境変数**（写した仕組みが読むもの。名前は変えない）:

  | 名前 | 設定するもの | 値 |
  |---|---|---|
  | `HARNESS_SCRIPTS_DIR` | 進める仕組み（ステップの子へ渡す。写した仕組みのまま） | `claude-harness-run --plugin-root` の結果の下の `scripts` |
  | `HARNESS_RUN_DIR` | 進める仕組み（写した仕組みのまま） | 実行のフォルダ |
  | `HARNESS_PLUGIN_VERSION` | `flywheel flow`（切り離して進める側へ引き継ぐ） | プラグインの宣言から読んだ版 |
  | `HARNESS_CLAUDE_PERMISSION_MODE` | `flywheel flow`（切り離して進める側へ引き継ぐ） | `--permission-mode` で受けた値 |
  | `HARNESS_CLAUDE_BIN`・`HARNESS_GIT_BIN`・`HARNESS_GH_BIN` | 試験だけ | 偽の実行ファイル |
  | `HARNESS_STATE_DIR`・`HARNESS_DATA_DIR` | 読まない | — |

### プラグインの版の確かめ

- **採用案**: フローを始めるとき、`claude-harness-run --plugin-root` が返した場所の、プラグインの宣言（`.claude-plugin/plugin.json`）の版を読み、4.9.0 以上 6.0.0 未満でなければ、始めずに誤りで終わる。範囲は、写した元と同じ値を、flywheel のコードに定数で持つ
- **理由**: ステップの中の claude は、入っているプラグインのエージェントとスキルを使う。範囲の外の版では、ステップの指示文と噛み合わない
- **代替案**: 確かめない（版がずれたとき、ステップの途中の分かりにくい失敗になる）
- **影響範囲**: `internal/flow/`

### セキュリティ: 権限モードと、子の目印

- **採用案**: (1) ステップが起動する claude には、宣言の `permission_mode` を `--permission-mode` で渡す。値の閉集合は変えない。Tom の切り替えでは、いまと同じ動きになる値を書く（いまの外部コマンドの形は、権限モードを渡していない。同じになるのは `default`）(2) ステップが起動する claude の子の環境に `FLYWHEEL_DELEGATED_RUN` を付ける。`flywheel flow` のコマンドも、ほかのコマンドと同じに、この目印のある環境からは実行できない（いまの、コマンドの照合より前の検査を、そのまま使う）
  - 値の渡し方: core は、`flow start` と `flow resume` に、`--permission-mode <宣言の値>` と `--delegated-run <そのコマンドの run の ID>`（契約のコマンド 1 回ごとの run。例: `R-2494`）を必ず付ける。`flywheel flow` は、どちらかが無い・権限モードが 3 つの値の外のとき、使い方の誤りで終わる。状態を読む・取り消すコマンドは、claude を起動しないので、どちらも受けない
  - 切り離して進める側へは、権限モードを `HARNESS_CLAUDE_PERMISSION_MODE`、run の ID を flywheel の内部の環境変数で引き継ぐ。進める仕組みは、claude を起動するときだけ、子の環境に `FLYWHEEL_DELEGATED_RUN=<run の ID>` を足す。進める側のプロセス自身の環境と、つなぎのスクリプト・プラグインのスクリプトの環境には、目印を置かない（置くと、進める側が自分の起動で拒否される）
- **理由**: いまは、委譲先の子が `harness` を呼ぶことはできても、flywheel のコマンドは別の道具なので届かなかった。フローを flywheel のバイナリが進めるようになると、子が `flywheel flow resume` を呼べば、自分のレビュー待ちに自分で答えられてしまう。承認と回答の口へ子から届かない、という決まり（設計書 §9）を、組み込みのフローでも保つ
- **代替案**: 目印を付けない（子が、待ちへの答えと取り消しを自分で実行できる）
- **影響範囲**: `internal/flow/` の claude の起動。サイクルが `flywheel flow` を起動するときは、いまの契約のコマンドの起動と同じに、目印を外した環境で起動する

### モデル

- **採用案**: フローの YAML の、種類が `llm` のステップに、任意のキー `model` を足す。書いたステップは `--model <値>` を付けて claude を起動する。ほかの種類のステップに書いたら、定義の誤りにする。ステップが終わったとき、claude の結果の、モデルごとの使用の欄（`modelUsage`）の名前を、使ったモデルとして記録する。上書きで変えられる値には、S1 では足さない
- **理由**: モデルは、フローのステップごとに書くと決めてある【決定 2026-11-24 オーナー】。使ったモデルは、書いた値ではなく claude の報告から取ることで、書かなかったステップ（既定のモデル）と、エージェントの定義が決めたモデルも記録できる
- **代替案**: 計画を作る判断点がタスクごとにモデルを選ぶ（採らない。同じ決定）
- **影響範囲**: `internal/flow/` の定義の読み取りと検査・claude の起動・記録の型
- **実装の最初に確かめること**: エージェントの定義（`--agent`）がモデルを決めているステップで、`--model` がどちらを優先するかは未確認。実測して、ステップに書いたモデルが使われないなら、実装を止めて仕様への指摘にする

### 依存

- **採用案**: 本番の依存の上限を、標準ライブラリ・`modernc.org/sqlite`・`golang.org/x/term`・`gopkg.in/yaml.v3`・`github.com/santhosh-tekuri/jsonschema/v6` に広げる【決定 2026-11-24 オーナー】
- **理由**: どちらも Go だけで書かれ、バイナリ 1 つで配れる性質は変わらない。写した仕組みを変えずに済む
- **代替案**: YAML だけ足して型の検査を自前で書く／どちらも足さず、定義を JSON にする（どちらも、写した仕組みと試験に手が入る）
- **影響範囲**: `go.mod`・`CLAUDE.md`・依存の検査の試験

### アーキテクチャ決定

写す範囲（写す元は claude-harness の `runtime/`。パスは `runtime/` からの相対）:

| `internal/flow`（直下） | 始める・状態を読む・続ける・取り消す・切り離して進める、の入口と、契約の形の出力・プラグインの場所と版の確かめ | 上の 4 つ |

- `internal/flow/` の配下は、上の表に無い flywheel のパッケージ（`internal/core`・ストア・`internal/invoker`・`internal/server`・`internal/view`・`internal/adapters/*`・`internal/cli`）を import しない
- `internal/core`・`internal/invoker`・`internal/server`・`internal/view` は、`internal/flow/` を import しない
- `internal/cli` だけが `internal/flow` を import する（`flow` のコマンドの定義と、自分の実行ファイルのパスを core へ渡すこと）
- 依存の向きは、いまの検査（`go list` の依存関係の試験）に足して固定する

### IF / API

**委譲先の宣言（`flow` の形）**:

```json
{
  "id": "flywheel-flow",
  "form": "flow",
  "permission_mode": "default",
  "challenge_id_prefix": "tom-",
  "operations": [
    { "id": "impl", "flow": "ticket", "interactive": false, "child_may_decide": true, "artifacts": "pr" }
  ],
  "required_facts": { "self_review": ["complete"] }
}
```

- `commands` と `contract_version` は書けない（書いたら設定の誤り）
- `permission_mode` は、ほかの形と同じ 3 つの値（`default`・`acceptEdits`・`auto`）だけ
- `operations[].flow` は必須。S1 で書けるのは `ticket` だけ（ほかの値は設定の誤り）
- `challenge_id_prefix` は任意（既定は空）。書いてよいのは `flow` の形の委譲先だけ（ほかの形に書いたら設定の誤り）。フローへ渡す課題の識別の前に付く。統合ブランチの名前の鍵になるので、同じリポジトリを複数のワークスペースが使うときに、名前が重ならないようにするためのもの
- `required_facts` は、`cli` の形と同じ意味
- `flow` を書いてよいのは、`flow` の形の委譲先の操作だけ

**core が組み立てるコマンド**（`<自分>` は、自分の実行ファイルの絶対パス）:

| 契約のコマンド | 引数 |
|---|---|
| 始める | `<自分> flow start --workspace <ワークスペース> --permission-mode <宣言の値> --delegated-run <run の ID> --input issue=<番号> --input task_file=<パス> --input task_id=<ID> --input uses_integration=<true か false> --input challenge_id=<前置き＋課題の ID> <フローの名前>` |
| 状態を読む | `<自分> flow status --workspace <ワークスペース> <実行の識別>` |
| 続ける | `<自分> flow resume --workspace <ワークスペース> --permission-mode <宣言の値> --delegated-run <run の ID> [--input <選んだもの>] [--note <添え書き>] [--approved-ref <通した中身>] <実行の識別>` |
| 取り消す | `<自分> flow cancel --workspace <ワークスペース> <実行の識別>` |
| 反映の依頼 | `<自分> flow start --workspace <ワークスペース> --permission-mode <宣言の値> --delegated-run <run の ID> --input artifact_ref=<成果物> --input challenge_id=<前置き＋課題の ID> reflect` |

- `<run の ID>` は、そのコマンド 1 回の run の ID（flywheel の run。例: `R-2494`）。`<実行の識別>` は、`flow start` が返した契約の `run_id`（組み込みのフローの実行の識別）で、別のもの
- `challenge_id` は、前置きと課題の ID を、区切りを足さずにつないだもの（例: 前置き `tom-` と課題 `C-186` で `tom-C-186`）

- 値が空の入力（取り込み元の Issue が無い課題の `issue`）は、いまの外部コマンドの形と同じに、空のまま渡す
- 反映の依頼は、宣言に書かなくても、いつも組み込みの `reflect` のフローで進む（`flow` の形の委譲先は、どれも反映の依頼の口を持つ）
- コマンドの時間切れは、いまの契約のコマンドと同じ（`cli` の形と同じ値）
- レビュー待ち（`kind: review`）は、いつも受け付ける（外部コマンドの形の `--accept-kind review` に当たる）
- 作業ディレクトリは、`cli` の形と同じ（リポジトリの元のクローンか、作業用のクローン）

## やらないこと

- 外部の委譲先の形（`cli`・`plugin`）を外す（理由: 組み込みのフローに不具合が出たとき、宣言を戻すだけで元の形に帰れるようにする。外すかは、Tom で安定してから別の区切りで決める）
- フローを利用側で変える口（上書き）を、組み込みのフローで使えるようにする（理由: 写した仕組みには読み取りの処理が入っているが、どこに置いて誰が変えるかを決めていない。入口では受け付けない）
- 技術調査のフロー（理由: 後の区切り。フローを選ぶ仕組み〔S2〕の後に決める）
- 計画を作る判断点がコードを読めるようにする（flywheel#1212。理由: フローの移植とは別の点）
- 改修の提案の判断点が課題を自分で作ることの扱い（理由: 取り込みの決まりの話で、別に決める）
- 画面から、反映先へ入れる承認を受ける（理由: 承認の経路の決まり〔設計書 §9〕の話で、別に決める）
- 記録の正本をストアへ移す（理由: S1 は、写した仕組みを変えない。後の区切りで移す道は残る）
- 費用の集計の画面・コマンド（`flywheel metrics`）に、ステップごと・モデルごとの集計を足す（理由: 設計の見直しの区切り 5「時間と費用の集計」で作る。S1 は記録を持つ所まで）
- CLI のテキストの出力に、ステップの一覧を足す（理由: S1 で人が見る口は画面。`--json` の出力には、API と同じ型で出る）
- claude-harness のリポジトリの変更（理由: claude-harness は残す。写した後の追従は手で選ぶ）
- 写した仕組みの環境変数の名前（`HARNESS_*`）と、資材の中の語を、flywheel の語へ直す（理由: 同じに動くことを確かめる範囲に、名前の変更を混ぜない）
- 走っている途中の委譲を、外部コマンドの形から組み込みのフローへ移す（理由: 切り替えは、走っている委譲が 0 件のときに行う手順にする）
