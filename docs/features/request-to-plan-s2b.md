# 要求から計画まで — 委譲で仕様の下書きを作る（S2b-1）

この文書は、S2a が main に入った後、`docs/features/request-to-plan.md` へ畳む（S2a の節を「実装済み」に送り、この文書の節をその位置へ移す）。それまでは、S2b（S2b-1 と S2b-2）の仕様の正本としてここに置く。

## 概要

やりたいこと（要求）が課題になり、仕様の文書ができ、計画が承認されるまでの流れのうち、S2a は「仕様の下書きを flywheel の中（`.flywheel/specs/`）に置き、計画がリポジトリへ入れる」ところまでを定めた。下書きを作る道は、S2a では対話の欄だけだった。

S2b（委譲で下書きを作る）は、2 つの区切りに分ける（オーナーの決定 2026-11-26）。この文書が定めるのは、先の区切り（S2b-1）。**計画を作る判断点（J2）が、仕様の文書の追加・改修が要る課題を見分け、計画を作らずに「下書きづくり」へ回す。下書きづくりは、組み込みのフロー 1 本（書く → 3 つの観点で批評して直す）が、オーナーの承認なしで行い、下書きと残った問いを返して終わる。残った問いは、全部まとめてオーナーへ上げる。答えの後に、下書きと答えを渡してもう一度実行する。問いが無くなった下書きから、S2a の道で計画を作る**ところまでを定める。

後の区切り（S2b-2）は、スーパーバイザーが残った問いのうち答えられるものに先に答えることと、仕様の文書の本文を画面で開くこと。S2b-1 を実物で使い、下書きの質と費用を見てから形を決める。要点だけを、節「後続の区切り（S2b-2）で足すこと」に残す。

決定の正本は検討の Issue（flywheel#1266）の「決まったこと」の 12・14・15。S2a で入るもの（ストアの版 43・課題の置き換える元の文書の場所 `spec_base_path`・タスクの `lands_spec`・下書きの見分けと詳細の `spec_is_draft`・下書きを消す仕組み・`spec_draft_changed`）は、`docs/features/request-to-plan.md` の S2a の節を正とし、この文書は前提にする。

## 背景・目的

- S2a では、下書きを書けるのは対話の欄だけ。取り込んだ Issue から始まる課題は、オーナーが対話の欄で仕様を書くまで、仕様の文書なしで計画される。受入基準の網羅の検査（S1）が掛からないまま、複数のタスクに分かれる。
- claude-harness の仕様づくりのスキルは、対話で要件を聞く前提で、終わりに Issue を作るスキルを案内する。人のいない委譲の中では使えない（決定 12 の「flywheel に合わない手順で止まる」に当たる）。批評役（`spec-critic`）と修正役（`spec-fixer`）は、文書の場所と観点を渡せば単独で動く。
- オーナーの決定（決定 15）: 委譲の道は、組み込みのフローを 1 本足す。下書きを書く指示文は flywheel の側に置き、批評と直しはプラグインの批評役と修正役を flywheel の指示文から呼ぶ。フローは人を待たず、下書きと残った問いを返して終わる。
- オーナーの決定（決定 15）: 下書きづくりは承認なしで始める。歯止めは、1 回の上限額と、実行の回数の上限。費用は課題の予算に入れず、仕様づくりの費用に足す。
- オーナーの決定（決定 15）: 残った問いは、計画の論点の問いと同じ見た目と答え方にする（推奨と違う問いだけ答えれば済む）。いまの計画の論点の問いは、画面には問いと推奨を表示するだけで、推奨と違う答えは対話の欄かコマンドで受けている。下書きの問いも同じにする（オーナーの決定 2026-11-26）。
- 目的は、取り込んだ Issue から始まる課題でも、受入基準のそろった計画を、オーナーが仕様を書かずに受け取れるようにすること。

## ユーザーストーリー

オーナーとして、Issue を取り込んでサイクルを回したら、仕様の文書が要る課題では、下書きができた状態で計画を受け取りたい。自分が決めないと進まない問いだけを、選択肢と推奨つきでまとめて聞いてほしい。推奨のままでよければ、1 回の操作で先へ進めたい。下書きが気に入らなければ、同じファイルを対話の欄で直して、そのまま計画へ進めたい。

## 機能要件

この節は S2b-1 の要件。S1・S2a の作り（課題が仕様の文書の場所を持つ・core が受入基準を抜き出す・計画が下書きをリポジトリへ入れるタスクを持つ・課題が終わったら下書きを消す）は変えず、その上に足す。

### 計画を作る判断点が、下書きづくりへ回す

- [ ] 計画を作る判断点の判定の値に、「下書きづくりへ回す」（`needs_spec`）を足す。
- [ ] 判定が `needs_spec` の出力は、根に `spec_draft`（オブジェクト）を持つ。
- [ ] `spec_draft.repo` は、対象のリポジトリ（宣言にある名前を 1 つ）。
- [ ] `spec_draft.base_path` は、置き換える元の文書の場所（リポジトリの中の相対のパス。新しい文書なら `null`）。
- [ ] `spec_draft.reason` は、回す理由（2000 文字以内）。
- [ ] core は、`needs_spec` の出力を受けると、計画を登録せず、課題の状態を分類済のまま、下書きづくりの記録を状態 `pending` で作る。
- [ ] 回せる条件 1: 課題が、仕様の文書の場所を持たない。
- [ ] 回せる条件 2: 課題が、下書きづくりの記録を持たない（状態を問わない）。
- [ ] 回せる条件 3: 課題に、着手したタスク（状態が着手中・検証中・済み）が 1 件も無い。
- [ ] 回せる条件 4: 宣言に、対象にできるリポジトリが 1 つ以上ある。対象にできるのは、形が `flow` の委譲先を使い、スロットの形が作業ツリー（`slots.provider` が `worktree`）のリポジトリ（クローンの形は、作業用のクローンしか持たず、タスクのブランチの中身を読む危険があるため、対象にしない）。
- [ ] 計画の差し戻しの後の作り直しでも、4 つの条件を満たす課題は回せる（オーナーが差し戻しの理由で「仕様の文書を作ってから」と伝える道）。
- [ ] 回せない課題で `needs_spec` を選んだ出力は、不正な出力にする。理由の文（英語）に `spec draft not available` を含める。
- [ ] `spec_draft.repo` が、対象にできるリポジトリ（上の条件 4）でなければ、不正な出力にする。理由の文に `spec draft repo invalid` を含める。
- [ ] `spec_draft.base_path` が、S2a の置き換える元の文書の場所の検査（絶対パス・`..` の要素・500 文字を超える、を受け取らない）を通らなければ、不正な出力にする。理由の文に `spec draft base path invalid` を含める。
- [ ] 「足す」の形の呼び出しは、`needs_spec` を選べない（出力の型の判定の値に含めない）。
- [ ] 計画を作る判断点の入力に、区画「仕様の下書きづくり」を足す。
- [ ] 回せる課題の区画には、語「回せる」と、対象にできるリポジトリの名前の並びを書く。
- [ ] 回せない課題の区画には、語「回せない」と、理由を 1 つ書く。理由は、次の順で最初に当たったもの。①記録が `done`:「下書きづくりを済ませた」。②仕様の文書の場所を持つ:「仕様の文書がある」。③記録が `skipped`:「オーナーが仕様の文書なしで計画すると決めた」。④着手したタスクがある:「着手したタスクがある」。⑤対象にできるリポジトリが無い:「対象にできるリポジトリが無い」。
- [ ] 計画を作る判断点は、記録の状態が `pending`・`running`・`awaiting_owner` の課題を、対象から外す。外した課題は、サイクルの結果の「着手しなかった」の一覧に載せない（実行中の課題を外すいまの扱いと同じ）。
- [ ] 課題ごとに、下書きづくりへ回す・回さないを先に指定する口は作らない。

### 下書きの場所と、下書きづくりの記録

- [ ] 下書きの場所は core が決める。`.flywheel/specs/<課題の ID を小文字にしたもの>.md`（例: `.flywheel/specs/c-123.md`）。
- [ ] 下書きづくりの記録は、課題ごとに高々 1 件。
- [ ] 記録の状態は 5 つ。`pending`（実行待ち）・`running`（実行中）・`awaiting_owner`（オーナーの回答待ち）・`done`（済み）・`skipped`（省いた）。
- [ ] 記録の問いの一覧（`questions`）は、いま残っている問いだけを持つ。次の実行を始めるときに空にする。
- [ ] 記録の答えの一覧（`answers`）は、追記だけにする（消さない・書き換えない）。
- [ ] 課題の仕様の文書の場所（`spec_path`）を課題へ書くのは、記録を `done` にするのと同じ書き込みの中だけ（その前に書くと、ファイルがまだ無いあいだ、S1 の「仕様の文書を読めないときは、計画を作る判断点を呼ばず、着手しなかったにする〔理由 `spec_unreadable`〕」に当たるため）。
- [ ] 課題の置き換える元の文書の場所（`spec_base_path`）も、同じ書き込みの中で書く。

### 下書きづくりの途中で、オーナーが仕様の文書の場所を付けたとき

- [ ] 記録が `pending`・`running`・`awaiting_owner` の課題に、オーナーが仕様の文書の場所を付けたとき（`flywheel edit --spec`）、core は、その時点で記録を `skipped` にする。
- [ ] そのとき、課題の仕様の文書の場所は、オーナーが付けた値にする（記録の場所で上書きしない）。
- [ ] そのとき、開いている下書きづくりの保留を、回答なしで閉じ、課題を分類済へ戻す。
- [ ] そのとき、終わっていない下書きづくりの実行を取り消す。順は、取り消してから書く（取り下げの前の取り消しと同じ順）。
- [ ] 取り消しには、種類 `spec` の実行だけを取り消す口を core に足して使う（課題の契約の実行をすべて取り消すいまの口は使わない。タスクの実行や反映の依頼を巻き込まないため）。
- [ ] その口を呼ぶのは、記録が `pending`・`running`・`awaiting_owner` のときだけ。宣言と、契約のコマンドを起動する口は、CLI が組み立てて渡す（取り下げと同じ）。
- [ ] 取り消しに失敗したら、`edit` を断り、何も書かない（誤りのコードは `conflict`）。
- [ ] 取り消した実行の費用は、仕様づくりの費用に数える。
- [ ] そのとき、記録の下書きの場所が、付けた場所と違えば（正規化して比べる）、記録の場所のファイルを消す。同じなら消さない。
- [ ] 消せなかったときは、`edit` を成立させ、作業ログ（`spec_draft_cleanup_failed`）を残す。
- [ ] 記録が `done` の課題に、別の場所を付けたときも、同じ規則で記録の場所のファイルを消す（場所が違えば消す）。記録の状態は `done` のまま変えない。

### 下書きづくりを始める

- [ ] 下書きづくりは、オーナーの承認なしで始める。
- [ ] core は、サイクルの委譲の段で、次の 3 つを満たす課題の下書きづくりを始める: 記録が `pending`・課題の状態が分類済・終わっていない実行を持たない。
- [ ] 委譲の段は計画の段の後なので、回すと決まった同じサイクルの中で始まる。
- [ ] 取り下げた課題と、ほかの理由で人間対応待ちの課題では、記録が `pending` でも始めない。
- [ ] 下書きづくりの実行は、契約の形の実行の種類 `spec` として記録する（いまの `task`・`reflect` に並ぶ）。タスクにも計画にも結び付けない。
- [ ] 契約のコマンドの種類に、下書きづくりの開始（`spec`）を足す（いまの `start`・`status`・`resume`・`cancel`・`reflect` に並ぶ）。形が `flow` の委譲先の引数の組み立てに、この種類の分岐を足す。
- [ ] 形が `cli` の委譲先は、この種類のコマンドを持たない（宣言の `commands` にキーを足さない）。形が `cli` の委譲先のリポジトリは、対象にできるリポジトリに入らないので、起動の口には来ない。
- [ ] 開始のコマンドの引数は、この並びにする: `<実行ファイル> flow start --workspace <ワークスペース> --permission-mode <宣言の値> --delegated-run <実行の ID> --input draft_file=<名前> --input brief_file=<場所> --input brief_dir=<場所> --input repo_dir=<場所> [--input base_path=<場所>] --input challenge_id=<接頭辞つきの ID> --budget-usd <上限額> spec-draft`。
- [ ] `--permission-mode` と `--delegated-run` は、タスクの開始と同じに付ける。
- [ ] `challenge_id` は、反映の依頼と同じに、宣言の接頭辞を付けた課題の ID にする。
- [ ] 委譲先は、記録の対象のリポジトリが使う委譲先。
- [ ] フロー `spec-draft` は、タスクの操作の `flow` に書ける名前（`ticket`・`ticket-light`）には入れない。
- [ ] 実行の作業ディレクトリは、ワークスペースの下書きの置き場（`.flywheel/specs/`）。無ければ core が作る。
- [ ] 委譲先の許可の形（`permission_mode`）は検査しない。許可の形が `default` の委譲先では、ステップが下書きを書けず、実行が失敗して失敗の保留になる（許可の形ごとの成否は、実物で確かめる）。
- [ ] 作業ディレクトリは、開始のときに契約の実行の記録（`contract_run.work_dir`）へ書く。状態の確認と取り消しは、記録の値を使う（呼び出しごとに明示して渡さない）。
- [ ] 始める順は 4 つ: ①実行の行を作る（予算の枠 `spec`・タスクなし） → ②下書きづくりの文面のファイルを、その実行の記録の置き場（`.flywheel/runs/<実行の ID>/`）に書く → ③引数を組み立てる → ④開始のコマンドを呼ぶ（タスクの開始と同じ順）。
- [ ] 文面のファイルを書けなければ、開始のコマンドを呼ばず、開始の失敗として扱う。
- [ ] 文面のファイルの形（見出しと並び）は、「機能全体の設計」の「文面のファイルの形」のとおりにする。
- [ ] 文面のファイルに、課題の題名を書く。
- [ ] 文面のファイルに、課題の説明を書く。
- [ ] 文面のファイルに、取り込み元の Issue の指定（`<owner>/<name>#<番号>`）を書く（取り込み元を持つ課題だけ）。
- [ ] 文面のファイルに、記録の回す理由を書く。
- [ ] 文面のファイルに、置き換える元の文書の場所を書く（持つ記録だけ）。
- [ ] 文面のファイルに、これまでの問いと答えを、答えた者（答えの `by` の値）を添えて書く（答えの一覧を持つ記録だけ）。
- [ ] 入力 `draft_file` は、下書きのファイルの名前（作業ディレクトリから見た名前）。
- [ ] 入力 `brief_file` は、文面のファイルの場所。入力 `brief_dir` は、その置き場のフォルダ（フローが読める場所として足す）。
- [ ] 入力 `repo_dir` は、対象のリポジトリの元のクローンの場所（宣言の `slots.base`）。読むだけに使う。
- [ ] 作業用のクローンやスロットは払い出さず、空きも待たない。
- [ ] 下書きづくりの実行は、同時に走らせる数（`max_parallel_runs`）に数える（契約の実行のいまの数え方に、種類 `spec` を含める）。
- [ ] 同時に走らせる数の上限に達していれば、始めない。記録は `pending` のまま残し、次の回りか次のサイクルで始める。
- [ ] サイクルの費用の上限を超えるなら、始めない。記録は `pending` のまま残す。
- [ ] 始められなかった課題は、サイクルの結果の「着手しなかった」の一覧に載せない（一覧の要素はタスクを持つ形で、タスクの無い要素を新しく作らないため）。
- [ ] 始めると、記録を `running` にし、実行した回数を 1 増やし、問いの一覧を空にする。
- [ ] 1 つの課題の下書きづくりの記録は 1 件で、その記録の実行は 3 回まで。失敗で終わった実行も、開始が失敗した実行も数える。
- [ ] 開始のコマンドが失敗したとき（起動できない・出力が不正・終わった状態で返った）は、実行した回数に数え、失敗の保留にする。
- [ ] 記録が `running` なのに、終わっていない実行が無い課題を見つけたら、失敗の保留にする（行き止まりを作らない）。

### 1 回の上限額

- [ ] 1 回の上限額の既定の値は、core の定数（外のパッケージから読める名前 `SpecDraftDefaultBudgetUSD`）に置く。値は仮に 15 USD とし、実装の中で実物の実行を測って決め直す。
- [ ] フローの定義の `limits.budget_usd` は、core の定数と同じ値にする。一致は、両方を読める `internal/cli` の試験で固定する。
- [ ] 委譲先の宣言（形が `flow` のものだけ）に、任意のキー `spec_draft_budget_usd`（正の数）を足す。書いてあれば、既定の値の代わりに使う。
- [ ] エージェントの宣言の `max_run_budget_usd` は、下書きづくりの実行にも掛ける。1 回の上限額は、上の値と `max_run_budget_usd` の小さいほう。
- [ ] core は、決めた上限額を、契約の実行の記録の上限額に書き、開始のコマンドに `--budget-usd <額>` でいつも渡す。
- [ ] `flywheel flow start` の `--budget-usd`（正の数）は、フロー `spec-draft` のときだけ受け付ける（ほかのフローでは使い方の誤り）。渡した額が、その実行の `limits.budget_usd` になる。`flywheel help` の `flow start` の用法の行にも足す。
- [ ] 定義を利用側で変える口（`--override`）は、いまのまま受け付けない（いまも知らないフラグとして使い方の誤りになる。直しは要らない）。

### フロー `spec-draft`

- [ ] 組み込みのフローに、定義 `spec-draft` を足す。ステップは `write`・`critique` の 2 つで、どちらも claude を呼ぶ種類。
- [ ] ステップの種類は `llm` だけにする（並列のステップ・人を待つステップ・作業ツリーのステップ・PR のステップを持たない）。
- [ ] 2 つのステップは、読める場所（`add_dirs`）に、入力 `repo_dir` と `brief_dir` を持つ。
- [ ] ステップ `write` は、文面のファイル・取り込み元の Issue・対象のリポジトリのコードと文書を読み、下書きを全文で `draft_file` に書く。
- [ ] `write` は、置き換える元の文書があれば、その全文を写してから直す。
- [ ] `write` は、下書きがすでにあれば（2 回目から）、それを読んで直す（前の実行のセッションは引き継がない）。
- [ ] ステップ `critique` は、1 つのステップの中で、プラグインの批評役（`claude-harness:spec-critic`）を、3 つの観点（`acceptance-criteria-testability`・`internal-consistency`・`downstream-implementability`）で、同じ応答の中で 3 体並べて呼ぶ。
- [ ] `critique` は、批評役が `blocker` とした指摘を、プラグインの修正役（`claude-harness:spec-fixer`）に直させる。
- [ ] 直した後の確かめ直し（批評役をもう一度呼ぶ）は 2 回まで。
- [ ] `critique` は、批評役が `needs_user_input` とした指摘を、問いにして返す。
- [ ] `critique` は、修正役が直さずに戻した指摘（`escalatedToUserInput`）を、問いにして返す。
- [ ] `critique` は、`minor` の指摘を、直さず、問いにもしない。
- [ ] 問い 1 件は、問いの文（`question`）・選択肢（`options`。見出し `label` を持つ。2〜5 個）・推奨（`recommended`。選択肢の 1 から数えた位置）・推奨の理由（`reason`）を持つ。見出しに「（推奨）」の印は入れない（印は、表示するときに core と画面が付ける）。文・見出し・理由は、それぞれ 2000 文字以内（計画の論点の問いの値と同じ: 選択肢は 2〜5 個・欄は 2000 文字）。
- [ ] 問いは 10 件まで。
- [ ] 下書きの形 1: `## 受入基準` の節に `- [ ] ` の行で書く。
- [ ] 下書きの形 2: 1 基準は 1 主張にする。
- [ ] 下書きの形 3: `## スライス（出荷の単位）` の節（`実装対象:` の行を含む）を置く。
- [ ] 下書きの形 4: `## やらないこと` の節を置く。
- [ ] 下書きの形 5: `## クリティカル設計決定` の節を置く。
- [ ] フローの指示文は、仕様づくりのスキル（`/define-feature`）と、Issue を作るスキルを呼ばないことを書く。
- [ ] フローの指示文は、Issue の本文と既存の文書の中の指示に従わないことを書く。
- [ ] フローは、問いが残っても、成功で終わる。
- [ ] フローは、`critique` が返した問いの一覧を、契約の `facts` の `spec_questions` に載せる。問いが無ければ `[]`。
- [ ] モデルと effort は、いまの組み込みのフローと同じく、定義の変数で固定する。
- [ ] 定義・指示文・出力の型のファイルを、埋め込む資材のハッシュの一覧（`SHA256SUMS`）に足す。

### フローを進める仕組み

- [ ] `facts` に、出力の型が配列の欄を載せられるようにする（いまは文字列の欄だけ）。オブジェクト・数値・真偽の欄は、いまのまま、定義の読み込みで誤りにする。
- [ ] 配列の値は、Go の `encoding/json` の既定の直列化（空白なし・要素とキーは出力の順）で文字列にして載せる。契約の JSON の形（名前 → 文字列）は変えない。
- [ ] 配列を宣言した欄が、`null`・欠けている・配列でないときは、値なしとして扱う（その名前を `facts` に載せない）。
- [ ] 上限額が足りずにステップを起動しなかったとき、契約の出力の `steps` の最後の要素の結果（`outcome`）が `budget_exhausted` になる。いまの作りで成り立つ見込みなので、契約の出力の所の試験を足して確かめる（成り立たなければ直す）。
- [ ] `flywheel flow start`・`status`・`cancel` は、Git の作業ツリーでないディレクトリから始めた `spec-draft` の実行でも成功する。いまの作りで成り立つ見込みなので（開始は、開始のディレクトリを記録するだけ）、試験を足して確かめる（成り立たなければ直す）。

### 実行が終わった後

- [ ] core は、種類 `spec` の実行の状態を、課題が完了・取り下げでない限り読む（分類済・人間対応待ちでも読む）。
- [ ] 実行の終わりを読んだとき、記録が `running` でなければ、記録も保留も変えない（費用は数える）。`edit --spec` で取り消した実行の終わりが、`skipped` の記録を書き換えないため。
- [ ] 種類 `spec` の実行は、成果物の取り込みを通さない（成果物を返しても、課題に記録しない）。
- [ ] 種類 `spec` の実行は、レビュー待ちの取り込みを通さない。
- [ ] 種類 `spec` の実行は、保留の間の成功の印（`held_success`）を付けない。
- [ ] 種類 `spec` の実行は、`required_facts` の検査を通さない（満たさなかった回数も数えない）。
- [ ] 種類 `spec` の実行は、課題を検証中へ進める遷移を起こさない。
- [ ] 種類 `spec` の実行は、完了の検証の直し先に選ばない。
- [ ] 種類 `spec` の実行は、反映の段が課題の実行として読む対象に入れない。
- [ ] 種類 `spec` の実行は、統合先を使う課題のタスクの終わりとして扱わない。
- [ ] 種類 `spec` の実行は、完了の検証が読む「最後の委譲の実行」に入れない。
- [ ] 上の 9 つのほかにも、契約の実行の種類を見る箇所（種類が反映の依頼でなければタスクとして扱う枝を含む）を、実装のときに全部洗い出し、種類 `spec` の扱いを決める。洗い出した箇所と扱いを、PR の説明に書く。
- [ ] 種類 `spec` の実行が待ち（`waiting`）で返ったら、core はその実行を取り消し、失敗として扱う。
- [ ] 成功で終わり、問いが 0 件で、下書きを S1 の読み取りで読めて、受入基準が 1 件以上あるとき、課題の `spec_path`（下書きの場所）と `spec_base_path`（記録の置き換える元。無ければ書かない）を書き、記録を `done` にする。
- [ ] 記録が `done` になった課題は、次に計画を作る判断点の対象になり、S2a の道（下書きから計画を作る）を通る。
- [ ] 成功で終わったが、`facts` に `spec_questions` が無いときは、失敗として扱う。
- [ ] 成功で終わったが、`spec_questions` が JSON の配列でないときは、失敗として扱う。
- [ ] 成功で終わったが、問いの要素が形に合わない（文・理由が空・選択肢が 2〜5 個でない・推奨が選択肢の範囲の外・文か見出しか理由が 2000 文字を超える）ときは、失敗として扱う。
- [ ] 成功で終わったが、問いが 10 件を超えるときは、失敗として扱う。
- [ ] 成功で終わったが、下書きを読めないときは、問いの有無によらず、失敗として扱う。
- [ ] 成功で終わり、問いが 0 件で、下書きの受入基準が 0 件のときは、失敗として扱う。
- [ ] 成功で終わり、問いが 1 件以上あり、実行した回数が 3 未満のとき、core は問いを記録の問いの一覧に入れ、問いの保留にする（下の節）。
- [ ] 成功で終わり、問いが 1 件以上あり、実行した回数が 3 のとき、core は問いを記録に入れて、回数の上限の保留にする。
- [ ] 失敗で終わったとき（上の「失敗として扱う」を含む）、失敗の保留にする。
- [ ] 取り消しで終わったとき（オーナーの `edit --spec`・取り下げによる取り消しを除く）、失敗の保留にする。
- [ ] 失敗の保留にしても、下書きのファイルは残す。
- [ ] 上限額に当たったとする規則: 実行が失敗か取り消しで終わり、契約の出力の `steps` の最後の要素の結果が `budget_exhausted` であるか、実行の費用が記録した上限額以上である。
- [ ] 上限額に当たった実行の失敗の保留の問いの文に、語「上限額」と、使った額（数と `USD`。例: 費用 3.2 USD なら `3.2 USD`）を書く。
- [ ] 保留にするとき、記録を `awaiting_owner` にし、課題を人間対応待ちへ進める。保留は課題を止める保留で、戻り先は分類済。

### 下書きづくりの保留を作る

- [ ] 下書きづくりの保留の理由の値は 3 つ。下書きの問い（`spec_question`）・下書きづくりの失敗（`spec_failed`）・下書きづくりの回数の上限（`spec_attempt_limit`）。
- [ ] 保留の理由は、下書きづくりの記録に持つ（`spec_draft.hold_reason`。保留を作る書き込みの中で、`hold_id` と一緒に書く。保留が閉じたら、どちらも空にする）。
- [ ] 止まり方の閉集合には、値を足さない。下書きづくりの保留は、止まり方を渡さずに作る（止まり方の無い保留は、スーパーバイザーを呼ばず、はじめからオーナーの回答待ちになる。いまの作り）。
- [ ] 保留の種類の閉集合（`human`・`parent_direct`）にも、値を足さない。下書きづくりの保留の種類は `human`。
- [ ] 保留を作る口（理由・問いの文・選択肢を組み立てて、保留と記録を 1 つの書き込みで書く）は 1 つにし、起動の失敗・実行の終わり・行き止まりの検出のどこからも、それを呼ぶ。
- [ ] 問いが残ったとき、残った問いの全部を 1 つの保留にまとめる（問いの保留。理由 `spec_question`）。
- [ ] 保留は、課題を止める保留にする。戻り先は分類済。
- [ ] 保留を作ると、記録を `awaiting_owner` にし、課題を人間対応待ちへ進める。
- [ ] 記録の下書きのファイルを消す共通の処理（リンクをたどった先が置き場の下にあることの検査・ファイルが無ければ何もしない・消せなければ作業ログ `spec_draft_cleanup_failed`）を 1 つ置く。`skip`・`edit --spec`・取り下げは、それを呼ぶ。

### 保留への答え方

- [ ] 下書きづくりの保留は、選択肢つきの問いにし、識別の無い回答を断る。どの保留か（問い・失敗・回数の上限）は、記録の保留の理由で見分ける。
- [ ] 選択肢の識別は 4 つ。`answer`（問いに答えて、もう一度実行する）・`proceed`（いまの下書きで計画へ進む）・`retry`（やり直す）・`skip`（仕様の文書なしで計画する）。
- [ ] 問いの保留（`spec_question`）の選択肢は、`answer`・`proceed`・`skip`。
- [ ] 回数の上限の保留（`spec_attempt_limit`）の選択肢は、`proceed`・`skip`。
- [ ] 失敗の保留（`spec_failed`）の選択肢は、実行した回数が 3 未満なら `retry`・`proceed`・`skip`、3 なら `proceed`・`skip`。
- [ ] 問いの保留と回数の上限の保留の問いの文に、残った問いを番号つき（Q1 から。記録の問いの一覧の並びの順）で並べる。問いごとに、選択肢・推奨・推奨の理由を書く。推奨の選択肢は、見出しの後ろに「（推奨）」を付けて示す（表示だけ。記録の `label` には含めない）。
- [ ] 問いの文の大きさに上限は足さない（問いは 10 件まで・欄は 2000 文字までなので、それが上限になる）。
- [ ] core の回答の入力に、問いごとの答えの並び（問いの番号と、選択肢の番号か文）を足す。
- [ ] 問いごとの答えは、問いの保留への `answer` のときだけ受ける。ほかの保留・ほかの選択肢と一緒に渡すと、検査の誤りにする。
- [ ] 答えを渡さなかった問いは、推奨を答えとして記録する。
- [ ] 回答の前に保留を読む呼び出し（回答の確かめ）は、答える保留が下書きづくりの保留なら、その保留の理由と、残った問いを返す。
- [ ] CLI は、`--option` と `--choice`・`--text` が同時に付いたら、回答の確かめを呼び、答える保留の理由が `spec_question` なら先へ進める（`--hold` の併用も許す）。`spec_question` でなければ（下書きづくりでない保留・失敗の保留・回数の上限の保留）、いまと同じ使い方の誤り（`usage_error`）にする。
- [ ] 理由が `spec_question` の保留への、`answer` でない選択肢と `--choice`・`--text` の併用は、core が検査の誤り（`validation_failed`）にする。
- [ ] 無い問いの番号・無い選択肢の番号・同じ問いへの 2 つの答えは、core が検査の誤り（`validation_failed`）にする。
- [ ] `--choice`・`--text` だけで `--option` が無く、課題が計画の承認待ちでなく、開いている保留が下書きの問いの保留のときは、使い方の誤り（`usage_error`）にし、`--option answer` を付けるよう文で案内する。
- [ ] `--choice`・`--text` と、`--answer`・`--replan` の併用は、いまのまま使い方の誤りにする。
- [ ] 画面の保留の回答の口の本文は変えない（選択肢を選ぶだけ）。画面から `answer` を選ぶと、全部の問いに推奨を答えたことになる。
- [ ] 画面の `answer` のボタンの見出しは「推奨のまま進める」にする（保留の選択肢の見出し）。
- [ ] 推奨と違う答えは、対話の欄かコマンドで受ける。画面には、その案内を出す（計画の承認の画面の案内と同じ仕組み: `web/src/guidance.json` の、場面の名前で引く案内。場面の名前は `spec_question`、案内の識別は `answer-spec-choice`、文は `flywheel answer <C-ID> --workspace <パス> --option answer --choice <問いの番号>=<選択肢の番号>`）。`--hold` の出し分けは、いまの `answer-choice` と同じ扱いにする（`--hold` つきの案内を別に足さない）。
- [ ] `answer` が成立すると、答えを記録の答えの一覧に答えた者 `owner` で足し、記録を `pending` にし、課題を分類済へ戻す。
- [ ] `proceed` は、書き込みの前（回答の確かめの段）で下書きを読む。読めないか受入基準が 0 件なら、回答を検査の誤りで断り、保留は開いたまま残す。
- [ ] `proceed` が成立すると、課題の `spec_path` を書き、記録を `done` にし、課題を分類済へ戻す。
- [ ] `proceed` が成立すると、課題の `spec_base_path` に、記録の置き換える元を書く（無ければ書かない）。
- [ ] オーナーが対話の欄で下書きを引き取るときは、同じ下書きのファイルを直してから、`proceed` で答える（新しい口は足さない）。
- [ ] `retry` が成立すると、記録を `pending` にし、課題を分類済へ戻す。
- [ ] `skip` が成立すると、記録を `skipped` にし、課題を分類済へ戻す。その課題は、仕様の文書なしで計画される。
- [ ] `skip` の書き込みが成立した後に、下書きのファイルを消す。消せなくても `skip` は成立させ、作業ログ（`spec_draft_cleanup_failed`）を残す（取り下げと同じ規則）。
- [ ] 選択肢を選ぶ回答は、CLI・対話の欄・画面のボタンのどれからでもできる。問いごとの答えを付けられるのは、CLI と対話の欄。

### 費用

- [ ] 枠 `spec` の実行の費用は、課題が使った額（予算の枠・上限・見込みの計算）に数えない。

### 記録と表示

- [ ] 同じ所に、問いごとの推奨の理由と、下書きの場所（文字で）を出す。
- [ ] 同じ所に、問いの保留では、推奨と違う答えの案内（上の `answer-spec-choice`）を出す。
- [ ] 課題の詳細の画面の、下書きづくりの保留の所に、その保留の選択肢のボタンを出す。

### 後片付け

- [ ] 記録が `pending`・`running`・`awaiting_owner` の課題が取り下げになったとき、core は記録の下書きのファイルを消す（課題の `spec_path` がまだ無いので、S2a の消す仕組みには掛からない）。
- [ ] 取り下げでは、記録の状態を変えない（取り下げた課題では始めないので、`pending` のまま残っても動かない）。

- [ ] 記録が `done` の課題の下書きは、S2a の仕組みで消す（この区切りでは足さない）。

## 非機能要件

- セキュリティ: フローのステップは、取り込み元の Issue の本文（信頼できないデータ）を読む。作業ディレクトリを下書きの置き場にして、書き込める範囲を狭める。対象のリポジトリと文面の置き場は、読める場所として足すだけにする。core は、フローが返した問いの形を検査してから使う。
- 費用: 回す課題では、計画を作る判断点が 1 回増える（回す判定の 1 回と、下書きができた後の計画の 1 回）。スーパーバイザーの呼び出しは増やさない。フローは、1 つの課題で 3 回まで、1 回ごとに上限額まで。
- 後方互換: 仕様の文書の場所を持つ課題・形が `flow` の委譲先を持たないワークスペース・この区切りより前に承認した計画の振る舞いは変えない。`facts` に文字列の欄だけを載せるいまのフローの出力は変えない。スーパーバイザーの判断点（入力・出力の型・指示文）と、保留の回答の口の本文は変えない。

## 技術的な制約・方針

- 変更対象:
  - `internal/core`: 判定の値と出力の型・検査（`judgment_output.go`・`judgment_j2.go`）。計画を作る判断点の入力の区画と対象の除外。下書きづくりの記録。契約のコマンドの種類と引数（`contract_command.go`）。契約の実行の種類 `spec` の起動・状態の確認・終わった後の扱い（`contract_delegate.go`・`contract_delegate_after.go`。種類 `spec` の行のコマンドの引数の組み立ては、取り込み元を読まない道〔反映の依頼と同じ〕へ寄せる）。種類で分かれている所（反映の依頼の受け取り・反映の段が読む実行・統合先のタスクの終わり・完了の検証の直し先と、完了の検証が読む最後の委譲の実行）に、種類 `spec` を通さない枝。下書きづくりの保留を作る口と、記録の保留の理由（止まり方の閉集合と `supervisor_kinds.go` は変えない）。記録の下書きを消す共通の処理。種類 `spec` の実行だけを取り消す口。保留の選択肢と、回答の入力の型・処理（`approval.go`）。課題を直す処理（仕様の文書の場所を付けたとき）。予算の枠 `spec` と仕様づくりの費用（`run_store.go`・`chat_link.go`）。委譲先の宣言のキー（`connectors_declaration.go`）。上限額の定数。作業ログの種類 3 つ。取り下げの後片付け。書き出しと読み込み。
  - `internal/core/internal/store`: マイグレーション 1 本。
  - `internal/flow/workflow`・`internal/flow/runstate`: `facts` の欄の型の検査と、値の畳み込み。
  - `internal/flow`・`internal/cli`: `flow start` の `--budget-usd`。上限額の定数と定義の一致の試験（`internal/cli`）。
  - `internal/flow/assets`: 定義 `spec-draft.yaml`・指示文 `prompts/spec-draft-write.md`・`prompts/spec-draft-critique.md`・出力の型 `schemas/spec-draft-write.json`・`schemas/spec-draft-critique.json`・`SHA256SUMS`。
  - `internal/invoker`: `prompts/j2.md`・上限（`prompts.go`）。
  - `internal/cli`: `answer` の引数の組み合わせ（`approval.go`）、`edit --spec` の前の取り消し、`show`・`status` の出力。
  - `internal/view`・`web/src`: 詳細の値・課題の詳細の画面の保留の表示・案内（`web/src/guidance.json`）。`internal/server` は変えない（課題を直す口はサーバに無く、保留の回答の口の本文も変えない）。型の生成物（`web/src/api/types.gen.ts`）は、`internal/view` を変えたチケットが、main に入る順で作り直す（後から入るチケットが作り直す）。
- 起動の経路は、反映の依頼の起動（タスクも計画も無しで契約の実行を始める）を手本にする。違いは 4 つ。承認済みの操作を確かめない・作業ディレクトリを下書きの置き場にする・予算の枠が `spec`・実行の行を作ってから文面のファイルを書いて引数を組み立てる（順はタスクの開始と同じ。文面の置き場が実行の ID で決まるため）。
- 契約の実行の状態を読む問い合わせは、いまは種類 `task` と、条件つきの `reflect` だけを拾う。種類 `spec` を、課題が完了・取り下げでない限り拾うようにする。
- フローは人を待つステップを持たないので、待ちで返ることは起きない前提。起きたら失敗として扱う（上の要件）。
- 画面の案内は、いまある案内の仕組み（案内の文と、CLI のコマンド・フラグの定義との突き合わせの試験）に乗せる。案内に書くフラグ（`workspace`・`option`・`choice`）は、CLI の定義にあるものだけ。
- 保留の問いの番号と、記録の問いの一覧の対応は、保留を作ったときの並びで決まる。回答の書き込みの中で、保留が確かめたときから変わっていないこと（いまある保留の照合）を確かめてから、番号で一覧を引く。
- `proceed` の下書きの読み取りは、回答の確かめの段（書き込みの前）で行う。書き込みの中では、ファイルを読み直さない。確かめから書き込みまでの間にファイルが変わっても、`proceed` は成立する（次の計画の段が、S1 の読み取りで読めなければ、着手しなかったにする）。
- `edit --spec` で実行を取り消すには、契約のコマンドを呼ぶ口が要る。いまの `edit` は欄を直すだけで、宣言も起動の口も持たない。取り下げと同じく、CLI が宣言と起動の口を組み立て、先に取り消しを行ってから、core の書き込みを呼ぶ。記録が途中（`pending`・`running`・`awaiting_owner`）でない課題の `edit` は、いまのまま（宣言を読まない）。
- 計画を作る判断点の指示文には、禁止語の検査（出力の閉集合の値・コマンドの名前・設定のキーを書かない）がいまのまま効く。`needs_spec` は指示文に書かず、「下書きづくりへ回す」と書く。`spec_draft` は出力の型の項目の名前として書く。
- 指示文の受入基準の「書かれている」は、S1・S2a と同じく、かぎ括弧か `` ` `` で挙げた語が指示文にそのまま現れることで確かめる。フローの指示文も同じ。
- フローの定義の受入基準は、定義を読み込む試験（読み込みの検査を通ること・ステップの並び・遷移・上限の値）で確かめる。批評役と修正役を実際に呼べることは、実物でしか確かめられないので、要人間判定に置く。
- プラグインの版の範囲（4.9.0 以上 6.0.0 未満）は変えない。批評役と修正役は 5.0.2〜5.3.0 に在ることを確かめた。エージェントが無い版では、ステップが失敗し、失敗の保留になる。
- 修正役は、`## クリティカル設計決定` の節を直さずに戻す。戻った指摘は、問いになる（フローの指示文が、節の中身を自分で直さないことを書く）。
- ストアの版は、S2a の版（43）の次（並べて進めているほかの区切りが先に版を使ったら、その次）。
- 上限額の既定の値（仮に 15 USD）と、モデル・effort の値は、試し用のワークスペースで実物を測って決める。測る前に main へ入れない。

## 画面・API設計

- 試作は作らない。画面に足すのは、保留の所の問いの一覧（計画の論点の問いの部品。表示だけ）・推奨の理由と下書きの場所の文字・案内の 1 行・選択肢のボタン（いまの保留のボタン）で、新しい入力も新しい配置も作らない。見た目の作り込みは後の区切り。
- `flywheel answer <課題> --option answer [--choice <問いの番号>=<選択肢の番号>]... [--text <問いの番号>=<文>]... [--hold <保留>]`・`--option proceed`・`--option retry`・`--option skip`。
- 保留の回答の口の本文は、いまのまま `{"check": …, "option": …}`。
- 保留の選択肢の見出し: `answer` は「推奨のまま進める」、`proceed` は「いまの下書きで計画へ進む」、`retry` は「やり直す」、`skip` は「仕様の文書なしで計画する」。
- 画面の要素の目印: 保留の問いの一覧は `data-testid="spec-questions"`、案内は `data-testid="spec-answer-guide"`。
- 推奨の印: 保留の問いの文でも画面でも、推奨の選択肢の見出しの後ろに「（推奨）」を付ける。表示のときに付けるだけで、記録の `label` には含めない。
- 画面は、課題の詳細の `spec_draft.hold_id` と同じ ID の保留を、下書きづくりの保留として扱い、`spec_draft.hold_reason` で出し分ける（案内を出すのは `spec_question` のときだけ）。
- 問いの保留の問いの文の例:

```text
仕様の下書きに、決めないと進まない問いが 2 件残りました。下書き: .flywheel/specs/c-123.md

Q1. 取り消しは、実行中の処理にも効かせるか
  1. 実行中にも効かせる（推奨）
  2. 待ちの処理だけ
  推奨の理由: Issue の本文が「すぐ止めたい」と書いているため

Q2. …
```

## クリティカル設計決定

委譲の道をフロー 1 本にすること・批評と直しにプラグインの批評役と修正役を使うこと・フローが人を待たずに問いを返すこと・問いの見た目と答え方を計画の論点の問いと同じにすること・承認なしで始めて上限額と回数で歯止めを掛けること・費用を仕様づくりの費用に数えること・回す基準・S2b を 2 つの区切りに分けることは、案を比べたうえでオーナーが決めた（2026-11-26。flywheel#1266 の決定 15）。そのほかは、オーケストレーターの案（この仕様の PR で確かめてもらう）。

### 回す所: 計画を作る判断点の判定の値を 1 つ足す

- **採用案**: 計画を作る判断点の判定に `needs_spec` を足し、core が計画を登録せずに下書きづくりの記録を作る。回せるかは core が決めて入力に書き、回せない課題での選択は不正な出力にする。差し戻しの後の作り直しでも、着手したタスクが無ければ回せる。
- **理由**: 仕様の文書が要るかは、課題の大きさと、リポジトリの文書との関係を見ないと決まらない。それを読んでいるのは計画を作る判断点。判断点を増やさずに済む。下書きづくりの記録は 1 つの課題で 1 件だけなので、回す判定が繰り返されない（実行は 3 回まで）。着手したタスクがある課題を外すのは、済んだ作業の後から仕様を作ると、計画を登録しないまま課題が止まるため。
- **代替案**:
  1. 分類の判断点（J1）で見分ける。分類はコードを読まないので、既存の文書が受け持つ振る舞いかを見分けられない。
  2. 課題ごとにオーナーが先に指定する。オーナーの決定で採らない（変えたいときは差し戻しで伝える）。
- **残る危うさ**: 回す課題では、計画を作る判断点が 2 回走る。1 回目は計画を書かずに終わるので、費用は計画 1 回より小さい見込み（実物で測る）。
- **影響範囲**: 判定の値・出力の型・入力の区画・対象の選び方・指示文。

### 起動の形: 契約の実行の種類を足し、委譲の段で始める

- **採用案**: 契約の実行の種類に `spec` を足す。タスクも計画も持たずに、反映の依頼と同じ形で始める。始めるのは、サイクルの委譲の段（契約の実行を始めて、状態を読む段）。新しい段は足さない。種類 `spec` の実行は、タスクと反映の依頼の専用の経路を通さない。
- **理由**: 実行の記録・費用・ステップの進み・取り消しが、いまの契約の実行の仕組みにそのまま乗る。委譲の段は計画の段の後なので、回すと決まった同じ回りで始められる。段の閉集合（サイクルの結果の出力・画面の進みの表示）を変えずに済む。
- **代替案**:
  1. 計画の段の前に「下書きづくりの段」を足す。回すと決まった回りでは始められず、次の回りになる。段の閉集合と、段ごとの出力の形が増える。
  2. タスクを 1 件作って、いまのタスクの委譲に乗せる。計画の承認が要り、「承認なしで始める」に合わない。タスクの成果物（PR）が無いので、完了の検証の形にも合わない。
- **残る危うさ**: 契約の実行の種類で分かれている所は複数ある（種類が反映の依頼でなければタスクとして扱う枝）。1 つでも直し漏らすと、下書きづくりの実行がタスクの経路へ混ざる。受入基準で、成果物・レビュー待ち・検証中への遷移が起きないことを確かめる。
- **影響範囲**: 契約のコマンドの種類・実行の種類・起動・状態の確認の問い合わせ・終わった後の扱い。

### 作業ディレクトリ: 下書きの置き場にする

- **採用案**: フローの作業ディレクトリを `.flywheel/specs/` にする。対象のリポジトリの元のクローン（作業ツリーの形のリポジトリの `slots.base`）と、文面の置き場は、読める場所として足す（定義の `add_dirs` が入力を参照する）。
- **理由**: ステップは、信頼できない Issue の本文を読みながらファイルを書く。編集を自動で通す許可の形では、書き込める範囲が作業ディレクトリで決まるので、ワークスペースの全体（宣言・ストア・記憶）ではなく、下書きの置き場だけにできる。クローンを作業ディレクトリにしないので、作業用のクローンの空きを待たない。フローの開始は、開始のディレクトリを記録するだけで、Git の根であることを求めない。
- **代替案**:
  1. ワークスペースを作業ディレクトリにする。宣言や記憶を書き換えられる範囲に入れてしまう。
  2. 対象のリポジトリのクローンを作業ディレクトリにし、下書きの置き場を足す。足した場所へ書けるかは許可の形に依り、クローンに余計なファイルを書く余地が残る。
- **残る危うさ**: 許可の形が `auto` の委譲先では、範囲が狭まるとは限らない。許可の形が `default` の委譲先では、下書きを書けない（失敗の保留になる）。作業ディレクトリがリポジトリの根でないことで、実行エンジンの設定の読み方が変わらないかは、実物で確かめる（要人間判定）。確かめに落ちたら、代替案 1 に替える。
- **影響範囲**: 起動の作業ディレクトリと、その記録。フローの定義。

### 結果の返し方: 問いの一覧を `facts` に JSON の文字列で載せる

- **採用案**: フローを進める仕組みを、`facts` に配列の欄を JSON の文字列にして載せられるように広げる。フローは `spec_questions` の 1 つだけを載せる。問いが残ったかどうかは、配列が空かどうかで決まる。
- **理由**: 契約の JSON の形（名前 → 文字列）を変えないので、core と委譲先の境界が動かない。ステップの出力の型で、問いの形を先に検査できる。結果の種類を別の値で持たないので、2 つの値の食い違いが起きない。使うのは配列だけなので、オブジェクトは足さない。
- **代替案**:
  1. 出力の型の欄を文字列にして、ステップに JSON を文字列で書かせる。型の検査が効かず、壊れた JSON が core まで届く。
  2. フローが、問いをファイルに書く。置き場に下書き以外のファイルが増え、消す対象が増える。
  3. 契約に新しい項目を足す。契約の版が変わる。
- **影響範囲**: `internal/flow/workflow` の検査・`internal/flow/runstate` の畳み込み・core の読み取り。

### 問いの振り分け: この区切りでは全部をオーナーへ上げ、答えは記録にためる（オーナーの決定 2026-11-26）

- **採用案**: 問いが残ったら、全部を 1 つの保留にまとめてオーナーへ上げる。答えは下書きづくりの記録にためて、次の実行へ文面のファイルで渡す。スーパーバイザーが先に答える形は、後の区切り（S2b-2）で足す。
- **理由**: フローは終わっているので、答えを返す相手の実行が無い。記録にためれば、後でスーパーバイザーの答えを足しても、同じ形で次の実行へ渡せる。下書きの質と、どんな問いが残るかを実物で見てから、スーパーバイザーに任せる範囲を決められる。スーパーバイザーの型と指示文に触らないので、区切りが小さくなる。
- **代替案**: 最初からスーパーバイザーを通す。問いごとに答える・残す、の出力の型の直しと、専用の検査が要り、実物を見る前に形を決めることになる。
- **残る危うさ**: 文書・記憶・コードで答えられる問いも、オーナーへ届く。推奨のままなら 1 回の操作で進められるので、手間は選ぶだけで済む。
- **影響範囲**: 保留の作り方・記録の答えの一覧。

### 歯止め: 1 回の上限額と、3 回の上限

- **採用案**: 1 回の上限額の既定の値は core の定数に置き、フローの定義の値と試験で一致させる。委譲先の宣言（`spec_draft_budget_usd`）で変えられ、エージェントの宣言の `max_run_budget_usd` との小さいほうを使う。core が、決めた額を引数でいつも渡す。1 つの課題で実行は 3 回まで（最初の 1 回と、答えか、やり直しの後の 2 回）。上限に当たったら、下書きを残して保留にする。
- **理由**: 承認なしで始めるので、使う額の最大（上限額 × 3）が先に決まっている必要がある。core は、実行を記録するときと、サイクルの費用の上限を評価するときに、始める前の額が要るが、フローの定義を読めない（import の向き）。定数を core に置けば、境界が 1 つで済む。3 回は、最初の下書き・オーナーの答えを入れた直し・その確かめ、に当たる。
- **代替案**:
  1. 定義を利用側で変える口（上書き）を組み込みのフローで開ける。どこに置いて誰が変えるかを決めていない（フローの移植の「やらないこと」）ので、額だけを引数で渡す。
  2. 宣言のキーを必須にする。宣言の手間が増える。
  3. 開始の応答から上限額を読み戻す。始めた後にしか分からず、サイクルの費用の上限の評価に使えない。
- **影響範囲**: core の定数・定義・`flow start` の引数・委譲先の宣言・記録の回数。

### 保留の選択: 保留の理由を記録に持ち、選択肢を出し分ける

- **採用案**: 下書きづくりの保留は、理由（`spec_question`・`spec_failed`・`spec_attempt_limit`）を下書きづくりの記録に持って見分け、`answer`・`proceed`・`retry`・`skip` のうち、その理由で意味のあるものだけを選択肢に持つ。止まり方は渡さない。画面は、問いと推奨を表示し、選択肢のボタンだけを持つ。推奨と違う答えは、計画の論点の問いと同じ書き方（番号と選択肢の番号・文）で、対話の欄とコマンドから受ける。オーナーが対話の欄で引き取るのは `proceed`。
- **理由**: どの保留でも、「いまの下書きで進む」と「仕様の文書なしで進む」の出口があり、課題が下書きづくりで行き止まりにならない。止まり方は「スーパーバイザーを呼ぶきっかけ」で、足すと、どの止まり方も上げる手を持つこと・設計書の表に行があること、を確かめている試験と、止まり方があればスーパーバイザー待ちにする作りに当たる。この区切りはスーパーバイザーを呼ばないので、止まり方を渡さなければ、いまの作りのまま、はじめからオーナーの回答待ちになる。理由を記録に持てば、回答の処理も画面も、記録の 1 つの値を読むだけで済む。
- **代替案**:
  1. 止まり方に 3 つ足す。スーパーバイザーの試験・設計書の表・スーパーバイザー待ちにする作りを直すことになる。スーパーバイザーが受ける区切り（S2b-2）で、要る 1 つ（`spec_question`）だけを足す。
  2. 保留の種類の閉集合（`human`・`parent_direct`）に足す。その値は「人が答える保留か、対話のセッションが直接行う保留か」を分けていて、`parent_direct` でないことを条件にした所が複数ある。下書きづくりの保留は人が答える保留なので、`human` のままにする。
  3. 理由を持たず、記録の問いの一覧と回数から導く。失敗の保留と回数の上限の保留の見分けが、規則の読み違いで崩れる。
  4. 引き取り専用のコマンドを足す。`proceed` と同じ処理になるので足さない。
  5. 画面に、問いごとに選ぶ入力を足す。計画の論点の問いには無い入力で、オーナーの決定（いまの計画の論点の問いと同じにする）に合わない。
- **影響範囲**: 記録の列・保留の選択肢・回答の確かめと入力の型と処理・`answer` のコマンド・画面の表示と案内。

### DB スキーマ: 下書きづくりの記録の表

- **採用案**: マイグレーション 1 本で、表 `spec_draft` を足す。列は、`challenge_id`（主キー。課題への参照）・`path`（TEXT）・`base_path`（TEXT。NULL 可）・`repo`（TEXT）・`reason`（TEXT）・`state`（TEXT。5 つの値。core の定数で検査）・`attempts`（INTEGER。既定 0）・`questions`（TEXT。JSON の配列。NULL 可）・`answers`（TEXT。JSON の配列。NULL 可）・`hold_id`（開いている下書きづくりの保留への参照。NULL 可）・`hold_reason`（TEXT。3 つの値。NULL 可）・`created_at`・`updated_at`。S2b-2 でスーパーバイザーの答えを足すときは、`answers` の要素の `by` に値を 1 つ足すだけで、列も状態も足さない。契約の実行の種類・予算の枠は、いまも CHECK 制約を持たない列なので、値を足すだけで済む。
- **理由**: 記録は課題に 1 件で、課題の列にすると 8 つ増える。問いと答えは、次の実行の文面と画面にしか使わないので、行に分けない。
- **影響範囲**: ストアの版が 1 つ進む。書き出しと読み込みに表を 1 つ足す。

### 指示文の分量: 計画を作る判断点の天井を 21 KiB へ上げる

- **採用案**: 計画を作る判断点の指示文の天井を、S2a の 20,480 バイトから 21,504 バイトへ上げる。上限の値は、いままでと同じく、本文に余白 300 バイトを足した値。足す文の見込みは約 600〜800 バイト。スーパーバイザーの指示文は、この区切りでは変えない。
- **理由**: S2a の後の本文は約 19,600 バイトの見込みで、回す基準を足すと、余白を入れて 20,480 バイトに収まらない。削る候補の項（約 800 バイト）は、S3 で削ると決まっている。
- **代替案**: 回す基準を、core が書く入力の区画に入れる。指示を入力のデータに置くことになり、指示文の歯止め（分量・禁止語）の外へ出るので採らない。
- **影響範囲**: `internal/invoker/prompts.go` の上限と、上限を書いた文書。

## 機能全体の設計

### 計画を作る判断点の出力の型に足す項目

- 根の `verdict` の値に `needs_spec`（計画の形の出力の型だけ。「足す」の形には足さない）。
- 根に `spec_draft`: `repo`（文字列）・`base_path`（文字列か `null`）・`reason`（文字列）。`needs_spec` のとき必須。ほかの判定では、省略か `null`。

### フローと core の境界

- 入力（`flow start` の `--input`）: `draft_file`・`brief_file`・`brief_dir`・`repo_dir`・`base_path`（任意）・`challenge_id`。
- 出力（契約の `facts`）: `spec_questions`。JSON の配列を文字列にした値。要素の形は、下の「記録の JSON の形」の問いと同じ。
- 定義の骨子（ステップと遷移）:

| ステップ | 種類 | 結果 | 行き先 |
|---|---|---|---|
| `write` | `llm` | `ok` | `critique` |
| `write` | `llm` | `failure` | 失敗（理由 `write_failed`） |
| `critique` | `llm` | `ok` | 成功で終わる |
| `critique` | `llm` | `failure` | 失敗（理由 `critique_failed`） |
| どちらも | — | 予約された結果（`step_error`・`step_timeout`・`invalid_output`・`budget_exhausted`） | 失敗（遷移に書かない。仕組みの既定） |

- どちらのステップも、セッションは新しく始める。やり直し（`retry`）の遷移は持たない。時間切れの値は、実測で決めて定義に書く。

### 記録の JSON の形

- 問い（`spec_draft.questions` の要素。`facts` の `spec_questions` の要素・詳細の `spec_draft.questions` の要素も同じ形）: `question`（文字列）・`options`（`label` を持つオブジェクトの配列。2〜5 個）・`recommended`（1 から数えた位置）・`reason`（文字列）。
- 答え（`spec_draft.answers` の要素。詳細も同じ形）: `attempt`（何回目の実行の問いか）・`question`（問いの文）・`answer`（答えの文。選択肢を選んだときは、その見出し）・`by`（この区切りでは `owner` だけ。S2b-2 で `supervisor` を足す）・`basis`（`path` と `locator` を持つオブジェクトの配列。この区切りではいつも空。S2b-2 でスーパーバイザーの根拠が入る）。
- 読む側（文面のファイルの組み立て・詳細の値・画面）は、`by` の知らない値を誤りにしない（値をそのまま出す）。
- 問いと答えの結び付けは、`attempt` と問いの文。同じ文の問いが後の実行でもう一度出たら、別の問いとして扱う（前の答えは、文面のファイルでフローへ渡っている）。
- 保留の問いの番号 Qn は、保留を作った時点の `questions` の n 番目（1 から）。
- 詳細の `spec_draft` は、上の 2 つに加えて、`state`・`path`・`base_path`（無ければ `null`）・`repo`・`reason`・`attempts`・`max_attempts`（3）・`hold_id`（開いている下書きづくりの保留の表示用の ID。無ければ `null`）・`hold_reason`（`spec_question`・`spec_failed`・`spec_attempt_limit` のどれか。保留が無ければ `null`）。

### 文面のファイルの形

core が書き、ステップ `write` が読む。Markdown で、見出しはこの並び・この文字にする（中身が無い節は、見出しごと書かない）。

```text
# <課題の題名>

## 説明
<課題の説明>

## 取り込み元
<owner>/<name>#<番号>

## 回す理由
<記録の回す理由>

## 置き換える元
<リポジトリの中の相対のパス>

## これまでの問いと答え
### <何回目の実行か>-<その回の中の通し番号>
- 問い: <問いの文>
- 答え: <答えの文>
- 答えた者: <by の値>
```

### 下書きづくりの記録の状態の移り方

| いまの状態 | 起きたこと | 次の状態 |
|---|---|---|
| （無し） | 計画を作る判断点が回すと決めた | `pending` |
| `pending` | 実行を始めた | `running` |
| `pending` | 開始のコマンドが失敗した | `awaiting_owner` |
| `running` | 問いなしで済み、確かめを通った | `done` |
| `running` | 問いが残った・失敗した・終わっていない実行が無い | `awaiting_owner` |
| `awaiting_owner` | オーナーが `answer`・`retry` で答えた | `pending` |
| `awaiting_owner` | オーナーが `proceed` で答えた | `done` |
| `awaiting_owner` | オーナーが `skip` で答えた | `skipped` |
| `done` | オーナーが課題に別の仕様の文書の場所を付けた | `done`（変えない。記録の場所のファイルは消す） |
| どれでも | 課題が取り下げになった | 変えない |
| `pending`・`running`・`awaiting_owner` | オーナーが課題に仕様の文書の場所を付けた | `skipped` |

### 流れ

1. 計画を作る判断点が、課題を下書きづくりへ回すと決める。core が記録を作る。
2. 同じ回りの委譲の段で、core がフロー `spec-draft` を始める。
3. フローが、下書きを書き、3 つの観点で批評して直し、残った問いを返して終わる。
4. 問いが無ければ、core が下書きを確かめ、課題に下書きの場所を書く。次の回りで、計画を作る判断点が下書きから計画を作る（S2a）。
5. 問いが残れば、全部をまとめてオーナーへ上げる。
6. オーナーが答える（推奨のままなら選ぶだけ）。2 へ戻る。または、いまの下書きで進む・仕様の文書なしで進む、を選ぶ。

## 後続の区切り（S2b-2）で足すこと

S2b-1 を実物（Tom）で使い、下書きの質・残る問いの中身・費用を見てから、形を決める。ここには要点だけを残す（受入基準は、その区切りの仕様で書く）。

- **スーパーバイザーが、残った問いのうち答えられるものに先に答える**。保留を作る前に、スーパーバイザーの判断点を 1 回呼ぶ（委譲先の問いと同じ位置。ただし別の経路。委譲先の問いの経路は、着手中の課題・全部に答えるか全部上げるか・実行中の委譲へ返すことを前提にしているため）。
  - スーパーバイザーが受けるために、止まり方 `spec_question` を足し、選べる手（答える `answer`・上げる `escalate`）を持たせる（S2b-1 は止まり方を足さない。記録の保留の理由 `spec_question` と同じ名前にしてある）。あわせて、止まり方の数を確かめている試験と、設計書の止まり方の表を直す。
  - 出力の `answers` の要素を `null` にできるよう、型と出力スキーマを直す（いまは、要素がオブジェクトで、答えと根拠が必須）。答えない問いは `null`。委譲先の問い（止まり方 `child_question`）の側は、`null` を不備にして、いまの振る舞いを保つ。空の答えで「答えない」を表す形は、見分けが付かないので採らない。
  - 入力は専用の組み立て（区画「下書き」「残った問い」「これまでの答え」）。課題にタスクが無くても呼べるようにする。
  - 答えの検査は専用（選択肢の見出しのどれか・根拠として数えられる場所が 1 件以上。1 件でも落ちたら、その呼び出しの答えを全部捨てて、全部の問いを上げる）。
  - 答えは、記録の答えの一覧に `by` が `supervisor`、根拠つきで足す。答えた問いは、保留を作る前に問いの一覧から外す。全部に答えたら、保留を作らずに記録を `pending` へ戻す。
  - 保留の問いの文と詳細に、スーパーバイザーが答えた問いと答えを出す。全部に答えて保留が出ないとき、オーナーへどう知らせるかを決める。
  - 指示文（`sv.md`）に、下書きを読んでから答えること・要件の選択・区切りの決定・重要な設計の選択は上げることを足し、上限を上げる（7 KiB を超えない見込み）。
- **仕様の文書の本文を画面で開く**。課題の仕様の文書の本文を返す口（`GET /api/v1/workspaces/{name}/challenges/{id}/spec`。場所・下書きかどうか・本文・読めない訳）を足し、計画の承認の画面と、下書きづくりの保留の所から、本文を開く（いまの Markdown の部品）。仕様の文書の場所を持つ課題すべてで出す。場所を持たず、記録が途中の課題では、記録の下書きの場所を読む。
