# 要求から計画まで — 仕様の下書きを flywheel の中に置き、計画がリポジトリへ入れる

## 概要

やりたいこと（要求）が課題になり、仕様の文書ができ、計画（タスクへの分解）が承認されるまでの流れを、flywheel の中で 1 本にする。最初の区切り（S1。実装済み）は、**分解を計画を作る判断点（J2）の 1 回だけにし、計画が仕様の文書の受入基準をすべて受け持っているかを core が機械的に検査する**ところまでを定めた。

この文書がいま定めるのは、次の区切り（S2a）。**仕様の文書づくりを計画の前のステップにし、その成果を「仕様の下書き」として flywheel の中（ワークスペースの下書きの置き場）に置く。計画は下書きの受入基準でタスクに分け、下書きをリポジトリへ入れることを計画のタスクが受け持つ**ところまでを定める。下書きを作る道は、この区切りでは対話の欄だけ。委譲で下書きを作る道（組み込みのフロー）は、次の区切り（S2b）で足す。

決定の正本は検討の Issue（flywheel#1266）の「決まったこと」の 12（仕様づくり・分解の作り直しで決めたこと。2026-11-25〜26）と 14（2 つ目の区切りで決めたこと。2026-11-26）。対話の欄の作り替えの仕様（`docs/features/chat-session.md`）のスライス表の S2 を、この文書が引き継ぐ。

## 背景・目的

- フローの移植の区切り 2（flywheel#1255）では、claude-harness の Issue に分けるスキルで実装の Issue を 10 件作った後に、計画を作る判断点が同じ中身をタスク 9 件に分け直した。分解が 2 回走り、片方は捨てられた。
- claude-harness の分解は、3 体の案と審判で分け方を比べ、受入基準の漏れと存在しない受入基準の指定を機械的に確かめている。計画を作る判断点の分解には、この 2 つが無い。
- オーナーの決定（決定 12）: 分解は計画を作る判断点の 1 回だけにする。受入基準の網羅の検査と、3 つの観点で分け方を比べることを、計画を作る判断点へ移す。分解のスキルは呼ばない。エージェントは 1 体のまま。claude-harness は変えず、スキルの終わりの案内（Issue を作るスキルを呼ぶ）は flywheel の側の指示文で上書きする。
- 仕様づくりのスキルが、実物で、Issue を作ろうとする・案内に従わない・flywheel に合わない手順で止まる、のどれかを 1 回でも起こしたら、そのスキルを flywheel の側へ移す（決定 12。この区切りでは移さない）。

- （S2a）S1 では、仕様の文書をリポジトリに置いてから課題を作る。core が読むのは手元のクローンのファイルなので、文書が既定ブランチに入って手元へ届くまで、計画を作れない（S1 の「残る危うさ」）。文書のためだけの PR を、実装の前に 1 本通す必要がある。
- （S2a）オーナーの決定（決定 14）: 文書づくりは、計画の中のタスクではなく、計画の前のステップにする。成果は使い捨ての下書きとして flywheel の中に置き、計画へ渡す。統合先を使わない計画では、文書をリポジトリへ入れることと実装を 1 つのタスクで行う。統合先を使う計画では、先に文書を統合ブランチへコミットする。下書きは常に全文にする（既存の文書を直すときは、写してから直す）。
- （S2a）「タスクを足す」仕組みに乗せる形（最初の計画を文書のタスク 1 件にして、済んだら実装のタスクを足す）は採らない。最初の計画の承認が、大きさも予算も分からないままの承認になり、分解が 2 回になるため（決定 14）。

## ユーザーストーリー

オーナーとして、対話の欄で仕様の下書きを書いたら、文書のためだけの PR を先に通さずに、そのまま計画を受け取りたい。下書きがリポジトリに入ることは、計画のタスクに任せたい。課題が終わったら、下書きは残っていてほしくない。

（S1・実装済み）オーナーとして、対話の欄で仕様の文書を書いて課題を作ったら、実装の Issue に分ける作業を挟まずに、計画を作る判断点の 1 回の分解で計画を受け取りたい。計画が仕様の受入基準を取りこぼしていないことは、自分で数えずに、仕組みに確かめてほしい。

## 機能要件

この節は S2a（仕様の下書きを flywheel の中に置き、計画がリポジトリへ入れる）の要件。S1 の要件は、後ろの「機能要件（S1・実装済み）」に残す。S1 の作り（課題が仕様の文書の場所を持つ・core が受入基準を抜き出す・計画が受け持つ）は変えず、その上に足す。

### 下書きの置き場と、下書きの見分け

- [ ] ワークスペースの `.flywheel/specs/` を、仕様の下書きの置き場とする。
- [ ] 課題の仕様の文書の場所が、下書きの置き場の下を指すとき、その文書を「下書き」として扱う。見分けは、場所を正規化（`.` の要素と重なった `/` を畳む。Go の `path.Clean` と同じ）した結果が `.flywheel/specs/` で始まり、その後ろに 1 文字以上続くこと。それ以外の場所の文書は、S1 のまま、下書きでない仕様の文書として扱う。
- [ ] `flywheel init` が作る `.flywheel/.gitignore` に、`specs/` の行を足す（下書きは使い捨てで、ワークスペースの Git に入れない）。すでにある `.flywheel/.gitignore` は書き換えない。
- [ ] 下書きの読み取り・受入基準の抜き出し・読めないときの扱いは、S1 の仕様の文書と同じにする（置き場が違うだけで、読む決まりは 1 つ）。

### 置き換える元の文書の場所

- [ ] 課題は、「置き換える元の文書の場所」を 0 個か 1 個持つ。下書きが既存の文書の直しであるときに、リポジトリの中のどの文書を丸ごと置き換えるかを示す、リポジトリの中の相対のパス。
- [ ] 課題を作るコマンド（`flywheel create`）と直すコマンド（`flywheel edit`）は、置き換える元の文書の場所を受け取る（`--spec-base <パス>`）。直すコマンドに空の値を渡すと、場所を消す。
- [ ] 置き換える元の文書の場所として、絶対パス・`..` の要素を含むパス・500 文字を超えるパスは受け取らず、検査の誤りにする。ファイルの有無は見ない（どのリポジトリの文書かは、計画のタスクが決めるため）。
- [ ] 置き換える元の文書の場所は、仕様の文書の場所と同じく、終わっていない課題ならどの状態でも直せる。直した場所は、次に計画を作る・作り直すときから効く。
- [ ] 置き換える元の文書の場所は、下書きを持つ課題にだけ効く。下書きを持たない課題では、記録はするが、計画の入力・計画に書き足す一覧・計画の本文・タスクの文面には出さない。
- [ ] 課題の詳細（画面の詳細の口と `flywheel show --json` が共有する形）に、仕様の文書が下書きかどうかと、置き換える元の文書の場所を出す。`flywheel show` の文の出力では、仕様の文書の場所の行に「（下書き）」を添え、置き換える元の文書の場所を 1 行で出す。

### 計画を作る判断点へ、下書きであることを渡す

- [ ] 下書きを持つ課題では、計画を作る判断点の入力の区画「受入基準」に、文書が下書きであることを 1 行で足す。行には、語「下書き（リポジトリにまだ入っていない）」を入れる。
- [ ] 済みのタスクが下書きをリポジトリへ入れているときは、その行の代わりに、「下書き（済みのタスク「<そのタスクの題名>」がリポジトリへ入れた）」を入れた行を出し、語「リポジトリにまだ入っていない」は区画に出さない。済みのタスクが入れたかは、計画の出力の検査と同じ判定（状態が済みのタスクすべて。計画の版と、統合先を使うかを問わない）で決める。置き換える元の行は変えない。
- [ ] 下書きを持つ課題が置き換える元の文書の場所を持つとき、区画「受入基準」に、語「置き換える元」とその場所を 1 行で足す。持たないときは、語「新しい文書」を入れた行を 1 行で足す。
- [ ] 下書きでない仕様の文書を持つ課題の区画「受入基準」は、S1 のまま変えない。

### 計画が、下書きをリポジトリへ入れるタスクを持つ

- [ ] 計画の出力のタスクに、そのタスクが下書きをリポジトリへ入れるかどうか（`lands_spec`。真偽）を足す。省略と `null` は偽と読む。
- [ ] 下書きを持つ課題の計画で、下書きをリポジトリへ入れるタスク（`lands_spec` が真の新しいタスクと、`lands_spec` を記録した済みのタスク）が 1 件も無ければ、不正な出力にする。ここでの済みのタスクは、その課題の、状態が済みのタスクすべて（計画の版と、統合先を使うかどうかを問わない。S1 の受け持ちの検査が使う集合〔統合先を使う課題の済みのタスク〕とは別の集合）。
- [ ] 下書きを持つ課題の計画で、下書きをリポジトリへ入れるタスクが 2 件以上あれば、不正な出力にする（済みのタスクが入れた後の作り直しで、新しいタスクがもう一度入れる計画を含む）。
- [ ] 下書きを持つ課題の計画で、新しいタスクが 2 件以上あり、下書きをリポジトリへ入れるタスクがその中にあるとき、ほかの新しいタスクのどれかが、前提をたどっても入れるタスクに届かなければ、不正な出力にする（文書が先に入る順にする）。
- [ ] 下書きを持たない課題（仕様の文書の場所を持たない課題と、下書きでない仕様の文書を持つ課題）の計画で、`lands_spec` が真のタスクが 1 件でもあれば、不正な出力にする。
- [ ] 「足す」の形の呼び出しで足すタスクの `lands_spec` が真なら、不正な出力にする。
- [ ] 不正な出力の理由の文（S1 の理由の文と同じく英語）は、どれで落ちたかを、決まった語で見分けられる。入れるタスクが無いは `spec landing missing`、2 件以上は `duplicate spec landing`、順が違うは `spec landing not first`、下書きを持たない課題と「足す」の形での指定は `unexpected spec landing` を含む。
- [ ] 受入基準の網羅の検査（漏れ・存在しない基準・重なり）は、下書きを持つ課題にも S1 のまま掛ける。
- [ ] 入れるタスクの検査（有無・数・順・下書きを持たない課題での指定）は、計画を登録するとき（計画の形と「足す」の形の出力を受け取るとき）だけ掛ける。承認した計画の検査し直し（S1 の「技術的な制約・方針」に挙げた 4 つの入口）では掛けない。

### 記録と表示

- [ ] 計画を登録するとき、タスクの記録に、下書きをリポジトリへ入れるタスクであることを残す。
- [ ] 計画を登録するとき、core が計画の構造化した出力へ書き足す受入基準の一覧（`acceptance_criteria`）に、下書きであること（`draft`。真偽）と、置き換える元の文書の場所（`base_path`。下書きでないか、場所を持たなければ `null`）を足す。
- [ ] 計画の本文の、下書きをリポジトリへ入れるタスクの行に、「仕様の文書をリポジトリへ入れる」と出す。
- [ ] 計画の本文の節「受入基準の受け持ち」の仕様の文書の行に、語「下書き」と、リポジトリへ入れるタスクの題名を出す。
- [ ] 下書きを持つ課題が置き換える元の文書の場所を持つときは、計画の本文の節「受入基準の受け持ち」に、語「置き換える元」とその場所を 1 行で出す。
- [ ] 課題の詳細のタスクに、下書きをリポジトリへ入れるタスクかどうかを出す。

### 下書きを委譲へ渡す

- [ ] 下書きをリポジトリへ入れるタスクの文面（契約の形・プラグインの形の委譲へ渡すタスクの文書と、指示文だけの形の委譲の指示文を書く判断点へ渡すタスクの区画）の「このタスク」の中（節「受け持つ受入基準」の後ろ。その節が無ければ、その位置）に、節「仕様の文書をリポジトリへ入れる」を足す。中身は 3 つ。渡した下書きの全文を、リポジトリの文書として「そのまま入れる」こと。「受入基準の文を変えない」こと。置き換える元の文書の場所があれば、語「丸ごと置き換える」とその場所を、無ければ、リポジトリの決まりの場所に「新しい文書として置く」ことを書く。
- [ ] 契約の形の委譲では、入れるタスクの文面のファイルの最後に、節「仕様の下書きの全文」を足す。節の中身は、下書きのファイルの全文をそのまま（この節より後ろに、ほかの節を置かない。ほかのタスクの節が無い文面でも、最後に足す）。
- [ ] プラグインの形と、指示文だけの形の委譲では、入れるタスクの委譲先が受け取る標準入力に、データの区画「仕様の下書きの全文」を足す。中身は下書きの全文で、いまのデータの区画と同じ包み方（区切りの行に当たる行の無害化を含む）をする。タスクの文書と、指示文を書く判断点の入力には、全文を入れない。全文は core が読んで起動の入力として渡し、標準入力へ入れるのは `internal/invoker`。
- [ ] 下書きを持つ課題の、入れるタスクでないタスクの文面には、「このタスク」の中（節「受け持つ受入基準」の後ろ。その節が無ければ、その位置）に、節「仕様の文書」を足す。中身は、仕様の文書をリポジトリへ入れるタスクの題名と、置き換える元の文書の場所（あれば）。全文は渡さない。
- [ ] 下書きかどうかと、置き換える元の文書の場所は、計画に書き足した一覧（`draft`・`base_path`）から引く（課題のいまの場所を読み直さない）。`draft` を持たない一覧（S1 で登録した計画）は、下書きでないと読む。
- [ ] 下書きを持たない課題のタスクの文面と標準入力は、S1 のまま変えない。
- [ ] 下書きをリポジトリへ入れるタスクを、委譲の対象として選ぶとき、core は下書きを読み直す。読めないか、抜き出した受入基準の識別の並びが、計画に書き足した一覧と違うときは、選ばず、そのタスクを「着手しなかった」として、理由（下書きが計画の後に変わった。値は `spec_draft_changed`）と細目（下書きの場所と、読めなかった訳か、並びが違う旨）を残す。同じサイクルの、ほかの課題の委譲は続ける。
- [ ] 委譲へ渡す全文は、この読み直しで読んだものを使う。
- [ ] 入れるタスクでないタスクを選ぶときは、下書きを読み直さない。

### 課題が終わったら下書きを消す

- [ ] 課題が取り下げになったとき、その課題の仕様の文書が下書きなら、core は下書きのファイルを消す。
- [ ] 課題が完了になり、その課題に、まだ実行していない不可逆操作（反映・削除・外への送信）が 1 件も無くなったとき、その課題の仕様の文書が下書きなら、core は下書きのファイルを消す。完了になった時点で 1 件も無ければ、そのとき消す。残っていれば、最後の 1 件が実行されたとき（または差し戻されたとき・実行されずに閉じたとき）に消す（完了した課題は、反映の前に検証中へ戻して検証し直すことがあり、そのあいだは計画の作り直しに下書きが要るため）。
- [ ] 同じ下書きを、ほかの課題が仕様の文書として指していて、その課題がまだ上の消す条件を満たしていないときは、消さない。
- [ ] 下書きのファイルがすでに無いときは、何もせずに成立させる。
- [ ] 消す前に、場所のリンクをたどった先（S1 の場所の検査と同じたどり方）が、下書きの置き場の実体の下にあることを確かめる。外にあるときは消さず、消せなかったときと同じ扱いにする。
- [ ] 下書きを消せなかったときは、完了・取り下げ・不可逆操作の実行は成立させ、消せなかったことを作業ログに残す（作業ログの種類は `spec_draft_cleanup_failed`。細目に、場所と訳）。
- [ ] 下書きを消した後も、課題の仕様の文書の場所と、置き換える元の文書の場所の記録は残す（どの下書きから計画したかの記録として）。
- [ ] 消すのは、下書きの置き場の下のファイルだけ。下書きでない仕様の文書は消さない。

### 計画を作る判断点の指示文

- [ ] 指示文（`internal/invoker/prompts/j2.md`）に、区画「受入基準」に下書きの印があるときの書き方を足す。中身は 3 つ。印「下書き」があるときは、下書きをリポジトリへ入れるタスクを「1 件だけ」決めて `lands_spec` を真にすること。タスクが 1 件の計画では、そのタスクが「文書を入れることと実装の両方」を行うこと。タスクが 2 件以上の計画では、文書を入れるタスクを「最初に置き」、ほかのタスクの前提にすること。あわせて、区画「受入基準」に「リポジトリへ入れた」の行があるときと、印が無いときは、どのタスクの `lands_spec` も真にしないことを書く（下書きを入れた後かどうかは、この行だけで見分けさせる）。
- [ ] 指示文の分量の上限は、足した文の分に余白 300 バイトを足した値へ引き上げる。20,480 バイト（20 KiB）を超えない（S1 で決めた 19,456 バイトの天井を、この区切りで置き換える。S1 の天井を確かめている試験は、この区切りの実装で新しい天井に合わせる）。

### 対話の欄の指示文

- [ ] 指示文（`internal/invoker/prompts/chat.md`）の節「仕様づくりの後」を、下書きの形に直す。中身は 4 つ。仕様の文書は、対象のリポジトリではなく、下書きの置き場（`.flywheel/specs/` の下）に書くこと。仕様づくりのスキルを使うときは、「保存先」を下書きの置き場にすること。既存の文書を直すときは、「全文を写してから直し」、課題に置き換える元の文書の場所（`--spec-base`）を付けること。課題を作るときは、下書きの場所を `--spec` で付けること。
- [ ] S1 で足した案内（スキルの終わりの案内に従って Issue を作らない・Issue に分けるスキルを呼ばない）は残す。
- [ ] 指示文の分量の上限は、足した文の分だけ引き上げる。5,632 バイト（5.5 KiB）を超えない。

### 書き出しと読み込み

- [ ] ストアの全状態の書き出しと読み込み（`export`・`import`）に、課題の置き換える元の文書の場所と、タスクの下書きを入れる印を入れる。

### 文書

- [ ] `docs/glossary.md` に「仕様の下書き」の行を足し、「仕様の文書」の行に、下書きの置き場の文書は下書きとして扱うことを足す。
- [ ] `docs/architecture.md` の計画を作る判断点の節に、仕様の文書づくりを計画の前のステップにすること（語「計画の前」）・下書きを flywheel の中に置くこと（`.flywheel/specs/`）・下書きをリポジトリへ入れるタスクの検査（`lands_spec`）を書く。
- [ ] `docs/features/m3-invoker-delegation.md` の判断点の出力（計画を作る判断点の行）に `lands_spec` を、指示文の歯止めの分量の上限の記述にこの区切りの上限を、委譲の「着手しなかった」の理由の一覧に `spec_draft_changed` を書く。
- [ ] `docs/features/chat-session.md` の、対話の欄で仕様の文書を対象のリポジトリの作業ツリーに書くとしている記述に、仕様の文書は下書きの置き場に書く（この文書を指す）ことを足す。

## 非機能要件

- セキュリティ: 下書きの全文は、標準入力ではデータの区画として（いまのデータの区画と同じ包み方で）、契約の形の文面のファイルでは最後の節として渡す（委譲先への指示は、節「仕様の文書をリポジトリへ入れる」だけが持つ）。下書きの置き場は、S1 の場所の検査（ワークスペースの中だけ）の内側にある。core が消すのは、課題が指すファイル 1 つだけで、リンクをたどった先が下書きの置き場の実体の下にあるときに限る。
- 費用: 判断点の呼び出しは増やさない（計画を作る判断点は 1 回のまま）。
- 後方互換: 下書きでない仕様の文書を持つ課題・仕様の文書の場所を持たない課題・この区切りより前に承認した計画の振る舞いは変えない。

## 技術的な制約・方針

- 変更対象:
  - `internal/core`: 下書きの見分け。課題の置き換える元の文書の場所。計画の入力の区画・出力の型・検査・計画の本文・タスクの記録。委譲へ渡すタスクの文面（`internal/core/delegate_task.go`）と、委譲の対象を選ぶときの読み直し。下書きの削除。書き出しと読み込み。「着手しなかった」の理由の値の集合（`internal/core/judgment_batch.go`）へ `spec_draft_changed` を、作業ログの種類の集合へ `spec_draft_cleanup_failed` を、1 つずつ足す。`flywheel init` が書く `.flywheel/.gitignore` の中身（`internal/core/store.go`）。
  - `internal/core/internal/store`: マイグレーション 1 本。
  - `internal/cli`: `create`・`edit` の `--spec-base`、`show` の出力。
  - `internal/view`・`web/src/api/types.gen.ts`: 課題の詳細の値（型の生成だけ。画面の部品は変えない）。
  - `internal/invoker`: `prompts/j2.md`・`prompts/chat.md`・上限（`prompts.go`）。プラグインの形と指示文だけの形の委譲の標準入力の組み立て（データの区画「仕様の下書きの全文」。全文は、core が起動の入力に載せて渡す）。
- 下書きかどうかは、場所から導く（ストアに印を持たない）。場所を直せば、下書きかどうかも変わる。場所の文字列は、S1 のまま、受け取ったとおりに記録する（正規化して書き換えない）。見分けるときだけ正規化する。
- 読み直しは、委譲の対象のタスクを選ぶ所（`internal/core/delegate_task.go` の、課題ごとに起動するタスクを選ぶ所）で 1 回だけ行う。委譲の形（契約・プラグイン・指示文だけ）ごとの起動の入口には置かない（契約の形の起動の入口は「着手しなかった」を返す口を持たないため）。
- `spec_draft_changed` で止まったタスクは、下書きを計画の時点の受入基準に戻せば、次に選ぶときに起動される。受入基準を変えたいときは、いまある口で計画を作り直す（入れるタスクが済んでいなければ、新しい計画は入れるタスクを持つことになる）。新しい口は足さない。
- 下書きを消す処理は、遷移と不可逆操作の実行のトランザクションが成立した後に行い、失敗しても巻き戻さない。差し込む所は 5 つ。取り下げの遷移の後・完了の遷移の後・不可逆操作の実行の記録の後・不可逆操作の単独の差し戻しの後・承認待ちや承認済みの不可逆操作を実行せずに閉じる書き込みの後（承認待ちの反映の片付けと、委譲先の成果物から外れた反映の操作を閉じる書き込み。課題が完了でなくなる書き込みの中で閉じる所〔反映の前に検証中へ戻す・完了の差し戻し・上げる依頼に結び付いた操作を閉じる〕には差し込まない）。完了・取り下げへ進む遷移が、ほかのトランザクションの中から呼ばれる経路を持つなら、その経路にも同じ後始末を掛ける（実装のときに経路を数え、PR の説明に書く）。
- 消せなかったことの作業ログは、遷移とは別の書き込みで残す。
- 書き込めないディレクトリを使う試験（消せなかったとき）は、権限を無視できる利用者で走らせると成り立たない。その環境では試験を飛ばし、PR の説明に書く（S1 の読めないファイルの試験と同じ扱い）。
- 指示文の受入基準の「書かれている」は、S1 と同じく、文書を読む試験で、その基準がかぎ括弧か `` ` `` で挙げた語が指示文にそのまま現れることで確かめる。計画を作る判断点の指示文には、禁止語の検査（出力の閉集合の値・コマンドの名前・設定のキーを書かない）がいまのまま効くので、`lands_spec` は出力の型の項目の名前として書き、値の語は書かない。タスクの文面と計画の入力の「書かれている」「出る」も、同じく、かぎ括弧か `` ` `` で挙げた語がそのまま現れることで確かめる。
- タスクの文面の受入基準は、契約の形・プラグインの形の委譲へ渡すタスクの文書（同じ組み立て）で確かめる。形ごとに違う所（文面のファイルの最後の節・標準入力のデータの区画）は、形を名指しした基準で確かめる。
- この文書の「文字」は、S1 と同じく、Unicode のコードポイントの数で数える。
- ストアの版は、いまの版（42）の次（並べて進めているほかの区切りが先に版を使ったら、その次）。

## 機能要件（S1・実装済み）

### 課題に仕様の文書の場所を持たせる

- [ ] 課題は、仕様の文書の場所を 0 個か 1 個持つ。場所は、ワークスペースから見た相対のパス（計画を作る判断点が読み取りの道具で読むのと同じファイル）。
- [ ] 課題を作るコマンド（`flywheel create`）と直すコマンド（`flywheel edit`）は、仕様の文書の場所を受け取る（`--spec <パス>`）。直すコマンドに空の値を渡すと、場所を消す。
- [ ] 場所として、絶対パス・ワークスペースの外へ出るパス（`..` を含むもの、リンクをたどった先が外のもの）は受け取らず、検査の誤りにする。書き込みのときにファイルの有無は見ない（文書がまだ既定ブランチに入っていないことがあるため）。
- [ ] 仕様の文書の場所は、いまある直すコマンドと同じく、終わっていない課題ならどの状態でも直せる。直した場所は、次に計画を作る・作り直すときから効く。すでに登録した計画（承認待ち・承認済み）は、その計画に書き足した一覧（文書の場所を含む）を正とし、場所を直しても検査し直しの結果は変わらない。計画の本文の節「受入基準の受け持ち」には、その計画が読んだ文書の場所が出たまま残る。
- [ ] 課題の詳細（画面の詳細の口と `flywheel show --json` が共有する形）に、仕様の文書の場所を出す。`flywheel show` の文の出力にも 1 行で出す。

### 受入基準を抜き出して識別を付ける

- [ ] core は、仕様の文書から受入基準を抜き出す。対象は、見出しが `## 受入基準` とちょうど一致する節（次の `## ` の見出しの前まで）の中の、行頭が `- [ ] `・`- [x] `・`- [X] ` の行。字下げした行と、括弧つきの見出し（`## 受入基準（S1・実装済み）` など）の節は対象にしない。
- [ ] 受入基準の文は、チェックの印の後ろから行末まで。前後の空白を除き、連続する空白を半角の空白 1 つにまとめたものを、その基準の文とする（空白は Unicode の空白。Go の `strings.Fields` で分けて半角の空白でつなぐのと同じ）。
- [ ] 受入基準の識別は、`AC-` に、基準の文の SHA-256 の 16 進の先頭 8 桁を付けたもの。文が同じ行は、1 つの基準として数える。
- [ ] 文が違うのに識別が同じになる基準が 1 組でもある文書は、読めない文書として扱う。

### 計画を作る判断点へ受入基準を渡す

- [ ] 仕様の文書の場所を持つ課題では、計画を作る判断点の入力（計画の形）に、区画「受入基準」を足す。区画には、文書の場所・基準の件数・基準ごとの識別と文の先頭 80 文字を、文書に出てくる順に入れる。
- [ ] 仕様の文書の場所を持たない課題では、区画「受入基準」を入れない。
- [ ] 計画を作り直すときの区画「受入基準」では、済みのタスクが記録した識別の基準の行に、印「済み」を付ける（判断点が、どの基準が受け持ち済みかを見分けられるようにする）。
- [ ] 「足す」の形の呼び出しの入力にも、区画「受入基準」を入れる。中身は、承認した計画に書き足した一覧から作る（文書の場所・基準の件数・基準ごとの識別と文の先頭 80 文字・済みの印。仕様の文書は読み直さない）。一覧を持たない計画への呼び出しには入れない。
- [ ] 仕様の文書の場所を持つ課題で、文書を読めないとき（ファイルが無い・読めない・2 MiB を超える・抜き出した基準が 0 件・識別が重なる）は、計画を作る判断点を呼ばず、その課題を「着手しなかった」として、理由（仕様の文書を読めない。値は `spec_unreadable`）と細目（場所と、読めなかった訳）を残す。上流を読めないときと同じ扱いで、ほかの課題の計画は続ける。

### 計画が受入基準を受け持つ

- [ ] 計画の出力のタスクに、そのタスクが受け持つ受入基準の識別の配列（`covers`）を足す。空でもよい（土台のタスクなど）。
- [ ] 計画の出力に、この計画で受け持たない受入基準の配列（`deferred_criteria`。要素は識別と理由）を足す。無ければ空か省略。
- [ ] 区画「受入基準」を渡した計画で、タスクの `covers` か `deferred_criteria` に、区画に無い識別があれば、不正な出力にする（存在しない基準の指定）。
- [ ] 区画「受入基準」を渡した計画で、どのタスクの `covers` にも、済みのタスクが受け持った識別にも、`deferred_criteria` にも無い基準が 1 件でもあれば、不正な出力にする（漏れ）。
- [ ] 1 つのタスクの `covers` に同じ識別が 2 回あれば、不正な出力にする。
- [ ] `deferred_criteria` の識別が、同じ計画のタスクの `covers` にもあれば、不正な出力にする。
- [ ] `deferred_criteria` の理由が無い・空白だけ・2000 文字を超えるときは、不正な出力にする。
- [ ] 区画「受入基準」を渡していない計画で、`covers` か `deferred_criteria` に 1 件でも識別があれば、不正な出力にする。
- [ ] 不正な出力の理由の文（実行の記録に残す短い文。いまの理由の文と同じく英語）は、漏れ・存在しない基準の指定・重なりのどれで落ちたかを、決まった語で見分けられる。漏れは `criteria not covered`、存在しない基準の指定は `unknown criterion`、重なり（1 つのタスクの中の重なりと、受け持たない基準との重なり）は `duplicate criterion` を含む。基準の文は理由に写さない。
- [ ] 1 つの基準を 2 つ以上のタスクが受け持つことは認める。

### 受け持ちの記録と表示

- [ ] 計画を登録するとき、core は、検査に使った受入基準の一覧（文書の場所・識別・文の全文）を、計画の構造化した出力（`task_plan.spec`）へ書き足す。
- [ ] 計画を登録するとき、タスクの記録に、受け持つ受入基準の識別を残す。
- [ ] 計画の本文のタスクごとの行に、受け持つ受入基準の件数を出す。
- [ ] 計画の本文に、節「受入基準の受け持ち」を出す。中身は、仕様の文書の場所・基準の全件数・受け持たない基準（文の先頭 80 文字・識別・理由）。受け持たない基準が無ければ、その旨を 1 行で出す。
- [ ] 仕様の文書の場所を持たない課題の計画の本文には、節「受入基準の受け持ち」に「仕様の文書が無いので、受入基準の網羅は検査していない」と出す。
- [ ] 課題の詳細のタスクに、受け持つ受入基準の識別の配列を出す。

### 受け持つ受入基準を委譲へ渡す

- [ ] 委譲へ渡すタスクの文面（契約の形・プラグインの形の委譲へ渡すタスクの文書と、指示文だけの形の委譲の指示文を書く判断点へ渡すタスクの区画）に、節「受け持つ受入基準」を足す。中身は、そのタスクが受け持つ基準の文の全文を、計画に書き足した一覧の順に並べたもの。識別は文の後ろに括弧で添える。
- [ ] 受け持つ基準が無いタスク（`covers` が空）と、一覧を持たない計画のタスクの文面には、この節を出さない。
- [ ] 基準の文は、計画に書き足した一覧から引く（仕様の文書を読み直さない）。タスクが記録した識別のうち、一覧に無いものは出さない。
- [ ] 完了の検証の入力は変えない（受け持つ基準を、完了の検証へは渡さない）。

### 計画の作り直し・足す形・検査し直し

- [ ] 計画を作り直すとき、済みのタスク（区画「済みのタスク」に出るタスクと同じ集合）が記録した識別のうち、いまの区画「受入基準」にあるものは、受け持ち済みとして漏れの検査で数える。区画「済みのタスク」のタスクごとに、受け持ち済みの件数を出す。
- [ ] 「足す」の形の呼び出しで足すタスクも `covers` を書ける。承認した計画に書き足した一覧に無い識別があれば、不正な出力にする（一覧を持たない計画に足すタスクは、識別が 1 件でもあれば不正な出力にする）。漏れの検査はしない。
- [ ] 承認した計画を委譲の段で検査し直すときと、保留中の足す依頼を回答の段で検査し直すときは、計画に書き足した一覧と突き合わせ、仕様の文書を読み直さない。一覧を持たない計画（この区切りより前に承認した計画・人が登録した計画）は、受入基準の検査をしない。

### 計画を作る判断点の指示文

- [ ] 指示文（`internal/invoker/prompts/j2.md`）に、タスクへの分け方を、3 つの観点（依存を最小にする・機能を縦に切る・層ごとに分ける）で比べてから 1 つに決めること、決めた分け方と理由を方針（要約）に書くことを足す。
- [ ] 指示文に、区画「受入基準」の読み方と、`covers`・`deferred_criteria` の書き方（識別は区画のものをそのまま写す・作らない。受け持たない基準は理由を書く）を足す。
- [ ] 指示文に、印「済み」の付いた基準は受け持ち済みで、`covers` にも `deferred_criteria` にも書かなくてよいことを足す。「足す形の呼び出し」の節には、`covers` の識別を区画「受入基準」から写すことを書く。
- [ ] 指示文に、仕様の文書は読むだけで、書き換える手順をタスクにする以外の形で直さないこと（判断点は書かない）を足す。
- [ ] 計画を作る判断点は、いまと同じく、読み取りの道具（Read・Grep・Glob）だけで起動する。サブエージェントと書き込みの道具は使えないまま。
- [ ] 指示文の分量の上限は、足した文の分に余白 300 バイトを足した値へ引き上げる。19,456 バイト（19 KiB）を超えない。

### 対話の欄の指示文

- [ ] 指示文（`internal/invoker/prompts/chat.md`）に、仕様づくりのスキルの後の案内を足す。中身は 3 つ。スキルの終わりの案内に従って Issue を作らない。Issue に分けるスキルを呼ばない。仕様の文書から課題を作るときは、仕様の文書の場所を付けて作る。
- [ ] 指示文の分量の上限は、足した文の分だけ引き上げる。5,632 バイト（5.5 KiB）を超えない。

### 文書

- [ ] `docs/features/m3-invoker-delegation.md` の判断点の出力（計画を作る判断点の行）と、指示文の歯止めの分量の上限の記述に、この区切りで足した項目と上限を書く。
- [ ] `docs/features/m3-invoker-delegation.md` の、サイクルの出力の「着手しなかった」の理由の一覧（`cycle --json` の `not_started[].reason` の閉集合の記述）に、新しい値 `spec_unreadable`（仕様の文書を読めない）を足す。

## 非機能要件（S1・実装済み）

## 技術的な制約・方針（S1・実装済み）

- 変更対象:
  - `internal/core`: 課題の仕様の文書の場所。文書の読み取りと受入基準の抜き出し（ワークスペースのファイルを読む。いまのポジション定義の読み取りと同じ層）。計画の入力の区画・出力の型・検査・計画の本文・タスクの記録。委譲へ渡すタスクの文面（`internal/core/delegate_task.go`）。作り直し・足す形・検査し直し。書き出しと読み込み。「着手しなかった」の理由の値の集合（`internal/core/judgment_batch.go` の `NotStartedReason`）へ、`spec_unreadable`（仕様の文書を読めない）を 1 つ足す。
  - `internal/core/internal/store`: マイグレーション 1 本。
  - `internal/cli`: `create`・`edit` の `--spec`、`show` の出力。
  - `internal/view`・`web/src/api/types.gen.ts`: 課題の詳細の値（型の生成だけ。画面の部品は変えない）。

## クリティカル設計決定

文書づくりを計画の前のステップにすること・下書きを flywheel の中に置くこと・下書きを常に全文にすること・区切りを 2 つに分けることは、案を比べたうえでオーナーが決めた（2026-11-26。flywheel#1266 の決定 14）。そのほかは、オーケストレーターの案（この仕様の PR で確かめてもらう）。

### 文書づくりの位置: 計画の前のステップにし、成果は flywheel の中の下書きにする（オーナーの決定 2026-11-26）

- **採用案**: 仕様の文書は、計画の前に、ワークスペースの下書きの置き場（`.flywheel/specs/`）に作る。課題の仕様の文書の場所は下書きを指し、計画は下書きから受入基準を読む（S1 の作りのまま読める）。リポジトリへ入れるのは計画のタスクで、入った文書が正本になる。下書きは課題が終わったら消す。
- **理由**: 計画が 1 回で済み、最初から受入基準と予算のそろった計画を承認できる。下書きはワークスペースのファイルなので、文書を読む新しい口も、計画の前の統合ブランチも要らない。S1 の「残る危うさ」（手元のクローンが既定ブランチの最新とは限らない）は、下書きを持つ課題には当たらない。
- **代替案**:
  1. 計画のタスクにして、済んだら実装のタスクを足す（「タスクを足す」仕組みに乗せる）。最初の計画の承認が、大きさも予算も分からないままの承認になる。足す形は承認済みの計画の続きを承認なしで足す仕組みで、実装の本体を決める所ではない。分解が 2 回になる。
  2. 文書を先に既定ブランチへ入れてから計画する（S1 のまま）。文書のためだけの PR と、手元のクローンへ届ける手順が要る。
  3. 文書を統合ブランチに置いて、そこから読む。統合ブランチを計画の前に作ることになり、統合先を使うかを計画が決められなくなる。ブランチのファイルを読む口も新しく要る。
- **残る危うさ**: 下書きとリポジトリに入った文書は、実装の途中の直しでずれうる。flywheel は、課題が終わるまで下書き（計画に書き足した一覧）を検査の正とし、リポジトリの文書を読み直さない。リポジトリへ入れるタスクの起動の前だけ、下書きが計画の後に変わっていないかを確かめる。
- **影響範囲**: `internal/core`・`internal/cli`・`internal/view`・`internal/invoker`・ストア。

### 下書きは常に全文にする（オーナーの決定 2026-11-26）

- **採用案**: 既存の文書を直す課題でも、下書きは全文にする（既存の文書を写してから直す）。リポジトリへ入れるときは、置き換える元の文書を丸ごと置き換える。
- **理由**: 計画も人も、1 つの文書を読めば済む。受入基準の抜き出しの決まりが 1 つのままで済む。
- **代替案**: 差分（足す・直す部分だけ）の下書き。小さく済むが、リポジトリへ入れるときに組み込む作業が要り、受入基準の読み方を別に決めることになる。
- **残る危うさ**: 下書きを写した後に、元の文書が別の変更で変わると、丸ごとの置き換えがその変更を消す。入れるタスクの PR の差分に出るので、レビューと完了の検証で見つける。仕組みでは防がない。
- **影響範囲**: 課題の置き換える元の文書の場所・タスクの文面。

### 下書きをリポジトリへ入れる所: 計画のタスクに印を付け、core が数と順を検査する

- **採用案**: 計画の出力のタスクに `lands_spec` を足す。下書きを持つ課題の計画には、入れるタスクがちょうど 1 件あり、ほかの新しいタスクがその後に並ぶ（前提をたどると届く）ことを、core が検査する。入れるタスクの委譲には、core が読んだ下書きの全文を渡す（契約の形は文面のファイルの最後の節、プラグインの形と指示文だけの形は標準入力のデータの区画）。
- **理由**: 「先に文書を入れる」を、判断点の書き方だけに任せない（S1 の網羅の検査と同じ考え）。タスクが 1 件の計画では、同じタスクが文書と実装を受け持つので、統合先を使わない課題でも形が変わらない。全文を渡せば、委譲先は作業場所の外のファイルを読む許可が要らない。標準入力では、いまのデータの区画と同じ包み方にして、下書きの中の行が指示や区切りとして読まれないようにする。
- **代替案**:
  1. flywheel が統合ブランチを作るときに、自動で下書きをコミットする。flywheel はリポジトリへ書き込まない決まり（反映は委譲先）を崩す。統合先を使わない課題に別の道が要る。
  2. 印を付けず、指示文で「最初のタスクで入れる」と書くだけにする。入れ忘れた計画を仕組みが弾けない。
  3. 全文を渡さず、下書きの場所だけを渡す。委譲の形ごとに、作業場所の外を読む許可（読める場所の追加）が要る。
- **残る危うさ**: 標準入力のデータの区画は、区切りの行に当たる行を無害化するので、下書きにそういう行があると、委譲先が受け取る全文がその行だけ変わる（受入基準の行は、チェックの印で始まるので当たらない）。
- **影響範囲**: 計画の出力の型・検査・タスクの記録・タスクの文面・委譲の起動の入力と標準入力。

### 下書きを消す時: 取り下げと、反映まで済んだ完了

- **採用案**: 下書きを消すのは、課題が取り下げになったときと、完了した課題に、まだ実行していない不可逆操作が無くなったとき。
- **理由**: 完了した課題は、反映の前に、検証中へ戻して検証し直すことがある（承認した後に PR の先頭が動いたとき）。そこから計画を作り直すと、下書きが要る。完了の時点で消すと、作り直しが「仕様の文書を読めない」で止まる。
- **代替案**: 完了の時点で消し、戻ったときはオーナーが仕様の文書の場所をリポジトリの文書へ直す。手で直す作業が要り、直すまで課題が止まる。
- **影響範囲**: 完了・取り下げの遷移の後と、不可逆操作の実行の記録の後の後始末。

### 置き換える元の文書の場所: リポジトリの中の相対のパスを、課題に持たせる

- **採用案**: 課題に、置き換える元の文書の場所を、リポジトリの中の相対のパスとして持たせる（`--spec-base`）。ファイルの有無は検査しない。どのリポジトリかは、入れるタスクの対象のリポジトリで決まる。
- **理由**: 委譲先が要るのは、作業ツリーの中のどのファイルを置き換えるか。ワークスペースから見たクローンのパスを渡すと、委譲先が読み替えることになる。
- **代替案**: 下書きの先頭に、置き換える元を書く行を置く。文書の書式を変え、リポジトリへ入れるときに取り除く作業が要る。
- **影響範囲**: 課題の列 1 つ・`create`・`edit`・`show`・詳細の値。

### DB スキーマ: 課題の置き換える元の文書の場所と、タスクの下書きを入れる印

- **採用案**: マイグレーション 1 本で、`challenge` に `spec_base_path`（TEXT。NULL 可）、`task` に `lands_spec`（INTEGER。0 か 1。既定 0）を足す。書き出しと読み込みに 2 つの列を入れる。版の違う書き出しは、これまでどおり読み込まない（移行の仕様 `docs/features/m5-tom-migration-and-switchover.md` の決まりのまま。前の版の書き出しを読み替える仕組みは足さない）。
- **理由**: 計画を作り直すとき、済みのタスクが下書きを入れたかを数えるのに、タスクの行に残っている必要がある（S1 の `covers` と同じ理由）。下書きかどうかは場所から導くので、列を持たない。
- **影響範囲**: ストアの版が 1 つ進む。既存の行は、置き換える元なし・入れるタスクでない、として読む。

### 指示文の分量: 計画を作る判断点の天井を 20 KiB へ上げる

- **採用案**: 計画を作る判断点の指示文の上限（いま 19,443 バイト。本文は 19,143 バイト）を、足した文の分に余白 300 バイトを足した値へ引き上げる。足す文の見込みは約 400〜500 バイト。S1 で決めた天井（19,456 バイト）は、この区切りで 20,480 バイトに置き換える。対話の欄の指示文の上限（いま 5,060 バイト。本文は 4,941 バイト）は、足した文の分だけ引き上げる（見込みは約 300〜400 バイト。5,632 バイトの天井は変えない）。
- **理由**: これまでの引き上げと同じ決まり（足した文の分だけ）。S1 の天井まで残り 13 バイトで、足す文が収まらない。削る候補の項（約 800 バイト）は、S3 で削ると決まっている（オーナーの決定 2026-11-26。決定 22 で S3b に決めた。`docs/features/request-to-plan-s3.md`）。
- **代替案**: S3b（`docs/features/request-to-plan-s3.md`）で削る項を、この区切りで前倒しして削る。その項の役目（取りまとめの課題を分ける回答の扱い）は S3b まで要るので採らない。
- **影響範囲**: `internal/invoker/prompts.go` の上限と、上限を書いた文書。flywheel#1327（S1 で残した点）の、指示文の上限の項は、この決定で片付く。

## クリティカル設計決定（S1・実装済み）

受入基準の出どころ・識別の付け方・受け持たない基準を書ける口・指示文の分量の 4 つは、案を比べたうえでオーナーが決めた（2026-11-26）。

### 受入基準の出どころ: 課題が指す仕様の文書を core が読む（オーナーの決定 2026-11-26）

- **採用案**: 課題に仕様の文書の場所を持たせ、core がその文書の `## 受入基準` の節を読んで一覧を作り、計画を作る判断点へ渡し、出力を突き合わせる。仕様の文書の場所を持たない課題では、検査をしない（計画の本文に、検査していない旨を出す）。
- **理由**: 漏れを機械的に弾くには、判断点が書いたものでない一覧が要る。受入基準の正本は仕様の文書で（決定 4・12）、既存の仕様は 1 本に 87〜478 件の基準を持つ。判断点に書き写させると、写し漏れを仕組みが見つけられず、出力も大きくなる。
- **代替案**:
  1. 計画の出力に受入基準の一覧を書かせ、core は出力の中だけを検査する。ストアもコマンドも変えずに済むが、文書から一覧への写し漏れは機械的に見つからない（判断点が挙げた基準の割り当て漏れと、無い識別だけを弾く）。基準が数百件の文書では写しが大きい。
  2. 課題の達成条件から読む。達成条件は 2000 文字までで、仕様の受入基準は入らない。達成条件は計画を作る判断点自身が書き直す欄でもあり、判断点が書いたものでない一覧にならない。
  3. 上流の Issue の本文の `## 受入基準` の節を読む（claude-harness の分解と同じ出どころ）。Issue の無い課題・手で書いた Issue に効かず、仕様の文書から Issue へ写す作業（Issue を作るスキル）が残る。
- **残る危うさ**: core が読むのは、そのときのワークスペースの作業ツリーのファイルで、既定ブランチの最新とは限らない（計画を作る判断点が読むものと同じ）。本体のクローンを最新にする仕組みは足さない。読んだ一覧は計画に書き足し、承認の画面で件数が見える。文書がまだ入っていないときは「着手しなかった」で止まる。
- **影響範囲**: `internal/core`・`internal/cli`・`internal/view`・ストア。後続の S2（仕様の文書づくりの委譲）は、できた文書の場所を課題へ書く形でこの欄を使う。

### 判断点に、基準の識別と済みの印を見せる（オーナーの決定 2026-11-26。実装の途中で見つかった穴の直し）

- **採用案**: 計画を作り直すときの区画「受入基準」に、済みのタスクが受け持った基準の印「済み」を付ける。「足す」の形の呼び出しの入力にも、承認した計画に書き足した一覧から作った区画「受入基準」を入れる。
- **理由**: 判断点は、見えている識別しか写せない。済みの件数だけでは、どの基準が済みかが分からず、済みの基準を重ねて割り当てる計画になりうる。「足す」の形に一覧が無いと、足すタスクの受け持ちは実質いつも空になり、委譲へ渡す文面に基準が出ない。
- **代替案**: 見せずに進め、指示文で「確かめられない基準は、受け持つか見送りに書く」と逃がす。動くが、上の 2 つが残るので採らない。
- **影響範囲**: `internal/core`（計画の形と「足す」の形の入力）・`internal/invoker/prompts/j2.md`。判断点の呼び出しは増えない。

### 受け持たない基準を、理由つきで書ける口を置く（オーナーの決定 2026-11-26）

- **採用案**: 計画の出力に、この計画で受け持たない受入基準を、理由つきで書ける口（`deferred_criteria`）を置く。書いた基準は漏れに数えず、計画の本文の節「受入基準の受け持ち」に文の先頭・識別・理由を出す。オーナーは計画の承認で認める。
- **理由**: 済みのタスクの後の作り直しや、続きを決めるタスクのある計画が、すべての基準の受け持ちを求められて止まらないようにする。黙った取りこぼしは弾き、理由を書いた見送りは人が承認で見る。
- **代替案**: 口を置かず、すべての基準をどれかのタスクが受け持つ計画だけを通す。続きを決めるタスクのある計画が、最初の計画で通らなくなるので採らない。
- **影響範囲**: 計画の出力の型・検査・計画の本文。

### 受入基準の識別: 文の内容から導く（オーナーの決定 2026-11-26）

- **採用案**: `AC-` に、基準の文（空白を正規化したもの）の SHA-256 の 16 進の先頭 8 桁を付ける。
- **理由**: 文書に基準を足しても並べ替えても、ほかの基準の識別が変わらない。文を変えた基準は別の識別になり、受け持ちを決め直すことになる（変えた基準は確かめ直すべきなので、これでよい）。文書の書式を変えず、仕様づくりのスキル（claude-harness）も変えずに済む。判断点が識別を写し間違えると、ほぼ必ず無い識別になり、検査で落ちる（連番では、写し間違いが別の有る識別になって通る）。
- **代替案**:
  1. 文書の並び順の連番（`AC-1`。claude-harness と同じ）。読みやすいが、途中に基準を足すと後ろがずれ、済みのタスクの受け持ちが別の基準を指す。
  2. 文書の行に識別を書く。最も安定するが、文書の書式と仕様づくりのスキルの出力を変えることになり、既存の文書にも振り直しが要る。
- **影響範囲**: `internal/core`（抜き出しと識別）。人が読む所（計画の本文）では、識別を単独で出さず、文の先頭を添える。

### DB スキーマ: 課題の仕様の文書の場所と、タスクの受け持ち

- **採用案**: マイグレーション 1 本で、`challenge` に `spec_path`（TEXT。NULL 可）、`task` に `covers`（識別の JSON の配列を入れた TEXT。NULL 可）を足す。書き出しと読み込み（`export`・`import`）に 2 つの列を入れる。
- **理由**: 計画を作り直すとき、済みのタスクの受け持ちを数えるのに、タスクの行に残っている必要がある（足す形で足したタスクは、計画の構造化した出力に載っていない）。
- **代替案**: 受け持ちを計画の構造化した出力だけに持つ。足したタスクと、版をまたぐ済みのタスクを引けないので採らない。
- **影響範囲**: ストアの版が 1 つ進む。既存の行は NULL のまま（検査をしない課題・受け持ちの無いタスクとして読む）。

### 指示文の分量: 上限を、足した文の分だけ上げる（オーナーの決定 2026-11-26）

- **採用案**: 計画を作る判断点の指示文の上限（いま 17,713 バイト。本文は 17,413 バイト）を、足した文の分に余白 300 バイトを足した値へ引き上げる。足す文の見込みは約 1,200〜1,400 バイトで、19 KiB を超えない。対話の欄の指示文の上限（いま 4,682 バイト。本文は 4,563 バイト）は、足した文の分だけ引き上げる（見込みは約 400 バイト。5.5 KiB を超えない）。
- **理由**: これまでの引き上げと同じ決まり（足した文の分だけ）。いまの指示文の文は、どれも起きた不具合から足したもので、この区切りの中で削る文を選ぶと、振る舞いが変わる範囲が広がる。
- **代替案**: 削って収める。削る候補は、計画の点検の「取りまとめの課題を子の課題に分けるという回答のとき」の項（約 800 バイト）。ただし、この項の役目は、取り込んだ Issue の仕分けを分類の判断点へ移す区切り（S3）で変わるので、削るのは S3 で行う（決定 22 で S3b に決めた。`docs/features/request-to-plan-s3.md`）。
- **S3b で削る文**: 計画の点検の「取りまとめの課題を子の課題に分けるという回答のとき」の項は、S3b（GitHub に書く部分の区切り。`docs/features/request-to-plan-s3.md`）で削り、上限もその分だけ下げる（オーナーの決定 2026-11-26）。S1 では触らない。
- **影響範囲**: `internal/invoker/prompts.go` の上限と、上限を書いた文書。

## 機能全体の設計

### 計画を作る判断点の出力の型に足す項目

- タスクの要素に `lands_spec`: 真偽。省略と `null` は偽と読む。計画の形と「足す」の形の出力の型（どちらも、知らない項目を許さない）の両方に足す（「足す」の形では、真なら core が不正な出力にする）。

### 計画の構造化した出力へ core が書き足す項目

- 根の `acceptance_criteria`（S1 で足した）に、`draft`（真偽）と `base_path`（文字列か `null`）を足す。

### 流れ

1. オーナーが対話の欄で、下書きを `.flywheel/specs/<名前>.md` に書く（仕様づくりのスキルを使ってよい）。既存の文書の直しなら、全文を写してから直す。
2. 対話の欄が、`flywheel create --spec .flywheel/specs/<名前>.md`（直しなら `--spec-base` も）で課題を作る。
3. 計画を作る判断点が、下書きの受入基準でタスクに分ける。入れるタスクを 1 件決める。core が、網羅と、入れるタスクの数と順を検査する。
4. オーナーが計画を承認する。
5. 入れるタスクの委譲が、渡された全文をリポジトリの文書として入れる（統合先を使う計画では統合ブランチへ。使わない計画では、実装と同じ PR で）。
6. 課題が取り下げになるか、完了して反映まで済むと、core が下書きを消す。

### 実装計画（タスクへの分解の見通し）

分け方の案（最終の分解は、計画を作る判断点が行う）。

1. 土台: マイグレーション、下書きの見分け、置き換える元の文書の場所（core・`create`・`edit`・`show`・詳細の値・書き出しと読み込み）、`.gitignore`。
2. 計画の検査と記録: 入力の区画、出力の型、入れるタスクの検査、一覧の書き足し、タスクの記録、計画の本文。
3. 委譲と後片付け: タスクの文面、委譲の対象を選ぶときの読み直し、標準入力のデータの区画、下書きの削除。
4. 指示文: `j2.md`・`chat.md`・上限。
5. 文書。

順は、1 → 2 → 3。4 は 2 の後。5 は 3 の後。

## 受入基準（S1・実装済み）

S1 の受入基準。core の基準はストアを使う試験で、コマンドの基準はコマンドを起動する試験で、指示文の基準は文書を読む試験と分量の検査で確かめる。

### 課題の仕様の文書の場所（core・cli）

- [ ] `flywheel create --title <題名> --spec docs/x.md` で作った課題の詳細（`show --json`）の `spec_path` が `docs/x.md` になる。
- [ ] `--spec` を付けずに作った課題の `spec_path` は `null` になる。
- [ ] `flywheel edit <課題> --spec docs/y.md` で、課題の `spec_path` が `docs/y.md` に変わる。
- [ ] `flywheel edit <課題> --spec ""` で、課題の `spec_path` が `null` になる。
- [ ] `flywheel create` の `--spec` に絶対パスを渡すと、検査の誤りになる。
- [ ] `flywheel create` の `--spec` が検査の誤りになったとき、課題は作られない。
- [ ] `flywheel edit` の `--spec` が検査の誤りになったとき、課題の `spec_path` は元の値のまま残る。
- [ ] `--spec` に `..` でワークスペースの外へ出るパスを渡すと、検査の誤りになる。
