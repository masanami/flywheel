## 概要

M4.5 は、新しい flywheel が旧 claude-flywheel から仕事を引き取る（M5）前に、旧側の run-cycle と reflect が持っていて新側に無い 3 つの仕事を埋める段である。1 つ目は承認した本番反映（既定ブランチへの PR のマージ）を人の手作業なしに実行すること、2 つ目は課題どうしの依存（先行課題が終わるまで着手しない）を持つこと、3 つ目は周の結果から学びを残し、それを集計して flywheel 自身の改修を提案し、効果を指標で確かめることである。

本仕様はこれを 4 つのスライスで満たす【決定 2026-10-22 オーナー M45H1】。S1 は承認済みの `release` の実行で、承認した時点の PR の head（最新のコミット）を記録し、実行の時点の head と一致するときだけ `gh pr merge --match-head-commit` でマージする。S2 は課題の依存で、旧台帳の `依存` に当たる関係をストアの表に持ち、依存先が完了してその `release` の実行も済むまで委譲を起動しない（【決定 2026-10-22 オーナー M45H12】）。S3 は学習の記録と効果の測定で、差し戻し・検証の失敗・実行の失敗などを core が 1 回の発生ごとに 1 行として記録し、判断点 J6 が原因を 3 分類して記憶（Markdown）を書き、`flywheel metrics` が指標を LLM なしで数える。S4 は判断点 J8 の改修提案で、未処理の発生がたまったら改修案を課題として起票し、通常の計画・完了の承認を通す（D21）。

いちばん重い判断は S1 の安全性である。守る対象は「人が承認していないコードが本番に入ること」で、守る相手は承認の後に PR へ push する者（委譲の子・他の作業者・オーナー自身の取り違え）と、承認なしにマージを起こしうる LLM のセッションである。実行の条件を「承認の記録に残した head と、実行の直前に GitHub が返す head が一致する」ことに置き、一致の検査を GitHub 側の `--match-head-commit` にも重ねる。実行の口（`flywheel op exec`）は承認を作らず、承認済みのものを実行するだけなので、端末での確認を求めない。

journal（周ごとの散文）と J7 要約は作らず、事実はストアに、学びは J6 の記憶に寄せると決めた（§16 Q6・【決定 2026-10-22 オーナー M45H6】）。課題未満の引き継ぎ事項（flywheel#109）は受け箱の表を作らず、記憶の草案は J6 の記憶へ、フォローアップは課題へ送る（【決定 2026-10-22 オーナー M45H7】）。

## 背景・目的

- M4 までで、新しい flywheel は課題を取り込み、分類・計画・委譲・検証を経て完了確認待ちまで進め、ボードと対話で承認できる（M4 の完了の目安は 2026-10-19 に満たされた＝M4 §スライス）。だが承認済みの `release` を実行する仕組みは無い（M1 は「承認の記録と可視化まで」、M4 は M4H10 で M4.5 へ送った）。いまの不可逆操作の状態は `pending`・`approved`・`rejected` の 3 値だけで、実行済みを表す状態も、承認した head の記録も無い【実コード確証 high: `internal/core/enums.go` の操作の状態・`internal/core/internal/store/migrations/0001_initial.sql` の `operation`】。完了の承認の要約は UI の経路でだけ PR の head を取って表示しており、端末と対話の承認（本番に届く承認を受ける唯一の経路）は head を取っていない【実コード確証 high: `internal/server/approval.go`・`internal/cli/approval.go`】。
- 旧側の承認済みのマージは、人が対話で昇格を承認した後に親の LLM が同じ周で実行している。手順に書かれているのは「マージ → 外部の実状態でマージ済みを確認 → 完了とアーカイブ」の順序だけで、マージの方式・CI と mergeable の確認・承認した head との比較・失敗したときと既にマージ済みだったときの扱いは書かれていない【旧 claude-flywheel `skills/run-cycle/SKILL.md`・origin/main・ドキュメント確証 high】。新側では、この空白を決定的な規則にする。
- 課題どうしの依存は、旧台帳の `依存`（先行課題の ID のカンマ区切り）として運用されている。M5 で旧台帳を移すとき、受け皿が要る（設計書 §6）。新側のストアには依存の表が無い【実コード確証 high】。
- 旧 reflect は処理済みの印を記憶のファイル単位で付けていたため、内省の後に同じファイルへ追記された再発が集計から漏れた（2026-10-11 の実測で 13 件中 9 件。flywheel#177）。新側は 1 回の発生を 1 行としてストアに持ち、処理済みの印も行ごとに付ける（設計書 §7「集計の単位は 1 回の発生とする」）。
- 新しい flywheel の Go のコードは、ポジション定義のファイルを判断点へ渡すだけで、ドメイン記憶・journal の Markdown を読み書きしない【実コード確証 high: `internal/` に該当のコードが無い】。設計書 §17 の M4.5 の完了の目安「新システムだけで記憶が育ち」を満たすには、記憶を書く経路と、書いた記憶を判断点が読む経路の両方が要る。

## ユーザーストーリー

- オーナーとして、完了を対話か端末で承認したら、その PR が、承認したときに見たコミットのまま既定ブランチへマージされてほしい。承認の後に誰かが push していたら、マージせずに承認をやり直させてほしい。
- オーナーとして、「C-20 は C-18 が終わってから」と伝えれば、C-18 が完了して本番に入るまで C-20 の委譲が始まらないでほしい。
- オーナーとして、差し戻した理由や失敗の傾向がたまったら、flywheel が「どの指示文・記憶・スキルを、どの指標を良くするために直すか」を課題として出してほしい。採るかどうかはいつもどおり計画の承認で決めたい。
- オーナーとして、改修を入れる前と後で、差し戻し率・resume の回数・1 課題あたりの費用・承認の件数を並べて見たい。
- M5 で移す Tom（旧 claude-flywheel のエージェント）として、旧台帳の `依存` と記憶のファイルを、意味を変えずに新しいワークスペースへ持ち込みたい。

## 機能要件

用語: **実行**＝承認済みの不可逆操作を flywheel が外部へ行うこと（S1 では `release` の PR のマージだけ）。**承認した head**＝`release` を承認した操作の ① で取得した、PR の head のコミット SHA（M1 の 2 段階の API の ①。§S1 の承認の時点の head）。**実行の試行**＝1 つの不可逆操作に対する実行の 1 回の試み（`operation_execution` の 1 行）。**依存**＝課題 A が課題 B の完了を待つ恒久的な関係（A を依存元、B を依存先と呼ぶ）。**発生**＝学習の集計の単位になる 1 回の出来事（差し戻し 1 回・J5 の `not_met` 1 回など。`occurrence` の 1 行）。**改修課題**＝J8 の改修提案から起票した課題。**記憶**＝ワークスペースの記憶の置き場（`.flywheel/agent.json` の `memory_dir`）にある Markdown のファイル。

各要件の末尾の `[S1]`〜`[S4]` は、その要件を実装するスライスを表す（§スライス）。S3・S4 の受入基準は、そのスライスを実装対象にするときに §受入基準の末尾へ足す（M4H14 の流儀。【決定 2026-10-22 親 M45P1】）。

### 承認の時点の head の記録 [S1]

- [ ] 端末（`tty_confirm`）と対話（`relayed`）の承認の ① は、承認によって承認される `release`（完了の承認で D12 により同時に承認されるもの、または `<OP-ID>` の単独の承認の対象）ごとに、参照の PR の head を GitHub から取得する（M4 の UI の経路が使っている `ResolveReleaseHeads`・`GetPullRequestChecks` と同じ取得）【決定 2026-10-09 オーナー M4H10 から導く】
- [ ] ① が承認の対象とするのは、head を取得でき、参照の PR のリポジトリが `.flywheel/connectors.json` の `repos[].remote` にある `release` だけである。それ以外（参照が GitHub の PR の URL でない・取得に失敗した・リポジトリが宣言に無い・検証の head と異なる〔M45H11〕）は、完了の承認では同時に承認せず未承認のまま残し、要約にそのことと理由を示す。単独の承認では承認を成立させず `upstream_unavailable` で終わる【決定 2026-10-22 親 M45P2】
- [ ] ② の入力は 2 つの組である。承認する `release` の ID と head の組と、① が対象から外した `release` の ID の組である。core は、2 つの ID の和集合が ② の時点の課題の未承認の `release` の全体と一致するときだけ承認し（一致しなければ何も書かず `conflict`。M1 の版の照合と同じ扱い）、承認するのは前者の組だけとする。外した `release` は `pending` のまま残る。外す理由（head の取得失敗・PR の URL でない・リポジトリが宣言に無い・検証の head と異なる）の判定は CLI が行い、core は GitHub を読まない。検証の head は core の ① の読み取り（`ApprovalPreview`・`OperationApprovalPreview`）が `release` ごとに `VerifiedHeadSHA`（NULL は記録なし）として返し、CLI が ① の head と比べる。head の値は ① のものを使い、② で取り直さない【仮定】
- [ ] ② は、`release` の承認の記録（`approval` の `kind=release` の行）の `head_sha` に、① で取得した head を残す【決定 M4H10 から導く／列の形は §データモデル】
- [ ] 外した理由は `head_unavailable`（取得に失敗）・`not_a_pr_url`・`repo_not_declared`・`verified_head_mismatch`（検証の head と異なる）・`merged_unapproved`（直前の試行の結果が `merged_unapproved`。M45H16）の閉集合で、端末の要約は理由の名前と説明の文を、`--relayed --json` の成功の出力は `excluded_releases`（`[{"operation_id", "reason"}]`）を示す。単独の承認の `upstream_unavailable` のエラーの詳細にも同じ理由の名前を入れる【仮定】
- [ ] 端末の要約は、承認の対象の `release` ごとに head の短縮形（先頭 12 文字）と完全形（40 文字）を示す【仮定】
- [ ] `--relayed --json` の成功の出力は、同時に承認した `release` ごとに `operation_id` と `head_sha`（完全形）を持つ（§IF / API）【仮定】
- [ ] ① で取得した PR の head が、その課題の最後の J5 の `met` の入力にした head と異なるときは、その `release` を同時に承認せず、要約に「検証の後に push されたコミットがある」ことを示す（外した理由 `verified_head_mismatch`）。単独の承認では承認を成立させず `upstream_unavailable` で終わる【決定 2026-10-22 オーナー M45H11】
- [ ] J5 の `met` を課題へ写すとき、core は J5 の起動の前に取得して入力にした PR ごとの head（写像の時点で取り直さない）を、J5 が参照した直前の委譲の run の `kind=pr` の成果物の行（URL を (repo, 番号) に正規化して一致するもの）の `verified_head_sha` に残す。書き込みは T8（`met` の遷移）と同じトランザクションで行う。`met` が実物の個数の不一致で保留に読み替えられたときと、`not_met`・`uncertain` のときは書かない【決定 M45H11 から導く／列の置き場と受け渡しは【仮定】】
- [ ] 比べる相手（最新の検証の head）は、`release` の参照と (repo, 番号) が一致する成果物の行のうち、`verified_head_sha` が NULL でない行で `run_artifact.id` が最大のものの値とする。`release` の参照の正規化は `parseReleasePullRequestRef`（末尾の `/files` 等を無視する）、成果物の参照は `parsePullRequestURL` を使う。該当する行が無ければ「検証の head の記録が無い」とする【仮定】
- [ ] 検証の head の記録が無い `release`（`op add` で人が登録したもの・本仕様のマイグレーションの前に J5 を通ったもの）は、比較をせずに承認の対象にし、要約に「検証の head の記録が無い」ことを示す【決定 2026-10-22 オーナー M45H15】
- [ ] UI の経路（`ui`・`none`）は `release` を承認しない（M4H20）ので、本節の head の記録は UI の承認では起きない【決定 M4H20】
- [ ] core の公開 API の変更: 課題の承認の要求（`ApprovalRequest`）に `release` ごとの head の組（既存の `ReleaseHead` の形）を、不可逆操作の単独の承認の要求（`OperationApprovalRequest`）に head を足す。head を持たない `release` を承認しないことは core が保証する（CLI に任せない）。head が空の組・和集合が合わない入力・承認する組の head が最新の検証の head（NULL でないとき）と異なる入力は、core が何も書かず `conflict` で拒否する（CLI の判定と core の検査を重ねる）【仮定】

### 承認済みの `release` の実行 [S1]

- [ ] flywheel は、状態が `approved` で、まだ実行していない `release` を実行する。`delete`・`external_send`・`other` は実行しない（承認済みのまま残り、人が外で行う）【決定 2026-10-22 オーナー M45H3】
- [ ] 実行の口は 2 つある。個別の操作 `flywheel op exec [<OP-ID>]`（ID を省けば承認済みで未実行の `release` をすべて、ID の昇順に）と、`flywheel cycle` の最初の段 `release` である。どちらも同じ core の処理を呼ぶ（D11）【決定 2026-10-22 オーナー M45H2】
- [ ] `op exec` は、M3 の個別の操作（`run`・`--auto`）と同じく `cycle` の表に 1 行（`trigger` は `op exec`）を作り、サイクルの排他ロックは取らない。`cycle` の `release` の段は `cycle` が取ったロックの中で動く。同じ `release` の二重の実行は、下の試行の一意索引で防ぐ【決定 M3 §用語「周」から導く】
- [ ] 実行の口は承認を作らないので、端末での確認を求めず、`CLAUDECODE` が設定されていても拒否しない。委譲の子は M3H13 の目印により `flywheel` の全コマンドを拒否されるので、`op exec` も実行できない【決定 M3H13 から導く】
- [ ] 実行は LLM を呼ばない（決定的）【決定 設計書 §7 の手順 6 と同じ扱い】
- [ ] 実行の前に、参照の PR を GitHub の REST（`gh api repos/<owner>/<repo>/pulls/<番号>` と、いまの `GetPullRequestChecks` が取るチェック）で読み取り、§IF / API「実行の判定の順」の順に条件を評価する。最初に当たった条件の結果を試行の結果とし、すべての条件を通ったときだけマージを依頼する【仮定: 順の細部】
- [ ] チェックの合否は §IF / API「チェックの分類」の表で決める。完了の判定は J5 の待ちと同じ規則（`checkCompleted`）を使う。チェックが 0 件なら合格とする【決定 M3P18 の完了の判定から導く／合否の分類は【決定 2026-10-22 オーナー M45H4】】
- [ ] マージの可否は REST の `mergeable` で決める（`true` は可、`false` は `not_mergeable`、`null`〔GitHub が計算中〕は `waiting_checks`）。`mergeable_state`（レビュー必須の `blocked` など）は読まず、ブランチの保護で拒まれたときはマージの依頼の失敗（`merge_failed`）になる【仮定】
- [ ] マージは `gh pr merge <PR の URL> --<方式> --match-head-commit <承認した head>` で依頼する。方式はリポジトリの宣言の `merge_method`（`squash | merge | rebase`、省略は `squash`）とする【決定 2026-10-22 オーナー M45H4／親 M45P8】
- [ ] マージの依頼に `--admin`・`--auto`・`--delete-branch` を付けない。ブランチの削除は GitHub のリポジトリの設定に任せる【決定 2026-10-22 オーナー M45H4】
- [ ] マージを依頼した後、PR をもう一度読み取る。状態が `merged` で、PR の head が承認した head と一致すれば実行済みにする。`merged` でなければ実行済みにせず、結果を `merge_unconfirmed`（数えない待ち）とする（`gh` は条件により自動マージの予約に切り替えることがあり、反映が遅れることもあるため）【実コード確証 high: `gh pr merge --help`（gh 2.67.0）の「If required checks have not yet passed, auto-merge will be enabled.」】
- [ ] 依頼の後の読み取りで `merged` だが PR の head が承認した head と異なるときは、結果を `merged_unapproved` とする（依頼の前の読み取りと同じ扱い）【決定 M3P15 から導く】
- [ ] 実行済みにした `release` は、不可逆操作の版と課題の版をそれぞれ 1 上げ（M1 の「その課題の不可逆操作の変更で課題の版を上げる」）、状態を `executed` にし、実行の日時（`executed_at`）とマージのコミット SHA（REST の `merge_commit_sha`。`merge_commit`）を残す【決定 M4H10 から導く／状態の名前は 2026-10-22 親 M45P4】
- [ ] 実行を試みるたびに、実行の試行を 1 行記録する（開始・終了の日時・結果・承認した head・観測した head・詳細・pid・host）。試行の結果は §IF / API の閉集合とする【仮定】

## 非機能要件

- セキュリティ（S1）: 本番に届く操作（マージ）は、承認の記録の head と GitHub の head の一致を core と GitHub（`--match-head-commit`）の 2 か所で検査する。実行の口は承認を作らないので、LLM が `op exec` を実行しても、承認していない head は本番に入らない。`gh` の認証に委ね、トークンを宣言に書かない（M3）。
- セキュリティ（S3）: J6 の入力には取り込み元の本文（外部由来の自由記述）が入るので、J6 の出力がそのまま記憶になり、後の判断点の入力へ戻る経路ができる。書き込みは置き場の中の作成と追記に限り、件数と大きさに上限を置き、作業ログに本文のハッシュを残す。記憶の置き場は Git で追跡されるので、人が差分で見つけられる（§クリティカル設計決定 3）。
- 費用: J6 は課題 1 件につき 1 回（未分類の発生があるときだけ）、J8 はしきい値に達したときだけ呼ぶ。判断点ごとの上限額（`judgment_budget_usd`）に `J6`・`J8` を足す【仮定: 既定は J6 2・J8 5】。
- 動作環境: macOS と Linux（M1 A2）。

## 技術的な制約・方針

- 置き場: 実行・依存・発生・指標の規則は `internal/core`、マイグレーションは `internal/core/internal/store`、マージの依頼と PR の読み取り（マージの可否・マージのコミット）は `internal/adapters/github`、J6・J8 の指示文は `internal/invoker/prompts/`、CLI は `internal/cli`。新しいパッケージは作らない（`CLAUDE.md` のモジュール構成）。
- `internal/adapters/github` に初めて書き込み（`gh pr merge`）が入る。M3 の照合の「`gh` の呼び出しはすべて GET」は照合の規則として残し、マージの依頼は実行の口だけが呼ぶ。`CLAUDE.md` の adapter の責務の行（「取得」）を S1 の実装チケットで更新する。
- 記憶のファイルの書き込みは core が行う（`internal/core` に、ストアの外のファイルを書く初めての処理が入る）。書き込み先は `memory_dir` の中に限る。
- 本番の依存の上限（標準ライブラリ・`modernc.org/sqlite`・`golang.org/x/term`）は広げない。
- テスト: core は実ストア、`gh` は偽の `gh`（M2 の方式。`pr merge` の引数を記録し、固定の応答を返す）、`claude` は偽の `claude`（M3）。本物の GitHub へは接続しない。

### 現行（旧 claude-flywheel）から引き継ぐ振る舞い・引き継がない振る舞い

| 旧側の挙動 | 扱い | 理由 |
|---|---|---|
| 承認の後、親の LLM が同じ周の中で既定ブランチへマージする（run-cycle 手順 4） | 置き換える: core が決定的に実行する（S1） | LLM に進行管理をさせない（P4）。承認した head との一致を検査する |
| マージを先にしてから完了とアーカイブを書く（逆順だとマージに失敗した課題が台帳から消える） | 引き継がない（順序は「承認 → 実行」） | 承認済みで未実行の `release` がストアに残り、`status` に出続ける |
| マージの方式・CI・mergeable・head の比較・失敗時の扱いが手順に無い | 新しく決める（S1） | 旧側の空白。新側では決定的な規則にする |
| 台帳の `依存`（先行課題の ID のカンマ区切り）。列挙した課題がすべて `完了` するまで着手しない | 引き継ぐ（S2）。「完了」に、その課題の `release` の実行まで含める（【決定 2026-10-22 オーナー M45H12】） | 旧側は完了の前にマージしていたので、完了はマージ済みを意味した。新側は D12 で完了の後にマージするので、同じ意味を保つには実行まで待つ |
| 存在しない ID・自己参照・循環を起動しない側へ倒す（`ledger-deps.rb`。循環は自動で解かない） | 引き継ぐ（S2）。登録の時点で拒否し、ストアに入ってしまった循環は起動しない | 旧側は台帳を後から検査したが、新側は書き込みの口が core の 1 本なので登録の時点で止められる |
| 依存を書くのは計画の手順（run-cycle 手順 2）。既存のエントリは遡って埋めない | 引き継ぐ（J2 の任意の出力。【決定 2026-10-22 親 M45P3】）。CLI でも足せる | M5 で移した後も同じ担い手にする |
| 取り込みを解除された依存先は台帳から消え、後続は `missing` のまま起動されない（規定なし） | 置き換える: 依存先は消えず、上流の状態を添えて `status` に出す | 新側は取り込みの解除で課題を消さない（M2） |
| experience を `outcome`・`target`・`signal`・`recurrence` 付きで記憶のファイルに残す | 記憶の形は引き継ぐ。集計の単位はストアの発生の行に移し、`recurrence` を数えない | 設計書 §7「集計は本文を読まない」。同じ症状の再発を同じファイルへ追記しても、集計は行で数える |
| reflect の処理済みの印（記憶のファイルの `reflected: <日付>`） | 引き継がない: 発生の行ごとに処理済みにする | 2026-10-11 の実測で 13 件中 9 件が漏れた（flywheel#177） |
| reflect の起動（N 周ごと〔既定 10〕・同種の bad の再発 2 回以上・手動）。周の終わりに催促を出す | 置き換える: しきい値（未処理の `bad` の件数）と手動（【決定 2026-10-22 オーナー M45H8】） | 周という単位は新側では課題の進み方と結びつかない（D11） |
| reflect の改修の対象（position・recall・brief・ローカルの skill は差分、共通の skill は upstream の Issue、`priority-policy.md` は所見だけ） | 層の分け方を設計書 §7 の 4 層に置き換える（【決定 2026-10-22 オーナー M45H9】） | D21 |
| 見送った提案を覚えておく仕組みが無い | 新しく足す（S4。【決定 2026-10-22 親 M45P10】） | 同じ提案の繰り返しを防ぐ |
| journal（1 周 1 ファイル・定型 5 節）と `journal/index.jsonl` | 引き継がない（【決定 2026-10-22 オーナー M45H6】） | 事実はストアにある。旧側の journal の読み手は reflect と人で、次の周は読んでいない。新側の J8 は発生の行を読む |

## クリティカル設計決定

### 1. 承認済みの `release` の実行の担い手と条件（セキュリティ・外部システム連携）【決定 2026-10-22 オーナー M45H2・M45H4・M45H5】

- **採用案**: core が決定的に実行する。口は `flywheel op exec` と `cycle` の最初の段 `release`。承認の ① で取った head を承認の記録に残し、実行の直前の読み取りで head・状態・base・チェック・マージの可否を確かめ、`gh pr merge --match-head-commit` で依頼し、読み取りで `merged` を確かめてから実行済みにする。条件を満たさないときは、待つか承認を取り消す。
- **理由**: M4H10 の「承認した head と実行する head が一致するときだけ」を、core の比較と GitHub の比較の 2 か所で守れる。core の比較だけだと、読み取りと依頼の間の push を防げない。GitHub の比較だけだと、承認した head の記録が無ければ何と比べるかが決まらない。実行を `cycle` の最初の段に置くと、前の周の後に受けた承認を次の周の初めに実行でき、同じ周の委譲の段で依存（S2）が満たされる。
- **代替案**: B: `approve` の ② の中で同期してマージする（承認と実行の間の時間が最小になる。だが ② が外部の書き込みとその失敗を抱え、承認の記録と GitHub の状態の両方を 1 つの操作で扱うことになる。対話の承認を受ける LLM が待たされる）／C: 委譲の子に `/pr-merge` で実行させる（LLM に本番の操作を渡すことになり、子は `flywheel` も既定ブランチへのマージも禁じられている＝M3）／D: server が実行する（P6 に反する。server は任意の付加物）。
- **影響範囲**: `operation` の状態の閉集合・`approval` の列・新しい表 `operation_execution`・`internal/adapters/github` の書き込み・CLI の `op exec`・`cycle` の段の閉集合（M3 の `phases`）。

### 2. 依存の満たし方（状態機械への影響・DB スキーマ変更）【決定 2026-10-22 オーナー M45H12】

- **採用案**: `challenge_dependency`（依存元・依存先・作成の日時。組で一意）を足す。依存先が「完了」かつ「`release` に未承認・承認済みで未実行のものが無い」ときに満たす。委譲の起動の判定だけに使い、状態は足さない。
- **理由**: 旧側の「完了」は、マージの後にだけ付いた。新側は D12 で完了の後にマージするので、完了だけで満たすと、依存元の子が依存先の変更の入っていない既定ブランチから作業を始める。状態を足さず起動の判定に置くのは、旧側と同じで、M1 の遷移表を変えないため。
- **代替案**: B: 依存先が完了なら満たす（旧側の字面に合う。だが上の理由で依存先の変更を待たない）／C: 依存元の状態に「依存待ち」を足す（遷移表 T1〜T15 を変える。`status` の注記で足りる）。
- **影響範囲**: マイグレーション・委譲の起動の判定（`not_started` の理由の閉集合）・J2 の出力・`show`・`status`。

### 3. 判断点の出力からワークスペースのファイルを書くこと（セキュリティ）【決定 2026-10-22 オーナー M45H10／親 M45P7】

- **採用案**: J6 は記憶の作成と追記を出力し、core が `memory_dir` の中に書く。上書き・削除・改名は持たない。件数と大きさの上限・作業ログの本文のハッシュを持つ。core はコミットしない。
- **理由**: 判断点は読み取りの道具だけを持つ（M3H4）ので、書くのは core になる。J6 の入力には取り込み元の本文が入るので、出力に書かれた指示めいた文が記憶として残り、後の J2・J3 の入力へ戻りうる。上書きと削除を持たなければ、既存の記憶を壊すことはできず、足された分は Git の差分として人が見つけられる。
- **代替案**: B: J6 の出力を草案としてストアに置き、人が承認したものだけを書く（安全だが、承認の件数が増え、「新システムだけで記憶が育つ」の目安に人の操作が要る）／C: 記憶を書く仕事を委譲の子（書き込みの道具を持つ）に渡す（費用が大きく、子の作業ディレクトリはワークスペースではない）。
- **影響範囲**: `.flywheel/agent.json` の `memory_dir`・上限のキー・J6 の出力の検査・作業ログ。

### 4. 発生の記録（DB スキーマ変更）【決定 2026-10-22 親 M45P5】

- **採用案**: `occurrence`（課題・周・run・種類・参照・良し悪し・出どころ〔`core | j6`〕・原因・層・対象・兆候・分類した run・処理の印〔処理した改修課題か「待つ」〕・日時）を足す。core が出来事と同じトランザクションで行を作り、J6 が分類の列を埋め、J8 の写像が処理の印を付ける。
- **理由**: 設計書 §7 の「集計の単位は 1 回の発生」をストアの行で持つ。出来事と同じトランザクションで作れば、記録の漏れが起きない（設計書 §7「イベントの記録漏れ」が消えるのと同じ理由）。
- **代替案**: B: 発生を作業ログ（`activity`）から毎回導く（表は増えないが、J6 が足す発生と処理の印の置き場が無い）／C: J6 だけが発生を作る（LLM の出力に集計の母数を任せることになり、決定的に数えられない）。
- **影響範囲**: 差し戻し・J5・委譲・保留・実行の各処理に行の作成が入る。

## 機能全体の設計

### アーキテクチャ決定

- 実行（S1）は `internal/core` に新しい公開 API（承認済みの `release` の一覧と実行）を置き、`internal/adapters/github` の新しい書き込みの関数（PR のマージの依頼）を core の IF（`internal/core/upstream.go` の流儀で、書き込みの IF を別に足す）として受け取る。CLI と `cycle` が組み立てて渡す（M3 の照合と同じ組み立て方）。
- 承認の ① の head の取得は、いま `internal/server` だけが行っている（`ResolveReleaseHeads`）。S1 で `internal/cli` の `approve`（端末と `--relayed`）も同じ関数を呼び、② の入力に `release` ごとの head を渡す。② は ① と同じ未承認の `release` の集合に head が付いていることを検査する（集合が違えば M1 の版の照合と同じく `conflict`）。
- `cycle` の段は「`release` → 取り込み → 分類 → 計画 → 委譲 → 検証 → `learn`（S3）→ `improve`（S4）」の順にする【仮定】。
- 依存の判定（S2）は委譲の起動の判定（`RunDelegation` の対象の選び方）に置く。
- 発生の作成（S3）は、各出来事を書く core の関数の中（同じトランザクション）に置く。
- J6・J8 は M3 の判断点の共通の規則（入力の組み立て・出力スキーマの検証・費用・連続失敗の上限）に乗せる。

#### 実行の試行の結果の閉集合（S1）

| 結果 | 分類 | 意味 |
|---|---|---|
| `merged` | 実行済み | 依頼してマージされ、依頼の後の読み取りで `merged` と承認した head を確かめた |
| `already_merged` | 実行済み | 依頼の前の読み取りで、承認した head でマージ済みだった |
| `waiting_checks` | 待つ（数えない） | 未完了のチェックがある、または REST の `mergeable` が `null`（計算中） |
| `upstream_failed` | 待つ（数えない） | GitHub の読み取りに失敗した・`gh` が無い |
| `checks_failed` | 待つ（数える） | 失敗に分類されるチェックがある |
| `not_mergeable` | 待つ（数える） | REST の `mergeable` が `false` |
| `merge_failed` | 待つ（数える） | `gh pr merge` が失敗を返した（終了コードが 0 でない） |
| `merge_unconfirmed` | 待つ（数えない） | `gh pr merge` は成功を返したが、依頼の後の読み取りで `merged` でなかった（反映の遅れ・自動マージの予約。次の試行の先頭の読み取りで `already_merged` かを確かめる） |
| `head_changed` | 取り消す | PR の head が承認した head と異なる（未マージ） |
| `closed` | 取り消す | PR が未マージのまま閉じられた |
| `base_changed` | 取り消す | PR の base が既定ブランチでない |
| `no_approved_head` | 取り消す | 承認の記録の `head_sha` が NULL |
| `unsupported` | 取り消す | 参照が GitHub の PR の URL でない・リポジトリが宣言に無い |
| `merged_unapproved` | 取り消す（食い違い） | PR が承認した head と異なる head でマージ済み（依頼の前か後の読み取りで） |
| `limit_reached` | 取り消す | 数える結果を足した連続の回数が `failure_limit` に達した（詳細に本来の結果） |
| `interrupted` | 実行の口の都合（数えない） | 止まったプロセスの試行を回収で閉じた |

#### 実行の判定の順（S1）【仮定】

1. 承認の記録の `head_sha` が NULL → `no_approved_head`
2. 参照が GitHub の PR の URL でない・リポジトリが `repos[].remote` に無い → `unsupported`
3. PR の読み取りに失敗 → `upstream_failed`
4. PR がマージ済み → head が承認した head と一致すれば `already_merged`、異なれば `merged_unapproved`
5. PR が閉じられている → `closed`
6. base が既定ブランチでない → `base_changed`
7. head が承認した head と異なる → `head_changed`
8. 失敗に分類されるチェックがある → `checks_failed`
9. 未完了のチェックがある → `waiting_checks`
10. `mergeable` が `null` → `waiting_checks`、`false` → `not_mergeable`
11. マージを依頼し、依頼の後の読み取りで `merged` と head を確かめる → `merged`／`merged_unapproved`／`merge_failed`（依頼の失敗）／`merge_unconfirmed`（依頼は成功・未マージ）

取り消しになる条件（1・2・4 の `merged_unapproved`・5〜7）と実行済みの判定（4 の `already_merged`）を、待つ条件（8〜10）より先に評価する。承認の前提が崩れたときに待ち続けないため。3 の読み取りの失敗は状態が分からないので待つ。

#### チェックの分類（S1）【決定 2026-10-22 オーナー M45H4】

| チェック | 合格 | 失敗 | 未完了 |
|---|---|---|---|
| check run（`status` が `completed`） | 結論が `success`・`neutral`・`skipped` | 結論がそれ以外（`failure`・`cancelled`・`timed_out`・`action_required`・`stale` など） | — |
| check run（`status` が `completed` 以外） | — | — | すべて |
| 旧式のコミットステータス | `success` | `failure`・`error` | `pending`・未知の値 |

完了の判定は J5 の待ちの判定（`checkCompleted`）と同じである。必須のチェックかどうかは区別しない（GitHub の必須の設定は読まない）。

#### `show`・`status` の不可逆操作の要素に足すキー（S1）【仮定: 名前】

| キー | 型 | 意味 |
|---|---|---|
| `approved_head` | string \| null | 最新の承認の記録の `head_sha`（承認が無ければ null） |
| `executed_at` | string \| null | 実行済みにした日時 |
| `merge_commit` | string \| null | マージのコミット SHA |

`show` の `operations`・`status` の `needs_human.operations`・`approved.operations` の要素はすべて同じ形にする（M1 の「`show` の `operations` の要素と同じ形」を保つ）。`--relayed --json` の承認の成功の出力は、`approval` に加えて `releases`（`[{"operation_id", "head_sha"}]`。同時に承認した `release` だけ）を持つ。

`not_started` の理由に、`in_progress`（同じ操作の試行が終わっていない）・`not_executable`（`release` 以外・状態が `approved` でない）を足す（S1）。`not_started` の要素の JSON に `operation_id` と `detail` を足す。`operation_id` は `release` の段と `op exec` の要素では常に持ち、それ以外の段では持たない。`detail` は値が空文字のとき持たない（M3 の既存の理由も、テキスト出力の詳細があれば JSON にも出す）。値は、`in_progress` は終わっていない試行の ID、`not_executable` は `kind=<種類> state=<状態>`、S2 の `dependency` は満たされていない依存先の ID を昇順に `,`（空白なし）で連ねた文字列とする。既存のキー（`challenge_id`・`reason`）の形は変えない（M3 の形の拡張。§仕様への指摘）。`status` の `needs_human.discrepancies` の要素に、`kind: merged_unapproved`（`operation_id`）と `kind: dependency_cycle`（`challenge_ids`。S2）を足す。

| S2 | 課題の依存（表・`dep add`／`rm`・循環の拒否・委譲の起動の判定・J2 の `depends_on`・`show`・`status`・UI の詳細） | 12-20 | S1 がマージされてから（依存の満たし方が `release` の実行を参照する） |
| S3 | 学習の記録（発生の表・core の記録・J6・記憶の書き込み・判断点への記憶の索引）と効果の測定（`flywheel metrics`・run の版の記録）・フォローアップの起票 | 30-45 | S2 がマージされてから。受入基準は S3 を実装対象にするときに足す |
| S4 | 改修提案（J8・`improve`・`cycle` の `improve` の段・改修課題の起票と重複の抑え・取り下げ）と前後の比較（`metrics --compare`） | 20-30 | S3 がマージされてから（S3 の発生と指標を入力にする）。受入基準は S4 を実装対象にするときに足す |

実装対象: S2

M4.5 の完了の目安（設計書 §17）のうち、「承認した本番反映が人の手作業なしに実行される」は S1、「記憶が育ち」「指標で効果を確かめられる」は S3、「改修が提案され、課題として承認・適用され」は S4 で満たす。S2 は M5 で旧台帳の `依存` を移す受け皿で、完了の目安には書かれていないが M5 の前に要る（flywheel#301）。

## やらないこと

- `delete`・`external_send`・`other` の実行（理由: 操作の中身がドメインごとに違い、core は手段を持たない。承認の記録までとし、人が外で行う＝【決定 2026-10-22 オーナー M45H3】）
- 承認済みの `release` の自動マージの予約（`gh pr merge --auto`）と、管理者権限でのマージ（`--admin`）（理由: 予約は承認した head の検査の後に GitHub 側でマージが起きる時点をずらし、`--admin` はリポジトリの保護を迂回する）
- マージした PR のブランチの削除（理由: GitHub のリポジトリの設定に任せる。`gh pr merge --delete-branch` は手元のブランチも消すため、スロットの作業ツリーに影響しうる）
- UI からの `release` の承認と、UI からの実行の起動（理由: 本番に届く承認は端末か対話に限る＝M4H20。実行は承認済みのものを実行するだけなので、1 周の起動〔M4H11〕で足りる）
- 定期実行（理由: D17。実行は `op exec` か 1 周の起動から始める）
- 依存の状態（「依存待ち」）を状態機械に足すこと（理由: 起動の判定と `status` の注記で足りる。§クリティカル設計決定 2）
- 課題どうしの関係のグラフ・背景のタイムライン（理由: M5 の後＝flywheel#176）
- 周ごとの journal の Markdown と J7 要約（理由: 事実はストアにあり、学びは J6 の記憶に寄せる＝【決定 2026-10-22 オーナー M45H6】）
- 受け箱の表・ファイル（理由: 受け箱を 2 本目の待ち行列にしない原則を、置き場を作らないことで守る＝【決定 2026-10-22 オーナー M45H7】）
- 記憶の上書き・削除・統合（maintain）を J6 にさせること（理由: §クリティカル設計決定 3。減らす改修は J8 の `reduce` の提案として課題を通す）
- 記憶のファイルの Git のコミット（理由: 【決定 2026-10-22 親 M45P7】。D10 の書き出しのコミットと合わせて M5 で決める）
- 指標の統計的な検定・グラフの表示（理由: M4.5 の完了の目安は前後を並べて示すまで）
- 承認の絞り込み（危険の小さい課題の承認を省く）（理由: §16 Q11。M5 の後に、本仕様の承認の件数の指標を見て決める）
- 取り込み元への書き戻し（理由: M4H12）
- 旧 claude-flywheel の変更（理由: 保守モード＝D2）
- 判断点と委譲の連続失敗の数え方の共通化（理由: flywheel#300。J3 の起動判定を触るときにまとめて行う）

## 受入基準

> AC の番号は本節の `- [ ]` の上からの序数（AC-1 から）で、M1〜M4 の番号とは別の系列である。いまの範囲は S1（見出しに `S2:` の付かない節。AC-1〜AC-145）と S2（`### S2: …` の節。AC-146〜AC-197）である【決定 2026-10-22 親 M45P1】。「要人間判定」の節は、M4 と同じくスライスの出荷の判定でオーナーが確かめ、結果を出荷の判定の Issue に残す。後から足す項目は、既存の番号が動かないよう節の末尾か枝番（【AC-12a】のように付け、序数に数えない）にする。S3・S4 の受入基準は、そのスライスを実装対象にするときに節の末尾へ足す。起票（`/create-ticket`）は `実装対象:` のスライスの節だけを使う（M4P28 の流儀）。「偽の `gh`」はテストが PATH の先頭に置く実行ファイル（引数を記録し、フィクスチャの応答を返す）で、本物の GitHub へは接続しない。「承認済みの `release`」は状態が `approved` の `release` を指し、承認の記録の `head_sha` の有無を問わない（NULL のものは本仕様のマイグレーションの前に承認されたもの）。「判定の順」は §IF / API「実行の判定の順」の番号である。

- [ ] `approve <C-ID> --relayed`（完了確認待ちの課題・`--hold-release` なし）で同時に承認された `release` の承認の行は、① で偽の `gh` が返した head を `head_sha` に持つ
- [ ] `approve <C-ID> --relayed --json` の成功の出力は、`releases` に同時に承認した `release` ごとの `operation_id` と `head_sha`（完全形）を持つ
- [ ] 端末ありの `approve <OP-ID>` で承認された `release` の承認の行は、① で偽の `gh` が返した head を `head_sha` に持つ
- [ ] `approve <OP-ID> --relayed` で承認された `release` の承認の行は、① で偽の `gh` が返した head を `head_sha` に持つ

- [ ] ① の後・② の前に、① が外した `release` が差し戻されて未承認でなくなったら、② は何も書かず `conflict` で終わる

- [ ] core の課題の承認の要求に、head が空文字の組を渡すと、何も書かず `conflict` で拒否される（core の公開 API を呼んで検証する）
- [ ] core の不可逆操作の単独の承認の要求に、head が空の `release` を渡すと、何も書かず `conflict` で拒否される（core の公開 API を呼んで検証する）

- [ ] 完了した課題の `pending` の `release` は、`approve <OP-ID>` で承認できる

### 実行の条件

- [ ] `op exec` は、偽の `gh` の PR が open・base が既定ブランチ・head が承認した head と一致・チェックがすべて合格・`mergeable` が `true` のとき、`gh pr merge` を 1 回呼ぶ
- [ ] `gh pr merge` の引数は、PR の URL・`merge_method` に対応するフラグ（`--squash`・`--merge`・`--rebase` の 3 つを列挙して検証する）・`--match-head-commit <承認した head>` だけである
- [ ] `gh pr merge` の引数は `--admin`・`--auto`・`--delete-branch` を含まない
- [ ] `merge_method` を省略したリポジトリでは `--squash` を渡す
- [ ] `merge_method` が `squash | merge | rebase` の外の `connectors.json` では、`op exec` は外部を呼ばず `config_invalid` で終わる
- [ ] `merge_method` が閉集合の外の `connectors.json` では、`cycle` は周を始める前に `config_invalid` で終わる
- [ ] 依頼の後の読み取りで `merged` と承認した head を返した PR の `release` は、状態が `executed` になる
- [ ] 実行済みになった `release` は、`executed_at` を持つ
- [ ] 実行済みになった `release` は、偽の `gh` が返した `merge_commit_sha` を `merge_commit` に持つ
- [ ] 実行済みにした試行は、`entity=operation`・`action=op_execute` の作業ログを残し、`after` に結果・承認した head・観測した head・マージのコミット・契機を持つ
- [ ] 実行の作業ログの経路は、`op exec` でも `cycle` の段でも `cli` である
- [ ] `gh pr merge` が成功を返しても、依頼の後の読み取りが `merged` でなければ、`release` は `approved` のままで、試行の結果は `merge_unconfirmed` である
- [ ] 結果が `merge_unconfirmed` の試行は、連続の回数を足さない
- [ ] 実行済みにした試行は、不可逆操作の版と課題の版をそれぞれ 1 上げる
- [ ] 依頼の後の読み取りで `merged` だが head が承認した head と異なるとき、試行の結果は `merged_unapproved` である
- [ ] チェックが 0 件の PR は、チェックの条件を満たす
- [ ] 結論が `neutral` のチェック、`skipped` のチェックは合格として扱う（それぞれ単独で持つ PR で検証する）
- [ ] 結論が `failure`・`cancelled`・`timed_out`・`action_required` のチェックは失敗として扱う（それぞれ単独で持つ PR で検証する）
- [ ] 旧式のコミットステータスの `failure`・`error` は失敗、`pending` は未完了として扱う
- [ ] REST の `mergeable` が `null` の PR は、`gh pr merge` を呼ばず、試行の結果を `waiting_checks` とする
- [ ] 状態が `pending`・`rejected`・`executed` の `release` に対して `op exec <OP-ID>` を実行しても、`gh pr merge` を呼ばない
- [ ] 状態が `approved` でない操作の ID を渡した `op exec <OP-ID>` は、`not_started` に理由 `not_executable` で示し、終了コード 0 で終わる
- [ ] `delete`・`external_send`・`other` の承認済みの不可逆操作の ID を渡した `op exec <OP-ID>` は、外部を呼ばず、状態を変えず、`not_started` に理由 `not_executable` で示す
- [ ] 存在しない `<OP-ID>` を渡した `op exec` は、終了コード 1・`not_found` で終わる
- [ ] `op exec`（ID なし）は、承認済みで未実行の `release` を ID の昇順に試す
- [ ] `connectors.json` が無いとき、`op exec` は `config_not_found` で終わる
- [ ] 待つ・取り消すの結果だけで終わった `op exec` の終了コードは 0 である
- [ ] `op exec` は、`CLAUDECODE` を設定し標準入力をパイプにした子プロセスとして起動しても実行する
- [ ] 委譲の目印（`FLYWHEEL_DELEGATED_RUN`）のある環境の `op exec` は、M3H13 のとおり終了コード 1・`verification_rejected` で終わり、偽の `gh` を呼ばず、試行の行を作らない
- [ ] `op exec` は `claude` を起動しない（偽の `claude` を PATH に置き、呼ばれないことを確かめる）
- [ ] `op exec` は `cycle` の表に `trigger` が `op exec` の行を 1 つ作る

### 実行できないときの扱い

- [ ] 偽の `gh` の PR の head が承認した head と異なるとき、`gh pr merge` を呼ばず、試行の結果は `head_changed` である
- [ ] 結果が `head_changed` の試行の後、`release` の状態は `pending` である
- [ ] 取り消しは、課題の版を 1 上げる
- [ ] 取り消しは、不可逆操作の版を 1 上げる
- [ ] 取り消しの前に得た不可逆操作の版を添えた `approve <OP-ID>` の ② は `conflict` で終わる
- [ ] 取り消された `release` の元の承認の行（`approval`）は消えずに残る
- [ ] 取り消しは、`entity=operation` と `entity=challenge` の `op_execute` の作業ログを同じトランザクションで残し、どちらも `after` に結果を持つ
- [ ] 取り消された `release` は `status --json` の `needs_human.operations` に現れる
- [ ] `needs_human.operations` の取り消された `release` の要素は、`last_execution_result` に取り消しの結果を持つ
- [ ] 取り消された `release` を `approve <OP-ID>` で承認し直すと、承認の行はその時点の head を `head_sha` に持つ
- [ ] 承認し直した `release` は、次の `op exec` で実行の対象になる
- [ ] PR が未マージのまま閉じられているとき、試行の結果は `closed` で、`gh pr merge` を呼ばない
- [ ] 結果が `closed` の試行の後、`release` の状態は `pending` である
- [ ] PR の base が既定ブランチでないとき、試行の結果は `base_changed` で、`release` は `pending` に戻る
- [ ] 承認の行の `head_sha` が NULL の承認済みの `release`（本仕様のマイグレーションの前に承認されたもの）は、`gh pr merge` を呼ばず、試行の結果を `no_approved_head` として `pending` に戻る

- [ ] 未完了のチェックがあるとき、`gh pr merge` を呼ばず、試行の結果は `waiting_checks` で、`release` は `approved` のままである
- [ ] 偽の `gh` が読み取りに失敗するとき、試行の結果は `upstream_failed` で、`release` は `approved` のままである
- [ ] `failure_limit` が 2 のとき、結果が `waiting_checks` の試行を 4 回続けても、`release` は `approved` のままで `consecutive_failures` は 0 である
- [ ] `failure_limit` が 2 のとき、結果が `upstream_failed` の試行を 4 回続けても、`release` は `approved` のままで `consecutive_failures` は 0 である
- [ ] 結果が `waiting_checks` の試行は、`op_execute` の作業ログを残さず、`operation_execution` に 1 行だけ残す
- [ ] 結果が `checks_failed` の試行は、`op_execute` の作業ログを残さない（連続の回数が上限に達した `limit_reached` を除く）
- [ ] 失敗のチェックがあるとき、`gh pr merge` を呼ばず、試行の結果は `checks_failed` である
- [ ] REST の `mergeable` が `false` のとき、`gh pr merge` を呼ばず、試行の結果は `not_mergeable` である
- [ ] `gh pr merge` が失敗を返したとき、試行の結果は `merge_failed` である
