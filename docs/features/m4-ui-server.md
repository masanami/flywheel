## 概要

旧 board が担っていた「見る・承認する」面を、M1〜M3 で作った core の上に作り直す。flywheel のバイナリに UI 用の server（`flywheel serve`）を足し、board の React UI を引き継いで、複数のワークスペースのストアを束ねて表示する。UI は 1 枚のボードに集約し、書き込みはボードのボタンでの計画・完了の承認と、1 周の手動の起動だけにする。起票・優先度の変更・差し戻し・保留への回答は UI に置かず、オーナーが Claude Code との対話で伝え、LLM が記録する（M4H19〜M4H23。2026-10-12 オーナーの決定）。

M4 の完了の目安は「ボードから計画・完了を承認でき、対話で受けた承認を LLM が記録できる」である（M4H19 で、設計書 §17 の当初の目安「UI から承認・優先度変更・起票ができる」を改めた）。本仕様はこれを 3 つのスライスで満たす。S1 は閲覧だけの server と UI、S2 は書き込みの土台とボードのボタンでの承認と 1 周の起動、S3 は LLM が対話で受けた承認・回答・差し戻しを記録する経路（core と CLI）である。S4 はカードの拡張（D20）である。モバイルからの経路（S5）と埋め込みターミナル（S6）は M5（一括移行と切り替え）の後へ送る。まず PC で使い、その経験から S5 の機能を詰め直す。移行の後は、埋め込みターミナルの代わりに外部のターミナルで Claude Code と CLI を使う（M4H16。2026-10-10 オーナーの決定）。

いちばん重い判断は、承認が誰の意思によるものかをどの経路でどこまで担保するかである。2026-10-09 の版は「Claude が承認に到達できない」ことを、操作のたびのパスキー（WebAuthn の利用者確認つきの署名）で担保すると決めた（旧 M4H1）。UX モックを触ったオーナーは、普通の開発の承認で毎回生体確認を求めるのは過剰だと判断し、2026-10-12 に次の線引きへ改めた。UI はボタンだけで承認できるが、受けるのは計画と完了の承認に限り、完了の承認は常に本番反映を保留扱いにする（UI からは本番に届かない）。本番に届く承認（既定ブランチへの昇格・`release`・`delete`・`external_send`）は端末か対話に限る。対話でオーナーが伝えた承認は、LLM が CLI の専用の口で記録し、記録に「LLM が対話で受けた」ことと会話の手がかりを必ず残す（M4H20・M4H21）。

定期実行は要件にしない（M4H11）。学習（J6・J7）・journal・承認済みの不可逆操作の実行・受け箱は、M4 と M5 の間に足した M4.5「学習と記録」の段で扱う（M4H8〜M4H10）。

## 背景・目的

- M3 までで、core が状態を決定的に進め、判断点だけを Claude に問う形ができた（M3 の要人間判定で、1 件の課題が取り込みから完了確認待ちまで自走することを 2026-10-07 に確かめた＝flywheel#157 の本文）。人間が触る面は CLI と端末の `approve` だけで、日々の運用は旧 claude-flywheel と board のままである。M5（切り替え）の前に、board の面を新しい core の上へ移す必要がある。
- board の書き込みは「承認チェックボックス 1 行の `[ ]` を `[x]` に置換し、人間の git identity で台帳だけを commit する」1 本だけだった（board `src/server/ledger-approval.ts`）。並べ替え・起票・人間記入欄の編集は「段階を分けて別途要件化」として止まっていた（board `docs/requirements.md` NFR-01）。理由は、Markdown の台帳をエージェントと board が同時に書く競合であり、ストアと core の楽観的な並行制御（M1 §クリティカル設計決定 2）がある新しい構成では成り立たない。
- 運用者の 5 つの迷い（設計書 §1.2・claude-flywheel#111）のうち、迷い 1〜3 は UI の表示で解く設計である（設計書 §12.3）。
- 旧側で先に運用した 2 つの改善を入力にする。課題カードの 4 項目（claude-flywheel#194・board#185・board PR #186）と、受け箱 `handoff/`（claude-flywheel#191）である（§課題カードの面・§課題未満の引き継ぎ事項）。
- S2〜S4 の画面を偽の API で先に作った UX モック（M4H18・PR #206）を、2026-10-12 にオーナーが触った。起票・編集・優先度・まとめての承認の画面、人間の対応待ち・ワークスペース・問いの一覧のタブ、課題カード単体のページは要らず、ボードの案をブラッシュアップする方向に決まった（flywheel#207）。旧 Tom（claude-flywheel）の日々の運用では、承認・差し戻し・回答をオーナーが対話で伝え、LLM が記録して進めており、この運用を新しい flywheel でも続けられるようにする。

## ユーザーストーリー

- オーナー（人間）として、ブラウザでボードを 1 枚開けば、すべてのエージェントについて「いま私の操作を待っているもの」「システムが次に進めるもの」「外部を待っているもの」を見分けたい。カードの面は「一言で」だけにし、位置づけ・いまの状態・次に私がすることは、カードを開いた詳細で読みたい。
- オーナーとして、ボードのボタンを押すだけで計画と完了を承認したい。本番に届く承認は、ボタンでは起きないでほしい。
- オーナーとして、Claude Code との対話で「C-12 の計画を承認」「C-15 の問いにはこう答える」「C-9 はこの理由で差し戻し」と伝えれば、LLM がそれを記録して状態が進んでほしい。後から、どの承認が対話で受けたもので、どの会話の何という発言によるものかを確かめたい。
- オーナーとして、外出先のスマートフォンから承認待ちを確かめ、通知を受けたい（S5。M5 の後）。
- 対話セッションの Claude（薄いスキル）として、UI が無くても CLI だけで状態を読め、オーナーが対話で伝えた承認・回答・差し戻しを CLI で記録できてほしい（P6）。

## 機能要件

用語: server＝`flywheel serve` で起動する UI 用の HTTP サーバ（設計書 §4）。UI＝server が配信するブラウザの画面（React）。fleet＝server が束ねて表示するワークスペースの集合。手元の待ち受け＝`127.0.0.1` で待ち受ける server の口（S1〜）。遠隔の待ち受け＝端末の外から届く経路のために別のポートで待ち受ける口（S5）。本人確認つきの操作＝M1 の定義（承認・差し戻し・保留への回答）に、M3 の予算の増額（`flywheel budget`）を加えたもの。カードの面＝課題カードの、開かなくても見える部分。詳細＝カードを押して開くモーダルの画面（S1 の「課題の詳細」の画面を S2 でモーダルにしたもの）。ボードのボタンでの承認＝UI から計画・完了を承認する操作（S2。経路 `ui`・本人確認の方式 `none`）。対話で受けた承認＝オーナーが Claude Code との対話で伝えた承認・差し戻し・回答を、LLM が CLI の専用の口で記録する操作（S3。経路 `cli`・本人確認の方式 `relayed`）。本番に届く承認＝不可逆操作（`release`・`delete`・`external_send`）の承認と、D12 によって `release` を同時に承認する完了の承認。

各要件の末尾の `[S1]`〜`[S6]` は、その要件を実装するスライスを表す（§スライス）。S2・S3 の受入基準は 2026-10-12 の書き直しで §受入基準の末尾へ足した（M4H19）。S4 以降の要件は方式と範囲を決めるために置いており、受入基準はそのスライスを実装対象にするときに足す（M4H14）。

### server の起動と待ち受け [S1]

- [ ] `flywheel serve` は UI と API を 1 つのプロセスで配信する。core をライブラリとして呼び、独自の状態を持たない（設計書 §4）【決定 設計書 §4・§15】
- [ ] 手元の待ち受けは `127.0.0.1` だけに bind する。bind する先を変える引数は持たない（旧 board と同じ）【決定 2026-10-09 親 M4P6】
- [ ] 待ち受けのポートは既定 `4318` とし、`--port <n>` で変えられる（旧 board の既定 4317 と並走できるようにする）【仮定】
- [ ] ポートを bind できなければ、何も配信せず終了コード 2・エラーコード `listen_failed` で終わる【決定 2026-10-09 親 M4P6】
- [ ] Host ヘッダが `localhost:<ポート>`・`127.0.0.1:<ポート>` のどれでもない要求（Host ヘッダが無い要求を含む）は、403 で拒否する（DNS rebinding への対策。旧 board の `isAllowedHost` を引き継ぐ）
- [ ] Origin ヘッダがあり、その origin が `http://localhost:<ポート>`・`http://127.0.0.1:<ポート>` のどれでもない要求は、403 で拒否する（旧 board の `isAllowedOrigin` を引き継ぐ）
- [ ] SIGINT・SIGTERM を受けたら、新しい要求を受け付けずに、処理中の要求を待ってから終了コード 0 で終わる【仮定】
- [ ] server が動いていなくても、CLI のすべての操作は変わらず動く（P6）。server はストアに独自の行・ロックを作らない【決定 設計書 P6】

### fleet（複数のワークスペースを束ねる）[S1]

- [ ] `serve` は、束ねるワークスペースを fleet の宣言ファイルから読む。形は §IF / API【決定 2026-10-09 親 M4P5】
- [ ] fleet の宣言ファイルの場所は `--fleet <path>` で指定し、指定が無ければ OS の利用者設定ディレクトリ（Go の `os.UserConfigDir()`）の `flywheel/fleet.json` とする（環境固有のパスをコードに埋めない＝D13）【決定 2026-10-09 親 M4P5】
- [ ] `--fleet` を指定せず、既定の場所にも fleet の宣言ファイルが無いときは、M1 のワークスペースの探索規則（`--workspace`・カレントディレクトリから上位へ）で見つけた 1 つのワークスペースだけを束ねる【決定 2026-10-09 親 M4P5】
- [ ] fleet の宣言ファイルを使わずに 1 つのワークスペースを束ねるとき、その名前は、M1 の探索規則（`--workspace` → 環境変数 `FLYWHEEL_WORKSPACE` → カレントディレクトリから上位へ）が返したワークスペースのパスの `filepath.Base`（symlink は解決しない）を `strings.ToLower` で小文字にし、Unicode のコードポイントごとに `[a-z0-9-]` 以外を `-` 1 つに置き換え（連続はまとめない）、先頭に続く `-` をすべて除いたものとする。空になれば `workspace` とする【決定 2026-10-09 親 M4P5】
- [ ] `--fleet` と `--workspace` を同時に指定すると `usage_error` で終わる
- [ ] `--fleet` で指定したファイルが無ければ `config_not_found` で終わる
- [ ] fleet の宣言ファイルが JSON として解釈できない・未知のキーがある・名前かパスが重複する・パスが絶対パスでない・名前が `[a-z0-9][a-z0-9-]*` に合わないときは、何も配信せず `config_invalid` で終わる（fail-closed。M2 の `sources.json` と同じ扱い）
- [ ] ワークスペースの状態（`ok`・`store_not_found`・`store_too_new`・`store_error`）は要求ごとに判定し直す。`ok` の間は開いた `Store` を保持するが、要求ごとにストアのスキーマ版を読み直し、バイナリの知る最新版より新しければ保持した `Store` を閉じて `store_too_new` にする。`ok` でないワークスペースは要求のたびに開き直す。条件が解消すれば次の要求から `ok` に戻る【決定 2026-10-09 親 M4P5】
- [ ] fleet のワークスペースのストアは、M1 のストアを開く規則（自動のマイグレーションを含む）で core が開く。開けないワークスペース（`store_not_found`・`store_too_new`・`store_error`）があっても server は起動し、そのワークスペースをエラーの状態として示し、他のワークスペースを配信する
- [ ] server の起動中に、ストアのスキーマ版がバイナリの知る最新版より新しくなった（別の新しい `flywheel` がマイグレーションした）ワークスペースは、次の要求から `store_too_new` の状態として示す。server は落ちない
- [ ] UI からワークスペースを fleet へ足す操作は持たない（旧 board の `POST /api/fleet/agents` は引き継がない）【決定 2026-10-09 親 M4P14】

### 閲覧の API [S1]

- [ ] API は `/api/v1/` の下に置き、成功は JSON（M1 の「成功時の JSON 出力の規約」：包みを持たない・最上位はオブジェクト・snake_case）で返す【決定 2026-10-09 親 M4P2】
- [ ] 課題の一覧・詳細・作業ログ・run の一覧・状況の表示は、対応する CLI の `--json` の出力と同じ形を返す（`list`・`show`・`log`・`runs`・`status`）。API のために別の形を作らない【決定 2026-10-09 親 M4P2】
- [ ] 失敗は CLI と同じエラーコードの閉集合を使い、本文を `{"error":{"code","message"}}` とする。HTTP の状態コードはエラーコードから決める（§IF / API「エラーコードと HTTP の状態コード」）
- [ ] `status` の `waiting_external`（M3。検証中で PR を持つ課題の CI の状態を `gh` で取る）は、CLI と同じく server が `internal/adapters/github` を組み立てて core へ渡して得る。`gh` が無い・失敗したときの扱いは CLI の `status` と同じにする。CLI の `status` は、`gh` で CI の状態を取れなかった課題を `waiting_external` に載せずに成功する（core の `ListWaitingExternal` が取得の失敗を課題ごとに飛ばす）ので、server も同じ結果を返す。server が保持するのは PR ごとのチェックの取得結果（成功・失敗とも、取得した時刻から 60 秒）で、`waiting_external` の候補（検証中で終了していない run の無い課題）は要求ごとに core が導き直す。`status` の API と課題カードの API（`GET …/challenges`・`GET …/challenges/{id}`）は、`gh` によるチェックの取得の間、そのワークスペースのストアの読み取りの借りを持たない（ストアを読む基本の `Overview` と候補の導出が済んだら借りを返してから `gh` を呼ぶ。遅い `gh` がストアの状態更新を待たせないため）。`gh` の時間の上限は CLI と同じく `internal/adapters/github` の既定（60 秒）を使う。`github.New` が失敗したとき（`ErrGHNotFound` を含む）は、CLI の `newCheckSource` と同じく取得を常に失敗させる取得の口を core へ渡し、エラーとして返さない。SSE の観測は `gh` を起動しない【決定 2026-10-09 親 M4P19／カードの API への適用は 2026-10-12 オーナー】
- [ ] `status` の `needs_human.budget_exhausted` に使うエージェントの宣言（`.flywheel/agent.json`）は、CLI の `status` と同じ規則でワークスペースから読む
- [ ] 閲覧の API は、ストアを開くときのマイグレーション（M1 の規則）を除いて、ストアへ書き込まない。M3 の中断した run の回収（`interrupted` への書き込み）も server の閲覧では行わない【仮定】
- [ ] fleet の全ワークスペースにわたって、人間の操作を待っているものを 1 つにまとめて返す API を持つ（§課題カードの面・§問いの一覧。S2 の UI はボードの上の人間待ちの帯にこの API を使う）
- [ ] 委譲の run の報告のうち `assumptions` と `unverified` を返す API を持つ。読む元は `.flywheel/runs/<run の ID>/stdout.json`（M3 の invoker が保存する子の標準出力）の `structured_output` で、run の ID の形（`R-<正の整数>`）とストアに run があることを確かめてからファイルを読む（パスの逸脱を防ぐ）

### 課題カードの面 [S1・S4]

設計書 §12.3 の迷い 1〜3 と flywheel#131 に対応する。課題が持つ 4 項目（一言で・位置づけ・いまの状態・次に人間がすること）は claude-flywheel#194 の運用で決まった形で、持ち方（§クリティカル設計決定 3）は変えない。2026-10-12 に表示の置き場所を改め、S2 からはボードのカードの面に「一言で」（無ければタイトル）と識別の印だけを出し、位置づけ・いまの状態・次に人間がすることは詳細（モーダル）に置く（M4H23。PR #206 で試作済み）。

## 非機能要件

- セキュリティ: 2026-10-12 に承認ゲートの担保を経路ごとに分けた（M4H20・M4H21。設計書 §9）。本番に届く承認は、端末（`tty_confirm`）と対話で受けた承認（`relayed`）だけが成立させ、UI からは届かない（core が経路 `ui` の範囲を強制する）。UI の承認はボタンだけで、同じマシンのプロセスが CSRF の値を取って `curl` で送る経路や、ログイン済みのブラウザを Claude in Chrome などが操作する経路を塞がない。この経路で起きうるのは計画の承認と、本番反映を保留した完了の承認までであり、記録に `channel=ui`・`verification=none` が残る。対話で受けた承認は、委譲の子と判断点の呼び出しが `flywheel` を実行できないことで自走中の自己承認を塞ぎ、会話の手がかりを記録に残すことで後から確かめられるようにする。対話のセッションの LLM がオーナーの指示なしに `--relayed` を使うことは防げない（旧 Tom の対話での承認と同じ前提）。
- 可用性: server は任意の付加物である（P6）。落ちている間は UI とモバイルから触れないだけで、エージェントと CLI は止まらない。
- 性能: 課題 1,000 件・ワークスペース 5 つの fleet で、最上位の画面を 1 秒以内に表示できる【仮定: 値は S1 の実測で較正する】。
- 動作環境: server は macOS と Linux（M1 A2）。UI は、オーナーの macOS の Safari・Chrome と、iOS の Safari（ホーム画面へ追加した場合を含む）で確かめる。

## 技術的な制約・方針

- 使用技術: server は Go の標準の HTTP サーバ、UI は React / TypeScript・Vite・Vitest・Biome（設計書 §15）【決定 D14・D16】。
- 置き場: `internal/server`（server・API）・`internal/view`（CLI と API が共有する JSON の形の型）・`web/`（UI のソース）を新設する。UI のビルド成果物はバイナリに埋め込む【決定 2026-10-09 親 M4P1・M4P13】。`CLAUDE.md` のモジュール構成の表は S1 の実装チケットで更新済み。S2 では import の向きの節に「承認の要約の head の取得」を足す（§アーキテクチャ決定）。
- 本番の依存の上限（標準ライブラリ・`modernc.org/sqlite`・`golang.org/x/term`）は S1〜S5 では広げない。ライブ更新は Server-Sent Events（標準ライブラリで書ける）。Web Push の暗号化と署名も標準ライブラリの `crypto/ecdh`・`crypto/hkdf`・`crypto/ecdsa` で書ける。S6 の埋め込みターミナルは pty の依存（テスト専用として既にある `github.com/creack/pty`）を本番へ上げる必要があり、依存の上限の変更として S6 の着手時に決める【決定 2026-10-09 オーナー M4H13】。
- core は server・view を import しない。server は core の公開 API と `internal/view` を呼ぶ。`internal/adapters/github` は、`waiting_external` の取得のために組み立てて core へ渡すことと、起動不能のエラー（`ErrGHNotFound`）の扱いにだけ使う（`internal/cli` と同じ限り方＝M4P19）。server はストアのパッケージ・`internal/cli`・`internal/invoker` を import しない（`internal/cli/depcheck_test.go` の検査に `internal/server`・`internal/view` を足す）【決定 P2・CLAUDE.md の import の向き】。
- テスト: server の API は実ストア（`t.TempDir()` の SQLite）と `net/http/httptest` で検証する。対話で受けた承認の口は、標準入力をパイプにし `CLAUDECODE` を設定した子プロセスとして CLI を起動して検証する（端末が無くても成立することを確かめる）。UI は Vitest。

## クリティカル設計決定

> 本節の決定は 2026-10-09 にオーナーと親が決めた（§決定事項の記録）。決定 1 は 2026-10-12 にオーナーが改めた（M4H20・M4H21）。後続の実装はここに従い、独自に逸脱しない。

### 1. 承認の経路ごとの担保（セキュリティ）【決定 2026-10-12 オーナー M4H20・M4H21。2026-10-09 の M4H1・M4H2 を改めた】

- 採用案: 承認の経路を 3 つ持ち、経路ごとに受けられる承認の範囲を core が決める。
  - 端末（経路 `cli`・方式 `tty_confirm`）: M1 のまま。すべての承認・差し戻し・回答・予算の増額を受ける。人間用の口として残す。
  - 対話で受けた承認（経路 `cli`・方式 `relayed`。S3）: オーナーが Claude Code との対話で伝えた承認・差し戻し・回答・予算の増額を、LLM が `flywheel approve|reject|answer|budget <ID> … --relayed --session <会話の識別> --quote <発言の要旨>` で記録する。端末での確認を求めず、本番に届く承認も受ける。会話の識別と発言の要旨を必須にし、承認・保留の記録と作業ログに残す（予算の増額を含めることは M4H28）。
  - ボードのボタン（経路 `ui`・方式 `none`。S2）: 計画の承認と完了の承認だけを受け、完了の承認は常に本番反映を保留扱いにする。ボタンを押すだけで成立させ、パスキー・対象の ID の入力を求めない。範囲の外の要求は core が `verification_rejected` で拒否する【拒否のエラーコードは仮定】。
  - core の登録簿は `(cli, tty_confirm)`・`(cli, relayed)`・`(ui, none)` の 3 組になる。経路 `ui` の範囲の検査は、登録簿の組ごとに「受けられる承認の範囲」を持たせる形で core に置き、server に置かない（server を通らずに core を呼ぶ経路が増えても範囲が崩れないため）。
- 理由: 2026-10-09 の版は、承認の経路を人間の直接操作に限り、ブラウザでは操作のたびにパスキーを求めた（設計書 D5・D18）。UX モックを触ったオーナーは、普通の開発の承認で毎回生体確認を求めるのは過剰で、旧 Tom のように対話で伝えた承認を LLM が記録できる方が日々の運用に合うと判断した（2026-10-12）。そこで「Claude が承認に到達できない」ことを全経路で担保する設計をやめ、守る対象を本番への影響で分けた。
  - UI のボタンは、同じマシンのプロセスが CSRF の値を取って `curl` で送る経路と、ブラウザを操作できる Claude（Claude in Chrome など）が押す経路を塞がない。その代わり UI からは本番に届かない。起きうるのは計画の承認と、本番反映を保留した完了の承認までで、記録に `channel=ui`・`verification=none` が残る。保留した `release` は端末か対話で別に承認するまで実行されない（M4.5 の実行も承認済みの `release` だけを扱う）。
  - 設計書 D5 が対話での承認を外した理由は 2 つあった。1 つ目の「自走中の Claude が自分の計画を承認できる」には、新しい構成では自走の担い手が core であることで答える。旧 Tom では自走の親が `flywheel` 相当の手順を実行できる LLM のセッションだったが、新しい構成では 1 周を core が進め、LLM は判断点の呼び出し（Bash を持たない＝`internal/invoker/args.go`）と委譲の子（`Bash(flywheel:*)` の禁止＝`internal/invoker/delegate.go` と、委譲の目印の環境で全コマンドを拒否する M3H13）にしか現れない。`flywheel` を実行できる LLM は、オーナーが対話しているセッションだけになる。2 つ目の「承認が人間の指示である根拠が会話にしか無い」には、記録で答える。`relayed` の承認は方式の値で端末・UI の承認と区別でき、会話の識別と発言の要旨から、どの会話のどの発言によるものかを後から確かめられる。根拠が会話にあることは変わらないが、記録から会話へ辿れるようにする。
  - 端末の `tty_confirm` と `CLAUDECODE` の検査（M1 H10）は人間用の口として変えない。LLM 用の口を別に足すことで、人間の口の担保を弱めない。
- 代替案:
  - A: 2026-10-09 の版のまま、UI の承認・差し戻し・回答・増額を操作のたびのパスキーで成立させ、対話での承認を持たない — 普通の開発の承認で毎回生体確認が要る（オーナーが退けた）。
  - B: UI のボタンで本番に届く承認（D12 の同時の承認・不可逆操作）まで受ける — ブラウザを操作できる Claude や同じマシンのプロセスが本番反映まで承認できる。
  - C: LLM 用の口を CLI でなく server の API にする — 委譲の子の `Bash(flywheel:*)` の禁止が効かず、`curl` で届く口を本番に届く承認まで広げることになる。
  - D: 端末での確認（TTY）を外し、`approve` を LLM も人間も同じ口で使う — 人間の口と LLM の口が記録で区別できなくなり、`CLAUDECODE` の歯止め（H10）も失う。
  - E: 会話の手がかりを自由記述の 1 項目（`--note`）にする — 必須の要素（会話の識別・発言の要旨）が欠けても記録でき、後から辿れない記録が残る（親 M4P26 で退けた）。
- 既知の限界: 対話のセッションの LLM が、オーナーの指示なしに `--relayed` を使うことは防げない。予算の増額も対話の口に含めた（M4H28）ので、対話中の LLM は委譲の予算を上げられる。委譲の子と判断点の呼び出しは `flywheel` を実行できないので、自走中の LLM が自分の予算を上げる経路は無い（D5 の改訂の 1 つ目の理由と同じ）。会話の手がかりは LLM が書くので、偽れる。防ぐのではなく、記録に方式と手がかりが残ることで後から見つける（旧 Tom の「対話で承認（サイクル名）」の注記と同じ水準）。委譲の子が server へ `curl` で書き込む経路は残る（UI の範囲に限られる。塞ぐかは M4H27）。
- 影響範囲: `internal/core`（登録簿の 2 組・経路ごとの承認の範囲・`relayed` の記録）・`internal/core/internal/store`（S3 のマイグレーション `0007`＝`approval`・`hold` に会話の手がかりの列、`hold` に回答の経路と方式の列）・`internal/cli`（`--relayed`・`--session`・`--quote`）・`internal/server`（承認と 1 周の起動の書き込みの API）・`web/`（ボードの承認のボタン）・設計書 D5・D18・§6・§9・§17（本 PR で改めた）。

### 2. 端末の外から届く経路（セキュリティ・外部システム連携）【決定 2026-10-09 オーナー M4H4・M4H5】

- 採用案: A。遠隔の待ち受けを手元とは別のポートで `127.0.0.1` に開き、オーナーの私設ネットワーク（VPN 型。例: Tailscale の serve）の逆プロキシが HTTPS で受けて転送する。遠隔の待ち受けは、閲覧を含むすべての API にサインインを求め、ターミナルの口を持たない。手元か遠隔かは待ち受けで決める。通知は Web Push で、本文は件数とワークスペース名だけにする。サインインの方式（2026-10-09 の版はパスキー）と、遠隔で承認のボタンを開くかは、M4H20 で UI の承認からパスキーを外したため S5 の着手時に決め直す。
- 理由: server をインターネットへ直接さらさない（設計書 §12.4 の 2 の候補）。私設ネットワークの製品を flywheel に組み込まないので、D7（ドメイン非依存）と D13（環境固有のパスを埋めない）を保てる。逆プロキシを通すと接続元の IP はすべて `127.0.0.1` に見えるので、接続元の IP で手元・遠隔を分けると、遠隔からターミナルに届く。待ち受けを分ければ、逆プロキシの転送先の設定だけで遠隔の口が決まる。Web Push は Apple・Google などの配信事業者を経由する組織外への送信であり、送信済みは撤回できないので、本文に課題の中身を入れない。
- 代替案:
  - B: flywheel が証明書のファイルを受け取り、TLS を自分で終端して `0.0.0.0` で待ち受ける — 私設ネットワークが無くても使えるが、インターネットへさらす構成を取れてしまう。証明書の更新を flywheel が抱える。
  - C: 公開のトンネル（インターネットから届く URL）を使う — 認証の失敗がそのまま外部からの侵入になる。
  - D: 通知を持たない — 設計書 §12.4 の 4（モバイルのブラウザは裏へ回ると止まる）を補えない。
- 影響範囲: `internal/server`（待ち受けの分離・サインインのセッション・Web Push）・`web/`（Service Worker・通知の購読）。私設ネットワークの設定はオーナーの運用（flywheel の範囲外）。

### 3. 課題カードの面の持ち方（DB スキーマ変更）【決定 2026-10-09 オーナー・親 M4H7・M4P7／M4P7】

- 採用案: A。「いまの状態」「次に人間がすること」はストアに持たず、core が読み取りのたびに導く（閉集合のコード）。「一言で」「位置づけ」は `challenge` に 2 つの列（`headline`・`context`。NULL 可）として足し、J1 の出力に 2 つのフィールドを足して書かせる（S4。マイグレーションの番号は S3 の `0007` の次）。人が直す口は S4 で決める（UI の編集画面は持たない＝M4H19）。取り込みは書かない（本文に無いことを推測しない＝M2 QH2）。
- 理由: 旧側では 4 項目をすべてエージェントが書き、「ステータスを変える書き込みでは、いまの状態と次に人間がすることを同じ書き込みで書き直す」規律で保っていた（claude-flywheel#194）。新しい構成では状態の遷移を core が持つので、状態の 2 項目は遷移・保留・不可逆操作・run から決定的に導け、書き直し忘れによるずれが起きない（P4・P7）。「一言で」「位置づけ」は背景が変わりにくい意味の要約であり、判断点に書かせる。J1 は課題とポジション定義を読む最初の判断点で、旧側の「分類した周に 4 つ書く」と同じ時点にあたる。
- 代替案:
  - B: 4 項目を別の表（`challenge_card`。版つき）に持つ — 書き直しの履歴を持てるが、状態の 2 項目を持つと遷移との二重管理になる。
  - C: 「一言で」「位置づけ」を J2（計画）に書かせる — 上流の本文とコメント・参照先を読むので位置づけの材料は多いが、分類済で計画を待つ課題のカードが空になる。
  - D: 4 項目とも持たず、タイトルと状態だけを出す — #131 の問題（カードを開いても中身が分からない）が残る。
- 影響範囲: `internal/core`（カードの面の導出・`challenge` の 2 列・J1 の写像）・`internal/core/internal/store`（S4 のマイグレーション）・`internal/invoker/prompts/`（J1 の指示文。M3P4 の上限 4 KiB に収める）・M3 の J1 の出力スキーマ（§決定事項の記録「仕様への指摘」）。

### 4. API の形と型の共有（外部システム連携ではないが、並列の実装チケットが共有する境界）【決定 2026-10-09 親 M4P2・M4P3】

- 採用案: A。API の成功の形は CLI の `--json` と同じにする。CLI の JSON の組み立てを `internal/view` の型つきの構造体へ移し、CLI と server が共有する。その構造体を正本として、リポジトリの中の小さな生成器（`go generate`・標準ライブラリだけ）が TypeScript の型（`web/src/api/types.gen.ts`）を書き出す。生成物はコミットし、生成し直した結果と差があれば落ちるテストを置く。
- 理由: M1〜M3 は CLI の JSON の形を仕様の表と `jsondoc_test.go` で固定している。API が同じ形なら、第 2 の正本を作らない。生成器を自前にすれば、本番の依存も UI のビルドの依存も増えない。
- 代替案:
  - B: OpenAPI の定義を手で書き、Go と TypeScript の両方を生成する — 定義が CLI の JSON の形と別の正本になる。
  - C: 型を共有せず UI 側で手書きする — board の `board-types.ts` が server の型を直接参照していた形を失い、ずれをテストで拾えない。
  - D: `internal/view` を作らず、server が CLI と同じ形を別に組み立て、等しいことをテストで確かめる — 組み立てが 2 か所になり、片方だけを直す誤りが起きる。生成器の入力（型）も無い。
- 影響範囲: `internal/view`（新設）・`internal/cli`（JSON の組み立ての移動。出力は変えない）・`internal/server`・`web/`・`Makefile`（生成の確認）。

## 機能全体の設計

### アーキテクチャ決定

- CLI の `--json` の形を組み立てる処理（今は `internal/cli` の `challengeJSON`・`runsJSON` などが `map[string]any` で組み立てている）を、新設の `internal/view` へ型つきの構造体（`json` タグつき）として移し、`internal/cli` と `internal/server` の両方がそれを使う。server は `internal/cli` を import しない（`internal/cli` が `serve` のために `internal/server` を import するので、逆向きは循環する）。移しても CLI の出力は変えない（M1〜M3 の `jsondoc_test.go` がそのまま通る）。TypeScript の型は `internal/view` の構造体から生成する【決定 2026-10-09 親 M4P3】。
- server が使う core の公開 API のうち、新しく足すもの: ⓪ M1 の探索規則でワークスペースのディレクトリだけを解決する関数（ストアが無くてもパスと名前を決めるため）とスキーマ版の読み直し ① 中断した run を回収しない run の一覧の読み取り（`OpenWorkspace` は回収しない。回収するのは run の一覧〔`ListRuns`〕・判断の呼び出し・周の開始・委譲の計画で、`status` が呼ぶ関数は回収しない。server が使うのは回収しない一覧の経路〔課題の詳細の run の欄も回収しない版を使う〕で、既存の `ListRuns` と CLI の出力は変えない） ② ストアの変化の観測（`PRAGMA data_version` を、書き込み・閲覧とは別の専用の 1 本の接続で読んで返す）③ カードの面の導出（課題・`status`・run・現在時刻から）④ 未回答の保留の一覧 ⑤ run の報告の読み取り（形の検査と run の存在の確認つき）。名前は実装で決めてよい【仮定】。
- server が状態を読み書きするのは core の公開 API だけである（P2。`waiting_external` のための `internal/adapters/github` の組み立ては M4P19 のとおり）。ワークスペースごとに core の `Store` を開き、要求ごとにワークスペースの名前から引く。server 自身はストアの外に状態を持たない。例外は、server の起動ごとに生成する CSRF の値（S2）・遠隔のサインインのセッション（S5。メモリ上）で、どれも server が落ちれば消えてよい【決定 2026-10-09 親 M4P1】。
- ライブ更新は、ワークスペースごとに専用の接続で `PRAGMA data_version` を 1 秒ごとに読み（`data_version` は他の接続の commit でだけ変わるので、観測の接続では書かない）、値が変わったら Server-Sent Events で `{"type":"workspace_changed","workspace":"<名前>"}` を送る。UI はその通知を受けて該当のワークスペースを読み直す。`data_version` は別の接続の commit で変わるので、CLI・`cycle`・別の server の書き込みを、作業ログに載らない `run`・`slot` の変化を含めて拾える【決定 2026-10-09 親 M4P4】。
- UI は単一ページのアプリとし、ビルド成果物をバイナリへ埋め込む。`go:embed` はパッケージのディレクトリより上を参照できないため、Vite の出力先は `internal/server` 配下の git で追跡しない `dist/` とする。Node が無い環境でも `go build ./...` が通るよう、「UI がビルドされていない」ことを示す最小の `index.html` を別のパスにコミットしておき、server は、ビルドした成果物があればそれを、無ければ最小の `index.html` を返す【決定 2026-10-09 親 M4P13。2026-10-10 親 M4P22 で具体化】。
- 書き込み（S2）は CLI の同じ操作と同じ core の API を呼び、遷移の可否・承認の成立条件・経路 `ui` の承認の範囲・作業ログの記録を server に書かない（`CLAUDE.md`「CLI は core の公開 API だけを呼ぶ」と同じ規律）。
- 経路 `ui` の承認の範囲は、core の登録簿の各行に「受けられる操作の集合」を持たせて表す。`(cli, tty_confirm)`・`(cli, relayed)` は M1 の操作と予算の増額のすべて、`(ui, none)` は計画の承認と `HoldRelease` が true の完了の承認だけを持つ。承認・差し戻し・回答・予算の増額・不可逆操作の承認と差し戻しの入口（`ExecuteApproval`・`ExecuteAnswer` と予算・不可逆操作の入口）は、同じ 1 つの述語で `Attestation` の組と操作を照らし、集合に無ければ何も書かず `verification_rejected` を返す【決定 2026-10-12 親 M4P23】。方式 `none` の Verifier は `internal/server` が `core.Verifier` として実装し、確認の入力を求めず、actor を `core.CurrentActor` から取る【仮定】。既存の core では `VerificationNone` が「本人確認の無い操作」の印で、本人確認つきの遷移（T5・T13・T14 など）の不変条件（`internal/core/transition_exec.go` の `hasVerification := p.verification != VerificationNone`）が方式 `none` での承認を実装誤りとして拒否する。オーナーの決定（記録は `verification=none`）に合わせて値は `none` のまま使い、この不変条件の判定を「方式が `none` でないか」から「`Verify` を通った `Attestation` を経由したか」に改める（遷移表の規則は変えず、不変条件の検査の入力を変える）【決定 2026-10-12 親 M4P29】。
- 完了の承認の要約の PR の head は、core の `PrepareApproval` の拡張で取る。`release` の `ref` が PR の URL のときだけ、core の既存の取得 IF（`internal/core/upstream.go` の `UpstreamCheckSource`。`HeadSHA` を返す）で取り、`ref` が PR の URL でない・取得に失敗したときは `head_sha` を `null` にして要約は返す（承認を止めない）。`release` が複数あれば要素ごとに取る。PR の URL とみなすのは `https://github.com/<owner>/<repo>/pull/<番号>` の形（末尾の `/files` 等の続きは無視する）だけで、それ以外は `head_sha` を `null` にする。head の取得は要約の組み立て（ストアの読み取り）と分け、読み取りの借りを返してから `gh` を呼ぶ（`status` と同じ＝M4P19・AC-44a）。CLI の `approve` の要約は変えない。server は `waiting_external` と同じく `internal/adapters/github` を組み立てて core へ渡す。`CLAUDE.md` の import の向きの節（`internal/server` が adapter を組み立ててよいのは `waiting_external` のためだけ）に「承認の要約の head」を足す更新を S2 の実装チケットに含める【仮定】。
- 1 周の起動の子プロセスは、`os.Executable()` の実行ファイルを、引数 `cycle --trigger ui --workspace <ワークスペースのパス>`・作業ディレクトリをワークスペースのパスとして起動する。終了は goroutine で `Wait` して回収する。server の終了では子を止めない。起動の前に core でサイクルのロックを読み、ロックの行があれば（heartbeat が古くても）起動せず `locked` を返す。古いロックの回収は次の CLI の `cycle` に任せる【仮定】。
- `POST …/cycle` は、子が周を記録した合図を最大 3 秒待ってから応答する。合図は、`--json` を付けない `cycle` が core の `BeginCycle` の成功の直後（段を始める前）に標準出力へ書く 1 行 `周 <周の ID> を開始した` とする（`--json` を付けた `cycle` は書かない。標準出力を 1 つの JSON に保つため）。合図が届けば `{"started": true}` を返す。合図の前に子が終了したら、`{"started": true}` を返さず、`internal_error`（500）で応答し、`message` に子の終了コードと子の標準エラーの末尾（最大 2,048 バイト。UTF-8 の文字の途中では切らない）を入れる。起動直後の失敗（`claude` が無い・設定の不備・読み取りと子の `BeginCycle` の間の競合での `locked` 等）はこの経路で UI へ返るので、周の行を作らずに終わる失敗も UI に届く。3 秒のうちに合図も終了も無ければ、`{"started": true}` を返して待つのをやめる（子は止めない）。周が始まった後の失敗は従来どおり `GET …/cycle` の `last_result` で見る。server は子の標準出力・標準エラーを合図か終了までだけ読み、その後は読み捨て続け、記録はストアにも server のメモリにも残さない（server に状態を増やさない）。server が先に終了して読み手が無くなっても周を止めないよう、`cycle` は書き込み先の切れた標準出力・標準エラーへの書き込みでプロセスを終えない（Go の既定では標準出力・標準エラーへの書き込みが `EPIPE` になるとプロセスが SIGPIPE で終わるため、`cycle` の実行中は SIGPIPE を無視する）【決定 2026-10-17 オーナー M4H33（合図を待つこと・終了したらエラーと標準エラーの末尾を返すこと・server に状態を増やさないこと）。合図の形・上限の秒数・エラーコード・末尾の長さ・SIGPIPE の扱いは起草者の仮定】。
- 対話で受けた承認（S3）は CLI の `approve`・`reject`・`answer`・`budget` の分岐として足し、`relayed` の Verifier は `internal/cli` に置く（`tty_confirm` の Verifier と同じ置き場）。Verifier は会話の手がかりの必須の検査だけを行い、本人確認の結果（`Attestation`）に手がかりを載せて core へ渡す。core は `(cli, relayed)` の結果を受けたときだけ手がかりを記録し、手がかりの無い `relayed` を拒否する【仮定: Verifier の形。M1 の `Confirm(summary, expectedID)` に手がかりを渡す口が無いので、core の公開 API の変更になる＝§M1〜M3 の仕様との関係。形は 2026-10-12 親 M4P27 で決定】。仮の形: core に `RelayEvidence{Session, Quote string}` と、`Verifier` に `Evidence() RelayEvidence` を足したインタフェースを置き、`Verify` がその Verifier から手がかりを取って `Attestation` の非公開のフィールドに載せる。`(cli, relayed)` で手がかりが空なら `Verify` が `verification_rejected` を返す。`Execute*` は `Attestation` に手がかりがあるときだけ `approval`・`hold` の列と作業ログの `after` に書く。`relayed` の操作では ① は版を得るためだけに使い、要約は表示しない【仮定】。

#### CLI に足すフラグ（S3）【決定 2026-10-12 親 M4P26（名前）】

| コマンド | 足すフラグ | 内容 |
|---|---|---|
| `flywheel approve <ID>` | `--relayed`・`--session <会話の識別>`・`--quote <発言の要旨>` | 対話で受けた承認。`--hold-release` は従来どおり完了確認待ちの課題にだけ指定できる |

#### 書き込みの API（S2）【決定 2026-10-12 親 M4P23（パスと本文の形）】

| メソッドとパス | 内容 |
|---|---|
| `GET /`（UI の HTML を返す経路のすべて） | CSRF の値を cookie `flywheel_csrf_<ポート>`（`SameSite=Strict`・`HttpOnly`・`Path=/`）で渡し、同じ値を `<meta name="flywheel-csrf" content="…">` で HTML に埋める。値は server の起動ごとに `crypto/rand` の 32 バイトを base64url にしたもの。cookie の名前にポートを入れるのは、同じホストの別の `serve` と値が上書きし合わないため |
| `GET /api/v1/workspaces/{name}/challenges/{id}/approval` | ① 承認の要約と版。`{"approval": {"challenge_id", "title", "kind": "plan" \| "completion", "version", "plan": {"version", "body"} \| null, "done_criteria": string \| null, "releases": [{"id", "summary", "ref", "head_sha": string \| null}], "other_pending_operations": [{"id", "kind", "summary"}], "release_held": bool}}`。M1 の承認の要約（`ApprovalPreview`）の中身に、`release` ごとの PR の head と、UI の承認では `release` が保留のまま残ること（`release_held` は常に `true`）を足す。型は `internal/view` に置き、`types.gen.ts` の生成の対象にする。承認待ちでない課題は `invalid_transition` |
| `POST /api/v1/workspaces/{name}/challenges/{id}/approve` | ② 本文 `{"version": <①の版>}`（`version` が無い・整数でない・未知のキーがあれば `validation_failed`）。計画承認待ちなら計画の承認、完了確認待ちなら本番反映を保留した完了の承認を行い、`flywheel show --json` と同じ形に `card` を足して返す |
| `POST /api/v1/workspaces/{name}/cycle` | 1 周の起動。`flywheel cycle --trigger ui` を別のプロセスで起動し、子が周を記録した合図を最大 3 秒待って `{"started": true}` を返す（3 秒のうちに合図も終了も無いときも同じ）。サイクルの排他に当たれば `locked`。合図の前に子が終了したら `internal_error`（`message` に子の終了コードと標準エラーの末尾）【決定 2026-10-17 オーナー M4H33。詳細は §アーキテクチャ決定】 |
| `GET /api/v1/workspaces/{name}/cycle` | サイクルの状態 `{"state": "idle" \| "running" \| "stale", "last_started_at", "last_ended_at", "last_result"}`。`state` はサイクルのロック（`lock` の行。`holder` が周）だけで決め、ロックの `heartbeat_at` が 300 秒以内なら `running`、300 秒より古ければ `stale`（M3 の中断の判定と同じしきい値）、ロックが無ければ `idle`。終了していない周（`cycle.ended_at` が NULL）の有無は `state` に数えない。`last_started_at` は、個別の操作の周を除いた周のうち ID が最大のものの開始時刻、`last_ended_at`・`last_result` は、個別の操作の周を除いた終了した周のうち ID が最大のものの値で、無ければ `null`。個別の操作の周は、`cycle.trigger` が CLI の渡す閉集合（`run`・`classify --auto`・`plan --auto`・`verify --auto`）のどれかである周とし、スキーマは変えない。時刻の形は `runs --json` にそろえる【決定 2026-10-17 オーナー M4H32。trigger で区別することは親 M4P30】 |

- 書き込みの API（`POST`）は、Host・Origin の検査に加えて CSRF の検査を通す。拒否は `forbidden_origin`（403）。
- 承認の範囲の外（差し戻し・回答・増額・不可逆操作）のエンドポイントは置かない。core の範囲の強制は、server を通らない呼び出しにも効く。

#### カードの面（`card`）【決定 2026-10-09 親 M4P7】

`{"state": <コード>, "modifiers": [<コード>…], "next_human_actions": [<コード>…], "slot_ids": ["SL-<n>"…], "headline": string|null, "context": string|null}`（`headline`・`context` は S4 まで常に `null`）。`slot_ids` は、スロットごとの直近の run（`run.slot_id` が一致する run のうち最新）がこの課題の run であるスロットの ID を昇順に並べる（API 専用。CLI の `--json` には出さない。M4H36）。

- `state` は課題の状態のコード（M1 の 8 値）そのもの。
- `modifiers` は `running`（終了していない run がある）・`unresponsive`（終了していない run の heartbeat が 300 秒より古い。しきい値は M3 の中断の判定と同じ値を core から使い、導出の関数は現在時刻を引数で受け取る）・`waiting_ci`（`status.waiting_external` にある）・`budget_exhausted`（`status.needs_human.budget_exhausted` にある）・`discrepancy`（`status.needs_human.discrepancies` にある）の閉集合で、この順に重複なく並べる。
- `next_human_actions` は次の表の条件に当たるものを表の順に重複なく並べる。どれにも当たらなければ `[]`（UI は「なし（エージェントが進める）」と表示する。S2 からはカードの面でなく詳細に表示する）。

| コード | 条件 |
|---|---|
| `approve_plan` | 状態が計画承認待ち |
| `approve_completion` | 状態が完了確認待ち |
| `answer_question` | 状態が人間対応待ち |
| `triage` | `status.needs_human.triage` にある |
| `increase_budget` | `status.needs_human.budget_exhausted` にある |
| `approve_operation` | 未承認（`pending`）の不可逆操作がある（完了した課題を含む） |
| `review_discrepancy` | `status.needs_human.discrepancies` にある |
| `clear_slot` | `card.slot_ids`（スロットごとの直近の run が課題の run であるスロット。`run.slot_id`〔M3 のマイグレーション `0005`〕で結ぶ）が `status.needs_human.slots` にある |

#### エラーコードと HTTP の状態コード

| エラーコード | HTTP の状態コード |
|---|---|
| `not_found`・`store_not_found` | 404 |
| `validation_failed`・`usage_error` | 400 |
| `invalid_transition`・`terminal_state`・`conflict`・`locked` | 409 |
| `verification_rejected`・`confirmation_mismatch` | 403 |
| `store_too_new`・`store_busy`・`store_error` | 503 |
| `internal_error` とその他 | 500 |

API の失敗の `code` は上の表に列挙した値（と `forbidden_origin`）だけである。CLI にあって表に無いコード（`tty_required`・`config_not_found`・`config_invalid`・`run_in_progress`・`budget_exceeded`・`slot_unavailable`・`serialized`）に当たる core のエラーは、API では `internal_error`（500）で返す【決定 2026-10-11 オーナー・AC-51】。

Host・Origin・CSRF の検査で拒否した要求は、core を呼ばずに 403 と `{"error":{"code":"forbidden_origin","message"}}` を返す【仮定: コード名】。

## 課題未満の引き継ぎ事項（flywheel#109）

旧側の受け箱（claude-flywheel#191）は、1 サイクル＝1 セッションの運用で会話にしか無い事項（記憶の草案・起票の草案・人間への依頼・フォローアップ候補）が、セッションを閉じると失われる問題への手当てだった。新しい構成では判断点が独立した呼び出しになり、会話の文脈を持ち越す親のセッションが無くなる（設計書 §7）。残る出どころは、委譲の報告の `assumptions`・`unverified`・`questions`（M3 §IF / API「判断点の出力」。`questions` は保留になる）と、J6 が扱う記憶の草案である。

本仕様は、受け箱をストアのエンティティにせず、J6・journal（Q6）と一緒に M4.5「学習と記録」の段へ送る【決定 2026-10-09 オーナー M4H8】。M4 では、委譲の報告の `assumptions` と `unverified` を課題の詳細の run の欄に表示する（S1。`.flywheel/runs/<run の ID>/` に保存済みの報告から読む）ところまでを持つ。根拠は旧側の運用の量で、親の要約によれば 2 周で 6 事項を仕分け、行き先は記憶 2・その場で人間に問う 2・捨てる 2・Issue の起票 0 だった【親の要約・未検証】。運用で確かめていない形をストアのスキーマに固定しない（flywheel#109 の合意）。受け箱を 2 本目の待ち行列にしない原則（やるべき作業は必ず課題を通す）は、後続の段で形を決めるときも引き継ぐ。

## 受入基準

> AC-1〜AC-144 は S1、AC-145〜AC-227 は S2、AC-228〜AC-253 は S3 の範囲（S2・S3 は 2026-10-12 の書き直しで足した。M4H19）。AC の番号は本節の `- [ ]` の上からの序数（AC-1 から）で、M1〜M3 の番号とは別の系列である。後から足す項目は、既存の番号が動かないよう節の末尾か枝番（【AC-12a】のように付け、序数に数えない）にする。S4 以降の受入基準は、そのスライスを実装対象にするときに節の末尾へ足す（M4H14）。起票（`/create-ticket`）は、`実装対象:` のスライスの節だけを使う（S1 なら見出しに `S2:`・`S3:` の付かない節、S2 なら `### S2: …` の節。M4P28）。S1 の受入基準のうち S2 で改めるものは、S1 の出荷の判定に使うため削らずに残し、項目の下に改める先の AC を注記した（S2 の受入基準が成り立った後は、注記した S1 の基準は改める先の基準に置き換わる）。「テストの fleet」は `t.TempDir()` に作ったワークスペースのストアを並べた `fleet.json` を指す。API の検証は `serve` の待ち受けへの実際の HTTP の要求で行う。

### server の起動と待ち受け

- [ ] `flywheel serve --workspace <dir>` は既定のポート 4318 で待ち受け、`GET /api/v1/workspaces` に 200 を返す

- [ ] `serve` の待ち受けのアドレスは `127.0.0.1:<ポート>` である（`0.0.0.0`・`::` ではない）。テストは `serve` が起動時に標準エラーへ出す 1 行（`listening on 127.0.0.1:<ポート>` の形）と、server のテストの中の待ち受けの `Addr()` の両方で確かめる
- [ ] 既に使われているポートを `--port` に指定すると、終了コード 2・エラーコード `listen_failed` で終わる
- [ ] Host ヘッダが `evil.example:4318` の要求は 403 で拒否される
- [ ] Host ヘッダが無い要求は 403 で拒否される
- [ ] Host ヘッダが `localhost:<ポート>` の要求と `127.0.0.1:<ポート>` の要求は、どちらも拒否されない
- [ ] Origin ヘッダが `http://evil.example` の要求は 403 で拒否される
- [ ] Origin ヘッダが `http://localhost:<ポート>` の要求は拒否されない
- [ ] Host・Origin の検査で拒否した応答の本文は `{"error":{"code":"forbidden_origin","message":…}}` である
- [ ] Host・Origin の検査で拒否した要求では、ストアのファイルの内容が変わらない
- [ ] `serve` に SIGTERM を送ると、終了コード 0 で終わる
- [ ] `serve` に SIGINT を送ると、終了コード 0 で終わる
- [ ] `GET /api/v1/events` を購読している接続がある状態で SIGTERM を送っても、`serve` は 5 秒以内に終了コード 0 で終わる（購読が終了を妨げない）【仮定: 5 秒】
