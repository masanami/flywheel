## 概要

旧 board が担っていた「見る・承認する」面を、M1〜M3 で作った core の上に作り直す。flywheel のバイナリに UI 用の server（`flywheel serve`）を足し、board の React UI を引き継いで、複数のワークスペースのストアを束ねて表示する。書き込みは core の公開 API だけを通す（P2）ので、board では段階を分けて後回しにした操作（起票・人間記入欄の編集・優先度の変更・承認・差し戻し・保留への回答・予算の増額）を UI から行えるようにする。

M4 の完了の目安は、設計書 §17 のとおり「UI から承認・優先度変更・起票ができる」である。本仕様はこれを 3 つのスライスで満たす。S1 は閲覧だけの server と UI、S2 は本人確認の要らない書き込み（起票・編集・優先度の変更）、S3 はパスキーによる本人確認つきの書き込み（承認・差し戻し・回答・予算の増額）である。モバイルからの経路（S5）と埋め込みターミナル（S6）は、方式を本仕様で決めたうえで、M5（一括移行と切り替え）の後へ送る。まず PC で使い、その経験から S5 の機能を詰め直す。移行の後は、埋め込みターミナルの代わりに外部のターミナルで Claude Code と CLI を使う（M4H16。2026-10-10 オーナーの決定）。

いちばん重い判断は、ブラウザ経由の承認で「Claude が承認に到達できない」ことをどう担保するかである（M4H1）。設計書 §9 は当初 server の起動時のトークンを想定していたが、Claude が server を起動したり、プロセスの環境やファイルを読んだりすればトークンを得られる。そこで、同じマシンのブラウザでも、操作のたびにパスキー（WebAuthn の利用者確認つきの署名）を求めると決めた。承認待ちが溜まったときは、同じワークスペースの承認待ちの集合を 1 回のパスキーでまとめて承認できる（M4H2・M4P20。2026-10-09 オーナー・親の決定）。

定期実行は要件にしない（M4H11）。学習（J6・J7）・journal・承認済みの不可逆操作の実行・受け箱は、M4 と M5 の間に足した M4.5「学習と記録」の段で扱う（M4H8〜M4H10）。

## 背景・目的

- M3 までで、core が状態を決定的に進め、判断点だけを Claude に問う形ができた（M3 の要人間判定で、1 件の課題が取り込みから完了確認待ちまで自走することを 2026-10-07 に確かめた＝flywheel#157 の本文）。人間が触る面は CLI と端末の `approve` だけで、日々の運用は旧 claude-flywheel と board のままである。M5（切り替え）の前に、board の面を新しい core の上へ移す必要がある。
- board の書き込みは「承認チェックボックス 1 行の `[ ]` を `[x]` に置換し、人間の git identity で台帳だけを commit する」1 本だけだった（board `src/server/ledger-approval.ts`）。並べ替え・起票・人間記入欄の編集は「段階を分けて別途要件化」として止まっていた（board `docs/requirements.md` NFR-01）。理由は、Markdown の台帳をエージェントと board が同時に書く競合であり、ストアと core の楽観的な並行制御（M1 §クリティカル設計決定 2）がある新しい構成では成り立たない。
- 運用者の 5 つの迷い（設計書 §1.2・claude-flywheel#111）のうち、迷い 1〜3 は UI の表示で解く設計である（設計書 §12.3）。
- 旧側で先に運用した 2 つの改善を入力にする。課題カードの 4 項目（claude-flywheel#194・board#185・board PR #186）と、受け箱 `handoff/`（claude-flywheel#191）である（§課題カードの面・§課題未満の引き継ぎ事項）。

## ユーザーストーリー

- オーナー（人間）として、ブラウザを 1 つ開けば、すべてのエージェントについて「いま私の操作を待っているもの」と「システムが進めているもの」を分けて見たい。カードを開かなくても、何の課題で、いまどこにあり、私が次に何をすればよいかが分かってほしい。
- オーナーとして、ブラウザから課題を起票し、優先度を変え、計画と完了を承認したい。承認が Claude に代行されないことを、端末の `approve` と同じ程度に信頼したい。
- オーナーとして、外出先のスマートフォンから承認待ちを確かめ、通知を受け、承認や回答をしたい（S5）。
- 対話セッションの Claude（薄いスキル）として、UI が無くても CLI だけで状態を読めることが変わらないでほしい（P6）。

## 機能要件

用語: server＝`flywheel serve` で起動する UI 用の HTTP サーバ（設計書 §4）。UI＝server が配信するブラウザの画面（React）。fleet＝server が束ねて表示するワークスペースの集合。手元の待ち受け＝`127.0.0.1` で待ち受ける server の口（S1〜）。遠隔の待ち受け＝端末の外から届く経路のために別のポートで待ち受ける口（S5）。本人確認つきの操作＝M1 の定義（承認・差し戻し・保留への回答）に、M3 の予算の増額（`flywheel budget`）を加えたもの。カードの面＝課題カードの、開かなくても見える部分。

各要件の末尾の `[S1]`〜`[S7]` は、その要件を実装するスライスを表す（§スライス）。S2 以降の要件は方式と範囲を決めるために置いており、受入基準はそのスライスを実装対象にするときに足す（M4H14）。

### server の起動と待ち受け [S1]

- [ ] `flywheel serve` は UI と API を 1 つのプロセスで配信する。core をライブラリとして呼び、独自の状態を持たない（設計書 §4）【決定 設計書 §4・§15】
- [ ] 手元の待ち受けは `127.0.0.1` だけに bind する。bind する先を変える引数は持たない（旧 board と同じ）【決定 2026-10-09 親 M4P6】
- [ ] 待ち受けのポートは既定 `4318` とし、`--port <n>` で変えられる（旧 board の既定 4317 と並走できるようにする）【仮定】
- [ ] ポートを bind できなければ、何も配信せず終了コード 2・エラーコード `listen_failed` で終わる【決定 2026-10-09 親 M4P6】
- [ ] Host ヘッダが `localhost:<ポート>`・`127.0.0.1:<ポート>` のどれでもない要求（Host ヘッダが無い要求を含む）は、403 で拒否する（DNS rebinding への対策。旧 board の `isAllowedHost` を引き継ぐ）
- [ ] Origin ヘッダがあり、その origin が `http://localhost:<ポート>`・`http://127.0.0.1:<ポート>` のどれでもない要求は、403 で拒否する（旧 board の `isAllowedOrigin` を引き継ぐ）
- [ ] SIGINT・SIGTERM を受けたら、新しい要求を受け付けずに、処理中の要求を待ってから終了コード 0 で終わる【仮定】
- [ ] server が動いていなくても、CLI のすべての操作は変わらず動く（P6）。server はストアに独自の行・ロックを作らない【決定 設計書 P6】

### fleet（複数のワークスペースを束ねる）[S1]

- [ ] `serve` は、束ねるワークスペースを fleet の宣言ファイルから読む。形は §IF / API【決定 2026-10-09 親 M4P5】
- [ ] fleet の宣言ファイルの場所は `--fleet <path>` で指定し、指定が無ければ OS の利用者設定ディレクトリ（Go の `os.UserConfigDir()`）の `flywheel/fleet.json` とする（環境固有のパスをコードに埋めない＝D13）【決定 2026-10-09 親 M4P5】
- [ ] `--fleet` を指定せず、既定の場所にも fleet の宣言ファイルが無いときは、M1 のワークスペースの探索規則（`--workspace`・カレントディレクトリから上位へ）で見つけた 1 つのワークスペースだけを束ねる【決定 2026-10-09 親 M4P5】
- [ ] fleet の宣言ファイルを使わずに 1 つのワークスペースを束ねるとき、その名前は、M1 の探索規則（`--workspace` → 環境変数 `FLYWHEEL_WORKSPACE` → カレントディレクトリから上位へ）が返したワークスペースのパスの `filepath.Base`（symlink は解決しない）を `strings.ToLower` で小文字にし、Unicode のコードポイントごとに `[a-z0-9-]` 以外を `-` 1 つに置き換え（連続はまとめない）、先頭に続く `-` をすべて除いたものとする。空になれば `workspace` とする【決定 2026-10-09 親 M4P5】
- [ ] `--fleet` と `--workspace` を同時に指定すると `usage_error` で終わる
- [ ] `--fleet` で指定したファイルが無ければ `config_not_found` で終わる
- [ ] fleet の宣言ファイルが JSON として解釈できない・未知のキーがある・名前かパスが重複する・パスが絶対パスでない・名前が `[a-z0-9][a-z0-9-]*` に合わないときは、何も配信せず `config_invalid` で終わる（fail-closed。M2 の `sources.json` と同じ扱い）
- [ ] ワークスペースの状態（`ok`・`store_not_found`・`store_too_new`・`store_error`）は要求ごとに判定し直す。`ok` の間は開いた `Store` を保持するが、要求ごとにストアのスキーマ版を読み直し、バイナリの知る最新版より新しければ保持した `Store` を閉じて `store_too_new` にする。`ok` でないワークスペースは要求のたびに開き直す。条件が解消すれば次の要求から `ok` に戻る【決定 2026-10-09 親 M4P5】
- [ ] fleet のワークスペースのストアは、M1 のストアを開く規則（自動のマイグレーションを含む）で core が開く。開けないワークスペース（`store_not_found`・`store_too_new`・`store_error`）があっても server は起動し、そのワークスペースをエラーの状態として示し、他のワークスペースを配信する
- [ ] server の起動中に、ストアのスキーマ版がバイナリの知る最新版より新しくなった（別の新しい `flywheel` がマイグレーションした）ワークスペースは、次の要求から `store_too_new` の状態として示す。server は落ちない
- [ ] UI からワークスペースを fleet へ足す操作は持たない（旧 board の `POST /api/fleet/agents` は引き継がない）【決定 2026-10-09 親 M4P14】

### 閲覧の API [S1]

- [ ] API は `/api/v1/` の下に置き、成功は JSON（M1 の「成功時の JSON 出力の規約」：包みを持たない・最上位はオブジェクト・snake_case）で返す【決定 2026-10-09 親 M4P2】
- [ ] 課題の一覧・詳細・作業ログ・run の一覧・状況の表示は、対応する CLI の `--json` の出力と同じ形を返す（`list`・`show`・`log`・`runs`・`status`）。API のために別の形を作らない【決定 2026-10-09 親 M4P2】
- [ ] 失敗は CLI と同じエラーコードの閉集合を使い、本文を `{"error":{"code","message"}}` とする。HTTP の状態コードはエラーコードから決める（§IF / API「エラーコードと HTTP の状態コード」）
- [ ] `status` の `waiting_external`（M3。検証中で PR を持つ課題の CI の状態を `gh` で取る）は、CLI と同じく server が `internal/adapters/github` を組み立てて core へ渡して得る。`gh` が無い・失敗したときの扱いは CLI の `status` と同じにする。CLI の `status` は、`gh` で CI の状態を取れなかった課題を `waiting_external` に載せずに成功する（core の `ListWaitingExternal` が取得の失敗を課題ごとに飛ばす）ので、server も同じ結果を返す。server が保持するのは PR ごとのチェックの取得結果（成功・失敗とも、取得した時刻から 60 秒）で、`waiting_external` の候補（検証中で終了していない run の無い課題）は要求ごとに core が導き直す。`gh` の時間の上限は CLI と同じく `internal/adapters/github` の既定（60 秒）を使う。`github.New` が失敗したとき（`ErrGHNotFound` を含む）は、CLI の `newCheckSource` と同じく取得を常に失敗させる取得の口を core へ渡し、エラーとして返さない。SSE の観測は `gh` を起動しない【決定 2026-10-09 親 M4P19】
- [ ] `status` の `needs_human.budget_exhausted` に使うエージェントの宣言（`.flywheel/agent.json`）は、CLI の `status` と同じ規則でワークスペースから読む
- [ ] 閲覧の API は、ストアを開くときのマイグレーション（M1 の規則）を除いて、ストアへ書き込まない。M3 の中断した run の回収（`interrupted` への書き込み）も server の閲覧では行わない【仮定】
- [ ] fleet の全ワークスペースにわたって、人間の操作を待っているものを 1 つにまとめて返す API を持つ（§課題カードの面・§問いの一覧）
- [ ] 委譲の run の報告のうち `assumptions` と `unverified` を返す API を持つ。読む元は `.flywheel/runs/<run の ID>/stdout.json`（M3 の invoker が保存する子の標準出力）の `structured_output` で、run の ID の形（`R-<正の整数>`）とストアに run があることを確かめてからファイルを読む（パスの逸脱を防ぐ）

### 課題カードの面 [S1・S4]

設計書 §12.3 の迷い 1〜3 と flywheel#131 に対応する。カードの面は 4 項目（一言で・位置づけ・いまの状態・次に人間がすること）とする（claude-flywheel#194 の運用で決まった形）。

- [ ] 「いまの状態」と「次に人間がすること」は、LLM に書かせず、core が課題の状態・保留・不可逆操作・run・予算・食い違いから決定的に導く。値は閉集合のコードで返し、表示の文言は UI が持つ（§IF / API「カードの面」）[S1]【決定 2026-10-09 親 M4P7】
- [ ] 「一言で」と「位置づけ」は S1 では持たない。S1 のカードの面は、タイトル・いまの状態・次に人間がすることの 3 つとする [S1]
- [ ] カードの面に、課題の ID・優先度・人間の操作を待っている区分の印を添える。計画の本文・完了条件・説明・承認と保留の記録・不可逆操作・run・費用・上流の参照・作業ログは、カードを開いたときの詳細に回す [S1]【仮定】
- [ ] 課題の説明・計画の本文・保留の問いと回答・上流由来のタイトルは、プレーンテキストとして表示する。HTML として解釈しない（取り込んだ Issue の本文はそのままストアに入る＝M2 QH2）[S1]【決定 2026-10-09 親 M4P10】
- [ ] カードの面の長い値は、既定で一定の行数で切り詰め、操作で全文を開けるようにする（旧 board は切り詰めず全文を折り返しており、幅 320px での伸び方は確かめられていない）[S1]【仮定: 行数は実装で決めてよい】
- [ ] 課題に「一言で」（40 字前後・動詞で終える）と「位置づけ」（全体計画のどこにあり、なぜ要るか。ID でなく言葉で 2〜3 文）を持たせ、J1（分類）がそれを書く。人は S2 の編集で直せる [S4]【決定 2026-10-09 オーナー M4H7】
- [ ] 「一言で」が無い課題（人が `classify --priority` で分類した課題など）のカードの面は、タイトルで代える [S4]

### 状況の表示とライブ更新 [S1]

- [ ] UI の最上位に、fleet 全体の「人間の操作を待っているもの」を集める。中身は各ワークスペースの `status.needs_human`（課題・不可逆操作・食い違い・`triage`・`budget_exhausted`・`slots`）と同じ区分である（設計書 §12.3 の迷い 2）
- [ ] UI は「人間の操作を待っているもの」「システムが次に進められるもの」「外部を待っているもの（`status.waiting_external`）」「承認済みの不可逆操作」を分けて示す（設計書 §12.3 の迷い 1・3）
- [ ] 実行中の run（終了していない run）を課題とワークスペースごとに示す。heartbeat が 300 秒より古い終了していない run は「応答なし」として区別して示す（M3 の中断の判定と同じしきい値。回収はしない）【仮定】
- [ ] 別のプロセス（CLI・`cycle`・別のブラウザ）がストアを変えたら、UI は再読み込みの操作なしに表示を更新する【決定 2026-10-09 親 M4P4】
- [ ] server との接続が切れたら、UI は切れていることと最後に更新した時刻を示し、再接続を試み続ける。再接続したら全体を読み直す
- [ ] 本人確認つきの操作は S1 の UI からは行えない。承認待ち・回答待ち・予算の使い切りのカードには、端末で実行するコマンド（例: `flywheel approve C-12 --workspace <パス>`）と「Claude Code の外の端末で実行する」旨を示す（設計書 §9 の「承認方法の案内」）

- [ ] まとめての承認の署名は、対象の集合の正規形に束ねる。正規形は core の公開関数が 1 つだけ定義し、要素を（対象の ID・検査する版・承認の種類・`--hold-release` の有無）の組とし、課題を先、不可逆操作を後とし、それぞれ番号の数値の昇順に `<ID>:<版>:<承認の種類>:<hold_release>` を改行でつないだ文字列とする（承認の種類は M1 の `approval.kind` の値、`hold_release` は `true`／`false`。完了の承認以外は `false`）。差し戻し・回答・予算の増額の署名は、`<ID>:<版>:<操作の種類>:<理由・回答の文・額の SHA-256 の 16 進>` の 1 行に束ねる。値の語彙の細部は S3 の受入基準を足すときに固定する。検査する版は、課題の承認では課題の版、不可逆操作の承認では不可逆操作の版とする（M1 の 2 段階の API が表示の時点で返す版と同じもの）【決定 2026-10-09 親 M4P21】

- [ ] 差し戻し・保留への回答・予算の増額は 1 件ずつ行い、操作のたびにパスキーを求める（理由・回答・額が対象ごとに違うため）【決定 2026-10-09 親 M4P21】

## 非機能要件

- セキュリティ: 承認ゲートの意味は「Claude が通常の道具立てで承認に到達できない」ことである（設計書 §9）。server の経路でも、トークン・cookie・Host の偽装を Claude が通常の道具（Bash の `curl` など）で満たせても承認に到達しないことを、パスキーの利用者確認で担保する（M4H1）。同じマシン・同じユーザーのプロセスが仮想の認証器を作るといった意図的な回避は、M1 と同じく防御の対象外とする。
- 可用性: server は任意の付加物である（P6）。落ちている間は UI とモバイルから触れないだけで、エージェントと CLI は止まらない。
- 性能: 課題 1,000 件・ワークスペース 5 つの fleet で、最上位の画面を 1 秒以内に表示できる【仮定: 値は S1 の実測で較正する】。
- 動作環境: server は macOS と Linux（M1 A2）。UI は、オーナーの macOS の Safari・Chrome と、iOS の Safari（ホーム画面へ追加した場合を含む）で確かめる。

## 技術的な制約・方針

- 使用技術: server は Go の標準の HTTP サーバ、UI は React / TypeScript・Vite・Vitest・Biome（設計書 §15）【決定 D14・D16】。
- 置き場: `internal/server`（server・API・パスキーの Verifier）・`internal/view`（CLI と API が共有する JSON の形の型）・`web/`（UI のソース）を新設する。UI のビルド成果物はバイナリに埋め込む【決定 2026-10-09 親 M4P1・M4P13】。`CLAUDE.md` のモジュール構成の表は S1 の実装チケットで更新する。
- 本番の依存の上限（標準ライブラリ・`modernc.org/sqlite`・`golang.org/x/term`）は S1〜S5 では広げない。ライブ更新は Server-Sent Events（標準ライブラリで書ける）、パスキーの検証は標準ライブラリの `crypto` と、ブラウザの `getPublicKey()` が返す SPKI 形式の公開鍵で行う（CBOR の解釈を要さない）。Web Push の暗号化と署名も標準ライブラリの `crypto/ecdh`・`crypto/hkdf`・`crypto/ecdsa` で書ける。S6 の埋め込みターミナルは pty の依存（テスト専用として既にある `github.com/creack/pty`）を本番へ上げる必要があり、依存の上限の変更として S6 の着手時に決める【決定 2026-10-09 オーナー M4H13】。
- core は server・view を import しない。server は core の公開 API と `internal/view` を呼ぶ。`internal/adapters/github` は、`waiting_external` の取得のために組み立てて core へ渡すことと、起動不能のエラー（`ErrGHNotFound`）の扱いにだけ使う（`internal/cli` と同じ限り方＝M4P19）。server はストアのパッケージ・`internal/cli`・`internal/invoker` を import しない（`internal/cli/depcheck_test.go` の検査に `internal/server`・`internal/view` を足す）【決定 P2・CLAUDE.md の import の向き】。
- テスト: server の API は実ストア（`t.TempDir()` の SQLite）と `net/http/httptest` で検証する。パスキーは、テストの中で生成した鍵で署名する偽の認証器で検証する（本物の認証器は要人間判定）。UI は Vitest。

### 現行（旧 board）から引き継ぐもの・引き継がないもの

| 旧 board の挙動 | 扱い | 理由 |
|---|---|---|
| `127.0.0.1` への bind 固定・Host と Origin の検査（`api.ts` `isAllowedHost`・`isAllowedOrigin`） | 引き継ぐ（S1） | DNS rebinding と他のサイトからの要求への対策として新しい構成でも要る |
| 認証を持たない（board `requirements.md` NFR-03「外部バインド・外部送信をしない代わりに認証を設けない」） | 閲覧は引き継ぐ。書き込みは CSRF への対策（S2）とパスキー（S3）を足す | 書き込みを解禁するため |
| 承認ボタンが台帳の `[ ]` を `[x]` に置換し、人間の git identity で台帳だけを commit する（`ledger-approval.ts`） | 引き継がない | 承認の正本はストアの `approval`（D3・D5）。真正性は git identity ではなく本人確認の方式で担保する（設計書 §12.2） |
| 承認の前に run-cycle のロック（`.flywheel/cycle.lock` のディレクトリ）を取り、取れなければ 409 を返す（`cycle-lock.ts`） | 引き継がない | 台帳を 2 者が同時に書く競合を避けるためのロックだった。新しい構成では、書き込みはストアのトランザクション（`BEGIN IMMEDIATE`）で直列化され、承認は表示した版に束ねられる（M1 §クリティカル設計決定 2）。周の run は課題の最新の状態を読み直してから写す（M3 §機能全体の設計「1 つの run の流れ」）ため、承認と周が並走しても状態は壊れない。サイクルの排他（M3 の `locked`）に当たるのは UI からの一括の操作の起動だけである |
| 承認で状態を進めず、次のサイクルでエージェントが遷移を代行する（board `requirements.md`） | 引き継がない | core が承認の操作の中で遷移する（T5・T13）。設計書 §12.3 の迷い 2「承認した瞬間に core が状態を進める」 |
| fleet のマニフェスト `~/.flywheel/fleet.tsv`（2 列の TSV）と、UI からのエージェントの追加 | 形を JSON の宣言に変える（S1）。UI からの追加は持たない | 宣言の形を `sources.json`・`connectors.json` とそろえる。追加の手順（`git init` など）は M5 の移行と一緒に扱う（M4P5・M4P14） |
| Markdown のパース層・ファイル監視による再構築・5 分ごとの再スキャン | 引き継がない | 設計書 §12.2。ライブ更新はストアの変化の検出に置き換える（M4P4） |
| stale の判定（委譲は開始からの経過 60 分・周は heartbeat） | 置き換える | M3 で run が heartbeat を持つので、heartbeat の古さ（300 秒）で判定する |

## クリティカル設計決定

> 本節の決定は 2026-10-09 にオーナーと親が決めた（§決定事項の記録）。後続の実装はここに従い、独自に逸脱しない。

### 1. ブラウザ経由の承認の本人確認（セキュリティ）【決定 2026-10-09 オーナー M4H1・M4H2】

- 採用案: UI からの本人確認つきの操作は、手元・遠隔を問わず、操作のたびにパスキー（WebAuthn の利用者確認つき）でだけ成立させる。承認は、同じワークスペースの承認待ちから利用者が選んだ集合を 1 回のパスキーでまとめて行える（1 件の承認は集合が 1 件の場合。集合の構成の規則と正規形は §本人確認つきの書き込み）。core の登録簿に `(ui, passkey)` を足し、`passkey` の Verifier は `internal/server` に置く。
  - 確認と署名の流れ: ① server が対象（集合）の要約と版を core から得て、challenge を発行する。challenge は、ワークスペース・対象の ID と版と承認の種類と `--hold-release` の有無の集合（差し戻し・回答・増額では 1 件の対象と理由・回答の文・額）に束ね、1 回だけ使え、5 分で失効する。② UI は対象の一覧と要約を示し、利用者がパスキーで署名する。③ server は、署名が登録済みの公開鍵で検証できること・利用者確認の印があること・署名が束ねた集合と実行を求められた集合が一致することを確かめ、成立したときだけ core を呼ぶ。対象の ID の手入力は求めない。
  - core は、集合の承認を 1 つの書き込みトランザクションで行い、集合の 1 件でも版が ① の時点から変わっていれば全体を `conflict` で拒否する。承認の規則（承認の種類の決め方・D12 の `release` の同時の承認・`--hold-release`）は M1 のまま 1 件ずつ当てはめる。作業ログの各件には同じ challenge の ID を残す。
  - パスキーの登録は、`tty_confirm` を通った CLI の操作が `/dev/tty` に表示する 1 回限りの符号でだけ始められる。
- 理由: 設計書 §9 の担保は「Claude が通常の道具立てで承認に到達できない」ことである。§9 が当初想定した「server の起動時に生成してブラウザにだけ渡すトークン」は、Claude が `flywheel serve` を Bash で起動すれば標準出力から、そうでなくても同じユーザーのプロセスの引数・環境・ブラウザに渡すファイルから読め、`curl` で満たせる。パスキーの利用者確認（Touch ID・Face ID・PIN）は人の操作を要し、Claude の道具立てでは満たせない。操作のたびに求めるのは、ログイン済みのブラウザを Claude in Chrome などが操作できるため、セッションの間はボタンだけ、という形ではブラウザを操作できる Claude が承認に届くからである（オーナー・2026-10-09）。承認待ちが溜まったときの手間は、集合を 1 回の署名でまとめることで減らす。集合に束ねた署名と、全体を `conflict` で拒否する規則により、表示した一覧と違うものが承認されることも、一部だけ承認されて状態が割れることも起きない。手元でもパスキーにすると、手元と遠隔で方式が 1 つにそろう。WebAuthn はブラウザの `localhost` を安全な文脈として扱うので、手元では HTTPS を要さない。
- 代替案:
  - B: 設計書 §9 の当初の記述どおり起動時のトークン＋対象の ID の入力（手元だけ）。遠隔だけパスキー — 手元の承認が Claude の `curl` で成立しうる。
  - C: 手元の UI からは承認させず、端末の CLI だけに残す — M4 の完了の目安「UI から承認ができる」を満たさない。
  - D: 1 回のパスキーで一定時間有効なセッションを作り、その間の承認はボタンだけで成立させる — ログイン済みのブラウザを操作できる Claude が承認できる（オーナーが退けた）。
  - E: 1 件ずつ署名し、まとめての承認を持たない（起案時の推奨）— 承認待ちが溜まると署名の回数が増える（オーナーが改めた）。
  - F: まとめての承認で、版の変わった件だけを外して残りを承認する — 利用者が確認した一覧と、実際に承認された集合が食い違う。
- 既知の限界: 同じユーザーのプロセスが登録済みの鍵を使うことはできない（鍵はプラットフォームの認証器の中にあり、使うたびに利用者確認を要する）。登録用の符号を盗んで自分の鍵を登録する経路は、符号を `/dev/tty` にだけ出すことで塞ぐ。M1 の既知の限界（疑似端末の作成）と同じく、意図的な回避は防御の対象外とする。
- 影響範囲: `internal/core`（登録簿に 1 行・経路 `ui`・方式 `passkey` の値・集合の承認を 1 つのトランザクションで行う公開 API）・`internal/server`（Verifier・challenge の発行と失効・公開鍵の保管）・`internal/cli`（パスキーの登録と削除のコマンド）・設計書 §9（本 PR で改めた）。

### 2. 端末の外から届く経路（セキュリティ・外部システム連携）【決定 2026-10-09 オーナー M4H4・M4H5】

- 採用案: A。遠隔の待ち受けを手元とは別のポートで `127.0.0.1` に開き、オーナーの私設ネットワーク（VPN 型。例: Tailscale の serve）の逆プロキシが HTTPS で受けて転送する。遠隔の待ち受けは、閲覧を含むすべての API にパスキーのサインインを求め、ターミナルの口を持たない。手元か遠隔かは待ち受けで決める。通知は Web Push で、本文は件数とワークスペース名だけにする。
- 理由: server をインターネットへ直接さらさない（設計書 §12.4 の 2 の候補）。私設ネットワークの製品を flywheel に組み込まないので、D7（ドメイン非依存）と D13（環境固有のパスを埋めない）を保てる。逆プロキシを通すと接続元の IP はすべて `127.0.0.1` に見えるので、接続元の IP で手元・遠隔を分けると、遠隔からターミナルに届く。待ち受けを分ければ、逆プロキシの転送先の設定だけで遠隔の口が決まる。Web Push は Apple・Google などの配信事業者を経由する組織外への送信であり、送信済みは撤回できないので、本文に課題の中身を入れない。
- 代替案:
  - B: flywheel が証明書のファイルを受け取り、TLS を自分で終端して `0.0.0.0` で待ち受ける — 私設ネットワークが無くても使えるが、インターネットへさらす構成を取れてしまう。証明書の更新を flywheel が抱える。
  - C: 公開のトンネル（インターネットから届く URL）を使う — 認証の失敗がそのまま外部からの侵入になる。
  - D: 通知を持たない — 設計書 §12.4 の 4（モバイルのブラウザは裏へ回ると止まる）を補えない。
- 影響範囲: `internal/server`（待ち受けの分離・サインインのセッション・Web Push）・`web/`（Service Worker・通知の購読）。私設ネットワークの設定はオーナーの運用（flywheel の範囲外）。

### 3. 課題カードの面の持ち方（DB スキーマ変更）【決定 2026-10-09 オーナー・親 M4H7・M4P7／M4P7】

- 採用案: A。「いまの状態」「次に人間がすること」はストアに持たず、core が読み取りのたびに導く（閉集合のコード）。「一言で」「位置づけ」は `challenge` に 2 つの列（`headline`・`context`。NULL 可）として足し、J1 の出力に 2 つのフィールドを足して書かせる（S4。マイグレーション `0007`）。人は S2 の編集で直せる。取り込みは書かない（本文に無いことを推測しない＝M2 QH2）。
- 理由: 旧側では 4 項目をすべてエージェントが書き、「ステータスを変える書き込みでは、いまの状態と次に人間がすることを同じ書き込みで書き直す」規律で保っていた（claude-flywheel#194）。新しい構成では状態の遷移を core が持つので、状態の 2 項目は遷移・保留・不可逆操作・run から決定的に導け、書き直し忘れによるずれが起きない（P4・P7）。「一言で」「位置づけ」は背景が変わりにくい意味の要約であり、判断点に書かせる。J1 は課題とポジション定義を読む最初の判断点で、旧側の「分類した周に 4 つ書く」と同じ時点にあたる。
- 代替案:
  - B: 4 項目を別の表（`challenge_card`。版つき）に持つ — 書き直しの履歴を持てるが、状態の 2 項目を持つと遷移との二重管理になる。
  - C: 「一言で」「位置づけ」を J2（計画）に書かせる — 上流の本文とコメント・参照先を読むので位置づけの材料は多いが、分類済で計画を待つ課題のカードが空になる。
  - D: 4 項目とも持たず、タイトルと状態だけを出す — #131 の問題（カードを開いても中身が分からない）が残る。
- 影響範囲: `internal/core`（カードの面の導出・`challenge` の 2 列・J1 の写像）・`internal/core/internal/store`（`0007`）・`internal/invoker/prompts/`（J1 の指示文。M3P4 の上限 4 KiB に収める）・M3 の J1 の出力スキーマ（§決定事項の記録「仕様への指摘」）。

### 4. API の形と型の共有（外部システム連携ではないが、並列の実装チケットが共有する境界）【決定 2026-10-09 親 M4P2・M4P3】

- 採用案: A。API の成功の形は CLI の `--json` と同じにする。CLI の JSON の組み立てを `internal/view` の型つきの構造体へ移し、CLI と server が共有する。その構造体を正本として、リポジトリの中の小さな生成器（`go generate`・標準ライブラリだけ）が TypeScript の型（`web/src/api/types.gen.ts`）を書き出す。生成物はコミットし、生成し直した結果と差があれば落ちるテストを置く。
- 理由: M1〜M3 は CLI の JSON の形を仕様の表と `jsondoc_test.go` で固定している。API が同じ形なら、第 2 の正本を作らない。生成器を自前にすれば、本番の依存も UI のビルドの依存も増えない。
- 代替案:
  - B: OpenAPI の定義を手で書き、Go と TypeScript の両方を生成する — 定義が CLI の JSON の形と別の正本になる。
  - C: 型を共有せず UI 側で手書きする — board の `board-types.ts` が server の型を直接参照していた形を失い、ずれをテストで拾えない。
  - D: `internal/view` を作らず、server が CLI と同じ形を別に組み立て、等しいことをテストで確かめる — 組み立てが 2 か所になり、片方だけを直す誤りが起きる。生成器の入力（型）も無い。
- 影響範囲: `internal/view`（新設）・`internal/cli`（JSON の組み立ての移動。出力は変えない）・`internal/server`・`web/`・`Makefile`（生成の確認）。

## 機能全体の設計

### アーキテクチャ決定

- CLI の `--json` の形を組み立てる処理（今は `internal/cli` の `challengeJSON`・`runsJSON` などが `map[string]any` で組み立てている）を、新設の `internal/view` へ型つきの構造体（`json` タグつき）として移し、`internal/cli` と `internal/server` の両方がそれを使う。server は `internal/cli` を import しない（`internal/cli` が `serve` のために `internal/server` を import するので、逆向きは循環する）。移しても CLI の出力は変えない（M1〜M3 の `jsondoc_test.go` がそのまま通る）。TypeScript の型は `internal/view` の構造体から生成する【決定 2026-10-09 親 M4P3】。
- server が使う core の公開 API のうち、新しく足すもの: ⓪ M1 の探索規則でワークスペースのディレクトリだけを解決する関数（ストアが無くてもパスと名前を決めるため）とスキーマ版の読み直し ① 中断した run を回収しない run の一覧の読み取り（`OpenWorkspace` は回収しない。回収するのは run の一覧〔`ListRuns`〕・判断の呼び出し・周の開始・委譲の計画で、`status` が呼ぶ関数は回収しない。server が使うのは回収しない一覧の経路〔課題の詳細の run の欄も回収しない版を使う〕で、既存の `ListRuns` と CLI の出力は変えない） ② ストアの変化の観測（`PRAGMA data_version` を、書き込み・閲覧とは別の専用の 1 本の接続で読んで返す）③ カードの面の導出（課題・`status`・run・現在時刻から）④ 未回答の保留の一覧 ⑤ run の報告の読み取り（形の検査と run の存在の確認つき）。名前は実装で決めてよい【仮定】。
- server が状態を読み書きするのは core の公開 API だけである（P2。`waiting_external` のための `internal/adapters/github` の組み立ては M4P19 のとおり）。ワークスペースごとに core の `Store` を開き、要求ごとにワークスペースの名前から引く。server 自身はストアの外に状態を持たない。例外は、server の起動ごとに生成する CSRF の値（S2）・パスキーの challenge（S3。メモリ上・5 分で失効）・遠隔のサインインのセッション（S5。メモリ上）で、どれも server が落ちれば消えてよい【決定 2026-10-09 親 M4P1】。
- ライブ更新は、ワークスペースごとに専用の接続で `PRAGMA data_version` を 1 秒ごとに読み（`data_version` は他の接続の commit でだけ変わるので、観測の接続では書かない）、値が変わったら Server-Sent Events で `{"type":"workspace_changed","workspace":"<名前>"}` を送る。UI はその通知を受けて該当のワークスペースを読み直す。`data_version` は別の接続の commit で変わるので、CLI・`cycle`・別の server の書き込みを、作業ログに載らない `run`・`slot` の変化を含めて拾える【決定 2026-10-09 親 M4P4】。
- UI は単一ページのアプリとし、ビルド成果物をバイナリへ埋め込む。`go:embed` はパッケージのディレクトリより上を参照できないため、Vite の出力先は `internal/server` 配下の git で追跡しない `dist/` とする。Node が無い環境でも `go build ./...` が通るよう、「UI がビルドされていない」ことを示す最小の `index.html` を別のパスにコミットしておき、server は、ビルドした成果物があればそれを、無ければ最小の `index.html` を返す【決定 2026-10-09 親 M4P13。2026-10-10 親 P4 で具体化】。
- 書き込み（S2・S3）は CLI の同じ操作と同じ core の API を呼び、遷移の可否・承認の成立条件・作業ログの記録を server に書かない（`CLAUDE.md`「CLI は core の公開 API だけを呼ぶ」と同じ規律）。

### IF / API

#### fleet の宣言ファイル（`fleet.json`）【決定 2026-10-09 親 M4P5】

```json
{
  "version": 1,
  "workspaces": [
    {"name": "tom", "path": "/Users/masami/Tom"},
    {"name": "harness", "path": "/Users/masami/agents/harness"}
  ]
}
```

- 上の値は例で、コードに埋めない。`name` は `[a-z0-9][a-z0-9-]*`、`path` は絶対パス。未知のキー・重複・型の違いは `config_invalid`。

#### `flywheel serve` の引数

| 引数 | 内容 | スライス |
|---|---|---|
| `--port <n>` | 手元の待ち受けのポート（既定 4318） | S1 |
| `--fleet <path>` | fleet の宣言ファイル（`--workspace` と排他） | S1 |
| `--workspace <dir>` | 1 つのワークスペースだけを束ねる（M1 の共通フラグ） | S1 |
| `--remote-port <n>` | 遠隔の待ち受けを開くポート（指定しなければ開かない） | S5 |

CLI に足す本人確認つきの操作（S3）: `flywheel passkey enroll`（`tty_confirm` で本人確認し、1 回限りの登録用の符号と登録の URL を `/dev/tty` に表示する）・`flywheel passkey list`・`flywheel passkey remove <id>`（`tty_confirm`）。名前は【仮定】。

CLI に足す本人確認の要らない操作（S2）: `flywheel prioritize <C-ID> --priority <P0|P1|P2>`（優先度の変更。名前は【仮定】）。

| メソッドとパス | 返す形 |
|---|---|
| `GET /api/v1/workspaces` | `{"workspaces": [{"name", "path", "state", "error"}]}`。`state` は `ok \| store_not_found \| store_too_new \| store_error` の閉集合、`error` は `ok` のとき `null` |
| `GET /api/v1/workspaces/{name}/status` | `flywheel status --json` と同じ形 |
| `GET /api/v1/workspaces/{name}/challenges` | `flywheel list --json` と同じ形の各要素に `card`（下の「カードの面」）を足したもの |
| `GET /api/v1/workspaces/{name}/challenges/{id}` | `flywheel show --json` と同じ形の最上位に `card` を足したもの |
| `GET /api/v1/workspaces/{name}/log?challenge={id}` | `flywheel log [<C-ID>] --json` と同じ形 |
| `GET /api/v1/workspaces/{name}/runs` | `flywheel runs --json` と同じ形 |
| `GET /api/v1/needs-human` | `{"workspaces": [{"name", "needs_human"}]}`。`needs_human` は各ワークスペースの `status.needs_human` と同じ形。`state` が `ok` でないワークスペースは含めない |

| `GET /api/v1/workspaces/{name}/runs/{id}/report` | `{"report": {"run_id", "assumptions": [string], "unverified": [string]}}`。報告・キーが無ければ空の配列。`{id}` が `R-<正の整数>` でなければ `validation_failed`、ストアに無ければ `not_found` |
| `GET /api/v1/events` | Server-Sent Events。`workspace_changed` と、30 秒ごとの keep-alive のコメント行 |

`{name}` が fleet に無ければ `not_found`、`state` が `ok` でないワークスペースへの要求はその `state` のエラーコードで返す。

#### カードの面（`card`）【決定 2026-10-09 親 M4P7】

`{"state": <コード>, "modifiers": [<コード>…], "next_human_actions": [<コード>…], "headline": string|null, "context": string|null}`（`headline`・`context` は S4 まで常に `null`）。

- `state` は課題の状態のコード（M1 の 8 値）そのもの。
- `modifiers` は `running`（終了していない run がある）・`unresponsive`（終了していない run の heartbeat が 300 秒より古い。しきい値は M3 の中断の判定と同じ値を core から使い、導出の関数は現在時刻を引数で受け取る）・`waiting_ci`（`status.waiting_external` にある）・`budget_exhausted`（`status.needs_human.budget_exhausted` にある）・`discrepancy`（`status.needs_human.discrepancies` にある）の閉集合で、この順に重複なく並べる。
- `next_human_actions` は次の表の条件に当たるものを表の順に重複なく並べる。どれにも当たらなければ `[]`（UI は「なし（エージェントが進める）」と表示する）。

| コード | 条件 |
|---|---|
| `approve_plan` | 状態が計画承認待ち |
| `approve_completion` | 状態が完了確認待ち |
| `answer_question` | 状態が人間対応待ち |
| `triage` | `status.needs_human.triage` にある |
| `increase_budget` | `status.needs_human.budget_exhausted` にある |
| `approve_operation` | 未承認（`pending`）の不可逆操作がある（完了した課題を含む） |
| `review_discrepancy` | `status.needs_human.discrepancies` にある |
| `clear_slot` | 課題の run の `run.slot_id`（M3 のマイグレーション `0005`）で結ばれたスロットが `status.needs_human.slots` にある |

#### エラーコードと HTTP の状態コード

| エラーコード | HTTP の状態コード |
|---|---|
| `not_found`・`store_not_found` | 404 |
| `validation_failed`・`usage_error` | 400 |
| `invalid_transition`・`terminal_state`・`conflict`・`locked` | 409 |
| `verification_rejected`・`confirmation_mismatch` | 403 |
| `store_too_new`・`store_busy`・`store_error` | 503 |
| `internal_error` とその他 | 500 |

Host・Origin・CSRF の検査で拒否した要求は、core を呼ばずに 403 と `{"error":{"code":"forbidden_origin","message"}}` を返す【仮定: コード名】。

## 課題未満の引き継ぎ事項（flywheel#109）

旧側の受け箱（claude-flywheel#191）は、1 サイクル＝1 セッションの運用で会話にしか無い事項（記憶の草案・起票の草案・人間への依頼・フォローアップ候補）が、セッションを閉じると失われる問題への手当てだった。新しい構成では判断点が独立した呼び出しになり、会話の文脈を持ち越す親のセッションが無くなる（設計書 §7）。残る出どころは、委譲の報告の `assumptions`・`unverified`・`questions`（M3 §IF / API「判断点の出力」。`questions` は保留になる）と、J6 が扱う記憶の草案である。

本仕様は、受け箱をストアのエンティティにせず、J6・journal（Q6）と一緒に M4.5「学習と記録」の段へ送る【決定 2026-10-09 オーナー M4H8】。M4 では、委譲の報告の `assumptions` と `unverified` を課題の詳細の run の欄に表示する（S1。`.flywheel/runs/<run の ID>/` に保存済みの報告から読む）ところまでを持つ。根拠は旧側の運用の量で、親の要約によれば 2 周で 6 事項を仕分け、行き先は記憶 2・その場で人間に問う 2・捨てる 2・Issue の起票 0 だった【親の要約・未検証】。運用で確かめていない形をストアのスキーマに固定しない（flywheel#109 の合意）。受け箱を 2 本目の待ち行列にしない原則（やるべき作業は必ず課題を通す）は、後続の段で形を決めるときも引き継ぐ。

### server の起動と待ち受け

- [ ] `flywheel serve --workspace <dir>` は既定のポート 4318 で待ち受け、`GET /api/v1/workspaces` に 200 を返す
- [ ] `--port <n>` を指定すると、そのポートで待ち受ける
- [ ] `serve` の待ち受けのアドレスは `127.0.0.1:<ポート>` である（`0.0.0.0`・`::` ではない）。テストは `serve` が起動時に標準エラーへ出す 1 行（`listening on 127.0.0.1:<ポート>` の形）と、server のテストの中の待ち受けの `Addr()` の両方で確かめる
- [ ] 既に使われているポートを `--port` に指定すると、終了コード 2・エラーコード `listen_failed` で終わる
- [ ] Host ヘッダが `evil.example:4318` の要求は 403 で拒否される
- [ ] Host ヘッダが無い要求は 403 で拒否される
- [ ] Host ヘッダが `localhost:<ポート>` の要求と `127.0.0.1:<ポート>` の要求は、どちらも拒否されない
- [ ] Origin ヘッダが `http://evil.example` の要求は 403 で拒否される
- [ ] Origin ヘッダが `http://localhost:<ポート>` の要求は拒否されない
- [ ] Host・Origin の検査で拒否した応答の本文は `{"error":{"code":"forbidden_origin","message":…}}` である
- [ ] Host・Origin の検査で拒否した要求では、ストアのファイルの内容が変わらない
- [ ] `serve` に SIGTERM を送ると、終了コード 0 で終わる
- [ ] `serve` に SIGINT を送ると、終了コード 0 で終わる
- [ ] `GET /api/v1/events` を購読している接続がある状態で SIGTERM を送っても、`serve` は 5 秒以内に終了コード 0 で終わる（購読が終了を妨げない）【仮定: 5 秒】
- [ ] `serve` を起動したまま、同じワークスペースで `flywheel create` と `flywheel status` が成功する
- [ ] 閲覧の API だけを呼んだ場合、`serve` の起動から終了までの間に、ストアの `activity`・`run`・`lock` の行の内容が変わらない（heartbeat が 300 秒より古い終了していない run を含むストアで確かめる）

### M1〜M3 の仕様との関係（仕様への指摘。M1〜M3 の仕様書は変えていない）

- M1 の経路の閉集合を広げる: 経路 `ui` を足す（S2）。本人確認の方式に `passkey` を足し、登録簿に `(ui, passkey)` を足す（S3）。M1 §クリティカル設計決定 1 が予定した拡張である。
- M1 の遷移表の外に、本人確認の要らない操作を足す: 優先度の変更（`prioritize`。状態を変えない）。M1 では優先度は遷移 T2（分類）でしか設定できず、分類の後に変える操作が無い。作業ログの `action` に `prioritize` を足す。
- M1 PD7 を server の経路だけ広げる: UI からの本人確認の要らない変更は、表示した版が違えば `conflict` を返す（M4P8）。CLI は変えない。
- M1 の `Verifier` の形（`Confirm(summary, expectedID)`）と 2 段階の API: 端末向けの形で、ブラウザでは表示（①）と署名（②）が別の要求になり、まとめての承認では対象が集合になる（M4P20）。本仕様は、`Confirm` は ② で受け取った署名の検証だけを行い、`expectedID` には集合の正規形（§本人確認つきの書き込みの定義。1 件の承認も同じ形）を渡す【決定 2026-10-09 親 M4P21】。CLI の `tty_confirm` の `expectedID` は M1 のまま対象の ID 単独とする。core には、集合の承認の要約と版をまとめて得る API と、集合を 1 つの書き込みトランザクションで承認する API を足す（今の `ExecuteApproval` は 1 件ずつのトランザクション）。M1 の承認の規則は 1 件ずつそのまま当てはめる。実装で `Verifier` の形を変える必要が出たら、core の公開 API の変更として親に上げる。
- M1 H9（確認は対象の ID の入力）は、UI の経路には当てはめない（M4P20）。CLI の `tty_confirm` は変えない。
- M3 の J1 の出力スキーマを広げる（S4）: `headline`・`context` を足す（M4H7）。J1 の指示文の上限（M3P4 の 4 KiB）は変えない前提である。
- core の公開 API を足す（S1）: 回収しない run の一覧の読み取り・ストアの変化の観測・カードの面の導出・未回答の保留の一覧・run の報告の読み取り（§アーキテクチャ決定）。M3 は「次にストアを開いた flywheel のコマンドが中断した run を回収する」としているが、実際に回収するのは run の一覧・判断の呼び出し・周の開始・委譲の計画の入口であり、server の閲覧はこの入口を通らない。
