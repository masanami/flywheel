## 概要

flywheel が **core の決定的な進行と、判断点でだけ呼ぶ Claude** でサイクルを回せるようにする（設計書 §7・P1）。invoker が `claude -p` を起動し、判断点 J1（分類）・J2（計画）・J3（ブリーフ）・J4（子の問いへの応答）・J5（検証）の型付きの出力を検証して、core の遷移（M1 の遷移表）へ写す。実作業は、エージェントごとの接続ツールの宣言（§10）に従って子セッションへ委譲し、合流・成果物の照合・人間対応待ちとの往復・予算と枠の評価を core が行う。入口は個別の操作と、cron から呼べる一括の操作 `flywheel cycle` である。

M3 の完了の目安は **1 件の課題が、取り込みから完了確認待ちまで自走する**（設計書 §17）。本仕様はこれをスライス S1（判断点の基盤と、取り込みから計画承認待ちまで）と S2（委譲・照合・検証で完了確認待ちまで。`worktree` のスロットと同じリポジトリの並列を含む）の 2 段で満たし、S3・S4 に J4・束ね・`cli` 形態の接続ツールを置く（§スライス）。

## 背景・目的

- 現行 claude-flywheel の `run-cycle`（139,685 B・2026-09-28 時点の `main`＝`a5dfd43`）は、分類・計画・ブリーフの作成・子の問いへの応答・検証という**判断**と、依存ゲート・スロット割り当て・費用ガードの評価式・枠超過の伝播・起動と合流・イベント記録・結果の照合という**決定的な事務**を、1 つの散文で 1 つの LLM セッションに実行させている（設計書 §1.2 の手順 1〜4）。M3 は後者を core のコードへ移し、前者を判断点ごとの独立した呼び出しに分ける。
- 現行の散文が守らせている規律（`session_id` の事前採番・予算の 2 枠・周の上限と予約額・子が生成しないフィールドだけでの判別・外部実状態での照合・枠超過の周内伝播・1 スロット 1 セッション・保留の不可分な記録）は、コードの分岐と受入基準へ移す（§技術的な制約・方針「現行から引き継ぐ振る舞い」）。
- claude-harness の runtime（claude-harness#201）は、**flywheel 側の §10 の契約が実装されるまで CLI の形態を確定させない**方針である（harness `docs/harness-runtime-design.md` §0.1・§5.6）。本仕様が §10 の契約の形を初めて決める。
- M2 からの申し送り（M2 §M3 への申し送り・QH14）: 計画（J2）とブリーフ（J3）の入力に、計画する時点の上流の本文・コメントと関連 Issue を含める。J2 が読んだ記録を付けるのは、最新のコメントを実際に入力へ含めた場合に限る。

## ユーザーストーリー

- **オーナー（人間）** として、cron から `flywheel cycle` を呼ぶだけで、取り込んだ課題が分類・計画され、私の承認を待つところまで進んでいてほしい。承認したら、次の周で委譲・検証まで進み、完了の承認を待っていてほしい。
- **オーナー** として、1 回の委譲・1 周あたりに使ってよい費用の上限が、散文の約束ではなくコードで守られていてほしい。上限・枠超過・子の異常終了で止まったときは、何が起きたかを `status` で知りたい。
- **オーナー** として、子や判断点の Claude が、承認・保留への回答・不可逆操作を自分で行えないことを信頼したい（設計書 §9）。
- **対話セッションの Claude**（薄いスキル）として、`flywheel cycle --json` と `flywheel status --json` で、何が進み何が人を待っているかを読みたい。
- **接続ツールの作者（claude-harness の runtime）** として、flywheel が自分を呼ぶときに何を出力すればよいかが、flywheel 側の契約として固定されていてほしい（§10）。

## 機能要件

用語: **判断点**＝設計書 §7 の J1〜J5。**判断の呼び出し**＝1 つの判断点のための `claude -p` の 1 回の起動。　**委譲**＝接続ツールの宣言に従って、実作業を子セッション（`claude -p`、または `cli` 形態の接続ツール）へ渡すこと。**子**＝委譲先のセッション。　**run**＝判断の呼び出し 1 回、または委譲の起動 1 回（`--resume` による再開も 1 回と数える）の実行記録（設計書 §6 の `run`）。**終了していない run** が「実行中」。　**周**＝`flywheel cycle` の 1 回の実行、または `--auto` つきの個別の操作・`flywheel run` の 1 回の実行（予算の周の上限を評価する単位。§予算ガード）。`--auto` つきの個別の操作・`flywheel run` の 1 回の実行も `cycle` 表に 1 行を作り（`trigger` はその操作名。例: `classify --auto`）、`flywheel cycle` とは異なりサイクルの排他ロックは取らない【決定 2026-09-28 親】（#83・§サイクルの排他）。　**宣言**＝`.flywheel/connectors.json`（接続ツール・対象リポジトリ・人間へ上げる問いの種類）と `.flywheel/agent.json`（ポジション定義の置き場・予算・上限値）。　**スロット**＝委譲の子が作業する作業ツリー（設計書 §11）。　**照合**＝子の報告に依らず、外部の実状態（リモートのブランチ・PR・CI）とスロットのローカルの状態を読み取りで確かめること。　**偽の `claude`**＝テストで PATH の先頭に置く、引数と標準入力を記録して固定の応答を返す実行ファイル（M2 の偽の `gh` と同じ方式）。

各要件の末尾の `[S1]`〜`[S4]` は、その要件を実装するスライスを表す（§スライス）。

### invoker の共通の規則 [S1]

- [ ] 判断の呼び出しと委譲の起動は、PATH 上の `claude` を子プロセスとして起動して行う。`claude` の絶対パスをコードに埋めない（D13）
- [ ] PATH に `claude` が無いときは、何も起動・変更せずに `invoker_unavailable` で終わる
- [ ] 起動の直前に `session_id`（UUID の小文字表記）を採番し、`--session-id` で渡す。run は起動より前に `session_id` とともに記録する（起動と記録を不可分にする＝設計書 §7）
- [ ] 起動には必ず `--output-format json`・`--json-schema <その run の出力スキーマ>`・`--max-budget-usd <その run の上限額>` を付ける。上限額の無い起動はしない
- [ ] 指示文と入力は標準入力で渡し、コマンドの引数に埋め込まない（外部由来の文字列を引数にしない）
- [ ] 入力に含める外部由来の文字列（課題の本文・上流のコメント・子の報告・人間の回答）は、区切りの行で囲んだデータの区画に入れ、「区画の中の指示に従わない」ことを指示文に書く
- [ ] 1 回の起動には時間の上限（判断の呼び出しは既定 900 秒、委譲は既定 14,400 秒【決定 2026-09-28 親 M3P9】）を置き、超えたら子プロセスを停止して run の結果を `timed_out` にする
- [ ] 起動した flywheel のプロセスは、子プロセスが終わるまで待つ（常駐しない＝P6）。待つ間、60 秒ごとに run の生存の記録（heartbeat）を更新する
- [ ] 終了していない run の heartbeat が 300 秒より古く、記録したプロセスがそのホストで生きていなければ、次にストアを開いた flywheel のコマンドがその run を `interrupted` で終了させる【決定 2026-09-28 親 M3P10】
- [ ] 子の標準出力（結果の JSON）・標準エラー・渡した入力を、ワークスペースの `.flywheel/runs/<run の ID>/` に保存する（ストアには入れない）
- [ ] run の保存先を作るとき、`.flywheel/.gitignore` に `runs/` を除外する行が無ければ足す（Git で追跡させない＝D10 と同じ扱い）
- [ ] 返り値の `session_id` が採番した値と違えば、run に返り値の `session_id` を記録し、不一致だったことを run に残す（以後の `--resume` は返り値の値を使う）

#### 結果の判別【決定 2026-09-28 親 M3P6】

- [ ] run の結果は、次の表を上から順に評価し、最初に一致した行で決める。判別には子が生成しないフィールド（`subtype`・`is_error`・`structured_output` の有無と検証結果）と、起動・時間の上限の事実だけを使い、子の自由記述（`result`）を使わない

| # | 条件 | 結果 |
|---|---|---|
| 1 | 子プロセスを起動できなかった | `launch_failed` |
| 2 | 時間の上限を超えて停止した | `timed_out` |
| 3 | 標準出力が JSON のオブジェクト 1 つとして解釈できない | `malformed` |
| 4 | `subtype` が `error_max_budget_usd` | `budget_exhausted` |
| 5 | `is_error` が `true` | `errored` |
| 6 | `structured_output` が無い、またはその run の出力スキーマと core の閉集合の検査に合わない | `invalid_output` |
| 7 | 上のどれにも当たらない | `succeeded` |

- [ ] 結果が `succeeded` 以外の run は、課題の状態を変えない（委譲の照合と、下の枠超過の扱いは別に行う）（P4・設計書 §8.2）
- [ ] 出力の検査は、`claude` の `--json-schema` に任せきりにせず、core が閉集合と必須の組（例: J1 の `mine` には優先度が要る）を検査し直す
- [ ] 判断点の出力に未知の値・閉集合の外の値・宣言に無い id があれば `invalid_output` にする（fail-closed）

#### 枠（レート制限）超過【決定 2026-09-28 親 M3P12】

- [ ] 結果の表のどの行に当たった run でも、返り値の `result` が文字列として存在すれば、前後の空白を除いた先頭が `You've hit your ` に一致するかを調べ、一致すれば run に枠超過を記録する（先頭一致だけ。部分一致・2 行目以降の行頭は見ない。現行 `quota-check.sh` の規則をそのまま移す）
- [ ] 枠超過の判定の材料が無い（`result` が無い・空）ときは、枠超過ではないとして扱う
- [ ] 枠超過を 1 件でも記録した周は、その周の残りの判断の呼び出しと委譲を起動しない。起動済みの run は打ち切らず合流させる
- [ ] 枠超過で起動しなかった課題は状態を変えず、周の結果に起動しなかった理由（`rate_limited`）とともに示す
- [ ] 枠超過の run は、下の連続失敗の数に数えない

#### 費用の記録【決定 2026-09-28 親 M3P7・M3P8】

- [ ] run の費用は、返り値の `total_cost_usd` から記録する。記録には費用の出所（`reported`・`delta`・`unknown`）を添える
- [ ] 同じ `session_id` を `--resume` した run の費用は、返り値の `total_cost_usd` から、同じ `session_id` の直前の run が報告した `total_cost_usd` を引いた額とし、出所を `delta` にする（`--resume` の `total_cost_usd` はセッションの累計を返すという実測に基づく＝§要人間判定で確かめる）
- [ ] 差が負になる・直前の run の報告が無い・返り値に `total_cost_usd` が無い・run が `launch_failed` 以外で結果の JSON を得られなかった（`timed_out`・`malformed`・`interrupted`）ときは、その run に渡した `--max-budget-usd` の額を費用とし、出所を `unknown` にする（fail-closed。harness Q15 と同じ）
- [ ] `launch_failed` の run の費用は 0 とする（Claude を呼んでいない）

### 判断点の共通の規則 [S1]

### 合流と照合 [S2]

- [ ] 委譲の run が終わったら（`launch_failed` を除くどの結果でも）、照合を行う。照合は子の報告に依らない
- [ ] 照合では、スロットの作業ツリーの現在のブランチと、未コミットの変更の有無を調べる
- [ ] 照合では、報告のブランチ（無ければスロットの現在のブランチ）がリモートにあるかを `gh` で調べる
- [ ] 照合では、そのブランチを head とする PR（open・closed・merged のすべて）を `gh` で調べ、URL・状態・base のブランチを run の成果物として記録する
- [ ] 照合の `gh` の呼び出しはすべて GET である（GitHub へ書き込まない）
- [ ] スロットの作業ツリーに未コミットの変更が残っていたら、スロットを `needs_attention` にし、人が解除するまでそのスロットへ新しい委譲を割り当てない。flywheel はその変更を消さない（`reset`・`clean`・`checkout --` をしない）
- [ ] 結果が `succeeded` で結末が `completed` の委譲で、操作の成果物の種類の宣言（`pr | branch | none`）の成果物が照合で確かめられたら、課題を検証中にする（M1 T7）
- [ ] 結果が `succeeded` で結末が `completed` なのに、宣言の成果物が照合で確かめられなければ、課題を人間対応待ちにし、問いに「子は完了を報告したが成果物が見つからない」ことと照合の結果を書く（M1 T11）
- [ ] 照合で見つけた PR の base が、そのリポジトリの宣言の既定ブランチなら、課題に不可逆操作 `release`（要約は PR のタイトル、参照は PR の URL）を登録する。同じ PR の URL の `release` が既にあれば登録しない（M1 `op add`・D12）
- [ ] 照合で見つけた PR が既定ブランチへマージ済みで、その PR の `release` が承認されていなければ、課題を人間対応待ちにし、問いに承認なしの本番反映を検出したことを書く【決定 2026-09-28 親 M3P15】

- [ ] 結果が `succeeded` で結末が `questions` の委譲は、S2 では、問いの一覧を整形した文で課題を人間対応待ちにする（J4 は S3）。保留の記録に原因の run の ID を残す

### 失敗・差し戻しの上限 [S2]

- [ ] 結果が `errored`・`malformed`・`invalid_output`・`timed_out`・`interrupted` の委譲は、課題の状態を変えず、次の周で同じ `session_id` へ `--resume` して、固定の文面（中断の事実と、状態の報告を求める）で再開する

- [ ] 同じ計画の版で J5 が `not_met` を返した回数が差し戻しの上限（既定 3）に達した課題は、次の周で委譲を起動せず、人間対応待ちにする【決定 2026-09-28 親 M3P17】
- [ ] J5 の `not_met` で着手中に戻った課題の次の委譲は、直前の委譲の `session_id` へ `--resume` し、J5 の指摘を渡す

### 実行スロット [S2〜S4]

2026-10-01 に flywheel#73 の決定（§決定事項の記録 M3H8）で改めた。やめるのは「リポジトリあたりスロット 1 本」の運用で、「1 スロット 1 セッション」（作業ツリー 1 本につき子 1 つ）は残す。複数の課題を並列に実行するのは flywheel の責務で、接続ツールは並列度・直列化・fan-out を持たない（claude-harness#201 のコメント・harness `docs/harness-runtime-design.md` §5.4）。

- [ ] S2 のスロットのプロバイダは `clone` と `worktree` とし、リポジトリごとに宣言で選ぶ【決定 2026-10-01 オーナー M3H8】[S2]
- [ ] プロバイダ `clone` のスロットは宣言に書いた既存の作業用クローンのパスであり、flywheel はクローンを作らない（無ければそのリポジトリへ委譲しない）[S2]
- [ ] 1 つのスロットに、同時に 1 つの委譲だけを割り当てる（1 スロット 1 セッション）[S2]
- [ ] スロットの割り当てと解放は、ストアのトランザクションの中で行う（2 つのプロセスが同じスロットを取らない）[S2]
- [ ] スロットは、委譲の run が終わった時点で解放する（子が問いを出して終わった後、回答を待つ間はスロットを保持しない＝#73 論点 6）[S2]
- [ ] 委譲を割り当てる前に、スロットの作業ツリーに未コミットの変更が無いこと・宣言のリモートのクローンであることを確かめ、満たさなければ割り当てずにスロットを `needs_attention` にする [S2]
- [ ] `flywheel slot clear <スロットの ID>` は、`needs_attention` のスロットを使える状態に戻す（人が作業ツリーを確かめた後に使う。本人確認のない単発の操作）[S2]
#### プロバイダ `worktree`（S2 に入れる手当て）【決定 2026-10-01 オーナー M3H8】

- [ ] プロバイダ `worktree` のスロットは、宣言の元のクローン（`base`）から `git worktree add --detach <スロットのパス> <既定ブランチの手元の参照>` で作る作業ツリーであり、スロットの数は宣言の `count` である（既定ブランチは元のクローンで checkout 済みのため、分離した HEAD で作る）[S2]
- [ ] 同じ元のクローンについて、2 つのプロセスが同時に `git worktree add` を実行しない（共有の `.git` を触るため。2 つのプロセスから同時に払い出しを求めても直列に実行される）[S2]
- [ ] 払い出し（`git worktree add`）が失敗したスロットは、委譲を割り当てずに `needs_attention` にし、理由を記録する [S2]
- [ ] 払い出したスロットは課題ごとに作り直さず、`count` の本数を使い回す（払い出しは、そのスロットの初回だけ）【仮定】[S2]
- [ ] flywheel が作業ツリーの外側から git を呼ぶとき（払い出し・割り当て前の検査・照合）は、`GIT_DIR`・`GIT_WORK_TREE` を明示する（作業ツリーの `.git` は書き換え可能なポインタのファイルのため。claude-harness#200 の実測）[S2]
- [ ] 割り当ての前に、作業ツリーの `.git` のポインタが元のクローンのその作業ツリーを指していることを確かめ、違えば割り当てずにスロットを `needs_attention` にする [S2]
- [ ] 払い出しと割り当ての検査で、`git fetch`・`git clone` を実行しない（元のクローンの取得・更新は flywheel が行わない。子はブリーフの固定の節に従って最新の既定ブランチから作業ブランチを切る）[S2]

ビルド成果物・`node_modules`・ポートの衝突は、S2 では flywheel が手当てしない（§やらないこと）。衝突するリポジトリは、宣言でプロバイダを `clone` にするか `count` を 1 にして避ける。隔離が要るものは S4 の `container`。

#### 同じリポジトリの並列と直列化グループ【決定 2026-10-01 オーナー M3H8】

同じリポジトリへ同時に複数の委譲を起動してよいかは、操作ごとの固定の宣言では決めない。委譲の段の実行計画（起動の前）で、そのリポジトリの接続ツールの宣言にある衝突の予測の口（claude-harness の `harness predict-conflicts`＝claude-harness#288）を問い、その結果から core が組ごとに直列化グループを作る。予測の口は予測だけを返し、並列にするか・どの順で入れるかは core が決める。用語: **委譲の候補**＝その周の委譲の段の対象になった課題（§J3 の対象の条件を満たすもの）のうち、スロット・予算による除外の前のもの。**予測できる候補**＝委譲の候補のうち取り込み元の対応があり Issue 番号を渡せるもの。

- [ ] 同じリポジトリの予測できる候補が 2 件以上あるときだけ、そのリポジトリについて予測の口を 1 回呼ぶ【仮定】[S2]
- [ ] 予測の口に渡す Issue は、予測できる候補を優先度（`P0`→`P1`→`P2`→未設定）・ID の昇順に並べた先頭の 20 件までとする（口の受け付ける件数が 2〜20 件のため）。21 件目以降の候補は予測できない候補として扱う [S2]
- [ ] 予測で共有ファイルを持つ組の課題は同じ直列化グループに入る。グループは組の連結成分とする（A と B、B と C がそれぞれ共有ファイルを持てば、A・B・C が 1 つのグループになる）[S2]
- [ ] `merge_friendly` か `ignored` の印の付いた共有ファイルだけを持つ組は、その組を理由に同じグループに入れない（M3Q4 の推奨）[S2]
- [ ] 予測が判断できない組（`status` が `unknown`）の 2 つの課題は、同じ直列化グループに入る [S2]
- [ ] 予測できない候補・予測の `status` が `predicted` でない課題（`failed`・`budget_exhausted`）が 1 件でもあれば、そのリポジトリの委譲の候補はすべて 1 つの直列化グループに入る（fail-closed）[S2]
- [ ] 予測の口の呼び出し全体が失敗したとき（`command` を起動できない・時間の上限を超えた・終了コードが 0 でない・標準出力が JSON として読めない・出力の `schema` が宣言と違う・出力の `error` が `null` でない）は、そのリポジトリの委譲の候補はすべて 1 つの直列化グループに入る [S2]
- [ ] 接続ツールに衝突の予測の口の宣言が無いリポジトリの委譲の候補は、すべて 1 つの直列化グループに入る [S2]
- [ ] 周の上限のため予測の口を呼べなかったリポジトリの委譲の候補は、すべて 1 つの直列化グループに入る（委譲は止めず、直列で起動する）[S2]
- [ ] 直列化グループの中は、予測の依存の向き（`dependency.first`＝先に入れるべき側）を辺とする位相順に起動する。辺で順が決まらない課題どうしは優先度・ID の昇順とし、辺が循環するグループはそのグループの辺をすべて無視して優先度・ID の昇順とする [S2]
- [ ] 1 つの直列化グループの中では、前の課題の委譲の run が終わってから次の課題の委譲を起動する [S2]
- [ ] 異なる直列化グループの委譲は同時に実行される（グループ 2 つ・空きスロット 2 本以上・`max_parallel_runs` 2 以上のとき、2 つの委譲が同時に終了していない run になる）[S2]
- [ ] 周の中で同時に終了していない委譲の run の数は、全リポジトリの合計で `.flywheel/agent.json` の `max_parallel_runs`（既定 2）を超えない [S2]
- [ ] 1 つのリポジトリで同時に終了していない委譲の run の数は、そのリポジトリの使えるスロット（`needs_attention` でないもの）の数を超えない [S2]
- [ ] 同じリポジトリに、その周より前から終了していない委譲の run がある課題（個別の `flywheel run` で起動したもの）は、予測の口に渡す Issue に含め、それと同じ直列化グループに入った候補はその周では起動せず、`not_started` に理由 `serialized` で示す（M3Q9 の推奨）[S2]
- [ ] `cycle --json` の委譲の段は、直列化グループを `serial_groups` に示す（形と理由の閉集合は §IF / API）[S2]

#### その他

スロットの払い出し主体: 操作の宣言で、スロットを flywheel が払い出すか（`flywheel`）、接続ツールに任せるか（`connector`）を選べるようにするか（`slot_owner: connector` の要否）は、S2・S3 の分解のときに決める。claude-harness の `harness run ticket` は呼び出し元が渡した作業ツリーを `provided` として受けて消さないため、claude-harness には不要になる見込み（flywheel#73 の 2026-09-29 のコメント）【決定 2026-10-01 オーナー M3H8】。決まったら、検証できる要件としてここに書く。

### 予算ガード

- [ ] 判断の呼び出しの `--max-budget-usd` は、`.flywheel/agent.json` の判断点ごとの上限額（既定 J1: 1・J2: 5・J3: 3・J4: 2・J5: 5。USD）とする【決定 2026-09-28 親 M3P9】[S1]
- [ ] 周の上限は `.flywheel/agent.json` の周の上限額（既定 300 USD。現行の `cycle_budget_usd` と同じ）とする [S1]
- [ ] 判断の呼び出しも委譲も、起動の前に「その周の既消費額 ＋ その周の終了していない run に渡した上限額の合計（予約額）＋ これから起動する run の評価額 ＞ 周の上限額」を評価し、真なら起動しない（現行の評価式）[S1]
  - 「その周」は run.cycle_id が指す `cycle` 表の行である。`flywheel cycle` の run だけでなく、`--auto` の個別の操作が作る run（用語「周」参照）も自分の cycle 行に対してこの評価を受ける【決定 2026-09-28 親】（#83）。
- [ ] 周の既消費額は、その周に終了した run の費用（§費用の記録）の合計である。run が終わったら、その run を予約額から外し、費用を既消費額へ足す（二重に数えない）[S1]
- [ ] 判断の呼び出しの評価額は、その呼び出しに渡す上限額である [S1]
- [ ] 周の上限で起動しなかった判断の呼び出し・委譲は、課題の状態を変えず、周の結果に理由（`cycle_budget`）とともに示す。周は、LLM を呼ばない処理（取り込み・照合）を続ける [S1]
- [ ] 実装の委譲の評価額は、その計画の版の実装枠の残りの額とレビュー対応枠の残りの額の和である（レビュー対応を実装の続きとして予約する＝現行 #173）。`--max-budget-usd` に渡すのと予約額に数えるのは、実装枠の残りの額だけである [S2]
- [ ] 計画の版の実装枠の残りの額は、承認済みの計画の実装枠の額から、その計画の版の実装の委譲の run の費用の合計を引いた額である（レビュー対応枠も同様。一方の残りを他方へ融通しない）[S2]
- [ ] 実装枠の残りの額が 1 USD 未満の課題には委譲を起動せず、`status` の `needs_human.budget_exhausted` に出す [S2]
- [ ] 予算を使い切った課題の予算を増やすのは、人間の本人確認つきの操作 `flywheel budget <C-ID> --impl-usd <額> [--review-usd <額>]` だけである。成立すると、承認の種類 `budget` の記録を残し、その計画の版の枠を指定した額へ置き換える【決定 2026-09-28 オーナー M3H3】[S2]
- [ ] 衝突の予測の口に渡す上限額（`--max-budget-usd`）は、渡す Issue の件数 × `.flywheel/agent.json` の `conflict_prediction_budget_usd`（1 件あたり。既定 1 USD）とする（M3Q7 の推奨）[S2]
- [ ] 衝突の予測の口の呼び出しの前に、周の既消費額 ＋ 予約額 ＋ 口に渡す上限額 ＞ 周の上限額なら、呼ばない（呼べなかったリポジトリの扱いは §実行スロット）[S2]
- [ ] 衝突の予測の口の出力に `cost_usd` が無い、または呼び出し全体が失敗したときは、渡した上限額を周の既消費額に数える（fail-closed）[S2]
- [ ] 同時に起動した委譲の上限額は、それぞれ予約額として周の上限の評価に含める（並列の本数が増えても評価式は変えない＝flywheel#73 論点 7）[S2]
- [ ] レビュー対応の委譲（PR のレビューへの対応）は、レビュー対応枠の残りを `--max-budget-usd` に渡す [S3]

### 一括の操作（サイクル）[S1。委譲と検証の段は S2]

- [ ] `flywheel cycle` は、サイクルの排他（下記）を取り、次の段を順に実行して、排他を解放する: 取り込み（`.flywheel/sources.json` があれば M2 の `ingest`）→ 分類（J1）→ 計画（J2）→ 委譲（S2）→ 検証（S2）
- [ ] 各段は、個別の操作（`classify --auto`・`plan --auto`・`run`・`verify --auto`）と同じ core の処理を呼ぶ。`cycle` は独自の遷移の規則を持たない（設計書 §7・D11）
- [ ] 各段の中では、対象の課題を優先度（`P0`→`P1`→`P2`→未設定）、同じ優先度では ID の昇順で処理する
- [ ] 前の段で状態が進んだ課題は、同じ周の後の段の対象になる（例: 分類で分類済になった課題は、同じ周の計画の段で計画される）
- [ ] 承認・差し戻し・保留への回答は行わない。計画承認待ち・完了確認待ち・人間対応待ちの課題は、どの段の対象にもならない
- [ ] 委譲の段は、起動の前に実行計画（リポジトリごとの直列化グループ＝§実行スロット「同じリポジトリの並列と直列化グループ」）を作る。同時に起動する委譲の数の上限は §実行スロットのとおり [S2]
- [ ] 検証の段は、その周の委譲の段で起動した委譲の run がすべて終わってから始まる [S2]
- [ ] `flywheel cycle --trigger <文字列>` は、起動の契機（例: `cron`・`manual`）を周の記録に残す（自己申告。省略時は `manual`）（設計書 §12.3 の 5）
- [ ] `flywheel cycle --json` は、周の ID・契機・段ごとの対象と結果・起動しなかった課題とその理由・周の既消費額・既定値を使った設定を出力する（形は §IF / API）
- [ ] 周の中の run が失敗しても、`cycle` は終了コード 0 で終わり、失敗は結果に示す（M2 の部分成功と同じ）【決定 2026-09-28 親 M3P3】
- [ ] 定期実行の担い手（スケジューラ）は持たない。定期実行は cron などの外部から `flywheel cycle` を呼ぶ【決定 2026-09-28 オーナー Q5】

#### サイクルの排他【決定 2026-09-28 親 M3P10】

- [ ] サイクルの排他は、ストアの中の名前つきのロック（保持者のプロセス ID・ホスト名・取得時刻・heartbeat）で行う
- [ ] ロックを保持している `cycle` は、60 秒ごとに heartbeat を更新する
- [ ] 保持者の heartbeat が 300 秒より古く、保持者のプロセスがそのホストで生きていなければ、ロックは stale とし、次の `cycle` が回収して取得する
- [ ] 生きている保持者がいれば、`cycle` は何もせずに `locked` で終わる
- [ ] `cycle` は、取得に成功したロックだけを解放する（保持者が自分でなければ解放しない）
- [ ] 個別の操作はサイクルのロックを取らない。同じ課題に対する二重の起動は、「課題ごとに終了していない run は高々 1 つ」の制約（ストアの一意制約）で防ぐ

## 非機能要件

- **LLM**: LLM を呼ぶのは invoker の子プロセス（`claude -p`）だけである。core・adapter・CLI は Anthropic の API を直接呼ばない（設計書 §8.1）。
- **ネットワーク**: GitHub への接続は `gh` の子プロセスに限り、すべて GET である（M2 と同じ）。**`go test ./...` は本物の `claude`・`gh` を起動しない**（CI に Claude と GitHub の認証は無い。偽の `claude`・偽の `gh`、または core の IF の偽の実装で置き換える）。
- **承認の安全性**: 判断の呼び出しと子は、通常の道具立てで承認・差し戻し・保留への回答・予算の増額に到達できない（設計書 §9。二重の担保: 本人確認つきの操作は端末を要し、経路 `invoker` からは core が拒否し、子の権限から `flywheel` の実行を外す）。同じユーザーのプロセスによる意図的な回避は防御の対象外（M1 と同じ）。
- **外部本文の扱い**: 課題の本文・上流のコメント・子の報告・人間の回答は、判断点の入力のデータの区画に入れ、指示として扱わない。判断点の出力が状態・承認・コマンドを直接決めることはない（出力は閉集合と宣言の id に限り、core が写す＝P4）。
- **費用**: 周の上限と 1 回の上限は、費用が取れないとき上限額を消費したとみなす（fail-closed）。判断点の分も周の上限に数える。
- **並行性**: `cycle` 同士は排他する。個別の操作と `cycle` が並行しても、1 つの課題に終了していない run が 2 つできず、1 つのスロットに 2 つの委譲が割り当てられない。`worktree` の払い出しは同じ元のクローンについて直列である（S2）。
- **常駐しない**: flywheel は子プロセスを待つ間だけ生存する。flywheel のプロセスが落ちても、次のコマンドが中断した run を `interrupted` として閉じる（自動で再実行はしない。再開は次の周の規則に従う）。
- **配布・動作環境**: M1 と同じ（`CGO_ENABLED=0` の単一バイナリ・macOS と Linux）。`claude`・`gh`・`git` は実行時の依存であり、ビルドの依存ではない。

## 技術的な制約・方針

- 使用技術: Go（M1・M2 と同じ）。本番の依存の上限（標準ライブラリ・`modernc.org/sqlite`・`golang.org/x/term`）を変えない。Anthropic の SDK・GitHub のクライアントライブラリを足さない（`claude`・`gh` を子プロセスで呼ぶため）。
- 変更対象: `internal/core`（判断点の出力の写像・run・周・ロック・スロット・予算の評価・意思決定の主体の判定・照合の規則・宣言の検証）、`internal/core/internal/store`（マイグレーション `0004`〔S1〕・`0005`〔S2〕）、`internal/cli`（`cycle`・`run`・`runs`・`classify --auto`・`plan --auto`・`verify --auto`・`slot clear`・`budget`・`status`／`show` の拡張）、**新設** `internal/invoker`（`claude` の起動と応答の正規化・指示文と雛形・出力スキーマ）、`internal/adapters/github`（上流のコメント・参照先の Issue・PR・CI の取得を足す。すべて GET）、**新設** `internal/adapters/git`（スロットの作業ツリーの検査。S2）【決定 2026-09-28 親 M3P2】。
- **import の向き**: `internal/core` は `internal/invoker`・`internal/adapters` を import しない。core は判断の呼び出し・委譲・上流の取得・スロットの検査の IF を定義し、invoker と adapter がそれを実装する（M2 の取得の IF と同じ形）。`internal/invoker` と `internal/adapters/*` はストアのパッケージを import しない。`internal/cli` が invoker と adapter を組み立てて core へ渡す。
- `CLAUDE.md` の「M1・M2 で置くパッケージ」の表は、`internal/invoker`・`internal/adapters/git` を足す実装チケットで同時に更新する（本仕様の PR では変えない）。

### テストでの Claude・GitHub の置き換え

- core の判断点・委譲・予算・照合は、判断の呼び出しと委譲の IF の偽の実装（固定の出力・費用・結果を返すメモリ上の実装）と、**実ストア**（`t.TempDir()` の SQLite）で検証する。ストアはモックしない（M1・M2 と同じ）。
- `internal/invoker` と CLI のテストは、**偽の `claude`**（テストが一時ディレクトリに置き、PATH の先頭に足す実行ファイル。受け取った引数と標準入力をファイルに記録し、フィクスチャの結果の JSON・終了コード・遅延を返す）で行う。本物の `claude` は呼ばない。
- 上流・PR・CI の取得は、M2 と同じ偽の `gh` か、取得の IF の偽の実装で置き換える。
- 実物の `claude` との疎通（構造化出力・費用・`--resume` の費用の累計・読み取り専用の道具の制限・枠超過の文面）は、受入基準の要人間判定に置く。

### 2. 判断の呼び出しと子の権限（セキュリティ）【決定 2026-09-28 オーナー M3H4】

- **採用案**:
  - 判断の呼び出しは、作業ディレクトリをワークスペースとし、読み取り専用の道具（ファイルの読み取り・検索）だけを許し、それ以外の道具を拒否して起動する。記憶・ポジション定義を読むのは道具で行う。
  - 委譲の子は、接続ツールの宣言の権限モード（`default | acceptEdits | auto`）で起動する。`bypassPermissions` は宣言できない。
  - 委譲の子には、`flywheel` の Bash での実行を拒否する指定を必ず付ける（承認・回答・予算の増額に加え、ストアの状態を子から変えさせない）。
  - 本人確認つきの操作は、M1 のとおり端末（TTY）と `CLAUDECODE` の検査で拒否され、core は経路 `invoker` の本人確認つきの組み合わせを受け付けない。
- **理由**: 判断点は意味判断だけを返す（P4）ので、書き込みの道具は要らない。道具を読み取りに限ると、外部本文に仕込まれた指示に判断の呼び出しが従っても、書き込み・外部送信に至らない。子の権限モードは接続ツールと対象 repo の設定（deny）に依存するため宣言に置く。`auto` の分類器は不可逆操作の歯止めに数えない（Tom の実測で同じ `gh repo delete` を止めた周と通した周がある）ので、歯止めは固定の節と `--disallowedTools` と対象 repo の deny が担う。
- **代替案**:
  - B: 判断の呼び出しに道具を与えない（入力に必要な知識をすべて invoker が詰める）— 記憶の索引から関係分を選ぶ recall を invoker に作り込む必要がある。
  - C: 権限モードを `auto` に固定する — `acceptEdits` で足りる接続ツールや、より絞った運用ができない。
- **影響範囲**: `internal/invoker`（起動の引数）・`internal/core`（経路の登録簿）・宣言の検証。

### 3. 接続ツールとの契約（§10。外部システム連携）【決定 2026-09-28 オーナー M3H2】

- **採用案**:
  - 宣言（`.flywheel/connectors.json`）は、接続ツールごとに形態（`plugin | brief | cli`）・権限モード・操作の一覧を、エージェント全体で人間へ上げる問いの種類を、リポジトリごとに使う接続ツールとスロットを持つ（形は §IF / API）。
  - 操作は、id・起動形（`plugin` はスキルの呼び出しの文字列、`cli` は引数の配列）・対話前提か・対話相手（`human | parent`）・子に決定を委ねてよいか・成果物の種類（`pr | branch | none`）・束ね（S3）を持つ。スロットの払い出し主体（`slot_owner`）を持たせるかは S2・S3 の分解のときに決める。操作ごとの「並列してよいか」（`parallel_safe`）は持たない（同じリポジトリの並列は §クリティカル設計決定 7 の予測で決める）【決定 2026-10-01 オーナー M3H8】。
  - 接続ツールは、衝突の予測の口（引数の配列と出力の形の版）を持てる（S2。§クリティカル設計決定 7）。
  - **`cli` 形態の契約は flywheel が定め、接続ツールが合わせる**。flywheel は `start`・`status`・`resume`・`cancel` の 4 つのコマンドを宣言の引数の配列（シェルを介さない。差し込みは閉集合）で呼び、`start`・`status`・`resume` の標準出力に次の JSON（契約の版 1）を求める: `{"contract_version": 1, "run_id", "state": "running|waiting|succeeded|failed|cancelled", "summary", "requested_action": null | {"kind": "answer|approve|observe", "decider": "human|parent|any", "text"}, "artifacts": [{"kind": "pr|branch|commit|other", "ref"}], "cost_usd": number|null}`。終了コードは「JSON を出力できたか」だけを表し（0 = 出力した）、待機・成功・失敗は `state` で表す。`decider` が `human` の `answer`・`approve` は flywheel が回答せず、人間対応待ちにして接続ツール側の承認経路（harness の `approve`・TTY）を案内する。接続ツール内部の手順・判断値は持ち込まない（設計書 §10）。
  - `cli` 形態の委譲は S4 で実装する。S1〜S3 では宣言の検証だけを行う。
  - 現行 `positions/<domain>.md` §5 からの写し方は §IF / API「現行の宣言からの写し方」に置く。
- **理由**: harness は「flywheel §10 の実装が入ってから起動形を確定させる」としている（harness 設計 §0.1）。flywheel が接続ツールごとの出力の形を写す仕組み（フィールド名の対応表）を持つと、core が接続ツール固有の形を抱える（P5・D7）。flywheel が汎用の形を 1 つ定め、接続ツールが合わせる方が、P5 と「flywheel は harness 内部の step・判断値を理解しない」（harness §0）の両方に合う。harness が「runtime が出せなければならない情報」（harness §5.6: run ID・汎用の状態・要約・人に求める操作・成果物の参照・中止と再開に必要な情報）と上の JSON は 1 対 1 に対応する。終了コードで待機と失敗を分ける harness §5.2 の形は、この契約でも妨げない（flywheel は終了コードの 0 以外を「出力なし」とだけ読み、`state` を正とする）。
- **代替案**:
  - B: 宣言に接続ツールの出力のフィールド名の対応表を持たせ、flywheel が写す — 接続ツールは自由に形を決められるが、core か adapter が写しの規則を持ち、宣言が肥大する。
  - C: `cli` 形態の契約を M3 で決めず、harness の CLI が固まってから flywheel が合わせる — harness が flywheel を待っているため、双方が待つ。
  - D: 終了コードで状態を表す（harness §5.2 の案を契約にする）— JSON を読めない失敗と `failed` の状態の区別が終了コードの割り当てに依存する。
- **影響範囲**: 宣言の検証（`internal/core`）・`internal/invoker`（`cli` 形態の起動は S4）・claude-harness の runtime（契約に合わせる側。harness 側の変更は本仕様の範囲外）。

### 4. 予算ガードと費用の数え方【決定 2026-09-28 オーナー M3H3／親 M3P7・M3P8】

- **採用案**:
  - 評価式は現行と同じ（既消費＋予約額＋評価額 ＞ 周の上限額なら起動しない）。判断点の分も周の上限に数える。1 回の `flywheel` のコマンドの実行を 1 周とする（個別の操作も周の上限の評価を受ける）。
  - `--resume` の run の費用は、返り値の累計と、同じセッションの直前の報告との差とする。差が負・直前の報告が無い・費用が取れない場合は、渡した上限額を消費したとみなす（fail-closed）。
  - 予算の増額は、人間の本人確認つきの操作（`flywheel budget`）だけで行い、承認の種類 `budget` として残す。
- **理由**: `--max-budget-usd` は起動ごとにしか効かず、`--resume` ではカウンタが 0 に戻る（Tom の実測）。harness の PR-3 の実測（2026-09-26・`claude` 2.1.283）で、`--resume` した 2 回目の `total_cost_usd` がセッションの累計（$0.2145 → $0.3514。出力トークン 165＝54＋111）だった。報告を丸ごと足すと累計を二重に数え、上限に早く届きすぎる。ただし実測は 1 例なので、要人間判定で確かめ、反証されたら丸ごと足す形（安全側）へ戻す。増額は安全性のトレードオフであり、計画の承認で人が承認した額を Claude が増やせてはならない。
- **代替案**:
  - B: `--resume` の報告を丸ごと足す（現行の書き方）— 実測どおりなら二重に数え、2 回目以降の再開が早く止まる。安全側ではある。
  - C: 予算を使い切った課題を、新しい遷移（着手中 → 計画承認待ち）で計画から出し直させる — M1 の遷移表を変える。J2 をもう一度呼ぶ費用がかかる。
  - D: 使い切った課題を人間対応待ちにし、回答の文で増額を受け付ける — 回答は自由記述で、額を型として受け取れない。
- **影響範囲**: `internal/core`（評価式・費用の記録・承認の種類 `budget`）・`internal/cli`（`budget`）。承認の種類の閉集合（M1 `approval.kind`）を広げる（§決定事項の記録「M1・M2 の仕様との関係」）。

### 5. J1 の `not_mine` の行き先（状態機械への影響）【決定 2026-09-28 オーナー M3H5】

- **採用案**: `not_mine` では課題の状態を変えない。J1 の run の記録（判定と、判定した時点の課題の版）から、自動の J1 の対象から外すことと、`status` の `needs_human.triage` に出すことを導く。人は `classify --priority` で分類するか、M1 S2 の取り下げ（実装されれば）で閉じる。
- **理由**: M1 H6 は取り下げを `not_mine` の行き先としたが、取り下げは M1 S2 で未実装で、終端である。Claude の判定だけで課題を終端へ送ると、誤りを戻せない。人間対応待ちへ送る案は、回答で未分類に戻ると J1 が再び走り、同じ判定を繰り返しうる。状態を変えずに「判定済み」を記録から導けば、M1 の遷移表を変えずに済む。
- **代替案**:
  - B: M1 S2 の取り下げを M3 の前提に入れ、`not_mine` で自動的に取り下げる — 終端のため戻せない。
  - C: `not_mine` で人間対応待ちにする（問いを自動で作る）— 回答後に同じ判定を繰り返す恐れがあり、人が毎回答える必要がある。
- **影響範囲**: `internal/core`（J1 の写像・自動の対象の選び方・`status`）。M1 の遷移表は変えない。

### 6. 外部への書き戻し（Q4）【決定 2026-09-28 オーナー M3H1】

- **採用案**: M3 では取り込み元の Issue へ書き戻さない（下の対象のすべてで A）。Issue の close は、子が作る PR の `Closes #<番号>` と、人が行う既定ブランチへのマージに任せる。
- 対象と契機ごとの選択肢:

| 対象 | 契機 | A（採用） | B | C |
|---|---|---|---|---|
| Issue の close | 完了の承認（T13・T14） | 書き戻さない（PR の `Closes #<番号>` とマージに任せる） | 完了の承認と同時に flywheel が close する（完了の承認の操作に含める。外部送信の承認を同じ操作で済ませる） | `external_send` の不可逆操作として登録し、個別に承認させてから close する |
| ラベル | 状態の遷移 | 付けない | 状態に対応するラベル（例: `flywheel:in-progress`）を付け替える | — |
| コメント | 保留の問い（人間対応待ち） | 書かない（問いは `status`・UI で示す） | 問いを Issue にコメントする | 問いを Issue にコメントし、Issue での返信を回答として取り込む |
| コメント | 計画の登録・PR の作成 | 書かない | 計画の要約・PR の URL をコメントする | — |
| assign | 取り込み・`not_mine` | 変えない | `not_mine` で自分の assign を外す | — |

- **理由**: 書き戻しは組織外への送信（FR-22 の外部送信）であり、送信済みは撤回できない。書き戻す場合は承認の設計（どの操作で外部送信を承認したとみなすか）が要る。M3 の完了の目安（完了確認待ちまでの自走）に書き戻しは要らない。Issue の close は PR の `Closes #<番号>` で現行と同じ結果になる。コメントでの回答の取り込み（コメント C 案）は、外部の文を本人確認なしに保留への回答として受け付けることになり、M1 H8（回答は本人確認つき）と衝突する。書き戻しは adapter の単位で後から足せる（設計書 §16 の見立て）。
- **既知の帰結**: 完了の承認を `--hold-release` で行い本番反映を保留した課題や、PR を伴わない課題では、完了後も Issue が open のまま残る（M2 は「課題は完了したが上流は open」を食い違いとして出さない）。
- **影響範囲**: なし（A の場合）。B・C を採る対象があれば、`internal/adapters/github` に書き込みの呼び出しを足し、承認の設計を本仕様に足す。

### 7. 同じリポジトリの並列と衝突の予測（外部システム連携）【決定 2026-10-01 オーナー M3H8】

- **採用案**:
  - `worktree` のスロットを S2 に置き、同じリポジトリに複数のスロットを払い出す。払い出しは直列、使用は並列。1 スロット 1 セッションは残す。
  - 同じリポジトリで並列にしてよいかは、委譲の段の実行計画で接続ツールの衝突の予測の口（claude-harness `harness predict-conflicts`・出力の形 `harness.conflict-prediction/v1`・claude-harness#288／PR #290）を問い、その結果から core が組ごとの直列化グループを作って決める。接続ツールは予測だけを返し、決定（並列にするか・順序）は flywheel が持つ。操作単位の `parallel_safe`（M3P20）は採らない。
  - 予測が得られない課題・判断できない組・予測の口の宣言が無いリポジトリ・周の上限で予測を問えなかったリポジトリは、直列にする（fail-closed）。
  - 予測の口は委譲ではない（run の開始・再開ではない）ので、接続契約 v1（§クリティカル設計決定 3）とは別の口として宣言する。
- **理由**: 衝突は操作の種類ではなく課題の組ごとに決まり、操作単位の固定のフラグでは表せない（flywheel#73 の 2026-09-29 のオーナーの方針）。ファイル単位の衝突は flywheel だけでは判定できないが、接続ツールはリポジトリの中身を読んで予測できる。予測を材料にとどめ、決定を flywheel に置けば、複数の課題の並列実行を flywheel の責務にする方針（claude-harness は並列度・直列化・fan-out を持たない）と合う。予測が無いときに直列へ倒せば、予測の口の失敗が衝突として現れない。
- **代替案**:
  - B: 操作の `parallel_safe` だけ並列にする（旧 M3P20）— 同じ操作の課題どうしの衝突を表せない。仕様の作成のように衝突しにくい工程でも、課題によっては同じ文書を触る。
  - C: 人間が依存・直列化グループを宣言する — 周ごとに人の手間がかかり、自走の律速が人に移る。
  - D: 衝突を許容し、マージの時点で気付く — 衝突した後のやり直しの費用が大きく、子の作業が無駄になる。
- **影響範囲**: `.flywheel/connectors.json` の検証（`conflict_prediction`・`slots` の `worktree`）・`internal/core`（実行計画・直列化グループ・予算の評価）・`internal/adapters/git`（払い出しと `.git` のポインタの検査）・予測の口を起動する adapter（置き場は未決）・ストア（`slot.provider` の閉集合に `worktree`・予測の記録。§クリティカル設計決定 1 の拡張。未決の論点 M3Q2）。claude-harness 側の変更は無い（#290 で実装済み）。

## 機能全体の設計

### アーキテクチャ決定

- **規則は core、入出力は invoker と adapter**。core は判断の呼び出し（`Judge(ctx, JudgmentRequest) (JudgmentResult, error)`）・委譲（`Delegate(ctx, DelegationRequest) (DelegationResult, error)`）・上流の取得（M2 の IF を拡張）・スロットの検査・PR と CI の取得の IF を定義し（名前は【仮定】）、対象の選び方・出力の写像・予算の評価・意思決定の主体の判定・照合の規則をすべて持つ。invoker は `claude` を起動し、結果の JSON を core の型（結果・費用・`session_id`・構造化出力・枠超過の判定材料）へ正規化するだけで、規則を持たない。
- **1 つの run の流れ**: ① 書き込みトランザクションで、対象の条件・予算の評価・スロットの割り当てを検査し、run を記録する（ここで課題ごとの一意制約が二重の起動を防ぐ）→ ② トランザクションの外で子プロセスを起動して待つ（heartbeat は短いトランザクションで更新）→ ③ 書き込みトランザクションで、run の結果・費用を記録し、課題の最新の状態を読み直して出力を写す（読み直した状態が遷移元でなくなっていれば写さず、run の出力だけを残す）。M2 の取り込みの ①〜③ と同じ形にし、子を待つ間にストアの書き込みロックを持たない。
- **周の流れ**: `cycle` は ロックの取得 → 段ごとに対象を選んで run を起動（委譲の段だけ並列）→ 合流 → ロックの解放。予算の評価は run の起動ごとに ① で行う。
- `internal/cli` の `cycle`・`run`・`--auto` は、宣言を core に読ませ、invoker と adapter を作って core へ渡し、結果を出力するだけ。

#### `.flywheel/connectors.json`【決定 2026-09-28 オーナー M3H2／親 M3P1】

```json
{
  "version": 1,
  "human_question_kinds": [
    {"id": "distribution", "label": "配布形態"},
    {"id": "responsibility_boundary", "label": "3 リポジトリ間の責務境界"}
  ],

    {
      "id": "claude-harness",
      "form": "plugin",
      "permission_mode": "auto",
      "conflict_prediction": {"command": ["harness", "predict-conflicts"], "schema": "harness.conflict-prediction/v1"},
      "operations": [
        {"id": "impl", "invocation": "/claude-harness:impl {issue_number}", "interactive": false, "child_may_decide": true, "artifacts": "pr"},
        {"id": "define-feature", "invocation": "/claude-harness:define-feature {issue_url}", "interactive": true, "counterpart": "parent", "child_may_decide": false, "artifacts": "pr"}

      "id": "direct",
      "form": "brief",

  ]
}
```

- 上の例の `conflict_prediction` と `provider: worktree` は S2 で足す形である（S1 の検証では未知のキー・閉集合の外として `config_invalid` になる）。
- `interactive` を省略した操作は対話前提（`true`）として扱う。`counterpart` は `human | parent` の閉集合で、省略は `parent`。`child_may_decide` の省略は `false`。
- `form: brief` の操作は `invocation` を持たない。`form: plugin` の操作は `invocation` を必須とする。
- `form: cli` の接続ツールは `commands`（`start`・`status`・`resume`・`cancel` の引数の配列）と `contract_version`（`1` だけ）を必須とする（§クリティカル設計決定 3）。
- S3 で操作に `bundle`（`{"max_parallel": <N>}`。束ねて受け取れる場合だけ）を足す。`slot_owner`（`flywheel | connector`）を足すかは S2・S3 の分解のときに決める【決定 2026-10-01 オーナー M3H8】。操作の `parallel_safe` は足さない（§クリティカル設計決定 7）。
- `slots` は `provider` で形が分かれる（S2）。`clone` は `paths`（既存の作業用クローンの列挙。数がスロットの数）を、`worktree` は `base`（元のクローンのパス）と `count`（正の整数。スロットの数）を必須とする。どちらもワークスペースからの相対パスで、未知のキー・閉集合の外の `provider` は `config_invalid`。
- S2 で接続ツールに `conflict_prediction`（`{"command": [<引数の配列>], "schema": "harness.conflict-prediction/v1"}`）を足す。flywheel は `command` の後ろに `--max-budget-usd <額>` と Issue 番号を別々の要素として足し、元のクローン（`worktree`）または最初の作業用クローン（`clone`）を作業ディレクトリにして、シェルを介さずに起動する。`command[0]` は PATH で解決する。時間の上限は `timeout_sec.judgment` とする【仮定】。予測は作業ディレクトリのチェックアウトの手元の HEAD に対するもので、flywheel は fetch しないため古いことがある（出力の `head_sha` を周の結果に残す）【仮定】。`schema` は閉集合（今は `harness.conflict-prediction/v1` だけ）。読むのは汎用のフィールド（`issues[].issue`・`issues[].status`・`pairs[].issues`・`pairs[].status`・`pairs[].shared_files[]`〔`path`・`merge_friendly`・`ignored`〕・`pairs[].dependency.first`・`cost_usd`）だけで、接続ツール内部の手順・判断値は持ち込まない（§クリティカル設計決定 7）。

#### 現行の宣言からの写し方（`positions/<domain>.md` §5 → `connectors.json`）

| 現行の項目 | 写し先 |
|---|---|
| 開発フロー（接続ツール）: `claude-harness`（`/define-feature` → `/create-ticket` → `/impl`・`/para-impl` → `/pr-review-respond` → `/pr-merge`） | `connectors[].form: plugin` と、スキルごとの `operations[]`（`invocation` にスキルの呼び出し）。`/pr-merge` は既定ブランチへのマージ（`release` の実行）を含むため、M3 では操作として宣言しない |
| ハーネス自身の repo は harness のスキルを使わず直接ブリーフで委譲する | そのリポジトリの `repos[].connector` を `form: brief` の接続ツールにする |
| 対話前提スキルの対話相手: `親`（`/define-feature`・`/create-adr`・`/create-ticket`） | それらの操作の `interactive: true`・`counterpart: parent` |
| 子に意思決定を委譲してよいスキル（単一 repo 完結に限る・列挙外は不可） | それらの操作の `child_may_decide: true`（列挙外は省略＝`false`） |
| 委譲の起動形（束ね）: flywheel・board は受け取れる（`--max-parallel`・`--serial`）。claude-harness・claude-flywheel は受け取れない | S3 の `operations[].bundle`（受け取れる操作だけ）。直列化（`--serial`）は、接続ツールの衝突の予測から core が作る直列化グループで表す（S2。§クリティカル設計決定 7）。衝突の予測の口は `connectors[].conflict_prediction` |

## flywheel#73（スロットの前倒し）の判断

2026-09-28 の判断（M3H6・M3P20）を、2026-10-01 のオーナーの決定（M3H8。flywheel#73 の 2026-09-29 のコメントの親の案を計画の承認で承認したもの）で改めた。設計書 §11・§17 も同じ PR で反映した。

- **論点 1（いつ入れるか）**: 旧 claude-flywheel へは入れない（保守モード）。M3 の中で `worktree` を S3 から **S2 へ前倒し**する。S2 で、`clone` と `worktree` のスロット・同じリポジトリの並列（衝突の予測による直列化グループ）を持つ【決定 2026-10-01 オーナー M3H8】。
- **論点 2（プロバイダの既定と最初の範囲）**: S2 は `clone` と `worktree`（リポジトリごとに宣言で選ぶ）、`container` は S4。S2 に入れる手当ては、払い出しの直列化・外側からの git での `GIT_DIR`／`GIT_WORK_TREE` の明示・割り当て前の `.git` のポインタの検査。ビルド成果物・`node_modules`・ポートの衝突は S2 では手当てせず、宣言（`clone` にする・`count` を 1 にする）で避ける（§実行スロット「プロバイダ `worktree`」）【決定 2026-10-01 オーナー M3H8】。
- **論点 3（接続ツール側の worktree との二重化）**: スロットは flywheel が払い出し、課題ごとに接続ツールへ作業ツリーを渡す（claude-harness の `harness run ticket` は渡された作業ツリーを `provided` として受け、消さない）。`slot_owner: connector` の要否は S2・S3 の分解のときに決める。束ねた委譲（`bundle`・S3）の扱いもそのときに合わせて決める【決定 2026-10-01 オーナー M3H8】。
- **論点 4（同じリポジトリの並列での衝突の判定）**: 委譲の段の実行計画で接続ツールの衝突の予測の口（`harness predict-conflicts`・claude-harness#288）を問い、core が組ごとの直列化グループを作る。決定は flywheel、予測は接続ツール。予測が無いものは直列（§クリティカル設計決定 7）【決定 2026-10-01 オーナー M3H8。M3P20 を置き換える】。
- **論点 5（対話前提の委譲を並列にしたときの人間の窓口）**: **S2** で扱う。S2 の子の問いはすべて課題ごとの保留（人間対応待ち）になり、戻った順に `status` の `needs_human` に並ぶ（並列でも宛先は課題ごとの `session_id` で混線しない）。親として答える問いの振り分け（J4）は **S3**。複数の課題の問いをまとめて示す仕組みは M4 の UI で扱う【決定 2026-10-01 オーナー M3H8】。
- **論点 6（回答待ちで空いたスロット）**: 回答を待つ間はスロットを保持せず、別の課題に使ってよい。再開は同じリポジトリの空いたスロットでブランチ名から続ける（§保留と再開）【決定 2026-09-28 親 M3P16】。`worktree` のスロットでも同じ。
- **論点 7（予算・trust）**: 予算は **S2** で扱う。同時に起動した委譲は、それぞれの上限額を予約額として周の上限に数え、衝突の予測の呼び出しも周の上限の評価を受ける（§予算ガード）。新しいパス（worktree）ごとの Claude Code の trust の承認は **S2 の分解のときに決める**（`claude -p` を新しいパスで起動したときに trust の承認が要るかを実測してから決める。スロットのパスを使い回すので、要るとしても払い出し 1 回につき 1 度＝§実行スロット）【決定 2026-10-01 オーナー M3H8】。

### M1・M2 の仕様との関係（仕様への指摘。M1・M2 の仕様書は変えていない）

- **M1 の経路の閉集合を広げる**: 経路 `invoker` を足す（M3P11）。本人確認つきの組み合わせには登録しない。M1 §クリティカル設計決定 1 の経路の登録簿の拡張にあたる。

- **M1 の「本人確認のない操作の actor の検証は M3 で invoker が actor を設定する」**（M1 §やらないこと）: 本仕様は actor を起動した OS のログインユーザー名のままとし、経路 `invoker` と `run_id` で区別する（M3P11）。
