# core の見直し 区切り S4d（画面）— 対話の欄

## 概要

`docs/features/core-redesign.md` の区切り S4d（画面）の仕様。S4d は、S4a（長く走るサイクル）と並べて進めるので、その間だけ別の文書に書き、main に入れた後に `core-redesign.md` へ畳む（S3d と同じ進め方。オーナーの決定 2026-11-22）。

S4d を、2 つに分ける。

- **S4d-1 対話の欄**（この文書のいまの実装対象）: 画面の右に、オーケストレーターとの対話の欄を置く。欄に書いた文を、サーバが起動する実行エンジンが受け、flywheel のコマンドで状況を読み、オーナーの指示を記録する。
- **S4d-2 残り**: 画面のボタンで受ける操作（選ぶだけの回答・取り込み・サイクルを止める・フォローアップの操作）、サイクルの画面の作り替え、意思決定の記録とスーパーバイザーの手の表示、オーケストレーターからの知らせ。S4a・S4b・S4c の値が入ってから、この文書に書き足す。

## 背景・目的

- いま、オーナーが文で伝える承認・回答・相談は、ターミナルの対話のセッションでしか受けられない。画面は、ボタンで受ける 3 つの操作（計画の承認・反映を保留にした完了の承認・サイクルを回す）だけを持つ。
- UX の決定（`docs/features/core-redesign/ux.md` の決定 6・11・19・27・28）は、全画面の右に対話の欄を置き、問いへの回答と相談の基本の口にすると決めている。
- 作り方は、検討の Issue（flywheel#787）のオーナーの方針（2026-11-18・2026-11-22）のとおり、実行エンジンの SDK を使わず、サーバが実行エンジンのコマンド（`claude -p`。出力は `stream-json`）を起動し、Go から直接読む。

## ユーザーストーリー

オーナーとして、画面を見ながら、その場で「この計画を承認します」「この問いは推奨で」「main へ入れてよいです」と文で伝えたい。見ている課題のことを、名指しせずに相談したい。ターミナルを開かなくても、承認と回答が記録されてほしい。

## 機能要件

### 欄の置き方

- [ ] 画面の共通の枠の右に、選んだエージェントの対話の欄を置く（枠を使う、いまある画面のすべてに出る。サイクルの画面の作り替えは S4d-2）。
- [ ] 欄は、たためる。たたんだ状態は、画面を移っても保つ。
- [ ] 欄の上に、「いま見ているもの」（開いている課題か、タスクの題名）を出す。課題もタスクも開いていない画面では、出さない。
- [ ] 課題の詳細の「この課題について相談する」を押すと、欄が開き、入力の場所へ移る。
- [ ] 欄には、いまの会話のやりとり（オーナーの発言と、オーケストレーターの返事）を、古い順に出す。
- [ ] オーケストレーターの返事は、Markdown として整えて出す（S2c の部品を使う）。
- [ ] 画面を読み込み直しても、いまの会話のやりとりが出る（進行中の返事の、それまでに出た分を含む）。

### 文を送る・返事を受ける

- [ ] 欄に文を書いて送ると、オーナーの発言として記録し、サーバが実行エンジンを起動して、返事を求める。
- [ ] 送るとき、画面は「いま見ているもの」の識別（課題と、開いていればタスク）を一緒に渡す。題名は、サーバが core から引く（画面が渡した文字は使わない）。
- [ ] サーバは、「いま見ているもの」の識別と題名を、実行エンジンへの入力に添え、発言の行にも残す（題名は、送ったときの写し）。
- [ ] 返事は、実行エンジンが 1 つの発言を出し終えるごとに、ストアの返事の行へ足す。画面は、いまある変化の知らせ（ストアの変化の SSE）を受けて読み直し、出来た分を出す（1 文字ずつでなくてよい。新しい SSE の口は作らない）。
- [ ] 返事を待っている間、欄に、待っている旨を出す。
- [ ] 返事を待っている間は、次の文を送れない（送る操作を受けず、その旨を返す）。
- [ ] 返事を待っている間、「止める」を押せる。押すと、実行エンジンを止め、その返事を「止めた」として記録する。それまでに出た分は残す。
- [ ] オーケストレーターが実行した flywheel のコマンドを、返事の下に、畳んだ一覧で出す（コマンドの行と、成否）。
- [ ] 空の文は、送れない。

### 会話

- [ ] 会話は、エージェントごとに 1 本を続ける（ストアはエージェントごとにあるので、ストアの中で、開いている会話は高々 1 つ）。2 通目からは、実行エンジンが、同じ会話の前のやりとりを覚えている。
- [ ] 「新しい会話」を押すと、いまの会話を閉じ、次の文から、新しい会話を始める（前のやりとりを覚えていない）。
- [ ] 閉じた会話のやりとりは、ストアに残す。閉じた会話の一覧と、開き直す操作は、作らない。
- [ ] 実行エンジンの側の会話が続けられない（実行エンジンが、会話の続きを見つけられない）ときは、その返事を「会話を続けられなかった」として記録し、会話を閉じる。欄に、新しい会話でもう一度送る旨を出す（自動では送り直さない）。

### オーケストレーターに許すこと

- [ ] 欄の実行エンジンに許す道具は、ファイルの読み取り・検索と、flywheel のコマンドの実行だけにする。ファイルの編集と、flywheel 以外のシェルのコマンドは、許さない（オーナーの決定 2026-11-22）。
- [ ] 実行エンジンは、エージェントのワークスペースを作業ディレクトリにして起動する。`flywheel` の名前で、サーバと同じバイナリが動くようにする（環境の `PATH` の先頭に、サーバのバイナリの場所を入れる）。
- [ ] サーバは、欄の実行エンジンの環境に、欄から起動された印を入れる。印は、環境変数 `FLYWHEEL_CHAT_SESSION`（会話の識別）と `FLYWHEEL_CHAT_MESSAGE`（いま答えているオーナーの発言の識別）。名前は、core の定数に 1 か所で持つ。
- [ ] flywheel のコマンドは、この印があるとき、下の「欄から受けるコマンドの一覧」のコマンドだけを受け、ほかは断る。
- [ ] 1 回の返事には、ターン数の上限と、時間の上限を置く。宣言（`.flywheel/agent.json`）の `chat_max_turns`（既定 30）と `chat_timeout_sec`（既定 600）で決める。
- [ ] 上限に当たった返事は、「上限で止まった」として記録し、欄にその旨を出す。

欄から受けるコマンドの一覧（印があるとき）。

| コマンド | 分け | 印の検査 | 本人確認を通る操作か（通るものは、経路 `chat` で記録する） |
|---|---|---|---|
| `status`・`show`・`list`・`log`・`runs`・`metrics`・`followup list`・`version` | 読む | かけない | 通らない |
| `cycle status`（S4a が足す） | 読む | かけない | 通らない |
| `approve`（計画・完了・不可逆操作） | 記録する | かける | 通る |
| `reject`（計画・完了・不可逆操作） | 記録する | かける | 通る |
| `answer`（保留への回答・計画の問いへの回答。`--replan` を含む） | 記録する | かける | 通る |
| `withdraw` | 記録する | かける | 通る |
| `budget` | 記録する | かける | 通る |
| `followup drop`・`followup promote` | 記録する | かける | 通る |
| `followup done` | 記録する | かける | 通らない（いまと同じ。経路は記録しない） |
| `create` | 記録する | かける | 通らない（同上） |
| `ingest <指定>...`（取り込み元を 1 つ以上指定した形だけ。引数の無い形は断る） | 記録する | かける | 通らない（同上） |
| `cycle --detach`・`cycle stop`（S4a が足す） | サイクル | かける | 通らない |

- [ ] 「印の検査」は、次の 3 つを確かめ、1 つでも満たさなければ、コマンドを断る。印の会話が開いている。印の発言が、その会話の最後のオーナーの発言である。その発言への返事が進行中である。
- [ ] 1 つの発言への返事の中で、記録するコマンドを、いくつ実行してもよい（「承認して、予算も上げて」に応える）。
- [ ] 一覧に無いコマンド（`serve`・`export`・`import`・`--detach` の無い `cycle`・`run` などの個別の操作・`op add`・`op exec`・`edit`・`bind` など）は、印があるとき、断る。

### 欄から受ける承認・回答

- [ ] 本人確認の登録簿に、経路「対話の欄」（`chat`）と、本人確認の方式「対話で受けた」（`relayed`）の組を足す。この組は、すべての操作を受ける。ターミナルの対話で受けた記録（経路 `cli`）と、見分けられる。
- [ ] 印があるとき、flywheel のコマンドは、経路を `chat`・方式を `relayed` として core へ渡す（`--relayed`・`--session`・`--quote` は要らない。付いていても、値は使わない）。経路と方式を決める所は、CLI の中の 1 か所にする。
- [ ] 記録の「発言」（`relay_quote`）には、印の発言の文面を、core がストアから引いて入れる。
- [ ] 記録の「会話の識別」（`relay_session`）には、印の会話の識別を、core が入れる。
- [ ] 欄から承認できる不可逆操作の種類を、宣言の `chat_approvable_operations` で決める。既定は、反映（`release`）だけ。
- [ ] 経路 `chat` の、不可逆操作の承認（`approve <操作>`）は、その操作の種類が宣言にあるときだけ受ける。無ければ断り、ターミナルで行う旨を返す。判定は、core が行う。
- [ ] 経路 `chat` の、完了の承認のうち、反映の承認を含む形（`approve_completion`。反映を保留にしない）は、反映（`release`）が宣言にあるときだけ受ける。反映を保留にした完了の承認（`approve_completion_hold`）は、宣言によらず受ける。
- [ ] 不可逆操作の差し戻しは、種類によらず受ける。
- [ ] `chat_approvable_operations` に、決まった種類（`release`・`delete`・`external_send`・`other`）以外の値があれば、宣言の読み込みを誤りにする。

### オーケストレーターの振る舞い（指示文）

- [ ] 欄の実行エンジンに渡す指示文を、`internal/invoker/prompts/chat.md` に足し、指示文の一覧（分量の上限の検査と、語の検査の対象）に登録する。
- [ ] 指示文は、実行エンジンの追加の指示として渡す。オーナーの発言と「いま見ているもの」は、入力として渡す。
- [ ] 指示文は、次を求める。オーナーの指示が無い承認を記録しない（推奨を示しただけ・質問されただけでは記録しない）。
- [ ] 指示文は、承認を記録する前に、何が承認されるか（反映先へ入るものを含む）の要約を示すことを求める。
- [ ] 指示文は、記録した後に、何を記録したかを伝えることを求める。
- [ ] 指示文は、用語集の語を使い、内部の ID を単独で出さないことを求める。
- [ ] 指示文は、範囲が変わる回答には、計画の作り直し（`answer --replan`）を使うことを求める。
- [ ] 指示文は、調べものや直しを頼まれたときは、課題にして委譲先に任せる（`create`）か、ターミナルの対話で行うよう案内することを求める。
- [ ] 指示文に、開発に固有の語と、実行エンジンに固有の語を書かない（指示文の語の検査を通す）。

### 費用

- [ ] 返事ごとに、実行エンジンが返した費用を記録する（実行エンジンが費用を返す前に止まった返事は、0 のまま）。
- [ ] 欄に、いまの会話の費用の合計を出す。
- [ ] 欄の費用は、サイクルの費用の上限に数えない。欄には、費用の上限を置かない（オーナーの決定 2026-11-22）。

### うまくいかないとき

- [ ] 実行エンジンが見つからないときは、文を送る操作を誤りにし、欄に、実行エンジンが要る旨を出す。オーナーの発言は記録しない。
- [ ] 実行エンジンが途中で失敗したときは、その返事を「失敗」として記録し、欄に、失敗した旨と、もう一度送れる旨を出す。それまでに出た分は残す。
- [ ] 利用上限に当たったときは、その返事を「利用上限」として記録し、欄にその旨を出す。
- [ ] サーバを止めるとき、進行中の返事の実行エンジンを止める。次に起動したとき、進行中のまま残った返事は「止めた」にする。

返事の終わり方（`state`）と、欄に出す文。

| `state` | 意味 | 欄に出す文 |
|---|---|---|
| `replying` | 返事が進行中 | 「返事を待っています…」 |
| `done` | 終わった | （出さない） |
| `stopped` | 止めた | 「止めました。」 |
| `limit` | ターン数か時間の上限 | 「上限に達したので、ここで止まりました。続きは、もう一度送ってください。」 |
| `rate_limited` | 利用上限 | 「利用上限に達しました。時間を置いて、もう一度送ってください。」 |
| `session_lost` | 会話を続けられなかった | 「前の会話を続けられませんでした。新しい会話として、もう一度送ってください。」 |
| `failed` | そのほかの失敗 | 「返事を作れませんでした。もう一度送れます。」 |

## 技術的な制約・方針

- 変更対象:
  - `internal/core`: 会話と発言の記録（表 2 つ・マイグレーション 1 本）と、その公開の API。経路 `chat` の登録と検査。対話の実行のインターフェース（判断点の呼び出しのインターフェースと同じく、core に置く）。宣言の項目。印の環境変数の名前。
  - `internal/invoker`: 対話の実行（実行エンジンの起動・`stream-json` の読み取り・止める・費用の取り出し）と、指示文 1 本。
  - `internal/cli`: 印があるときの、コマンドの一覧の検査と、経路の切り替え。`serve` が、invoker の対話の実行を組み立てて、サーバへ渡す。
  - `internal/server`: 対話の口（下の「画面・API設計」）。`internal/invoker` を import しない決まりのまま、対話の実行は、core のインターフェースで受け取る。
  - `internal/view`・`web/src`: 型と、欄の部品。
- core の公開の API（名前は実装で決めてよい。役割はこのとおり）: いまの会話を読む／オーナーの発言を記録して返事の行を作る（会話が無ければ作る。返事が進行中なら断る）／返事の行へ、発言の 1 つ分を足す／実行したコマンドを足す／返事を終える（終わり方・費用）／会話を閉じる／進行中のまま残った返事を「止めた」にする。
- ストアが正。サーバがストアの外に持つのは、進行中の返事の実行エンジンのプロセス（止めるため）だけ。返事の進みは、ストアへ書き、いまある変化の知らせで画面へ届く。
- 実行エンジンに固有の形（コマンドの引数・`stream-json` の形）は、`internal/invoker` の中に閉じる。core とサーバは、「発言を渡すと、返事の発言・実行したコマンド・費用・終わり方が返る」形だけを知る。
- 1 回の返事ごとに、実行エンジンのプロセスを 1 つ起動する（常駐させない）。会話の識別（UUID）は、判断点と同じく、flywheel が決めて渡す（1 通目は新しい会話として、2 通目からは続きとして）。
- 起動の引数は、判断点の引数（`internal/invoker/args.go`）にならう。違いは、出力を `stream-json` にすること、許す道具に flywheel のコマンドの実行（`Bash(flywheel:*)`）を足し、禁じる道具から `Bash` を外すこと、ターン数の上限。許可を尋ねる動きは、判断点と同じ指定（`--permission-mode default`。尋ねる相手がいないので、許していない道具は断られる）。
- `stream-json` から読むもの: オーケストレーターの発言の文、道具の実行（コマンドの行）とその結果（成否）、終わりの行（終わり方・費用）。**形は、実物の出力を見て固める**: 最初の Issue で、実物の実行エンジンの出力を 1 回取り、その写しを試験のデータ（`testdata`）に置く。テスト用の実行エンジンは、その写しの形で、場面ごとの出力（発言 2 つ・コマンドの実行・費用・ターン数の上限・会話を続けられない・利用上限・0 でない終了）を出す。
- 道具の制限は、2 重にする。実行エンジンの許可の設定と、flywheel のコマンドの側の一覧の検査。ただし、flywheel 以外のシェルのコマンド（`flywheel status; ほかのコマンド` のような連結を含む）を断るのは、実行エンジンの許可の設定だけが頼りになる。実物で断られることを、main へ入れる前に確かめる（下の「要人間判定」）。断られないと分かったときは、入れずに、オーナーへ上げる。
- 欄の実行エンジンは、サイクルの排他を取らない。欄から実行した flywheel のコマンドは、それぞれの決まりで排他を取る。
- S4a と並べて進める。S4a のコマンド（`cycle status`・`cycle stop`・`--detach`）と、承認がサイクルを始める動きは、S4a が持つ。この区切りは、一覧に名前を入れるだけで、動きを作らない。ストアの版は、S4a（版 31）の次の 32。この区切りの統合ブランチは、S4a が main に入った後に main を取り込み、版の番号を確かめてから、main へ入れる（それまでは、統合ブランチの中で、いまの版の次の番号を使う）。

## 画面・API設計

- `ux.md` と試作: `docs/features/core-redesign/ux.md`・`docs/features/core-redesign/prototype/web/`（`w3-task-chat.html`・`w5-completion-chat.html` ほか）・`prototype/chat/scenes.md`。
- 対話の口（エージェントごと。書き込みは、いまの画面の口と同じ守り〔127.0.0.1・Host と Origin の検査・CSRF〕）:
  - `GET …/chat`: いまの会話。`session_id`（無ければ `null`）・`started_at`・`cost_usd`（合計）・`state`（`idle`・`replying`）・`messages[]`。
  - `messages[]` の要素: `id`・`role`（`owner`・`orchestrator`）・`body`・`state`（上の表の 7 つ。`owner` の行は `done`）・`cost_usd`・`created_at`・`viewing`（`challenge_id`・`task_id`・`title`。無ければ `null`）・`activity[]`（`command`・`ok`）。
  - `POST …/chat/messages`: 文を送る。入力は `text`・`viewing`（`challenge_id`・`task_id`。無ければ省く）。受けたら、発言の `id` を返す。返事が進行中なら 409。
  - `POST …/chat/stop`: 進行中の返事を止める。
  - `POST …/chat/new`: いまの会話を閉じる。
- 返事の進みを流す、新しい口は作らない。画面は、いまある変化の知らせを受けて、`GET …/chat` を読み直す。
- 費用の表示は、`$0.42` の形（小数 2 桁）。

## クリティカル設計決定

### 承認の真正性: 対話の欄から、反映の承認を受ける（UX の決定 27 を改める）

- **採用案**: 対話の欄を、新しい経路 `chat` として登録する。欄から、承認・差し戻し・回答・取り下げ・予算の増額・フォローアップの操作を受ける。不可逆操作の承認は、宣言 `chat_approvable_operations` にある種類だけを受ける。既定は、反映（`release`）だけ。記録の「発言」には、オーナーが欄に書いた文面そのものを、core が入れる。
- **理由**: オーナーの決定（2026-11-22）。反映先へ入れること（main へのマージなど）は、対話から行えるようにする。本番へのデプロイに当たる操作（外部への送信など）は、人が直接行うのを既定にし、設定で変えられるようにする。
- **受け入れた危険**: サーバは、文の送り手を見分けない（設計書 §9）。同じマシンのプロセス（委譲の子を含む）は、画面の HTML から CSRF の値を取って、欄へ文を送れる。その文が「承認します」であれば、オーケストレーターは、承認を記録しうる。この危険を、次の 3 つで小さくしたうえで、受け入れる。(1) 欄から起こせることを、flywheel の決まったコマンドだけにする（ファイルの編集・任意のシェルは無い）。(2) 欄から承認できる不可逆操作の種類を、宣言で絞る。(3) 記録に、欄に書かれた文面そのものが残り、経路 `chat` として、後から見分けられる。送り手を見分ける仕組み（パスキーなど。決定 D18 で外した）は、足さない。
- **代替案**: 欄からは、反映を保留にした完了の承認までにし、反映の承認はターミナルだけで受ける（いまの画面のボタンと同じ範囲）。オーナーの決定で採らない。
- **影響範囲**: 本人確認の登録簿（`verification.go`）に、(`chat`, `relayed`) の行を足す（すべての操作を受ける）。不可逆操作の種類の絞りと、反映の承認を含む完了の承認の絞りは、登録簿の外の、core の検査で行う（core は、経路が `chat` のとき、宣言の一覧を読んで判定する）。設計書 §9。UX の決定 27 は、「ターミナルの対話と同じ扱い」から、「経路 `chat`。不可逆操作は、宣言で選んだ種類だけ」に改める。

### 承認の真正性: 発言の文面を、core がストアから引く

- **採用案**: 欄から起動された flywheel のコマンドは、環境の印（会話の識別・発言の識別）を core へ渡す。core は、印の検査（会話が開いている・最後のオーナーの発言である・返事が進行中である）を通し、発言の文面を、記録の「発言」に入れる。
- **理由**: ターミナルの対話の記録（`--relayed`）は、発言の要旨を、Claude が書く。欄では、発言そのものがストアにあるので、書き写しを挟まずに残せる。古い発言や、ほかの会話の発言を根拠にした記録も、断れる。
- **残る危うさ**: 印は環境変数なので、同じマシンのプロセスは、自分で付けられる。ただし、印を付けると、受けるコマンドは狭くなり（一覧だけ）、印の検査も通す必要がある（進行中の返事がある間だけ）。印の無い `--relayed`（要旨を自分で書ける）より、広くはならない。サーバが落ちて、進行中の返事の行が残っている間は、印の検査が通りうる（次の起動で「止めた」に直す）。
- **影響範囲**: `internal/core` の承認の記録。記録の表は変えない（`channel`・`verification`・`relay_session`・`relay_quote` の列は、いまあるものを使う）。

### DB スキーマ: 会話と発言の表（版 32）

- **採用案**: マイグレーション 1 本で、表を 2 つ足す。
  - `chat_session`: `id`・`engine_session`（flywheel が決めた会話の識別。UUID）・`engine_started`（実行エンジンが、この識別の会話を作り終えたか。既定 0）・`started_at`・`closed_at`（NULL 可）。開いている会話（`closed_at` が NULL）は、高々 1 つ（部分一意索引）。
  - `chat_message`: `id`・`session_id`・`role`（`owner`・`orchestrator`）・`body`・`state`・`cost_usd`（既定 0）・`viewing_challenge_id`・`viewing_task_id`・`viewing_title`（どれも NULL 可）・`activity`（JSON の配列。既定は空）・`created_at`・`ended_at`（NULL 可）。
- **理由**: 読み込み直しても、やりとりが出ること・費用を記録すること・承認の記録が発言を引けることに、ストアの行が要る。実行エンジンの側の記録（会話のファイル）は、実行エンジンに固有の形なので、頼らない。ストアはエージェントごとにあるので、エージェントの列は持たない。
- **代替案**: 実行エンジンの会話のファイルを読む。上の理由で採らない。
- **影響範囲**: ストアの版が 32 になる。書き出しと読み込み（`export`・`import`）に、表が 2 つ増える（ほかの表と同じに、行をそのまま書き出す）。

### 外部システム連携: 実行エンジンを、サーバから起動する

- **採用案**: 対話の実行のインターフェースを core に置き、実装を `internal/invoker` に置く。`serve` が組み立てて、サーバへ渡す。1 回の返事ごとに、プロセスを 1 つ起動する。道具は、読み取り・検索・flywheel のコマンドだけを許し、許可を尋ねる動きは、断られる形で起動する。
- **理由**: 判断点と同じ置き場にすれば、実行エンジンに固有の形が 1 か所に閉じる（flywheel#787 の「core に持ち込まない」）。プロセスを常駐させると、止め方・残ったプロセスの片付け・サーバの再起動の扱いが増える。
- **代替案**: 実行エンジンの SDK を、別の実行環境（TypeScript か Python）で動かす。オーナーの方針（2026-11-18）で採らない。画面にターミナルを埋め込む。道具を絞れないので採らない。
- **影響範囲**: `internal/core`（インターフェース）・`internal/invoker`・`internal/cli`（`serve`）・`internal/server`。

### 欄から起こせることを、flywheel のコマンドの側でも絞る

- **採用案**: flywheel のコマンドは、欄から起動された印があるとき、決まった一覧のコマンドだけを受ける。検査は、委譲の子の印（`FLYWHEEL_DELEGATED_RUN`）の検査と同じ層（コマンドを選ぶ所）に置き、委譲の子の印の検査を先に行う。
- **理由**: 実行エンジンの許可の設定だけに頼ると、設定の書き方の誤りや、実行エンジンの版による違いで、範囲が広がりうる。flywheel の側の検査は、実行エンジンによらない。
- **影響範囲**: `internal/cli`。委譲の子からのコマンドを断る決まりは、そのまま（子が欄の印を足しても、断られる）。

### 道具の範囲は、絞って入れ、Tom で使ってから見直す

- **採用案**: 欄の道具は、読み取り・検索・flywheel のコマンドだけにして入れる。断られたコマンドを記録に残し、Tom で使った実績を見て、範囲を広げるか（宣言で道具を足せる形など）を、S4d-2 で決める。
- **理由**: オーナーの決定と懸念（2026-11-22）。絞ると、「その場で調べる・直す」は欄では出来ず、課題にして委譲先に任せるか、ターミナルの対話で行うことになる。開発の速さへの影響は、使ってみないと分からない。絞る所は 2 か所（実行エンジンの許可の設定と、コマンドの一覧）だけなので、後から広げる直しは小さい。
- **代替案**: 最初から、すべて許す。欄へ文を送れる者が、マシンの上で何でも出来ることになるので、守りの設計が要り、区切りが大きくなる。

## 受入基準

特に断らない限り、テスト用の実行エンジン（実物の出力の写しの形で、場面ごとの `stream-json` を出すコマンド）で確かめる。「印がある環境」は、`FLYWHEEL_CHAT_SESSION` と `FLYWHEEL_CHAT_MESSAGE` に、開いている会話と、その最後のオーナーの発言（返事が進行中）を入れた環境。

### 欄の置き方

- [ ] 共通の枠を使う画面のルートのそれぞれ（表にして、全部を回す）で、対話の欄の要素が描かれる。
- [ ] 欄をたたんだ状態で見えるのは、開く操作だけになる。
- [ ] 欄をたたんで別の画面へ移ると、たたんだままになっている。
- [ ] 課題の詳細を開いているとき、欄の上に、その課題の題名が「いま見ているもの」として出る。
- [ ] タスクの詳細を開いているとき、欄の上に、そのタスクの題名が出る。
- [ ] 課題もタスクも開いていない画面では、「いま見ているもの」が出ない。
- [ ] 課題の詳細の「この課題について相談する」を押すと、たたんでいた欄が開く。
- [ ] そのとき、入力の場所にフォーカスが移る。
- [ ] やりとりが 0 件の会話では、欄に「オーケストレーターに、相談や指示を書けます。」が出る。

### 文を送る・返事を受ける

- [ ] 文を送ると、`chat_message` に、`role` が `owner` の行が 1 つ出来る。
- [ ] 文を送ると、実行エンジンが、ちょうど 1 回起動される。
- [ ] 実行エンジンへの入力に、送った文の本文が入っている。
- [ ] 課題の識別を付けて文を送ると、発言の行の `viewing_challenge_id` が、その課題になる。
- [ ] そのとき、発言の行の `viewing_title` が、core から引いた課題の題名になる（入力に別の題名の文字を付けても、変わらない）。
- [ ] そのとき、実行エンジンへの入力に、その課題の題名が入っている。
- [ ] そのとき、実行エンジンへの入力に、その課題の識別が入っている。
- [ ] タスクの識別を付けて文を送ると、発言の行の `viewing_task_id` が、そのタスクになる。
- [ ] そのとき、実行エンジンへの入力に、そのタスクの題名が入っている。
- [ ] 存在しない課題の識別を付けた `POST …/chat/messages` は、400 を返し、行を作らない。
- [ ] 実行エンジンが発言を 2 つ続けて出す場面で、1 つ目を出し終えた時点で、返事の行の `body` に 1 つ目が入っている（2 つ目を待たない）。
- [ ] 返事が終わると、`role` が `orchestrator` の行の `state` が `done` になる。
- [ ] 返事の本文の `# 見出し` が、見出しの要素として描かれる。
- [ ] 返事の本文の `- 項目` が、箇条書きの要素として描かれる。
- [ ] 返事の行の `state` が `replying` のとき、欄に「返事を待っています…」が出る。
- [ ] 返事が進行中のとき、`POST …/chat/messages` は 409 を返す。
- [ ] その 409 の後も、`chat_message` の行は増えていない。
- [ ] 返事が進行中のとき、画面の送るボタンは押せない。
- [ ] 返事が進行中に `POST …/chat/stop` を呼ぶと、実行エンジンのプロセスが終わる。
- [ ] そのとき、返事の行の `state` が `stopped` になる。
- [ ] そのとき、止める前に出し終えていた発言が、返事の行の `body` に残っている。
- [ ] 返事が進行中でないときの `POST …/chat/stop` は、何も変えずに成功を返す。
- [ ] 実行エンジンが flywheel のコマンドを 1 つ実行して成功する場面で、返事の行の `activity` に、そのコマンドの行と `ok` が真の要素が 1 件入る。
- [ ] 実行エンジンが実行したコマンドが断られた場面で、`activity` に、`ok` が偽の要素が入る。
- [ ] 返事の下の「実行したコマンド」は、畳んで出る。
- [ ] 開くと、コマンドの行が見える。
- [ ] 空白だけの文の `POST …/chat/messages` は、400 を返し、行を作らない。
- [ ] CSRF の値が無い `POST …/chat/messages` は、断られる。
- [ ] CSRF の値が無い `POST …/chat/stop` は、断られる。
- [ ] CSRF の値が無い `POST …/chat/new` は、断られる。
- [ ] 画面を読み込み直すと、いまの会話の発言と返事が、古い順に出る。

### 会話

- [ ] 会話が無いときに文を送ると、`chat_session` の行が 1 つ出来、`engine_session` に UUID が入る。
- [ ] 1 通目では、実行エンジンを、新しい会話の指定（その UUID）で起動する。
- [ ] 1 通目の返事が `done` で終わると、`engine_started` が 1 になる。
- [ ] 2 通目では、実行エンジンを、続きの指定（同じ UUID）で起動する。
- [ ] 1 通目の返事が `failed` で終わり、`engine_started` が 0 のままのとき、次の文は、新しい会話の指定で起動する。
- [ ] `POST …/chat/new` を呼ぶと、いまの `chat_session` の `closed_at` が入る。
- [ ] その後の 1 通目では、新しい `chat_session` の行が出来る。
- [ ] その後の `GET …/chat` の `messages` は、空の配列になる。
- [ ] その後も、閉じた会話の `chat_message` の行は残っている。
- [ ] 返事が進行中の `POST …/chat/new` は、409 を返す。
- [ ] 実行エンジンが、会話の続きを見つけられない場面で、返事の行の `state` が `session_lost` になる。
- [ ] そのとき、`chat_session` の `closed_at` が入る。
- [ ] `state` が `session_lost` の返事には、欄に「前の会話を続けられませんでした。新しい会話として、もう一度送ってください。」が出る。

### オーケストレーターに許すこと
