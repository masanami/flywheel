# core の見直し 区切り S4d（画面）— 対話の欄と、画面の残り

## 概要

`docs/features/core-redesign.md` の区切り S4d（画面）の仕様。S4d は、S4a（長く走るサイクル）と並べて進めるので、その間だけ別の文書に書き、main に入れた後に `core-redesign.md` へ畳む（S3d と同じ進め方。オーナーの決定 2026-11-22）。

S4d を、2 つに分ける。

- **S4d-1 対話の欄**（出荷済み）: 画面の右に、オーケストレーターとの対話の欄を置く。欄に書いた文を、サーバが起動する実行エンジンが受け、flywheel のコマンドで状況を読み、オーナーの指示を記録する。
- **S4d-2 残り**（この文書のいまの実装対象。要件は「画面の残り（S4d-2）」の節、受入基準は括弧なしの「受入基準」の節）: 画面のボタンで受ける操作（選ぶだけの回答・取り込み・サイクルを止める・フォローアップの操作）、サイクルの画面の作り替え、意思決定の記録とスーパーバイザーの手の表示、オーケストレーターからの知らせ。S4a・S4b・S4c の値が入ってから、この文書に書き足す。

## 背景・目的

- いま、オーナーが文で伝える承認・回答・相談は、ターミナルの対話のセッションでしか受けられない。画面は、ボタンで受ける 3 つの操作（計画の承認・反映を保留にした完了の承認・サイクルを回す）だけを持つ。
- UX の決定（`docs/features/core-redesign/ux.md` の決定 6・11・19・27・28）は、全画面の右に対話の欄を置き、問いへの回答と相談の基本の口にすると決めている。
- 作り方は、検討の Issue（flywheel#787）のオーナーの方針（2026-11-18・2026-11-22）のとおり、実行エンジンの SDK を使わず、サーバが実行エンジンのコマンド（`claude -p`。出力は `stream-json`）を起動し、Go から直接読む。

## ユーザーストーリー

オーナーとして、画面を見ながら、その場で「この計画を承認します」「この問いは推奨で」「main へ入れてよいです」と文で伝えたい。見ている課題のことを、名指しせずに相談したい。ターミナルを開かなくても、承認と回答が記録されてほしい。

## 機能要件

### 欄の置き方

- [ ] 画面の共通の枠の右に、選んだエージェントの対話の欄を置く（枠を使う、いまある画面のすべてに出る。サイクルの画面の作り替えは S4d-2）。
- [ ] 欄は、たためる。たたんだ状態は、画面を移っても保つ。
- [ ] 欄の上に、「いま見ているもの」（開いている課題か、タスクの題名）を出す。課題もタスクも開いていない画面では、出さない。
- [ ] 課題の詳細の「この課題について相談する」を押すと、欄が開き、入力の場所へ移る。
- [ ] 欄には、いまの会話のやりとり（オーナーの発言と、オーケストレーターの返事）を、古い順に出す。
- [ ] オーケストレーターの返事は、Markdown として整えて出す（S2c の部品を使う）。
- [ ] 画面を読み込み直しても、いまの会話のやりとりが出る（進行中の返事の、それまでに出た分を含む）。

### 文を送る・返事を受ける

- [ ] 欄に文を書いて送ると、オーナーの発言として記録し、サーバが実行エンジンを起動して、返事を求める。
- [ ] 送るとき、画面は「いま見ているもの」の識別（課題と、開いていればタスク）を一緒に渡す。題名は、サーバが core から引く（画面が渡した文字は使わない）。引けない識別（存在しない課題・存在しないタスク・その課題に属さないタスク・課題の無いタスクだけ）が付いていたら、400 で断り、行を作らない。
- [ ] サーバは、「いま見ているもの」の識別と題名を、実行エンジンへの入力に添え、発言の行にも残す（題名は、送ったときの写し）。
- [ ] 返事は、実行エンジンが 1 つの発言を出し終えるごとに、ストアの返事の行へ足す。画面は、いまある変化の知らせ（ストアの変化の SSE）を受けて読み直し、出来た分を出す（1 文字ずつでなくてよい。新しい SSE の口は作らない）。
- [ ] 返事を待っている間、欄に、待っている旨を出す。
- [ ] 返事を待っている間は、次の文を送れない（送る操作を受けず、その旨を返す）。
- [ ] 返事を待っている間、「止める」を押せる。押すと、実行エンジンを止め、その返事を「止めた」として記録する。それまでに出た分は残す。
- [ ] オーケストレーターが実行した flywheel のコマンドを、返事の下に、畳んだ一覧で出す（コマンドの行と、成否）。
- [ ] 空の文は、送れない。

### 会話

- [ ] 会話は、エージェントごとに 1 本を続ける（ストアはエージェントごとにあるので、ストアの中で、開いている会話は高々 1 つ）。2 通目からは、実行エンジンが、同じ会話の前のやりとりを覚えている。
- [ ] 「新しい会話」を押すと、いまの会話を閉じ、次の文から、新しい会話を始める（前のやりとりを覚えていない）。返事が進行中のときは、受けない（409）。
- [ ] 閉じた会話のやりとりは、ストアに残す。閉じた会話の一覧と、開き直す操作は、作らない。
- [ ] 実行エンジンの側の会話が続けられない（実行エンジンが、会話の続きを見つけられない）ときは、その返事を「会話を続けられなかった」として記録し、会話を閉じる。欄に、新しい会話でもう一度送る旨を出す（自動では送り直さない）。

### オーケストレーターに許すこと

- [ ] 欄の実行エンジンに許す道具の範囲を、宣言の `chat_tools` で選ぶ。`restricted`（絞る。既定）か、`full`（すべて許す）。それ以外の値は、宣言の読み込みを誤りにする（オーナーの決定 2026-11-22。雑用を欄から任せられるように、すべて許す形も選べるようにする）。
- [ ] `restricted` のとき、許す道具は、ファイルの読み取り・検索と、flywheel のコマンドの実行にする。ファイルの編集と、書き込む・実行するシェルのコマンド（`flywheel status` の後ろに別のコマンドを連結した形も）は、許さない。読み取りだけのシェルのコマンド（`ls`・`which`・`head` など。実行エンジンが読み取りだけと見なして尋ねずに通すもの）は通る（読む・探す道具を許しているのと同じ範囲。オーナーの決定 2026-11-22）。起動の引数で、設定の出どころを空にし、利用者の設定の許可が加わらないようにする。
- [ ] `full` のとき、道具を絞らず、許可を尋ねる動きは、すべて許す形で起動する（ファイルの編集・任意のシェル・ウェブの読み取りを含む。ターミナルの対話のセッションで、すべて許したときと同じ範囲）。
- [ ] `full` のとき、flywheel のコマンドの一覧の検査は、かけない（印があっても、すべてのコマンドを受ける）。印の検査と、経路 `chat` での記録、不可逆操作の種類の絞りは、`full` でも同じにかける。
- [ ] 欄の上に、いまの道具の範囲（`full` のときは「すべての道具を許可しています」）を出す。
- [ ] 実行エンジンは、エージェントのワークスペースを作業ディレクトリにして起動する。`flywheel` の名前で、サーバと同じバイナリが動くようにする（返事ごとに、一時のディレクトリを作り、`flywheel` の名前で、サーバの実行ファイルへのシンボリックリンクを置き、そのディレクトリを環境の `PATH` の先頭に入れる。返事が終わったら消す）。
- [ ] サーバは、欄の実行エンジンの環境に、欄から起動された印を入れる。印は、環境変数 `FLYWHEEL_CHAT_SESSION`（会話の識別）と `FLYWHEEL_CHAT_MESSAGE`（いま答えているオーナーの発言の識別）。名前は、core の定数に 1 か所で持つ。
- [ ] サーバは、道具の範囲も、環境変数 `FLYWHEEL_CHAT_TOOLS`（`restricted`・`full`）で渡す。flywheel のコマンドは一覧の検査の可否をこの環境変数から読まず、ワークスペースの宣言（`chat_tools`）から読む（宣言が `restricted` なら、環境変数が `full` でも一覧の検査をかける）。
- [ ] flywheel のコマンドは、印があり、道具の範囲（宣言の `chat_tools`）が `restricted` のとき、下の「欄から受けるコマンドの一覧」のコマンドだけを受け、ほかは断る。
- [ ] 1 回の返事には、ターン数の上限と、時間の上限を置く。宣言（`.flywheel/agent.json`）の `chat_max_turns`（既定 30）と `chat_timeout_sec`（既定 600）で決める。
- [ ] 上限に当たった返事は、「上限で止まった」として記録し、欄にその旨を出す。

欄から受けるコマンドの一覧（印があり、道具の範囲が `restricted` のとき。「印の検査」と「本人確認を通る操作か」の列は、`full` でも同じ）。

| コマンド | 分け | 印の検査 | 本人確認を通る操作か（通るものは、経路 `chat` で記録する） |
|---|---|---|---|
| `status`・`show`・`list`・`log`・`runs`・`metrics`・`followup list`・`version`・`help` | 読む | かけない | 通らない |
| `cycle status`（S4a が足す） | 読む | かけない | 通らない |
| `approve`（計画・完了・不可逆操作） | 記録する | かける | 通る |
| `reject`（計画・完了・不可逆操作） | 記録する | かける | 通る |
| `answer`（保留への回答・計画の問いへの回答。`--replan` を含む） | 記録する | かける | 通る |
| `withdraw` | 記録する | かける | 通る |
| `budget` | 記録する | かける | 通る |
| `followup drop`・`followup promote` | 記録する | かける | 通る |
| `followup done` | 記録する | かける | 通らない（いまと同じ。経路は記録しない） |
| `create` | 記録する | かける | 通らない（同上） |
| `ingest <指定>...`（取り込み元を 1 つ以上指定した形だけ。引数の無い形は断る） | 記録する | かける | 通らない（同上） |
| `cycle --detach`・`cycle stop`（S4a が足す） | サイクル | かける | 通らない |

- [ ] 一覧との照合は、全体のフラグ（`--json`・`--workspace` など）を除いた後の、コマンドの名前（`followup`・`cycle` は、その次の語まで）で行う。
- [ ] 「印の検査」は、次の 3 つを確かめ、1 つでも満たさなければ、コマンドを断る。印の会話が開いている。印の発言が、その会話の最後のオーナーの発言である。その発言への返事が進行中である。
- [ ] 1 つの発言への返事の中で、記録するコマンドを、いくつ実行してもよい（「承認して、予算も上げて」に応える）。
- [ ] 一覧に無いコマンド（`serve`・`export`・`import`・`--detach` の無い `cycle`・`run` などの個別の操作・`op add`・`op exec`・`edit`・`bind` など）は、印があり、道具の範囲が `restricted` のとき、断る。

### 欄から受ける承認・回答

- [ ] 本人確認の登録簿に、経路「対話の欄」（`chat`）と、本人確認の方式「対話で受けた」（`relayed`）の組を足す。この組は、すべての操作を受ける。ターミナルの対話で受けた記録（経路 `cli`）と、見分けられる。
- [ ] 印があるとき、本人確認を通るコマンドは、経路を `chat`・方式を `relayed` として core へ渡す（本人確認を通らないコマンドは、印の検査だけをかけ、経路は渡さない。`--relayed`・`--session`・`--quote` は要らない。付いていても、値は使わない）。経路と方式を決める所は、CLI の中の 1 か所にする。
- [ ] 記録の「発言」（`relay_quote`）には、印の発言の文面を、core がストアから引いて入れる。
- [ ] 記録の「会話の識別」（`relay_session`）には、印の会話の識別を、core が入れる。
- [ ] 欄から承認できる不可逆操作の種類を、宣言の `chat_approvable_operations` で決める。既定は、反映（`release`）だけ。
- [ ] 経路 `chat` の、不可逆操作の承認（`approve <操作>`）は、その操作の種類が宣言にあるときだけ受ける。無ければ断り、ターミナルで行う旨を返す。判定は、core が行う。
- [ ] 経路 `chat` の、完了の承認のうち、反映の承認を含む形（`approve_completion`。反映を保留にしない）は、反映（`release`）が宣言にあるときだけ受ける。反映を保留にした完了の承認（`approve_completion_hold`）は、宣言によらず受ける。
- [ ] 不可逆操作の差し戻しは、種類によらず受ける。
- [ ] `chat_approvable_operations` に、決まった種類（`release`・`delete`・`external_send`・`other`）以外の値があれば、宣言の読み込みを誤りにする。

### オーケストレーターの振る舞い（指示文）

- [ ] 欄の実行エンジンに渡す指示文を、`internal/invoker/prompts/chat.md` に足し、指示文の一覧（分量の上限の検査と、語の検査の対象）に登録する。
- [ ] 指示文は、実行エンジンの追加の指示として渡す。オーナーの発言と「いま見ているもの」は、入力として渡す。
- [ ] 指示文は、次を求める。オーナーの指示が無い承認を記録しない（推奨を示しただけ・質問されただけでは記録しない）。
- [ ] 指示文は、承認を記録する前に、何が承認されるか（反映先へ入るものを含む）の要約を示すことを求める。
- [ ] 指示文は、記録した後に、何を記録したかを伝えることを求める。
- [ ] 指示文は、用語集の語を使い、内部の ID を単独で出さないことを求める。
- [ ] 指示文は、範囲が変わる回答には、計画の作り直し（`answer --replan`）を使うことを求める。
- [ ] 指示文は、調べものや直しを頼まれたとき、道具の範囲が `restricted` なら、課題にして委譲先に任せる（`create`）か、ターミナルの対話で行うよう案内することを求める。`full` なら、その場で行ってよいが、不可逆な操作（外への送信・削除・反映先へ入れること）の前には、オーナーに確かめることを求める。道具の範囲は、入力に添えて渡す。
- [ ] 指示文に、開発に固有の語と、実行エンジンに固有の語を書かない（指示文の語の検査を通す）。

### 費用

- [ ] 返事ごとに、実行エンジンが返した費用を記録する（実行エンジンが費用を返す前に止まった返事は、0 のまま）。
- [ ] 欄に、いまの会話の費用の合計を出す。
- [ ] 欄の費用は、サイクルの費用の上限に数えない。欄には、費用の上限を置かない（オーナーの決定 2026-11-22）。

### うまくいかないとき

- [ ] 実行エンジンが見つからないときは、文を送る操作を誤りにし、欄に、実行エンジンが要る旨を出す。オーナーの発言は記録しない。
- [ ] 実行エンジンが途中で失敗したときは、その返事を「失敗」として記録し、欄に、失敗した旨と、もう一度送れる旨を出す。それまでに出た分は残す。
- [ ] 利用上限に当たったときは、その返事を「利用上限」として記録し、欄にその旨を出す。
- [ ] サーバを止めるとき、進行中の返事の実行エンジンを止める。次に起動したとき、進行中のまま残った返事は「止めた」にする（起動のときに、すべてのエージェントのストアを、core の API で 1 回ずつ見る。ストアの無いワークスペースは、作らずに飛ばす）。

返事の終わり方（`state`）と、欄に出す文。

| `state` | 意味 | 欄に出す文 |
|---|---|---|
| `replying` | 返事が進行中 | 「返事を待っています…」 |
| `done` | 終わった | （出さない） |
| `stopped` | 止めた | 「止めました。」 |
| `limit` | ターン数か時間の上限 | 「上限に達したので、ここで止まりました。続きは、もう一度送ってください。」 |
| `rate_limited` | 利用上限 | 「利用上限に達しました。時間を置いて、もう一度送ってください。」 |
| `session_lost` | 会話を続けられなかった | 「前の会話を続けられませんでした。新しい会話として、もう一度送ってください。」 |
| `failed` | そのほかの失敗 | 「返事を作れませんでした。もう一度送れます。」 |

### 画面の残り（S4d-2）

S4d-2 は、対話の欄（S4d-1）の後に残った、画面の分を入れる。画面の分が 4 つと、文書に分かれる: (A) 画面のボタンで受ける操作を広げる、(B) サイクルの画面を作り替える、(C) 意思決定の記録・スーパーバイザーの手・足されたタスクを画面に出す、(D) 起きたことを知らせる、(E) 文書。core に新しい状態・表は足さない（ストアの版は進めない）。決めたことは、下の「オーナーの決定（S4d-2。2026-11-23）」のとおり。

#### (A-1) 選ぶだけの回答を、ボタンで受ける

- [ ] 画面のボタンで、保留の選択肢を 1 つ選んで答えられる（口は、下の「画面・API設計」）。答える相手は、保留の ID（S4c-3）で指す。
- [ ] ボタンの回答は、経路 `ui`・本人確認なし（`none`）で記録する。
- [ ] 経路 `ui` の回答は、選択肢の識別が要る。文だけの回答は、core が断る。
- [ ] 経路 `ui` の回答は、添え書き（選択肢に添える文）を受けない。添え書きが空でなければ、core が断る。記録する回答の文は、選んだ選択肢の見出しだけになる。
- [ ] 経路 `ui` の回答は、計画を作り直す指定（`--replan` に当たるもの）を受けない。core が断る。
- [ ] 経路 `ui` の回答は、足す依頼の保留（上限を超える足す依頼）の、「足す」（上限が上がる）を受けない。core が断る。
- [ ] 経路 `ui` の回答は、足す依頼の保留の、「計画を作り直す」を受けない。core が断る。
- [ ] 経路 `ui` の回答は、足す依頼の保留の、「足さずに進める」を受ける。
- [ ] 選択肢を持たない保留への、経路 `ui` の回答は、core が断る。
- [ ] API は、保留の選択肢ごとに、「ボタンで選べるか」を返す。決めるのは core で、画面は、その値のとおりに出す（画面の側で、選べるかを判定しない）。
- [ ] 「ボタンで選べない」のは、足す依頼の保留（上限を超える足す依頼。理由 `task_add_over_limit`）の、識別 `add` と `replan` だけ。core は、保留の理由と、選択肢の識別だけで決める（選択肢の文は読まない）。ほかの保留（委譲先の問い・スーパーバイザーが上げた問い・足す依頼の中身の問い〔理由 `task_add_question`〕）の選択肢は、すべてボタンで選べる。
- [ ] API は、保留ごとに、照合の値（問いと選択肢から、core が作る値）を返す。
- [ ] ボタンの回答は、画面が読んだときの照合の値を送る。いまの保留の照合の値と違えば、core が競合（409 に当たる誤り）で断る（問いか選択肢が、読んだ後に変わった）。
- [ ] 保留が閉じていた（答え済み・ほかの手段で閉じた）ときの、ボタンの回答は、競合（409 に当たる誤り）で断る。
- [ ] ボタンの回答が成立したら、ターミナルの回答（`flywheel answer`）と同じ決まりで、サイクルを始める。
- [ ] 選択肢のボタンは、タスクの詳細の、待っている問いの所に出す。
- [ ] 選択肢のボタンは、課題の詳細の、待ちの所に出す。
- [ ] 選択肢のボタンは、「いま進められること」の、回答を待っている行に出す。
- [ ] 「いま進められること」で、ボタンの回答が通ったら、課題の題名と選んだ選択肢の語つきで、答えた旨を、回答の行の外に出す（通ると行が消えるので、押した結果が見えるようにする。オーナーの決定 2026-11-23）。
- [ ] ボタンで選べない選択肢は、ボタンにせず、選択肢の見出しと説明に、「対話で伝えてください」の案内を添えて出す。
- [ ] 選択肢を持たない問いには、ボタンを出さず、いまの案内（対話かターミナルで答える）を出す。
- [ ] ボタンを押したら、選んだ選択肢の見出しを出して、確かめを 1 回はさむ（押し間違いを防ぐ）。確かめた後に、送る。
- [ ] 競合（409 に当たる誤り）で断られたら、画面は、問いが変わった旨を出し、読み直した問いを出す。
- [ ] 答えた後のタスクの詳細の「問いと回答」に、答えた人を「あなた（画面のボタン）」と出す。

#### (A-2) 取り込みを、ボタンで受ける

- [ ] 「いま進められること」の、取り込めるものの行に、チェックを付けられる。
- [ ] チェックを 1 つ以上付けると、「選んだ N 件を取り込んで、計画まで進める」のボタンを押せる（0 件のときは、押せない）。
- [ ] ボタンは、選んだものを取り込む。取り込みの決まり（指定の形・親と子の扱い・断る条件）は、ターミナルの取り込み（`flywheel ingest <指定>...`）と同じ。
- [ ] 取り込みは、経路 `ui` で記録する（本人確認は要らない。ターミナルと同じ）。
- [ ] 取り込み元は、宣言のすべての取り込み元を対象にする（取り込み元を 1 つに絞る指定は、渡さない）。取り込み元の宣言が無いときは、指定が取り込めるものでない誤りと同じに返す。
- [ ] 取り込みが成立したら、サイクルを始める（計画の承認のボタンと同じ決まり。すでに走っていれば、始めない）。
- [ ] ボタンの脇に、取り込むと何になるかを、事実だけで出す: 課題になる件数（選んだ行の数）と、取り込み元の子として記録する件数（選んだ行の、API が返した子の数の合計）。画面は、API の値を足すだけで、親子を自分で判定しない。
- [ ] タスクの案の数と、費用の見込みは、出さない。「計画が出来たら、承認を求めます」と案内する。
- [ ] 取り込みが失敗したら（上流を読めない・指定が取り込めるものでない）、何も取り込まず、理由を画面に出す。
- [ ] 取り込みが成立したら、作った課題へのリンクを出し、取り込めるものの一覧を読み直す。

#### (A-3) サイクルを止めるのを、ボタンで受ける

- [ ] サイクルの画面に、サイクルが走っている間だけ、「サイクルを止める」のボタンを出す。
- [ ] ボタンは、ターミナルの `flywheel cycle stop` と同じ、止める指示を出す（いまの段が終わると止まる。委譲先の実行は取り消さない）。
- [ ] 止める指示が出ている間は、ボタンを出さず、「止める指示を出しました。いまの段が終わると止まります」と出す。
- [ ] サイクルが走っていないときに、止める口へ送っても、何も変えずに、走っていない旨を返す。

#### (A-4) フォローアップを済みにする・捨てるのを、ボタンで受ける

- [ ] フォローアップの一覧の、未の行に、チェックを付けられる。
- [ ] チェックを 1 つ以上付けると、「済みにする」を押せる。押すと、確かめた結果を書く欄が出る（空では送れない）。
- [ ] チェックを 1 つ以上付けると、「捨てる」を押せる。押すと、理由を書く欄が出る（空では送れない）。
- [ ] 済みにする決まり（まとめて行う・断る条件）は、ターミナルの `flywheel followup done` と同じ。経路 `ui` で記録する。
- [ ] 捨てる決まりは、ターミナルの `flywheel followup drop` と同じ。経路 `ui`・本人確認なしで記録する。
- [ ] 選んだものの 1 つでも断られたら、どれも変えず、理由を画面に出す。
- [ ] 済み・捨てたの行には、チェックを出さない。
- [ ] タスクに上げるボタンは、置かない（対話で伝える。UX の決定 20）。

#### (A-5) 承認の経路の決まり

- [ ] 経路と本人確認の登録簿の、画面のボタン（`ui`・`none`）に、回答と、フォローアップを捨てる、を足す。
- [ ] 画面のボタン（`ui`・`none`）は、差し戻し・計画の問いへの答え・取り下げ・予算の増額・不可逆操作の承認と差し戻し・反映を保留にしない完了の承認・フォローアップをタスクに上げる、を受けない（いまと同じ）。

#### (B) サイクルの画面

- [ ] 走っているとき、始まった時刻と、きっかけを出す。
- [ ] 走っているとき、回りの数を出す。
- [ ] 走っているとき、作業中の実行の件数と、同時に走らせる上限を出す。
- [ ] 走っているとき、このサイクルの費用と、上限を出す。
- [ ] 走っているとき、見ているタスクを並べる: 題名（タスクの題名。タスクに結び付かない実行では、課題の題名）・様子（作業中・検証中・あなたの回答か承認待ち）・実行の始まり・費用。行から、タスクの詳細（タスクが無ければ課題の詳細）へ移れる。
- [ ] 走っていないとき、最後のサイクルの、始まりと終わりの時刻・結果を出す。結果の語は、「異常なく終わった」・「途中でやめた」・「途中で止まった」。1 つ目は、誤りなく終わったサイクルに付き、終わった理由が、止めた・費用の上限・利用上限・進まなくなった、のときにも付くので、「最後まで」とは言わない（終わった理由は、別に出す。オーナーの決定 2026-11-23）。
- [ ] 走っていないとき、最後のサイクルの、終わった理由を、言葉で出す（7 つ: 進められるものが無くなった・費用の上限・止めた・利用上限・進まなくなった・エラー・中断）。
- [ ] 終わった理由が、費用の上限のとき、続け方の案内（サイクルを回すと続きから進む・上限は宣言で変える）を出す。
- [ ] サイクルの構造の図を出す: 段を、進む順に並べ、段ごとに、「サイクルを回すと進むもの」の件数を出す（値は、いまある `status` の `cycle_work` のもの。「いまその段にいる件数」は、出さない）。
- [ ] 構造の図に、あなたの番のもの（承認待ち・回答待ち）の件数を出す。
- [ ] スーパーバイザーの記録を出す: 対象のサイクル（走っていればそのサイクル、走っていなければ最後のサイクル）で、スーパーバイザーが打った手を、新しい順に並べる。1 行に、手の種類・課題とタスクの題名・調べたことの要旨・結果（成った・断られた）を出す。行から、タスクの詳細（タスクが無ければ課題の詳細）へ移れる。
- [ ] 対象のサイクルで、スーパーバイザーが打った手が 0 件なら、「このサイクルでは、スーパーバイザーの手はありません」と出す。
- [ ] 費用の内訳を出す: 対象のサイクルの、終わった実行を、実行の種類（`run.kind`。判断点の実行は、判断点の役割ごと）で分けて、額を出す。合計は、丸める前の値で足し、サイクルの費用（終わった実行の費用の合計）と等しい。
- [ ] 対象のサイクルは、サイクルの様子（`cycle status`）と同じ決まりで選ぶ（個別の操作のために作られた周は、除く）。
- [ ] 状態が「止まったまま残っている」（`stale`）のときは、走っていない扱いにする: 「サイクルを止める」は出さず、いまの表示（残っている旨）を出す。対象のサイクルは、最後のサイクル。
- [ ] 「サイクルを回す」のボタンは、いまと同じ（走っていないときに押せる）。
- [ ] サイクルを一度も回していないときは、状態と「サイクルを回す」だけを出す（スーパーバイザーの記録・費用の内訳の枠は、出さない）。
- [ ] 時間の内訳・段ごとの結果・振り返りは、出さない（区切り S5 の振り返りで決める）。

#### (C-1) タスクの詳細

- [ ] スーパーバイザーがあなたへ上げた問いには、「スーパーバイザーが調べたこと」と「推奨」を、問いの上に出す（値は、保留の `supervisor_findings`・`supervisor_recommendation`）。
- [ ] 「意思決定の記録」の節を足す。このタスクに関わる出来事を、古い順に並べる: 計画の承認・このタスクの問いへの回答・このタスクへのスーパーバイザーの手・完了の検証・（足されたタスクなら）足された経緯。
- [ ] 意思決定の記録の 1 行に、いつ・誰が（あなた〔経路の言葉つき〕・スーパーバイザー・完了の検証の判断点）・何を決めたか・理由（あれば）を出す。
- [ ] 計画の承認の行は、課題につくものなので、その課題のどのタスクの記録にも出す。計画を作り直して承認し直した課題では、承認のたびに 1 行ずつ出す（オーナーの決定 2026-11-23）。
- [ ] スーパーバイザーの手の行に、手の種類・調べたこと・添え書き（条件・答えた問い）・結果を出す。断られた手は、断られた理由を出す。
- [ ] 足されたタスクには、「後から足したタスク」の印と、足した時刻・出どころ（タスクの完了の検証・フォローアップをタスクに上げた・スーパーバイザー）を出す。出どころのタスクかフォローアップがあれば、そこへ移れる。
- [ ] 意思決定の記録に出すものが無いタスクでは、節を出さない。

#### (C-2) 課題の詳細

- [ ] ツリーの、足されたタスクに、「後から足した」の印を出す（点線の枠）。
- [ ] 「スーパーバイザーの記録」の節を足す: この課題で打った手の数と、手ごとの行（手の種類・タスクの題名・調べたことの要旨・結果・時刻）。行から、タスクの詳細へ移れる。手の数は、成った手だけを数える。行は、断られた手・失敗した手も含めて全部出す（オーナーの決定 2026-11-23）。
- [ ] スーパーバイザーの手が 0 件の課題では、節を出さない。
- [ ] 足す依頼を出す: 依頼ごとに、状態（足した・上限を超えるので問い中・足さなかった・取り消した）・足すタスクの題名・足した後の見込みと上限を出す。
- [ ] 足す依頼が 0 件の課題では、足す依頼の枠を出さない。
- [ ] 待ちの所に、開いている保留を、保留ごとに 1 つの枠で出す（S4c-3 で、開いている保留が複数になりうる）。枠に、保留の ID・問い・止めている範囲（タスク・課題）・選択肢を出す。
- [ ] 経緯の画面で、スーパーバイザーの手・問いの書き換え・上限の変更・足す依頼の出来事を、言葉で出す（いまは、生の値で出る）。

#### (C-3) いま進められること

- [ ] 「あなたを待っているもの」の件数を、承認と回答に分けて出す。
- [ ] 回答を待っている行に、問いの要旨と、選択肢のボタン（A-1）を出す。

#### (D) 起きたことの知らせ

- [ ] 知らせは、作業ログとサイクルの記録から、決まった文で作る（実行エンジンを起こさない。費用が出ない）。
- [ ] 知らせの種類は、4 つ: タスクを足した・反映先へ入った・サイクルが終わった・スーパーバイザーがあなたへ上げた。元の記録と条件は、次の表のとおり。

| 種類 | 元の記録と条件 | 時刻 |
|---|---|---|
| タスクを足した | 足す依頼が「足した」になった記録（足す依頼の作業ログの、タスクを足した出来事） | その出来事の時刻 |
| 反映先へ入った | 反映の操作の、実行の作業ログ（`op_execute`）のうち、後の状態が実行済み（`executed`）のもの。取り消し・やり直しで同じ出来事の名前が付く記録は、含めない | その出来事の時刻 |
| サイクルが終わった | 終わったサイクルのうち、終わった理由が入っているもの。個別の操作のために作られた周と、終わった理由が空の古い周は、含めない | サイクルの終わりの時刻 |
| スーパーバイザーがあなたへ上げた | スーパーバイザーの印が「オーナーへ上げた」（`escalated`）の保留。スーパーバイザーが関わらずに上がった保留（印が空）は、含めない | その保留に結び付く、スーパーバイザーの対処の記録の最新の時刻。無ければ、保留が立った時刻 |
- [ ] 「タスクを足した」の知らせは、課題の題名・足した件数・出どころを言い、課題の詳細へ移れる。
- [ ] 「反映先へ入った」の知らせは、課題の題名を言い、課題の詳細へ移れる。
- [ ] 「サイクルが終わった」の知らせは、終わった理由を言葉で言い、サイクルの画面へ移れる。
- [ ] 「サイクルが終わった」の知らせは、終わった理由が、費用の上限・利用上限・進まなくなった・エラー・中断のとき、決まった文の続け方の案内を添える。
- [ ] 「スーパーバイザーがあなたへ上げた」の知らせは、課題とタスクの題名を言い、タスクの詳細（タスクが無ければ課題の詳細）へ移れる。タスクに結び付かない保留のときは、課題の題名だけを言う（オーナーの決定 2026-11-23）。
- [ ] 知らせを読む口は、新しい順に、直近の 20 件までを返す。
- [ ] 「いま進められること」に、「最近起きたこと」として、知らせを新しい順に並べる。0 件のときは、枠を出さない。
- [ ] 対話の欄は、会話が開いているとき、会話の始まりより後の知らせを、時刻の順に、発言の間へ差し込んで出す。
- [ ] 対話の欄は、会話が無いとき、直近の知らせを 3 件まで出す。
- [ ] 欄の知らせは、「知らせ」の札を付け、オーケストレーターの返事と見分けられる形で出す。
- [ ] 知らせは、会話と発言の記録（ストアの表）に書かない。印の検査（最後のオーナーの発言への返事が進行中）は、知らせがあっても変わらない。
- [ ] 知らせは、実行エンジンへ渡す発言に入れない（オーケストレーターは、要るときに、いまあるコマンドで状況を読む）。
- [ ] 画面は、いまある変化の知らせを受けたら、知らせの口を読み直す（知らせのための、新しい流す口は作らない）。
- [ ] 知らせの既読は、持たない。
- [ ] 考えて書く提案（「次は何をすればよいか」）は、オーナーが欄で聞いたときだけ返す（いまと同じ。自動では書かない）。

## 技術的な制約・方針

- 変更対象:
  - `internal/core`: 会話と発言の記録（表 2 つ・マイグレーション 1 本）と、その公開の API。経路 `chat` の登録と検査。対話の実行のインターフェース（判断点の呼び出しのインターフェースと同じく、core に置く）。宣言の項目。印の環境変数の名前。
  - `internal/invoker`: 対話の実行（実行エンジンの起動・`stream-json` の読み取り・止める・費用の取り出し）と、指示文 1 本。
  - `internal/cli`: 印があるときの、コマンドの一覧の検査と、経路の切り替え。`serve` が、invoker の対話の実行を組み立てて、サーバへ渡す。
  - `internal/server`: 対話の口（下の「画面・API設計」）。`internal/invoker` を import しない決まりのまま、対話の実行は、core のインターフェースで受け取る。
  - `internal/view`・`web/src`: 型と、欄の部品。
- core の公開の API（名前は実装で決めてよい。役割はこのとおり）: いまの会話を読む／オーナーの発言を記録して返事の行を作る（会話が無ければ作る。返事が進行中なら断る）／返事の行へ、発言の 1 つ分を足す／実行したコマンドを足す／返事を終える（終わり方・費用）／会話を閉じる／進行中のまま残った返事を「止めた」にする。
- ストアが正。サーバがストアの外に持つのは、進行中の返事の実行エンジンのプロセス（止めるため）だけ。返事の進みは、ストアへ書き、いまある変化の知らせで画面へ届く。
- 実行エンジンに固有の形（コマンドの引数・`stream-json` の形）は、`internal/invoker` の中に閉じる。対話の実行のインターフェースは、判断点（1 回で結果を返す）と違い、途中の分を順に渡す形にする。入力は、発言・いま見ているもの・会話の識別と、新しい会話か続きか・作業ディレクトリ・環境・道具の範囲・ターン数と時間の上限。途中で、発言を 1 つ出し終えるたびと、コマンドを 1 つ実行し終えるたびに、呼び出し元の関数を呼ぶ。会話の始まりの行が現れたことも知らせる。最後に、終わり方と費用を返す。止めるのは、実行の取り消し（`ctx`）で行い、実行エンジンが起動した子のプロセスも、まとめて止める（プロセスのグループへ合図を送る）。
- 1 回の返事ごとに、実行エンジンのプロセスを 1 つ起動する（常駐させない）。会話の識別（UUID）は、判断点と同じく、flywheel が決めて渡す（1 通目は新しい会話として、2 通目からは続きとして）。
- 起動の引数は、判断点の引数（`internal/invoker/args.go`）にならう。違いは、出力を `stream-json` にすること（要る引数〔`--verbose` など〕は、最初の Issue で、実物で確かめる。発言の途中の断片を流す指定は、付けない）、許す道具に flywheel のコマンドの実行（`Bash(flywheel:*)`）を足し、禁じる道具から `Bash` を外すこと、ターン数の上限。許可を尋ねる動きは、判断点と同じ指定（`--permission-mode default`。尋ねる相手がいないので、許していない道具は断られる）。
- `stream-json` から読むもの: オーケストレーターの発言の文、道具の実行（コマンドの行）とその結果（成否）、終わりの行（終わり方・費用）。**形は、実物の出力を見て固める**: 最初の Issue で、実物の実行エンジンの出力を 1 回取り、その写しを試験のデータ（`testdata`）に置く。テスト用の実行エンジンは、その写しの形で、場面ごとの出力（発言 2 つ・コマンドの実行・費用・ターン数の上限・会話を続けられない・利用上限・0 でない終了）を出す。
- 道具の制限（`restricted`）は、2 重にする。実行エンジンの許可の設定と、flywheel のコマンドの側の一覧の検査。ただし、書き込む・実行するシェルのコマンド（`flywheel status; ほかのコマンド` のような連結を含む）を断るのは、実行エンジンの許可の設定だけが頼りになる（読み取りだけと見なされるシェルのコマンドは通る）。実物で断られることを、main へ入れる前に確かめる（下の「要人間判定」）。断られないと分かったときは、入れずに、オーナーへ上げる。
- 宣言の読み込みは、項目が無いことと、空の一覧・0 を見分ける（既定を入れるのは、項目が無いときだけ）。
- 欄の実行エンジンは、サイクルの排他を取らない。欄から実行した flywheel のコマンドは、それぞれの決まりで排他を取る。
- S4a と並べて進める。S4a のコマンド（`cycle status`・`cycle stop`・`--detach`）と、承認がサイクルを始める動きは、S4a が持つ。この区切りは、一覧に名前を入れるだけで、動きを作らない。ストアの版は、S4a（版 31）の次の 32。この区切りの統合ブランチは、S4a が main に入った後に main を取り込み、版の番号を確かめてから、main へ入れる（それまでは、統合ブランチの中で、いまの版の次の番号を使う）。

## クリティカル設計決定

### 承認の真正性: 対話の欄から、反映の承認を受ける（UX の決定 27 を改める）

- **採用案**: 対話の欄を、新しい経路 `chat` として登録する。欄から、承認・差し戻し・回答・取り下げ・予算の増額・フォローアップの操作を受ける。不可逆操作の承認は、宣言 `chat_approvable_operations` にある種類だけを受ける。既定は、反映（`release`）だけ。記録の「発言」には、オーナーが欄に書いた文面そのものを、core が入れる。
- **理由**: オーナーの決定（2026-11-22）。反映先へ入れること（main へのマージなど）は、対話から行えるようにする。本番へのデプロイに当たる操作（外部への送信など）は、人が直接行うのを既定にし、設定で変えられるようにする。
- **受け入れた危険**: サーバは、文の送り手を見分けない（設計書 §9）。同じマシンのプロセス（委譲の子を含む）は、画面の HTML から CSRF の値を取って、欄へ文を送れる。その文が「承認します」であれば、オーケストレーターは、承認を記録しうる。道具の範囲が `restricted` のときは、この危険を、次の 3 つで小さくしたうえで、受け入れる（`full` のときの危険は、下の「道具の範囲を、宣言で選ぶ」）。(1) 欄から起こせることを、flywheel の決まったコマンドと読み取りだけのシェルのコマンドにする（ファイルの編集・書き込む・実行するシェルのコマンドは無い）。(2) 欄から承認できる不可逆操作の種類を、宣言で絞る。(3) 記録に、欄に書かれた文面そのものが残り、経路 `chat` として、後から見分けられる。送り手を見分ける仕組み（パスキーなど。決定 D18 で外した）は、足さない。
- **代替案**: 欄からは、反映を保留にした完了の承認までにし、反映の承認はターミナルだけで受ける（いまの画面のボタンと同じ範囲）。オーナーの決定で採らない。
- **影響範囲**: 本人確認の登録簿（`verification.go`）に、(`chat`, `relayed`) の行を足す（すべての操作を受ける）。不可逆操作の種類の絞りと、反映の承認を含む完了の承認の絞りは、登録簿の外の、core の検査で行う（core は、経路が `chat` のとき、宣言の一覧を読んで判定する）。設計書 §9。UX の決定 27 は、「ターミナルの対話と同じ扱い」から、「経路 `chat`。不可逆操作は、宣言で選んだ種類だけ」に改める。

### 承認の真正性: 発言の文面を、core がストアから引く

- **採用案**: 欄から起動された flywheel のコマンドは、環境の印（会話の識別・発言の識別）を、そのまま core へ渡す。形は、次のとおり。core に、対話の欄のための本人確認（印の 2 つの値だけを持つ）を置く。本人確認の検査（`Verify`）は、(`chat`, `relayed`) の組では、印が空でないことだけを見る（ターミナルの対話の `relayed` が求める、会話の識別と発言の要旨は、求めない）。操作を行う core の処理が、同じトランザクションの中で、印の検査（会話が開いている・最後のオーナーの発言である・返事が進行中である）を行い、発言の文面を引いて、記録の「発言」と「会話の識別」を埋める。CLI は、ストアを開かず、承認の記録も組み立てない。
- **理由**: ターミナルの対話の記録（`--relayed`）は、発言の要旨を、Claude が書く。欄では、発言そのものがストアにあるので、書き写しを挟まずに残せる。古い発言や、ほかの会話の発言を根拠にした記録も、断れる。
- **残る危うさ**: 印は環境変数なので、同じマシンのプロセスは、自分で付けられる。ただし、印を付けると、受けるコマンドは狭くなり（一覧だけ）、印の検査も通す必要がある（進行中の返事がある間だけ）。印の無い `--relayed`（要旨を自分で書ける）より、広くはならない。サーバが落ちて、進行中の返事の行が残っている間は、印の検査が通りうる（次の起動で「止めた」に直す）。
- **影響範囲**: `internal/core` の承認の記録。記録の表は変えない（`channel`・`verification`・`relay_session`・`relay_quote` の列は、いまあるものを使う）。

### DB スキーマ: 会話と発言の表（版 32）

- **採用案**: マイグレーション 1 本で、表を 2 つ足す。
  - `chat_session`: `id`・`engine_session`（flywheel が決めた会話の識別。UUID）・`engine_started`（実行エンジンが、この識別の会話を作ったか。既定 0。返事の終わり方によらず、実行エンジンの出力に、会話の始まりの行が現れた時点で 1 にする）・`started_at`・`closed_at`（NULL 可）。開いている会話（`closed_at` が NULL）は、高々 1 つ（部分一意索引）。
  - `chat_message`: `id`・`session_id`・`role`（`owner`・`orchestrator`）・`body`・`state`・`cost_usd`（既定 0）・`viewing_challenge_id`・`viewing_task_id`・`viewing_title`（どれも NULL 可）・`activity`（JSON の配列。既定は空）・`created_at`・`ended_at`（NULL 可）。
- **理由**: 読み込み直しても、やりとりが出ること・費用を記録すること・承認の記録が発言を引けることに、ストアの行が要る。実行エンジンの側の記録（会話のファイル）は、実行エンジンに固有の形なので、頼らない。ストアはエージェントごとにあるので、エージェントの列は持たない。
- **代替案**: 実行エンジンの会話のファイルを読む。上の理由で採らない。
- **影響範囲**: ストアの版が 32 になる。書き出しと読み込み（`export`・`import`）に、表が 2 つ増える（ほかの表と同じに、行をそのまま書き出す）。

### 外部システム連携: 実行エンジンを、サーバから起動する

- **採用案**: 対話の実行のインターフェースを core に置き、実装を `internal/invoker` に置く。`serve` が組み立てて、サーバへ渡す。1 回の返事ごとに、プロセスを 1 つ起動する。道具は、読み取り・検索・flywheel のコマンドだけを許し、許可を尋ねる動きは、断られる形で起動する。
- **理由**: 判断点と同じ置き場にすれば、実行エンジンに固有の形が 1 か所に閉じる（flywheel#787 の「core に持ち込まない」）。プロセスを常駐させると、止め方・残ったプロセスの片付け・サーバの再起動の扱いが増える。
- **代替案**: 実行エンジンの SDK を、別の実行環境（TypeScript か Python）で動かす。オーナーの方針（2026-11-18）で採らない。画面にターミナルを埋め込む。道具を絞れないので採らない。
- **影響範囲**: `internal/core`（インターフェース）・`internal/invoker`・`internal/cli`（`serve`）・`internal/server`。

### 欄から起こせることを、flywheel のコマンドの側でも絞る

- **採用案**: flywheel のコマンドは、欄から起動された印があるとき、決まった一覧のコマンドだけを受ける。検査は、委譲の子の印（`FLYWHEEL_DELEGATED_RUN`）の検査と同じ層（コマンドを選ぶ所）に置き、委譲の子の印の検査を先に行う。
- **理由**: 実行エンジンの許可の設定だけに頼ると、設定の書き方の誤りや、実行エンジンの版による違いで、範囲が広がりうる。flywheel の側の検査は、実行エンジンによらない。
- **影響範囲**: `internal/cli`。委譲の子からのコマンドを断る決まりは、そのまま（子が欄の印を足しても、断られる）。

### 道具の範囲を、宣言で選ぶ（絞る・すべて許す）

- **採用案**: 宣言の `chat_tools` で、`restricted`（読み取り・検索・flywheel のコマンドだけ。既定）か、`full`（すべて許す）を選ぶ。Tom のワークスペースは、`full` にして使う。断られたコマンドは、どちらでも、記録に残す。
- **理由**: オーナーの決定（2026-11-22）。いまの対話のセッションでは、調べものや直しなどの雑用を、その場で任せることが多い。絞った形だけでは、それが欄で出来ず、不満につながる。既定を絞る側にするのは、何も設定していないワークスペースで、欄へ文を送れる者が何でも出来る状態にしないため。
- **受け入れた危険（`full`）**: `full` のとき、欄へ文を送れる者（同じマシンのプロセス。委譲の子を含む）は、オーナーの権限で、マシンの上のことを何でも起こせる。欄から承認できる不可逆操作の種類の絞りも、守りにはならない（任意のシェルが使えるので、印を外して、ターミナルの対話の記録の形で承認できる）。指示文での求めと、記録に残ることだけが、歯止めになる。これは、ターミナルの対話のセッションで、すべて許して使うときと同じ危険で、選んだワークスペースだけが負う。
- **代替案**: 絞った形だけにして、Tom で使ってから広げる。オーナーの決定で採らない。道具を 1 つずつ宣言で足す形。設定と確かめが増えるので、2 つの値にする。
- **影響範囲**: `agent_declaration.go`・`internal/invoker`（起動の引数）・`internal/cli`（一覧の検査）・画面（範囲の表示）。設計書 §9 に、`full` の危険を書く。

### 承認の真正性: 画面のボタンで受ける操作を広げる（UX の決定 26 を、設計書 §9 に入れる）

- **決定**: 経路と本人確認の登録簿の、画面のボタン（`ui`・`none`）に、回答と、フォローアップを捨てる、を足す。取り込み・サイクルを止める・フォローアップを済みにするは、もともと本人確認の要らない操作なので、登録簿は変えず、サーバに口を足すだけにする。
- **経路 `ui` の回答の限り**（core が、回答の書き込みの中で強制する。サーバと画面の検査に頼らない）: 選択肢の識別が要る／添え書きは空であること／計画を作り直す指定を受けない／足す依頼の保留（理由 `task_add_over_limit`）の、識別 `add` と `replan` を受けない／選択肢を持たない保留を受けない。「ボタンで選べるか」は、保留の理由と、選択肢の識別だけで決める。
- **理由**: 設計書 §9 が、画面のボタンを狭くしていたのは、同じマシンのプロセス（委譲の子を含む）が、画面の口へ送れるため。対話の欄（S4d-1）で、同じマシンのプロセスが欄へ文を送れる危険は、すでに受け入れている（欄からは、回答も予算の増額も通る）。選択肢を選ぶ回答と、フォローアップを捨てるは、欄ですでに受け入れた危険と同じ種類で、危険の種類は増えない。取り込みと、サイクルを止めるは、ターミナルでは本人確認なしの操作で、委譲の子のコマンドは印で断られるが、画面の口からは届くようになる。その分の危険は増えるが、どちらも、予算の上限・範囲・反映先を、直接は変えない。予算の上限が上がる選択と、範囲が変わる選択（計画を作り直す）は、ボタンでは受けない（UX の決定 15）。
- **受け入れた危険**: 同じマシンのプロセスが、CSRF の値を取って画面の口へ送ると、問いの選択肢のうちボタンで選べるものを選ぶ・未のフォローアップを捨てる（記録は残り、消えない）・取り込めるものを取り込む・サイクルを止める、ができる。どれも、予算の上限・範囲・反映先を、直接は変えない。記録には、経路 `ui` が残る。委譲先やスーパーバイザーが作った選択肢は、自由な文なので、選んだ先で範囲や費用に触れる中身でも、core は見分けない（選択肢の文から、承認・予算の増額・取り下げは起こさない、といういまの決まりは変わらない）。
- **代替案**: ボタンは対話の欄へ下書きを入れるだけにする（決まりは広げずに済むが、押して終わりにならず、返事を待つ分だけ遅く、費用が出る）。足す依頼の「足す」もボタンで受ける（UX の決定 15 を改めることになる）。どちらも採らない（オーナーの決定 2026-11-23）。

### 状態遷移・排他: ボタンの回答の照合

- **決定**: ボタンの回答は、保留の ID と、画面が読んだときの照合の値を送る。core は、書き込みの中で、その保留が開いたままで、いまの照合の値が同じことを確かめる（S4c-3 の、保留での照合と同じ確かめ。確かめたときの問いと選択肢を、照合の値で持ち運ぶ）。課題の版は、照合に使わない。
- **照合の値**: 問いの文と、選択肢（識別・見出し・説明・識別なしの回答を断るか）から、core が作る。作り方は core に閉じ、画面は、受けた値をそのまま返す。
- **二度押し**: 1 回目で保留が閉じるので、2 回目は、競合で断られる。画面は、押した後、応答が返るまでボタンを押せなくする。
- **理由**: 画面は、読んでから押すまでに時間が空く。その間に、スーパーバイザーが問いを書き換える・額が変わって問いが出し直される、がありうる。古い問いに答えた形にしないために、読んだときの中身で照合する。

### 外部システム連携: サーバが、取り込みで上流の Issue を読む

- **決定**: 取り込みの口は、サーバが組み立てた上流の読み取り（いまは、取り込めるものの読み取りに使っている）を、core の取り込み（選んで取り込む）へ渡す。上流を読む時間の上限は、上流の読み取りの部品の既定のまま（ターミナルの取り込みも、値を指定していない）。サーバで値を足さない。取り込み元を 1 つに絞る指定は、渡さない。上流を読めないときは、ストアを変えずに、誤りを返す。再試行は、しない（オーナーが、もう一度押す）。
- **サイクルを始める**: 取り込みが成立した後、承認のボタンと同じ決まり（すでに走っていれば始めない）で、サイクルを始める。きっかけの値は、いまある画面の値を使い、新しい値は足さない。
- **理由**: 取り込みは、もともと本人確認の要らない操作で、上流を読むのはサーバの読み取りと同じ道具。新しい連携先・新しい認証は、足さない。

### DB スキーマ: 変えない

- **決定**: S4d-2 は、表も列も足さない（ストアの版を進めない）。サイクルの画面の値は、いまある記録（サイクル・実行・スーパーバイザーの対処）から読む。知らせは、作業ログとサイクルの記録から導く。照合の値は、保留の行から、その場で作る。
- **見送るもの**: 段ごとの結果・振り返り・時間の内訳・「いま各段にいる件数」は、いまの記録に無い。区切り S5 の、スーパーバイザーの振り返りと一緒に決める。サイクルを止める指示を、誰がどの経路で出したかの記録も、足さない（残るのは、止める指示の時刻と、終わった理由）。

### 知らせ: 記録から導き、対話の欄の記録には書かない

- **決定**: 知らせは、読むたびに、作業ログとサイクルの記録から導く。対話の欄には、画面の側で、発言の間へ時刻の順に差し込んで出す。会話と発言の表には、書かない。
- **理由**: 欄から受ける承認の守りは、「最後のオーナーの発言への返事が進行中」であることを、ストアの発言の行で確かめている。知らせを発言の行として書くと、この確かめの前提（発言の行は、オーナーの発言と、その返事だけ）が変わる。導く形なら、守りを変えずに、欄だけ見ていても気づける。
- **代替案**: 発言の表に、知らせの行の種類を足す（会話を閉じた後も、やりとりと一緒に残るが、表と、印の検査の両方を変える）。採らない。知らせの元の記録（作業ログ・サイクル）は、ストアに残る。

## 受入基準

S4d-2 の受入基準。core の基準は、ストアを使う試験で確かめる。サーバの基準は、口へ要求を送る試験で確かめる。画面の基準は、偽の API を使う部品の試験と、画面の通しの試験で確かめる。「足す依頼の保留」は、上限を超える足す依頼で立った保留（選択肢は「足す」「足さずに進める」「計画を作り直す」）。

### 選ぶだけの回答（core）

- [ ] 経路 `ui`・本人確認なしで、選択肢を持つ保留に、選択肢の識別で答えると、回答が成立する。
- [ ] その回答の記録の、経路は `ui`、本人確認は `none` になる。
- [ ] 経路 `ui` で、選択肢の識別を付けずに文だけで答えると、検証の誤りで断られ、保留は開いたまま残る。
- [ ] 経路 `ui` で、選択肢の識別に添え書きを付けて答えると、検証の誤りで断られ、保留は開いたまま残る。
- [ ] 経路 `ui` の回答が成立したとき、記録される回答の文は、選んだ選択肢の見出しだけになる。
- [ ] 経路 `ui` で、計画を作り直す指定を付けて答えると、検証の誤りで断られ、保留は開いたまま残る。
- [ ] 経路 `ui` で、足す依頼の保留に「足す」で答えると、本人確認の誤り（経路で受けない操作）で断られ、予算の上限は変わらない。
- [ ] 経路 `ui` で、足す依頼の保留に「計画を作り直す」で答えると、本人確認の誤り（経路で受けない操作）で断られ、課題の状態は変わらない。

### 要人間判定の手順（S4d-2。オーケストレーターが、試し用のワークスペースで行う）

実物では、実装の担当は行わない。次の 4 件を、main へ入れる前に、オーケストレーターが行う。どれも、試し用のワークスペース（運用中のものとは別。`flywheel init` で作る）で `flywheel serve` を起動し、同じマシンのブラウザで開く。運用中のワークスペースのストアは使わない。

**1. 選択肢つきの問いに、ボタンで答える**

- 前提: 選択肢を持つ保留を 1 件つくる（委譲先が選択肢つきの問いを返す形で作る。選択肢を持つ保留の作り方は、S4b-1 の受入基準に従う）。もう 1 件、ボタンで選べない選択肢（上限を超える足す依頼の「足す」）を持つ保留があれば、その表示も見る。
- 操作: 課題の詳細（またはタスクの詳細・「いま進められること」）の、その問いの選択肢のボタンを押し、確かめで「送る」を選ぶ。
- 見えるはず: ボタンで選べる選択肢だけがボタンになり、ボタンで選べない選択肢には「対話で伝えてください」の案内が出る。送ると、課題が進み（保留が閉じ）、タスクの詳細の「問いと回答」に、答えた人が「あなた（画面のボタン）」と出る。サイクルを始められる状態なら、サイクルが始まる。問いを書き換えた後に押すと、問いが変わった旨が出て、読み直される。

**2. 取り込みのボタンから、課題ができ、サイクルが始まる**

- 前提: `.flywheel/sources.json` で取り込み元を宣言し、`gh` が使え、取り込み元に、まだ取り込んでいない Issue が 2 件ある（うち 1 件は子を持つ）。
- 操作: 「いま進められること」の「取り込めるもの」で、2 件にチェックを付け、「選んだ 2 件を取り込んで、計画まで進める」を押す。
- 見えるはず: ボタンの脇に「課題 N 件・取り込み元の子として記録 M 件」が出て（費用の見込みとタスクの案の数は出ない）、押すと作った課題へのリンクが出る。取り込めるものの一覧から、取り込んだ 2 件が消える。サイクルが始まり、サイクルの画面に走っている様子が出る。取り込み元の宣言を消して押すと、何も取り込まず、理由が出る。

**3. 走っているサイクルを、ボタンで止める**

- 前提: サイクルが走っている（進められるものがある状態で「サイクルを回す」を押す。長く走るよう、実行が終わらない委譲先を使う）。
- 操作: サイクルの画面で「サイクルを止める」を押す。
- 見えるはず: 止める指示が出た旨の案内に変わり、ボタンは消える。サイクルが自分で終わると、サイクルの画面に、終わった理由が「止めた」として出る。委譲先の実行は取り消されない。走っていないとき（と、状態が古いとき）は、ボタンが出ない。

**4. フォローアップを済みにする・捨てる、と「最近起きたこと」の知らせ**

- 前提: 未のフォローアップを 3 件つくる。タスクを足す依頼（足したタスクの記録）か、サイクルが終わった記録が 1 件以上ある。
- 操作: フォローアップの一覧で、1 件にチェックを付けて「済みにする」を押し、確かめた結果を書いて送る。別の 1 件で「捨てる」を押し、理由を書いて送る（空のままでは送れない）。その後、「いま進められること」を開く。
- 見えるはず: 一覧で、済みと捨てたの切り替えに、それぞれ移った行が出る（済みには確かめた結果、捨てたには理由が付く）。「タスクに上げる」ボタンは出ない。「いま進められること」の「最近起きたこと」に、記録から作った知らせが新しい順に出て（タスクを足した・反映先へ入った・サイクルが終わった・スーパーバイザーがあなたへ上げた）、リンクで課題・サイクル・タスクの詳細へ移れる。知らせが 0 件なら、その枠は出ない。対話の欄は、会話が無いとき、直近の知らせを 3 件まで出し、「知らせ」の札が付く。

## オーナーの決定（S4d-2。2026-11-23）

1. 選ぶだけの回答を、画面のボタンで受ける。受けるのは、選択肢を 1 つ選ぶ回答だけ。文で書く回答・予算の上限が上がる選択（足す依頼の「足す」）・計画を作り直す選択は、ボタンでは断り、対話（かターミナル）へ案内する。この限りは、core が強制する。
2. フォローアップは、済みにする・捨てるの両方を、ボタンで受ける。UX の決定 26 に書き足す。
3. 取り込みのボタンは、取り込んで、サイクルを始める。費用の見込みと、タスクの案の数は、出さない。
4. サイクルの画面は、すでに出ている値と、いまある記録から集計できる値（スーパーバイザーの手・費用の内訳）までを作る。新しい記録の仕組みは足さない。段ごとの結果・振り返り・時間の内訳は、区切り S5 の振り返りと一緒に決める。
5. 知らせは、記録から作る決まった文で出し、「いま進められること」と、対話の欄の両方に出す。実行エンジンは、起こさない。
6. 仕様の承認（2026-11-23）。あわせて、次の作りを承認した: 知らせは、対話の欄の記録に書かず、表示のときに記録から導いて、発言の間へ差し込む／ボタンの回答は、添え書きを受けない／ボタンで選べないのは、上限を超える足す依頼の「足す」と「計画を作り直す」だけで、委譲先やスーパーバイザーが作った選択肢は、すべてボタンで選べる（受け入れた危険として、設計書に書く）／サイクルを誰がどの経路で止めたかは、記録しない。ストアの版は、進めない／知らせの種類は 4 つで、直近の 20 件まで。
