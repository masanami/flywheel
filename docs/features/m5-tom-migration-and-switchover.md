## 概要

M5 は、旧 claude-flywheel の run-cycle で周を回しているエージェントを新しい flywheel へ移し、旧 2 repo（claude-flywheel・claude-flywheel-board）をアーカイブする段である。まず Tom（AI 開発ハーネスのエージェント）を移し、問題が出たら直しながら進める（【決定 2026-10-18 オーナー】）。Tom で評価した後に、同じ手順で他のワークスペースを移し、旧 2 repo のアーカイブはその後に行う（【決定 2026-10-29 オーナー M5H4・M5H5】）。

移行は機能として開発しない。旧台帳の変換スクリプトを作らない（【決定 2026-10-25 オーナー】）だけでなく、照らし合わせ・旧 ID の対応・ファイルの移動も、手順と使い捨ての簡易スクリプトで行う。機能にするのは、切り替えの後も常設で要るものだけである（【決定 2026-10-29 オーナー M5H7】）。それに当たるのはストアの書き出しと再構築（`flywheel export`／`import`。D10）と、1 周の最後に書き出しと記憶をワークスペースへコミットする段 `backup` で、これが本仕様のコードの変更のすべてになる（S1）。

本仕様は 4 つのスライスで満たす。S1 は常設の書き出し（`export`・`import`・`backup` の段）である。S2 は Tom の移行と切り替えで、最後の旧周で仕掛かりを片付け、旧側を止め、宣言を書き移し、課題を取り込みと手で移し、照らし合わせが一致してから新しい flywheel の最初の周を回す。S3 は他のワークスペースの移行、S4 は旧 2 repo のアーカイブである。S1 の受入基準と、S2 の手順の受入基準をいま書く。S3・S4 は、その段を実装対象にするときに受入基準を足す。

いちばん重い判断は承認の状態の移し方である。旧側の計画の承認は移さず、新しい側で J2 が作り直した計画を、オーナーが通常の経路で承認し直す（【決定 2026-10-29 オーナー M5H2】）。人が手で登録した計画（`plan --file`）は構造化した中身を持たず委譲を起動できない【実コード確証 high: `internal/core/delegate.go` の `the challenge has no approved plan with a structured spec`】ので、承認の印だけを写しても委譲は始まらず、J2 の計画を承認済みとして写すとオーナーが見ていない計画で委譲が始まる。守る相手は移行を行うエージェント自身である。

## 背景・目的

- Tom は旧 claude-flywheel 0.31.0 の run-cycle で回っている。新しい flywheel は M4.5 S4 まで出荷した（#384 を 2026-10-28 に close）が、動かしたのは使い捨てのワークスペースだけである（Tom の `briefs/realrun/README.md`）。Tom の実データでしか出ない問題（件数・旧台帳の書式の揺れ・長い本文）は、移すときにしか確かめられない（#404）。
- 2026-10-25 のオーナー発言（#404）: M5 で Tom を移したら、M5 の後の追加機能（#380〜#382 ほか）の実装を新しい flywheel で回し、それで新しい flywheel を評価する。
- 移す量は少ない。2026-10-29 に旧 claude-flywheel 0.31.0 の `scripts/ledger-index.rb` で Tom の台帳を投影した結果は 3 件（分類済 1・着手中 2）で、3 件とも取り込み元マーカーを持つ（`ingested=y`）。手書きの課題は 0 件である【親が実行・実物確証 high】。同日の GitHub で、取り込み元の 4 リポジトリの open で masanami を assign した Issue も 3 件（claude-harness#331・flywheel#404・flywheel#176）で、台帳と一致する【実測 high: `gh issue list --assignee masanami`】。
- 新しいストアは Git で追跡しない（D10）。だが書き出しと再構築は M1 の S3 に置いたまま実装されていない【実コード確証 high: `internal/cli/commands.go` に `export`・`import` が無い】。M1 PD5 は「実運用の前に必須」としており、Tom を移す前に要る。
- 前段の仕様が M5 へ送った事項がある（§前段から送られた事項の扱い）。

## ユーザーストーリー

- オーナーとして、Tom を新しい flywheel へ移した日から、承認と状況の確認を新しいボードと対話だけで行いたい。旧台帳のチェックボックスと新しいボードの両方を見る日を作りたくない。
- オーナーとして、移した後の課題の一覧が旧台帳の open の課題と同じ件数・同じ状態であることを、エージェントの報告ではなく機械の突き合わせで確かめたい。
- オーナーとして、旧側で承認した計画が、新しい側で私の知らないうちに承認済みとして扱われないでほしい。
- オーナーとして、移した後に新しい flywheel で問題が出ても、ストアを失わず、直しながら進めたい。
- エージェントの運用者として、ストアのファイルを失っても、ワークスペースのリポジトリにコミットされた書き出しから状態を戻したい。

## 機能要件

用語: **旧台帳**＝移すワークスペースの `challenge-ledger.md`（open の課題だけを持つ）。**旧 ID**＝旧台帳の課題の ID（`C-246` ほか）。**期待の一覧**＝最後の旧周の後に旧台帳を `ledger-index.rb` で投影した TSV（1 行目がヘッダ。列 `id`・`status`・`prio`・`deps` を使う）。**対応表**＝旧 ID と新しい課題の ID の対応を 1 行 1 件で持つ TSV。**最後の旧周**＝旧側を止める直前に回す、仕掛かりを片付けるための旧 run-cycle の周。**旧側を止める**＝ワークスペースで旧 run-cycle と adhoc が周を回せない状態にすること。**移行の作業**＝旧側を止めてから新しい側の最初の `cycle` までの作業。**使い捨てのスクリプト**＝移行の作業のためだけに書き、flywheel のリポジトリに置かず、実行の記録として `legacy/migration/` に残すスクリプト。

各要件の末尾の `[S1]`〜`[S4]` は、その要件を実装・実施するスライスを表す（§スライス）。チェックボックスは実装対象の S1 の節の要件だけに付け、S2〜S4 の要件は通常の箇条書きにする（S2 の確かめ方は §受入基準の `### S2: …` の節。S3・S4 は実装対象にするときにチェックボックスと受入基準を足す）。

### 書き出し（`flywheel export`）[S1]【決定 D10・M1 PD5 から導く】

- [ ] `flywheel export --out <path>` は、ストアの全状態を 1 つの JSON に書き出す。全状態とは、`sqlite_master` の表のうち名前が `sqlite_` で始まらないものすべての行と、スキーマの版（`PRAGMA user_version`）と、採番の状態（`sqlite_sequence` の行）である
- [ ] `export` は 1 つの読み取りのトランザクションで全表と採番の状態を読む
- [ ] 同じ状態からの書き出しは、バイト単位で同じになる（形は §IF / API「書き出しの形」）
- [ ] 書き出しは、委譲と判断点の出力の保存先（run のディレクトリ）の中のファイルを含まない。表の列にあるパスの値はそのまま書き出す【仮定】
- [ ] `export` はストアを変えない

### 再構築（`flywheel import`）[S1]【決定 D10・M1 PD5 から導く】

- [ ] `flywheel import --in <path>` は、すべての表（`export` と同じ表の集合）に行が無いストアへだけ書き出しを読み込み、採番の状態を書き出しの値にする
- [ ] 書き出し → 再構築 → 書き出しの往復で、2 つの書き出しが一致する（D10「往復で状態が一致することをテストで固定」）
- [ ] 書き出しのスキーマの版がストアの版と違えば、読み込まない【仮定】
- [ ] `import` は 1 つのトランザクションで書き、途中で失敗したら何も残さない
- [ ] 行のあるストアへの `import`・版の違う書き出し・外部キーの違反を含む書き出しは、何も書かず `validation_failed` で終わる

目的はストアを失ったときの復旧で、常設で要る（§問題が出たときの扱いの「ストアが壊れ書き出しから戻せない」は、この復旧が効かない場合を指す）。移行の作業では、新しい課題の ID を旧側の続きから振るためにも使う（§旧 ID と新しい ID）。

### 書き出しのコミット（`backup` の段）[S1]【決定 2026-10-29 親 M5P3】

- [ ] `flywheel cycle` の最後の段 `backup` は、書き出しをワークスペースの決まった場所（`.flywheel/export.json`【仮定】）へ書く
- [ ] `backup` の段は、周が排他を取った後なら、ほかの段の成否・予算による打ち切り・承認待ちでの停止にかかわらず実行する（排他を取れなかった周・宣言の検査で始まらなかった周では実行しない）。段がエラーで終わった周でも、周の記録を閉じる前に実行する【仮定】
- [ ] `backup` の段の core の関数はストアを書き換えない。段の結果は、`cycle` の側がその関数の後に、周の成否にかかわらず作業ログ（`entity=cycle`・`action=backup`。`after` に `outcome`・`commit`・`detail`）に残す。周が正常に終わったときは `cycle --json` の `phases` にも出す（段がエラーで終わった周は `phases` を返さないため＝`internal/core/cycle_run.go`）【仮定】
- [ ] ワークスペースが Git の作業ツリーで、書き出しか記憶の置き場（`memory_dir`。宣言に無ければ書き出しだけ）に前のコミットからの差（`git status --porcelain -- <パス>` が空でない）があれば、その 2 つのパスだけをコミットする。手順は `git add -- <パス>` の後に `git commit --only -m <要約> -- <パス>` とし、ほかのファイルのステージの状態を変えない【仮定】
- [ ] コミットの要約は `chore(flywheel): backup <周の ID>` とする【仮定】
- [ ] 書き出しのパスが Git の除外の対象（`git check-ignore` が一致する）なら、書き出しをコミットせず、`outcome` を `ignored` にする。このときも `memory_dir` に差があれば `memory_dir` だけをコミットし、`commit` にその SHA を入れる（記憶のコミットは M45P7 から引き継いだ別の目的のため）【仮定】
- [ ] `backup` の段は push しない
- [ ] `backup` の段全体（書き出しと git の起動）には 120 秒の期限を付ける。期限切れは `failed` にし、`detail` の先頭を `timeout` にする（フックや署名で git が止まっても、周が閉じて排他が解放されるようにするため）【決定 2026-10-30 オーナー】
- [ ] コミットの前に、HEAD がブランチを指していない（detached HEAD）・rebase の途中・merge の途中のいずれかを検査し、該当すればコミットせず `failed` にして `detail` に理由（`detached HEAD`・`rebase in progress`・`merge in progress`）を書く。差が無いときは検査せず `unchanged` のまま。`outcome` の閉集合に値は足さない【決定 2026-10-30 オーナー】
- [ ] `memory_dir` の宣言が `.flywheel` を含む場所（`.` など）を指すときは、記憶をコミットの対象から外し、外したことを `detail` に出す（ワークスペース全体を巻き込まないための安全策）【決定 2026-10-30 オーナー】。ワークスペースの外を指す `memory_dir`（絶対パス・字面で `..` に始まる相対パス）の宣言は、宣言の検査（`LoadAgentDeclaration`）で `config_invalid` にし、周を始めない【決定 2026-10-30 オーナー】
- [ ] `memory_dir` を宣言していないワークスペースでは、記憶（J6 が既定の `memory/` に書く分）はコミットされない。記憶もコミットしたいワークスペースは `memory_dir` を宣言する【決定 2026-10-30 オーナー】
- [ ] 作業ログへの記録だけが失敗したときは、周を `completed` で閉じ、`cycle --json` の `phases` に段の結果を出す。記録に失敗したことは `detail` に足す（警告。`cycle` はエラーを返さない）【仮定】
- [ ] 段の結果の `outcome` は `committed`（コミットした）・`unchanged`（差が無い）・`not_git`（Git の作業ツリーでない）・`ignored`（書き出しのパスが除外の対象）・`failed`（書き出しかコミットに失敗した）の閉集合とする【仮定: 名前】
- [ ] `backup` の段の `failed` は、`cycle` の終了コードとほかの段の結果を変えない【仮定】

理由: ストアは Git で追跡しない（D10）ので、書き出しのコミットが無いとストアが単一障害点になる。旧側では run-cycle の手順 6 が台帳・journal・記憶をパス指定でコミットしていた（push はしない。Tom の `main` は 2026-10-29 に origin より 5 コミット先にある）。人の手に任せると、旧側で周ごとに自動で行っていたコミットが止まる。周の途中で止まった周でもストアは変わっているので、止まった周ほど書き出しが要る。

### 移行の作業の進め方（手順と使い捨てのスクリプト）[S2・S3]【決定 2026-10-29 オーナー M5H7】

- 移行の作業のために flywheel のコマンド・スキーマ・宣言のキーを足さない。照らし合わせ・旧 ID の対応・ファイルの移動は、本仕様の手順と、使い捨てのスクリプト（jq・シェル）で行う [S2]
- 使い捨てのスクリプトとその出力（期待の一覧・対応表・照らし合わせの結果）は、移すワークスペースの `legacy/migration/` に置いてコミットする（後から何をどう移したかを辿れるように）【仮定: 置き場の名前】[S2]
- 使い捨てのスクリプトは flywheel の既存のコマンドの JSON（`list --json`・`show --json`）を読むだけで、ストアのファイルを直接開かない（ストアを開くのは core だけ＝P2）[S2]

移行の手順そのものは S2 の実装 Issue の計画として課題にし、オーナーが計画を承認してから行う（Tom のワークスペースの変更と GitHub の設定の変更を含むため）。

### 課題の移し方 [S2]【決定 2026-10-29 オーナー M5H2】

期待の一覧の課題を、旧側の状態ごとに次の手順で移す。手で書くのは分類・依存・保留中の問い・旧 ID の注記だけで、計画は J2 に作り直させる。

| 旧側の状態 | 新しい側の手順 | 移した直後の状態 |
|---|---|---|
| 未分類 | 取り込み（`ingest`）で入る | 未分類 |
| 分類済 | 取り込み → `classify <C-ID> --priority <旧台帳の優先度>` → `edit --headline --context`（旧台帳の「一言で」「位置づけ」） | 分類済 |
| 計画承認待ち | 分類済と同じ → `plan <C-ID> --auto`（J2 が計画を作り直す。旧台帳のタスク案は `--context` に添えて J2 の入力に含める） | 計画承認待ち |
| 着手中 | 計画承認待ちと同じ → オーナーが新しい計画を承認する（§承認の状態の移し方） | 着手中 |
| 検証中・完了確認待ち | 移さない。最後の旧周で旧側の完了まで終える【決定 M5H1】 | — |
| 人間対応待ち | 保留に入る直前の状態が分類済・計画承認待ちなら分類済まで、着手中なら承認し直しの後の着手中まで上の手順で移す → `hold <C-ID> --question <未回答の問い>`（`hold` は計画承認待ちから入れない＝M1 T11。回答の後の戻り先は旧側の保留前の状態と一致しなくてよい） | 人間対応待ち |

- 取り込みで入れ直す課題は、M2 の取り込みが作り、エージェントが `create` で作り直さない（2026-10-25 の決定）[S2]

- 期待の一覧に無い旧 ID への依存のうち、旧側のアーカイブにも無いものがあれば、移行の作業を止めてオーナーへ上げる（旧 run-cycle の依存の fail-closed と同じ）[S2]
- 回答済みの問い・計画の旧版・承認と差し戻しの記録・委譲の記録は移さない（履歴は持ち込まない＝2026-10-25 の決定）[S2]
- 移行の作業の間、新しい側では `cycle` と ID を省いた個別の操作（`classify --auto`・`plan --auto`・`run`・`verify --auto`）を実行しない。省くと移し終えていない課題まで判断点と委譲が走る [S2]

### 旧 ID と新しい ID [S2]【決定 2026-10-29 親 M5P1】

スキーマも CLI も変えない。旧 ID と新しい ID の対応は、対応表と、新しい課題の「位置づけ」欄に書く注記で持つ。

- 対応表（`legacy/migration/id-map.tsv`。列 `legacy_id`・`challenge_id`）は使い捨てのスクリプトが作る。取り込みで入れ直した課題は、旧台帳の取り込み元マーカーの外部キー（`<name>#<番号>` に `sources.json` の owner を補ったもの）と、`show --json` の取り込み元の外部キーの一致で対応させる。`create` で作った課題は、作ったときにエージェントが行を足す [S2]
- 新しい課題の「位置づけ」欄（`edit --context`）は `旧 C-<n>` の 1 行に続けて旧台帳の「位置づけ」を書く（`edit --context` は欄を丸ごと置き換えるので 1 回で書く）。説明欄に書かないのは、取り込みが上流の本文の変化で説明を置き換える（M2 §冪等な作成と更新）ため【仮定】[S2]
- 新しい課題の ID は、旧側の続きから振る。手順は、`init` した空のストアを `export` し、その書き出しの `sequences` に `challenge` のキーを足して（空のストアには `challenge` の採番の行が無いため）旧側の最大の ID の番号（旧台帳とアーカイブを通した最大。2026-10-29 は 372）にし、Tom のワークスペースで `init` した直後の空のストアへ、取り込みより前に `import` する。空のストアの書き出しは `$TMPDIR` に `mktemp -d` で作った一時のワークスペース（`flywheel --workspace <一時> init` → `export`）で作る。ストアのファイルを直接書かずに済む（S1 の `import` が採番の状態を書き出しの値にするため）【仮定】[S2]
- 上の手順が使えないとき（S1 の `import` がこの書き出しを受け付けないなど）は、新しい課題の ID を `C-1` から振り直すことを受け入れる。その場合、同じ `C-n` が旧側のアーカイブの課題と新しい課題の 2 つを指すので、旧側の記憶・journal・Issue・`legacy/` にある ID は「旧 C-n」と読み、新しい側で旧 ID を書くときは常に `旧 C-n` と書く [S2]

## クリティカル設計決定

### 1. 承認の状態の移し方（セキュリティ）【決定 2026-10-29 オーナー M5H2】

- **採用案**: 旧側の計画の承認は移さず、J2 が作り直した計画をオーナーが通常の経路で承認し直す。`--relayed` は移行の対話でのオーナーの発言があるときだけ使う。
- **理由**: 人が登録した計画では委譲を起動できないので、承認済みの状態を移しても J2 の計画の作り直しと、その計画への承認が要る。旧台帳の印を写して新しい計画を承認済みにすると、オーナーが見ていない計画で委譲が始まる。Tom で承認し直す件数は 2 件で、手間は小さい。
- **代替案**: B: 移行のエージェントが旧台帳の承認の印と旧周の名前を会話の手がかりにして `approve --relayed` で記録する（オーナーの新しい発言なしに承認の記録を作ることになり、設計書 §9「オーナーの指示の無い承認を記録してはならない」に反する）／C: 本人確認の方式に `migrated` を足し、旧側の承認を写した記録として区別する（経路の登録簿と core の変更が要り、写した承認で J2 の新しい計画が委譲される問題は残る）。
- **影響範囲**: コードの変更なし（S2 の手順）。

### 2. 書き出しのコミット（ワークスペースの Git を core が触る）【決定 2026-10-29 親 M5P3】

- **採用案**: `cycle` の最後の段 `backup` が、書き出しと `memory_dir` だけをパス指定でコミットする。push しない。
- **理由**: D10 は書き出しの定期的なコミットを求めている。人の手に任せると、旧側で周ごとに自動で行っていたコミットが止まり、ストアが単一障害点になる。パスを閉じた集合に限るので、オーナーの未コミットの変更を巻き込まない。
- **代替案**: B: core は書き出しだけを書き、コミットは人か対話のセッションが行う（コミットが滞る）／C: `flywheel export --commit` を人が呼ぶ（B と同じく滞る）。
- **影響範囲**: `cycle` の段の閉集合（M3・M4.5）・core のコミットの IF・`internal/adapters/git`。

## 機能全体の設計

### アーキテクチャ決定

- `export`／`import` は core の 1 つのトランザクションで全表を読み書きする。`import` は、マイグレーションを最新まで当てたストアの表が空であることを確かめてから書く。
- `backup` は `cycle` の最後の段（`improve` の後）に置き、段がエラーで終わった周でも周の記録を閉じる前に実行する【仮定】。

### IF / API

#### CLI に足すもの【仮定: 名前】

| コマンド | 引数 | スライス |
|---|---|---|
| `export --out <path>` | 新しいコマンド | S1 |
| `import --in <path>` | 新しいコマンド | S1 |
| `cycle` の段 `backup` | 段の閉集合に足す | S1 |

`export --json` の成功の出力は `{"export": {"path", "schema_version"}}`、`import --json` の成功の出力は `{"import": {"path", "schema_version"}}` とする（`path` は書き出した・読み込んだファイルの絶対パス、`schema_version` は書き出しのスキーマの版）【仮定: キー名】。

#### 書き出しの形【仮定】

SQLite の値は、INTEGER を JSON の整数、REAL を数、TEXT を文字列、NULL を `null` へ写す（いまのスキーマに BLOB の列は無い。足すときにこの写像を決め直す）。最上位のキーは `schema_version`（整数）・`sequences`（`sqlite_sequence` の表の名前から値への対応）・`tables`（表の名前から行の配列への対応）の 3 つ。行は列の名前をキーにしたオブジェクトで、表ごとに主キーの昇順（主キーの列の宣言順での辞書的な昇順）に並べ（INTEGER の列は数の順、TEXT の列はバイト列の順。いまのスキーマの表はすべて主キーを持つ）、すべてのオブジェクトのキーを辞書順にする。`import` は `sequences` のキーを `tables` にある表の名前に限り、行が無い表のキーも受け付けて `sqlite_sequence` へ書く。値が整数でないか、その表の行の最大の ID より小さいときは読み込まない。書き出しは周の途中の状態（終わっていない `cycle` の行・`lock` の行）もそのまま含み、復旧の後の最初の `cycle` は既存の古い排他の回収（pid・host・heartbeat の判定）に任せる【仮定】。書き出しから戻した直後は、最後の heartbeat から最大 5 分（300 秒）は最初の `cycle` が `locked` になり、それを過ぎると前の周を `interrupted` で閉じて進む（同じホストで pid が再利用されていれば `locked` が続きうる）。コードは変えず、復旧は稀で待てば進むものとして扱う【決定 2026-10-30 オーナー】。run のディレクトリは書き出しに含まれないので、復旧の後の run の出力の保存先のパスは存在しないファイルを指しうる。

#### `backup` の段の JSON【仮定: キー名】

`cycle --json` の `phases` の最後の要素は `{"phase": "backup", "skipped": false, "result": {"outcome": <閉集合>, "commit": <SHA か null>, "detail": <文字列か null>}}` とする（`failed` と `ignored` は `detail` に理由を持つ）。`ignored` は「書き出しをコミットしなかった」ことを表し、記憶をコミットしたかは `commit` が `null` かどうかで読む。
