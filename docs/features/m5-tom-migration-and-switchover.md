## 概要

M5 は、いま旧 claude-flywheel の run-cycle で周を回している Tom（AI 開発ハーネスのエージェント）を新しい flywheel へ移し、旧 run-cycle を止める段である。全ワークスペースを一括では移さず、Tom を先に移して、問題が出たら直しながら進める（【決定 2026-10-18 オーナー】）。旧台帳の変換スクリプトは作らない。open の課題とその状態だけを移し、GitHub Issue 由来の課題は M2 の取り込みで入れ直し、残りはエージェントが手で移し、照らし合わせだけを機械で行う（【決定 2026-10-25 オーナー】）。

本仕様はこれを 4 つのスライスで満たす。S1 は移行の道具で、旧台帳の課題 ID を新しい課題に記録する口、新しい課題の ID を旧台帳の最大より後から振る口、旧台帳の一覧と新しいストアを突き合わせる読み取り専用のコマンド（`flywheel migrate verify`）を足す。S2 はストアの書き出しと再構築（`flywheel export`／`import`。D10）と、1 周の終わりに書き出しをワークスペースへコミットする段である。M1 が「実運用の前に必須」として S3 に置いたまま実装されていないので、切り替えの前に M5 で埋める。S3 は切り替えの実施で、旧側の最後の周で仕掛かりを片付け、旧 run-cycle を止め、宣言を書き移し、課題を移して照らし合わせが一致してから、新しい flywheel の最初の周を回す。S4 は旧 2 repo（claude-flywheel・claude-flywheel-board）のアーカイブである。

いちばん重い判断は承認の状態の移し方である（【要決定 Q2】）。人が手で登録した計画（`plan --file`）は構造化した中身を持たず委譲を起動できない【実コード確証 high: `internal/core/delegate.go` の `the challenge has no approved plan with a structured spec`】ので、旧側で計画を承認済みの課題も、新しい側では J2 に計画を作り直させ、オーナーが承認し直す形を推奨する。守る対象は「オーナーが承認していない計画で委譲が始まること」で、守る相手は移行を行うエージェント自身（旧台帳の印を読み違える・承認の記録を自分で作る）である。

- 移す量は少ない。2026-10-29 に旧 claude-flywheel 0.31.0 の `scripts/ledger-index.rb` で Tom の台帳を投影した結果は 3 件（分類済 1・着手中 2）で、3 件とも取り込み元マーカーを持つ（`ingested=y`）。手書きの課題は 0 件である【親が実行・実物確証 high】。同日の GitHub で、取り込み元の 4 リポジトリの open で masanami を assign した Issue も 3 件（claude-harness#331・flywheel#404・flywheel#176）で、台帳と一致する【実測 high: `gh issue list --assignee masanami`】。

## ユーザーストーリー

- オーナーとして、Tom を新しい flywheel へ移した日から、承認と状況の確認を新しいボードと対話だけで行いたい。旧台帳のチェックボックスと新しいボードの両方を見る日を作りたくない。
- オーナーとして、移した後の課題の一覧が旧台帳の open の課題と同じ件数・同じ状態であることを、エージェントの報告ではなく機械の突き合わせで確かめたい。
- オーナーとして、旧側で承認した計画が、新しい側で私の知らないうちに承認済みとして扱われないでほしい。
- オーナーとして、移した後に新しい flywheel で問題が出ても、ストアを失わず、直しながら進めたい。
- 移行を行うエージェントとして、旧台帳の `C-246` が新しいストアのどの課題かを、題名の照合ではなく記録された値で引きたい。

## 機能要件

用語: **旧台帳**＝Tom の `challenge-ledger.md`（open の課題だけを持つ）。**旧 ID**＝旧台帳の課題の ID（`C-246` など）。**期待の一覧**＝切り替えの時点で旧台帳を `ledger-index.rb` で投影した TSV（1 行目がヘッダ。列 `id`・`status`・`prio`・`deps` を使う）。**移す**＝期待の一覧の課題を新しいストアに、同じ状態・優先度・依存で置くこと。**旧側を止める**＝Tom のワークスペースで旧 run-cycle と adhoc が周を回せない状態にすること。**最後の旧周**＝旧側を止める直前に回す、仕掛かりを片付けるための旧 run-cycle の周。

各要件の末尾の `[S1]`〜`[S4]` は、その要件を実装・実施するスライスを表す（§スライス）。S3・S4 の受入基準は、そのスライスを実装対象にするときに §受入基準の末尾へ足す（M4H14・M45P1 の流儀）【要決定 Q14】。

### 旧 ID の記録 [S1]【要決定 Q9】

- [ ] 課題は旧 ID を 1 つ持てる（`legacy_id`。NULL 可）。`edit <C-ID> --legacy-id <値>` で記録する
- [ ] 旧 ID の値の形は `<英字 1 文字以上>-<正の整数>`（例 `C-246`）とし、それ以外は記録しない【仮定】
- [ ] 旧 ID は一度記録したら別の値へ変えられない（同じ値の再指定は何も変えずに成功する）【仮定】
- [ ] 旧 ID はストアの中で一意で、別の課題が持つ値は記録しない
- [ ] `show --json` と `list --json` の課題は `legacy_id` を持つ
- [ ] 旧 ID の記録は作業ログに残る（M1 の `edit` と同じ記録）
- [ ] `--legacy-id` は M1 の `edit` と同じ状態の制約に従い（完了の課題には `terminal_state`）、`edit` のほかのフラグと同時に指定できる【仮定】

### 新しい課題の ID の始まり [S1]【要決定 Q9】

- [ ] 新しいストアを作るときに、課題の ID を振り始める下限を指定できる（`init --id-floor <n>`）。最初に作る課題の ID は `C-<n+1>` になる
- [ ] 下限は、課題が 1 件も無いストアにだけ指定できる
- [ ] 下限は課題の表の採番の状態（SQLite の `sqlite_sequence` の `challenge` の行。無ければ作り、有れば上書き）に書き、別の設定の表を持たない。初期化済みで課題が 0 件のストアへの `init --id-floor` も同じく書く【仮定】。書き出しと再構築は採番の状態も移す（§書き出しと再構築）

理由: 旧側の記憶（`memory/harness/` の 226 ファイル）・journal・Issue・`CLAUDE.md` は `C-186` のような旧 ID で課題を指している。新しいストアが `C-1` から振ると、同じ `C-n` が旧側のアーカイブの課題と新しい課題の 2 つを指し、人と判断点が取り違える。

### 照らし合わせ（`flywheel migrate verify`）[S1]【要決定 Q10】

- [ ] `flywheel migrate verify --expected <path>` は、期待の一覧と新しいストアを突き合わせる。LLM も `gh` も呼ばず、ストアと作業ログを変えない
- [ ] 期待の一覧は TSV で、1 行目のヘッダから列 `id`・`status`（必須）と `prio`・`deps`（任意）を名前で探す。ほかの列は読まない（旧 claude-flywheel の版で列が増えても読める）
- [ ] `status` の値は、旧台帳の語彙の 8 値（`未分類`・`分類済`・`計画承認待ち`・`着手中`・`検証中`・`完了確認待ち`・`完了`・`人間対応待ち`）の表示名か、それに対応する英字のコード（`unclassified`・`classified`・`awaiting_plan_approval`・`in_progress`・`verifying`・`awaiting_completion_approval`・`done`・`awaiting_human`）を受け付ける。取り下げ（`withdrawn`）は旧台帳の語彙に無いので受け付けない
- [ ] `prio` の値は `P0 | P1 | P2`（新しい側と同じ閉集合）か空で、空の行は優先度を比べない
- [ ] `deps` の値はカンマ区切りの旧 ID で、前後の空白と順序を無視した集合として比べる。空は依存なし
- [ ] 同じ `id` の行が 2 つ以上ある一覧は読まない
- [ ] 突き合わせの鍵は旧 ID で、期待の一覧の `id` と課題の `legacy_id` が一致するものを同じ課題とみなす
- [ ] 結果は 6 つに分ける: 一致・新しいストアに無い（`missing`）・期待の一覧に無い終端でない課題（`unexpected`）・状態の違い・優先度の違い・依存の違い
- [ ] 期待の一覧の旧 ID を持つ課題は、終端（完了・取り下げ）でも同じ課題として突き合わせ、状態を比べる
- [ ] 課題の依存先が旧 ID を持たないときは、依存の違いの `actual` にその課題の ID（`C-<n>`）のまま示す
- [ ] 依存の比較は、期待の一覧にある旧 ID の間の依存だけを対象にし、一覧に無い旧 ID への依存（旧側で完了してアーカイブへ移った先行課題など）は「移さなかった依存」として別に示す
- [ ] 突き合わせを最後まで行えたときは、一致しないものがあっても成功（終了コード 0）とし、結果の `ok` を `false` にする。一致を条件にする手順（§切り替えの手順）は `ok` を見る（M1 の `status` が食い違いを示しても成功で終わるのと同じ扱い。エラーの封筒〔`code`・`message` だけ〕には突き合わせの結果を載せられない）【仮定】

旧台帳の形式（見出しの書式・承認のチェックボックス・取り込み元マーカー）を flywheel は知らない。投影は旧側の `ledger-index.rb` が行い、flywheel は列の名前で TSV を読むだけにする（flywheel は他の道具の固有の形を知らない設計にする＝オーナーの方針）。

### 書き出しと再構築（`flywheel export`／`import`）[S2]【決定 D10・M1 PD5 から導く】

- [ ] `flywheel export --out <path>` は、ストアの全状態を 1 つの JSON に書き出す。全状態とは、`sqlite_master` の表のうち名前が `sqlite_` で始まらないものすべての行と、スキーマの版（`PRAGMA user_version`）と、採番の状態（`sqlite_sequence` の行）である
- [ ] 同じ状態からの書き出しは、バイト単位で同じになる（行は表ごとに id の順、キーは辞書順）
- [ ] `flywheel import --in <path>` は、すべての表に行が無いストア（`init` の直後。`init --id-floor` の採番の状態だけを持つものを含む）へだけ書き出しを読み込み、採番の状態は書き出しの値で置き換える
- [ ] `import` は 1 つのトランザクションで書き、途中で失敗したら何も残さない
- [ ] 書き出し → 再構築 → 書き出しの往復で、2 つの書き出しが一致する（D10「往復で状態が一致することをテストで固定」）
- [ ] 書き出しはスキーマの版を持ち、版が違う書き出しは読み込まない【仮定】
- [ ] `export` は 1 つの読み取りのトランザクションで全表と採番の状態を読む。`import` の「すべての表に行が無い」の判定は、`export` と同じ表の集合に対して行う
- [ ] 書き出しは、委譲と判断点の出力の保存先（run のディレクトリ）の中のファイルを含まない。表の列にあるパスの値はそのまま書き出す【仮定】

### 書き出しのコミット [S2]【要決定 Q11】

- [ ] `flywheel cycle` の最後の段 `backup` は、書き出しをワークスペースの決まった場所（`.flywheel/export.json`【仮定】）へ書く
- [ ] `backup` の段は、周が排他を取った後なら、ほかの段の成否・予算による打ち切り・承認待ちでの停止にかかわらず実行する（排他を取れなかった周・宣言の検査で始まらなかった周では実行しない）。段がエラーで終わった周でも、周の記録を閉じる前に実行する【仮定】
- [ ] `backup` の段の結果は、周の成否にかかわらず作業ログ（`entity=cycle`・`action=backup`。`after` に `outcome`・`commit`・`detail`）に残す。周が正常に終わったときは `cycle --json` の `phases` にも出す（段がエラーで終わった周は `phases` を返さないため＝`internal/core/cycle_run.go`）【仮定】
- [ ] ワークスペースが Git の作業ツリーで、書き出しか記憶の置き場（`memory_dir`。宣言に無ければ書き出しだけ）に前のコミットからの差（`git status --porcelain -- <パス>` が空でない）があれば、その 2 つのパスだけをコミットする。手順は `git add -- <パス>` の後に `git commit --only -m <要約> -- <パス>` とし、ほかのファイルのステージの状態を変えない【仮定】
- [ ] コミットの要約は `chore(flywheel): backup <周の ID>` とする【仮定】
- [ ] 書き出しのパスが Git の除外の対象（`git check-ignore` が一致する）なら、書き出しをコミットせず、`outcome` を `ignored` にする。このときも `memory_dir` に差があれば `memory_dir` だけをコミットし、`commit` にその SHA を入れる（記憶のコミットは M45P7 から引き継いだ別の目的のため）【仮定】
- [ ] `backup` の段は push しない
- [ ] 段の結果は `outcome` で示し、`committed`（コミットした）・`unchanged`（差が無い）・`not_git`（Git の作業ツリーでない）・`ignored`（書き出しのパスが除外の対象）・`failed`（書き出しかコミットに失敗した）の閉集合とする【仮定: 名前】
- [ ] `backup` の段の `failed` は、`cycle` の終了コードとほかの段の結果を変えない【仮定】

理由: ストアは Git で追跡しない（D10）ので、書き出しのコミットが無いとストアが単一障害点になる。旧側では run-cycle の手順 6 が台帳・journal・記憶をパス指定でコミットしていた（push はしない。Tom の `main` は 2026-10-29 に origin より 5 コミット先にある）。周の途中で止まった周でもストアは変わっているので、止まった周ほど書き出しが要る。

## クリティカル設計決定

### 1. 承認の状態の移し方（セキュリティ）【要決定 Q2】

- **採用案（推奨）**: A。旧側の計画の承認は移さず、J2 が作り直した計画をオーナーが通常の経路で承認し直す。`--relayed` は移行の対話でのオーナーの発言があるときだけ使う。
- **理由**: 人が登録した計画では委譲を起動できないので、承認済みの状態を移しても J2 の計画の作り直しと、その計画への承認が要る。旧台帳の印を写して新しい計画を承認済みにすると、オーナーが見ていない計画で委譲が始まる。Tom で承認し直す件数は 2 件で、手間は小さい。
- **代替案**: B: 移行のエージェントが旧台帳の承認の印と旧周の名前を会話の手がかりにして `approve --relayed` で記録する（オーナーの新しい発言なしに承認の記録を作ることになり、設計書 §9「オーナーの指示の無い承認を記録してはならない」に反する）／C: 本人確認の方式に `migrated` を足し、旧側の承認を写した記録として区別する（経路の登録簿と core の変更が要り、写した承認で J2 の新しい計画が委譲される問題は残る）。
- **影響範囲**: コードの変更なし（S3 の手順）。

### 2. 旧 ID の記録と ID の下限（DB スキーマ変更）【要決定 Q9】

- **採用案（推奨）**: A。マイグレーション `0013` で `challenge.legacy_id`（TEXT・NULL 可・NULL でない値は一意）を足し、`init --id-floor` は課題の ID の採番の始まりを下限の次にする。
- **理由**: 照らし合わせを題名の照合にせず、記録した値で決定的に行える。下限は、旧 ID と新しい ID が同じ `C-n` で別の課題を指すことを防ぐ。
- **代替案**: B: 旧 ID だけを足し、新しい ID は `C-1` から振る（旧側の記憶・Issue の `C-n` と取り違える）／C: スキーマを変えず、取り込みで入れ直す課題は外部キー（`owner/name#番号`）で、手書きの課題は題名で突き合わせる（手書きの課題が来ると決定的でなくなる。他のワークスペースは手書きの課題を持ちうる）。
- **影響範囲**: `challenge` の列・`edit`・`show`／`list` の JSON・`internal/view` の型・`web/src/api/types.gen.ts`。

### 3. 書き出しのコミット（ワークスペースの Git を core が触る）【要決定 Q11】

- **採用案（推奨）**: A。`cycle` の最後の段 `backup` が、書き出しと `memory_dir` だけをパス指定でコミットする。push しない。
- **理由**: D10 は書き出しの定期的なコミットを求めている。人の手に任せると、旧側で周ごとに自動で行っていたコミットが止まり、ストアが単一障害点になる。パスを閉じた集合に限るので、オーナーの未コミットの変更を巻き込まない。
- **代替案**: B: core は書き出しだけを書き、コミットは人か対話のセッションが行う（コミットが滞る）／C: `flywheel export --commit` を人が呼ぶ（B と同じく滞る）。
- **影響範囲**: `cycle` の段の閉集合（M3・M4.5）・`internal/adapters/git` の IF。

## 機能全体の設計

### アーキテクチャ決定

- `migrate verify` は core の読み取りの関数（課題・旧 ID・依存を読む）と CLI の TSV の解析に分ける。TSV の解析と状態の表示名の解決は CLI、突き合わせの規則は core に置く【仮定】。
- `export`／`import` は core の 1 つのトランザクションで全表を読み書きする。`import` はマイグレーションを最新まで当てた空のストアへ書く。
- `backup` は `cycle` の最後の段（`improve` の後）に置く【仮定】。

### IF / API

#### CLI に足すもの【仮定: 名前】

| コマンド | 引数 | スライス |
|---|---|---|
| `edit <C-ID> --legacy-id <値>` | 既存の `edit` にフラグを足す | S1 |
| `init --id-floor <n>` | 既存の `init` にフラグを足す | S1 |
| `migrate verify --expected <path>` | 新しいコマンド | S1 |
| `export --out <path>` / `import --in <path>` | 新しいコマンド | S2 |

#### `migrate verify --json` の成功時の形【仮定】

```json
{
  "dropped_dependencies": [{"from": "C-246", "to": "C-245"}],
  "matched": ["C-246", "C-370", "C-372"],
  "mismatches": {
    "dependency": [{"legacy_id": "C-1", "expected": ["C-2"], "actual": []}],
    "missing": ["C-9"],
    "priority": [{"legacy_id": "C-1", "expected": "P1", "actual": "P2"}],
    "status": [{"legacy_id": "C-1", "expected": "in_progress", "actual": "awaiting_plan_approval"}],
    "unexpected": ["C-380"]
  },
  "ok": true
}
```

- `unexpected` は新しいストアの課題 ID、それ以外は旧 ID で示す。一致しないものがあれば `ok: false` で、終了コードは 0（§照らし合わせ）。`mismatches` の 5 つのキーは常に配列で持つ（空でも省かない）。
- テキスト出力は、一致しないものを種類ごとに 1 行ずつ（旧 ID か課題 ID と、期待と実物）示し、最後に `ok` を示す【仮定】。
- 期待の一覧が読めない（パスが無い・読めない）ときは `plan --file` と同じエラー（無い: `usage_error`。読めない: `internal_error`）で終わる【仮定】。
- 配列はすべて、ID の数値の部分の昇順に並べる（`dropped_dependencies` は `from`、次に `to` の順）。テキスト出力にも `dropped_dependencies` を示す【仮定】。

#### 書き出しの形【仮定】

SQLite の値は、INTEGER を JSON の整数、REAL を数、TEXT を文字列、NULL を `null` へ写す（いまのスキーマに BLOB の列は無い。足すときにこの写像を決め直す）。並べ順の「主キーの昇順」は、主キーの列の宣言順での辞書的な昇順とする。最上位のキーは `schema_version`（整数）・`sequences`（`sqlite_sequence` の表の名前から値への対応）・`tables`（表の名前から行の配列への対応）の 3 つ。行は列の名前をキーにしたオブジェクトで、表ごとに主キーの昇順に並べ、すべてのオブジェクトのキーを辞書順にする。

#### `backup` の段の JSON

`cycle --json` の `phases` の最後の要素は `{"phase": "backup", "skipped": false, "result": {"outcome": <閉集合>, "commit": <SHA か null>, "detail": <文字列か null>}}` とする（`failed` と `ignored` は `detail` に理由を持つ）【仮定: キー名】。
