# core の見直し 区切り S3d（画面: 完了の承認・タスクの詳細）

## 概要

core の見直し（`docs/features/core-redesign.md`）の区切り S3d。区切り S3b（複数のタスクと統合先）で core に入った値を、画面に出す。

- 完了の承認の画面を作る（課題の単位の確かめの結果・反映するもの・タスク・フォローアップを 1 画面で見る）。
- タスクの詳細に、委譲先の実行の状態・成果物・委譲先が値で返したこと・タスクの検証の結果・枠と使った額を出す。
- タスクのツリーに、タスクと課題の、細かい進み（検証を待っている・統合先へ入れている・反映先へ上げている・全体を確かめている）を出す。
- 区切り S2c の画面で、仕様に残した 5 点（flywheel#840）を決めて直す。

この文書は、S3c（`core-redesign.md` の実装対象）と並べて進めるために、別の文書にしてある（オーナーの決定 2026-11-21）。S3d を main に入れるときに、`core-redesign.md` へ畳む。

## 背景・目的

S3b で、計画がタスクを分けた課題が進むようになった。画面は S2c のままで、次が見えない。

- 完了の承認は、課題の詳細の中の小さな区画で受けている。課題の単位の確かめの結果と、反映先に何が入るかを、承認の前に 1 か所で読めない（`ux.md` の決定 17）。
- タスクの詳細に、委譲先がいま何をしているか・何を作ったか・検証がどう判定したかが出ない（`ux.md` の決定 14）。API にも出ていない。
- タスクのツリーの箱は、検証を待っているタスクも、統合先へ入れているタスクも、「走っている」の 1 つに見える。全部のタスクが済んだ後、反映先へ上げている間は、何も走っていないように見える。
- タスクの枠と使った額は、S3b で API に足したが、画面が使っていない。

## ユーザーストーリー

オーナーとして、完了の承認を求められたとき、1 つの画面で、全体を確かめた結果・反映先に入るもの・残っているフォローアップを読んで、承認するかを決めたい。走っている課題では、タスクごとに、委譲先がいまどの状態か・何を作ったか・検証がどう判定したか・いくら使ったかを、端末を開かずに見たい。

## 機能要件

語は `docs/glossary.md` に合わせる。画面に、開発に固有の語（PR・CI・ブランチ・マージ・Issue）を出さない決まり（S2c）は変えない。画面のボタンで受ける書き込みは、S2c のまま（計画の承認・反映を保留にした完了の承認・サイクルを回す）で、広げない。

### 完了の承認の画面

- [ ] 行き先 `approve_completion`（URL のハッシュ。課題の ID を持つ）を足す。完了の承認待ちの課題について、完了の承認の画面を出す。
- [ ] 「いま進められること」の、完了の承認待ちの行は、この画面へ行く（S2c は、課題の詳細へ行っていた）。
- [ ] 課題の詳細の「あなたを待っているもの」の、完了の承認の区画は、要約とボタンを外し、この画面へのリンクにする。
- [ ] 画面は、承認の要約の API（`GET …/challenges/{id}/approval`）と、課題の詳細の API（`GET …/challenges/{id}`）を読む。
- [ ] 左の列に、上から次を出す。
  - 確かめの結果: 「完了したら見えるもの」と、確かめた実物の対（`pairs`）。反映の後に確かめる条件（`conditions_after_release`）があれば、その一覧。
  - 反映するもの: 反映の操作ごとに、要約・成果物へのリンク・いまの中身の識別（`releases[]`）。統合先を使う課題では、統合先の識別（`challenge.integration_ref`）。同時には承認されない、ほかの不可逆操作（`other_pending_operations`）。
  - タスク: タスクごとに、題名・状態・使った額と枠（`tasks[]`）。題名は、タスクの詳細へのリンク。
  - フォローアップ: 未のフォローアップの件数と題名（`followups[]`）。0 件なら「未のフォローアップはありません」。未が残っていても、承認のボタンは出す。
- [ ] 右の列に、承認の操作を出す。ボタン「完了を承認する（反映は保留）」と、反映まで承認するときの案内（端末のコマンドと、対話で伝える方法）。ボタンの動き（版と CSRF の値を送る・食い違いのときは読み直して送り直さない）は、S2c の区画のまま。
- [ ] 承認の要約が、完了の承認待ちでない（計画の承認待ち・待っていない）ときは、ボタンを出さず、その旨と、課題の詳細へのリンクを出す。
- [ ] 承認した後は、承認を記録した旨と、反映先へ入れる承認は端末か対話から行う旨を出す（`ux.md` のシナリオ 11）。
- [ ] 差し戻しのボタンは置かない（`ux.md` の決定 26）。差し戻しの案内（端末のコマンドと、対話で伝える方法）を出す。

### タスクの詳細

課題の詳細の API の `tasks[]` の要素に、次のキーを足す（core が、契約の実行・成果物・作業ログから組み立てる）。

- [ ] `delegate`: そのタスクの、最後の契約の実行の状態。`state`（`running`・`waiting`・`succeeded`・`failed`・`cancelled`）・`summary`（委譲先が返した要約）・`requested_kind`（委譲先が求めていること。無ければ `null`）・`run_id`。契約の実行が無いタスクは `null`。
- [ ] `artifacts`: そのタスクの、成果物を持つ最後の実行の成果物の配列。要素は `kind`・`ref`・`state`・`role`（`integration` か `null`）。無ければ空の配列。
- [ ] `facts`: そのタスクの、最後の契約の実行が値で返したこと（名前から値への対応）。無ければ空の対応。
- [ ] `verification`: そのタスクの、最後のタスクの検証の結果。`verdict`（満たした・満たしていない・判断できないの値）・`reason`・`at`。まだ無ければ `null`。
- [ ] `landing`: 統合先へ入れる進み。`verified`（検証を通って、「入れてよい」を返す前）・`sent`（「入れてよい」を返して、入るのを待っている）・`landed`（統合先へ入った）。統合先を使わない課題のタスクと、まだ検証を通っていないタスクは `null`。

タスクの詳細の画面に、次を足す。

- [ ] 「委譲先の実行」の区画: 状態（語に直す）・委譲先が返した要約・委譲先が求めていること（あれば）。
- [ ] 「成果物」の区画: 成果物ごとに、種類・リンク・状態。統合先の印がある成果物は、統合先のものと分かる語を添える。
- [ ] 「委譲先が値で返したこと」の区画: 名前と値の一覧（自己レビューを実行したか、など）。無ければ区画を出さない。
- [ ] 「検証」の区画: タスクの検証の判定と理由、判定した時刻。統合先を使う課題では、統合先へ入れる進み（`landing`）を語で出す。
- [ ] 「費用」に、タスクの枠（実装とレビュー対応）と、使った額を出す。
- [ ] 課題の詳細の API の `runs[]` の上限を、20 件から 100 件に上げる（タスクが多い課題で、タスクの詳細の実行の記録が欠けないようにする）。

### タスクのツリー

- [ ] ツリーの API の `tasks[]` の要素に、`progress` を足す。表示の区分（`phase`）が `running` のタスクの、細かい進み。値は、`working`（委譲先が進めている）・`verifying`（検証を待っている）・`landing`（検証を通って、統合先へ入れている）。`phase` が `running` でないタスクは `null`。`phase` の値の集合は変えない。
- [ ] ツリーの API の課題の要素に、`progress` を足す。値は、`reflecting`（全部のタスクが済み、反映先へ上げる依頼が走っている）・`checking`（課題の単位の確かめを待っている）。どちらでもなければ `null`。
- [ ] 値は core が決める（画面は、状態から導かない。S2c の「表示の区分と件数を core が決める」と同じ）。値の集合は、`internal/view` の閉集合に足し、画面の語の表（`labels.ts`）に、対応する語を足す。
- [ ] ツリーの箱に、`progress` の語を出す（「検証を待っている」「統合先へ入れている」）。課題の枠の見出しに、課題の `progress` の語を出す（「反映先へ上げている」「全体を確かめている」）。
- [ ] 課題の詳細のツリーにも、同じ語を出す。

### S2c の画面で仕様に残した点（flywheel#840）

- [ ] 経緯で、不可逆操作の 1 つの出来事（承認・差し戻し）が 2 行になる点: 画面で 1 行にまとめる。不可逆操作の側の記録の行を出さず、課題の側の行に、操作の種類の語を添える。作業ログの記録は変えない。
- [ ] 関係する課題の、満たされていない前提の語「未完了」: 「まだ満たされていない」に改める。前提の課題の状態の語は、いまのまま並べる。
- [ ] タスクの前提に、その課題に無いタスクが書かれているとき: 計画の出力の検査で断る（計画を作る判断点の出力が、同じ計画に無いタスクの鍵を前提に書いていたら、出力の誤りとして扱う。すでに断っていれば、その試験を足すだけ）。画面は変えない。
- [ ] 課題の詳細の、不可逆操作の区画の語: 種類（`release`・`delete`・`external_send`・`other`）と状態（`pending`・`approved`・`rejected`・`executed`・`closed`）を、語の表で語に直して出す（反映・削除・外部への送信・その他／承認待ち・承認済み・差し戻した・実行した・閉じた）。完了の承認の画面の、ほかの不可逆操作の行も同じ。
- [ ] 計画の承認の画面の、差し戻しの案内: 端末のコマンドに加えて、対話で伝える方法の注記（`guidance.json` の `conversation_note`）を出す。

## クリティカル設計決定

### 画面のボタンで受ける範囲を広げない（S3d）

- **採用案**: 完了の承認の画面のボタンは、S2c の区画と同じ口（反映を保留にした完了の承認）だけを使う。反映まで承認する・差し戻す・問いに答えるは、端末か対話に寄せる。
- **理由**: 設計書 §9 の承認の経路の決まり（画面の口には、委譲の子からも届きうる）。広げるのは、対話の欄と一緒に、S4 で決める（`ux.md` の未決）。
- **影響範囲**: 画面の横断の試験（送る要求は、GET と、承認・サイクルの POST だけ）は、そのまま通す。

### 外へ出す値: 委譲先が返した要約と値を、画面に出す（S3d）

- **採用案**: 委譲先が返した要約（`summary`）・値（`facts`）・成果物の識別を、課題の詳細の API に足す。値は、core が記録したものをそのまま返し、画面は、文字として出す（Markdown として整えない。リンクにするのは、成果物の識別のうち、http か https のものだけ。S2c の、安全なリンクの決まりを使う）。
- **理由**: 委譲先の出力は、flywheel の外で作られた文字。画面で解釈すると、意図しない表示やリンクになりうる。
- **影響範囲**: `internal/view`・`web/src/task`。API は、`127.0.0.1` だけで待ち受ける決まりのまま。

### 細かい進みは、表示の区分と別のキーにする（S3d）

- **採用案**: タスクの表示の区分（`phase`。6 値）は変えず、別のキー `progress` を足す。
- **理由**: 表示の区分は、箱の色と件数（走っている・あなたを待っている・次に走る など）の決まりに使っている。値を足すと、件数の数え方と、画面の全部の分けが変わる。
- **代替案**: `phase` に値を足す。上の理由で採らない。タスクの状態（`status`）に値を足す。`core-redesign.md` の決定で、採らないと決めている。

## 機能全体の設計

### 実装計画（チケット分解の見通し）

分け方の案（最終の分解は `/create-ticket` で行う）。

1. API: タスクの要素の 5 つのキー、`runs[]` の上限、型の生成、偽のデータの追従。
2. API: ツリーの `progress`（タスクと課題）、閉集合、語の表。
3. 画面: 完了の承認の画面（行き先・画面・「いま進められること」と課題の詳細からの入口）。
4. 画面: タスクの詳細（委譲先の実行・成果物・値で返したこと・検証・費用）。
5. 画面: ツリーの `progress` の語（課題の画面と、課題の詳細）。
6. flywheel#840 の 5 点。
7. S3c の値を画面に出す（通した衝突の解消の一覧を、完了の承認の画面と課題の詳細に。確かめを待っている旨を、タスクの詳細に）。S3c が main に入り、統合ブランチへ取り込んだ後に行う。
8. 文書。

順は、1・2 → 3・4・5（並行にできる）→ 6 → 7 → 8。

## やらないこと

- 委譲先の実行が「いまいる段」の並びを出すこと（理由: 契約の出力に、段の値が無い。委譲先との契約と claude-harness の側の拡張が要る。要るときに、別の Issue にする）
- 完了の検証の、条件ごとの判定と件数を出すこと（理由: 判断点の出力に無い）
- 意思決定の記録、スーパーバイザーが答えた問いと打った手、計画の後に足したタスクの印、対話の欄（理由: S4）
- 画面のボタンで受ける範囲を広げること（反映まで承認する・差し戻す・問いに答える・取り込む・サイクルを止める）（理由: S4。上の「クリティカル設計決定」）
- 承認の要約の API を変えること（理由: 画面が、課題の詳細の API と合わせて読めば足りる）
- 前提が満たされていない理由（反映がまだ・前提が循環している）を、API に足して画面に出すこと（理由: 語を改めるだけにする。要るときに足す）
- 承認の後に反映先が動いたときの、変わり方（取り込みだけ・衝突の解消あり）を、画面に出すこと（理由: 通した衝突の解消の一覧までにする。S3c の値）
- ストアの形を変えること（理由: 読むだけで足りる）
- S2c の画面の掃除の残り・API の読み取りの直し・読み直しの直し・フォローアップの数え方（理由: flywheel#836〜#839。別の Issue）
- 手触りと見た目の作り込み（理由: S5 より後。オーナーの決定 2026-11-20）

## 受入基準

特に断らない限り、API は、実ストアを使う Go のテストで、画面は、偽の API を使う Vitest のテストで確かめる。ブラウザの試験（Playwright）で確かめるものは、その旨を書く。

### 完了の承認の画面

- [ ] 行き先のハッシュが `approve_completion` と課題の ID のとき、完了の承認の画面が出る。
- [ ] 「いま進められること」の、完了の承認待ちの行のリンク先は、その課題の完了の承認の画面である。
- [ ] 課題の詳細の「あなたを待っているもの」に、完了の承認の画面へのリンクがある。
- [ ] 課題の詳細の「あなたを待っているもの」に、完了を承認するボタンは無い。
- [ ] 画面に、「完了したら見えるもの」と、確かめた実物の対が、`pairs` の件数だけ出る。
- [ ] 反映の後に確かめる条件があるとき、画面に、その条件が出る。
- [ ] 画面に、反映の操作ごとに、要約と、成果物へのリンクが出る。
- [ ] 統合先を使う課題のとき、画面に、統合先の識別が出る。
- [ ] 統合先を使わない課題のとき、画面に、統合先の行が出ない。
- [ ] 同時には承認されない不可逆操作があるとき、画面に、その操作が出る。
- [ ] 画面に、タスクごとに、題名と状態の語が出る。
- [ ] 画面に、タスクごとに、使った額と枠が出る。
- [ ] タスクの題名は、そのタスクの詳細へのリンクである。
- [ ] 未のフォローアップがあるとき、画面に、その件数と題名が出る。
- [ ] 未のフォローアップが 0 件のとき、画面に「未のフォローアップはありません」が出る。
- [ ] 未のフォローアップがあっても、承認のボタンが出る。
- [ ] 完了の承認の画面でボタンを押すと、`POST …/approve` が、読んだ版を付けて 1 回送られる。
- [ ] 承認が成功すると、承認を記録した旨が出る。
- [ ] 承認が成功すると、反映先へ入れる承認は端末か対話から行う旨が出る。
- [ ] 承認の応答が、版の食い違いのとき、要約を読み直し、承認の要求は送り直されない。
- [ ] 承認の要約が、完了の承認待ちでないとき、ボタンが出ない。
- [ ] そのとき、課題の詳細へのリンクが出る。
- [ ] 画面に、差し戻しのボタンは無い。
- [ ] 画面に、差し戻しの案内として、端末のコマンドが出る。
- [ ] 画面に、差し戻しの案内として、対話で伝える方法の注記が出る。
- [ ] 画面が送る要求は、GET と、`…/approve` の POST だけである。
- [ ] ブラウザの試験で、「いま進められること」から、完了の承認の画面を開き、ボタンを押して、承認を記録した旨が出る。

### タスクの詳細の API

- [ ] 契約の実行があるタスクの `delegate.state` は、最後の契約の実行の状態である。
- [ ] そのタスクの `delegate.summary` は、委譲先が返した要約である。
- [ ] 委譲先が求めていることがあるとき、`delegate.requested_kind` は、その値である。
- [ ] 委譲先が求めていることが無いとき、`delegate.requested_kind` は `null` である。
- [ ] 契約の実行が無いタスクの `delegate` は `null` である。
- [ ] 成果物を持つ実行があるタスクの `artifacts` は、成果物を持つ最後の実行の成果物である。
- [ ] 統合先の印がある成果物の要素の `role` は `integration` である。
- [ ] 印が無い成果物の要素の `role` は `null` である。
- [ ] 成果物が無いタスクの `artifacts` は、空の配列である。
- [ ] 委譲先が値を返したタスクの `facts` は、その名前と値である。
- [ ] 値を返していないタスクの `facts` は、空の対応である。
- [ ] タスクの検証が済んだタスクの `verification.verdict` は、最後の検証の判定である。
- [ ] そのタスクの `verification.reason` は、その検証の理由である。
- [ ] 検証がまだ無いタスクの `verification` は `null` である。
- [ ] 統合先を使う課題で、検証した中身があり、「入れてよい」を返していないタスクの `landing` は `verified` である。
- [ ] 「入れてよい」を返して、入るのを待っているタスクの `landing` は `sent` である。
- [ ] 統合先へ入って済みになったタスクの `landing` は `landed` である。
- [ ] 統合先を使わない課題のタスクの `landing` は `null` である。
- [ ] `flywheel show <課題の ID> --json` の `tasks[]` は、課題の詳細の API と同じキーを持つ。
- [ ] 実行が 21 件ある課題の、課題の詳細の API の `runs[]` は、21 件である。
- [ ] 実行が 101 件ある課題の `runs[]` は、新しい順の 100 件である。

### タスクの詳細の画面

- [ ] `delegate` があるタスクの詳細に、委譲先の実行の状態の語が出る。
- [ ] そのとき、委譲先が返した要約が出る。
- [ ] `delegate` が `null` のタスクの詳細に、「委譲先の実行」の区画は出ない。
- [ ] 成果物があるタスクの詳細に、成果物ごとに、種類とリンクが出る。
- [ ] 成果物の識別が http でも https でもないとき、リンクにならず、文字で出る。
- [ ] 統合先の印がある成果物に、統合先のものと分かる語が出る。
- [ ] `facts` があるタスクの詳細に、名前と値が出る。
- [ ] `facts` が空のタスクの詳細に、「委譲先が値で返したこと」の区画は出ない。
- [ ] `verification` があるタスクの詳細に、判定の語と理由が出る。
- [ ] `landing` が `sent` のタスクの詳細に、統合先へ入れている旨の語が出る。
- [ ] タスクの詳細の「費用」に、枠（実装とレビュー対応）が出る。
- [ ] タスクの詳細の「費用」に、使った額が出る。
- [ ] 委譲先が返した要約に Markdown の記法があっても、整えられず、文字のまま出る。

### タスクのツリー

- [ ] 着手中で、委譲先が進めているタスクの `progress` は `working` である。
- [ ] 検証中で、検証した中身が無いタスクの `progress` は `verifying` である。
- [ ] 検証中で、検証した中身があるタスクの `progress` は `landing` である。
- [ ] `phase` が `running` でないタスクの `progress` は `null` である。
- [ ] `progress` を足しても、タスクの `phase` の値は、S3b と同じである（検証中のタスクは `running`）。
- [ ] 全部のタスクが済み、上げる依頼の、終わっていない契約の実行がある課題の `progress` は `reflecting` である。
- [ ] 課題の状態が検証中で、統合先を使う課題の `progress` は `checking` である。
- [ ] どちらでもない課題の `progress` は `null` である。
- [ ] 課題の画面のツリーで、`progress` が `verifying` の箱に、「検証を待っている」が出る。
- [ ] `progress` が `landing` の箱に、「統合先へ入れている」が出る。
- [ ] 課題の `progress` が `reflecting` のとき、課題の枠の見出しに、「反映先へ上げている」が出る。
- [ ] 課題の `progress` が `checking` のとき、課題の枠の見出しに、「全体を確かめている」が出る。
- [ ] 課題の詳細のツリーの箱にも、`progress` の語が出る。
- [ ] 語の表に、`progress` の値の全部（タスクの 3 つ・課題の 2 つ）の語がある。

### S2c の画面で仕様に残した点

- [ ] 経緯に、不可逆操作の承認が 1 件あるとき、その出来事の行は 1 行である。
- [ ] その行に、操作の種類の語がある。
- [ ] 経緯に、不可逆操作の差し戻しが 1 件あるとき、その出来事の行は 1 行である。
- [ ] 関係する課題の、満たされていない前提に、「まだ満たされていない」が出る。
- [ ] 画面に、「未完了」の語は出ない。
- [ ] 計画の出力で、タスクの前提に、同じ計画に無い鍵が書かれているとき、その出力は、誤りとして扱われる（計画は記録されない）。
- [ ] 課題の詳細の、不可逆操作の区画に、種類の語（`release` なら「反映」）が出る。
- [ ] 課題の詳細の、不可逆操作の区画に、状態の語（`closed` なら「閉じた」）が出る。
- [ ] 課題の詳細の、不可逆操作の区画に、種類と状態の内部の値（`release`・`closed`）は出ない。
- [ ] 語の表に、不可逆操作の種類の値の全部の語がある。
- [ ] 語の表に、不可逆操作の状態の値の全部の語がある。
- [ ] 計画の承認の画面の、差し戻しの案内に、対話で伝える方法の注記が出る。

### S3c の値を画面に出す
