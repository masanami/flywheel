# core の見直し 区切り S3d（画面: 完了の承認・タスクの詳細）

## 概要

core の見直し（`docs/features/core-redesign.md`）の区切り S3d。区切り S3b（複数のタスクと統合先）で core に入った値を、画面に出す。

- 完了承認画面を作る（課題の単位の確かめの結果・反映するもの・タスク・フォローアップを 1 画面で見る）。
- タスクの詳細に、委譲先の実行の状態・成果物・委譲先が値で返したこと・タスクの検証の結果・枠と使った額を出す。
- タスクのツリーに、タスクと課題の、細かい進み（作業中・検証待ち・検証済み・統合中／反映中・全体の確認中）を出す。
- 区切り S2c の画面で、仕様に残した 5 点（flywheel#840）を決めて直す。

この文書は、S3c（`core-redesign.md` の実装対象）と並べて進めるために、別の文書にしてある（オーナーの決定 2026-11-21）。S3d を main に入れるときに、`core-redesign.md` へ畳む。

## 背景・目的

S3b で、計画がタスクを分けた課題が進むようになった。画面は S2c のままで、次が見えない。

- 完了の承認は、課題の詳細の中の小さな区画で受けている。課題の単位の確かめの結果と、反映先に何が入るかを、承認の前に 1 か所で読めない（`ux.md` の決定 17）。
- タスクの詳細に、委譲先がいま何をしているか・何を作ったか・検証がどう判定したかが出ない（`ux.md` の決定 14）。API にも出ていない。
- タスクのツリーの箱は、検証を待っているタスクも、統合先へ入れているタスクも、「走っている」の 1 つに見える。全部のタスクが済んだ後、反映先へ上げている間は、何も走っていないように見える。
- タスクの枠と使った額は、S3b で API に足したが、画面が使っていない。

## ユーザーストーリー

オーナーとして、完了の承認を求められたとき、1 つの画面で、全体を確かめた結果・反映先に入るもの・残っているフォローアップを読んで、承認するかを決めたい。走っている課題では、タスクごとに、委譲先がいまどの状態か・何を作ったか・検証がどう判定したか・いくら使ったかを、ターミナルを開かずに見たい。

## 機能要件

語は `docs/glossary.md` に合わせる。画面に、開発に固有の語（PR・CI・ブランチ・マージ・Issue）を出さない決まり（S2c）は変えない。画面のボタンで受ける書き込みは、S2c のまま（計画の承認・反映を保留にした完了の承認・サイクルを回す）で、広げない。

### 完了承認画面

- [ ] 行き先 `approve_completion`（URL のハッシュ。課題の ID を持つ）を足す。完了の承認待ちの課題について、完了承認画面を出す。
- [ ] 「いま進められること」の、完了の承認待ちの行は、この画面へ行く（S2c は、課題の詳細へ行っていた）。
- [ ] 課題の詳細の「あなたを待っているもの」の、完了の承認の区画は、要約とボタンを外し、この画面へのリンクにする。
- [ ] 画面は、承認の要約の API（`GET …/challenges/{id}/approval`）と、課題の詳細の API（`GET …/challenges/{id}`）を読む。
- [ ] 左の列に、上から次を出す。
  - 確かめの結果: 「完了したら見えるもの」と、確かめた実物の対（`pairs`）。反映の後に確かめる条件（`conditions_after_release`）があれば、その一覧。
  - 反映するもの: 反映の操作ごとに、要約・成果物へのリンク・いまの中身の識別（`releases[]`）。統合先を使う課題では、統合先の識別（`challenge.integration_ref`）。同時には承認されない、ほかの不可逆操作（`other_pending_operations`）。
  - タスク: タスクごとに、題名・状態・使った額と枠（`tasks[]`）。題名は、タスクの詳細へのリンク。計画を作り直した課題では、前の版の計画の済みのタスクだけを並べ（未完・取りやめのタスクは並べない）、その題名はリンクにしない（タスクの詳細の画面は、最新の版のタスクだけを開けるため）。
  - フォローアップ: 未のフォローアップの件数と題名（`followups[]`）。0 件なら「未のフォローアップはありません」。未が残っていても、承認のボタンは出す。
- [ ] 右の列に、承認の操作を出す。ボタン「完了を承認する」と、その下に、このボタンは完了だけを記録し、反映先へ入れる承認は対話で行う旨の 1 行。反映まで承認するときの案内は、対話で伝える方法だけを出す（コマンドの例は出さない）。ボタンの動き（版と CSRF の値を送る・食い違いのときは読み直して送り直さない）は、S2c の区画のまま。
- [ ] 承認の要約が、完了の承認待ちでない（計画の承認待ち・待っていない）ときは、ボタンを出さず、その旨と、課題の詳細へのリンクを出す。
- [ ] 承認した後は、承認を記録した旨と、反映先へ入れる承認は対話で行う旨を出す（`ux.md` のシナリオ 11）。
- [ ] 差し戻しのボタンは置かない（`ux.md` の決定 26）。差し戻しの案内は、対話で伝える方法だけを出す（コマンドの例は出さない）。
- [ ] S2c の、課題の詳細の区画に対する試験（ボタン・要約・送る要求）は、完了承認画面の試験へ移す。画面の横断の試験（送る要求の種類・開発に固有の語が無いこと）の対象に、この画面を足す。

### タスクの詳細

課題の詳細の API の `tasks[]` の要素に、次のキーを足す（core が、契約の実行・成果物・作業ログから組み立てる）。「最後の契約の実行」は、そのタスクの契約の実行（`contract_run` の `kind` が `task` で、`task_id` がそのタスクの行）のうち、ID が最大の行（終わった行も含む）。

- [ ] `delegate`: 最後の契約の実行の状態。`state`（`running`・`waiting`・`succeeded`・`failed`・`cancelled`。記録した値のまま）・`summary`（委譲先が返した要約）・`requested_kind`（委譲先が求めていること。無ければ `null`）・`run_id`（その実行の ID）。契約の実行が無いタスクは `null`。
- [ ] `artifacts`: そのタスクの実行のうち、成果物を持つ、ID が最大の実行の成果物の配列。要素は `kind`・`ref`・`state`（どれも、記録した値のまま）・`role`（`integration` か `null`）。無ければ空の配列。
- [ ] `facts`: 最後の契約の実行が値で返したこと（名前から値への対応）。無ければ空の対応。
- [ ] `verification`: そのタスクの、タスクの検証の作業ログ（`entity` がタスクで、`action` が `task_verify`）のうち、ID が最大の記録。`verdict`（`met`・`not_met`・`uncertain`。記録した値のまま）・`reason`・`at`（記録の時刻）。記録が無ければ `null`。
- [ ] `landing`: 統合先へ入れる進み。統合先を使う課題で、タスクが済みなら `landed`。最後の契約の実行が終わっておらず、`land_ref` があれば `sent`（届いたかの印 `land_delivered` は問わない）。最後の契約の実行が終わっておらず、`verified_ref` があり `land_ref` が無ければ `verified`。それ以外（統合先を使わない課題のタスクを含む）は `null`。

タスクの詳細の画面に、次を足す。

- [ ] 「委譲先の実行」の区画: 状態（語に直す）・委譲先が返した要約・委譲先が求めていること（あれば）。
- [ ] 「成果物」の区画: 成果物ごとに、種類・リンク・状態。統合先の印がある成果物は、統合先のものと分かる語を添える。
- [ ] 「委譲先が値で返したこと」の区画: 名前と値の一覧（自己レビューを実行したか、など）。無ければ区画を出さない。
- [ ] 「検証」の区画: タスクの検証の判定と理由、判定した時刻。統合先を使う課題では、統合先へ入れる進み（`landing`）を語で出す。
- [ ] 「費用」に、タスクの枠（実装とレビュー対応）と、使った額を出す。
- [ ] 課題の詳細の API の `runs[]` の上限を、20 件から 100 件に上げる（タスクが多い課題で、タスクの詳細の実行の記録が欠けないようにする）。

### タスクのツリー

- [ ] ツリーの API の `tasks[]` の要素に、`progress` を足す。表示の区分（`phase`）が `running` のタスクの、細かい進み。タスクの状態が着手中なら `working`（語は「作業中」）。タスクの状態が検証中で、最後の契約の実行に `verified_ref` が無ければ `verifying`（語は「検証待ち」。統合先を使わない課題の、検証中のタスクも、これ）。統合先を使う課題で、検証中で、最後の契約の実行が終わっておらず `verified_ref` があり `land_ref` が無ければ `verified`（検証を通っただけで、統合先へ入れる依頼はまだ。語は「検証済み」。タスクの詳細の `landing` の `verified` と同じ）。同じ条件で `land_ref` があれば `landing`（統合先へ入れる依頼を出している。語は「統合中」。詳細の `landing` の `sent` と同じ）。ツリーの `progress` の `verified`・`landing` は、詳細の `landing` と同じ決め方・同じ語にする（決定 2026-11-21 #964: 検証を通っただけのタスクが、ツリーでは「統合中」、詳細では「検証済み」と出ていた食い違いを、詳細の側に寄せて解く）。`phase` が `running` でないタスク（あなたを待っているタスクを含む）は `null`。`phase` の値の集合は変えない。
- [ ] ツリーの API の課題の要素に、`progress` を足す。統合先を使う課題だけに出す。課題の状態が検証中なら `checking`（課題の単位の確かめを待っている。統合先を使う課題が検証中になるのは、この確かめのときだけ）。課題の状態が着手中で、取りやめを除く全部のタスクが済みで、上げる依頼（`contract_run` の `kind` が `reflect`）の、終わっていない行があれば `reflecting`。それ以外は `null`。統合先を使わない課題は、タスクが 1 個で、タスクの `progress` で足りるので、常に `null`。
- [ ] 値は core が決める（画面は、状態から導かない。S2c の「表示の区分と件数を core が決める」と同じ）。値の集合は、`internal/view` の閉集合に足し、画面の語の表（`labels.ts`）に、対応する語を足す。
- [ ] ツリーの箱に、`progress` の語を出す（「作業中」「検証待ち」「検証済み」「統合中」）。課題の枠の見出しに、課題の `progress` の語を出す（`reflecting` は「反映中」、`checking` は「全体の確認中」）。
- [ ] 課題の詳細のツリーにも、同じ語を出す。

### S3c の値を画面に出す

S3c が、課題の詳細の API に足す値（根の `conflict_fixes`〔通した衝突の解消の一覧〕と、`runs[]` の `fix_pending_ref`〔確かめ待ちの中身〕。形は `core-redesign.md` の S3c の「画面・API設計」）を、画面に出す。S3c が main に入り、S3d の統合ブランチへ取り込んだ後に行う。

- [ ] 完了承認画面の「反映するもの」の下に、通した衝突の解消の件数と、1 件ごとの、宛先（統合先か反映先）・直したファイルの名前を出す。0 件なら、区画を出さない。
- [ ] 課題の詳細にも、同じ一覧を出す。0 件なら、区画を出さない。
- [ ] タスクの詳細に、そのタスクの実行に確かめ待ちの中身があるとき、衝突の解消の確かめを待っている旨を出す。

### S2c の画面で仕様に残した点（flywheel#840）

- [ ] 経緯で、不可逆操作の 1 つの出来事（承認・差し戻し）が 2 行になる点: 画面で 1 行にまとめる。不可逆操作の側の、承認・差し戻しの記録の行（`entity` が不可逆操作）は、同じ操作の、課題の側の行（`op_approve`・`op_reject` で、`operation_id` がその操作）が経緯にあるときだけ出さない。対になる課題の側の行が無い経路（完了の承認と同時の反映の承認・取り下げによる差し戻し）では、不可逆操作の側の行を出す（出来事が経緯から消えないようにする）。課題の側の行（`action` が `op_approve`・`op_reject`）は残し、その記録の `operation_id` を、課題の詳細の `operations[]` と突き合わせて、操作の種類の語を添える（見つからなければ、添えない）。不可逆操作の登録など、ほかの行は変えない。作業ログの記録は変えない。
- [ ] 課題の詳細の「関係する課題」の、満たされていない前提の語「未完了」: 「未解消」に改める（前提の課題が完了でも、反映がまだのときは、前提は満たされていない。「完了」と「未完了」が同じ行に並ぶのを避ける）。前提の課題の状態の語は、変えない。
- [ ] タスクの前提に、その課題に無いタスクが書かれているとき: 計画の出力の検査で断る（計画を作る判断点の出力が、同じ計画に無いタスクの鍵を前提に書いていたら、出力の誤りとして扱う）。いまの検査が断っているかを、実装の最初に確かめ、断っていれば、その試験だけを足す。画面は変えない。
- [ ] 課題の詳細の、不可逆操作の区画の語: 種類（`release`・`delete`・`external_send`・`other`）と状態（`pending`・`approved`・`rejected`・`executed`・`closed`）を、どちらも、語の表で日本語の語に直して出す（種類は、反映・削除・外部送信・その他。状態は、承認待ち・承認済み・差し戻し・実行済み・終了）。完了承認画面の、ほかの不可逆操作の行も同じ。
- [ ] 計画の承認の画面の、差し戻しの案内: コマンドの例を外し、対話で伝える方法だけを出す。

### 画面の語の見直し（オーナーの決定 2026-11-21）

札（タグ）に出す語は、動詞の形をやめて、名詞の形にする。一般に通じる英単語は、英語のまま出してよい。画面の文では、「端末」と書かず「ターミナル」と書く。

- [ ] タスクの表示の区分（`phase`）の語を改める: `running` は「実行中」、`waiting` は「あなた待ち」、`next` は「次に実行」、`blocked` は「前提待ち」。`done`（済み）と `cancelled` は変えない。課題の画面の凡例・サイクルの状態の語など、同じ語を使っている所も、同じに改める（「走っている」を「実行中」に）。
- [ ] 統合先へ入れる進み（`landing`）の語: `verified` は「検証済み」、`sent` は「統合中」、`landed` は「統合済み」。
- [ ] 委譲先の実行の状態の語: `running` は「実行中」、`waiting` は「待機中」、`succeeded` は「成功」、`failed` は「失敗」、`cancelled` は「中止」。
- [ ] 委譲先が求めていること（`requested_kind`）は、語だけを出す（括弧の補足は付けない）。
- [ ] 成果物の状態（`artifacts[].state`）は、記録した値を、そのまま出す（語に直さない）。
- [ ] 画面の文（案内の文を含む）の「端末」を、「ターミナル」に改める。

## 技術的な制約・方針

- 使用技術: 既存のまま（Go・SQLite・React・TypeScript）。依存は増やさない。ストアの版は変えない（読むだけ）。
- 変更対象:
  - `internal/core`: `challenge.go`（タスクの要素に足す値の読み取り）・`tree.go`（`progress`）・計画の出力の検査（`judgment_j2.go`）。
  - `internal/view`: タスクの要素・ツリーの要素・閉集合、型の生成（`web/src/api/types.gen.ts`）。
  - `internal/cli`: `flywheel show --json` は、課題の詳細の API と同じ型を使うので、同じキーが増える。テキストの出力は変えない。
  - `web/src`: 行き先（`shell/route.ts`・`Shell.tsx`・`shell/waitingRows.ts`）、完了承認画面（新しいディレクトリ）、`task/`・`detail/`・`challenges/`・`plan-approval/`、語の表（`labels.ts`）、偽のデータ（`mock/`）、試験。
  - 文書: `docs/features/m4-ui-server.md`。
- 既存コードとの関係:
  - 承認の要約の API は変えない。完了承認画面は、承認の要約と課題の詳細の 2 つを読む。
  - S3c が足す値（通した衝突の解消の一覧 `conflict_fixes`・`runs[]` の `fix_pending_ref`）は、S3c が main に入った後に、S3d の統合ブランチへ取り込んでから、画面に足す（下の「スライス」）。
- 手触りと見た目の作り込み（配色・余白・動き）は入れない（S5 より後。オーナーの決定 2026-11-20）。配置は、試作（`w5-completion.html`・`w3-task-running.html`・`w3-task-done.html`）に合わせる。

## クリティカル設計決定

### 画面のボタンで受ける範囲を広げない（S3d）

- **採用案**: 完了承認画面のボタンは、S2c の区画と同じ口（反映を保留にした完了の承認）だけを使う。反映まで承認する・差し戻す・問いに答えるは、ターミナルか対話に寄せる（画面の案内に出すのは、対話で伝える方法だけ）。
- **理由**: 設計書 §9 の承認の経路の決まり（画面の口には、委譲の子からも届きうる）。広げるのは、対話の欄と一緒に、S4 で決める（`ux.md` の未決）。
- **影響範囲**: 画面の横断の試験（送る要求は、GET と、承認・サイクルの POST だけ）は、そのまま通す。

### 外へ出す値: 委譲先が返した要約と値を、画面に出す（S3d）

- **採用案**: 委譲先が返した要約（`summary`）・値（`facts`）・成果物の識別を、課題の詳細の API に足す。値は、core が記録したものをそのまま返し、画面は、文字として出す（Markdown として整えない。リンクにするのは、成果物の識別のうち、http か https のものだけ。S2c の、安全なリンクの決まりを使う）。
- **理由**: 委譲先の出力は、flywheel の外で作られた文字。画面で解釈すると、意図しない表示やリンクになりうる。
- **影響範囲**: `internal/view`・`web/src/task`。API は、`127.0.0.1` だけで待ち受ける決まりのまま。

### 細かい進みは、表示の区分と別のキーにする（S3d）

- **採用案**: タスクの表示の区分（`phase`。6 値）は変えず、別のキー `progress` を足す。
- **理由**: 表示の区分は、箱の色と件数（走っている・あなたを待っている・次に走る など）の決まりに使っている。値を足すと、件数の数え方と、画面の全部の分けが変わる。
- **代替案**: `phase` に値を足す。上の理由で採らない。タスクの状態（`status`）に値を足す。`core-redesign.md` の決定で、採らないと決めている。

## 機能全体の設計

### 実装計画（チケット分解の見通し）

分け方の案（最終の分解は `/create-ticket` で行う）。

1. API: タスクの要素の 5 つのキー、`runs[]` の上限、型の生成、偽のデータの追従。
2. API: ツリーの `progress`（タスクと課題）、閉集合、語の表。
3. 画面: 完了承認画面（行き先・画面・「いま進められること」と課題の詳細からの入口）。
4. 画面: タスクの詳細（委譲先の実行・成果物・値で返したこと・検証・費用）。
5. 画面: ツリーの `progress` の語（課題の画面と、課題の詳細）。
6. flywheel#840 の 5 点。
7. S3c の値を画面に出す（通した衝突の解消の一覧を、完了承認画面と課題の詳細に。確かめを待っている旨を、タスクの詳細に）。S3c が main に入り、統合ブランチへ取り込んだ後に行う。
8. 文書。

順は、1・2 → 3・4・5（並行にできる）→ 6 → 7 → 8。

## やらないこと

- 委譲先の実行が「いまいる段」の並びを出すこと（理由: 契約の出力に、段の値が無い。委譲先との契約と claude-harness の側の拡張が要る。要るときに、別の Issue にする）
- 完了の検証の、条件ごとの判定と件数を出すこと（理由: 判断点の出力に無い）
- 意思決定の記録、スーパーバイザーが答えた問いと打った手、計画の後に足したタスクの印、対話の欄（理由: S4）
- 画面のボタンで受ける範囲を広げること（反映まで承認する・差し戻す・問いに答える・取り込む・サイクルを止める）（理由: S4。上の「クリティカル設計決定」）
- 承認の要約の API を変えること（理由: 画面が、課題の詳細の API と合わせて読めば足りる）
- 前提が満たされていない理由（反映がまだ・前提が循環している）を、API に足して画面に出すこと（理由: 語を改めるだけにする。要るときに足す）
- 承認の後に反映先が動いたときの、変わり方の見分け（取り込みだけ・衝突の解消あり・関係のない変更あり）そのものを、画面に出すこと（理由: 画面に出すのは、通した衝突の解消の一覧と、確かめを待っている旨まで）
- ストアの形を変えること（理由: 読むだけで足りる）
- S2c の画面の掃除の残り・API の読み取りの直し・読み直しの直し・フォローアップの数え方（理由: flywheel#836〜#839。別の Issue）
- 「反映先」「反映」の語の見直し（理由: オーナーが、語に違和感があるとして、後で決める。2026-11-21）
- 文書（仕様・用語集）の中の「端末」の語を改めること（理由: 画面の文だけを改める。文書は、語の見直しのときに一緒に行う）
- 問いへの回答・取り込み・予算の増額など、ほかの案内のコマンドの例を外すこと（理由: 対話の欄を作る S4 で、一緒に見直す）
- 手触りと見た目の作り込み（理由: S5 より後。オーナーの決定 2026-11-20）
