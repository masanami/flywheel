# core の見直し 区切り S4c — 計画の後にタスクを足す

## 概要

`docs/features/core-redesign.md` の区切り S4c の仕様。S4a（長く走るサイクル）の実装と並べて書くので、その間だけ別の文書に書き、main に入れるときに `core-redesign.md` へ畳む（S3d・S4d と同じ進め方。オーナーの決定 2026-11-22）。実装は、S4a が main に入ってから始める。

S4c は、次の 3 つを入れる。

- **計画の後にタスクを足す**: 計画の承認で、課題の予算の上限も承認する。その内なら、計画を作る判断点（J2）が、承認なしでタスクを足す。
- **フォローアップを、開いている課題のタスクに上げる**: 上げる先の既定を、元の課題のタスクにする。
- **保留中の課題のほかのタスクを進める**: 保留が 1 つのタスクについての問いなら、そのタスクと、その先のタスクだけを止める。

> **仮の決め**: 下の「オーナーに伺う点（仮に決めて書いたもの）」の 4 点は、推奨の案で仮に書いてある。オーナーの回答で、該当の要件と受入基準を直す。

## 背景・目的

- 設計書（`docs/architecture.md` §21.2）は、「計画の承認で、方針・範囲・予算の上限を承認する。その内なら、計画の判断点が承認なしでタスクを足す。足した後の予算の合計が、承認した上限を超えるなら、必ずオーナーへ問う」と決めている。いまは、後からタスクを足せるのは、オーナーが計画の作り直しを指示して、承認し直すときだけ（S3b）。設計が済んでから実装のタスクを確定する課題は、計画を 2 回承認することになる。
- いまは「上限」という別の数字が無い。課題の予算の上限は、取りやめでないタスクの枠の合計を、そのつど計算している（S3b）。タスクを 1 つ足すと、必ず合計が増えるので、「承認した上限」を別に持たないと、毎回問うか、歯止めが無いかのどちらかになる。
- フォローアップを上げると、いつも新しい課題になる（S2b）。元の課題がまだ開いていても、分類・計画・計画の承認からやり直しになり、成果は、元の課題と別に検証・承認・反映される。
- 保留は課題の単位で、保留中の課題では、新しいタスクを起動せず、レビュー待ちの受け取り・タスクの検証・「入れてよい」を返すことを、保留が解けるまで延ばす（S3b）。1 つのタスクの問いで、関係の無いタスクまで止まる。測った期間、回答待ちは、委譲で完了した課題の時間の 40% だった（設計書 §21.0）。

## ユーザーストーリー

- オーナーとして、計画の承認のときに「この課題は、ここまでなら任せる」という額を 1 回決め、その内で増えるタスクには、いちいち承認を求められたくない。超えるときは、必ず聞いてほしい。
- オーナーとして、開いている課題の途中で出た「後でやること」を、その課題の成果と一緒に仕上げたい。
- オーナーとして、1 つのタスクの問いに答えるまでの間も、関係の無いタスクは進んでいてほしい。

## 機能要件

語は `docs/glossary.md` に合わせる。この文書では、次の語を使う。

| 語 | 意味 |
|---|---|
| 見込み | 課題の、取りやめでないタスク（済みを含む）の枠の実効値の合計（実装の枠とレビュー対応の枠を足した額）。S3b の「課題の予算の上限」と同じ計算 |
| 上限 | 計画の承認で、オーナーが承認した、課題の予算の上限。見込みが、これを超えてはならない |
| 足す依頼 | 計画の承認の後に、タスクを足すことの 1 件の記録。出どころは、「続きを決めるタスクが済んだ」（`expand`）か、「フォローアップを上げた」（`followup`） |
| タスクの保留・課題の保留 | タスクの保留は、タスクを指す保留（保留の記録に、タスクの識別がある。親が直接進める保留〔`parent_direct`〕は除く）。課題の保留は、それ以外の保留 |

### 予算の上限

- [ ] 計画を作る判断点（J2）の出力に、課題の上限（`budget_limit_usd`）と、その理由（`budget_limit_reason`）を足す。どちらも省ける。
- [ ] `budget_limit_usd` が無い計画の上限は、見込みと同じ額にする。
- [ ] `budget_limit_usd` が見込みより小さい計画は、不正な出力として扱う（いまの、判断点の不正な出力と同じ扱い）。
- [ ] `budget_limit_usd` が見込みより大きいのに、`budget_limit_reason` が無いか空の計画は、不正な出力として扱う。
- [ ] 計画の承認（T5）で、承認した版の上限と理由を、課題に記録する。計画を作り直して承認し直したときは、新しい版の値で置き換える。
- [ ] 上限の記録が無い課題（S4c より前に計画を承認した課題）の上限は、そのときの見込みと同じ額として扱う（足すと、必ず上限を超える）。
- [ ] タスクの枠の増額（`flywheel budget`。S3b）で、見込みが上限を超えるときは、同じ書き込みで、上限を見込みまで上げる（枠の増額の承認が、上限の引き上げの承認を兼ねる）。
- [ ] `flywheel budget <課題の ID> --limit <USD>` で、上限だけを変えられる。本人確認は、枠の増額と同じ（ターミナルでの本人確認か、対話で受けたことの記録〔`--relayed`〕）。見込みより小さい値は断る。
- [ ] 上限を変えたことは、作業ログに残す（前の値・後の値・本人確認の方式）。

### 計画の後にタスクを足す（続きを決めるタスク）

- [ ] 計画のタスクに、「このタスクが済んだら、続きのタスクを決める」という印（`expand_after`。真偽）を付けられる。
- [ ] `expand_after` が真のタスクを持つ計画が、統合先を使わない（`uses_integration` が偽）なら、不正な出力として扱う。
- [ ] 統合先を使う、着手中の課題（開いている保留が、どれもタスクの保留である保留中の課題を含む）で、`expand_after` が真のタスクが済みになったら、次の回りの計画の段が、そのタスクについての足す依頼を 1 件作り、計画を作る判断点を「足す」の形で呼ぶ。同じタスクについて、足す依頼は 1 件だけ作る。
- [ ] 「足す」の形の入力は、承認した計画（方針・完了条件・やらないこと）、いまのタスクの一覧（題名・状態・前提）、済んだタスクの結果（委譲先の要約・成果物の一覧・タスクの検証の結果）、上限と、上限までの残り（上限 − 見込み）。
- [ ] 「足す」の形の出力は、判断値（`add`・`none`・`ask`）と、足すタスクの一覧（`add` のとき。形は、計画のタスクと同じ。前提に、いまあるタスクの鍵も書ける）、問い（`ask` のとき）。
- [ ] 判断点の費用は、計画を作る判断点の予算（`judgment_budget_usd.J2`）で数える。課題の見込みには数えない。
- [ ] `none` → 足す依頼を「足さない」で閉じ、何も足さない。
- [ ] `add` で、足した後の見込みが上限以下 → タスクの行を作る（状態は未着手。計画の版は、承認済みの版）。足す依頼を「足した」で閉じる。オーナーの承認は求めない。
- [ ] `add` で、足した後の見込みが上限を超える → タスクの行を作らず、足す依頼を「オーナー待ち」にして、課題を保留にする（保留の理由 `task_add_over_limit`。問いに、足すタスクの題名と枠・足した後の見込み・上限・超える額・進め方〔下の 3 つ〕を書く）。保留は、足す依頼の出どころのタスクを指す。
- [ ] `ask` → タスクの行を作らず、課題を保留にする（保留の理由 `task_add_question`。問いは、判断点の問い）。保留は、出どころのタスクを指す。回答の後、次の回りで、回答を入力に足して、判断点を呼び直す。
- [ ] 判断点の指示文に、次を書く: 計画の「やらないこと」に触れるタスクは足さない。方針の外かどうか迷ったら `ask` にする。判断や人の作業が要る点が出たら `ask` にする。
- [ ] 足すタスクの検査は、計画のタスクと同じ（題名・本文・完了条件・リポジトリ・操作の種類・枠）。加えて、鍵が、その課題のいまのタスクの鍵と重ならないこと、前提が、足すタスクか、取りやめでないいまのタスクを指すこと、前提に輪が無いこと。検査に通らない出力は、不正な出力として扱う。
- [ ] `task_add_over_limit` の保留は、次の 3 つで進められる。
  - 上限を、足した後の見込み以上に上げる（`flywheel budget <課題の ID> --limit <USD>`）→ 同じ書き込みで、タスクの行を作り、足す依頼を「足した」で閉じ、保留を閉じる（回答なしで閉じる）。
  - 回答する（`flywheel answer`）→ 足す依頼を「見送り」で閉じ、足さずに進む。
  - 計画を作り直す回答（`--replan`）→ 足す依頼を「取り替え」で閉じ、計画を作り直す（S3b のまま）。
- [ ] 足す依頼が「仕様待ち」か「オーナー待ち」の間、その課題の上げる依頼は始めない。
- [ ] 計画を作り直して承認し直したとき、閉じていない足す依頼は「取り替え」で閉じる。

### フォローアップを、開いている課題のタスクに上げる

- [ ] `flywheel followup promote <フォローアップの ID>` の上げる先を、次の順で決める。
  - `--new-challenge` を付けた → 新しい課題（いまと同じ）。
  - フォローアップが課題に属し、その課題が、統合先を使い、着手中か、開いている保留がどれもタスクの保留である保留中 → その課題のタスク。
  - それ以外（課題に属さない・元の課題が終わっている・検証中より先へ進んでいる・統合先を使わない・課題の保留がある）→ 新しい課題。
- [ ] 上げる先がタスクのとき、足すタスクの枠は、サイズ S の既定（宣言 `size_budgets_usd.S`）。`--budget-impl-usd`・`--budget-review-usd` で変えられる。
- [ ] 本人確認の前に見せる要約に、上げる先（課題の題名と ID、または「新しい課題」と、タスクにしなかった理由）、足すタスクの枠、足した後の見込み、上限、上限を超える額（超えるとき）を出す。
- [ ] `flywheel followup promote <ID> --preview` は、上の要約と同じ値を、何も書かずに返す（本人確認なし。`--json` あり）。
- [ ] 足した後の見込みが上限を超えるとき、ターミナルでの本人確認では、要約に「上限を、いくらからいくらへ上げる」を出し、確かめた指示を、上限の引き上げの承認として扱う。
- [ ] 足した後の見込みが上限を超えるとき、対話で受けたことの記録（`--relayed`）では、`--raise-limit` が無ければ断る（終了コードは検証の誤り。出力に、超える額と、`--preview` で確かめられる旨）。
- [ ] 上げる先がタスクのとき、上げる操作は、同じ書き込みで、足す依頼（出どころ `followup`。状態「仕様待ち」。枠の額つき）を作り、要るなら上限を上げ、フォローアップに、足す依頼を記録する。フォローアップの状態は、未のまま。
- [ ] 次の回りの計画の段が、「仕様待ち」の足す依頼について、計画を作る判断点を「足す」の形で呼ぶ（入力に、フォローアップの題名と説明を足す）。出力のタスクは 1 個で、枠は、足す依頼の額を使う（出力の枠は読まない）。
- [ ] `add` → タスクの行を作り、フォローアップに、上げた先のタスクを記録する。`ask` → 上の `task_add_question` と同じ。`none` と、タスクが 2 個以上の出力は、不正な出力として扱う。
- [ ] 上げた先のタスクが済みになったら、core が、そのフォローアップを済みにする（確かめた結果に、上げた先のタスクを書く）。
- [ ] 上げた先のタスクが取りやめになったら、フォローアップは未のまま残り、上げ直せる。
- [ ] その課題の上げる依頼が開いているときに、タスクとして上げたら、上げる依頼を取り消す（S3b の、課題の単位の確かめが「満たしていない」のときと同じ道。作った反映の操作は閉じる）。足したタスクが統合先に入った後、上げる依頼を始め直す。
- [ ] 1 回に上げるのは 1 件（いまと同じ）。

### 保留中の課題のほかのタスクを進める

- [ ] 開いている保留が、どれもタスクの保留である課題では、止めるのは、「保留が指すタスクのうち、済みでも取りやめでもないもの」と、「それを前提に持つタスク（前提をたどった先を含む）」だけにする。
- [ ] 止めないタスクには、着手中の課題と同じに、起動・レビュー待ちの受け取り・タスクの検証・「入れてよい」を返すことを行う。同時に走らせる数・タスクの枠・サイクルの費用の上限は、いまと同じ。
- [ ] 止めるタスクの扱いは、S3b の保留中の課題のタスクと同じ（走っている実行の状態は読み続ける。レビュー待ちの受け取り・タスクの検証・「入れてよい」は、保留が解けるまで延ばす）。
- [ ] 課題の保留が 1 つでも開いている課題は、S3b のまま（新しいタスクを起動しない）。
- [ ] 保留中の課題では、上げる依頼を始めない（S3b のまま）。
- [ ] 止めないタスクの処理が保留を要するとき（いま、タスクの処理から課題を保留にしている場面のすべて。保留の理由は、いまのまま）、その課題に、保留をもう 1 つ足す。課題の状態は、保留中のまま。同じタスクを指す、開いている保留は、1 つまで。
- [ ] 開いている保留がある課題に、課題の保留を足すこともある（いま、タスクを指さずに課題を保留にしている場面のすべて。例: 進めようが無くなった〔`tasks_blocked`〕）。足した後は、上の「課題の保留が開いている課題」の扱いになる。
- [ ] `flywheel answer <課題の ID>` は、開いている保留が 1 つなら、いまと同じ。2 つ以上なら、`--hold <保留の ID>` で選ぶ。選ばなければ断り、開いている保留の一覧（ID・指すタスクの題名・問いの先頭）を出す。
- [ ] 回答すると、その保留だけが解ける。ほかに開いている保留があれば、課題は保留中のまま。最後の 1 つが解けたら、最初に保留にしたときの状態へ戻る（T12 のまま）。
- [ ] 計画を作り直す回答（`--replan`）は、選んだ保留に答え、ほかの開いている保留を閉じ（回答なしで閉じる）、計画を作り直す。作業している実行があるときに断る決まりは、S3b のまま。
- [ ] 課題の取り下げは、開いている保留をすべて閉じる（いまは 1 つを閉じる）。
- [ ] 対話で受けた回答（`--relayed`）・画面の対話の欄からの回答も、同じ決まり（`--hold`）で受ける。

### 見せ方（core・CLI・API の値）

- [ ] 課題の詳細（`GET …/challenges/<ID>` と `flywheel show --json`）に、予算（`budget`: `estimate_usd`・`limit_usd`・`limit_reason`）を足す。上限の記録が無い課題の `limit_usd` は、見込みと同じ額。
- [ ] 計画の承認待ちの課題では、`budget` は、承認を待っている版の計画の値を返す。
- [ ] 画面の計画の承認に、「見込み・上限」と、上限の理由を出す（上限が見込みと同じなら、理由は出さない）。
- [ ] `flywheel show`（テキスト）に、見込みと上限を出す。
- [ ] 課題の詳細のタスクの要素に、足されたタスクの印（`added`: `origin`・`origin_task_id`・`followup_id`・`added_at`。計画の承認で作ったタスクは `null`）を足す。
- [ ] 課題の詳細に、足す依頼の一覧（`additions[]`: 出どころ・状態・出どころのタスクかフォローアップ・足したタスク・足した後の見込み・そのときの上限・日時）を足す。
- [ ] 課題の詳細に、開いている保留の一覧（`open_holds[]`: 保留の ID・指すタスク・理由・問い・日時）を足す。いまある、保留 1 件を返すキーは、変えない（いちばん古い、開いている保留を返す）。
- [ ] フォローアップの要素に、上げた先のタスク（`promoted_task_id`）を足す。
- [ ] タスクを足したことは、作業ログに残す（足す依頼・足したタスク・足した後の見込みと上限）。
- [ ] `flywheel cycle` の出力に、その回に足したタスクを出す（課題・タスクの題名・出どころ）。
- [ ] 完了の承認の要約（`flywheel show` と API）に、計画の後に足したタスクの一覧を出す。

### サイクルとの関係（S4a）

- [ ] 「いま始められるもの」（S4a）に、「仕様待ち」の足す依頼と、済みになった `expand_after` のタスクで足す依頼がまだ無いもの、保留中の課題の、止めないタスクで起動できるものを数える。「オーナー待ち」の足す依頼は数えない。
- [ ] 上限を変える操作（`flywheel budget … --limit`）は、枠の増額と同じに、成立の後でサイクルを始める（S4a の決まり。きっかけは `budget`）。

## 技術的な制約・方針

- 開発に固有の知識を、core に新しく足さない（オーナーの決定 2026-11-22）。足すタスクの中身は、計画のタスクと同じ項目だけを持つ。
- 判断は判断点が返し、遷移と数字の判定は core が行う（P2 のまま）。上限を超えるかは、core が数字で判定する。
- 委譲先との契約は、変えない。claude-harness の側で要るものは無い。
- ストアの版は、S4a（版 31）・対話の欄（版 32）の次。番号は、main に入れる順で決める。マイグレーションは 1 本。
- 進行中の課題を新しい形へ移す処理は作らない。過去の行は書き換えない（上限の記録が無い課題は、読むときに見込みと同じ額として扱う）。

## 画面・API設計

- 画面で変えるのは、計画の承認の「見込み・上限」の 1 か所だけ。足されたタスクの印・足す依頼・開いている保留の一覧の見せ方、フォローアップと取り込みのボタンは、S4d-2（`core-redesign-s4d.md`）。S4c は、そのための値を API に出す。
- 新しい口は作らない。`GET …/challenges/<ID>`・フォローアップの一覧の応答にキーを足す。型は `internal/view` に足し、`go generate ./internal/view` で作り直す。

## クリティカル設計決定

### 承認の意味: 上限は 1 つの額で、課題に記録する

- **採用案**: 上限は、実装の枠とレビュー対応の枠を足した、1 つの額にする。計画の承認のときに、課題の記録（`challenge.budget_limit_micros`・`budget_limit_reason`）に写す（統合先を使うか〔`uses_integration`〕と同じ持ち方）。
- **理由**: オーナーが承認するのは「この課題に、いくらまで」の 1 つの数字（オーナーの決定 2026-11-22「計画が上限を別に示す」）。枠ごとに 2 つ持つと、承認の画面の数字が 4 つになり、どちらの枠で超えたかの問いが増える。枠ごとの歯止めは、タスクの枠（S3b）が持っている。課題に写すのは、サイクルが、計画の本文を読み直さずに判定するため。
- **代替案**: 計画の表（`task_plan`）に持つ。版ごとに値が残るが、承認していない版の値を読む誤りが起きうる。承認した値だけを課題に持つほうが、読む所が 1 つで済む。

### 承認の意味: 上限を超えて足すには、上限を上げる操作を使う

- **採用案**: 上限を超える足す依頼は、オーナーが上限を上げたとき（`flywheel budget … --limit`。本人確認つき）にだけ、足す。保留への文の回答は、「足さずに進む」として扱う。
- **理由**: 設計書は「超えるなら、必ずオーナーへ問う」としている。文の回答を「足してよい」と読むと、core が文の意味を判定することになる（P2 に反する）。額を上げる操作は、数字で判定でき、枠の増額と同じ本人確認と記録を使える。
- **代替案**: 保留の問いに選択肢を持たせ、選ぶだけで答える。問いの構造は S4b・S4d-2 で入るので、S4c は待たない。入った後は、この保留にも選択肢を付けられる。

### 承認の意味: フォローアップを上げる指示が、上限の引き上げの承認を兼ねる

- **採用案**: タスクとして上げて上限を超えるときは、上げる前に、増える額を見せ、上げる指示を、その引き上げの承認として扱う（オーナーの決定 2026-11-22）。対話で受けた記録では、`--raise-limit` を明示したときだけ受ける。
- **理由**: 上げる操作は、本人確認つきの、オーナーの指示。ターミナルでは、本人確認の前の要約で額を見せられる。対話で受けた記録では、core は、オーナーが額を見たかを確かめられないので、オーケストレーターが `--preview` で額を伝えたうえで、明示の印を付ける形にする。
- **代替案**: 上限を超えるときは、先に `flywheel budget … --limit` を求める。操作が 2 回になる。

### 状態遷移: 保留を、課題に重ねて持てるようにする

- **採用案**: 課題の状態は「保留中」のまま、開いている保留を複数持てるようにする（同じタスクを指すものは 1 つまで）。課題の状態機械に、タスクごとの状態を足さない。遷移表は、T11（保留）に「保留中から保留中へ（保留を足す）」を足し、T12（回答）を「開いている保留が残れば保留中のまま、無くなれば前の状態へ」に改める。
- **理由**: オーナーから見える「この課題は、あなたを待っている」は変わらない（一覧・カード・件数は、いまのまま）。止める範囲だけを、保留が指すタスクから決める。いま、タスクの処理から立つ保留には、タスクの識別が付いている（`hold.task_id`。S2a）。
- **代替案 1**: 開いている保留は 1 つのままにし、2 つ目が要る場面は、最初の保留が解けるまで延ばす。延ばせる形（読み直せる状態）が無い場面（例: タスクの検証の「判断できない」）では、判断点を呼び直すことになり、費用が二重にかかる。
- **代替案 2**: 保留をタスクの状態にして、課題は着手中のままにする。課題の一覧から「あなた待ち」が消え、課題の状態を読んでいる所（カード・件数・学びの判断点の対象）をすべて直すことになる。
- **影響**: 「課題の、いちばん新しい保留」を読んでいる所（`FROM hold … ORDER BY id DESC LIMIT 1` の形の問い合わせ。回答・親が直接進める保留・失敗の回数の数え方・課題の単位の確かめ・統合先へ入れた後の確かめ）を、保留の ID かタスクで絞る形に改める。

### DB スキーマ: 足す依頼の表と、列

- **採用案**: 表 `task_addition`（足す依頼）を足す。`id`・`challenge_id`・`origin`（`expand`・`followup`）・`origin_task_id`（NULL 可）・`followup_id`（NULL 可）・`state`（`pending`〔仕様待ち〕・`awaiting_owner`〔オーナー待ち〕・`applied`〔足した〕・`none`〔足さない〕・`declined`〔見送り〕・`superseded`〔取り替え〕）・`spec`（判断点が返したタスクの一覧。NULL 可）・`budget_impl_micros`・`budget_review_micros`（出どころが `followup` のときの枠。NULL 可）・`total_after_micros`・`limit_micros`（判定したときの値。NULL 可）・`hold_id`（NULL 可）・`created_at`・`decided_at`。列は、`task.addition_id`（NULL 可）・`task.expand_after`（既定 0）・`challenge.budget_limit_micros`（NULL 可）・`challenge.budget_limit_reason`（NULL 可）・`followup.promoted_task_id`（NULL 可）。同じ出どころのタスクについて、`origin = 'expand'` の行は 1 つ（部分一意索引）。
- **理由**: 上限を超えたときに、タスクの行を作らずに、足す中身を持っておく場所が要る。タスクの状態に「提案」を足すと、タスクを数えている所（起動・上げる依頼の条件・見込み）をすべて直すことになる。足す依頼の行は、「足したことの記録」と、足されたタスクの印（`task.addition_id`）も兼ねる。
- **代替案**: 作業ログだけに残す。上限を超えて待っている中身を、後で読み出す所が無い。

## 機能全体の設計

### 流れ

1. 計画の承認: 上限と理由を課題に写す。タスクの行に `expand_after` を写す。
2. 計画の段（回りごと）: ① 済みになった `expand_after` のタスクで、足す依頼が無いもの → 足す依頼を作る。② 「仕様待ち」の足す依頼ごとに、判断点を「足す」の形で呼ぶ。③ 出力を検査し、見込みと上限を比べ、足すか、保留にする。
3. 委譲の段: 起動するタスクの選び方に、「止めるタスク」を外す条件を足す。足したタスクは、ほかのタスクと同じに起動する。
4. 上げる依頼を始める条件（S3b）に、「閉じていない足す依頼が無い」「開いている保留が無い」を足す。

### 変える所（見込み）

- `internal/core`: ストアのマイグレーション、計画の出力の検査（`judgment_j2.go`）、計画の承認（`plan_answer.go`）、足す依頼（新規）、予算（`budget.go`）、フォローアップ（`followup.go`）、保留と回答（`transition.go`・`transition_exec.go`・`approval.go`）、起動の選び方（`contract_delegate.go`・`contract_delegate_after.go`・`contract_review_intake.go`・`integration_land.go`）、上げる依頼（`reflect_up.go`）、「いま始められるもの」（`cycle_work.go`）、課題の詳細（`challenge.go`・`tree.go`）。
- `internal/invoker/prompts/j2.md`: 上限と `expand_after` の書き方、「足す」の形の指示。
- `internal/cli`: `budget`（`--limit`）・`followup promote`（`--new-challenge`・`--preview`・`--raise-limit`・枠）・`answer`（`--hold`）・`show`・`cycle` の出力。
- `internal/view`・`web/src`: 型と、計画の承認の 1 行。

### S4b（スーパーバイザーのその場の対処）との境目

- S4c は、「保留が立った後に、何が止まるか」を変える。S4b は、「保留を立てる前に、スーパーバイザーが手を選ぶ」を足す。スーパーバイザーが「オーナーへ上げる」を選んだ後の保留は、S4c の決まり（タスクの保留なら、ほかのタスクは進む）に乗る。
- フォローアップの、出どころのタスク（`followup.task_id`）は、S4b が足す（スーパーバイザーの手 5「残った条件をフォローアップへ回す」）。S4c は、この列を読まない。出どころが `followup` の足す依頼の `origin_task_id` は、S4c では NULL。S4b は、列を足すときに、上げる処理で `origin_task_id` へ写す。
- スーパーバイザーの手 6「計画を作り直す」は、S3b の作り直しの道を使う。S4c の「足す」の形は使わない。
- S4b と S4c は、同じ表（`hold`・`followup`）に列を足す。ストアの版の番号は、後から main に入るほうが、次の番号を取る。

### 実装計画（チケット分解の見通し）

1. 土台: マイグレーション・足す依頼の core の API・型。
2. 上限: 計画の出力と検査・承認で写す・`budget --limit`・見せ方。
3. 続きを決めるタスク: `expand_after`・「足す」の形・検査・上限の判定・保留と 3 つの進め方。
4. フォローアップをタスクに上げる: 上げる先の決め方・`--preview`・`--raise-limit`・済みにする。
5. 保留を重ねる: 遷移表・`--hold`・「いちばん新しい保留」を読む所の直し。
6. 保留中の課題のほかのタスク: 止めるタスクの計算・起動と受け取りの条件。
7. 文書と全体の確かめ。

1 → 2 → 3 → 4 は順に。5 → 6 は、1 の後なら 2〜4 と並べられる（触るファイルが重なる所は、順にする）。

## スライス（出荷の単位）

| スライス | 入れるもの | 受入基準の見込み | 前提 |
|---|---|---|---|
| S4c | 予算の上限・計画の後にタスクを足す・フォローアップをタスクに上げる・保留中の課題のほかのタスクを進める | 150-170 | S4a が main に入ってから |

実装対象: S4c

## やらないこと

- 統合先を使わない課題（タスクが 1 個の課題）にタスクを足すこと（理由: 統合先を使うかは、計画の承認の時点の値で、途中で変えない。フォローアップは、新しい課題に上がる）
- 検証中・完了の承認待ちより先へ進んだ課題に、タスクを足すこと（理由: 完了の差し戻しの後の、計画の作り直しの道〔S3b〕がある）
- 取り込み元の親に、後から足された子を、タスクとして取り込むこと（理由: いまは、新しい課題として「取り込めるもの」に並ぶ。取り込みの形を変えるのは、別の区切りで決める）
- 上限を、実装の枠とレビュー対応の枠に分けて持つこと
- 計画を 2 段にして、設計の後にもう一度承認する形（理由: 設計書 §21.2 で、既定にしないと決めている）
- 保留の問いに選択肢を持たせること、画面のボタンで答えること（理由: S4b・S4d-2）
- 足されたタスクの印・足す依頼・開いている保留の一覧の画面、フォローアップと取り込みのボタン（理由: S4d-2。S4c は API の値まで）
- スーパーバイザーが、タスクを足す・フォローアップを書くこと（理由: S4b）
- 足したことを、画面の外へ知らせること（通知。理由: オーケストレーターからの知らせは S4d-2）
- 開発に固有の知識を、core に足すこと（理由: flywheel#981）

## 受入基準

実ストアと、テスト用の委譲先・テスト用の判断点で確かめる。

### 予算の上限

- [ ] 計画の出力に `budget_limit_usd` が無い → 計画の承認の後、課題の上限は、見込みと同じ額になる。
- [ ] 計画の出力の `budget_limit_usd` が見込みより大きく、`budget_limit_reason` がある → 計画の承認の後、課題の上限は、その額になる。
- [ ] 同じ計画の承認の後、課題の上限の理由は、`budget_limit_reason` の文になる。
- [ ] 計画の出力の `budget_limit_usd` が見込みより小さい → 不正な出力として扱い、計画を記録しない。
- [ ] 計画の出力の `budget_limit_usd` が見込みより大きく、`budget_limit_reason` が無い → 不正な出力として扱う。
- [ ] 計画の出力の `budget_limit_usd` が見込みより大きく、`budget_limit_reason` が空白だけ → 不正な出力として扱う。
- [ ] 計画を承認する前は、課題の上限の記録は変わらない。
- [ ] 計画を作り直して承認し直す → 課題の上限は、新しい版の値で置き換わる。
- [ ] 上限の記録が無い課題の詳細の `budget.limit_usd` は、`budget.estimate_usd` と同じ額になる。
- [ ] タスクの枠の増額で、見込みが上限を超える → 同じ書き込みで、上限が、増額の後の見込みと同じ額になる。
- [ ] タスクの枠の増額で、見込みが上限以下 → 上限は変わらない。
- [ ] `flywheel budget <課題の ID> --limit <見込み以上の額>` を、本人確認を通して実行 → 上限が、その額になる。
- [ ] `flywheel budget <課題の ID> --limit <見込みより小さい額>` → 検証の誤りで断り、上限は変わらない。
- [ ] `flywheel budget <課題の ID> --limit` を、本人確認なし（ターミナルでなく、`--relayed` も無い）で実行 → 断り、上限は変わらない。
- [ ] 上限を変えると、作業ログに、前の額と後の額が残る。
- [ ] `--limit` と、タスクの枠の指定を同時に付けた → 検証の誤りで断る。

### 続きを決めるタスク

- [ ] 計画のタスクに `expand_after: true` がある → 計画の承認の後、そのタスクの行に、印が付く。
- [ ] `expand_after: true` のタスクを持ち、`uses_integration` が偽の計画 → 不正な出力として扱う。
- [ ] 印の付いたタスクが済みになった、着手中の課題 → 次の計画の段で、足す依頼が 1 件でき、判断点が「足す」の形で 1 回呼ばれる。
- [ ] 同じタスクについて、次の回りの計画の段を通しても、足す依頼は増えない。
- [ ] 印の無いタスクが済みになっても、足す依頼はできない。
- [ ] 印の付いたタスクが、済みでない間は、足す依頼はできない。
- [ ] 「足す」の形の入力に、上限までの残り（上限 − 見込み）が入っている。
- [ ] 「足す」の形の入力に、済んだタスクの、委譲先の要約が入っている。
- [ ] 「足す」の形の入力に、計画の「やらないこと」が入っている。
- [ ] 判断値が `none` → 足す依頼の状態は `none` になる。
- [ ] 判断値が `none` → タスクの行は増えない。
- [ ] 判断値が `add` で、足した後の見込みが上限と同じ額 → タスクの行ができる。
- [ ] 判断値が `add` で、足した後の見込みが上限より小さい → 足す依頼の状態は `applied` になる。
- [ ] 足したタスクの状態は、未着手（`pending`）である。
- [ ] 足したタスクの計画の版は、承認済みの版である。
- [ ] 足したタスクの行は、足す依頼を指す（`addition_id`）。
- [ ] 足したタスクの前提に、いまあるタスクの鍵を書いた → 前提の行ができる。
- [ ] 足したタスクは、前提が済みなら、同じサイクルの委譲の段で起動される。
- [ ] 上限以下で足したとき、課題は保留にならない。
- [ ] 判断値が `add` で、足した後の見込みが上限を超える → タスクの行は増えない。
- [ ] 同じとき、足す依頼の状態は `awaiting_owner` になる。
- [ ] 同じとき、課題は保留中になり、保留の理由は `task_add_over_limit` である。
- [ ] その保留の問いに、足した後の見込みの額が入っている。
- [ ] その保留の問いに、上限の額が入っている。
- [ ] その保留の問いに、足すタスクの題名が入っている。
- [ ] その保留は、足す依頼の出どころのタスクを指す。
- [ ] `task_add_over_limit` の保留の間に、上限を、足した後の見込み以上へ上げる → タスクの行ができる。
- [ ] 同じ操作で、足す依頼の状態は `applied` になる。
- [ ] 同じ操作で、その保留は、回答なしで閉じる。
- [ ] 同じ操作で、ほかに開いている保留が無ければ、課題は着手中へ戻る。
- [ ] `task_add_over_limit` の保留の間に、上限を、足した後の見込みより小さい額へ上げる → タスクの行は増えず、保留は開いたまま。
- [ ] `task_add_over_limit` の保留に、文で回答する → 足す依頼の状態は `declined` になり、タスクの行は増えない。
- [ ] 同じ回答の後、課題は着手中へ戻る（ほかに開いている保留が無いとき）。
- [ ] `task_add_over_limit` の保留に、計画を作り直す回答（`--replan`）をする → 足す依頼の状態は `superseded` になる。
- [ ] 判断値が `ask` → 課題は保留中になり、保留の理由は `task_add_question` である。
- [ ] 判断値が `ask` → タスクの行は増えない。
- [ ] `task_add_question` の保留に回答する → 次の計画の段で、判断点が「足す」の形で呼ばれ、入力に回答の文が入っている。
- [ ] 足すタスクの鍵が、いまのタスクの鍵と重なる出力 → 不正な出力として扱い、タスクの行は増えない。
- [ ] 足すタスクの前提が、存在しない鍵を指す出力 → 不正な出力として扱う。
- [ ] 足すタスクの前提が、取りやめのタスクを指す出力 → 不正な出力として扱う。
- [ ] 足すタスクどうしの前提に輪がある出力 → 不正な出力として扱う。
- [ ] 足す依頼が `pending` の課題は、未着手・着手中・検証中のタスクが 0 個でも、上げる依頼を始めない。
- [ ] 足す依頼が `awaiting_owner` の課題は、上げる依頼を始めない。
- [ ] 足す依頼が `none` で閉じ、ほかの条件を満たす課題は、上げる依頼を始める。
- [ ] 計画を作り直して承認し直す → `pending` の足す依頼は `superseded` になる。
- [ ] 「足す」の形の判断点の費用は、課題の見込みに入らない。

### フォローアップをタスクに上げる

- [ ] 統合先を使う、着手中の課題に属する、未のフォローアップを上げる → 新しい課題はできず、その課題に、出どころ `followup` の足す依頼（`pending`）ができる。
- [ ] 同じフォローアップを `--new-challenge` で上げる → 新しい課題ができ、足す依頼はできない。
- [ ] 課題に属さないフォローアップを上げる → 新しい課題ができる。
- [ ] 完了した課題に属するフォローアップを上げる → 新しい課題ができる。
- [ ] 完了の承認待ちの課題に属するフォローアップを上げる → 新しい課題ができる。
- [ ] 統合先を使わない、着手中の課題に属するフォローアップを上げる → 新しい課題ができる。
- [ ] 課題の保留が開いている課題に属するフォローアップを上げる → 新しい課題ができる。
- [ ] 開いている保留がタスクの保留だけの、保留中の課題に属するフォローアップを上げる → その課題に、足す依頼ができる。
- [ ] 上げる先が新しい課題になったとき、要約と出力に、タスクにしなかった理由が出る。
- [ ] 枠を指定せずにタスクとして上げる → 足す依頼の枠は、宣言のサイズ S の額になる。
- [ ] `--budget-impl-usd` を付けて上げる → 足す依頼の実装の枠は、その額になる。
- [ ] `--preview` → 上げる先・足すタスクの枠・足した後の見込み・上限を返す。
- [ ] `--preview` → フォローアップも課題も、書き換えない。
- [ ] `--preview` は、本人確認なしで通る。
- [ ] 足した後の見込みが上限を超える、ターミナルでの本人確認の要約に、上限の前の額と後の額が出る。
- [ ] その本人確認を通す → 上限が、足した後の見込みと同じ額になる。
- [ ] 足した後の見込みが上限を超える、`--relayed` で `--raise-limit` 無しの実行 → 検証の誤りで断り、足す依頼はできない。
- [ ] 同じ実行の出力に、超える額が出る。
- [ ] 足した後の見込みが上限を超える、`--relayed` で `--raise-limit` 付きの実行 → 足す依頼ができ、上限が上がる。
- [ ] 足した後の見込みが上限以下のとき、上限は変わらない。
- [ ] タスクとして上げた後、フォローアップの状態は、未のまま。
- [ ] 出どころ `followup` の足す依頼の「足す」の形の入力に、フォローアップの題名が入っている。
- [ ] 判断値が `add`（タスク 1 個）→ タスクの行ができ、枠は、足す依頼の額である（出力の枠の値を使わない）。
- [ ] 同じとき、フォローアップに、上げた先のタスクが記録される。
- [ ] 出どころ `followup` で、判断値が `none` → 不正な出力として扱う。
- [ ] 出どころ `followup` で、タスクが 2 個の出力 → 不正な出力として扱う。
- [ ] 上げた先のタスクが済みになる → フォローアップが済みになる。
- [ ] 同じとき、フォローアップの「確かめた結果」に、上げた先のタスクの ID が入る。
- [ ] 上げた先のタスクが取りやめになる → フォローアップは未のままで、もう一度上げられる。
- [ ] 上げた先のタスクが未着手・着手中のフォローアップを、もう一度上げる → 検証の誤りで断る。
- [ ] 上げる依頼が開いている課題に、タスクとして上げる → 次の状態の確認で、上げる依頼が取り消される。
- [ ] 同じとき、作ってあった反映の操作は閉じる。
- [ ] 足したタスクが統合先に入った後、上げる依頼が始まる。

### 保留中の課題のほかのタスク

- [ ] タスク A の保留が開いている課題で、A を前提に持たない、前提が済みの未着手のタスク B → 委譲の段で起動される。
- [ ] 同じ課題で、A を前提に持つ未着手のタスク C → 起動されない。
- [ ] 同じ課題で、C を前提に持つ未着手のタスク D → 起動されない。
- [ ] 同じ課題で、レビュー待ちの、止めないタスクの実行 → レビュー待ちの受け取りが行われる。
- [ ] 同じ課題で、検証中の、止めないタスク → タスクの検証が行われる。
- [ ] 同じ課題で、検証に通った、止めないタスクの実行に → 「入れてよい」が返る。
- [ ] 同じ課題で、タスク A の実行がレビュー待ちになっても → 受け取りは、保留が解けるまで行われない。
- [ ] 保留が指すタスクが済みの課題（例: `task_add_over_limit` の保留）→ 前提が済みの未着手のタスクは、どれも起動される。
- [ ] 課題の保留が開いている課題 → 未着手のタスクは起動されない。
- [ ] タスクの保留と、課題の保留の両方が開いている課題 → 未着手のタスクは起動されない。
- [ ] 親が直接進める保留（`parent_direct`）が開いている課題 → 未着手のタスクは起動されない。
- [ ] 保留中の課題は、未着手・着手中・検証中のタスクが 0 個でも、上げる依頼を始めない。
- [ ] タスク A の保留が開いている課題で、タスク B の処理が保留を要する → 保留の行が 1 つ増え、B を指す。
- [ ] 同じとき、課題の状態は、保留中のまま。
- [ ] 同じとき、タスク A の保留は、開いたまま。
- [ ] タスク B の保留が開いているときに、B の処理が、もう一度保留を要する → 保留の行は増えない。
- [ ] 開いている保留が 2 つの課題に、`--hold` 無しで回答する → 検証の誤りで断り、どの保留も変わらない。
- [ ] 同じ実行の出力に、開いている保留の ID が 2 つとも出る。
- [ ] 開いている保留が 2 つの課題に、`--hold <片方の ID>` で回答する → その保留に回答が記録される。
- [ ] 同じ回答の後、課題は保留中のまま。
- [ ] 同じ回答の後、回答した保留が指していたタスクは、止めるタスクでなくなる。
- [ ] 残りの 1 つに回答する → 課題は、最初に保留にしたときの状態へ戻る。
- [ ] 開いている保留が 1 つの課題に、`--hold` 無しで回答する → いまと同じに通る。
- [ ] `--hold` に、その課題のものでない保留の ID を付ける → 断る。
- [ ] `--hold` に、すでに解けた保留の ID を付ける → 断る。
- [ ] 開いている保留が 2 つの課題に、`--hold <片方>` と `--replan` で回答する → もう片方の保留は、回答なしで閉じる。
- [ ] 同じ回答の後、課題は、計画を作り直す道へ進む。
- [ ] 開いている保留が 2 つの課題を取り下げる → 2 つとも閉じる。
- [ ] 止めないタスクの起動は、同時に走らせる数の上限を超えない。

## オーナーに伺う点（仮に決めて書いたもの）

1. 統合先を使わない課題（タスクが 1 個の課題）に属するフォローアップを上げたときは、新しい課題にする（タスクにできない）。
2. 上限を超えて足すときの進め方は、「上限を上げる操作」「回答（足さずに進む）」「計画を作り直す回答」の 3 つ。
3. 開いている保留が 2 つ以上のとき、回答に、どの保留かの指定（`--hold`）を求める。
4. S4c は、1 つの区切りのまま出す（受入基準は 160 件）。
