# core の見直し 区切り S4c — 計画の後にタスクを足す

## 概要

`docs/features/core-redesign.md` の区切り S4c の仕様。S4a（長く走るサイクル）の実装と並べて書くので、その間だけ別の文書に書き、main に入れるときに `core-redesign.md` へ畳む（S3d・S4d と同じ進め方。オーナーの決定 2026-11-22）。実装は、S4a が main に入ってから始める。

S4c は、2 つに分けて出す（オーナーの決定 2026-11-22）。この文書の実装対象は S4c-1。

- **S4c-1（実装対象）**: 予算の上限。計画の後にタスクを足す。フォローアップを、開いている課題のタスクに上げる。
- **S4c-2（後続）**: 保留中の課題のほかのタスクを進める。

S4c-1 では、保留は、いまと同じ（課題に 1 つ。保留中の課題では、新しいタスクを起動しない）。

設計書（`docs/architecture.md` §21.2）の「足したことは記録して知らせる」のうち、S4c-1 が入れるのは、記録と API の値まで。知らせる口は S4d-2。

> **仮の決め**: 下の「オーナーに伺う点（仮に決めて書いたもの）」は、推奨の案で仮に書いてある。該当の要件には「（仮）」と印す。オーナーの回答で、要件と受入基準を直す。

## 背景・目的

- 設計書（§21.2）は、「計画の承認で、方針・範囲・予算の上限を承認する。その内なら、計画の判断点が承認なしでタスクを足す。足した後の予算の合計が、承認した上限を超えるなら、必ずオーナーへ問う」と決めている。いまは、後からタスクを足せるのは、オーナーが計画の作り直しを指示して、承認し直すときだけ（S3b）。設計が済んでから実装のタスクを確定する課題は、計画を 2 回承認することになる。
- いまは「上限」という別の数字が無い。いまのコードと文書が「課題の上限」と呼んでいるのは、取りやめでないタスクの枠の合計を、そのつど計算した値（`sumTaskBudgets`。S3b）。タスクを 1 つ足すと、必ず合計が増えるので、「承認した上限」を別に持たないと、毎回問うか、歯止めが無いかのどちらかになる。
- フォローアップを上げると、いつも新しい課題になる（S2b）。元の課題がまだ開いていても、分類・計画・計画の承認からやり直しになり、成果は、元の課題と別に検証・承認・反映される。

## ユーザーストーリー

- オーナーとして、計画の承認のときに「この課題は、ここまでなら任せる」という額を 1 回決め、その内で増えるタスクには、いちいち承認を求められたくない。超えるときは、必ず聞いてほしい。
- オーナーとして、開いている課題の途中で出た「後でやること」を、その課題の成果と一緒に仕上げたい。

## 機能要件

語は `docs/glossary.md` に合わせる。この文書では、次の語を使う。

| 語 | 意味 |
|---|---|
| 見込み | 課題の、取りやめでないタスク（済みを含む）の枠の実効値の合計（実装の枠とレビュー対応の枠を足した額）。いまのコードと文書が「課題の上限」と呼んでいる値と同じ計算。枠を決められないタスクがある課題の見込みは「不明」 |
| 上限 | 計画の承認で、オーナーが承認した、課題の予算の上限。見込みが、これを超えてはならない |
| 足す依頼 | 計画の承認の後に、タスクを足すことの 1 件の記録。出どころは、「続きを決めるタスクが済んだ」（`expand`）か、「フォローアップを上げた」（`followup`） |
| 足した後の見込み | いまの見込みに、足すタスクの枠を足した額。比べるそのときに計算する |
| 上げる依頼 | 課題の成果を、統合先から反映先へ上げる依頼（S3b）。「足す依頼」とは別のもの |
| 足せる課題 | 統合先を使う（`uses_integration` が真）、着手中か保留中の課題。検証中・完了の承認待ち・完了・取り下げの課題と、統合先を使わない課題には、足せない |

### 予算の上限

- [ ] 計画を作る判断点（J2）の出力に、課題の上限（`budget_limit_usd`）と、その理由（`budget_limit_reason`）を足す。どちらも省ける。
- [ ] 計画の見込みは、次の値。タスクが全部枠を持てば、その合計。タスクが 1 個で枠が無い計画は、サイズから解決した、実装の額とレビュー対応の額の合計。
- [ ] `budget_limit_usd` が無い計画の上限は、見込みと同じ額にする。
- [ ] `budget_limit_usd` が見込みと同じ額の計画は、理由が無くても通す。
- [ ] `budget_limit_usd` が見込みより小さい計画は、不正な出力として扱う（いまの、判断点の不正な出力と同じ扱い。計画を記録しない）。
- [ ] `budget_limit_usd` が見込みより大きいのに、`budget_limit_reason` が無いか空白だけの計画は、不正な出力として扱う。
- [ ] 計画の承認（T5）で、承認した版の上限と理由を、課題に記録する。計画を作り直して承認し直したときは、新しい版の値で置き換える。
- [ ] 上限の記録が無い課題（S4c-1 より前に計画を承認した課題）の上限は、そのときの見込みと同じ額として扱う（足すと、必ず上限を超える）。
- [ ] 枠を決められないタスクがある課題は、見込みを不明として扱う。API の見込みと上限は `null` を返す。
- [ ] タスクの枠の増額（`flywheel budget`。S3b）で、見込みが上限を超えるときは、同じ書き込みで、上限を見込みまで上げる（枠の増額の承認が、上限の引き上げの承認を兼ねる）。
- [ ] `flywheel budget <課題の ID> --limit <USD>` で、上限だけを変えられる。本人確認は、枠の増額と同じ（ターミナルでの本人確認か、対話で受けたことの記録〔`--relayed`〕）。
- [ ] `--limit` に、見込みより小さい値を付けたら、断る。
- [ ] `--limit` と、タスクの枠の指定（額・タスクの指定）を同時に付けたら、断る。
- [ ] `--limit` の承認の記録は、いまある予算の増額と同じ種類（`budget`）で残す（タスクの指定は無し。対象の版は、承認済みの計画の版）。
- [ ] 上限を変えたことは、作業ログに残す（前の額・後の額・本人確認の方式）。上限を変える 3 つの道（`--limit`・枠の増額・フォローアップを上げる）のどれでも残す。

### 計画の後にタスクを足す（続きを決めるタスク）

- [ ] 計画のタスクに、「このタスクが済んだら、続きのタスクを決める」という印（`expand_after`。真偽）を付けられる。計画の承認で、タスクの行に写す。
- [ ] `expand_after` が真のタスクを持つ計画が、統合先を使わない（`uses_integration` が偽）なら、不正な出力として扱う。
- [ ] 足せる課題で、`expand_after` が真のタスクが済みになったら、次の回りの計画の段が、そのタスクについての足す依頼（状態は「仕様待ち」）を 1 件作る。同じタスクについて、足す依頼は 1 件だけ作る。
- [ ] 計画の段は、着手中の課題の「仕様待ち」の足す依頼について、計画を作る判断点を「足す」の形で呼ぶ。1 回の計画の段で、課題ごとに 1 件（足す依頼の古い順）。
- [ ] 保留中の課題の足す依頼は、保留が解けるまで、判断点を呼ばない。
- [ ] 見込みが不明の課題の足す依頼は、判断点を呼ばず、「仕様待ち」のまま待つ。
- [ ] 「足す」の形は、計画を作る判断点の識別（J2）を保ったまま、対象の選び方・入力の区画・出力の形と検査を、計画の形と別に持つ。
- [ ] 「足す」の形の入力は、次の項目。承認した計画の方針・完了条件・やらないこと。いまのタスクの一覧（鍵・題名・状態・前提）。済んだタスクの結果（委譲先の要約・成果物の一覧・タスクの検証の結果）。上限。上限までの残り（上限 − 見込み）。足す依頼の保留への回答があれば、その文。
- [ ] 「足す」の形の出力は、判断値（`add`・`none`・`ask`）と、足すタスクの一覧（`add` のとき。形は、計画のタスクと同じ）、問い（`ask` のとき）。
- [ ] 判断点の費用は、計画を作る判断点の予算（`judgment_budget_usd.J2`）で数える。課題の見込みには数えない。
- [ ] `none` → 足す依頼を「足さない」で閉じ、何も足さない。
- [ ] `add` で、足した後の見込みが上限以下 → タスクの行を作る（状態は未着手。計画の版は、承認済みの版。足す依頼を指す）。足す依頼を「足した」で閉じる。オーナーの承認は求めない。
- [ ] `add` で、足した後の見込みが上限を超える → タスクの行を作らず、足す依頼を「オーナー待ち」にして、課題を保留にする（保留の理由 `task_add_over_limit`。課題の保留 1 つ。足す依頼が、その保留を指す）。
- [ ] `task_add_over_limit` の保留の問いに、次を書く。足すタスクの題名と枠。足した後の見込み。上限。超える額。3 つの進め方（下）。
- [ ] `ask` → タスクの行を作らず、課題を保留にする（保留の理由 `task_add_question`。問いは、判断点の問い。足す依頼が、その保留を指す）。足す依頼は「仕様待ち」のまま。回答の後、次の回りで、回答を入力に足して、判断点を呼び直す。
- [ ] 足すタスクの検査は、計画のタスクと同じ項目（題名・本文・完了条件・リポジトリ・操作の種類・枠）に、次を足す。
  - 鍵が、承認済みの版のタスク（取りやめ・済みを含む）の鍵と重ならない。
  - 前提は、足すタスクか、同じ課題の、取りやめでない、いまあるタスクの鍵を指す。
  - 前提に輪が無い（いまあるタスクとの辺を含めて調べる）。
  - リポジトリは、いまあるタスクと同じ 1 つ。
  - 1 回に足せるのは、1 回の計画のタスクの上限（いま 12）と同じ件数まで。
- [ ] 検査に通らない出力と、形が不正な出力は、不正な出力として扱う。そのとき、足す依頼は「仕様待ち」のまま、タスクの行は増やさず、計画を作る判断点の連続の失敗に数え、次の回りで呼び直す。連続の失敗が上限に達したら、いまある、連続失敗の保留にする。
- [ ] `task_add_over_limit` の保留は、次の 3 つで進められる（仮）。
  - 上限を、足した後の見込み以上に上げる（`flywheel budget <課題の ID> --limit <USD>`）→ 同じ書き込みで、タスクの行を作り、足す依頼を「足した」で閉じ、保留を閉じ（回答なしで閉じる）、課題を、保留の前の状態へ戻す。
  - 文で回答する（`flywheel answer`）→ 足す依頼を「見送り」で閉じ、足さずに進む。
  - 計画を作り直す回答（`--replan`）→ 足す依頼を「取り替え」で閉じ、計画を作り直す（S3b のまま）。
- [ ] 足した後の見込みは、保留を解くときに計算し直す（判定したときの値で固定しない）。
- [ ] `task_add_over_limit` の保留の間に、`--limit` に、見込み以上で、足した後の見込みより小さい値を付けたら、上限は変わるが、タスクは足さず、保留も、足す依頼も、開いたまま。
- [ ] `--limit` が保留を閉じるときは、状態遷移を伴う操作として扱う（課題の版を進める。確かめたときの課題の版と違えば断る）。上限だけを変えるときは、課題の版を進めない。
- [ ] 済みの `expand_after` のタスクで、足す依頼がまだ無いものがある課題と、閉じていない（「仕様待ち」「オーナー待ち」）足す依頼がある課題は、上げる依頼を始めず、検証中へ進めない。
- [ ] 計画を作り直して承認し直したとき、閉じていない足す依頼は「取り替え」で閉じる。出どころがフォローアップのものは、フォローアップが未のまま残り、上げ直せる。

### フォローアップを、開いている課題のタスクに上げる

- [ ] `flywheel followup promote <フォローアップの ID>` の上げる先を、次の順で決める。
  - `--new-challenge` を付けた → 新しい課題（いまと同じ）。
  - フォローアップが課題に属し、その課題が、足せる課題 → その課題のタスク。
  - それ以外 → 新しい課題。課題に属さない。元の課題が、検証中・完了の承認待ち・完了・取り下げ。元の課題が、統合先を使わない（仮）。
- [ ] 上げる先が新しい課題になったとき、要約と出力に、タスクにしなかった理由を出す。
- [ ] 上げる先がタスクのとき、足すタスクの枠は、サイズ S の既定（宣言 `size_budgets_usd.S`）。`--budget-impl-usd`・`--budget-review-usd` で変えられる。
- [ ] 本人確認の前に見せる要約に、次を出す。上げる先（課題の題名と ID、または「新しい課題」）。足すタスクの枠。足した後の見込み。上限。上限を超えるときは、超える額と、上げた後の上限。
- [ ] `flywheel followup promote <ID> --preview` は、上の要約と同じ値を、何も書かずに返す（本人確認なし。`--json` あり）。
- [ ] 足した後の見込みが上限を超えるとき、ターミナルでの本人確認では、確かめた指示を、上限の引き上げの承認として扱う（上限を、足した後の見込みまで上げる）。
- [ ] 足した後の見込みが上限を超えるとき、対話で受けたことの記録（`--relayed`）では、`--raise-limit <上げた後の上限の額>` が無ければ断る（終了コードは検証の誤り。出力に、超える額と、`--preview` で確かめられる旨）。額が、足した後の見込みと違えば、断る。
- [ ] 上げる操作の実行は、確かめたとき（要約を作ったとき）の、上げる先・課題の版・足した後の見込み・上限を入力に持ち、書き込みのときの値と食い違えば、断る（見せた額と違う額で、上限を上げない）。
- [ ] 上げる先がタスクのとき、上げる操作は、同じ書き込みで、足す依頼（出どころ `followup`。状態「仕様待ち」。枠の額つき。フォローアップを指す）を作り、要るなら上限を上げる。フォローアップの状態は、未のまま。
- [ ] 上げる操作の戻り値と CLI の出力（テキストと `--json`）に、上げた先の種類（課題かタスク）と、足す依頼の ID を持たせる。
- [ ] 計画の段が、出どころ `followup` の足す依頼について、判断点を「足す」の形で呼ぶとき、入力に、フォローアップの題名と説明を足す。出力のタスクは 1 個で、枠は、足す依頼の額を使う（出力の枠は読まない）。
- [ ] 出どころ `followup` の `add` にも、上の「続きを決めるタスク」と同じ上限の判定をかける（上げたときに上限を上げていても、そのときの見込みで判定し直す。超えたら `task_add_over_limit` の保留）。
- [ ] 出どころ `followup` の `add` で足したら、フォローアップに、上げた先のタスクを記録する（`promoted_task_id`）。上げた先の課題の列（`promoted_challenge_id`）は、変えない。上げた先を読む所は、タスクの列に値があれば、そちらを使う。
- [ ] 出どころ `followup` の `ask` は、上の `task_add_question` と同じ。`none` と、タスクが 2 個以上の出力は、不正な出力として扱う。
- [ ] 上げた先のタスクが済みになったら、タスクの状態を書く共通の所で、同じ書き込みで、そのフォローアップを済みにする（確かめた結果に、上げた先のタスクを書く）。
- [ ] 上げ直せるのは、未のフォローアップで、次のどれか。上げたことが無い。上げた先の課題が取り下げ（いまと同じ）。上げた先のタスクが取りやめ。フォローアップを指す足す依頼が、「見送り」か「取り替え」で閉じた。フォローアップを指す、閉じていない足す依頼がある間と、上げた先のタスクが未着手・着手中・検証中の間は、断る。
- [ ] その課題の上げる依頼が開いているときに、タスクとして上げたら、上げる依頼を取り消す（S3b の、課題の単位の確かめが「満たしていない」のときと同じ道。作った反映の操作は閉じる）。足したタスクが統合先に入った後、上げる依頼を始め直す。
- [ ] 1 回に上げるのは 1 件（いまと同じ）。

### 見せ方（core・CLI・API の値）

- [ ] 課題の詳細（`GET …/challenges/<ID>` と `flywheel show --json`）に、予算（`budget`: `estimate_usd`・`limit_usd`・`limit_reason`）を足す。上限の記録が無い課題の `limit_usd` は、見込みと同じ額。見込みが不明の課題は、`estimate_usd`・`limit_usd` が `null`。
- [ ] 計画の承認待ちの課題では、`budget` は、承認を待っている版の計画の値を返す。
- [ ] 画面の計画の承認に、「見込み・上限」と、上限の理由を出す（上限が見込みと同じなら、理由は出さない）。
- [ ] `flywheel show`（テキスト）に、見込みと上限を出す。
- [ ] 課題の詳細のタスクの要素に、足されたタスクの印（`added`: `origin`・`origin_task_id`・`followup_id`・`added_at`。計画の承認で作ったタスクは `null`）を足す。
- [ ] 課題の詳細に、足す依頼の一覧（`additions[]`: `id`・`origin`・`state`・`origin_task_id`・`followup_id`・`task_ids`・`total_after_usd`・`limit_usd`・`created_at`・`decided_at`。閉じたものも含む）を足す。
- [ ] フォローアップの要素に、上げた先のタスク（`promoted_task_id`）を足す。
- [ ] タスクを足したことは、作業ログに残す（足す依頼・足したタスク・足した後の見込みと上限）。
- [ ] `flywheel cycle` の出力に、その回に足したタスクを出す（課題・タスクの題名・出どころ）。
- [ ] 完了の承認の要約（`flywheel show` と API）に、計画の後に足したタスクの一覧を出す。

### サイクルとの関係（S4a）

- [ ] 「いま始められるもの」（S4a）に、着手中の課題の「仕様待ち」の足す依頼と、足せる着手中の課題の、済みになった `expand_after` のタスクで足す依頼がまだ無いものを数える。「オーナー待ち」の足す依頼、保留中の課題の足す依頼、見込みが不明の課題の足す依頼は、数えない。
- [ ] 上限を変える操作（`flywheel budget … --limit`）は、枠の増額と同じに、成立の後でサイクルを始める（S4a の決まり。きっかけは `budget`）。

### 文書

## 技術的な制約・方針

- 開発に固有の知識を、core に新しく足さない（オーナーの決定 2026-11-22）。足すタスクの中身は、計画のタスクと同じ項目だけを持つ。
- 判断は判断点が返し、遷移と数字の判定は core が行う（P2 のまま）。上限を超えるかは、core が数字で判定する。
- 委譲先との契約は、変えない。claude-harness の側で要るものは無い。
- ストアの版は、S4a（版 31）・対話の欄（版 32）の次。番号は、main に入れる順で決める。マイグレーションは 1 本。
- 進行中の課題を新しい形へ移す処理は作らない。過去の行は書き換えない（上限の記録が無い課題は、読むときに見込みと同じ額として扱う）。
- 判断点の指示文（`j2.md`）に、次を書く。上限と理由の書き方。`expand_after` の付け方。「足す」の形では、計画の「やらないこと」に触れるタスクは足さない・方針の外かどうか迷ったら `ask` にする・判断や人の作業が要る点が出たら `ask` にする。
- 型を変えたら、`go generate ./internal/view` で `web/src/api/types.gen.ts` を作り直す。

## 画面・API設計

- 画面で変えるのは、計画の承認の「見込み・上限」の 1 か所だけ。足されたタスクの印・足す依頼の見せ方、フォローアップと取り込みのボタンは、S4d-2（`core-redesign-s4d.md`）。S4c-1 は、そのための値を API に出す。
- 新しい口は作らない。`GET …/challenges/<ID>`・フォローアップの一覧の応答にキーを足す。型は `internal/view` に足す。

## クリティカル設計決定

### 承認の意味: 上限は 1 つの額で、課題に記録する

- **採用案**: 上限は、実装の枠とレビュー対応の枠を足した、1 つの額にする。計画の承認のときに、課題の記録（`challenge.budget_limit_micros`・`budget_limit_reason`）に写す（統合先を使うか〔`uses_integration`〕と同じ持ち方）。
- **理由**: オーナーが承認するのは「この課題に、いくらまで」の 1 つの数字（オーナーの決定 2026-11-22「計画が上限を別に示す」）。枠ごとに 2 つ持つと、承認の画面の数字が 4 つになり、どちらの枠で超えたかの問いが増える。枠ごとの歯止めは、タスクの枠（S3b）が持っている。課題に写すのは、サイクルが、計画の本文を読み直さずに判定するため。
- **代替案**: 計画の表（`task_plan`）に持つ。版ごとに値が残るが、承認していない版の値を読む誤りが起きうる。承認した値だけを課題に持つほうが、読む所が 1 つで済む。

### 承認の意味: 上限を超えて足すには、上限を上げる操作を使う（仮）

- **採用案**: 上限を超える足す依頼は、オーナーが上限を上げたとき（`flywheel budget … --limit`。本人確認つき）にだけ、足す。保留への文の回答は、「足さずに進む」として扱う。足した後の見込みは、上げるときに計算し直す。
- **理由**: 設計書は「超えるなら、必ずオーナーへ問う」としている。文の回答を「足してよい」と読むと、core が文の意味を判定することになる（P2 に反する）。額を上げる操作は、数字で判定でき、枠の増額と同じ本人確認と記録を使える。保留の間に、枠の増額で見込みが動きうるので、判定したときの値では比べない。
- **代替案**: 保留の問いに選択肢を持たせ、選ぶだけで答える。問いの構造は S4b・S4d-2 で入るので、S4c-1 は待たない。入った後は、この保留にも選択肢を付けられる。

### 承認の意味: フォローアップを上げる指示が、上限の引き上げの承認を兼ねる

- **採用案**: タスクとして上げて上限を超えるときは、上げる前に、増える額を見せ、上げる指示を、その引き上げの承認として扱う（オーナーの決定 2026-11-22）。上げる操作の書き込みは、見せたときの値（上げる先・課題の版・足した後の見込み・上限）と同じであることを確かめ、違えば断る。対話で受けた記録では、`--raise-limit <上げた後の上限の額>` を明示したときだけ受け、額が違えば断る。
- **理由**: 上げる操作は、本人確認つきの、オーナーの指示。ターミナルでは、本人確認の前の要約で額を見せられる。対話で受けた記録では、core は、オーナーが額を見たかを確かめられないので、オーケストレーターが `--preview` で額を伝えたうえで、その額を明示する形にする。見せた額と違う額で上限が上がると、承認していない額を承認したことになる。
- **代替案**: 上限を超えるときは、先に `flywheel budget … --limit` を求める。操作が 2 回になる。

### 状態遷移: 足す依頼から立つ保留は、いまある保留の遷移を使う

- **採用案**: `task_add_over_limit`・`task_add_question` の保留は、いまある保留（T11）と回答（T12）の遷移を使う。課題に、開いている保留は 1 つ（S3b のまま）。保留中の課題の足す依頼は、保留が解けるまで判断点を呼ばないので、2 つ目の保留は要らない。新しく足すのは、`--limit` が保留を閉じる道だけ（回答なしで閉じ、保留の前の状態へ戻す。課題の版を進める）。
- **理由**: 保留を課題に重ねて持つ形（S4c-2）を待たずに出せる。`--limit` が保留を閉じるのは、額の操作が「足してよい」の答えを兼ねるため。回答なしで保留を閉じる前例は、親が直接進める保留にある。
- **代替案**: `--limit` の後、別に `flywheel answer` を求める。操作が 2 回になり、上限を上げたのに足されない状態が見える。

### DB スキーマ: 足す依頼の表と、列

- **採用案**: 表 `task_addition`（足す依頼）を足す。`id`・`challenge_id`・`origin`（`expand`・`followup`）・`origin_task_id`（NULL 可）・`followup_id`（NULL 可）・`state`（`pending`〔仕様待ち〕・`awaiting_owner`〔オーナー待ち〕・`applied`〔足した〕・`none`〔足さない〕・`declined`〔見送り〕・`superseded`〔取り替え〕）・`spec`（判断点が返したタスクの一覧。NULL 可）・`budget_impl_micros`・`budget_review_micros`（出どころが `followup` のときの枠。NULL 可）・`total_after_micros`・`limit_micros`（最後に判定したときの値。記録のためで、判定には使わない。NULL 可）・`hold_id`（足す依頼から立てた保留。NULL 可）・`created_at`・`decided_at`。列は、`task.addition_id`（NULL 可）・`task.expand_after`（既定 0）・`challenge.budget_limit_micros`（NULL 可）・`challenge.budget_limit_reason`（NULL 可）・`followup.promoted_task_id`（NULL 可）。同じ出どころのタスクについて、`origin = 'expand'` の行は 1 つ（部分一意索引）。
- **理由**: 上限を超えたときに、タスクの行を作らずに、足す中身を持っておく場所が要る。タスクの状態に「提案」を足すと、タスクを数えている所（起動・上げる依頼の条件・見込み）をすべて直すことになる。足す依頼の行は、「足したことの記録」と、足されたタスクの印（`task.addition_id`）も兼ねる。保留への回答の処理は、`hold_id` から足す依頼を引く。
- **代替案**: 作業ログだけに残す。上限を超えて待っている中身を、後で読み出す所が無い。

## 機能全体の設計

### 流れ

1. 計画の承認: 上限と理由を課題に写す。タスクの行に `expand_after` を写す。
2. 計画の段（回りごと）: ① 足せる課題の、済みになった `expand_after` のタスクで、足す依頼が無いもの → 足す依頼を作る。② 着手中の課題ごとに、「仕様待ち」の足す依頼の古いもの 1 件について、判断点を「足す」の形で呼ぶ。③ 出力を検査し、足した後の見込みと上限を比べ、足すか、保留にする。
3. 委譲の段: 足したタスクは、ほかのタスクと同じに起動する。
4. 上げる依頼を始める条件（S3b）に、「閉じていない足す依頼が無い」「済みの `expand_after` のタスクで、足す依頼がまだ無いものが無い」を足す。

## やらないこと

- 統合先を使わない課題（タスクが 1 個の課題）にタスクを足すこと（理由: 統合先を使うかは、計画の承認の時点の値で、途中で変えない。フォローアップは、新しい課題に上がる）
- 検証中・完了の承認待ち・完了・取り下げの課題に、タスクを足すこと（理由: 完了の差し戻しの後の、計画の作り直しの道〔S3b〕がある）
- 取り込み元の親に、後から足された子を、タスクとして取り込むこと（理由: いまは、新しい課題として「取り込めるもの」に並ぶ。取り込みの形を変えるのは、別の区切りで決める）
- 上限を、実装の枠とレビュー対応の枠に分けて持つこと
- 計画を 2 段にして、設計の後にもう一度承認する形（理由: 設計書 §21.2 で、既定にしないと決めている）
- 保留の問いに選択肢を持たせること、画面のボタンで答えること（理由: S4b・S4d-2）
- 足されたタスクの印・足す依頼の画面、フォローアップと取り込みのボタン（理由: S4d-2。S4c-1 は API の値まで）
- スーパーバイザーが、タスクを足す・フォローアップを書くこと（理由: S4b）
- 足したことを、画面の外へ知らせること（理由: 知らせる口は S4d-2）
- 開発に固有の知識を、core に足すこと（理由: flywheel#981）

## 受入基準

実ストアと、テスト用の委譲先・テスト用の判断点で確かめる。「足せる課題」は、統合先を使う課題を指す。

### 予算の上限

- [ ] 計画の出力に `budget_limit_usd` が無い計画を承認すると、課題の上限は、見込みと同じ額になる。
- [ ] `budget_limit_usd` が見込みより大きく、`budget_limit_reason` がある計画を承認すると、課題の上限は、`budget_limit_usd` の額になる。
- [ ] `budget_limit_usd` が見込みより大きく、`budget_limit_reason` がある計画を承認すると、課題の上限の理由は、`budget_limit_reason` の文になる。
- [ ] `budget_limit_usd` が見込みと同じ額で、`budget_limit_reason` が無い計画は、不正な出力にならず、計画が記録される。
- [ ] `budget_limit_usd` が見込みより小さい計画の出力は、不正な出力として扱われ、計画が記録されない。
- [ ] `budget_limit_usd` が見込みより大きく、`budget_limit_reason` が無い計画の出力は、不正な出力として扱われる。
- [ ] `budget_limit_usd` が見込みより大きく、`budget_limit_reason` が空白だけの計画の出力は、不正な出力として扱われる。
- [ ] タスクが 1 個で枠が無い計画の見込みは、サイズから解決した、実装の額とレビュー対応の額の合計である。
- [ ] 計画を承認する前の、計画の承認待ちの課題の、上限の記録は、NULL のまま。
- [ ] 上限の記録がある課題で、計画を作り直して承認し直すと、課題の上限は、新しい版の値になる。
- [ ] 上限の記録が無い課題の詳細の `budget.limit_usd` は、`budget.estimate_usd` と同じ額である。
- [ ] 枠を決められないタスクがある課題の詳細の `budget.estimate_usd` は `null` である。
- [ ] 枠を決められないタスクがある課題の詳細の `budget.limit_usd` は `null` である。
- [ ] タスクの枠の増額で、見込みが上限を超えると、同じ書き込みで、上限が、増額の後の見込みと同じ額になる。
- [ ] タスクの枠の増額で、見込みが上限以下のままなら、上限は変わらない。
- [ ] `flywheel budget <課題の ID> --limit <見込み以上の額>` を、ターミナルでの本人確認を通して実行すると、上限が、その額になる。
- [ ] `flywheel budget <課題の ID> --limit <見込み以上の額>` を、`--relayed` で実行すると、上限が、その額になる。
- [ ] `flywheel budget <課題の ID> --limit <見込みより小さい額>` は、検証の誤りで断られ、上限は変わらない。
- [ ] `flywheel budget <課題の ID> --limit` を、本人確認なし（ターミナルでなく、`--relayed` も無い）で実行すると、断られ、上限は変わらない。
- [ ] `flywheel budget` に、`--limit` と、タスクの枠の額の指定を同時に付けると、検証の誤りで断られる。
- [ ] 保留が無い課題で `--limit` が成立しても、課題の版は変わらない。
- [ ] `--limit` が成立すると、承認の記録（種類 `budget`・タスクの指定なし）が 1 行できる。

### 続きを決めるタスク

印・足す依頼を作る:

- [ ] `expand_after: true` のタスクを持つ計画を承認すると、そのタスクの行の `expand_after` が 1 になる。
- [ ] `expand_after: true` のタスクを持ち、`uses_integration` が偽の計画の出力は、不正な出力として扱われる。
- [ ] 足せる着手中の課題で、印の付いたタスクが済みになると、次の計画の段で、そのタスクを出どころにする足す依頼（`origin` が `expand`・`state` が `pending`）が 1 件できる。
- [ ] 足す依頼ができた、足せる着手中の課題では、同じ計画の段で、判断点が「足す」の形で 1 回呼ばれる。
- [ ] 足す依頼がすでにあるタスクについて、次の回りの計画の段を通しても、足す依頼は増えない。
- [ ] 印の無いタスクが済みになっても、足す依頼はできない。
- [ ] 印の付いたタスクが済みでない間は、足す依頼はできない。
- [ ] 保留中の課題の `pending` の足す依頼について、計画の段は、判断点を呼ばない。
- [ ] 保留が解けて着手中へ戻った課題の `pending` の足す依頼について、次の計画の段で、判断点が「足す」の形で呼ばれる。
- [ ] 見込みが不明の課題の `pending` の足す依頼について、計画の段は、判断点を呼ばない。
- [ ] `pending` の足す依頼が 2 件ある着手中の課題では、1 回の計画の段で、判断点は、古いほうの 1 件についてだけ呼ばれる。

入力:

- [ ] 「足す」の形の入力に、承認した計画の方針が入っている。
- [ ] 「足す」の形の入力に、承認した計画の完了条件が入っている。
- [ ] 「足す」の形の入力に、承認した計画の「やらないこと」が入っている。
- [ ] 「足す」の形の入力に、いまのタスクの鍵と題名が入っている。
- [ ] 「足す」の形の入力に、いまのタスクの状態が入っている。
- [ ] 「足す」の形の入力に、いまのタスクの前提が入っている。
- [ ] 「足す」の形の入力に、済んだタスクの、委譲先の要約が入っている。
- [ ] 「足す」の形の入力に、済んだタスクの、成果物の一覧が入っている。
- [ ] 「足す」の形の入力に、済んだタスクの、タスクの検証の結果が入っている。
- [ ] 「足す」の形の入力に、上限の額が入っている。
- [ ] 「足す」の形の入力に、上限までの残り（上限 − 見込み）の額が入っている。
- [ ] 「足す」の形の判断点の費用は、課題の見込みに入らない。

`none`・`add`:

- [ ] 判断値が `none` のとき、足す依頼の状態は `none` になる。
- [ ] 判断値が `none` のとき、タスクの行は増えない。
- [ ] 判断値が `add` で、足した後の見込みが上限と同じ額のとき、タスクの行ができ、足す依頼の状態は `applied` になり、課題は保留にならない。
- [ ] 判断値が `add` で、足した後の見込みが上限より小さいとき、タスクの行ができ、足す依頼の状態は `applied` になり、課題は保留にならない。
- [ ] 上限以下で足したタスクの状態は、未着手（`pending`）である。
- [ ] 上限以下で足したタスクの計画の版は、承認済みの版である。
- [ ] 上限以下で足したタスクの行の `addition_id` は、足す依頼の ID である。
- [ ] 上限以下で足したタスクの題名は、判断点の出力の題名である。
- [ ] 足すタスクの前提に、いまあるタスクの鍵を書いた出力で足すと、そのタスクへの前提の行ができる。
- [ ] 上限以下で足したタスクは、前提が済みなら、同じサイクルの委譲の段で起動される。

上限を超える:

- [ ] 判断値が `add` で、足した後の見込みが上限を超えるとき、タスクの行は増えない。
- [ ] 判断値が `add` で、足した後の見込みが上限を超えるとき、足す依頼の状態は `awaiting_owner` になる。
- [ ] 判断値が `add` で、足した後の見込みが上限を超えるとき、課題は保留中になり、保留の理由は `task_add_over_limit` である。
- [ ] `task_add_over_limit` の保留を立てた足す依頼の `hold_id` は、その保留の ID である。
- [ ] `task_add_over_limit` の保留の問いに、足すタスクの題名が入っている。
- [ ] `task_add_over_limit` の保留の問いに、足すタスクの枠の額が入っている。
- [ ] `task_add_over_limit` の保留の問いに、足した後の見込みの額が入っている。
- [ ] `task_add_over_limit` の保留の問いに、上限の額が入っている。
- [ ] `task_add_over_limit` の保留の問いに、超える額が入っている。
- [ ] `task_add_over_limit` の保留の問いに、3 つの進め方（上限を上げる・回答する・計画を作り直す）が入っている。
- [ ] `task_add_over_limit` の保留の間に、`--limit` で、上限を、足した後の見込みと同じ額へ上げると、タスクの行ができる。
- [ ] `task_add_over_limit` の保留の間に、`--limit` で、上限を、足した後の見込み以上へ上げると、足す依頼の状態は `applied` になる。
- [ ] `task_add_over_limit` の保留の間に、`--limit` で、上限を、足した後の見込み以上へ上げると、保留は、回答なしで閉じる。
- [ ] `task_add_over_limit` の保留の間に、`--limit` で、上限を、足した後の見込み以上へ上げると、課題は、保留の前の状態（着手中）へ戻る。
- [ ] `task_add_over_limit` の保留の間に、`--limit` で、上限を、足した後の見込み以上へ上げると、課題の版が進む。
- [ ] `--limit` が保留を閉じて作ったタスクの題名・前提・計画の版は、足す依頼に保存した判断点の出力のとおりである。
- [ ] `task_add_over_limit` の保留を閉じる `--limit` の実行で、確かめたときの課題の版と、書き込みのときの版が違うと、断られ、上限も保留も変わらない。
- [ ] `task_add_over_limit` の保留の間に、`--limit` に、見込みより小さい額を付けると、検証の誤りで断られる。
- [ ] `task_add_over_limit` の保留の間に、`--limit` に、見込み以上で、足した後の見込みより小さい額を付けると、上限は、その額になる。
- [ ] `task_add_over_limit` の保留の間に、`--limit` に、見込み以上で、足した後の見込みより小さい額を付けると、タスクの行は増えず、保留は開いたままで、足す依頼は `awaiting_owner` のまま。
- [ ] `task_add_over_limit` の保留の間に、タスクの枠の増額で見込みが増えた後は、`--limit` に、保留を立てたときの「足した後の見込み」の額を付けても、タスクは足されない（計算し直した額より小さいため）。
- [ ] `task_add_over_limit` の保留に、文で回答すると、足す依頼の状態は `declined` になる。
- [ ] `task_add_over_limit` の保留に、文で回答すると、タスクの行は増えず、課題は着手中へ戻る。
- [ ] `task_add_over_limit` の保留に、計画を作り直す回答（`--replan`）をすると、足す依頼の状態は `superseded` になる。

`ask`:

- [ ] 判断値が `ask` のとき、課題は保留中になり、保留の理由は `task_add_question` である。
- [ ] 判断値が `ask` のとき、保留の問いは、判断点が返した問いの文である。

上げる依頼・作り直し:

- [ ] 足す依頼が `none` で閉じ、ほかの条件を満たす課題は、上げる依頼を始める。
- [ ] 足す依頼が `pending` の課題は、検証中へ進まない。
- [ ] `pending` の足す依頼がある課題で、計画を作り直して承認し直すと、その足す依頼は `superseded` になる。
- [ ] `awaiting_owner` の足す依頼がある課題で、計画を作り直して承認し直すと、その足す依頼は `superseded` になる。

- [ ] 取り下げた課題に属するフォローアップを上げると、新しい課題ができる。
