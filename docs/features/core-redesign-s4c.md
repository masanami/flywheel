# core の見直し 区切り S4c — 計画の後にタスクを足す

## 概要

`docs/features/core-redesign.md` の区切り S4c の仕様。S4a（長く走るサイクル）の実装と並べて書くので、その間だけ別の文書に書き、main に入れるときに `core-redesign.md` へ畳む（S3d・S4d と同じ進め方。オーナーの決定 2026-11-22）。実装は、S4a と S4b（S4b-1〜S4b-3）が main に入ってから始める（上限を超えたときの問いに、S4b-1 が足す、選択肢つきの問いの口を使うため。順番は S4a → S4b-1（選択肢で答える仕組み）→ S4b-2（想定外の止まりへの対処）→ S4b-3（委譲先の問いに答える）→ S4c-1 → S4c-2 → S4c-3 → 画面の残り〔S4d-2〕。1 回ごとに実装して確かめ、main へ入れる）。

S4c-1 の仕様は `core-redesign.md`（「S4c-1 で入れた要件」「S4c-1 の受入基準」）へ畳んだ。この文書の S4c-1 の節は、S4c-2 が参照するため残す。

S4c は、3 つに分けて出す（オーナーの決定 2026-11-22）。この文書の実装対象は S4c-3（S4c-1 は flywheel#1126、S4c-2 は flywheel#1162 で main に入った）。機能要件・設計の決定・実装の見通しの項目は、節の見出しか、項目の頭の印（〔S4c-2〕・〔S4c-3〕）で、どのスライスかを示す（印の無い項目は S4c-1）。

- **S4c-1（出荷済み）**: 予算の上限。計画の後にタスクを足す（続きを決めるタスク）。
- **S4c-2（出荷済み）**: フォローアップを、開いている課題のタスクに上げる。
- **S4c-3（実装対象）**: 保留中の課題のほかのタスクを進める。

S4c-1 と S4c-2 では、保留は、いまと同じ（課題に 1 つ。保留中の課題では、新しいタスクを起動しない）。S4c-3 で、タスクを止める保留を、課題に重ねて持てるようにする。

設計書（`docs/architecture.md` §21.2）の「足したことは記録して知らせる」のうち、S4c-1 と S4c-2 が入れるのは、記録と API の値まで。知らせる口は S4d-2。

## 背景・目的

- 設計書（§21.2）は、「計画の承認で、方針・範囲・予算の上限を承認する。その内なら、計画の判断点が承認なしでタスクを足す。足した後の予算の合計が、承認した上限を超えるなら、必ずオーナーへ問う」と決めている。いまは、後からタスクを足せるのは、オーナーが計画の作り直しを指示して、承認し直すときだけ（S3b）。設計が済んでから実装のタスクを確定する課題は、計画を 2 回承認することになる。
- いまは「上限」という別の数字が無い。いまのコードと文書が「課題の上限」と呼んでいるのは、取りやめでないタスクの枠の合計を、そのつど計算した値（`sumTaskBudgets`。S3b）。タスクを 1 つ足すと、必ず合計が増えるので、「承認した上限」を別に持たないと、毎回問うか、歯止めが無いかのどちらかになる。
- フォローアップを上げると、いつも新しい課題になる（S2b）。元の課題がまだ開いていても、分類・計画・計画の承認からやり直しになり、成果は、元の課題と別に検証・承認・反映される。

## ユーザーストーリー

- オーナーとして、計画の承認のときに「この課題は、ここまでなら任せる」という額を 1 回決め、その内で増えるタスクには、いちいち承認を求められたくない。超えるときは、必ず聞いてほしい。
- オーナーとして、開いている課題の途中で出た「後でやること」を、その課題の成果と一緒に仕上げたい。

## 機能要件

語は `docs/glossary.md` に合わせる。この文書では、次の語を使う。

| 語 | 意味 |
|---|---|
| 見込み | 課題の、取りやめでないタスク（済みを含む）の枠の実効値の合計（実装の枠とレビュー対応の枠を足した額）。いまのコードと文書が「課題の上限」と呼んでいる値と同じ計算。枠を決められないタスクがある課題の見込みは「不明」 |
| 上限 | 計画の承認で、オーナーが承認した、課題の予算の上限。見込みが、これを超えてはならない |
| 足す依頼 | 計画の承認の後に、タスクを足すことの 1 件の記録。出どころは、「続きを決めるタスクが済んだ」（`expand`）か、「フォローアップを上げた」（`followup`。S4c-2 から。S4c-1 の出どころは `expand` だけ） |
| 足した後の見込み | いまの見込みに、足すタスクの枠を足した額。比べるそのときに計算する |
| 上げる依頼 | 課題の成果を、統合先から反映先へ上げる依頼（S3b）。「足す依頼」とは別のもの |
| 足せる課題 | 統合先を使い（`uses_integration` が真）、着手中か保留中で、見込みが不明でない課題。これ以外の課題（着手中より前の状態・検証中・完了の承認待ち・完了・取り下げの課題、統合先を使わない課題、見込みが不明の課題）には、足せない |
| 計画の見込み | 承認を待っている版の計画を承認したときに、課題の見込みになる額。下の「予算の上限」の定義 |

### 予算の上限（S4c-1）

- [ ] 計画を作る判断点（J2）の出力に、課題の上限（`budget_limit_usd`）と、その理由（`budget_limit_reason`）を足す。どちらも省ける。
- [ ] 計画の見込みは、次の 2 つの合計。(1) その課題の、取りやめにならずに残る、ほかの版のタスク（計画の作り直しで残る、済みのタスク）の枠の実効値の合計。(2) この版のタスクの枠の実効値の合計。枠の無いタスクは、いまある決まりで埋める（2 個以上のタスクの計画で枠を省いたタスクは、計画の額〔`resolveSpecBudgets`〕。タスクが 1 個で枠が無い計画は、`soleTaskFrames` の決まり）。
- [ ] 承認の前に出す計画の見込みと、承認した直後の課題の見込み（`loadTaskBudgets` と `sumTaskBudgets`）は、同じ値になる。計算は、共通の関数 1 つに置く。
- [ ] `budget_limit_usd` が無い計画の上限は、見込みと同じ額にする。
- [ ] `budget_limit_usd` が見込みと同じ額の計画は、理由が無くても通す。
- [ ] `budget_limit_usd` が見込みより小さい計画は、不正な出力として扱う（いまの、判断点の不正な出力と同じ扱い。計画を記録しない）。
- [ ] `budget_limit_usd` が見込みより大きいのに、`budget_limit_reason` が無いか空白だけの計画は、不正な出力として扱う。
- [ ] 計画の承認（T5）で、承認した版の上限と理由を、課題に記録する。計画を作り直して承認し直したときは、新しい版の値で置き換える。
- [ ] 上限の記録が無い課題（S4c-1 より前に計画を承認した課題）の上限は、そのときの見込みと同じ額として扱う（足すと、必ず上限を超える）。
- [ ] 枠を決められないタスクがある課題は、見込みを不明として扱う。API の見込みと上限は `null` を返す。
- [ ] タスクの枠の増額（`flywheel budget`。S3b）で、見込みが上限を超えるときは、同じ書き込みで、上限を見込みまで上げる（枠の増額の承認が、上限の引き上げの承認を兼ねる）。
- [ ] `flywheel budget <課題の ID> --limit <USD>` で、上限だけを変えられる。本人確認は、枠の増額と同じ（ターミナルでの本人確認か、対話で受けたことの記録〔`--relayed`〕）。
- [ ] `--limit` に、見込みより小さい値を付けたら、断る。
- [ ] `--limit` と、タスクの枠の指定（額・タスクの指定）を同時に付けたら、断る。
- [ ] `--limit` の承認の記録は、いまある予算の増額と同じ種類（`budget`）で残す（タスクの指定は無し。対象の版は、承認済みの計画の版）。
- [ ] 上限を変えたことは、作業ログに残す（前の額・後の額・本人確認の方式）。上限を変える道（`--limit`・枠の増額・`task_add_over_limit` の保留への選択肢 `add` の回答の 3 つ。S4c-2 で、フォローアップを上げる道が加わり、4 つ）のどれでも残す。

### 計画の後にタスクを足す（続きを決めるタスク）（S4c-1）

- [ ] 計画のタスクに、「このタスクが済んだら、続きのタスクを決める」という印（`expand_after`。真偽）を付けられる。計画の承認で、タスクの行に写す。
- [ ] `expand_after` が真のタスクを持つ計画が、統合先を使わない（`uses_integration` が偽）なら、不正な出力として扱う。
- [ ] 足せる課題（着手中でも、保留中でも）で、`expand_after` が真のタスクが済みになったら、次の回りの計画の段が、そのタスクについての足す依頼（状態は「仕様待ち」）を 1 件作る。同じタスクについて、足す依頼は 1 件だけ作る。
- [ ] 計画の段は、着手中の課題の「仕様待ち」の足す依頼について、計画を作る判断点を「足す」の形で呼ぶ。1 回の計画の段で、課題ごとに 1 件（足す依頼の古い順）。
- [ ] 保留中の課題の足す依頼は、保留が解けるまで、判断点を呼ばない。
- [ ] 見込みが不明の課題には、足す依頼を作らない（足せる課題でない）。足す依頼ができた後に見込みが不明になった課題の足す依頼は、判断点を呼ばず、「仕様待ち」のまま待つ。
- [ ] 「足す」の形の判断点の実行は、タスクを持たない、課題の単位の実行にする。同じ課題の、タスクの実行（委譲・タスクの検証）が終わっていなくても、呼べる。サイクルの中の「課題に、終わっていない実行が無い」の検査（`RunJudgment`）は、この形のときだけ、タスクを持たない実行（`taskLessHasActiveRun`）に絞る。
- [ ] 「足す」の形には、計画の形の「分類済みの課題だけ」の検査を当てず、「足す」の形専用の写像を使う（課題の状態は変えない）。
- [ ] 「足す」の形は、計画を作る判断点の識別（J2）を保ったまま、対象の選び方・入力の区画・出力の形と検査を、計画の形と別に持つ。
- [ ] 「足す」の形の入力の先頭に、呼び出しの形の区画（値は「足す」）を置く。指示文（`j2.md`）は、この区画の値で読む節を分ける。計画の形の入力には、この区画が無い。
- [ ] 「足す」の形の入力は、次の項目。承認した計画の方針・完了条件・やらないこと。いまのタスクの一覧（鍵・題名・状態・前提）。済んだタスクの結果（委譲先の要約・成果物の一覧・タスクの検証の結果）。上限。上限までの残り（上限 − 見込み）。足す依頼の保留への回答があれば、その文。
- [ ] 「足す」の形の出力は、判断値（`add`・`none`・`ask`）と、足すタスクの一覧（`add` のとき。形は、計画のタスクと同じ）、問い（`ask` のとき）。
- [ ] 判断点の費用は、計画を作る判断点の予算（`judgment_budget_usd.J2`）で数える。課題の見込みには数えない。
- [ ] `none` → 足す依頼を「足さない」で閉じ、何も足さない。
- [ ] `add` で、足した後の見込みが上限以下 → タスクの行を作る（状態は未着手。計画の版は、承認済みの版。足す依頼を指す）。足す依頼を「足した」で閉じる。オーナーの承認は求めない。
- [ ] `add` で、足した後の見込みが上限を超える → タスクの行を作らず、足す依頼を「オーナー待ち」にして、課題を保留にする（保留の理由 `task_add_over_limit`。課題の保留 1 つ。足す依頼が、その保留を指す）。
- [ ] `task_add_over_limit` の保留の問いに、次を書く。足すタスクの題名と枠。足した後の見込み。上限。超える額。「動いている作業が終わるまで、計画の作り直しは選べない」旨。
- [ ] `task_add_over_limit` の保留は、選択肢つきの問いにする（S4b-1 の、選択肢つきの問いの口を使う。オーナーの決定 2026-11-22）。選択肢は 3 つ。`add`（足す。説明に、上げた後の上限の額＝足した後の見込みを書く）・`skip`（足さずに進める）・`replan`（計画を作り直す）。
- [ ] `ask` → タスクの行を作らず、課題を保留にする（保留の理由 `task_add_question`。問いは、判断点の問い。足す依頼が、その保留を指す）。足す依頼は「仕様待ち」のまま。回答の後、次の回りで、回答を入力に足して、判断点を呼び直す。
- [ ] `ask` の出力に、判断点が選択肢を付けていたら、`task_add_question` の保留を、選択肢つきの問いにする（選択肢は任意。無ければ、文の問いのまま）。選んだ選択肢の見出しは、回答の文と同じに、次の「足す」の形の入力に入る。
- [ ] 足すタスクの検査は、計画のタスクと同じ項目（題名・本文・完了条件・リポジトリ・操作の種類・枠）に、次を足す。
  - 鍵が、承認済みの版のタスク（取りやめ・済みを含む）の鍵と重ならない。
  - 前提は、足すタスクの鍵か、承認済みの版の、取りやめでないタスクの鍵を指す（前の版のタスクへの前提は持てない。鍵の無いタスクは指せない）。当てはまらない前提は、不正な出力。
  - 前提に輪が無い（いまあるタスクとの辺を含めて調べる）。
  - リポジトリは、いまあるタスクと同じ 1 つ。
  - 1 回に足せるのは、1 回の計画のタスクの上限（いま 12）と同じ件数まで。
- [ ] 検査に通らない出力と、形が不正な出力は、不正な出力として扱う。そのとき、足す依頼は「仕様待ち」のまま、タスクの行は増やさず、計画を作る判断点の連続の失敗に数え、次の回りで呼び直す。連続の失敗が上限に達したら、いまある、連続失敗の保留にする（課題が着手中であることを前提に呼ぶ。保留が解けたら、着手中へ戻る）。
- [ ] `task_add_over_limit` の保留には、選択肢の識別で答える。回答の本人確認は、いまの保留への回答と同じ。core は、回答の記録から、選んだ識別を読んで、次の動きをする。
  - `add` → 同じ書き込みで、上限を、足した後の見込みの額へ上げ（いまの上限のほうが大きければ、変えない）、タスクの行を作り、足す依頼を「足した」で閉じ、保留を閉じ、課題を、保留の前の状態へ戻す。上限を上げたときは、承認の記録（種類 `budget`。`--limit` と同じ形）を残す。
  - `skip` → 足す依頼を「見送り」で閉じ、足さずに進む。
  - `replan` → 足す依頼を「取り替え」で閉じ、計画を作り直す（S3b の、計画を作り直す回答と同じ動き。選ぶときに添えた文は、作り直しの入力に入る）。
- [ ] 選択肢 `replan` の回答は、動いている作業（作業している契約の実行。S3b の、計画を作り直す回答が断る条件と同じ）があるときは、断る（検証の誤り）。保留も、足す依頼も、変えない。出力に、理由（動いているタスクの題名と ID）を出す。
- [ ] 選択肢 `add` の回答で、上限が上がらなかったとき（いまの上限が、足した後の見込み以上）は、承認の記録（`budget`）を足さない。
- [ ] `task_add_over_limit` の保留への、選択肢の識別が無い回答（文だけの回答。`--replan` だけを付けた回答を含む）は、断る（検証の誤り。出力に、選択肢の識別と見出しを出す）。保留も、足す依頼も、変えない。文の意味を core が読んで「足さずに進む」と決めることは、しない。
- [ ] 足した後の見込みは、`add` の回答を受けたときに計算し直す（判定したときの値で固定しない）。計算し直した額が、選択肢の説明に書いた額と違うときは、回答を成立させず、足さない（「出し直し」）。
- [ ] 出し直しは、エラーで巻き戻さず、成功の書き込みとして確定する。同じ書き込みで、保留の問いの文の額と、選択肢 `add` の説明の額を、計算し直した額に書き換え、課題の版を 1 つ進める。保留は開いたまま、足す依頼は「オーナー待ち」のまま、上限は変えない。回答の処理（`ExecuteAnswer`）の結果に、「出し直した」を表す値を足す。
- [ ] 出し直しのとき、CLI は、検証の誤りと同じ終了コードで終わり、出力に、新しい額と、問いを出し直した旨を出す。API（S4d-2 が画面のボタンを足すとき）は、コンフリクトに当たる応答を返す。
- [ ] `task_add_over_limit` の保留の間の `flywheel budget … --limit` は、上限だけを変える（足さない。保留も、足す依頼も、開いたまま）。足すのは、選択肢 `add` の回答だけ。
- [ ] 対話・対話の欄では、オーケストレーターが、オーナーの発言を選択肢の識別に直して記録する（発言が、どの選択肢か決められないときは、記録せずに確かめる。指示文と案内の文に書く）。
- [ ] 済みの `expand_after` のタスクで、足す依頼がまだ無いものがある課題と、閉じていない（「仕様待ち」「オーナー待ち」）足す依頼がある課題は、上げる依頼を始めない。
- [ ] 済みの `expand_after` のタスクで、足す依頼がまだ無いものがある課題と、閉じていない足す依頼がある課題は、検証中へ進めない。
- [ ] 計画を作り直して承認し直したとき、閉じていない足す依頼は「取り替え」で閉じる。
- [ ] 〔S4c-2〕作り直しの承認で閉じた足す依頼のうち、出どころがフォローアップのものは、フォローアップが未のまま残り、上げ直せる。

### フォローアップを、開いている課題のタスクに上げる（S4c-2）

この節の項目は、すべて S4c-2。S4c-1 だけが入っている間、フォローアップを上げると、いまと同じに、いつも新しい課題になる。

- [ ] `flywheel followup promote <フォローアップの ID>` の上げる先を、次の順で決める。
  - `--new-challenge` を付けた → 新しい課題（いまと同じ）。
  - フォローアップが課題に属し、その課題が、足せる課題 → その課題のタスク。
  - それ以外（足せる課題以外のすべて）→ 新しい課題。例: 課題に属さない。元の課題が、着手中より前の状態（分類・計画・計画の承認待ち）・検証中・完了の承認待ち・完了・取り下げ。元の課題が、統合先を使わない（タスクが 1 個の課題。オーナーの決定 2026-11-22）。元の課題の見込みが不明（枠を決められないタスクがある）。
  - オーナーの決定の「反映へ進んでいない」は、「課題が、検証中より先へ進んでいない」ことを指す。着手中で、上げる依頼が開いているだけの課題は、上げる依頼を取り消して足せる（下の項目）。
- [ ] 上げる先が新しい課題になったとき、要約と出力に、タスクにしなかった理由を出す。
- [ ] 上げる先がタスクのとき、足すタスクの枠は、サイズ S の既定（宣言 `size_budgets_usd.S`）。`--budget-impl-usd`・`--budget-review-usd` で変えられる。
- [ ] 本人確認の前に見せる要約に、次を出す。上げる先（課題の題名と ID、または「新しい課題」）。足すタスクの枠。足した後の見込み。上限。上限を超えるときは、超える額と、上げた後の上限。
- [ ] `flywheel followup promote <ID> --preview` は、上の要約と同じ値を、何も書かずに返す（本人確認なし。`--json` あり）。
- [ ] 足した後の見込みが上限を超えるとき、ターミナルでの本人確認では、確かめた指示を、上限の引き上げの承認として扱う（上限を、足した後の見込みまで上げる）。`--raise-limit` は、付けなくてよい。付けたら、額を、足した後の見込みと照らし、違えば断る。
- [ ] `--raise-limit` は、足した後の見込みが上限を超えるときだけ、意味を持つ。超えないとき（上げる先が新しい課題のときを含む）に付けたら、断る（検証の誤り）。
- [ ] 足した後の見込みが上限を超えるとき、対話で受けたことの記録（`--relayed`）では、`--raise-limit <上げた後の上限の額>` が無ければ断る（終了コードは検証の誤り。出力に、超える額と、`--preview` で確かめられる旨）。額が、足した後の見込みと違えば、断る。
- [ ] 上げる操作の実行は、確かめたとき（要約を作ったとき）の、上げる先・課題の版・足した後の見込み・上限を入力に持ち、書き込みのときの値と食い違えば、断る（見せた額と違う額で、上限を上げない）。
- [ ] 上げる先がタスクのとき、上げる操作は、同じ書き込みで、足す依頼（出どころ `followup`。状態「仕様待ち」。枠の額つき。フォローアップを指す）を作り、要るなら上限を上げる。フォローアップの状態は、未のまま。
- [ ] 上げる操作の戻り値と CLI の出力（テキストと `--json`）に、上げた先の種類（課題かタスク）と、足す依頼の ID を持たせる。
- [ ] 計画の段が、出どころ `followup` の足す依頼について、判断点を「足す」の形で呼ぶとき、入力に、フォローアップの題名と説明を足す。出力のタスクは 1 個で、枠は、足す依頼の額を使う（出力の枠は読まない）。
- [ ] 出どころ `followup` の `add` にも、上の「続きを決めるタスク」と同じ上限の判定をかける（上げたときに上限を上げていても、そのときの見込みで判定し直す。超えたら `task_add_over_limit` の保留）。
- [ ] 出どころ `followup` の `add` で足したら、フォローアップに、上げた先のタスクを記録する（`promoted_task_id`）。上げた先の課題の列（`promoted_challenge_id`）は、変えない。
- [ ] 上げた先を読む所は、タスクの列（`promoted_task_id`）に値があれば、そちらを使い、無ければ、課題の列を使う。読む所は、下の「変える所」の一覧。
- [ ] 新しい課題へ上げる（上げ直す）ときは、同じ書き込みで、`promoted_task_id` を NULL に戻す（上げた先は、最後に上げたほうの 1 つ）。
- [ ] 出どころ `followup` の `ask` は、上の `task_add_question` と同じ。`none` と、タスクが 2 個以上の出力は、不正な出力として扱う。
- [ ] 上げた先のタスクが済みになったら、タスクの状態を書く共通の所で、同じ書き込みで、そのフォローアップを済みにする（確かめた結果に、上げた先のタスクを書く）。
- [ ] 上げ直せるのは、未のフォローアップで、次のどれか。上げたことが無い。上げた先の課題が取り下げ（いまと同じ）。上げた先のタスクが取りやめ。フォローアップを指す足す依頼が、「見送り」か「取り替え」で閉じた。フォローアップを指す、閉じていない足す依頼がある間と、上げた先のタスクが未着手・着手中・検証中の間は、断る（検証の誤り）。上げた先のタスクが済みのフォローアップは、済みになっているので、上げられない（いまの、済みのフォローアップと同じ断り方）。
- [ ] フォローアップを指す足す依頼がオーナー待ち（問いが回答待ち）の間は、そのフォローアップを捨てる・済みにする操作を、検証の誤りで断る（何も書かない。出力に、先に問いへ回答する旨を出す）。仕様待ちの足す依頼は、捨てる・済みにするときに、見送りで閉じる（オーナーの決定 2026-11-23）。
- [ ] その課題の上げる依頼が開いているときに、タスクとして上げたら、上げる依頼を取り消す（S3b の、課題の単位の確かめが「満たしていない」のときと同じ道。作った反映の操作は、上げる操作と同じ書き込みで閉じる。開いている上げる依頼の実行は、次の回りの反映の段が取り消す）。足したタスクが統合先に入った後、上げる依頼を始め直す。
- [ ] 1 回に上げるのは 1 件（いまと同じ）。

### 保留中の課題のほかのタスクを進める（S4c-3）

この節の項目は、すべて S4c-3。S4c-2 までは、タスク 1 つに保留が立つと、課題の全部のタスクが、回答まで止まる。

止める範囲:

- [ ] 保留は、止める範囲を持つ: 「タスクを止める保留」（そのタスクだけを止める）と、「課題を止める保留」（課題の全部を止める。S4c-2 までの保留と同じ）。範囲は、保留を立てるときに決めて、保留に記録する（`hold.scope`。`task` か NULL。NULL は、課題を止める保留）。後から変えない。
- [ ] 止める範囲は、保留を立てる呼び出し元が、保留と一緒に渡す（止まり方 `stop_kind` と同じ渡し方。渡さなければ、課題を止める保留）。タスクを止める保留として渡すのは、統合先を使う課題で、1 つのタスクの作業の中で起きた止まり（そのタスクの実行・レビュー待ち・検証・統合先への受け取り・委譲先の問い）を写す保留で、タスクが結び付いているもの（`hold.task_id`）。それ以外は、課題を止める保留: タスクに結び付かない保留、統合先を使わない課題の保留、検証中から立つ保留、足す依頼から立つ保留（保留の理由 `task_add_over_limit`・`task_add_question`）、`tasks_blocked`、`challenge_check_not_met`、上げる依頼の保留（`reflect_unavailable`・`reflect_failed`）、親が直接行う保留。
- [ ] タスクを止める保留として渡された保留を、実際に立てられるのは、課題が着手中のときか、下の「保留を重ねる」の条件を満たす人間対応待ちのとき。立てられないときの扱いは、「保留を重ねる」に書く（範囲を、課題を止める保留に読み替えて立てることはしない）。
- [ ] 課題の状態は、開いている保留が 1 つでもあれば、人間対応待ち（オーナーの決定 2026-11-23）。タスクを止める保留だけが開いている間も、人間対応待ち。課題の状態の値は増やさない。
- [ ] タスクを止める保留だけが開いている課題では、保留が結び付くタスク以外のタスクについて、着手中の課題と同じに進める: 新しいタスクの起動、状態の確認、レビュー待ちの受け取り、タスクの検証、「入れてよい」を返すこと、観測の待ちの再開、委譲先の問いをスーパーバイザーが受けること（S4b-3）、タスクを済みにすること。
- [ ] 保留が結び付くタスクは、いまの保留中の課題のタスクと同じに止める（S3b の決まりのまま。走っている実行の状態は読み続け、レビュー待ちの受け取り・タスクの検証・「入れてよい」は、その保留が閉じるまで延ばす）。
- [ ] 止めたタスクを前提に持つタスクは、前提が済みにならないので、起動しない（前提の決まりのまま。新しい決まりは足さない）。
- [ ] 課題を止める保留が 1 つでも開いている間は、課題の全部を、いまと同じに止める（S3b の決まりのまま）。
- [ ] タスクを止める保留が開いている間、その課題では、次を始めない（いまの保留中の課題と同じに、課題の状態で決める）: 上げる依頼、課題の単位の確かめ、足す依頼の判断点（「足す」の形）、進めようが無い課題の保留（`tasks_blocked`）の判定。保留が全部閉じて、着手中へ戻ってから行う。ほかのタスクが全部済みになっても、保留のタスクが済みでないので、課題は先へ進まない。
- [ ] 枠が尽きたタスクの数え（`flywheel status` の「枠が尽きた」）は、タスクを止める保留だけが開いている課題の、進めてよいタスクも数える。

保留を重ねる:

- [ ] 人間対応待ちの課題に、保留を重ねて立てられるのは、開いている保留が、どれもタスクを止める保留で、新しい保留も、開いている保留の無い別のタスクを止める保留のときだけ（遷移 T11 に、人間対応待ちからの行を足す。課題の状態は人間対応待ちのまま、版は進める）。条件は、保留の行を作る共通の所が、同じ書き込みの中で確かめ、満たさなければ、いまの「保留にできない」と同じ誤り（遷移の誤り）にする。重ねた保留の戻り先（`from_status`）は、共通の所が、着手中に固定する。
- [ ] 開いている保留は、タスクごとに 1 つまで、課題を止める保留は、課題に 1 つまで。課題を止める保留と、タスクを止める保留は、同時に開かない。
- [ ] 保留を立てられない場合（タスクを止める保留が開いている間に、課題を止める保留が要ることが起きた。課題を止める保留が開いている間に、タスクを止める保留が要ることが起きた。同じタスクに、開いている保留がある）は、いまの保留中の課題と同じに、保留にしないで待つ（止まりの元は残るので、立てられる状態になった後の回りで、改めて保留になる）。
- [ ] 保留を閉じる（オーナーの回答 T12・スーパーバイザーが閉じる T20）とき、同じ課題に、ほかの開いている保留が残っていれば、課題は人間対応待ちのまま（版は進める）。残っていなければ、閉じた保留の戻り先へ戻る（いまと同じ）。残っているかは、閉じる書き込みの中で数える。
- [ ] 取り下げは、開いている保留を、止める範囲によらず、全部閉じる（いまと同じ）。
- [ ] 保留が閉じたタスクは、ほかの保留が残っていても、次の回りから進める。回答の後に行う直し（`facts_unmet` の数えの戻し・統合先のタスクの受け取り直し）は、いまと同じに、回答の書き込みの中で行う（課題の遷移先によらない）。契約の待ちへの答えを委譲先へ返すのは、その保留が回答済みになった後の回り（課題が着手中へ戻るのを待たない）。
- [ ] スーパーバイザー待ちの保留は、保留ごとに扱う（いまと同じ）。手を実行できるかの確かめ（判断の間に状態が変わったか）は、課題の状態ではなく、その保留が開いているかと、戻り先で見る。

回答する保留の指定:

- [ ] 保留に、表示用の ID（`H-<番号>`）を付ける（オーナーの決定 2026-11-23）。番号は、保留の行の番号。過去の保留も、同じ形で読める。
- [ ] `flywheel answer <課題> --hold <H-ID>` で、答える保留を指定する。開いている保留が 1 つのときは、省略できる（いまのコマンドが、そのまま使える）。
- [ ] 開いている保留が 2 つ以上あるのに `--hold` を省いたら、検証の誤りで断る（何も書かない）。出力に、開いている保留の一覧（ID・タスクの題名・問いの先頭）を出す。
- [ ] `--hold` に、その課題の開いている保留でない ID（別の課題の保留・閉じた保留・無い ID）を渡したら、検証の誤りで断る。
- [ ] 本人確認の前の要約に、答える保留の ID・タスクの題名・問いを出す。確かめた後の書き込みは、確かめたときと同じ保留に書く。
- [ ] 回答の書き込みの照合は、保留で行う: 確かめた保留が開いたままで、問いと選択肢が、確かめたときと同じなら、通す。ほかのタスクの保留が立った・閉じたことで課題の版が進んだだけでは、断らない（いまは、課題の版が違えば断る）。確かめた保留が閉じていた・問いか選択肢が変わっていたら、コンフリクトで断る（いまと同じ）。計画を作り直す回答の条件（動いている作業が無い）は、書き込みの中で確かめる（いまと同じ）。
- [ ] 対話で受けた回答の記録（`--relayed`）も、同じ決まり（開いている保留が 2 つ以上なら、`--hold` が要る）。
- [ ] 「課題の最新の保留」を 1 件読んで相手や境を決めている所は、全部を一覧にして（最初の Issue。PR の説明に書く）、所ごとに、次のどれかに改める: 保留の ID で決める（回答・問いと選択肢の書き換え）。課題を止める保留に絞って読む（足す依頼の問いの出し直し・足せるかの判定・親が直接行う保留の判定）。保留ごとに返す（一覧の選択肢）。タスクを止める保留が別に開いていても、課題を止める保留を相手にする所の振る舞いは、変えない。

計画を作り直す回答:

- [ ] 計画を作り直す回答（`--replan`・選択肢 `replan`）は、動いている作業（作業している契約の実行。S3b の条件）があるときは、いまと同じに断る。S4c-3 では、ほかのタスクが進むので、断られる場面が増える（出力に、動いているタスクの題名と ID を出す。いまと同じ）。
- [ ] 計画を作り直す回答が成立したら、その課題の、ほかの開いている保留を、同じ書き込みで、回答なしで閉じる（閉じた理由を、作業ログに残す。課題は、分類済みへ戻る）。取り下げが、開いている保留を全部閉じるのと同じ。
- [ ] スーパーバイザーの手「計画を作り直す」も、同じ決まり（動いている作業があれば実行できない状態として扱い、成立したら、ほかの開いている保留を閉じる）。

数えと境:

- [ ] タスクの単位の数え（連続の失敗・差し戻し・再開の対象・`facts_unmet`）の境は、そのタスクの保留だけで決める（いまと同じ。ほかのタスクの保留が開いていても、変わらない）。
- [ ] 課題の単位で「最後の保留」を読んで境を決めている所（判断点の連続失敗の数え直し・課題の単位の確かめの入力・実行の終わりの時刻）は、ほかのタスクの、開いている保留を、境に数えない。
- [ ] サイクルの「いま始められるもの」の数えに、タスクを止める保留だけが開いている課題の、進められるタスクを入れる（進められるものが無いサイクルは、いまと同じに終わる）。
- [ ] 同時に走らせる数（`max_parallel_runs`）の数え方は、変えない。
- [ ] 学びの判断点・課題の一覧の「人間対応待ち」の数（`needs_human`）・画面の「問いに答える」の出し方は、課題の状態で決めるまま、変えない。

### 見せ方（core・CLI・API の値）（S4c-1。印のある項目は S4c-2・S4c-3）

- [ ] 課題の詳細（`GET …/challenges/<ID>` と `flywheel show --json`）に、予算（`budget`: `estimate_usd`・`limit_usd`・`limit_reason`）を足す。上限の記録が無い課題の `limit_usd` は、見込みと同じ額。見込みが不明の課題は、`estimate_usd`・`limit_usd` が `null`。
- [ ] 計画の承認待ちの課題では、`budget` は、承認を待っている版の計画の値を返す。
- [ ] 画面の計画の承認に、「見込み・上限」と、上限の理由を出す（上限が見込みと同じなら、理由は出さない）。
- [ ] `flywheel show`（テキスト）に、見込みと上限を出す。
- [ ] 課題の詳細のタスクの要素に、足されたタスクの印（`added`: `origin`・`origin_task_id`・`added_at`。計画の承認で作ったタスクは `null`）を足す。
- [ ] 〔S4c-2〕足されたタスクの印（`added`）に、`followup_id` を足す。
- [ ] 課題の詳細に、足す依頼の一覧（`additions[]`: `id`・`origin`・`state`・`origin_task_id`・`task_ids`・`total_after_usd`・`limit_usd`・`created_at`・`decided_at`。閉じたものも含む）を足す。
- [ ] 〔S4c-2〕足す依頼の一覧（`additions[]`）の要素に、`followup_id` を足す。
- [ ] 〔S4c-2〕フォローアップの要素に、上げた先のタスク（`promoted_task_id`）を足す。
- [ ] タスクを足したことは、作業ログに残す（足す依頼・足したタスク・足した後の見込みと上限）。
- [ ] `flywheel cycle` の出力に、その回に足したタスクを出す（課題・タスクの題名・出どころ）。
- [ ] 完了の承認の要約（`flywheel show` と API）に、計画の後に足したタスクの一覧を出す。
- [ ] 〔S4c-3〕保留を返す所（課題の詳細の保留の一覧・課題の保留の API・問いの一覧 `GET …/questions`・タスクの詳細・スーパーバイザーの対処の一覧）に、保留の ID（`hold_id`。`H-<番号>`）と、止める範囲（`scope`。`task` か `challenge`）を足す。

## 技術的な制約・方針

- 開発に固有の知識を、core に新しく足さない（オーナーの決定 2026-11-22）。足すタスクの中身は、計画のタスクと同じ項目だけを持つ。
- 判断は判断点が返し、遷移と数字の判定は core が行う（P2 のまま）。上限を超えるかは、core が数字で判定する。
- 委譲先との契約は、変えない。claude-harness の側で要るものは無い。
- ストアの版は、S4a（版 31）・対話の欄（版 32）・S4b の各スライスの次。番号は、main に入れる順で決める。マイグレーションは、スライスごとに 1 本（S4c-1 に 1 本・S4c-2 に 1 本・S4c-3 に 1 本〔版 38〕）。列は、使うスライスで足す。
- 進行中の課題を新しい形へ移す処理は作らない。過去の行は書き換えない（上限の記録が無い課題は、読むときに見込みと同じ額として扱う）。
- 対話・対話の欄の指示文（`internal/invoker/prompts/chat.md`。S4d-1 で入る）と案内の文に、「オーナーの発言を、選択肢の識別に直して記録する。どの選択肢か決められないときは、記録せずに確かめる」を書く（文書を読む試験で、その文があることを確かめる）。
- 判断点の指示文（`j2.md`）に、次を書く。呼び出しの形の区画の値で読む節を分けること。上限と理由の書き方。`expand_after` の付け方。「足す」の形では、計画の「やらないこと」に触れるタスクは足さない・方針の外かどうか迷ったら `ask` にする・判断や人の作業が要る点が出たら `ask` にする。
- 型を変えたら、`go generate ./internal/view` で `web/src/api/types.gen.ts` を作り直す。

## クリティカル設計決定

### 承認の意味: 上限は 1 つの額で、課題に記録する（S4c-1）

- **採用案**: 上限は、実装の枠とレビュー対応の枠を足した、1 つの額にする。計画の承認のときに、課題の記録（`challenge.budget_limit_micros`・`budget_limit_reason`）に写す（統合先を使うか〔`uses_integration`〕と同じ持ち方）。
- **理由**: オーナーが承認するのは「この課題に、いくらまで」の 1 つの数字（オーナーの決定 2026-11-22「計画が上限を別に示す」）。枠ごとに 2 つ持つと、承認の画面の数字が 4 つになり、どちらの枠で超えたかの問いが増える。枠ごとの歯止めは、タスクの枠（S3b）が持っている。課題に写すのは、サイクルが、計画の本文を読み直さずに判定するため。
- **代替案**: 計画の表（`task_plan`）に持つ。版ごとに値が残るが、承認していない版の値を読む誤りが起きうる。承認した値だけを課題に持つほうが、読む所が 1 つで済む。

### 承認の意味: 上限を超えて足すには、選択肢「足す」で答える（S4c-1）

- **採用案**: 上限を超える足す依頼の保留は、選択肢つきの問いにし、オーナーが選択肢 `add` を選んだときにだけ、上限を、説明に書いた額へ上げて、足す（オーナーの決定 2026-11-22）。選択肢の識別が無い回答は断る。足した後の見込みは、答えを受けたときに計算し直し、説明の額と違えば、足さずに、新しい額で問いを出し直す。`flywheel budget … --limit` は、上限だけを変える道として残し、保留を閉じない。
- **理由**: 設計書は「超えるなら、必ずオーナーへ問う」としている。文の回答を「足してよい」と読むと、core が文の意味を判定することになる（P2 に反する）。選択肢の識別は、値で判定できる。額は、選択肢の説明に出ているので、オーナーが見た額と、上がる額が同じになる。保留の間に、枠の増額や `--limit` で数字が動きうるので、答えのときに計算し直し、違えば出し直す（見せた額と違う額で上限を上げない）。足す道を選択肢の回答 1 つにすると、`--limit` が保留を閉じる道（回答なしで閉じる・状態遷移）が要らない。出し直しを、エラーでなく成功の書き込みにするのは、いまの回答の処理が 1 つの書き込みで、エラーを返すと、問いの書き換えも巻き戻るため。課題の版が進むので、古い版を持った再送は、版の不一致で断られる（オーナーは、新しい額の問いを見て、答え直す）。選択肢 `replan` を、動いている作業があるときに断るのは、S3b の、計画を作り直す回答と同じ決まり（作業している実行を残したまま、計画を取り替えない）。
- **代替案**: 「上限を上げる操作＝足す／文の回答＝足さずに進む／計画を作り直す回答」の 3 つの操作で答える。S4b-1 を待たずに出せるが、オーナーは、問いへの答えを、別のコマンドの形に直す必要がある。オーナーの決定で採らない。
- **影響**: S4c-1 は、S4b-1 の、選択肢つきの問いの口に依存する（下の「S4b との境目」）。

### 承認の意味: フォローアップを上げる指示が、上限の引き上げの承認を兼ねる（S4c-2）

- **採用案**: タスクとして上げて上限を超えるときは、上げる前に、増える額を見せ、上げる指示を、その引き上げの承認として扱う（オーナーの決定 2026-11-22）。上げる操作の書き込みは、見せたときの値（上げる先・課題の版・足した後の見込み・上限）と同じであることを確かめ、違えば断る。対話で受けた記録では、`--raise-limit <上げた後の上限の額>` を明示したときだけ受け、額が違えば断る。
- **理由**: 上げる操作は、本人確認つきの、オーナーの指示。ターミナルでは、本人確認の前の要約で額を見せられる。対話で受けた記録では、core は、オーナーが額を見たかを確かめられないので、オーケストレーターが `--preview` で額を伝えたうえで、その額を明示する形にする。見せた額と違う額で上限が上がると、承認していない額を承認したことになる。
- **記録**: 上げる指示で上限が上がったときは、作業ログ（`budget_limit`）に加えて、承認の記録（種類 `budget`。`--limit` と同じ形）を残す。上がらなかったときは残さない（オーナーの決定 2026-11-23）。
- **代替案**: 上限を超えるときは、先に `flywheel budget … --limit` を求める。操作が 2 回になる。

### 状態遷移: 足す依頼から立つ保留は、いまある保留の遷移を使う（S4c-1）

- **採用案**: `task_add_over_limit`・`task_add_question` の保留は、いまある保留（T11）と回答（T12）の遷移を使う。課題に、開いている保留は 1 つ（S3b のまま）。保留中の課題の足す依頼は、保留が解けるまで判断点を呼ばないので、2 つ目の保留は要らない。新しい遷移は足さない（選択肢 `add`・`skip` は、保留の前の状態へ戻る回答。`replan` は、計画を作り直す回答）。
- **理由**: 保留を課題に重ねて持つ形（S4c-3）を待たずに出せる。足す・足さない・作り直すは、どれも回答の遷移に載る。
- **代替案**: `--limit` が保留を閉じる道を足す（回答なしで閉じる）。額の操作が答えを兼ねるが、状態遷移を伴う新しい操作が要る。選択肢の回答に 1 本化したので、採らない。

### 状態遷移: 保留を課題に重ねて持ち、課題は人間対応待ちのまま（S4c-3）

- **採用案**: 課題の状態は、開いている保留が 1 つでもあれば人間対応待ち（オーナーの決定 2026-11-23）。保留は、止める範囲（タスクか課題）を持つ。タスクを止める保留だけが開いている間は、そのタスク以外を進める。遷移 T11 に、人間対応待ちからの行を足す（条件: 開いている保留が、どれもタスクを止める保留で、戻り先が着手中。新しい保留も、開いている保留の無い別のタスクを止める保留。遷移先は人間対応待ち）。回答 T12 と、スーパーバイザーが閉じる T20 は、ほかの開いている保留が残っていれば、遷移先を人間対応待ちにする（残っていなければ、いまと同じに、保留の戻り先）。重ねられる保留の戻り先は、どれも着手中なので、最後に閉じた保留の戻り先が、課題の戻り先になる。
- **理由**: 「オーナーを待っている課題」の一覧・数・用語集の定義を変えずに、進められるタスクだけを進められる。課題の状態の値と、タスクの状態の値を増やさない。
- **代替案**: タスクを止める保留では、課題を着手中のままにし、タスクの状態に「オーナー待ち」を足す。「オーナーを待っているもの」を、課題の状態ではなく保留から数える形に、一覧・数・画面を作り直すことになるので、採らない。
- **遷移の決め方**: 遷移の表は、ストアを読まない。T11 の人間対応待ちからの行は、表に足すだけにして、重ねられる条件は、保留の行を作る共通の所（`insertHoldWithOptions`）が、同じ書き込みの中で確かめる。T12・T20 の遷移先は、閉じる書き込みの中で、ほかの開いている保留を数えて決める。
- **影響範囲**: 「課題が着手中か」で、進める・延ばすを決めている所を、「このタスクを進めてよい」（課題が着手中、または、課題が人間対応待ちで、開いている保留がどれもタスクを止める保留で、そのタスクに開いている保留が無い）に改める。この述語は、1 か所に置いて、全部の所が同じものを使う。当てる所は、次のとおり（最初の Issue で、`StatusInProgress`・`status = 'in_progress'`・`challengeInProgress` を引いて全件を一覧にし、所ごとに「述語に改める・課題の状態のまま」を PR の説明に書く）。
  - 起動: 委譲の候補（`selectDelegationTargetsFor`・`selectLaunchTasks`）と、契約の実行を起動する前の確かめ（`contract_delegate.go`・`delegate.go`・`delegate_plan.go`）。
  - 契約の実行の後処理（`contract_delegate_after.go`・`contract_delegate_review.go`・`contract_review_intake.go`・`contract_release.go`）: 終わりの記録・観測の待ちの再開・契約の待ちへの答えを返す所（`loadContractAnswer`）・予算超過の中止・レビュー待ちの受け取り・保留にし損ねた停止の判定・取り戻した起動の判定・保留の間の成功の扱い。
  - タスクの検証の対象（`judgment_j5_task.go`）と、「入れてよい」（`integration_land.go`）。
  - 子の問い（`supervisor_child_question.go`）と、スーパーバイザーの手の実行の確かめ（`supervisor_hand_answer.go`・`supervisor_hand_escalate.go`・`supervisor_hands.go`）。
  - 保留を立てる入口の「着手中でなければ立てない」の確かめ（`holdContractWaitWith`・`delegate_reconcile.go`・`contract_review_intake.go`・`contract_delegate.go`・`delegate.go` ほか）: タスクを止める保留は、重ねられる人間対応待ちでも通す。
  - 数え: 「いま始められるもの」（`cycle_work.go`）・枠が尽きたタスク（`listBudgetExhausted`）。
  - 課題の状態のまま残す所: 上げる依頼（`reflect_up.go`）・課題の単位の確かめ・足す依頼の判断点（`judgment_j2_expand.go`）・`tasks_blocked` の判定・学びの判断点・一覧と数（`needs_human`）・画面の「問いに答える」。

### 承認の意味: 回答は、指定した保留 1 つへの回答（S4c-3）

- **採用案**: 回答の相手は、保留の ID（`H-<番号>`）で決める（オーナーの決定 2026-11-23）。開いている保留が 1 つなら省略できる。2 つ以上なら、指定が無い回答を断る（最新の保留を、黙って相手にしない）。本人確認の前の要約に、相手の保留を出し、書き込みは、確かめたときと同じ保留に書く。本人確認の対象は、いまと同じ（課題）。対話で受けた記録も同じ。
- **照合**: 書き込みの照合は、課題の版ではなく、保留で行う（確かめた保留が開いたままで、問いと選択肢が同じ）。保留が複数ある課題では、ほかのタスクの保留が立つ・閉じるたびに課題の版が進むので、版で照合すると、関係の無い変化で回答が断られる。保留で照合するのは、回答（T12。`ExecuteAnswer`）だけ。承認・差し戻し・完了の承認など、ほかの本人確認つきの操作の、課題の版の照合は変えない。遷移の共通の所の「本人確認つきの操作は、確かめたときの版を持つ」という確かめは残し、回答だけ、版の食い違いを、保留の照合に読み替える。回答の書き込みは、「最新の保留」ではなく、確かめた保留の ID で行を引く。S4c-1 の、額が変わったときの問いの出し直しの後の、古い回答の再送は、S4c-3 からは、版の食い違いではなく、問いと選択肢の食い違い（保留の照合）で断られる（結果は同じコンフリクト。版の食い違いを前提にした試験は、最初の Issue で洗い出して直す）。
- **理由**: 保留が複数あるときに、違う問いへ答えを記録すると、止めていたタスクが、オーナーの意図と違う答えで進む。
- **代替案**: タスクで指定する（`--task`）。課題を止める保留を指せず、指定の形が 2 つになる。いつも最新の保留を相手にする。古い保留に先に答えられず、取り違えやすい。どちらも採らない。

### DB スキーマ: 保留の止める範囲と、開いている保留の一意の索引（S4c-3）

- **採用案**: `hold.scope`（TEXT。`task` か NULL。NULL は、課題を止める保留。`CHECK (scope IS NULL OR (scope = 'task' AND task_id IS NOT NULL))`）を足す。開いている保留（回答が無く、閉じていない）に、部分一意索引を足す: 課題と、止めるタスク（課題を止める保留は 0）の組ごとに 1 つ（`hold (challenge_id, CASE WHEN scope = 'task' THEN task_id ELSE 0 END) WHERE answer IS NULL AND closed_at IS NULL`）。マイグレーションは 1 本（版 38）。過去の行は書き換えない（`scope` は NULL。過去の保留は、課題を止める保留として読める）。保留の表示用の ID は、行の番号から作り、列は足さない。
- **理由**: 止める範囲を、保留の理由やタスクの有無から、読む所ごとに導くと、所によって食い違う。立てるときに決めた値を 1 つ持てば、進める・延ばすの判定と、見せ方が、同じ値を読む。索引は、同じタスクに保留が重なること・課題を止める保留が重なることを、ストアで防ぐ最後の歯止め（いまは、遷移の表だけが防いでいる）。重なりは、保留の行を作る共通の所が、行を作る前に読んで、遷移の誤りで断る（索引の違反を、呼び出し元へそのまま返さない。呼び出し元は、いまと同じに、遷移の誤りを「保留にしなかった」として扱う）。課題を止める保留と、タスクを止める保留が同時に開かないことは、索引では防げないので、共通の所の確かめで保つ。
- **代替案**: 列を足さず、`task_id` があるかどうかで決める。足す依頼の保留など、タスクに結び付くが課題を止める保留を、区別できない。
- **影響範囲**: 書き出しと再構築（`Export`/`Import`）に、足した列を通す。いまの運用中のストアで、開いている保留が課題に 2 つ以上ある行は無い（遷移の表が防いでいる）ので、索引は通る（マイグレーションの試験で、S4c-2 までの版のストアから上げて確かめる）。

### DB スキーマ: 足す依頼の表と、列（S4c-1 と S4c-2）

- **採用案**: 表 `task_addition`（足す依頼）を足す。`id`・`challenge_id`・`origin`（`expand`・`followup`）・`origin_task_id`（NULL 可）・`followup_id`（NULL 可）・`state`（`pending`〔仕様待ち〕・`awaiting_owner`〔オーナー待ち〕・`applied`〔足した〕・`none`〔足さない〕・`declined`〔見送り〕・`superseded`〔取り替え〕）・`spec`（判断点が返したタスクの一覧。NULL 可）・`budget_impl_micros`・`budget_review_micros`（出どころが `followup` のときの枠。NULL 可）・`total_after_micros`・`limit_micros`（最後に判定したときの値。記録のためで、判定には使わない。NULL 可）・`hold_id`（足す依頼から立てた保留。NULL 可）・`created_at`・`decided_at`。列は、`task.addition_id`（NULL 可）・`task.expand_after`（既定 0）・`challenge.budget_limit_micros`（NULL 可）・`challenge.budget_limit_reason`（NULL 可）・`followup.promoted_task_id`（NULL 可）。同じ出どころのタスクについて、`origin = 'expand'` の行は 1 つ（部分一意索引）。
- **スライスへの割り振り**: S4c-1 のマイグレーションが、表 `task_addition`（`followup_id`・`budget_impl_micros`・`budget_review_micros` を除く列。`origin` に入る値は `expand` だけ）・`task.addition_id`・`task.expand_after`・`challenge.budget_limit_micros`・`challenge.budget_limit_reason`・部分一意索引を足す。S4c-2 のマイグレーションが、`task_addition.followup_id`・`task_addition.budget_impl_micros`・`task_addition.budget_review_micros`・`followup.promoted_task_id` を足す（`origin` に `followup` が入るのは S4c-2 から）。
- **理由**: 上限を超えたときに、タスクの行を作らずに、足す中身を持っておく場所が要る。タスクの状態に「提案」を足すと、タスクを数えている所（起動・上げる依頼の条件・見込み）をすべて直すことになる。足す依頼の行は、「足したことの記録」と、足されたタスクの印（`task.addition_id`）も兼ねる。保留への回答の処理は、`hold_id` から足す依頼を引く。
- **代替案**: 作業ログだけに残す。上限を超えて待っている中身を、後で読み出す所が無い。

## 機能全体の設計

### 流れ

1. 計画の承認: 上限と理由を課題に写す。タスクの行に `expand_after` を写す。
2. 計画の段（回りごと。出どころがフォローアップの足す依頼を扱うのは S4c-2 から）: ① 足せる課題の、済みになった `expand_after` のタスクで、足す依頼が無いもの → 足す依頼を作る。② 着手中の課題ごとに、「仕様待ち」の足す依頼の古いもの 1 件について、判断点を「足す」の形で呼ぶ。③ 出力を検査し、足した後の見込みと上限を比べ、足すか、保留にする。
3. 委譲の段: 足したタスクは、ほかのタスクと同じに起動する。
4. 上げる依頼を始める条件（S3b）に、「閉じていない足す依頼が無い」「済みの `expand_after` のタスクで、足す依頼がまだ無いものが無い」を足す。

この文書に書いた区切りの順（S4b-3 → S4c-1 → S4c-2）と、上の表の S4c-1 の前提（S4b-1〜S4b-3 が main に入ってから）は、仕様を書いた時点のもの。実装は、依存の無い区切りを並べて進めた（オーナーの決定 2026-11-22。S4b-2 と S4c-1 を並べ、次に S4b-3 と S4c-2 を並べる）。S4c-1 は S4b-1 の土台だけを使い、S4c-2 は S4c-1 の土台だけを使うので、S4b-3 を待たない。ストアの版は、main に入れる順で決める。

スライスの間の依存と、先のスライスだけが入っている間の動き:

- S4c-1 は、それだけで出荷できる。設計が済んでから実装のタスクを確定する課題が、計画の承認 1 回で、上限の内なら承認なしに進む。

## やらないこと

- 開発に固有の知識を、core に足すこと（理由: flywheel#981）

- 〔S4c-3〕1 回の操作で、複数の保留に答えること（理由: 回答は、保留 1 つごとに、本人確認を通す）

- 〔S4c-3〕画面のボタンで答えること・保留ごとの画面（理由: S4d-2。S4c-3 は、いまある表示に ID と案内を足すまで）

### 保留を重ねる

- [ ] 重ねて立った保留の `from_status` は、着手中である。
- [ ] 保留を重ねて立てたとき、課題の状態は人間対応待ちのままである。
- [ ] 保留を重ねて立てたとき、課題の版が進む。
- [ ] タスク a を止める保留が開いている間に、タスク a について、もう 1 つ保留になることが起きても、タスク a の開いている保留は 1 つのままである。

- [ ] 課題を止める保留が開いている間に、タスク b が保留になることが起きても、保留は立たない（開いている保留は 1 つのまま）。

- [ ] 保留が 2 つ開いている課題で、タスク a の保留に答えると、タスク b の保留は開いたままである。

### 回答する保留の指定

- [ ] 開いている保留が 1 つの課題で、`flywheel answer <課題> --answer …`（`--hold` 無し）は、その保留への回答として成立する。
- [ ] 開いている保留が 2 つの課題で、`flywheel answer <課題> --hold <H-ID> --answer …` は、指定した保留に回答を書く。
- [ ] 開いている保留が 2 つの課題で、`--hold` を付けて答えたとき、指定しなかった保留の回答は、空のままである。
- [ ] 開いている保留が 2 つの課題で、`--hold` 無しの回答は、検証の誤りで断られる。
- [ ] 開いている保留が 2 つの課題で、`--hold` 無しの回答が断られた後、どの保留も変わっていない。
- [ ] 開いている保留が 2 つの課題で、`--hold` 無しの回答が断られたとき、出力に、開いている保留の ID が 2 つ出る。
- [ ] 開いている保留が 2 つの課題で、`--hold` 無しの回答が断られたとき、出力に、保留ごとのタスクの題名が出る。
- [ ] 開いている保留が 2 つの課題で、`--hold` 無しの回答が断られたとき、出力に、保留ごとの問いの先頭が出る。
- [ ] `--hold` に、別の課題の保留の ID を渡した回答は、検証の誤りで断られる。
- [ ] `--hold` に、閉じた保留の ID を渡した回答は、検証の誤りで断られる。
- [ ] `--hold` に、`H-<番号>` の形でない値を渡した回答は、検証の誤りで断られる。
- [ ] 本人確認の前の要約に、答える保留の ID が出る。
- [ ] 本人確認の前の要約に、答える保留のタスクの題名が出る。
- [ ] 本人確認の前の要約に、答える保留の問いが出る。
- [ ] タスク a の保留を確かめた後、書き込みの前に、タスク b の保留が立っても、タスク a の保留への回答は成立する。
- [ ] タスク a の保留を確かめた後、書き込みの前に、タスク a の保留が閉じていたら、回答はコンフリクトで断られる。
- [ ] 保留を確かめた後、書き込みの前に、その保留の問いが書き換わっていたら、回答はコンフリクトで断られる。
- [ ] 開いている保留が 2 つの課題で、`--relayed` で `--hold` 無しの回答は、検証の誤りで断られる。
- [ ] 開いている保留が 2 つの課題で、`--relayed` で `--hold` を付けた回答は、指定した保留に回答を書く。
- [ ] 選択肢つきの保留を `--hold` で指定して、その保留の選択肢の識別を `--option` で渡すと、回答は成立する。
- [ ] 選択肢つきの保留を `--hold` で指定して、別の保留にだけある選択肢の識別を `--option` で渡すと、検証の誤りで断られる。
- [ ] `hold_id` の番号は、保留の行の番号と同じである。
- [ ] 閉じた保留にも、`hold_id` が出る。
- [ ] 課題を止める保留（足す依頼の問い）が 1 つ開いている課題で、問いの出し直しは、その保留を相手にする（いまと同じ）。
- [ ] 最初の Issue の PR の説明にある「『課題の最新の保留』を読んでいる所と、改め方」の表の所ごとに、タスクを止める保留が 2 つ開いている課題で、相手を取り違えないことを確かめる試験がある。

### 計画を作り直す回答

- [ ] タスク a を止める保留が開いていて、タスク b の実行が動いている間、タスク a の保留への計画を作り直す回答は、検証の誤りで断られる。
- [ ] 上の回答が断られたとき、出力に、動いているタスクの題名が出る。
- [ ] 上の回答が断られたとき、出力に、動いているタスクの ID が出る。

- [ ] 保留が 2 つ開いていて、動いている作業が無い課題で、片方の保留に計画を作り直す回答をすると、もう片方の保留は、回答なしで閉じる。

### 数えと境

- [ ] タスク b の保留が開いている間に、タスク a の保留に答えた後、タスク a の差し戻しの数えは、タスク a の保留の回答を境に数え直される。
- [ ] タスク b の保留が開いている間に、タスク a の保留に答えた後、タスク a の連続の失敗の数えは、タスク a の保留の回答を境に数え直される。
- [ ] タスク b を止める保留が開いている間、課題の単位の、判断点の連続失敗の数えの境は、タスク b の開いている保留では決まらない（その前の、閉じた保留で決まる）。

## オーナーの決定（2026-11-22）

1. 予算の上限は、計画が、見込みと別に示し、計画の承認で、上限ごと承認する。
2. フォローアップを上げる先は、既定で、元の課題のタスク（元の課題が開いていて、反映へ進んでいないとき）。「新しい課題で」と指定したときだけ、新しい課題。
3. S4c を分けて出す。はじめに 2 つ（上限・足す・上げる／保留中の課題のほかのタスク）に分け、仕様が大きくなったので、前のほうをさらに 2 つに分けた。いまの呼び名は、S4c-1（上限とタスクを足す）・S4c-2（フォローアップを上げる）・S4c-3（保留中の課題のほかのタスクを進める）。
4. 上限を超えて足すときの問いは、選択肢を選ぶ形（足す・足さずに進める・計画を作り直す）。選択肢つきの問いの仕組みが入るまで、待つ。
5. 統合先を使わない課題（タスクが 1 個の課題）のフォローアップは、新しい課題にして、理由を出す。
6. 波 2 は、スライスを細かく分けて、1 回ごとに実装して確かめ、main へ入れる。順番は、S4b-1 → S4b-2 → S4b-3 → S4c-1 → S4c-2 → S4c-3 → 画面の残り（S4d-2）。

## オーナーの決定（2026-11-23。S4c-3）

1. 1 つのタスクがオーナーの回答を待っていて、ほかのタスクが進んでいる間も、課題の状態は、人間対応待ちのままにする（開いている保留が 1 つでもあれば、人間対応待ち。最後の保留が閉じたら、着手中へ戻る）。
2. 保留に ID（`H-<番号>`）を付け、`flywheel answer <課題> --hold <H-ID>` で、答える保留を指定する。開いている保留が 1 つなら省略できる。2 つ以上あるのに省いたら、断って、開いている保留の一覧を出す。

仕様の検討で決めて、承認のときに確かめる点（S4c-3）:

- 回答の書き込みの照合を、課題の版から、保留（開いたままで、問いと選択肢が同じ）に替える。
- 止める範囲は、保留に記録する（`hold.scope`）。保留を立てられない場合は、範囲を読み替えずに、待つ。
- 計画を作り直す回答が成立したら、ほかの開いている保留を、回答なしで閉じる。
