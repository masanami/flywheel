# フローのカスタマイズ（最初の区切り: 内側のフローの上書きの口）

## 概要

タスクを実装するフロー（実装・レビュー・品質の検査・CI・マージ）を、ワークスペースに置いた定義で変えられるようにする。あわせて、いまは実装のステップの中で行っているセルフレビューを、フローのステップとして外に出し、レビューへ戻る回数の上限とレビュアーの構成を定義で決められるようにする。

決定の正本は GitHub Issue masanami/flywheel#981 の本文の「フローのカスタマイズ」の 1〜7。

## 背景・目的

- flywheel は claude-harness の実行の仕組みを取り込み、タスクを実装するフローを自分で進めるようになった。そのため、フローを変えられるのは flywheel だけになった。
- いまは組み込みのフローしか使えない。品質の検査をいつ回すか、CI を待つか、レビュアーを何体にして何回まで回すか、をワークスペースごとに変えられない。
- セルフレビューは実装のステップの指示文の中で行っているので、レビューの回数・費用・指摘の推移が記録に残らず、上限もシステムで数えていない。
- 将来は、学習のサイクルで AI がフローを直す。そのために、定義を置いて差し替える口が先に要る。

## ユーザーストーリー

- オーナーとして、組み込みのフローを写して直したものをワークスペースに置き、次のタスクからその定義で動かしたい。
- オーナーとして、置いた定義が正しいかを、動かす前に確かめたい。
- オーナーとして、定義を壊してしまっても、ほかの仕事が止まらず、どこが悪いかが分かるようにしたい。
- オーナーとして、タスクがどの定義で動いたかを後から確かめたい。
- オーナーとして、レビューの回数と費用を、ステップの記録で見たい。

## スライス（出荷の単位）

| スライス | 中身 |
|---|---|
| S1 | 内側のフローの上書きの口（ワークスペースの定義・写す口・確かめる口・壊れた定義の扱い・どの定義で動いたかの記録・外せない線）と、レビューのステップ化 |
| S2 | 自分たちの開発（flywheel のリポジトリ）を flywheel のフローで進める形に切り替える（Tom の宣言の切り替え。この仕様の外の作業として行う） |
| S3 | 外側のフロー（課題の進め方。オーナーの承認のタイミングなど）の上書き |
| S4 | 完了の検証をフローのステップにし、上書きできる形で入れる |

実装対象: S1

## 機能要件

### 定義を置く

- [ ] ワークスペースの `.flywheel/flows/<名前>.yaml` に、フローの定義を丸ごと置ける
- [ ] 組み込みと同じ名前の定義を置くと、その名前のフローで始まる委譲は、すべて置いた定義で動く
- [ ] 組み込みに無い名前の定義は、委譲先の宣言の操作に並べたときだけ、計画を作る判断点（J2）が選べる
- [ ] 置いた定義は、組み込みと同じ検査を通ったときだけ使う
- [ ] 置いた定義の指示文は、ワークスペースの `.flywheel/flows/` の下に置ける。置いていない指示文は組み込みのものを使う
- [ ] 出力の型とつなぎのスクリプトは、ワークスペースに置けない。定義からは組み込みのものを名前で指すだけ
- [ ] 組み込みとの差分だけを書く上書きは受けない

### 写す口と確かめる口

- [ ] `flywheel flow export <名前>` で、組み込みのフローの定義を `.flywheel/flows/<名前>.yaml` に書き出せる
- [ ] `flywheel flow export` は定義だけを書き出し、指示文は書き出さない（置いていない指示文は組み込みの最新を使う。決定 2026-11-28 オーナー）
- [ ] 書き出す先にファイルが既にあるときは、上書きせずに誤りで終わる
- [ ] `flywheel flow check` で、ワークスペースに置いた定義をすべて検査し、悪い所をファイルと場所（行か項目）つきで示す
- [ ] `flywheel flow check` は、すべて通れば 0、1 つでも通らなければ 0 以外で終わる
- [ ] `flywheel flow check` は、定義ごとに、組み込みの置き換えか、新しい名前かを示す

### 壊れた定義

- [ ] 置いた定義が検査を通らないとき、そのフローで始まる委譲は始めない
- [ ] そのとき、「あなたを待っているもの」に、どのファイルのどこが悪いかを出す
- [ ] 壊れた定義のフローを使わない委譲と、委譲以外のステップ（取り込み・計画・完了の検証など）は続ける
- [ ] 壊れた定義の代わりに、組み込みの定義で動かすことはしない
- [ ] 定義を直した後のサイクルでは、止めていた委譲を始める

### どの定義で動くか

- [ ] 走っている実行は、始めたときの定義で最後まで動く（途中で定義を置き換えても変わらない）
- [ ] まだ始まっていないタスクは、始めるときの最新の定義で動く（計画の承認は、フローの名前を認めたものとして扱う）
- [ ] 委譲の記録に、ワークスペースの定義か組み込みかと、定義の中身のハッシュを残す
- [ ] タスクの詳細の「委譲先の実行」の区画に、「ワークスペースの定義」か「組み込み」かと、ハッシュの先頭を出す

### 外せない線

- [ ] 定義が書く予算の上限が、委譲先の宣言や課題の予算の上限より大きくても、宣言と課題の上限で止まる
- [ ] レビュー・品質の検査・CI を待つステップは、定義から外せる（外した定義も検査を通る）

既定ブランチへ入れるのは、S1 では、いまと同じく完了と反映の承認の後だけ（承認を待つのは外側の流れで、S1 では変えない）。承認を待たずに入れる形は、外側のフローの上書き（S3）で、開発者の判断で選べるようにする。定義では外せない線として固定しない（決定 2026-11-28 オーナー）。

**有効な定義は人が決める（方針・決定 2026-11-28 オーナー）**: 将来、学習のサイクルで AI がフローを直すときも、AI は定義の案を作るまでとし、どの定義を有効にするかは人が決める。S1 では、ワークスペースに定義を置くこと（ワークスペースの Git に履歴が残る）が有効にすることにあたる。

### レビューのステップ

- [ ] 組み込みの実装のフロー（標準と簡略）では、セルフレビューを実装のステップの外の、レビューのステップとして行う（レビュー → 直す → レビュー…）
- [ ] レビューのステップは、結果を「直すべき指摘あり」「直すべき指摘なし」「レビューを最後まで行えなかった」のどれかで返す
- [ ] 結果ごとの次のステップは定義（YAML）の遷移に書く。ループするか（指摘ありを直すステップへ向けて、レビューへ戻す）、ループしないか（指摘ありをそのまま先へ進める）も、遷移の書き方で決まる
- [ ] レビューへ戻る回数の上限は定義に書き、システムが数える
- [ ] 「直すべき指摘」とみなす重さの境目（既定は中以上）は、レビューのステップの入力として定義に書ける
- [ ] 上限に達しても直すべき指摘が残るとき、またはループしない定義で指摘があるときは、残った指摘を PR に載せて先へ進む
- [ ] レビューを最後まで行えなかったときの進み方（止める・もう一度レビューする）も、定義の遷移に書く（組み込みの定義は、いまと同じく PR へ進めずに止める）
- [ ] レビュアーの構成（どのレビュアーを使うか、指摘を疑う役を置くか）は、レビューのステップの入力として定義に書く
- [ ] 標準のフローの既定は、レビュアー 2 体（コード・設計）と指摘を疑う役、レビューへ戻る回数の上限は 3（最初のレビューと合わせて最大 4 回レビューする）
- [ ] 簡略なフローの既定は、レビュアー 2 体（コード・設計）、指摘を疑う役なし、レビューへ戻る回数の上限は 1（最初のレビューと合わせて最大 2 回レビューする）
- [ ] 標準のフローの Codex のレビューは、実装のステップではなく、レビューのステップで、レビュアーと並べて行う（決定 2026-11-28 オーナー）
- [ ] Codex のレビューを使うかは、レビューのステップの入力として定義に書く（標準のフローは使う・簡略なフローは使わない）
- [ ] レビューの 1 回ごとに、ステップの記録（費用・時間・指摘の数）が残り、タスクの詳細で見える
- [ ] レビューのステップを通らずに PR へ進む実行は、レビューのステップを外した定義を使ったときだけにする（組み込みの定義では、いまと同じくレビューを省けない）

### 文書

- [ ] 設計書と用語集に、ワークスペースの定義・写す口・確かめる口・外せない線・レビューのステップを書く
- [ ] フローの書き方の手引き（置き場・置ける物・写して直す手順・確かめ方）を文書に足す

## 非機能要件

- 検査は組み込みと同じ規則を使い、ワークスペースの定義だけを緩くも厳しくもしない
- 定義を置かないワークスペースの振る舞いは、レビューのステップ化を除いて、いまと変わらない

## 基本設計

- **定義の探し方**: 委譲を始めるとき、フローの名前でワークスペースの置き場を先に探し、無ければ組み込みを使う。見つけた定義はその場で検査し、通ったものだけを実行に渡す。実行は、渡された定義を始めた時点の写しとして持つので、途中で置き場のファイルが変わっても影響しない。
- **指示文の探し方**: ワークスペースの定義が指す指示文は、ワークスペースの置き場を先に探し、無ければ組み込みを使う。組み込みの定義は、組み込みの指示文だけを使う。
- **外せない線の置き場**: 予算の上限は、フローを進める仕組みではなく core が持つ。定義はこれを外す口を持たない。既定ブランチへ入れる前の承認は、外側の流れ（core）が持ち、S3 で上書きの対象にする。
- **壊れた定義の知らせ**: 委譲を始める前の検査で落ちたものは、その課題を進めずに、オーナーの対応を待つものとして出す。直されたかは次のサイクルで検査し直して判断する。
- **レビューのステップ**: 実装のステップは実装と必須ゲートまでを行い、レビューのステップがレビュアー（と指摘を疑う役・Codex）を呼んで指摘を返し、直すステップが直す。レビューへ戻る回数は定義の上限でフローを進める仕組みが数える。レビュアー自体は、いまと同じく claude-harness のプラグインのものを使う（claude-harness は変えない）。

## やらないこと

- 外側のフロー（課題の進め方）の上書き（S3。承認を待たずに既定ブランチへ入れる形を含む）
- 完了の検証のステップ化（S4）
- 部品の Go への書き直し
- 学習のサイクルでのフローの最適化
- 出力の型とつなぎのスクリプトをワークスペースに置くこと
- 組み込みとの差分だけを書く上書き
- claude-harness のリポジトリの変更
