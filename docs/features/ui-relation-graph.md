## 概要

課題が増えて、課題どうしの関係を頭で追えなくなっている。計画を承認した課題を完了確認で差し戻すことが増えた（オーナー・2026-10-09）。UI に、ワークスペース（エージェント）ごとの課題の関係グラフを足し、文章を読む前に「どの課題がどの課題を待っているか」「誰が動くべきか」を一目で分かるようにする。

グラフは手で書く図にしない。core の記録（課題・依存・親子・run・カードの導出）から**決定的に**作り、LLM に書かせない（#176 の本文）。

#176 の 3 つの見せ方（関係グラフ・背景のタイムライン・予想と実物の 2 列のプレビュー）のうち、この区切りでは関係グラフだけを作る【決定 2026-11-02 オーナー Q1=1】。

## 機能要件

### 親子（core）

- 課題は親を 0 個か 1 個持てる（`challenge_parent`）。1 つの課題が持てる親は 1 つまで【決定 2026-10-14 オーナー（PR #210 の問い 2）】
- 自分自身を親にする登録と、親子が循環する登録は拒否する（何も書かない）【決定 PR #210 の仕様の変更案 3】
- 親子は表示（関係グラフの入れ子）にだけ使う。状態機械・委譲の起動の判定・依存の評価には使わない【仮定】
- 親子の変更は課題の版を上げない。作業ログに `entity=challenge`・`action=parent_set`（または `parent_clear`）を残す【仮定。版は承認の照合に使うため、表示だけの関係の変更で上げない】
- ストアの全状態の書き出しと再構築（`Export`・`Import`）に親子を含める

### 取り込み（GitHub のコネクタ）

- 上流の Issue の sub-issue の関係（REST の Issue の応答の `parent_issue_url`）を読む。親の Issue と子の Issue がどちらも core の課題に対応している（`source_binding` がある）とき、子の課題の親を親の課題にする【決定 2026-11-02 オーナー Q2=2】
- 取り込みで見えた子の Issue の上流に親が無い（sub-issue から外された）か、親の Issue が core に無いときは、子の課題の親を外す
- 取り込みを繰り返しても結果は変わらない（冪等。変わらなければ作業ログも残さない）
- 一覧の取得に失敗したリポジトリ・この回に見えなかった Issue（閉じた・取り込みの対象から外れた）の課題の親子は変えない【仮定】
- 親を付けると循環になるときは、その親子を付けずに取り込みを続ける（取り込み全体を失敗にしない）【仮定】
- `/create-ticket` で課題を分解すると sub-issue が付くので、それがそのまま親の大枠になる【決定 Q2=2】

### 関係グラフの API

`GET /api/v1/workspaces/{name}/graph`（閲覧の API。ワークスペース単位）。応答は次の形で、`internal/view` の型から `web/src/api/types.gen.ts` を生成する。

| キー | 中身 |
|---|---|
| `nodes[]` | 課題 1 件ごと（ID の数の昇順）。`id`・`title`・`headline`（一言で。無ければ `null`）・`context`（位置づけ。無ければ `null`）・`category`・`running`・`stale`・`parent_id`（親の課題の ID。無ければ `null`） |
| `edges[]` | 依存 1 本ごと（`from` の数・`to` の数の昇順）。`from`（先行＝依存先）・`to`（後続＝依存元）・`kind`・`satisfied`（依存が満たされているか。M45H12 の評価と同じ）・`registered_via`・`registered_at` |

- `category` は「誰が動くべきか」の 4 区分で、上から先に当たったものを採る【決定 2026-10-14 オーナー（#176 コメント 4「区分」）】
  1. `human`（人間の操作待ち）: カードの `next_human_actions` が空でない
  2. `external`（外部待ち）: 自動では解けない、相手と理由を持つ待ち。いまの core にはこれを表す記録が無いので、この区切りでは出ない（外部待ちの印を core に足すときに使う）【決定 #176 コメント 4。出ないことは仮定】
  3. `done`（完了）: 状態が完了
  4. `system`（システムが進めている）: 上のいずれでもない。CI の待ち（カードの印 `waiting_ci`）はここに入る【決定 #176 コメント 4】
- `running` は課題の run が動いている（カードの印 `running` か `unresponsive`）、`stale` は動いている run の記録が途絶えている（カードの印 `unresponsive`。M4H34 の「更新なし」）。カードの導出はボードの `GET …/challenges` と同じ規則を使う
- `kind` は依存の種類の閉集合 `prerequisite`（終わらないと始められない。先行の成果を使う）・`conflict`（同時に走らせると衝突する。同じものを触るので順に走らせる）【決定 #240 の決定 4（線の 2 種）】。`challenge_dependency` は先行関係だけを記録するので、いまの core からは `prerequisite` だけが出る（`conflict` を記録する口は #240 の「本実装への問い」1・2 で決める）【仮定】
- 依存の理由は、core の記録から決まる `kind`・`satisfied`・`registered_via`（依存を登録した経路。`plan`＝計画の判断・`manual`＝端末のコマンド・`unknown`＝作業ログから決まらない）・`registered_at`（登録の日時）で表し、人に読ませる文は UI が組み立てる【仮定。理由の文を LLM に書かせない（#176 の本文）】
- 中身は core の記録だけから作り、LLM を呼ばず、上流（GitHub）にも問い合わせない。同じストアと同じ現在時刻からは、バイト列として同じ応答になる
- 依存の循環がストアにあっても失敗にしない（辺はそのまま返す。UI が扱う）

### 画面（web）

- 本番の画面はボードの 1 枚のまま（M4H23）で、その中に「グラフ」と「ボード」の表示の切り替えを置く。**既定はグラフ**で、ボードへ切り替えられる。ボードの挙動は変えない【決定 2026-10-13 オーナー（#176 コメント 3 の 1）】
- グラフはワークスペースごとに描き、ワークスペースは選択欄で選ぶ【仮定。アイコンの列の作り直しは範囲外】
- 親子は線でなく、**親の大枠の中に子を置く入れ子**で表す（AWS の構成図のように）。親ごとに畳め、畳んだ親は重ねた箱になり、中の件数と、実施中・人間の操作待ちの子の件数を示す【決定 #176 コメント 3 の 4・追加の指示】
- 開いたときは、実施中か人間の操作待ちの子（孫を含む）を持つ親だけを開いておく。開いた親の状態はサーバに持たない【決定 2026-10-14 オーナー（PR #210 の問い 1 の (b)）】
- 開いた親の大枠の見出しは、1 行目に ID と題名、その下の欄に一言で、さらにその下に位置づけを出す。一言では常に全文を出し、位置づけは見出しの幅で 1 行に収まらなければ畳み、末尾を「…」にして「▾ 続き」で広げる。「続き」はボタンの見た目にせず文字だけにするが、キーボードで押せる【決定 #240 の決定 3・8】
- ノードには常に題名を出す。一言では、カーソルを重ねたとき（キーボードで移ったときも）に吹き出しで出す。重ねている間は先行と後続を強調する。開いた大枠には吹き出しを出さない【決定 #240 の決定 1・2・9】
- 依存の線は、`prerequisite` を実線と塗りの矢じり、`conflict` を破線と中抜きの矢じりで描く。理由の札は、線を押したとき（もう一度押すと外す）と重ねたときだけ出し、課題に重ねても出さない。札には種類と、登録の経路と日時と、満たされているかを書く【決定 #240 の決定 4】
- 色は、区分の 4 色（人間の操作待ち・外部待ち・システムが実行中〔`running`〕・システムが次に進めるもの〔それ以外の `system`〕）に完了の灰色を加える。完了は灰色だけで示し、取り消し線は付けない【決定 #176 コメント 3 の 2・コメント 4】
- 凡例は区分の名前と色だけにし、実装の語（`waiting_ci`・`next_human_actions` など）を画面に出さない【決定 #240 の決定 12・#176 コメント 4】
- 実施中（`running`）の課題は光の輪で強調する。OS で動きを減らす設定にしていれば明滅しない。「先行待ち」の区分や色は足さない【決定 #176 コメント 3 の 3】
- `stale` の課題は箱を赤みにして「⚠ 更新なし（要確認）」と出す【決定 #176 コメント 4・M4H34】
- 課題（ノード・開いた大枠の見出し）を押すか Enter・Space を押すと、ボードのカードと同じ詳細のモーダルを同じ開き方で開き、閉じたら押したものへフォーカスを戻す【決定 #240 の決定 9】
- グラフから開いた詳細のモーダルには、「課題」の節の後ろに「待っている理由（直前の先行）」の節を出す。その課題が直接待っている先行課題を ID の順に並べ、題名・完了か実施中かの印・依存の種類と理由を添える。待っている先行が無ければ節ごと出さない。ボードから開いた詳細には出さない【決定 #240 の決定 13。ボードに出さないことは仮定（#240 の本実装への問い 5 は未決）】
- 画面の右側は、ターミナル／対話の欄のために空けておく（欄は作らない）【決定 #240 の決定 9・10・Q5=1】
- 幅 480px 以下では、グラフの代わりに親ごとに畳んだ一覧を出す。各課題には区分と、先行と後続を文字で付ける。幅 360px で横スクロールが出ない【決定 Q4=1。境の 480px は試作の狭い画面の境に合わせた仮定】
- 表示（グラフ・ボード）は、ボードと同じくストアの変更の通知と 60 秒ごとの取り直しで読み直す【仮定】

## 受入基準

- [ ] 課題に親を 1 つ保存でき、2 つ目の親の登録は付け替えになり（1 つまで）、自己参照と循環を拒否して何も書かない（`internal/core` のテスト）
- [ ] 親子が書き出しと再構築で保たれる
- [ ] 取り込みで、上流の sub-issue の関係が core の親子に写る。同じ上流で取り込みを繰り返しても親子と作業ログが変わらない。sub-issue を外すと親子も外れる（`internal/core` と `internal/adapters/github` のテスト）
- [ ] `GET …/graph` が、ノード・依存の辺・親子を core の記録だけから返し、LLM と上流を呼ばない。同じストアと同じ現在時刻から同じバイト列を返す（`internal/core`・`internal/server` のテスト）
- [ ] UI の既定の表示がグラフで、ボードへ切り替えられる。親の大枠を畳め・開ける。人間の操作待ちの課題が色（区分）で区別できる。ノードを押すと詳細のモーダルが開き、待っている理由の節が出る（Vitest のコンポーネントのテスト）
- [ ] 幅 360px で、親ごとに畳んだ一覧（先行・後続を文字で示す）が出て、横スクロールが出ない（ブラウザの E2E）
- [ ] 本番のビルドに偽の API・試作の画面の文言が入らない（`web/src/build.test.ts`）

### 未決（#240 の「本実装への問い」）

- 問い 1・2（依存の理由と種類の出どころ）: この区切りでは `kind` を閉集合として持ち、いまの core からは `prerequisite` だけを出す。`conflict` を記録する口（衝突の予測の結果から core が書くか）と、理由の文を誰が書くかは未決

- 問い 4（タッチ端末での強調）: この区切りでは足さない（押すと詳細が開き、一言では詳細で読める）
- 問い 5（待っている理由をボードから開いた詳細にも出すか）: この区切りではグラフから開いたときだけ出す
