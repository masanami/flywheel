## 概要

課題が増えて、課題どうしの関係を頭で追えなくなっている。計画を承認した課題を完了確認で差し戻すことが増えた（オーナー・2026-10-09）。UI に、ワークスペース（エージェント）ごとの課題の関係グラフを足し、文章を読む前に「どの課題がどの課題を待っているか」「誰が動くべきか」を一目で分かるようにする。

グラフは手で書く図にしない。core の記録（課題・依存・親子・run・カードの導出）から**決定的に**作り、LLM に書かせない（#176 の本文）。

#176 の 3 つの見せ方（関係グラフ・背景のタイムライン・予想と実物の 2 列のプレビュー）のうち、この区切りでは関係グラフだけを作る【決定 2026-11-02 オーナー Q1=1】。

## 機能要件

### 親子（core）

- 課題は親を 0 個か 1 個持てる（`challenge_parent`）。1 つの課題が持てる親は 1 つまで【決定 2026-10-14 オーナー（PR #210 の問い 2）】
- 自分自身を親にする登録と、親子が循環する登録は拒否する（何も書かない）【決定 PR #210 の仕様の変更案 3】
- 親子は表示（関係グラフの入れ子）にだけ使う。状態機械・委譲の起動の判定・依存の評価には使わない【仮定】
- 親子の変更は課題の版を上げない。作業ログに `entity=challenge`・`action=parent_set`（または `parent_clear`）を残す【仮定。版は承認の照合に使うため、表示だけの関係の変更で上げない】
- ストアの全状態の書き出しと再構築（`Export`・`Import`）に親子を含める

### 取り込み（GitHub のコネクタ）

- 上流の Issue の sub-issue の関係（REST の Issue の応答の `parent_issue_url`）を読む。親の Issue と子の Issue がどちらも core の課題に対応している（`source_binding` がある）とき、子の課題の親を親の課題にする【決定 2026-11-02 オーナー Q2=2】
- 取り込みで見えた子の Issue の上流に親が無い（sub-issue から外された）か、親の Issue が core に無いときは、子の課題の親を外す
- 取り込みを繰り返しても結果は変わらない（冪等。変わらなければ作業ログも残さない）
- 一覧の取得に失敗したリポジトリ・この回に見えなかった Issue（閉じた・取り込みの対象から外れた）の課題の親子は変えない【仮定】
- 親を付けると循環になるときは、その親子を付けずに取り込みを続ける（取り込み全体を失敗にしない）【仮定】
- `/create-ticket` で課題を分解すると sub-issue が付くので、それがそのまま親の大枠になる【決定 Q2=2】

### 衝突（core）

衝突の予測の結果（`harness predict-conflicts` の出力。[M3 の仕様](m3-invoker-delegation.md) §実行スロット）を、core が保存し、関係グラフの API が衝突の辺（`kind=conflict`）として返す【決定 2026-11-05 オーナー（flywheel#474）】。

- **別の表に置く**: 衝突は `challenge_conflict`（マイグレーション 0018）に記録し、`challenge_dependency` と、それを使う依存の評価・委譲の対象の選び方・起動の判定は変えない。依存の判定は `challenge_conflict` を読まない。衝突は着手の門にしない（前提の依存が満たされていれば、衝突の行があっても依存の判定は通る）【決定 2026-11-05 オーナー Q3=2】
- 持つ情報: `challenge_id`（後回しにした課題。向きの無い組は ID の小さい側）・`conflicts_with_id`（先に委譲した課題。向きの無い組は大きい側）・`directed`（向きの有無）・`cycle_id`（予測した周）・`run_id`（予測の口を呼んだ run）・`created_at`。主キーは `(challenge_id, conflicts_with_id)`。自己参照と、向きの無い組で `challenge_id` が大きい行は CHECK 制約で拒否する。ストアの全状態の書き出しと再構築（`Export`・`Import`）に含める
- **向き**: 「後回しにした課題 → 先に委譲した課題」の向きで記録する【決定 2026-11-05 オーナー Q2=1】。まだどちらも委譲していない組（衝突と予測されたが、どちらを先にするかが決まっていない間）は、向きの無い関係（`directed = 0`）として持ち、UI は矢印なしの破線で描く【決定 2026-11-05 オーナーの補足】
- **置き換え**: 予測のたびに、その予測の結果で記録を最新にする。片方が完了・取り下げになった衝突は、グラフの API が返さない（行は残す）【決定 2026-11-05 オーナー Q1=1】
- 記録する組は、直列化グループを作る組（理由が `shared_files`・`dependency`・`unknown_pair` のいずれか）とする【仮定。同時に委譲されなかった理由が見えることと、既存の直列化の挙動を変えないこと（直列化の判断は記録を読まない）から】。共有ファイルが `merge_friendly`・`ignored` だけの組など、直列化されない組は記録しない
- 置き換えの範囲は、その予測の対象にした課題（委譲の候補と、その周より前から終了していない委譲の run を持つ課題）のうち、両端がその対象に入っている既存の行をすべて消し、新しい結果の組を入れる【仮定】。今回の予測の対象に入らなかった課題との組は触らない（今回は予測していないので新しい情報が無い。相手が終われば、返さない条件で消える）
- 予測が得られなかったとき（`prediction_failed`・`prediction_budget`・`not_predictable`・`no_prediction_declared`、予測の口を呼ばなかった周）は、既存の行を残し、行も足さない【仮定。組の情報が無く、相手を決められないので、候補をまとめて直列化する既存の挙動のまま、衝突の記録は変えない】
- 間接的に同じ直列化グループに入っただけの組（A と B、B と C が衝突し、A と C は予測されていないとき）は足さない。「衝突のため後回し」の相手は、予測が見た組の相手になる【仮定】
- 組の向きは、次の時点で決める【仮定】。実行中の課題（その周より前から終了していない委譲の run を持つ課題）との組は、予測の結果を記録する時点で「候補 → 実行中の課題」の向きにする。候補どうしの組は、まず向きの無い組として記録し、片方の委譲の run を記録するトランザクションの中で「もう片方 → 起動した課題」の向きにする（すでに向きのある組は変えない）。実行中の課題どうしの組は、後回しにした課題が無いので記録しない。後回しにした課題が後で委譲を起動したら（run の記録と同じトランザクション）、その課題を後回しの側とする向きのある組は外す（もう待っていないので、待っている理由とグラフの線に残さない）
- 衝突の記録の書き込みに失敗しても、委譲の計画は止めない（記録は表示のためで、着手の門にしない）【仮定】
- 前提の依存と衝突が同じ課題どうしにあっても、別々の辺として返す

### 関係グラフの API

`GET /api/v1/workspaces/{name}/graph`（閲覧の API。ワークスペース単位）。応答は次の形で、`internal/view` の型から `web/src/api/types.gen.ts` を生成する。

| キー | 中身 |
|---|---|
| `nodes[]` | 課題 1 件ごと（ID の数の昇順）。`id`・`title`・`headline`（一言で。無ければ `null`）・`context`（位置づけ。無ければ `null`）・`category`・`running`・`stale`・`state`（課題の状態。カードの `state` と同じ値）・`next_human_actions`（人間の操作待ちの中身。カードの `next_human_actions` と同じ値・並び。無ければ `[]`）・`priority`（課題の優先度。カード・一覧の `priority` と同じ値。付いていなければ `null`）・`parent_id`（親の課題の ID。無ければ `null`） |
| `edges[]` | 依存 1 本ごと（`from` の数・`to` の数の昇順。同じ組なら前提が先）。`from`・`to`・`kind`・`directed`（辺に向きがあるか。前提は常に `true`）・`satisfied`（前提が満たされているか。M45H12 の評価と同じ。衝突は常に `false`）・`registered_via`・`registered_at`。前提（`prerequisite`）は `from`＝先行（依存先）・`to`＝後続（依存元）。衝突（`conflict`）は向きが逆で、`from`＝後回しにした課題・`to`＝先に委譲した課題（`directed` が `false` の組は向きが無く、`from` は ID の小さい側） |

- `category` は「誰が動くべきか」の 6 区分で、上から先に当たったものを採る【決定 2026-10-14 オーナー（#176 コメント 4「区分」）。10/14 の決定は 4 区分で、`withdrawn` を足したのは【決定 2026-11-04 オーナー（PR #455 の動作確認）】、`parent_agent` を足したのは【決定 2026-11-05 オーナー（#452 の Q6=1）】】
  1. `human`（人間の操作待ち）: カードの `next_human_actions` が空でない
  2. `external`（外部待ち）: 自動では解けない、相手と理由を持つ待ち。いまの core にはこれを表す記録が無いので、この区切りでは出ない（外部待ちの印を core に足すときに使う）【決定 #176 コメント 4。出ないことは仮定】
  3. `parent_agent`（親のエージェントが動く番）: 状態は人間対応待ちのまま、いま開いている保留の種類が親が直接行う（`parent_direct`。#452）で、人間の操作待ちが別に無い課題。オーナーが答える問いではないので `human` に入れない（カードの `answer_question` も出ない）。新しい状態は作らない【決定 2026-11-05 オーナー（#452 の Q6=1）】
  4. `done`（完了）: 状態が完了
  5. `withdrawn`（取り下げ）: 状態が取り下げ。完了と同じく終わった課題で、進める主体がいない（以前は `system` に入っていたのを分けた）【決定 2026-11-04 オーナー（PR #455 の動作確認）】
  6. `system`（システムが進めている）: 上のいずれでもない。CI の待ち（カードの印 `waiting_ci`）はここに入る【決定 #176 コメント 4】（【方針の更新 #523】ボードのカードの「CI 待ち」の印は外す方針。委譲先が CI を待つ間は委譲が「実行中」に見える。コードの変更は #547 の後に別の PR で行い、それまでは今の印が残る。この行の期待値は書き換えない。M3P48 を参照）
- `running` は課題の run が動いている（カードの印 `running` か `unresponsive`）、`stale` は動いている run の記録が途絶えている（カードの印 `unresponsive`。M4H34 の「更新なし」）。`state`・`next_human_actions`・`priority` を含め、カードの導出はボードの `GET …/challenges` と同じ規則を使う（画面が「ほかの課題」の判定（注目の決め方）と札の語をこの応答だけで決められるように、グラフの応答に持つ。ボードの取得とのずれを避けるため）
- `kind` は依存の種類の閉集合 `prerequisite`（終わらないと始められない。先行の成果を使う。`challenge_dependency` から出す）・`conflict`（同時に走らせると衝突する。同じものを触るので順に走らせる。`challenge_conflict` から出す。§衝突（core））【決定 #240 の決定 4（線の 2 種）。`conflict` を core が保存して返すことは 2026-11-05 オーナー（flywheel#474）】。片方が完了・取り下げになった衝突は返さない
- 依存の理由は、core の記録から決まる `kind`・`satisfied`・`registered_via`（依存を登録した経路。`plan`＝計画の判断・`manual`＝端末のコマンド・`unknown`＝作業ログから決まらない・`prediction`＝衝突の予測の結果〔衝突の辺だけ〕）・`registered_at`（登録の日時。衝突は `challenge_conflict.created_at`）で表し、人に読ませる文は UI が組み立てる【仮定。理由の文を LLM に書かせない（#176 の本文）】
- 中身は core の記録だけから作り、LLM を呼ばず、上流（GitHub）にも問い合わせない。同じストアと同じ現在時刻からは、バイト列として同じ応答になる
- 依存の循環がストアにあっても失敗にしない（辺はそのまま返す。UI が扱う）。衝突の辺は先行・後続の順序を持たないので、前提の辺と合わせても循環とは数えない

### 画面（web）

- 本番の画面はボードの 1 枚のまま（M4H23）で、その中に「グラフ」と「ボード」の表示の切り替えを置く。**既定はグラフ**で、ボードへ切り替えられる。ボードの挙動は変えない【決定 2026-10-13 オーナー（#176 コメント 3 の 1）】
- グラフはワークスペースごとに描き、ワークスペースは選択欄で選ぶ【仮定。アイコンの列の作り直しは範囲外】
- 親子は線でなく、**親の大枠の中に子を置く入れ子**で表す（AWS の構成図のように）。親ごとに畳め、畳んだ親は重ねた箱になり、中の件数と、実施中・人間の操作待ちの子の件数を示す【決定 #176 コメント 3 の 4・追加の指示】
- 開いたときは、実施中か人間の操作待ちの子（孫を含む）を持つ親だけを開いておく。開いた親の状態はサーバに持たない【決定 2026-10-14 オーナー（PR #210 の問い 1 の (b)）】
- 開いた親の大枠の見出しは、1 行目に ID と題名、その下の欄に一言で、さらにその下に位置づけを出す。一言では常に全文を出し、位置づけは見出しの幅で 1 行に収まらなければ畳み、末尾を「…」にして「▾ 続き」で広げる。「続き」はボタンの見た目にせず文字だけにするが、キーボードで押せる【決定 #240 の決定 3・8】
- ノードには常に題名を出す。一言では、カーソルを重ねたとき（キーボードで移ったときも）に吹き出しで出す。重ねている間は先行と後続を強調する。開いた大枠には吹き出しを出さない【決定 #240 の決定 1・2・9】
- 依存の線は、`prerequisite` を実線と塗りの矢じり（先行 → 後続）、`conflict` を破線と中抜きの矢じり（後回しにした課題 → 先に委譲した課題。前提と向きが逆）で描く。向きの無い衝突（`directed` が `false`）は、矢じりなしの破線で描く。理由の札は、線を押したとき（もう一度押すと外す）と重ねたときだけ出し、課題に重ねても出さない。札には種類と、前提は登録の経路と日時と満たされているか、衝突は後回しの向き（向きの無い組は「向きは未定」）と予測の日時を書く【決定 #240 の決定 4。向きの無い線と衝突の札の中身は 2026-11-05 オーナー（flywheel#474）の決定を受けた仮定】
- 衝突の辺は先行・後続に数えない【仮定】。配置の層は前提の辺だけで決め、衝突の線は両端の箱の位置に合わせて引く（上下に離れていれば向かい合う端、同じ段なら向かい合う側面）。衝突だけの課題も「関係の無い課題」にはしない（線を持つ）。課題に重ねると、衝突の相手と線も濃く残る。幅 480px 以下の一覧には、先行・後続と別に「衝突のため後回し: C-xx」「衝突で先に委譲: C-xx」「衝突の可能性（順序は未定）: C-xx」を文字で出す
- 色は、区分の 4 色（人間の操作待ち・外部待ち・システムが実行中〔`running`〕・システムが次に進めるもの〔それ以外の `system`〕）に完了の灰色を加える。完了は灰色だけで示し、取り消し線は付けない【決定 #176 コメント 3 の 2・コメント 4】。親のエージェントが動く番（`parent_agent`）は、これらと見分けられる色を 1 つ足し、凡例に「親のエージェントが動く番」の名前で出す【決定 2026-11-05 オーナー（#452 の Q6=1）。色の選びは仮定】
- 取り下げ（`withdrawn`）は完了と同じ灰色で描き（取り消し線なし）、ノード（開いた親の大枠の見出しを含む）に「取り下げ」の札を出して完了と区別する。凡例にも「取り下げ」を完了と同じ灰色で出し、狭い画面の一覧の区分の表示も「取り下げ」にする【決定 2026-11-04 オーナー（PR #455 の動作確認）。札の置き場所〔ノードの右上〕は仮定】

- **流し方**: `make e2e-real`（`ui-build` と `build` の後に `npm run e2e:real`）。`make check` にも `make e2e` にも入れない。初回は `cd web && npx playwright install chromium` が要る
- **種**: 準備の段が毎回、一時ディレクトリにワークスペース（`seed`）を作り、Go のテスト `TestRelationGraphSeed`（`internal/core/relation_graph_seed_test.go`）を環境変数 `FLYWHEEL_E2E_SEED_WORKSPACE` に置き場を渡して呼び、種のストアを作る。種は core の公開 API で作り、公開 API で作れない状態（完了・取り下げ・着手中・優先度つきの分類待ち）だけを `internal/core/coretest` で書く。固定のストアのファイルも本番のストアの写しも置かない。同じテストは `make check` でも置き場を `t.TempDir()` にして流れ、種の中身（区分・状態ごとの件数・線・親子）を検査する
  - 種の中身: 人間の操作待ち（未回答の問い・不可逆操作の承認）、着手中、P0 の計画待ち・分類待ち、関係を持たない課題、起点を含まないまとまり（「ほかの課題」）、完了（前提・親になっているものと、どこにもつながらないもの。「ほかの課題」のまとまりの前提になっているもの。終わった課題の前提でしかないもの〔既定で隠れ、その線も描かれない〕）、取り下げ（前提になっているものと、どこにもつながらないもの）。推移的な注目のために、人間待ちの起点から依存で 2 段先の課題と、着手中の起点から親子で 2 段先の課題（どちらも自身は起点に当たらない）を入れる
- **環境の切り離し**: 準備の段は一時ディレクトリに HOME・XDG_CONFIG_HOME・作業ディレクトリを作り、ビルド済みの `build/flywheel` を `serve --port 0 --workspace <一時のワークスペース>` で起動する（開発機の `fleet.json` を読まない。#430）。標準エラーの `listening on <addr>` から番地を読み、そこが配信する UI に Playwright を向ける（Vite の proxy の 4318 番は使わない）。一時の HOME・XDG_CONFIG_HOME は serve にだけ渡し、Go のキャッシュと Playwright のブラウザの置き場は元のまま。終了時に serve を止め、一時ディレクトリを消す
- **確かめること**: ① 取り下げの区分と札 ② 終わった課題の既定の非表示と、前提・親の灰色の残し方、「終わった課題もすべて表示」 ③ 「ほかの課題」の大枠の中身 ④ 依存の線と親子の入れ子 ⑤ 人間の操作待ちの札 ⑥ P0 の分類待ち・計画待ちが前に出ること ⑦ 推移的な注目（2 段以上先の課題が大枠に入らず前に出る）。幅 480px 以下の一覧・見た目の細部（位置・色・コントラスト）は偽の API の E2E の分担のまま
- **偽の API の E2E との分担**: 偽の API の E2E は画面の挙動の細部（位置・色・狭い画面・開閉）を、作りやすい偽のデータで広く確かめる。本物の serve の E2E は、core の導出から API・配信した UI までをつないだときの区分と注目の判定を、関係グラフに絞って確かめる。偽の API の E2E は残す
- **CI**: `.github/workflows/ci.yml` のジョブ `e2e-real`（ubuntu-latest・`timeout-minutes: 20`）が、依存の導入（`make ui-install`）→ `npx playwright install --with-deps chromium` → `make e2e-real` の順に流す。既存のジョブ `check` は変えない
- **委譲の子の環境では流せない**: 委譲の子の環境（目印 `FLYWHEEL_DELEGATED_RUN` がある）では、flywheel のコマンドは help 以外拒否される（`internal/cli/cli.go`）ので、準備の段が起動する serve が拒否されて試験は失敗する（想定どおり）。準備の段は目印を外さない。子は本物の serve の試験を手元で流さず、PR の CI のジョブ `e2e-real` の成功で確かめる
