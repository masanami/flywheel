# 要求から計画まで — 取り込んだ Issue を区切りの課題に分け、課題の Issue を flywheel が作る（S3）

この文書は、要求と Issue の区切り（S3。前半 S3a と後半 S3b）の仕様の正本。S1・S2a は `docs/features/request-to-plan.md`、S2b（S2b-1・S2b-2）は `docs/features/request-to-plan-s2b.md` を正とし、この文書は前提にする。いまの実装対象は前半（S3a）。後半（S3b）の要件・設計・受入基準は、見出しに「（S3b）」を付けた節に置く（S3b を実装対象にするときに、括弧の無い節へ移す）。S3 が済んだ後、`docs/features/request-to-plan.md` へ畳む。それまではここに置く。

## 概要

やりたいこと（要求）が課題になり、仕様の文書ができ、計画が承認されるまでの流れのうち、S1〜S2b は「課題 1 件から、仕様の下書きと計画を作る」ところまでを定めた。課題 1 件が出荷の区切り 1 つに収まる前提で、収まらない Issue を取り込んだときの扱いと、課題と GitHub の Issue の対応は、いまのまま残っていた。

S3 は 2 つの区切りに分けた（オーナーの決定 2026-11-27。決定 22）。S3a、S3b の順に main へ入れる。

**前半（S3a。この文書の実装対象）: GitHub に書かない部分。**

1. **取り込んだ Issue を、区切り 1 つに収まるかで仕分ける。** 分類の判断点（J1）が、担当の課題について、区切り 1 つに収まるかを見る。収まらないと見たら、読み取りだけの新しい判断点「区切りを分ける判断点（J10）」が、分け方を調べて案を作る。core は、案を推奨にして、オーナーへ「この課題たちに分けるか」を 1 回だけ問う。調べた結果「分けなくてよい」なら、問わずにそのまま計画へ進む。
2. **分けると決まったら、区切りごとの課題を作り、要求の記録でまとめる。** 取り込みで最初にできた課題は取り下げ（元の Issue と紐づいたまま残す）、区切りごとに新しい課題を作って、課題の依存で順番をつなぐ。新しい課題は、要求の軽い記録（出どころ＝元の Issue、調べた証跡のファイルの場所）を指す。チャットの欄から、要求の記録を作って課題を分ける口も足す。要求から生まれた課題がすべて解決したら、証跡を消す。
3. **「この案で分ける」は、画面のボタンでも受ける。** 取り下げを伴う答えを画面のボタンで受けない決まり（設計書 §9）に、この答えだけの例外を作る。

S3a だけが入っている間は、分けた区切りの課題に GitHub の Issue は無く、元の Issue はオーナーが手で閉じる。

**後半（S3b）: GitHub に書く部分。**

1. **Issue の無い課題には、flywheel が課題の Issue を作る。** 計画を作る判断点（J2）が、計画に Issue を作るリポジトリを書く。オーナーは計画の承認で、どこに Issue ができるかも見て認める。承認の後、最初の委譲の前に、core が Issue を作り、取り込み元の対応（`source_binding`）にする。その後は、取り込みの追従と、委譲先の PR の `Closes` が、いまのまま効く。
2. **flywheel が作った課題の Issue は、課題が完了したときに開いていれば、どの PR で済んだかをコメントして閉じる。** 統合ブランチを使う計画では委譲先の PR に `Closes` が付かず、閉じる役が無いため（決定 22）。取り込んだ Issue は対象外（いまのまま）。
3. **分けた元の Issue は、区切りの課題がすべて解決したら、flywheel が「どの課題で済んだか」をコメントしてから閉じる。**
4. **計画を作る判断点の指示文から、取りまとめの課題を子の課題に分ける回答の項を削る。** 仕分けが分類の判断点へ移るので、計画の点検の項は要らなくなる。指示文の上限も、その分だけ下げる。

「flywheel は GitHub に書き込まない」という決まりは、S3b で、次の 4 つに限って緩める: 課題の Issue を作る（担当者を付ける）・flywheel が作った課題の Issue へのコメントと閉じる・分けた元の Issue へのコメント・分けた元の Issue を閉じる。ブランチ・PR・マージは、これまでどおり委譲先が行う。

決定の正本は検討の Issue（flywheel#1266）の「決まったこと」の 12（要求は課題を作るための材料として軽く扱う・取り込んだ Issue の仕分け・課題は出荷の区切り 1 つ・Issue の無い課題には flywheel が Issue を作る）・13（3 つ目の区切りの範囲）・21（S3 の仕様の前に決めた 6 点）・22（S3 を 2 つに分ける・「この案で分ける」は画面のボタンでも受ける・flywheel が作った課題の Issue を完了で閉じる）。
## 背景・目的

- いまの分類の判断点（J1）は、担当か・優先度だけを見る。区切り 1 つに収まらない Issue（例: 機能をまるごと求める Issue）も、そのまま 1 つの課題として計画へ進む。計画を作る判断点（J2）は、その課題を大きな 1 つの計画にするか、計画の点検の項（取りまとめの課題を子の課題に分ける回答のとき）でオーナーに問うしかなかった。
- オーナーの決定（決定 12）: 取り込んだ Issue は、いまと同じくまず課題になる。分類の判断が、区切り 1 つに収まるかを見る。収まらないものは、計画へ進めずにオーナーへ問う。すべてを要求として取り込む形は採らない（多くの Issue は課題 1 つになるため）。
- オーナーの決定（決定 21）: 分け方は問う前に調べ、案を推奨にして 1 回だけ問う（往復を 1 回にする）。最初にできた課題は取り下げて置き換える（最初の区切りの課題として使い続けると、最初の区切りの PR で元の Issue が早く閉じるため）。元の Issue は、区切りの課題がすべて解決したら flywheel が閉じる。
- いまの Issue の無い課題（チャットの欄・`flywheel create` で作った課題）は、GitHub の上で周りから見えない。オーナーの決定（決定 12・21）: flywheel が課題の Issue を 1 つ作って紐づける（独立の Issue。sub issue にしない。取り込みで sub issue はタスクと読むため＝設計書の D22）。作るのは計画の承認の後・最初の委譲の前（取り下げた・担当外の課題の Issue を残さないため）。タスクの Issue は作らない（分解の正本は計画のタスク）。
- 目的は、大きな Issue を取り込んでも、オーナーが 1 回答えるだけで、出荷の区切りごとの課題と計画に分かれて進み、GitHub の上でも、課題ごとの Issue と、元の Issue の閉じた理由が見えるようにすること。

- オーナーの決定（決定 22）: GitHub に書かない部分（S3a）と書く部分（S3b）に分け、S3a を先に入れる。S3a の間は、分けた課題に Issue は無く、元の Issue は手で閉じる。

## ユーザーストーリー

オーナーとして、大きな Issue を取り込んでサイクルを回したら、区切りに分ける案を、推奨つきで 1 回だけ聞いてほしい。「この案で分ける」を押せば、区切りごとの課題ができ、順番どおりに計画へ進んでほしい。分け方を少し直したいときは、分けた後に対話の欄で課題を足したり取り下げたりしたい。区切りの課題がすべて済んだら、元の Issue には、どの課題で済んだかが書かれて閉じていてほしい。

チャットの欄で話して作った課題も、計画を承認したら GitHub に Issue ができて、周りの人から見えるようにしたい。どのリポジトリに Issue ができるかは、計画の承認のときに見て決めたい。

## 機能要件

この節は、実装対象の S3a の要件。S3b の要件は、下の「機能要件（S3b）」に置く。

### 分類の判断点が、区切り 1 つに収まるかを見る

- [ ] 分類の判断点（J1）の出力に、区切り 1 つに収まるか（`fits_one_slice`。真偽）を足す。
- [ ] 判定が担当（`mine`）の出力では、`fits_one_slice` を必須にする（無い・`null` は不正な出力）。
- [ ] 判定が担当でない（`not_mine`）・判断できない（`uncertain`）の出力では、`fits_one_slice` を省いてよい。値があっても使わない。
- [ ] core が `fits_one_slice` の偽を使うのは、課題が次の 3 つをすべて満たすときだけ: 出どころ（`challenge.origin`）が取り込み（`ingest`）・取り込み元の子（`source_child`）の記録を持たない・要求の記録を指していない。ほかの課題では偽でも使わず、いまのまま計画へ進む。
- [ ] 偽を使う課題では、core は、いまの担当の写し（分類済へ進め、優先度・一言で・位置づけを書く）に加えて、同じ書き込みで、区切りを分ける記録（`slice_split`）を状態 `pending` で作り、その分類の判断点の実行の理由を記録の `classify_reason` に書く。
- [ ] 作業ログに、区切りを分けると決まったこと（`slice_split_requested`）を残す。
- [ ] 区切りを分ける記録が `pending` か `awaiting_owner` の課題は、計画を作る判断点の対象から外す（自動の対象選びでも、ID を指定した `flywheel plan` でも）。ID を指定したときは、「着手しなかった」に理由 `slice_split_pending` で出す。

### 区切りを分ける判断点（J10）

- [ ] 判断点を 1 つ足す。役割の語は「区切りを分ける判断点」、ID は `J10`。
- [ ] 区切りを分ける判断点は、読み取りの道具だけを持つ（いまの判断点と同じ。書き込み・外部への送信はできない）。
- [ ] 作業ディレクトリは、ワークスペース（いまの判断点の既定と同じ）。リポジトリの元のクローン（`.flywheel/repos/` の下）の文書とコードを、読み取りの道具で読める。
- [ ] サイクルの分類の段で、分類の判断点の後に、記録が `pending` の課題ごとに 1 回呼ぶ。
- [ ] 手で呼ぶ口として、`flywheel classify --auto` にも同じ扱いを入れる（分類の判断点の後に、記録が `pending` の課題を呼ぶ）。
- [ ] 入力の区画は 5 つで、この並び: 「課題」「取り込み元の対応」「分類の理由」「リポジトリ」「ポジション定義」。
- [ ] 区画「課題」には、課題の題名・説明・達成条件・緊急度・起票者を書く（分類の判断点の区画「課題」と同じ）。
- [ ] 区画「取り込み元の対応」には、元の Issue の URL と外部キーを書く。
- [ ] 区画「分類の理由」には、記録の `classify_reason`（区切りを分けると決めた分類の判断点の実行の理由）を書く。
- [ ] 区画「リポジトリ」には、委譲先の宣言（`connectors.json`）のリポジトリごとに、名前・GitHub の上の名前（`remote`）・元のクローンの場所（宣言の `slots.base`。ワークスペースから見た相対のパス。`slots.base` を持たない〔`provider` が `clone` の〕リポジトリは「なし」）を書く。
- [ ] 区画「ポジション定義」には、ポジション定義の本文を書く。
- [ ] 出力の判定は 2 つ: 分ける（`split`）・分けない（`single`）。
- [ ] 判定が `split` の出力は、区切りの一覧（`slices`）を 2 件以上 8 件以下で持つ。
- [ ] 区切り 1 件の項目は 7 つ: 題名（`title`）・一言で（`headline`）・位置づけ（`context`）・要旨（`summary`）・範囲（`scope`）・リポジトリ（`repo`）・前に済ませる区切り（`depends_on`。一覧の中の番号の並び）。
- [ ] 区切りの題名は、空白だけでなく 200 文字以内。
- [ ] 区切りの一言でと位置づけは、分類の判断点の出力と同じ検査（`CheckHeadline`・`CheckContext`）を通る。
- [ ] 区切りの要旨は、空白だけでなく 2000 文字以内。
- [ ] 区切りの範囲は、空白だけでなく 2000 文字以内。
- [ ] 区切りのリポジトリは、区画「リポジトリ」に並ぶ名前のどれか。区切りのリポジトリは、案の表示（問いの文・証跡・画面）に使う（S3b で、その区切りの課題の計画を作る判断点の既定のリポジトリにも使う）。
- [ ] 区切りの `depends_on` の番号は、1 から始まる一覧の番号で、その区切りより前の番号だけ（自分と後ろの番号は不正。これで輪はできない）。重ねた番号は不正。
- [ ] 判定が `split` でも `single` でも、分ける・分けない理由（`reason`。空白だけでなく 2000 文字以内）を必須にする。
- [ ] 判定が `split` でも `single` でも、調べた根拠（`evidence`）を 1 件以上必須にする。根拠 1 件は、場所（`path`。ワークスペースからの相対のパス）と手がかり（`note`）。
- [ ] 根拠の場所は、絶対パスと `..` を含むものが不正。core は、根拠の場所のファイルを読まない（証跡に書き写すだけ）。
- [ ] 判定が `single` の出力は、`slices` を空か `null` にする（区切りを書くと不正）。
- [ ] 検査に落ちた出力は、いまの判断点と同じに、実行の結果を `invalid_output` に書き換える。記録は `pending` のまま残し、次の回りで呼び直す。
- [ ] 区切りを分ける判断点の連続失敗は、いまの判断点（分類・計画・完了の検証）の連続失敗の上限の扱いに入れる（上限に達したら、止まり方「判断点の連続失敗」の保留を作る）。
- [ ] 1 回の呼び出しの上限額は、エージェントの宣言の判断点ごとの上限額（`judgment_budget_usd`）に `J10` を足して決める。既定は 3 USD。
- [ ] 費用は、いまの判断点の枠（`judgment`）のまま数え、サイクルの費用にも数える。
- [ ] 判断の間に、課題が分類済でなくなったか、記録が `pending` でなくなったときは、出力を捨て、記録も課題も変えない。
- [ ] 判断点の実行は、いまの判断点と同じく、起動したときの課題の版を実行の記録（`run.challenge_version`）に持つ。出力を写す直前に読み直した課題の版が、実行の記録の版と違うとき（実行の間に `flywheel edit` か取り込みの追従で課題が変わった）は、出力を捨て、記録も課題も変えない（分類の判断点の写しと同じ照合）。記録は `pending` のまま残り、次の回りで、変わった後の課題で呼び直す。

### 判断の結果の扱い

- [ ] 判定が `single` のとき: 記録を `single` にし、課題は分類済のまま、計画へ進める（オーナーへは問わない）。作業ログ `slice_split_single` を残す（細目 `by` は `judgment`）。
- [ ] 判定が `single` のとき、証跡のファイルは作らない。
- [ ] 判定が `split` のとき: core は、証跡のファイルを書き、記録に案（区切りの一覧と理由）と証跡の場所を書き、保留を作り、記録を `awaiting_owner` にし、課題を人間対応待ちへ進める。
- [ ] 証跡のファイルの場所は、`.flywheel/requirements/split-C-<番号>.md`（ワークスペースから見た相対のパス。課題の番号）。
- [ ] 証跡のファイルの中身は、題名・元の Issue の URL・分ける理由・区切りの一覧（7 つの項目）・調べた根拠（場所と手がかり）。形は「機能全体の設計」の「証跡のファイルの形」。
- [ ] 証跡のファイルを書けなかったときは、保留も記録の変更も行わず、記録を `pending` のまま残す（次の回りで、判断点から呼び直す）。作業ログ `slice_split_evidence_failed` を残す。
- [ ] `.flywheel/.gitignore` の既定の内容に `requirements/` の行を足す。証跡を書く前に、`.flywheel/.gitignore` に `requirements/` の行が無ければ足す。
- [ ] 証跡のファイルを書く前に、書く先を確かめる（`internal/core/memory_write.go` の索引の書き込み先の検査と、`internal/core/spec_draft_cleanup.go` の下書きを消す守りと同じ流儀）。確かめは 3 つ: ①置き場 `.flywheel/requirements/` のリンクをたどった先が、ワークスペースの実体の `.flywheel/` の下のディレクトリである（置き場が無ければ作る）。②書く先のファイルのリンクをたどった先が、①の置き場の実体の中にある。③書く先が無いか、シンボリックリンクでない通常のファイルである。
- [ ] 確かめのどれかに落ちたら、書かない。証跡のファイルを書けなかったときと同じに扱う（保留を作らず、記録は `pending`、作業ログ `slice_split_evidence_failed` に落ちた確かめを入れる）。
- [ ] 証跡のファイルの書き込みは、書いた後に、記録・保留・課題の遷移・作業ログを 1 つの書き込みで行う。

### オーナーへの問い（分けるかの保留）

- [ ] 保留は、選択肢つきの問いにし、識別の無い回答を断る。
- [ ] 選択肢は 2 つ: `split`（見出し「この案で分ける」）・`single`（見出し「分けずに 1 つの課題で進める」）。
- [ ] 推奨は `split`。問いの文に「推奨: この案で分ける」と書く。
- [ ] 保留は、課題を止める保留にする。戻り先は分類済。
- [ ] 保留の種類は `human`。止まり方は渡さない（スーパーバイザーを呼ばず、はじめからオーナーの回答待ちになる）。
- [ ] 問いの文には、区切りの件数・区切りごとの番号と題名と要旨とリポジトリと前に済ませる区切り・分ける理由・証跡の場所を書く。
- [ ] 問いの文の最後に、案を直したいときの案内を 1 行書く: 「案を直したいときは、この案で分けてから、対話の欄で課題を足す・取り下げる・依存を直してください」。
- [ ] 区切りを分ける記録は、保留の識別（`hold_id`）を持つ。保留が閉じたら空にする。
- [ ] どの保留が区切りを分ける保留かは、記録の `hold_id` で見分ける（保留の表に値を足さない）。
- [ ] 選択肢を選ぶ回答は、CLI・対話の欄・画面のボタンのどれからでもできる（画面のボタンは `split` も `single` も受ける）。
- [ ] 画面のボタンの口（経路 `ui`）の、取り下げを伴う回答を受けない決まりに、区切りを分ける保留の `split` だけを例外として足す（決定 22）。ほかの守り（選択肢だけ・照合の値・経路 `ui` の記録）は、いまのまま掛ける。
- [ ] 回答に添え書き（`--answer <文>`）を付けたときは、保留の回答の文にだけ残す。

### 「この案で分ける」の答え

- [ ] `split` の回答が成立すると、core は 1 つの書き込みで次の 6 つを行う。
- [ ] 1 つ目: 要求の記録を作る。出どころは元の Issue（`issue`）、外部キーと URL は元の課題の取り込み元の対応の値、題名は元の課題の題名、証跡の場所は区切りを分ける記録の証跡の場所、元の課題は取り下げる課題。

## 機能要件（S3b）

この節は S3b の要件。S3a の作りは、ここに書いた点のほかは変えない。S3a の受入基準のうち「`internal/adapters/github` に、GET でない HTTP の方法を使う口が無い」は、S3b の「3 つの口のほかは GET だけ」に置き換える。

### 分けた元の Issue を閉じる

- [ ] 出どころが `issue` の要求の記録が解決したとき、指す課題に完了が 1 件以上あれば、元の Issue を閉じる手続きに入る（記録の閉じる状態を `pending` にし、コメントの印の値〔`marker`。ランダムな 128 ビットの 16 進〕を書く）。
- [ ] S3b の前（S3a の間）に解決した要求の記録は、閉じる手続きに入らない（閉じる状態は `NULL` のまま。S3a の間は、元の Issue を手で閉じる決まりのため）。
- [ ] 指す課題がすべて取り下げのときは、元の Issue にコメントも閉じることもしない（閉じる状態を `not_needed` にする）。
- [ ] 出どころが `chat`・`manual` の記録は、閉じる手続きを持たない（閉じる状態は `NULL`）。
- [ ] 閉じる手続きは、片付けの段が、閉じる状態が `pending` か `commented` の記録ごとに行う。
- [ ] 手続きの 1 つ目: 閉じる状態が `pending` なら、元の Issue のコメントを読み、flywheel が書いた印（記録ごとの印。「機能全体の設計（S3b）」の「元の Issue へのコメントの形」）を持つコメントが無ければ、コメントを書く。書けたら（または既にあれば）閉じる状態を `commented` にする。
- [ ] コメントには、指す課題ごとに、題名・その課題の Issue（課題の取り込み元の対応の URL。無ければ「Issue なし」）・結果（「完了」か「取り下げ」）を 1 行ずつ書く。
- [ ] 手続きの 2 つ目: 閉じる状態が `commented` なら、元の Issue を読み、開いていれば閉じる（閉じた理由は完了）。閉じたか、既に閉じていたら、閉じる状態を `closed` にし、閉じた日時を書く。
- [ ] 作業ログに、コメントを書いたこと（`requirement_issue_commented`）と、閉じたこと（`requirement_issue_closed`）を残す。
- [ ] 手続きの失敗（GitHub への読み書きの失敗・`gh` が無い）は、記録の連続失敗の回数に 1 を足し、失敗の文を記録に残す。成功したら回数を 0 にする。
- [ ] 失敗した記録は、次の回りかサイクルで、また手続きを行う。
- [ ] 連続失敗の回数が 3 に達したら、閉じる状態を `stopped` にし、それ以上は自動で行わない。作業ログ `requirement_issue_close_stopped` を残す。
- [ ] 閉じる状態が `stopped` の記録は、`flywheel status` の「あなたを待っているもの」（`needs_human.issue_closes`）に、種類 `requirement`・要求の ID・題名・元の Issue の URL・最後の失敗の文つきで出す。
- [ ] コマンド `flywheel close-issue <RQ-ID か C-ID>` を足す。要求の ID なら分けた元の Issue を、課題の ID なら flywheel が作った課題の Issue を（下の「課題の Issue を閉じる」）、閉じる手続きの対象にする。要求の ID のとき: 閉じる状態が `stopped` か `pending` か `commented` の記録で、連続失敗の回数を 0 にして、その場で手続きを 1 回行う（`stopped` なら、手続きの前の状態へ戻してから行う）。
- [ ] `flywheel close-issue` は、閉じる状態が `closed`・`not_needed`・`NULL` の記録では、検査の誤りにする。
- [ ] `flywheel close-issue` は、本人確認を求めない（`flywheel bind` と同じ扱い。閉じることは、オーナーが分けると答えた時点で決まっている）。

### 課題の Issue を閉じる（決定 22）

- [ ] 取り下げた課題の Issue は、対象にしない。
- [ ] 手続きの 1 つ目: 閉じる状態が `pending` なら、Issue を読み、閉じていれば（委譲先の PR の `Closes` で閉じた）コメントを書かずに閉じる状態を `closed` にする。
- [ ] 開いていれば、Issue のコメントを読み、flywheel が書いた印（記録の印の値。「機能全体の設計（S3b）」の「課題の Issue へのコメントの形」）を持つコメントが無ければ、コメントを書く。書けたら（または既にあれば）閉じる状態を `commented` にする。
- [ ] コメントには、どの PR で済んだかを書く: 課題の反映の不可逆操作（`release`）のうち実行済みのものの参照（PR の URL）を 1 行ずつ。1 件も無ければ「PR なし」と書く。
- [ ] 手続きの 2 つ目: 閉じる状態が `commented` なら、Issue を読み、開いていれば閉じる（閉じた理由は完了）。閉じたか、既に閉じていたら、閉じる状態を `closed` にし、閉じた日時を書く。
- [ ] 作業ログに、コメントを書いたこと（`challenge_issue_commented`）と、閉じたこと（`challenge_issue_closed`）を残す。
- [ ] 手続きの失敗・連続失敗の回数・3 回で `stopped`（作業ログ `challenge_issue_close_stopped`）・`needs_human.issue_closes`（種類 `challenge`・課題の ID・題名・Issue の URL・最後の失敗の文）・`flywheel close-issue <C-ID>` での再試行は、分けた元の Issue を閉じる手続きと同じ決まりにする（回数と失敗の文は、課題の Issue の記録の閉じる手続きの欄に持つ）。
- [ ] 課題の Issue の記録の閉じる状態は、作る手続きの状態（`creating`・`created`・`skipped`・`stopped`）と別の欄に持つ。

### 課題の Issue を作る

- [ ] core が課題の Issue の手続きを行うのは、次の 3 つをすべて満たす課題だけ: 着手中・承認済みの計画が Issue を作るリポジトリ（`issue_repo`）を持つ・課題の Issue の記録（`challenge_issue`）が無いか、作った（`created`）・作らない（`skipped`）・止めた（`stopped`）のどれでもない。
- [ ] 作るのは、サイクルの委譲の段で、その課題の最初の委譲を始める前。Issue ができるか、作らないと決まる（`skipped`）まで、その課題の委譲を始めない。
- [ ] 作る先の GitHub の上の名前は、委譲先の宣言のリポジトリのうち、名前が `issue_repo` のものの `remote`。
- [ ] 手続きの最初に、課題の Issue の記録が無ければ、状態 `creating` で作り、承認済みの計画の `issue_repo` と、課題ごとの印の値（ランダムな 128 ビットの 16 進）を書く。作る先の `remote` と担当者は、記録を作った後に解決する。
- [ ] 作る先の `remote` を解決できたら、記録に書く。解決できない（`issue_repo` の名前が委譲先の宣言に無い）ときは、記録の `remote` を `NULL` のままにして、作る手続きの失敗として数える。
- [ ] GitHub を呼ぶのは、記録の書き込みを 1 回終えた後。
- [ ] 記録が `creating` で、承認済みの計画の `issue_repo` が記録の `repo` と違うとき（計画を作り直して承認し直した）、手続きの前に、記録の `repo` を新しい値に、`remote` を解決し直した値に書き換え、連続失敗の回数を 0 にする（計画の承認で見せた作る先と、実際の作る先をそろえる）。
- [ ] 記録が `creating` のまま残っていたら（前の回で途中で落ちた）、作る前に、作る先の Issue のうち、記録を作った日時（から 1 分前）より後に更新されたものを、開いている・閉じているを問わず読み（下の「GitHub に書く口」の読み取りの口）、本文に同じ印を持つ Issue を探す。
- [ ] 同じ印の Issue が開いていれば、新しく作らずにその Issue で対応を作る。
- [ ] 同じ印の Issue が閉じていれば、新しく作らず、対応も作らず、作る手続きの失敗として数える（失敗の文は「印の Issue が閉じている: <URL>」）。3 回で保留に上げ、オーナーが開き直して「もう一度作る」か、「Issue を作らずに進める」を選ぶ。
- [ ] 題名は、課題の題名。
- [ ] 本文は、「機能全体の設計（S3b）」の「課題の Issue の本文の形」のとおり（要旨・範囲・元の Issue へのリンク〔要求の出どころが `issue` のときだけ〕・flywheel が作った印）。
- [ ] ラベルは付けない。
- [ ] 担当者は 1 人付ける。作る先のリポジトリを `repos` に持つ取り込み元（`sources.json` の `github-issue`）の `self_assignees` の最初の値。`self_assignees` を省いた取り込み元なら、認証しているアカウント（`CurrentLogin`）。
- [ ] Issue ができたら、1 つの書き込みで、取り込み元の対応を作り（取り込み元は上の取り込み元、外部キー・URL は作った Issue の値、上流の状態 `open`・ポリシーの状態 `in_policy`）、記録を `created` にし、記録に外部キーを書き、課題の版を 1 上げ、作業ログ `challenge_issue_created` を残す。
- [ ] 作った対応の fingerprint は、作った Issue の本文から、取り込みと同じ規則（`Fingerprint`）で作る（次の取り込みが、課題の説明を Issue の本文で置き換えない）。
- [ ] 対応ができた後は、いまの規則のまま、計画のタスクが 1 個の課題では委譲先へ取り込み元として渡る（PR の `Closes`）。
- [ ] 手続きの最初に、課題が取り込み元の対応を持っていたら（オーナーが計画の承認の後に `flywheel bind` で紐づけた）、Issue を作らずに、記録を `skipped` にする（記録が無ければ `skipped` で作り、`creating` なら `skipped` に変える）。その回りで委譲へ進む。
- [ ] 作る手続きの失敗（GitHub への読み書きの失敗・`gh` が無い・担当者を決められない・作る先が宣言に無い）は、記録の連続失敗の回数に 1 を足し、失敗の文を残す。記録は `creating` のまま。
- [ ] 失敗したときは、その回りでは委譲を始めず、「着手しなかった」に理由 `challenge_issue_failed` で出す。次の回りかサイクルで、また作る。
- [ ] 連続失敗の回数が 3 に達したら、記録を `stopped` にし、保留を作る。
- [ ] 課題の Issue の保留は、選択肢つきの問いにする。選択肢は 2 つ: `retry`（見出し「もう一度作る」）・`skip`（見出し「Issue を作らずに進める」）。
- [ ] 課題の Issue の保留は、課題を止める保留にする。戻り先は着手中。止まり方は渡さない。
- [ ] 課題の Issue の保留の問いの文には、作る先・失敗の回数・最後の失敗の文を書く。
- [ ] 課題の Issue の記録は、保留の識別（`hold_id`）を持つ。どの保留かは、それで見分ける。
- [ ] 記録が `stopped` のあいだに計画を作り直したときの作る先は、`retry` の回答で `creating` へ戻った後の手続きで、上の書き換えの決まりに従ってそろえる。
- [ ] `retry` の回答が成立すると、記録を `creating` に戻し、連続失敗の回数を 0 にし、課題を着手中へ戻す。
- [ ] `skip` の回答が成立すると、記録を `skipped` にし、課題を着手中へ戻す。その課題は、Issue なしで委譲へ進む。
- [ ] 課題の Issue の保留の選択肢は、画面のボタンでも受ける。
- [ ] 取り下げた課題・担当外と分類した課題には、Issue を作らない（計画の承認を経ないので、上の条件に当たらない）。

### GitHub に書く口（adapter）

- [ ] core に、GitHub の Issue へ書く IF（`UpstreamIssueWriter`）を足す。口は 3 つ: Issue を作る（題名・本文・担当者を渡し、作った Issue を返す）・Issue にコメントを書く・Issue を閉じる（閉じた理由は完了）。

## 非機能要件

この節は S3a の分。S3b の分は、下の「非機能要件（S3b）」に置く。

- GitHub への書き込み: S3a は GitHub に書かない（adapter の口も足さない）。分けた区切りの課題に Issue は作らず、元の Issue は閉じない（オーナーが手で閉じる）。

- セキュリティ（区切りを分ける判断点）: 信頼できない文（Issue の本文）を読んで案を作る。道具は読み取りだけで、案は core の検査（件数・長さ・リポジトリの名前・依存の番号）を通ったものだけを使う。根拠の場所のファイルは core が読まない。案から課題を作るのは、オーナーが答えた後だけ。
- セキュリティ（画面のボタン）: 「この案で分ける」はボタンで受ける。元の課題の取り下げを伴うが、作るのは分類済の課題だけで、計画も GitHub への書き込みも、その後のオーナーの承認を経る。いまの画面のボタンの守り（選択肢だけ・照合の値・経路 `ui` の記録）は変えない。
- 費用: 区切りを分ける判断点は、区切り 1 つに収まらないと見た課題 1 件につき 1 回（失敗の呼び直しを除く）。分けないと答えた場合も、その 1 回分は掛かる（決定 21）。分類の判断点・計画を作る判断点の 1 回の費用は、指示文の差分の分だけ変わる。
- 後方互換: S3a より前に分類した課題は、そのまま進む（区切りを分ける記録を作らない）。ストアの版は 44 から 45 へ上げ、既存の課題の `requirement_id` は `NULL` にする。

## 非機能要件（S3b）

- セキュリティ（GitHub への書き込み）: 書き込みは外部送信で、取り消せない。書く範囲は 4 つ（課題の Issue の作成・課題の Issue へのコメントと閉じる・分けた元の Issue へのコメント・閉じる）に限り、adapter の口も 3 つ（作る・コメント・閉じる）だけにする。課題の Issue の作成は、オーナーが計画の承認で作る先を見て認めた後にだけ行う。課題の Issue を閉じるのは、flywheel が作った Issue の課題が完了したときだけ。元の Issue へのコメントと閉じることは、オーナーが「この案で分ける」と答えた要求にだけ行う。本文に入れるのは、課題の題名・説明・達成条件・元の Issue の URL・課題の ID と印だけで、ワークスペースのファイルの中身や秘密は入れない。
- 不可逆操作の境界: S3b の 5 つの書き込みは、不可逆操作（`external_send`）にしない（クリティカル設計決定（S3b）の「GitHub への 5 つの書き込みを、不可逆操作にしない」）。画面のボタンで受けた計画の承認・「この案で分ける」の答えの後にも起きる。
- 後方互換: S3b より前に承認した計画（`issue_repo` を持たない）の課題には、Issue を作らない。S3a の間に解決した要求の元の Issue は閉じない。ストアの版は 45 から 46 へ上げる。`sources.json` が無いワークスペースでは、Issue を作れるリポジトリが無いので、課題の Issue を作らない。
- 運用: 課題の Issue の作成と、Issue を閉じる手続きは、失敗しても、ほかの課題を止めない（失敗した課題・記録だけが待つ）。

## 技術的な制約・方針

この節は S3a の分。

- 区切りを分ける判断点は、いまの判断点の呼び出しの口（`JudgmentInvoker`）と出力の検査の流れ（実行の記録 → 出力の検査 → 写し）に乗せる。新しい起動の形は足さない。
- 証跡のファイルは、ワークスペースの Git に入れない置き場（`.flywheel/requirements/`）に置く。`flywheel init` が書く `.flywheel/.gitignore` の既定の内容（`internal/core/store.go` の `gitignoreContents`）に `requirements/` の行を足し、証跡を書く前に、行が無ければ足す（作業ツリーの置き場の `worktrees/` の行と同じ扱い）。
- 課題の依存は、いまの表（`challenge_dependency`）と検査（輪を作らない）を使う。課題の親子（`challenge_parent`）は使わない。
- 取り下げは、いまの取り下げの書き込み（前提の検査・保留の閉じ方・不可逆操作の差し戻し）を、`split` の回答の書き込みの中から呼ぶ。

## 技術的な制約・方針（S3b）

- core は GitHub を直接呼ばず、IF（`UpstreamIssueWriter`）を通す。`internal/core` は `internal/adapters` を import しない（いまの依存の検査のまま）。
- GitHub への書き込みは、ストアの書き込みのトランザクションの外で行う。順は「記録を書く（書き込み 1）→ GitHub を呼ぶ → 結果を書く（書き込み 2）」で、書き込み 1 と 2 の間で落ちても、次の回が印で同じ Issue・同じコメントを見つけて重ねない。
- 課題の Issue の印は、作る先の Issue のうち記録を作った日時（から 1 分前）より後に更新されたものから、閉じた Issue も含めて探す。作った Issue は必ずその日時より後に作られ・更新されるので、作った直後に閉じられても見つかる。読む量は、その間に更新された Issue の数に比例し、リポジトリの Issue の総数には比例しない。
- 作った課題の Issue は、担当者が自分なので取り込みの方針に合う。GitHub で作れた後、ストアへ書く前に落ちると、その Issue が「取り込めるもの」に出る。オーナーがそこで `flywheel ingest` で取り込むと、別の課題ができうる（取り込みは自動で課題を作らないので、オーナーの操作が無ければ起きない）。この残る危うさは受け入れる。次の手続きは、印の Issue がほかの課題に対応していたら、手続きの失敗として数え、3 回で保留に上げる（オーナーが重なりを片付ける）。

## クリティカル設計決定

この節は S3a の分。S3b の分は、下の「クリティカル設計決定（S3b）」に置く。

### 分け方を調べる所: 読み取りだけの判断点を 1 つ足す（オーナーの決定 2026-11-27。決定 21）

- **採用案**: 分類の判断点（J1）は「区切り 1 つに収まるか」の真偽だけを返す。収まらないと見た課題は、区切りを分ける判断点（J10）が、ワークスペースを作業ディレクトリにして、元の Issue とリポジトリの文書・コードを読み取りで調べ、案を返す。core は案を推奨にして、オーナーへ 1 回だけ問う。
- **理由**: オーナーが案を見て決められ、往復が 1 回で済む（決定 21）。分類の判断点に調べさせると、すべての課題の分類が重くなる（多くの Issue は課題 1 つ）。判断点は書き込めないので、証跡は core が出力から書く。
- **代替案**: ①分けると決まってから調べる（決定 12 の当初の順）。問いが 2 回になるので採らない。②チャットの欄で調べる。オーナーが画面の前にいないと進まないので採らない（チャットの欄の口は、案を直す道として残す）。③フローにする。判断点は読み取りで足り、批評と直しの往復は要らないので採らない。
- **ID**: `J10`。`J7`（日々の要約。作らない）と `J9`（同時に進めてよいか。外した）は、過去に別の役割で使った番号なので使わない。

### 最初にできた課題は取り下げて置き換える（オーナーの決定 2026-11-27。決定 21）

- **採用案**: `split` の回答の書き込みで、元の課題を取り下げ、区切りごとに新しい課題を作る。元の課題の取り込み元の対応は残す。
- **理由**: 元の課題を最初の区切りとして使い続けると、最初の区切りの PR の `Closes` で、元の Issue が早く閉じる（決定 21）。対応を残すと、同じ Issue は「取り込めるもの」に戻らない。
- **代替案**: 元の課題を最初の区切りにする。上の理由で採らない。

### 区切りの課題は分類済から始める

- **採用案**: 作る課題は分類済から始め、優先度・緊急度・起票者は元の課題から写し、一言でと位置づけは区切りを分ける判断点が書く。
- **理由**: 分類の判断点を二度通さない（担当かは元の課題で決まっている）。二度通すと、区切りの課題をさらに分けると判定しうる。
- **代替案**: 未分類から始める。判断点の呼び出しが区切りの数だけ増え、分け直しの輪を止める決まりが要るので採らない。

### 要求の記録: 軽い表を 1 つ足し、課題が指す（オーナーの決定 2026-11-27。決定 21）

- **採用案**: 表 `requirement` を足す。出どころ（元の Issue かチャットの欄の会話）・証跡の場所・作成と解決の日時を持つ（S3b で、元の Issue を閉じる手続きの欄を足す）。課題に `requirement_id` を足す。委譲・問い・承認はひも付けない。
- **理由**: チャットの欄からの要求には元の課題が無いので、取り下げた元の課題を印に使えない（決定 21）。解決（証跡を消す・元の Issue を閉じる）の判定も、この記録で行える。
- **代替案**: ①取り下げた元の課題を印にする。上の理由で採らない。②要求を記録の単位として重く持ち、委譲・問いをひも付ける（決定 12 で採らなかった形）。
- **出どころ `manual`**: 決定 21 は出どころを「元の Issue か、チャットの欄の会話」とした。ターミナルの対話のセッション（オーケストレーター）からもコマンドで作れるよう、印の無いときの値 `manual` を足す（作りと扱いは `chat` と同じで、会話を持たないだけ）。


### 「この案で分ける」は画面のボタンでも受ける（オーナーの決定 2026-11-27。決定 22）

- **採用案**: 画面のボタンの口（経路 `ui`）で、区切りを分ける保留の `split` を受ける。取り下げを伴う回答をボタンで受けない決まり（設計書 §9）の、この答えだけの例外にする。
- **理由**: できるのは、元の課題の取り下げと分類済の課題を作ることだけで、計画と GitHub への書き込みは、その後の計画の承認を経る。オーナーが推奨のまま 1 回で進められる。
- **受け入れる危険**: 同じマシンのプロセス（委譲の子を含む）が、画面の HTML から CSRF の値を取って `split` を選べる。いまの守り（選択肢だけ・照合の値・経路 `ui` の記録）は掛ける。
- **代替案**: ボタンでは受けず、対話の欄かコマンドだけで受ける。推奨のまま進めるのに対話が要り、往復が増えるので採らない。

### DB スキーマ: ストアの版 45

- **採用案**: マイグレーション `0045_requirement.sql` で、表 `requirement`・`slice_split` を足し、`challenge` に `requirement_id`（`REFERENCES requirement(id)`・`NULL` 可）を足す。値の閉集合（状態・出どころ）は core の定数で検査し、CHECK 制約は付けない（いまの流儀）。
- **理由**: 区切りを分ける記録は、下書きづくりの記録（`spec_draft`）と同じく、課題ごとに高々 1 件で、保留の識別を持つ。要求の記録は課題をまたぐので別の表にする。
- **代替案**: 区切りを分ける状態を要求の記録に持たせる。分けないと答えた課題にも要求の記録が残り、「要求から生まれた課題」の数え方が崩れるので採らない。

### 指示文の分量

- **採用案**: 分類の判断点の上限を、4,096 バイトから足した節の分だけ上げる（5,120 バイトを超えない）。区切りを分ける判断点は 6,144 バイト。対話の欄は、足した節の分だけ上げる（6,656 バイトを超えない）。
- **理由**: これまでの決まり（足した文の分だけ上げる）。

## クリティカル設計決定（S3b）

### 元の Issue を閉じる時と、閉じない場合

- **採用案**: 要求を指す課題がすべて終端になったら、完了が 1 件以上あるときだけ、コメント（課題ごとの題名・Issue・結果）を書いてから閉じる。すべて取り下げなら、コメントも閉じることもしない。
- **理由**: 決定 21（区切りの課題がすべて解決したら閉じる）。すべて取り下げたときに「済んだ」と閉じると、事実と違う記録が GitHub に残る。その Issue をどうするかは、オーナーが決める。
- **代替案**: すべて取り下げでも閉じる（閉じた理由を「予定どおりに進めない」にする）。オーナーの判断を先取りするので採らない。

### 閉じる手続きの失敗: 保留でなく、「あなたを待っているもの」に出す（オーケストレーターの案から変えた）

- **採用案**: 連続 3 回の失敗で自動の手続きを止め、`flywheel status` の `needs_human.issue_closes` と画面の「いま進められること」に出す。再試行は `flywheel close-issue`。
- **理由**: 保留は課題に付き、課題を人間対応待ちへ進める。閉じる手続きの時点では、要求を指す課題も元の課題もすべて終端なので、保留を付けられる課題が無い。
- **代替案**: 最後に終端になった課題に保留を付ける。終端の課題を人間対応待ちへ戻す遷移が要り、状態機械を広げるので採らない。

### 課題の Issue を作る時と所（オーナーの決定 2026-11-27。決定 21）

- **採用案**: 計画を作る判断点が `issue_repo` を書き、オーナーが計画の承認で認める。承認の後、サイクルの委譲の段で、最初の委譲の前に core が作り、取り込み元の対応にする。
- **理由**: 課題を作った時点で作ると、後で取り下げた・担当外だった課題の Issue が残る（決定 21）。対応にすると、取り込みの追従と、委譲先の PR の `Closes` が、いまの作りのまま効く。
- **代替案**: 計画の承認の書き込みの中で作る。承認は画面・CLI・対話の欄のどこからでも来て、GitHub の呼び出しを書き込みの中に入れられないので採らない。

### 二重に作らない・二重にコメントしない: 記録の印を Issue の本文とコメントに入れる

- **採用案**: 作る前に、課題ごとのランダムな印の値を記録へ書く。本文に印を入れて作る。記録が `creating` のまま残っていたら、作る先の Issue のうち記録を作った日時より後に更新されたもの（閉じた Issue を含む）の本文から同じ印を探す。元の Issue へのコメントと、課題の Issue を閉じるときのコメントも、記録ごとの印をコメントに入れ、書く前にコメントを読んで探す。
- **理由**: GitHub の呼び出しとストアの書き込みを 1 つにできない。印の値は、ワークスペースをまたいでも重ならない（課題の ID はワークスペースごとに重なる）。
- **代替案**: 題名で探す。同じ題名の Issue がありうるので採らない。

### 課題の Issue の担当者: 取り込み元の自分の担当者を付ける

- **採用案**: 作る先を `repos` に持つ取り込み元の `self_assignees` の最初の値（省いた取り込み元は認証しているアカウント）を担当者にする。
- **理由**: 取り込み元の方針（`assignee_policy`）が `self-only` のとき、担当者の無い Issue は方針の外（`out_of_policy`）になり、課題が自動の対象から外れる。`exclude-others` でも、自分を付けた Issue は方針に合う。
- **代替案**: 担当者を付けない。上の理由で採らない。

### 作る先を、取り込み元の宣言にあるリポジトリに限る

- **採用案**: Issue を作れるのは、委譲先の宣言のリポジトリのうち、`remote` がどれかの取り込み元の `repos` にあるものだけ。
- **理由**: 取り込み元の宣言に無いリポジトリの Issue は、取り込みが追従せず（閉じたこと・方針を読まない）、`flywheel bind` と同じ決まり（宣言に無いリポジトリの Issue に紐づけない）にも合わない。


### flywheel が作った課題の Issue を、完了で閉じる（オーナーの決定 2026-11-27。決定 22）

- **採用案**: 課題が完了したとき、flywheel が作った課題の Issue が開いていれば、片付けの段で、どの PR で済んだか（課題の反映の実行済みの不可逆操作の PR）をコメントしてから閉じる。既に閉じていれば（委譲先の PR の `Closes` で閉じた）、何も書かない。取り込んだ Issue は対象外。
- **理由**: 計画のタスクが 2 個以上の課題（統合ブランチを使う計画を含む）では、委譲先の PR に課題の Issue の `Closes` が付かず、閉じる役が無い。取り込んだ Issue は、いまの作り（委譲先の PR）のまま。
- **代替案**: ①開いたまま残し、オーナーが閉じる。閉じ忘れが残るので採らない。②統合ブランチの PR の本文に `Closes` を足す。統合ブランチを使わない複数タスクの計画に効かないので採らない。

### GitHub への 5 つの書き込みを、不可逆操作（`external_send`）にしない（オーナーの決定 21・22 から）

- **採用案**: S3b の GitHub への書き込み 5 つ（課題の Issue を作る・課題の Issue へのコメント・課題の Issue を閉じる・分けた元の Issue へのコメント・分けた元の Issue を閉じる）は、不可逆操作（`operation`。とくに外部送信 `external_send`）として記録も承認もしない。core が、上の決まりのとおりに行う。
- **理由**: ①開き直せる（閉じた Issue は開き直せ、作った Issue とコメントは消せる・直せる。マージや削除と違い、本番の中身を変えない）。②オーナーの承認か課題の完了に付く（作るのは計画の承認の後、元の Issue を閉じるのは「この案で分ける」の答えの後、課題の Issue を閉じるのは完了の承認の後）。③中身が決まった形（題名・本文・コメントは、課題・要求の記録から core が組み立てる。LLM の自由な文を送らない）。決定 21・22 は「計画の承認で作る先を見て認める」「全部済んだら flywheel が閉じる」「作った Issue は完了で閉じる」で、1 件ずつの承認を求めていない。
- **画面のボタンとの関係**: 計画の承認と「この案で分ける」は、画面のボタン（経路 `ui`）でも受ける。そのため、この 5 つの書き込みは、画面のボタンで受けた承認・回答の後にも起きる。設計書の D18（本番に届く承認〔`external_send` を含む〕は端末か対話に限る）は、不可逆操作の承認の決まりで、この 5 つは不可逆操作にしないので当たらない。この関係を設計書に書く。
- **代替案**: 5 つを `external_send` の不可逆操作にし、端末か対話で 1 件ずつ承認する。オーナーの決定（計画の承認と split の答えで足りる）と合わず、Issue が増えるたびに承認が増えるので採らない。

### DB スキーマ: ストアの版 46

- **採用案**: マイグレーション `0046_challenge_issue.sql` で、表 `challenge_issue` を足し、表 `requirement` に閉じる手続きの欄（`marker`・`close_state`・`close_state_before_stop`・`close_failures`・`close_error`・`closed_at`）を足す。既存の要求の記録の閉じる状態は `NULL`（S3a の間に解決した要求は閉じない）。
- **理由**: 課題の Issue の記録は課題ごとに高々 1 件で、保留の識別を持つ（区切りを分ける記録と同じ形）。

### 指示文の分量（S3b）

- **採用案**: 計画を作る判断点の上限は、直した後の本文に余白 300 バイトを足した値（削った分だけ下がる）。
- **理由**: これまでの決まり（本文に余白 300 バイト）。削る項は、S3 で削ると決まっていた（オーナーの決定 2026-11-26。`docs/features/request-to-plan.md` の指示文の分量の節）。決定 22 で、削るのを S3b にした。

## 機能全体の設計

この節は S3a の分。S3b の分は、下の「機能全体の設計（S3b）」に置く。

### 流れ

```text
取り込み（いまのまま）→ 未分類の課題
  → 分類の判断点（J1）: 担当・区切り 1 つに収まるか
       収まる・取り込み以外・子を持つ → 分類済 → 計画へ（いまのまま）
       収まらない → 分類済＋区切りを分ける記録（pending）
  → 区切りを分ける判断点（J10）
       single → 記録 single → 計画へ
       split  → 証跡を書く → 保留（split / single）・記録 awaiting_owner・人間対応待ち
  → オーナーの回答（CLI・対話の欄・画面のボタン）
       single → 記録 single・分類済へ戻す → 計画へ・証跡を消す

  → 区切りの課題ごとに: 計画 → 承認 → 委譲（いまのまま。課題の Issue は無い）

  （元の Issue は、オーナーが手で閉じる）
```

## やらないこと

S3a でやらないこと。

- GitHub への書き込みすべて（理由: S3b の範囲。決定 22）
- S3a の間に、分けた元の Issue を flywheel が閉じること（理由: S3a の間は、オーナーが手で閉じる。決定 22）

- 区切りの案を、保留の回答の中で直す口（理由: 分けた後に対話の欄で課題を調整する。決定 12 の「仕組みは足さない」）
- 区切りの課題を、さらに区切りを分ける判断点にかけること（理由: 分類の判断点を通さないため、輪にしない）
- 取り込み以外の出どころの課題（チャットの欄・手・フォローアップ・改修）を、区切りを分ける判断点にかけること（理由: 決定 21 は取り込んだ Issue の仕分け。チャットの欄からは、要求の記録を作る口で分ける）
- 取り込み元の子を持つ課題を、区切りを分ける判断点にかけること（理由: 子はタスクの初期値で、分解は計画を作る判断点が行う）
- 指す課題が 0 件の要求の記録の自動の後片付け（理由: チャットの欄で作りかけの要求を、勝手に消さないため）
- 要求の記録の削除・取り下げの口（理由: 課題の指し先として残す）
- `flywheel edit` で課題の要求を付け替える口（理由: 分け直しは課題を作る・取り下げることで足りる）
- 要求の一覧のコマンド・画面（理由: 課題の詳細から同じ要求の課題を辿れる。見た目の作り込みは後の区切り）
- 区切りを分ける判断点の出力のうち、根拠の場所のファイルが在るかを core が確かめること（理由: 証跡に書き写すだけで、根拠として数える検査に使わない）

## やらないこと（S3b）

- 元の Issue の sub issue として区切りの Issue を作ること（理由: 取り込みで sub issue はタスクと読むため。設計書の D22。決定 21）
- タスクの Issue を作ること（理由: 分解の正本は計画のタスク。決定 12）
- 課題の Issue へのラベルの付与（理由: ラベルの意味が取り込み元ごとに違い、緊急度のラベルの写しを逆向きに持つことになるため）

- すべて取り下げになった要求の元の Issue を、flywheel が閉じること（理由: 上の「元の Issue を閉じる時と、閉じない場合」）
- 閉じる手続きの失敗を保留にすること（理由: 保留を付けられる終端でない課題が無い）
- 取り下げた課題の、flywheel が作った課題の Issue を閉じること（理由: 決定 22 は課題が完了したときだけ）

### 要人間判定（オーケストレーターが、試し用のワークスペースと試し用のリポジトリで、実物の実行エンジンと GitHub で行う）

- [ ] 計画を承認してサイクルを回すと、試し用のリポジトリに課題の Issue が 1 件できる。
- [ ] その Issue の本文が「課題の Issue の本文の形」のとおりで、印の行が GitHub の画面に出ない。
- [ ] その Issue の担当者が、取り込み元の `self_assignees` の最初の値である。
- [ ] 次の取り込みの後、課題の説明が変わらない。
- [ ] 区切りの課題をすべて完了にすると、元の Issue にコメントが 1 件書かれて閉じる。
