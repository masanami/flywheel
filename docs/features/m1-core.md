## 概要

flywheel の core を、LLM を一切使わない最小の形で作る。SQLite のストアに課題を持ち、状態機械が遷移を検証し、承認は人間の直接操作だけが成立させ、すべての変更を作業ログに残す。入口は CLI だけで、**CLI だけで課題を起票し、承認し、状態を完了まで進められる**ことを完了の目安とする（設計書 §17）。

## 背景・目的

- 設計書 §1.1 の課題 1（Claude を要しない処理まで Claude が実行している）を解く土台である。M2〜M4 の取り込み adapter・invoker・UI は、いずれもここで作る core を通して状態を変える（設計書 §3 P2）。
- 状態機械と承認は、後から変えると手戻りが大きい。そのため M1 の着手前に次の 2 点が決まっている:
  - **完了の承認と本番反映の承認は 1 回の操作で両方を承認し、作業ログには別々に残す**（D12【決定 2026-09-21】）
  - **承認は、経路（channel）と本人確認の方式を後から足せる作りにする**（D15 からの入力【決定 2026-09-21】。M4 でモバイルからの経路を足すときに作り直さない）
- 現行の bash / ruby スクリプトのテストが固定している振る舞い（冪等性・fail-closed・語彙の一致）は、移植先の要件として引き継ぐ（設計書 §15。対応は §現行から引き継ぐ振る舞い）。

## ユーザーストーリー

- **オーナー（人間）**として、端末の CLI だけで課題を起票し、状態を進め、計画と完了を承認したい。承認が Claude に代行されないことを信頼したい。
- **対話セッションの Claude**（将来の薄いスキル）として、CLI の JSON 出力と終了コードで状態を読み、承認以外の操作を行いたい。承認は案内だけする（設計書 §9）。
- **M2 以降の開発者**（adapter・invoker・server の実装者）として、core の API だけを通して状態を変えたい。ストアを直接開けない構造であってほしい。

## 機能要件

用語: **課題**＝設計書 §6 の `challenge`。**不可逆操作**＝FR-22 の承認対象になる操作。種類は `release`（本番反映＝既定ブランチへの昇格マージ・本番デプロイ）・`delete`（削除）・`external_send`（外部送信）・`other` の閉集合。**本人確認つきの操作**＝承認・差し戻し・保留への回答（§クリティカル設計決定 1）。

### ワークスペースとストア

- [ ] `flywheel init` は、`--workspace <dir>` → 環境変数 `FLYWHEEL_WORKSPACE` → カレントディレクトリの順で対象のディレクトリを決め、そこに `.flywheel/flywheel.db` を作る。親ディレクトリへの遡り探索はしない【決定 2026-09-21 PD6（親）】
- [ ] 対象のディレクトリに既にストアがあれば、`init` は何も変えずに成功する（冪等）
- [ ] ストアを Git で追跡させないため（D10）、`init` は `.flywheel/.gitignore` に、ストアとその付随ファイル（`-wal`・`-shm`）を除外する行を置く【仮定】
- [ ] `init` 以外のコマンドは、`--workspace <dir>` → 環境変数 `FLYWHEEL_WORKSPACE` → カレントディレクトリから親へ遡って最初に見つかる `.flywheel/flywheel.db` の順でワークスペースを決める【仮定】。見つからなくてもストアを作らない（fail-closed）
- [ ] 環境固有のパスをコードへ埋め込まない（D13）
- [ ] ストアのスキーマ版がバイナリの知る版より新しければ、`init` と読み取りを含むすべてのコマンドを `store_too_new` で拒否する（§クリティカル設計決定 2）
- [ ] ストアのスキーマ版がバイナリの知る版より古ければ、開くときに前方のマイグレーションを順に適用する（§クリティカル設計決定 2）

### 課題の起票・参照・編集

- [ ] `create` は課題を状態 `未分類` で作り、ID を返す。ID は `C-<正の整数>` で、ストアの中で作成順に単調増加する【仮定】
- [ ] `create` は起票者（`reporter`）に、actor と同じ規則で OS のログインユーザー名を自動で設定する。CLI に起票者を指定するフラグは持たない【仮定】
- [ ] 人間記入欄として、タイトル・説明・完了条件・緊急度を持つ
- [ ] タイトルは必須
- [ ] 緊急度は任意で、`高 | 中 | 低` の閉集合（現行台帳と同じ）
- [ ] `show` は課題の全フィールド・現在の状態・計画（全版）・承認と差し戻しの記録・保留の記録・不可逆操作を示す
- [ ] `list` は課題の一覧を示す。状態で絞り込める
- [ ] `edit` は人間記入欄を変更する。`完了` の課題は変更できない
- [ ] 課題の削除・取り下げは M1 S1 に持たない（§決定事項の記録 H6）

| `in_progress` | 着手中 | 主経路 4 |
| `verifying` | 検証中 | 主経路 5 |

- [ ] `--question` は `verify --result uncertain` と `hold` にだけ指定できる。`--result met`・`not_met` と同時に指定すると `usage_error` で拒否する（fail-closed）【仮定】
- [ ] T10・T11 は問いの文を必須とする。`--question` の省略は空の問いとして扱い、`usage_error` ではなく `validation_failed` にする
- [ ] 人間対応待ちに入ると、問いと入る直前の状態を記録する【決定 2026-09-21 H4（オーナー）】

- [ ] `conflict` は本人確認つきの操作だけが返す。要約を表示した時点の版と、確認後に書き込む時点の版が違うときである（§クリティカル設計決定 2）【決定 2026-09-21 PD7（親）】

### 承認（計画・完了・本番反映）

- [ ] `approve <課題 ID>` は、課題の状態から承認の種類を決める（計画承認待ち→計画の承認、完了確認待ち→完了の承認）
- [ ] 承認・差し戻し・保留への回答は、本人確認つきの操作としてだけ成立する（§クリティカル設計決定 1）
- [ ] 本人確認では、対象の要約を表示してから、**対象の ID の入力**を求める【決定 2026-09-21 H9（オーナー）】
- [ ] 計画の承認の要約は、課題の ID・タイトル・承認の種類と、計画の本文と版を含む
- [ ] 完了の承認の要約は、課題の ID・タイトル・承認の種類と、完了条件・同時に承認される `release`・同時には承認されない不可逆操作の一覧を含む
- [ ] 差し戻しの要約は、対応する承認の要約と同じ内容に、入力された理由を加えたものである【仮定】
- [ ] 保留への回答の要約は、課題の ID・タイトルと、問い・入力された回答を含む【仮定】
- [ ] 不可逆操作の単独の承認・差し戻しの要約は、操作の ID・種類・要約・参照と、課題の ID・タイトル・状態を含む（差し戻しでは入力された理由も含む）【仮定】
- [ ] 要約を表示してから確認が入力されるまでの間に、対象（課題のフィールド・状態・計画の版・その課題の未承認の不可逆操作の集合）が変わっていれば、承認を成立させない
- [ ] 差し戻しは理由を必須とする
- [ ] 不可逆操作の承認と差し戻しは、操作の種類にかかわらず種類「本番反映」として記録し、対象の不可逆操作の ID を添える【決定 2026-09-21 H2・H5（オーナー）】
- [ ] 承認と差し戻しは、種類（計画・完了・本番反映）・決定・actor・経路・本人確認の方式・対象の版・日時・理由を記録する
- [ ] **不可逆操作**を課題に登録できる（`op add`）。種類は `release`（本番反映）・`delete`・`external_send`・`other` の閉集合【仮定】。それ以外は拒否する
- [ ] `op add` の要約は必須、参照（PR の URL など）は任意
- [ ] 不可逆操作の ID は `OP-<正の整数>` で、ストアの中で（課題をまたいで）作成順に単調増加する【仮定】
- [ ] 完了した課題への `op add` は拒否する
- [ ] **完了の承認は、その課題の未承認の `release` を同じ操作で承認する**（D12）
- [ ] 完了の承認と `release` ごとの承認は、別々の記録として残す（D12）
- [ ] 完了の承認は、`release` 以外の未承認の不可逆操作（`delete`・`external_send`・`other`）を承認しない【決定 2026-09-21 A1（オーナー）。`delete`・`external_send`・`other` は個別に承認する】
- [ ] `approve --hold-release` は完了だけを承認し、`release` を未承認のまま残す（D12）
- [ ] `--hold-release` は完了確認待ちの課題への `approve` にだけ指定できる。それ以外（計画承認待ちの課題・不可逆操作の ID）に指定すると `usage_error` で拒否する（fail-closed）【仮定】
- [ ] 未承認の不可逆操作は `approve <OP-ID>` / `reject <OP-ID> --reason` で単独に承認・差し戻しできる。課題が完了した後でも行える（保留した本番反映のため）
- [ ] 承認済みの不可逆操作を**実行する**機能は持たない（M3 以降）。M1 は承認の記録と可視化まで

#### 承認の操作手順（利用者向け）

1. **Claude Code の外の端末**（ターミナルの別のウィンドウやタブ）を開く。
2. 承認は `flywheel approve <ID>`、差し戻しは `flywheel reject <ID> --reason <理由>`、保留への回答は `flywheel answer <ID> --answer <回答>` を実行する。
3. 表示された要約を読み、確認として対象の ID（`C-12`・`OP-3` など）を入力する。

**Claude Code の `!`（シェルモード）や Bash ツールから実行すると、`tty_required` で拒否される**（環境変数 `CLAUDECODE` が設定されるため＝H10。オーナーが承知のうえで決めた帰結）。Claude Code の対話で受けられるのは、承認待ちの一覧と、この手順の案内までである（設計書 §9）。

### 作業ログ

- [ ] 状態・フィールド・計画・承認・保留・不可逆操作を変える操作は、成功するたびに、日時・actor・経路・本人確認の方式・対象・操作・変更前・変更後を持つエントリを作業ログへ記録する
- [ ] 変更と作業ログへの記録は同じトランザクションで行い、片方だけが残ることはない
- [ ] 拒否・失敗した操作と、値が変わらない操作は作業ログを残さない
- [ ] `log [<課題 ID>]` は作業ログを古い順に示す
- [ ] 作業ログを変更・削除する操作は持たない
- [ ] actor は OS のログインユーザー名とする。取得は Go の `os/user.Current()` の `Username` を使い、取得できないとき（`CGO_ENABLED=0` の Linux で、ユーザーが `/etc/passwd` に無い場合など）は環境変数 `USER`、次に `LOGNAME` を使う。どれも得られなければ変更せずに `internal_error` で終わる【仮定】。本人確認のない操作は本人確認の方式を `none` として記録する（誰が実行したかは申告であり、検証していないことを記録から読めるようにする）【仮定】

### 状況の表示

- [ ] `status` は「人間の操作を待っているもの」（計画承認待ち・完了確認待ち・人間対応待ちの課題と、未承認の不可逆操作）と「システムが次に進められるもの」（未分類・分類済・着手中・検証中の課題）と「承認済みの不可逆操作」を分けて示す（設計書 §7・§12.3 の迷い 1〜3 への対応）

### CLI 共通

- [ ] すべてのコマンドが `--json` を持つ。成功時は標準出力に JSON 1 文書、失敗時は標準エラーに `{"error":{"code":"…","message":"…"}}` を出す
- [ ] 終了コードは 3 値に限る（現行スクリプトの規約を引き継ぐ）: `0` 成功／`1` 規則による拒否（要求は理解したが受け付けない。状態は変わらない）／`2` 実行できなかった（使い方の誤り・ストアの不在や破損・入出力の失敗）
- [ ] エラーコードは次の閉集合に限る

| エラーコード | 終了コード | 意味 |
|---|---|---|
| `usage_error` | 2 | 引数・フラグの誤り |
| `store_not_found` | 2 | ストアが見つからない |
| `store_too_new` | 2 | ストアのスキーマ版がバイナリより新しい |
| `store_busy` | 2 | 他のプロセスの書き込みを待つ上限を超えた |
| `store_error` | 2 | ストアを開けない・読めない・書けない |
| `internal_error` | 2 | 想定外の失敗 |
| `not_found` | 1 | 指定した ID が無い |
| `validation_failed` | 1 | 入力が規則に反する（必須値の欠落・閉集合外の値） |
| `invalid_transition` | 1 | 現在の状態から許されない操作 |
| `terminal_state` | 1 | 完了した課題を変えようとした |
| `conflict` | 1 | 本人確認つきの操作で、要約の表示後・確認の書き込みまでの間に対象が変わった |
| `tty_required` | 1 | 本人確認つきの操作を端末なしで実行した |
| `confirmation_mismatch` | 1 | 確認の入力が一致しない、または入力が中断された |
| `verification_rejected` | 1 | 許可していない経路と本人確認の方式の組み合わせ（core の API へ直接要求された場合） |

#### 成功時の JSON 出力の規約【決定 2026-09-21 #5（実装チケットの意思決定者）】

- **包み（envelope）は持たない**。成功は終了コード 0 と標準出力、失敗は非 0 と標準エラーの `error` で判別できるため `ok`・`data` の包みは冗長。最上位は**必ずオブジェクト**（配列・スカラーを最上位にしない）。一覧は複数形の名前つきキーの配列で返す（例 `{"challenges":[…]}`）。単一のエンティティは、そのエンティティ名のキーの下に置く（例 `{"challenge":{…}}`）— 後から付随情報を足しても壊れないようにするため。
- **命名**: キーは snake_case の英字。§データモデルの属性名と同じ名前を使う（`done_criteria`・`created_at` など）。
- **ID**: 表示形の文字列（`"C-12"`・`"OP-3"`）。エンティティ自身の ID は `id`、参照は `<エンティティ>_id`（`challenge_id`・`operation_id`）。内部の整数は出さない。
- **状態**: `status` に語彙のコード（`awaiting_plan_approval`）、`status_label` に表示名（`計画承認待ち`）を**常に両方**出す（H3）。機械はコードだけを読む。
- **閉集合の値**: CLI が入力として受け付ける綴りをそのまま文字列で出す（`priority`: `P0|P1|P2`、`urgency`: `高|中|低`、`kind`・`state`・`decision`・`result` は英字のコード）。緊急度は現行台帳と同じ日本語の値が正であり、別のコードを設けない。
- **未設定と空**: キーは省略しない。未設定の任意値は `null`、空の一覧は `[]`。
- **日時**: RFC 3339・UTC・ミリ秒固定（`2026-09-21T08:30:00.123Z`）。文字列の辞書順が時刻順に一致する。
- **版**: `version` は整数。
- **文字**: UTF-8・非 ASCII をエスケープしない・HTML エスケープしない・末尾に改行 1 つ。
- `--json` なしの出力は人間向けで、形式の安定を保証しない。機械は `--json` を使う。
  - ただし `show` の `--json` なしの出力も、計画の全版の本文と保留への回答を含める（受入基準 17〔`show` が計画の全版・保留の記録を出力する〕と 35〔以前の版の本文も `show` で読める〕はテキスト出力にも適用する【決定 2026-09-23（オーナー）】。#31）。
- 各コマンド固有のフィールドは、この規約に従って後続チケットが追記する。本チケット（#5）が追加した成功出力は無い（スタブのみ。`--help` はテキスト）。
- 以下の小見出しは §IF / API の全コマンドを覆う。小見出しの形（最上位のキーと、`challenge`・`plan`・`approval`・`hold`・`operation`・`activity` の要素のキー）と実際の `--json` の出力の一致は、`internal/cli/jsondoc_test.go` のテストが全コマンドの成功経路で照合する（#15）。形を変えるときは、この節と実装を同じ変更で直す。

`{"activities": [{…}, ...]}`。

| `actor` | string | 実行した OS のログインユーザー名 |

| `action` | string | `create`\|`edit`\|`classify`\|`plan`\|`submit`\|`verify_met`\|`verify_not_met`\|`verify_uncertain`\|`hold`\|`approve`\|`approve_hold_release`\|`reject`\|`answer`\|`op_add`\|`op_approve`\|`op_reject`（`op_add`・`approve_hold_release` は #13 で追加。`op_approve`・`op_reject` は #39 で追加。`op_add` は `entity=operation`（不可逆操作自身の登録）と `entity=challenge`（`op add` が課題の版を1つ上げたことの記録。#39）の両方で使う。`op_approve`・`op_reject` は `entity=challenge` のときだけ（`<OP-ID>` への approve／reject が課題の版を1つ上げたことの記録。#39。`entity=operation` 側の `approve`／`reject`〔不可逆操作自身の承認・差し戻し〕、および `entity=challenge` の `approve`／`reject`〔課題そのものの承認・差し戻し。`approval_kind` を持つ〕と紛れないための別語彙）。`approve_hold_release` は `entity=challenge` のときだけ〔`approve <C-ID> --hold-release`＝T14〕。`approve`・`reject` は `entity=challenge`・`entity=operation` の両方で使う） |
| `before` | object \| null | 変わった項目だけの JSON オブジェクト。`create`、`entity=operation` の `op_add`、`entity=challenge` の `op_add`・`op_approve`・`op_reject`（#39）は常に `null`。**`before` には `version` を載せない**（H7 の「変わった項目」に版も含まれるが、変更前の版は `after` の `version` − 1 として求まるため。S1〔#39〕）。エンティティの既存の項目が未設定から値を得た場合（`classify` の `priority`、`edit` の `urgency`、`plan` の初回〔T3〕の `plan_version`、`answer` の `answer`）は、その項目のキーを `null` で載せる（S3〔#39〕。`priority`・`urgency` は元からこの形、`plan_version`・`answer` は #39 でそろえた）。一方、その操作で新しく作られる記録の内容（保留の `question`、承認の `approval_kind`・`decision`・`target_version`・`reason`、不可逆操作の登録内容）はこの規則の対象外（キー自体を持たない） |
| `after` | object \| null | 変わった項目だけの JSON オブジェクト。`create`・`op_add`（`entity=operation`）以外は常に `version` を含む（`entity=operation` の `version` は不可逆操作自身の版）。状態が変わる遷移では `status`（T4 のように状態が変わらない遷移では含まない）、`classify` は `priority`、`plan` は `plan_version`、保留に入る操作（`verify_uncertain`・`hold`）は `question` を含む、`entity=challenge` の `approve`・`approve_hold_release`・`reject` は `approval_kind`・`decision`・`target_version`（`reject` はさらに `reason`）を含む、`answer` は `answer` を含む、`entity=operation` の `op_add` は `operation_id`・`kind`・`summary`・`ref`・`state` を含む、`entity=operation` の `approve`・`reject` は `state`（`reject` はさらに `reason`）を含む、`entity=challenge` の `op_add`・`op_approve`・`op_reject`（#39）は `version` と、原因になった不可逆操作への参照 `operation_id` を含む |

`log [<C-ID>]` は、`<C-ID>` を指定した場合、その課題自身のエントリ（`entity=challenge`）に加え、その課題が持つ不可逆操作のエントリ（`entity=operation`。`operation.challenge_id` で従属する行）も古い順に含める（#13）。`<C-ID>` を省略した場合は全エンティティを対象にする。

`op add`（`entity=operation` の `op_add`）と `<OP-ID>` への単独の approve／reject（`entity=operation` の `approve`／`reject`）は、同じ操作で対象の課題の版も1つ上げる（親要件チケット #4 §アーキテクチャ決定）。この版の変化を作業ログに残すため、`entity=operation` のエントリと同じトランザクションで `entity=challenge` のエントリ（`action` は順に `op_add`・`op_approve`・`op_reject`）も記録する（S2〔#39〕。これが無いと `log <C-ID>` で課題のエントリの `version` が飛んで見え、仕様冒頭の「すべての変更を作業ログに残す」と食い違う）。一方、D12（完了の承認による release の一括承認）で `entity=operation` に記録される `approve`・`reject` は、その完了の承認自身の `entity=challenge` エントリ（`approve`・`approve_hold_release`・`reject`）が既に版の変化を記録しているため、release ごとの `entity=challenge` エントリは追加しない（二重記録の回避）。

##### `approve`・`reject`（#12 で追加。#13 で `<OP-ID>` を拡張）

`<C-ID>` を対象にした場合: `{"challenge": {…}, "approval": {…}}`。`challenge` は上表と同じ形、`approval` は `show` の `approvals` の要素と同じ形。完了の承認（D12。`<C-ID>` が完了確認待ちの課題）は、同じ呼び出しで未承認の `release` を一括承認するが、この成功出力の `approval` は完了の承認そのもの（`kind=completion`）だけを表す。一括承認された `release` ごとの承認は `show <C-ID>` の `approvals`（`kind=release`・`operation_id` つき）、または `log <C-ID>`（`entity=operation`・`action=approve`）で確認する。

`<OP-ID>` を対象にした場合（#13）: `{"operation": {…}, "approval": {…}}`。`operation` は `show` の `operations` の要素と同じ形、`approval` は `show` の `approvals` の要素と同じ形（`kind` は常に `release`）。`--hold-release` は `<OP-ID>` には指定できない（`usage_error`）。

##### `answer`（#12 で追加）

`{"challenge": {…}, "hold": {…}}`。`challenge` は上表と同じ形、`hold` は `show` の `holds` の要素と同じ形。

##### `op add`（#13 で追加）

`{"operation": {…}}`。`operation` は `show` の `operations` の要素と同じ形（`state` は常に `"pending"`・`version` は常に `1`）。

##### `status`（#14 で追加）

`{"needs_human": {"challenges": [...], "operations": [...]}, "actionable": {"challenges": [...]}, "approved": {"operations": [...]}}`【仮定】。3 つの区分を最上位の 3 キーで分け（#5 の規約）、各区分の下に一覧を複数形の名前つきキーで置く（「人間の操作を待っているもの」は課題と不可逆操作の 2 種類を含むため）。区分のキーに `awaiting_human` を使わないのは、状態のコード `awaiting_human`（人間対応待ち。この区分に入る 3 状態の 1 つ）と紛れるため。

| フィールド | 型 | 内容 |
|---|---|---|
| `needs_human.challenges` | array | 人間の操作を待っているもの: 計画承認待ち・完了確認待ち・人間対応待ちの課題。要素は `challenge`（上表と同じ形） |
| `needs_human.operations` | array | 人間の操作を待っているもの: 未承認（`state=pending`）の不可逆操作。要素は `show` の `operations` の要素と同じ形 |
| `actionable.challenges` | array | システムが次に進められるもの: 未分類・分類済・着手中・検証中の課題。要素は `challenge`（上表と同じ形） |
| `approved.operations` | array | 承認済みの不可逆操作（`state=approved`）。要素は `show` の `operations` の要素と同じ形 |

完了（`done`）の課題と差し戻し済み（`state=rejected`）の不可逆操作はどの一覧にも含めない。各一覧は `id` 昇順。

## 非機能要件

- **配布**: `CGO_ENABLED=0` でビルドできる単一バイナリ（D14）。動作環境は **macOS と Linux**【決定 2026-09-21 A2（オーナー）】。受入基準はどちらの OS でも同じく成り立たなければならない。Windows は対象外。
- **セキュリティ**: Claude Code の Bash ツールから、通常の道具立てで承認・差し戻し・回答に到達できない（設計書 §9）。同じユーザーのプロセスによる意図的な回避（疑似端末の作成など）は防御の対象外とし、その限界を仕様と作業ログの両方から読めるようにする（§クリティカル設計決定 1）。
- **LLM とネットワーク**: M1 は LLM を呼ばず、ネットワークへ接続しない。
- **並行性**: 人間の CLI・対話セッションの Claude が実行する CLI・将来の server が同じストアを同時に開いても、ストアが壊れず、変更が失われない。ストアはローカルのファイルシステムに置く（ネットワークファイルシステムは非対応）。

## 技術的な制約・方針

- 使用技術: Go（core・CLI）【決定 D14】。SQLite は C コンパイラ不要の実装（`modernc.org/sqlite`【決定 2026-09-21 PD1（親）・§クリティカル設計決定 2】）。
- 変更対象: 新規（リポジトリにコードは無い）。`CLAUDE.md` は S1 の最初のチケットの後に `/init-project` で生成する（本仕様の範囲外）。
- 既存コードとの関係: 旧 2 repo のコードは持ち込まない（設計書 §15）。claude-harness の runtime ともコードを共有しない（D14）。

### Go のモジュール構成【仮定】

設計書 §15 の構成のうち、M1 で作るのは次だけである。

```text
go.mod                    モジュール 1 つ（github.com/masanami/flywheel）
cmd/flywheel/             バイナリの入口。引数を解釈して internal/cli を呼ぶだけ
internal/core/            状態機械・承認（経路と本人確認の登録簿）・作業ログ・課題と不可逆操作の操作。公開 API はここだけ
  internal/store/         （＝internal/core/internal/store）SQLite の接続・PRAGMA・スキーマ・マイグレーション。Go の internal 規則で core 以外から import できない（P2）
internal/cli/             コマンドの定義・JSON／テキスト出力・終了コードとエラーコードの写像・端末での本人確認（Verifier の CLI 実装）
```

- CLI は core の公開 API だけを呼ぶ。遷移の可否・承認の成立条件・作業ログの記録は core が持ち、CLI に規則を書かない（P2・P4）。
- 依存は最小にする。本番の依存は標準ライブラリ・SQLite ドライバ・`golang.org/x/term` に限る（引数の解析も標準ライブラリで行う）【仮定】。テスト専用に疑似端末のライブラリ（`github.com/creack/pty` など）を使ってよい。

### 品質ゲート【仮定】

| ゲート | コマンド | 通過条件 |
|---|---|---|
| 整形 | `gofmt -l .` | 出力が空 |
| 静的検査 | `go vet ./...` | 終了コード 0 |
| lint | `golangci-lint run`（設定ファイル `.golangci.yml` をリポジトリに置き、版を固定する） | 終了コード 0 |
| テスト | `go test -race ./...` | 終了コード 0 |
| ビルド | `CGO_ENABLED=0 go build ./cmd/flywheel` | 終了コード 0 |

- 5 つをまとめて実行する入口を 1 つ置く（例: `make check`）。`/init-project` で生成する `CLAUDE.md` にこの入口を書く。
- **core のテストは実ストア（`t.TempDir()` の SQLite）で行い、ストアをモックしない**（設計書 §15）。
- 本人確認のテストは、疑似端末を割り当てた子プロセスとして CLI を起動して行う（端末がある場合）と、標準入力をパイプにして起動して行う（端末がない場合）。
- **PR ごとの CI（GitHub Actions で上の品質ゲートを実行）を S1 の最初のチケットで入れる**【決定 2026-09-21 PD3（親）】。品質ゲートは macOS と Linux の両方で回す（A2）。ランナーの構成は実装チケットで決める【仮定】。ワークフローの実行（`gh workflow`）はリポジトリの ask 設定のまま。
  - 注記: `.github/workflows/*` を含む push は、gh の OAuth トークンに `workflow` スコープが無いと HTTPS で拒否される（親の運用実績・2026-07 時点・環境依存）。実装チケットには、代替手段として **SSH の remote で push する**ことを書く。

### 現行から引き継ぐ振る舞い

現行スクリプトのテスト（claude-flywheel 0.29.0＝`75bf13f`）が固定している振る舞いのうち、M1 に関係するものの対応。

| 現行（テスト） | 固定している振る舞い | M1 での扱い |
|---|---|---|
| `validate-artifact`（#151） | 状態名は前後の空白だけを除いて語彙と完全一致させる。`計画承認待ち（未分類 → … → 完了）` や `レビュー待ち` は拒否 | 状態名の指定（`list --status` など）は語彙のコードか表示名と完全一致だけを受け付ける |
| `validate-artifact` | 語彙ファイルの欠落・空・重複は fail-closed（exit 2） | 語彙は実装に埋め込むため該当する失敗は起きない。代わりに語彙と遷移表の閉包をテストで検査する（受入基準） |
| `ledger-index` T7・T10 | 語彙と他の列挙（遷移列・スキーマの enum）を双方向で照合 | 語彙の正本をコードの 1 箇所に置き、遷移表・表示名・エラーコードとの閉包をテストで検査する |
| `pause-for-set-approval` | 語彙に `昇格`・`一時停止` を足さない | 本番反映は状態を足さず、不可逆操作として別に持つ（§決定事項の記録 H2） |
| `migrate-workspace` | 2 回目の適用はバイト一致・失敗時に途中状態を残さない | `init` の冪等・マイグレーションの原子性 |
| `migrate-workspace` | 機械は承認（`[x]`）を書かない・消さない | 承認を作るのは本人確認つきの操作だけ。`init`・マイグレーションは承認を作らない |
| `cycle-commit` | 変更が無ければ空のコミットを作らない | 値が変わらない操作は作業ログを残さない |
| `log-run-event` | 呼び出し側の誤り（不正な名前・値の欠落）は何も書かずに exit 2 | 使い方の誤りは何も書かずに終了コード 2（`usage_error`） |
| `noop-check` ほか | 判定できないときは安全側に倒す | ストアを読めない・版が新しいときは変更せずに終了コード 2 |
| 承認の無効化（台帳の規約） | 差し戻し後に書き換えた計画の `[x]` はリセット。保留に入ると回答を消す | 承認は対象の版に束ねる。改訂された計画に古い承認は効かない。新しい保留に古い回答は効かない |
| 各スクリプトの終了コード | 0 成功／1 違反／2 判定不能 | 0／1／2 の 3 値（上記 CLI 共通） |
| `ledger-deps` | 存在しない ID・自己参照・循環は着手不可（fail-closed） | S2（依存関係） |
| `log-run-event check` | 未終了の `*_start` の検出 | 対象外（実行記録は M3） |

## クリティカル設計決定

> 2026-09-21 に確定した。安全性のトレードオフを含む項目（1 の H8〜H10）はオーナーが決めた。後続の実装はここに従い、独自に逸脱しない。

### 1. 承認の本人確認と、経路の拡張性（セキュリティ）

- **採用案**【決定 2026-09-21: 登録簿方式と成立条件 1〜2・確認の読み取り方は親、H9・H10 はオーナー】:
  - core は承認を「**要求（対象・期待する版・決定・理由）**」と「**経路（channel）**」「**本人確認の方式（verification）**」の組で受け取る。core は**許可した（経路, 方式）の組の登録簿**を持ち、登録簿に無い組の要求を `verification_rejected` で拒否する。M1 の登録簿は `(cli, tty_confirm)` の 1 組だけ。M4 でパスキーつきのブラウザ経路などを足すときは、方式の実装と登録を足すだけで core の遷移規則は変えない。
  - 本人確認の方式は Verifier として実装し、core は Verifier が返した結果（本人確認済みの actor・方式）だけを信用する。呼び出し側が「確認済み」と申告する経路は持たない。
  - `tty_confirm` の成立条件（すべてを満たさなければ `tty_required`）:
    1. 標準入力が端末である
    2. 制御端末（`/dev/tty`）を開ける
    3. 環境変数 `CLAUDECODE` が設定されていない【決定 2026-09-21 H10（オーナー）。補助の歯止めであり、設定されていないことを本人確認の根拠にはしない】
  - 要約の表示と確認の読み取りは `/dev/tty` に対して行い、標準入力からは読まない（パイプで流し込んだ入力を確認として使わせない）。確認の入力は対象の ID（`C-12`・`OP-3`）の完全一致とし、`y` では成立させない。
  - 確認が成立したら、表示時点の対象の版を条件にして、承認と遷移と作業ログを 1 つの書き込みトランザクションで行う（版が変わっていれば `conflict`）。
- **理由**: D5 は「Claude が承認を実行できない」を経路を持たないことで担保する。Claude Code の Bash ツールには端末が接続されない（2026-09-21、headless の `claude -p` で `stdin`・`stdout`・`stderr` が非端末、`/dev/tty` が開けないことを実測）。登録簿方式は D15 の「経路と本人確認の方式を後から足せる」を core の変更なしで満たす唯一の案である。
- **代替案**:
  - B: 承認を型付きのコマンドとし、証跡を自由形式で受け取り、経路ごとの分岐を core の中に書く — M1 は単純になるが、経路を足すたびに core の分岐が増え、D15 の要件に反する。
  - C: 呼び出し側の「確認済み」の申告を信用する — core を呼べる経路（Claude が実行する CLI を含む）すべてが承認できてしまい、D5 を崩す。
  - 確認を `y/N` にする — うっかりの承認を防げない。ID の入力は意図的な疑似端末の回避には効かないが、誤操作と自動化の事故には効く（H9）。
- **既知の限界**: `script` などで疑似端末を割り当てれば、同じユーザーのプロセスは 1〜3 を満たせる（設計書 §9 が受容済みの限界）。M3 で invoker が起動する Claude セッションには、承認コマンドを deny する権限設定を渡す（設計書 §9 の補助策。M1 の範囲外）。**Claude Code を対話モードで使うときの Bash ツールで 1〜2 がどうなるかは未検証**であり、受入基準の要人間判定に置く。
- **影響範囲**: `internal/core`（登録簿・承認の成立条件）、`internal/cli`（`tty_confirm` の Verifier）。M4 の server は同じ登録簿へ方式を足す。

### 2. ストアの実装方式（DB スキーマの扱い）

- **採用案**【決定 2026-09-21 PD1・PD2（親）】:
  - ドライバは `modernc.org/sqlite`（cgo 不要・`database/sql` 対応・採用実績が厚く、2026-09 時点で SQLite 本体への追随も速い）。
  - 開くたびに WAL・`busy_timeout`（5000 ミリ秒【仮定】）・`foreign_keys=ON` を設定し、**書き込みトランザクションはすべて `BEGIN IMMEDIATE`** で始める（読みから書きへ昇格するときの即時の `SQLITE_BUSY` を避ける）。プロセス内の書き込み接続は 1 本に絞る。待ちの上限を超えたら `store_busy`。
  - 楽観的な並行制御: 課題（と不可逆操作）に単調増加する整数の版を持たせ、`UPDATE … WHERE id = ? AND version = ?` の影響行数で衝突を検出する。人間の承認は、要約を表示した時点の版に束ねる。本人確認のない単発の操作は、`BEGIN IMMEDIATE` による直列化と最新の状態での再検査で守り、`conflict` は返さない（PD7・親の決定 2026-09-21）。
  - マイグレーションは `PRAGMA user_version` と、バイナリへ埋め込んだ SQL（`embed.FS`）による**前方のみ**の自前の実行器で行う。開くときに自動で適用し、1 つの版の適用は 1 トランザクションで行う（途中で失敗したら版も内容も元のまま）。ストアの版がバイナリの知る最新版より新しければ、開くこと自体を失敗させる（`store_too_new`）。
  - スキーマ（テーブルと列）は §データモデル の決定に従う。
- **理由**: どの案も「ストアを開くのは core だけ」（P2）と矛盾しない。自動適用は、CLI が人間・Claude・server の複数のプロセスから都度起動される形（P6）で「誰が最初にマイグレーションするか」の運用を消せる。goose・golang-migrate を使っても「新しすぎる版の拒否」は自前で書く必要があり、依存を足す見返りが小さい。
- **代替案**:
  - ドライバ `github.com/ncruces/go-sqlite3`（wasm）— 本家に最も近い挙動だが、wazero から別方式への移行が進行中で、ビルド特性が近く変わりうる。
  - 書き込みを rollback journal のまま直列化 — 読み取りが書き込みに塞がれ、将来の UI の問い合わせと相性が悪い。
  - 版の列を持たず `WHERE status = ?` で衝突を検出 — 同じ状態のまま中身（計画の版・完了条件）が変わった場合を見分けられず、人間が見た版への束縛ができない。
  - マイグレーションを明示コマンドにする — 意図しない時点の適用は避けられるが、複数の入口のどれが最初に踏むかの運用が要る。
- **影響範囲**: `internal/core/internal/store`。M1 のスキーマ版は 1 から始める。

## 機能全体の設計

### アーキテクチャ決定

- **core の公開 API が、状態を変える唯一の入口**である（P2）。CLI は引数の解釈と出力の整形だけを持つ。M2 の adapter・M3 の invoker・M4 の server も同じ API を呼ぶ。
- **遷移表はデータとして持つ**（コード中の分岐に散らさない）。許可された遷移の検査、本人確認の要否、作業ログへの記録を 1 か所で行う。
- **本人確認つきの操作は 2 段階の API** にする: ① 対象の要約と版を得る（読み取り）② 版と本人確認の結果を添えて実行する（書き込み）。CLI は ① の結果を `/dev/tty` に表示し、確認を得てから ② を呼ぶ。① と ② の間に対象が変われば ② が `conflict` を返す。M4 の UI も同じ 2 段階を使う。
- M1 では、課題の変更（フィールド・状態・計画の登録・保留・回答）と、その課題の不可逆操作の登録・承認・差し戻しで課題の版を 1 増やす【仮定】。これにより「確認の途中で未承認の不可逆操作の集合が変わった」ことも課題の版の比較で検出できる。

### Linux での未検証事項（A2 により発生。文書だけでは確かめられない）

- `/dev/tty` の判定（本人確認の成立条件 1〜2）と、Claude Code の Bash ツールに端末が見えないこと: 実測は macOS の headless `claude -p` だけ
- `CGO_ENABLED=0` の `os/user.Current()`: Linux では `/etc/passwd` だけを読むため、LDAP などのユーザーでは取得できない（上記の環境変数への退避で扱う）
- `modernc.org/sqlite` の WAL・`busy_timeout`・`BEGIN IMMEDIATE` の挙動の同一性（どちらもローカルのファイルシステム前提）
- テスト専用の疑似端末ライブラリの挙動の同一性
