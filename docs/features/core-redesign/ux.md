## 未決・見送り

- **Markdown を描画する部品の選定**: 静的な試作では決められない。機能仕様か実装の段で決める（flywheel#682 の決定の持ち越し）。
- **実物の部品での動きの確かめ**: flywheel#682 では「実物の部品を作り替え、偽のデータで動かす試作」と決めていたが、今回は静的な HTML にした。実物での確かめは、実装の段で行う。
- **CLI のコマンドの名前とフラグ**: 案。`flywheel status` の出力を改めることで、いまの `--json` の利用に影響が出ないかを、機能仕様で確かめる。
- **画面から受ける操作を広げることと、承認の経路の決まりの関係**: 決定 26（選ぶだけの回答・取り込み・サイクルを止める、を画面のボタンで受ける）と決定 27（画面の中の対話の欄で、反映先へ入れる承認も受ける）は、設計書の承認の経路の決まり（§9。画面のボタンで受けるのは計画の承認と、反映を保留した完了の承認だけ。理由は、画面の口には委譲の子からも届きうるため）を広げる。対話の欄を作る区切り（S4）のクリティカル設計で、子から届かないことの守り方を決め、設計書の決定として足す。対話の欄の分と画面のボタンの分は、次のとおり決めた。**対話の欄の分（決定 27）は、S4d の区切りで決めた**: 新しい経路 `chat` として登録し、不可逆操作の承認は宣言 `chat_approvable_operations` で選んだ種類だけ（既定は反映だけ）受ける。子から届かないことの守りと受け入れた危険は、設計書 §9 に書いた。**画面のボタンで受ける分（決定 26）は、区切り S4d-2 で決めた**: 経路 `ui` で受ける回答の限り（選択肢だけ・作り直しなし・足す依頼の「足す」「計画を作り直す」を受けない）と、広げたことで受け入れた危険は、設計書 §9 の「画面のボタンの回答の限り」に書いた。
- **タスクが複数の課題で、統合先を使わない形**: 計画の承認の画面の「統合先を使わない」は、タスクが 1 個の課題のときだけ選べる。タスクが複数の課題で、タスクごとに承認して反映先へ入れる形（承認の単位「タスクごと」）は、後で足す（設計書 §21.2）。試作は、この形に直した（レビューの指摘。2026-11-17）。

## 範囲外
