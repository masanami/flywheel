## 1. 背景: 何を解くのか

flywheel は、自律エージェントが課題を取り込み、計画し、実作業を委譲し、検証し、学習するサイクルを回す仕組みである。現在は Claude Code プラグイン（`claude-flywheel`）と、読み取り中心の UI（`claude-flywheel-board`）の 2 つで構成されている。

### 1.1 解きたい課題【決定 2026-09-20】

1. **Claude を必要としない処理まで Claude が実行しており、無駄にコストがかかる。** スクリプト化で改善はされたが、スクリプトを呼ぶのは依然として LLM セッションである。
2. **UI をシステムに含めたい。ただし Markdown をデータソースにすると UX に限界がある。**
3. **現状の管理はユーザーの認知力を要求する。** UI/UX による支援が今後重要になる。
4. したがって**データの持ち方を含めて**作り直す。**UI からの状態変更**と**外部システムとの連携**も射程に入れる。

### 1.2 実測による裏付け

**散文は個別の是正では減らない。** `run-cycle/SKILL.md` は 73,598 B（2026-08-20）から **130,145 B**（2026-09-14）へ 77% 増えた。この間に「分量と散文で持つべき規定の範囲を見直す」課題（claude-flywheel#97）が完了しているにもかかわらず、である。

**散文の大半は、判断ではなく制御である。** 現行 `run-cycle` の手順別の分量と中身（2026-09-14 時点）:

| 手順 | 分量 | 中身の実態 |
|---|---:|---|
| 0. 観測・取り込み | 15.1 KB | ロック取得・heartbeat・外部ソースの取り込み・fingerprint 照合。**ほぼ全部が決定的** |
| 1. 整理 | 9.2 KB | 課題が自ポジションのものかの分類。**判断** |
| 2. 計画 | 18.3 KB | タスク案の作成は**判断**。予算・枠・直列化グループの算出は**決定的** |
| 3. 実行 | 51.9 KB | 依存ゲート・スロット割り当て・費用ガードの評価式・枠超過の伝播・起動と合流・イベント記録・結果の照合。**大半が決定的**。判断は「ブリーフを書く」「子の問いに答える」の 2 つ |
| 4. 検証 | 4.3 KB | 成果が完了条件を満たすかの**判断** |
| 5. 学習 | 0.8 KB | 知見の記録。**判断** |
| 6. 報告・コミット | 26.6 KB | バリデータ・pathspec コミット・未終了イベントの検算・ロック解放。**ほぼ全部が決定的** |

**コンテキストの固定費が構造的に大きい。** 1 サイクルごとに約 66k トークンの固定文脈を読み、さらに 1 セッションで複数周回すと親のトークンが二乗的に積み上がる（実測: 親 1,793 ターンでキャッシュ読み 8 億トークン）。現在は「1 サイクル = 1 セッション」という運用規律で抑えている。

**Markdown 正本は UI 側にもコストを払わせている。** board は 38,706 行のうち **7,229 行が Markdown のパース層**である。書き込みは「承認チェックボックス 1 行の置換」だけが許可された唯一の経路で、優先度の並べ替え・新規起票・人間記入欄の編集は実装できないまま止まっている。

**運用者は実際に迷っている。** 1 か月の運用で繰り返し迷った点として、次の 5 つが報告されている（claude-flywheel#111）。本設計が UI/UX で解消すべき認知負荷の実例として扱う（対応は §12.3）。

1. サイクルを回すのか、対話で指示するのか
2. 承認はいつ・どこで行うのか
3. 「サイクルの終わり」と「仕事の終わり」がずれる
4. 1 セッションで何周回してよいのか
5. 定期実行と都度実行のどちらが標準か

## 3. 設計原則

**P1. 制御の主従を反転する。** 現在は Claude がスクリプトを呼んでいる。これを、**システムが回り、判断が要る箇所でだけ Claude を呼ぶ**形にする。

**P2. 状態の書き込み経路は core の 1 本だけ。** UI・CLI・外部連携・Claude のいずれも、状態を変えるときは同じ core を通る。状態遷移の検証と承認ゲートを、散文の約束ではなくコードの分岐にする。

**P3. データを性質で分ける。** 機械が遷移させ、UI が問い合わせ、外部と同期するものは構造化ストアに置く。LLM が読む知識は Markdown のまま Git で追跡する（§5）。

**P4. Claude には意味判断だけをさせ、進行管理をさせない。** Claude は型付きの判断値を返し、core がそれを決定的な状態遷移へ写像する。不正な値・未知の値・`uncertain` は fail-closed か人間へのエスカレーションに倒す（claude-harness#201 最終決定 §5 と同じ原則）。

> **2026-11-17 の設計の見直しで改める（未実装）**: 不正な値・未知の値・`uncertain` の上げ先を、core → スーパーバイザー（SV）→ オーナーの 3 段にする（D27）。SV も型付きの判断値（手の一覧からの選択）を返すだけで、遷移は core が行う点は変えない。

**P5. 外の委譲先に固有の形を、core に持ち込まない。** core は、宣言で指定する外の委譲先の名前・コマンド・フラグを持たない。接続の仕方はエージェントごとの宣言が担う（§10）。当初の「ドメイン非依存を保つ」のうち、「業務の種類（開発かそれ以外か）に依存しない」は外した（D7 の改訂・D35。2026-11-24）: flywheel は開発に特化し、開発の概念（フロー・ステップ・ブランチ・PR）を自分の語として持ってよい。組み込みのフロー（flywheel が自分で進めるフロー）は、外の委譲先ではなく flywheel の一部で、core とは契約の状態の形で話す（[features/flow-port.md](features/flow-port.md)）。

**P6. 常駐プロセスを必須にしない。** サイクルは有限のプロセスとして起動し、終わる。UI サーバは任意の付加物であり、落ちていても CLI と対話でエージェントは回る（承認も端末の CLI で行える）。モバイルから UI を使う間は server が動いている必要がある（D15）が、落ちている間はモバイルから触れないだけで、エージェントは止まらない。

**P7. 散文が再び肥大化しない構造を持つ。** 決定的な処理を散文で書ける場所を残さない。Claude に渡す指示は呼び出し点ごとに分割し、分量の上限をテストで固定する（§8.3）。

## 4. 全体構成

```mermaid
flowchart TB
    ui["UI（ブラウザ）"]
    human["人間の端末 / cron"]
    chat["対話セッション<br/>（Claude Code ＋ 薄いスキル）"]
    engine["実行エンジン（claude）<br/>対話の欄の会話ごとに起動したまま続ける"]
    ext["外部システム<br/>（GitHub Issue 等）"]

    subgraph sys["flywheel"]
        server["server（UI 用 API）"]
        cli["CLI"]
        adapters["adapters（外部連携）"]
        core["core<br/>状態機械・承認ゲート・ロック・予算<br/>スケジューリング・作業ログ"]
        store[("構造化ストア<br/>SQLite")]
        invoker["invoker<br/>Claude の呼び出し（判断点・委譲・対話の欄の会話）"]
    end

    knowledge[/"知識（Markdown・Git 追跡）<br/>positions / memory"/]
    tool["接続ツール<br/>（例: claude-harness）"]

    ui --> server --> core
    human --> cli --> core
    chat --> cli
    ext <--> adapters --> core
    core <--> store
    core --> invoker
    invoker -- "読む" --> knowledge
    invoker -- "実作業の委譲" --> tool
    server -- "対話の欄の会話" --> invoker
    invoker --> engine
    engine -- "flywheel のコマンド" --> cli
```

| 構成要素 | 責務 |
|---|---|
| **core** | 状態機械・遷移の検証・承認ゲート・ロック・予算と枠の評価・依存の解決・スケジューリング・作業ログ。**状態を書けるのはここだけ**（P2） |
| **store** | core だけが開く構造化ストア。スキーマとマイグレーションを core が所有する |
| **CLI** | core の全機能への入口。人間・cron・対話セッション中の Claude が使う。JSON 出力を持つ |
| **server** | UI 用の API。core をライブラリとして呼ぶだけで、独自の状態を持たない（例外は、動いている実行エンジンのプロセスと、その入出力の管、休ませるための時計だけ）。**画面の対話の欄のために、サーバが実行エンジン（`claude`）を起動する**。起動の口は core の IF（`ChatInvoker`）で、実装は invoker。`serve` が組み立ててサーバへ渡す。IF は会話の単位で、起動（新しい会話か続き）・発言を送る・確認へ答える・止める、の口を持つ。**会話ごとに実行エンジンを起動したまま続け**、返事が終わってもプロセスを止めずに、次の発言を同じプロセスへ送る。動いているプロセスはエージェントごとに高々 1 つ。返事が終わってから 30 分（定数。宣言の項目にしない）、発言も確認も無ければプロセスを止める（会話は閉じない）。「止める」は返事の割り込みではなく、プロセス（と子のプロセス）を止める。プロセスが動いていない開いた会話へ発言を送ると起動し直す（会話の始まりが記録できた会話は `--resume`、できていない会話は `--session-id`）。1 回の返事のターン数と時間の上限は置かない。返事の進みはストアの会話と発言の表（`chat_session`・`chat_message`）へ書き、画面へはいまある変化の知らせで届ける。欄から起動された実行エンジンが行う操作は、flywheel のコマンドとして CLI を通り、経路 `chat` で承認される（§9） |
| **UI** | 状態の閲覧と、人間による状態変更（承認・優先度・起票など） |
| **adapters** | 外部システムとの同期。取り込みは完全に決定的で、LLM を介さない |
| **invoker** | 判断点ごとに Claude を呼ぶ（委譲と、対話の欄の会話の起動も担う）。入力の組み立て、出力スキーマの検証、費用の記録を担う |
| **薄いスキル** | 対話セッションで「サイクルを回して」「この課題を取り込んで」と言える体験を保つための入口。中身は CLI を呼ぶだけ。**承認は代行しない**（承認待ちの提示と、承認方法の案内まで＝§9） |

### ストアの置き場とバックアップ（D9・D10）

- ストアはエージェントのワークスペース内に 1 ファイルで置く（例: `.flywheel/flywheel.db`【仮定】）。**Git では追跡しない**。エージェントが自己完結し、現行の「エージェントの repo が単位」という構造をそのまま保てる。
- Git 追跡から外れるとストアが単一障害点になるため、core が**全状態を JSON へ書き出す操作**（`flywheel export`）を持ち、その出力を定期的にコミットする。目的は復旧であり、監査ではない。書き出しからストアを再構築する操作（`flywheel import`）と対にし、**往復で状態が一致することをテストで固定**する。
- 書き出しの契機は、サイクルの終了時と、人間による状態変更のあと【仮定】。差分が無ければコミットしない。
- エージェント横断の課題（FR-08）は、当面 UI の集約表示で扱う。ストアをまたぐ参照が実際に必要になった時点で見直す。

旧 journal は、実行の事実（どの課題がどう遷移したか）と所感が 1 ファイルに混ざっていた。新しい構成では周ごとの journal を持たない。事実はストアの作業ログ・`run`・`cycle` にあり、学びは J6 が記憶（Markdown）と発生の行（ストア）へ書く（2026-10-22 オーナー＝[M4.5 の機能仕様](features/m4.5-learning-and-self-improvement.md) M45H6。旧 journal の読み手は reflect と人で、次の周は読んでいなかった）。課題未満の引き継ぎ事項の受け箱も持たず、記憶の草案は J6 の記憶へ、フォローアップと人への依頼は課題へ送る（同 M45H7）。

> 人間対応待ちには種類がある（`human`＝人の対応を待つ・`parent_direct`＝対話のセッションの親が直接行う。#452）。種類が `parent_direct` の保留からは、回答（T12）・取り下げ（T16）に加え、親が直接行った作業を成果物の参照つきで記録する T17（`complete-direct`）で、完了の検証を通さずに完了確認待ちへ進める（完了の承認は従来どおりオーナー。[M1 の機能仕様](features/m1-core.md) §親が直接行った作業の完了）。状態は人間対応待ちのままで、`status`・関係グラフは種類を見て「親のエージェントが動く番」の区分に分ける。判断点 J2 が判定 `parent_direct`（委譲の計画が立たず親が直接行うのが適切）を返したときも、この種類の保留が立つ（T11。親の達成条件を課題の達成条件の後ろへ見出しを付けて書き足す。元の達成条件は残す。[M3 の機能仕様](features/m3-invoker-delegation.md) §J2）。親が直接した完了の差し戻し（T15）は、着手中ではなく「親が直接やる」保留（種類 `parent_direct`・問いは差し戻しの理由）へ戻す。保留への回答に「範囲が変わる」印（`answer --replan`）を付けると、回答は保留の直前の状態ではなく分類済へ戻り、計画を作る判断点（J2）が回答と前の計画から計画を作り直して計画承認待ちへ戻す（[M1 の機能仕様](features/m1-core.md) §範囲が変わる回答。着手中・検証中の保留だけ。スキーマ版 22 の `hold.replan`）。完了確認待ちが T17 で入ったものかは、課題の記録 `challenge.completion_direct`（T17 で 1・ほかの遷移で 0）で分ける（#481。スキーマ版 17）。
>
> 完了は通常の操作から出られない終端のままだが、承認まで済んだ `release` の PR の中身が、検証の後に、取り込みだけではない形で変わったとき（区切り S3a で、「マージできなくなったとき」から改めた。反映先へ入れられないことを理由には戻さない）に限り、専用の書き込み（`ReopenChallengeForRelease`）だけが完了から検証中へ戻す（遷移表の制限つきの行 T18。CLI のコマンドは無い。#485）。戻した課題は完了の検証をやり直し（満たさなければ着手中へ戻して差し戻し）、新しい完了の承認で新しい `release` を承認する。

遷移ごとに「誰が起こせるか」を core が持つ。**人間だけが起こせる遷移を、自走中の Claude が起こせない**ことが承認ゲートの実体になる（§9）。

## 7. サイクルの再設計

> **2026-11-17 の設計の見直しで改める（未実装）**: サイクルは走っているタスクを見ながら進める（D26）。判断点は 4 つにし、下の表の J3・J4・J6・J8 は外すか SV にまとめる（D27・D28）。「カードの段階の欄と論点の段」の、論点を計画の前に問う形は、計画と同時に出す形にする（D23）。学びの出口は課題の起票ではなくフォローアップにする（D22）。形は §21.4〜§21.6。

> **core の見直し（§17 の段 2）の区切り S1「外す」で実装済み（2026-11-17）**: 同時に進めてよいかの判断点（J9）とコンフリクトの予測を外した（D28・D29。過去の run を読むための識別子だけが残る）。参照: [features/core-redesign.md](features/core-redesign.md)。

現行の `run-cycle` は 1 つの LLM セッションが全手順を通しで実行する。新しいサイクルは **core が進行し、判断点でだけ Claude を呼ぶ**。

| 0. 観測・取り込み | **core ＋ adapters**（LLM なし） | — |

> **スーパーバイザーの遷移 `supervisor_resolve`（T20。区切り S4b-2）**: 遷移表に、本人確認の要らない行を 1 つ足した（遷移元は保留中、戻り先は保留の直前の状態。`replan` は、作り直しの回答と同じ先）。呼べるのはスーパーバイザーの段の手の実行だけで、対象はスーパーバイザー待ち（`supervisor_state` が `pending`）の保留だけ。人の回答の遷移（T12）と、本人確認の登録簿は変えず、本人確認つきの行と本人確認なしの呼び出しを交えない不変条件も弱めない。この行から承認・予算の増額・取り下げへは進めない（形は §21.5。J4 は区切り S4b-3 で外した）。
>
> **保留を課題に重ねて持つ（区切り S4c-3）**: 保留は、止める範囲（タスクか課題）を持つ（`hold.scope`。NULL は課題を止める保留）。遷移 T11 に、人間対応待ちからの行を足した（条件: 開いている保留が、どれもタスクを止める保留で、戻り先が着手中。新しい保留も、開いている保留の無い別のタスクを止める保留。遷移先は人間対応待ち）。回答 T12 と T20 は、ほかの開いている保留が残っていれば、遷移先を人間対応待ちにする（残っていなければ、保留の戻り先。重ねられる保留の戻り先はどれも着手中で、最後に閉じた保留の戻り先が課題の戻り先になる）。遷移の表はストアを読まない。重ねられる条件は、保留の行を作る共通の所が同じ書き込みの中で確かめ、T12・T20 の遷移先は、閉じる書き込みの中でほかの開いている保留を数えて決める。課題を止める保留とタスクを止める保留が同時に開かないことも、索引ではなくこの確かめで保つ。計画を作り直す回答（T12）とスーパーバイザーの手 replan（T20）は、ほかの開いている保留を回答なしで閉じる。取り下げ（T16）は、止める範囲によらず開いている保留をすべて閉じる。

### カードの段階の欄と論点の段（D20・M4 の S4）

- J1（分類）が「一言で」「位置づけ」を書く。サイズ M 以上の課題では、J2（計画）の前に、論点 3〜5 個（選択肢・推奨・例）を保留の問いとしてオーナーへ出し、選んだ結果をカードの論点欄に残す。
- J2（計画）がタスク案と一緒に「完了したら見えるもの（予想）」「やらないこと」を書く。見えるものの形は課題の種類で変える（UI＝変更前・変更後の画面、CLI＝同じ入力に対する出力の 2 列、ルール・スキル＝場面ごとの振る舞いの変更前・変更後）。図は、書くかどうかと何を書くかを J2 が判断する（1 件の課題の中身だけを描く）。
- J5（検証）が「完了したら見えるもの（実物）」を書き、完了の承認では予想と実物を並べて示す。
- 差し戻しは「どの欄とずれたか」を記録し、効果の測定（差し戻し率）の材料にする。

### 自己改善ループ（D21・M4.5）

- **効果の測定**: 指標はストア（`activity`・`run`・`approval`）から LLM なしで集計する（例: `flywheel metrics`）。初期の指標は、差し戻し率（計画の承認の後に完了で差し戻した割合。欄ごとの内訳つき）・resume の回数・1 課題あたりの費用・人の承認の件数。改修の適用の前後で並べて示す。
- **改修提案（J8）**: 失敗・差し戻しを原因で 3 分類する。文脈不足は指示・記憶・テストを足す提案へ、権限不足は権限を与えられるかの検討へつなげ、性能不足は「待つ」と記録して改修を提案しない。提案ごとに改善したい指標を書き、「やめる・減らす」の候補（指標と検査が増えるほど 1 周が重くなるため）も出す。指標の取り方に穴が無いか（ループそのもの）も点検する。
- **改修の対象は層で分かれ、適用の経路も分かれる**: flywheel の判断点の指示文（`internal/invoker/prompts/`。flywheel への PR。§8.3 の分量の上限と構造の不変条件のテストを通すことを適用の条件にする）／接続ツールのスキル（claude-harness 等。そのリポジトリへの Issue）／Claude Code との入口のスキル（§14）／Markdown の知識（ポジション・記憶・ブリーフの雛形）。提案はどの層への改修かを明示する。
- **承認と適用**: 改修案は課題として起票し、通常の計画・完了の承認（§9）を通す。委譲・検証の仕組みもそのまま使う。
- **集計の単位は 1 回の発生とする**: 学習の記録（J6）は、1 回の発生ごとの行（課題・周・原因の分類・対象）としてストアに持ち、J8 などの集計はその行から決定的に数える。「処理済み」の印も発生の行ごとに付けるので、同じ症状の再発を後から足しても、新しい行は未処理として集計に入る。記憶の本文（人が読む Markdown）は症状ごとにまとめてよいが、集計は本文を読まない。旧 reflect は処理済みの印を記憶のファイル単位で付けていたため、内省の後に同じファイルへ追記された再発が集計から漏れた（2026-10-11 の実測で 13 件中 9 件）。
- 起動の頻度: 未処理の `bad` の発生（原因が性能不足のものを除く）が `improve_threshold`（既定 10）に達したら `flywheel cycle` の段で J8 を呼び、手動の `flywheel improve` も置く（2026-10-22 オーナー＝[M4.5 の機能仕様](features/m4.5-learning-and-self-improvement.md) M45H8。§16 の Q12 を閉じた）。
- 改修の層ごとの適用の経路: 判断点の指示文と入口のスキルは flywheel への PR、接続ツールのスキルはそのリポジトリへの Issue、Markdown の知識はワークスペースの変更とし、いずれも改修課題として委譲する。flywheel のリポジトリを `repos[]` に宣言していないエージェントでは、指示文の改修も Issue にとどめる。Markdown の知識の委譲は、ワークスペース自身を `repos[]` に宣言することを前提にする（同 M45H9）。採らない改修課題は終端の状態「取り下げ」にする（同 M45H13）。

### この形で構造的に消えるもの

- **固定文脈の読み直し。** 各判断点は、その判断に必要な入力だけを受け取る独立した呼び出しになる。66k トークンの固定文脈も、「1 サイクル = 1 セッション」という運用規律も不要になる（§1.2 の迷い 4 が消える）。
- **取り込み・ロック・検証・コミット・イベント記録の LLM コスト。** 手順 0 と 6 は LLM を一切介さない。
- **イベントの記録漏れ。** 現行は `delegate_start` の書き忘れをサイクル境界の検算で拾っている。起動するのが core なら、記録は起動と不可分になる。
- **予算ガードの散文。** 評価式は core のコードになり、破られる余地がなくなる。

### サイクルを回さなくても進むもの

取り込み・分類・計画は、サイクルという単位に束ねる必要がない。課題が入ってきた時点で J1 を、分類された時点で J2 を走らせてよい。**個別操作を基本にし、サイクルは「進められるものを全部進める」一括操作として残す**（D11）。

| 操作【仮定: コマンド名は例】 | 中身 | LLM |
|---|---|---|
| `flywheel ingest` | 外部ソースから取り込む | なし |
| `flywheel classify [<id>]` | 未分類の課題を分類する（J1） | あり |
| `flywheel plan [<id>]` | 分類済の課題にタスク案を作る（J2） | あり |
| `flywheel approve <id>` / `reject <id>` | 計画・完了・不可逆操作の承認と差し戻し。**端末での対話的な確認が必須**で、Claude からは実行できない（§9） | なし |
| `flywheel run [<id>]` | 着手中の課題を委譲する（J3） | あり |
| `flywheel verify [<id>]` | 成果を検証する（J5） | あり |
| `flywheel status` | 人間の操作を待っているものと、システムが次に進められるものを示す | なし |
| `flywheel cycle` | 上記のうち**進められるものを全部、順に進める**。承認待ちに当たったらそこで止まり、待っているものを報告する | 必要な分だけ |
| `flywheel export` / `import` | ストアの書き出しと再構築（D10） | なし |

`cycle` は個別操作を順に呼ぶだけの薄い層とし、独自の規則を持たせない。こうすると、対話で 1 件だけ動かす場合も、cron で全部を進める場合も、同じ操作が同じ検証を通る。**「サイクルを回すか、対話で指示するか」という迷い（§1.2 の 1）は、どちらを選んでも結果が同じになることで消える。**

## 8. Claude の呼び出し（invoker）

### 8.1 呼び出しの形【仮定】

判断点は `claude -p`（headless）で呼ぶ。入力は invoker が組み立て、出力は JSON Schema で検証する。Anthropic API を直接呼ばないのは、接続ツールがプラグインの場合にスキル・サブエージェント・権限モデルをそのまま使えるようにするためである。

### 8.2 判断値から状態遷移への写像（P4）

> **2026-11-17 の設計の見直しで改める（未実装）**: 完了の検証はタスクごとに行い、`met` はタスクの成果を統合先へ入れること、`not_met` は動いている委譲への差し戻し、`uncertain` は SV へ上げることに写す（D24・D26・D27）。課題が完了確認待ちになるのは、ツリーのタスクが全部終わった後。形は §21.2〜§21.5。

```text
J5 検証の出力:    met | not_met | uncertain
core の遷移:      met        → 完了確認待ち
                  not_met    → 着手中（再委譲）
                  uncertain  → 人間対応待ち
                  不正な値    → run を failed として記録し、状態は動かさない
```

Claude の自由記述に、次の手順や権限を決めさせない。

### 8.3 散文の肥大化を防ぐ歯止め（P7）

- 判断点ごとの指示文は別ファイルにし、**分量の上限をテストで固定**する。
- **ファイル名は、番号に役割の名前を添える**（`j1_classify.md`・`j2_plan.md`・`j5_verify.md` の形。番号だけの `j2.md` にしない）。仕様やテストなど、判断点ごとに分けるほかのファイルも同じ形にする（D30・2026-11-17 オーナー）。いまある指示文の改名は、判断点を 4 つに整理する core の改修（段 2）で一緒に行う（先に改名だけを出すと、ストアの既存の記録・止めている課題と開いている PR・ワークスペース側の文書と記憶が旧名を指したまま残るため。flywheel#726）。
- 決定的に検査できる規定（評価式・語彙・遷移条件）を指示文に書いたら落ちるテストを置く。旧 repo で実績のある構造不変条件テストの方式を引き継ぐ。
- 現行の散文に埋まっている「落とし穴」の知見は、コードの分岐になるもの・指示文に残すもの・記憶（Markdown）へ移すものに仕分ける。

## 9. 承認ゲート

承認点は現行を引き継ぐ: **計画の承認**（FR-13）、**完了の承認**（FR-32）、**本番に影響する不可逆操作の承認**（FR-22。既定ブランチへの昇格マージ＝本番反映を含む）。

### 完了と本番反映は 1 回の操作で承認し、記録は分ける（D12）

> **2026-11-17 の設計の見直しで改める（未実装）**: 人の 1 回の操作で両方を承認する点は変えない。変えるのは、承認の単位（既定は課題ごと。D23）と、実行する主体（委譲先が反映先へ入れる。D24・D32）と、承認の後に中身が変わったときの扱い（反映先の最新の取り込みと、検証を通ったコンフリクトの解消は、承認し直さずに入れる。D31）。スキルを直接呼ぶ形や指示文を直接渡す形の委譲の成果物も、委譲先の宣言にある操作として委譲先へ頼む。委譲先に口ができるまでは、この項の最後の段落のとおり core が実行する。オーケストレーターが直接作った成果物は、flywheel の外で、オーナーの指示を受けてオーケストレーターが反映先へ入れる。形は §21.2・§21.3。

- **人の操作は「完了を承認」の 1 回**にする。課題に未実行の本番反映（未マージの昇格 PR など）があれば、同じ操作で本番反映の承認まで済む。
- **作業ログには、完了の承認と本番反映の承認を別々の記録として残す**（それぞれ `actor`・`channel` つき）。モデル上のゲートは 3 つ（計画・完了・本番反映）のまま持つ。
- **「完了だけ承認して、本番反映は保留」も選べる**。マージを伴わない完了や、マージの時機を人がずらしたい場合のためである。保留した本番反映は、後から単独で承認できる。
- マージを伴わない不可逆操作（削除・外部送信など）の承認は、本番反映のゲートとして引き続き単独でも扱える。

背景: 現行では完了の承認と本番反映の承認が別の操作であるため、「台帳上は完了・アーカイブ済みなのに本番に入っていない PR が残る」事象が 86 周中 55 周で起きていた（claude-flywheel#176）。0.29.0 で同じ停止点にまとめたが、操作は別々のままで、2026-09-21 の周でも完了の承認のあとに「main へマージして」の別指示が 4 回必要になった。操作を 1 つにまとめ、ずれが起きる余地をなくす。

> **区切り S3a で置き換えた（上の見直しの注記のとおり）**: 以下の「core が `gh pr merge --match-head-commit` でマージする」前提は外した。flywheel は反映先へ入れず、マージを持たない。反映の段は、承認した中身（または、それに反映先の最新の取り込みだけを足したもの）で、チェックがすべて通っているときだけ、委譲先へ「入れてよい」を返し、入ったのを上流で読んで実行済みにする。口が無いリポジトリは、flywheel の外での反映を待つ。

承認済みの本番反映は **core が LLM なしで実行する**（2026-10-22 オーナー＝[M4.5 の機能仕様](features/m4.5-learning-and-self-improvement.md) M45H2〜M45H5）。口は `flywheel op exec` と `flywheel cycle` の最初の段で、端末・対話の承認の時点に取得した PR の head を承認の記録に残し、実行の直前の head と一致するときだけ `gh pr merge --match-head-commit` でマージする。head の変化・PR の close などで前提が崩れたら承認を取り消して承認待ちへ戻す。実行するのは `release`（PR のマージ）だけで、`delete`・`external_send`・`other` は承認の記録までとし人が外で行う（同 M45H3）。M1 は承認の記録と、未実行・保留中の本番反映の可視化までを持つ（[M1 の機能仕様](features/m1-core.md)）。

### ハーネスの改修も課題として承認する（D21）

> **2026-11-17 の設計の見直しで改める（未実装）**: 改善の候補は、SV の振り返りがフォローアップとして書く。課題（タスク）になるのは、オーナーが上げたものだけ（D22・D27）。上げた後に通常の承認を通す点は変えない。形は §21.5。

自己改善ループ（§7）の改修案は課題として起票し、計画・完了の承認を通す。承認の種類（`kind`）は足さない。改修の承認だけ別の経路・画面を持つと、承認の経路（D5・D18）と作業ログの仕組みを二重に持つことになるためである。

### 差し戻しはずれた欄を記録する（D20）

完了の差し戻しでは、理由（自由記述）に加えて、カードのどの欄（論点・完了したら見えるもの・やらないこと 等）とずれたかを記録する。効果の測定（差し戻し率）の内訳に使う。

### 経路（D5・D18）

**承認は、人間が直接行う操作と、人間が対話で伝えた承認を LLM が記録する操作に限る。** 経路ごとに受けられる承認の範囲を core が決め、本番に届く承認は端末か対話に限る（2026-10-12 改訂）。

| 経路（`channel`・`verification`） | 形 | 受ける承認 |
|---|---|---|
| UI（`ui`・`none`） | 画面のボタン → server → core（M4 の S2。D18。設計の見直しの区切り S4d-2 で広げた） | 計画の承認と完了の承認（完了は常に本番反映を保留扱い）、選ぶだけの回答（選択肢の識別で答える保留への回答。下の「画面のボタンの回答の限り」）、フォローアップを捨てる。取り込み・サイクルを止める・フォローアップを済みにするは、承認ではなく本人確認を通さない操作で、同じ口の守り（Host と Origin の検査・CSRF の値）で受ける |
| CLI・端末（`cli`・`tty_confirm`） | 人間が端末から `flywheel approve <id>` を実行 → **端末（TTY）での対話的な確認** → core | すべて（差し戻し・回答・予算の増額を含む） |
| CLI・対話（`cli`・`relayed`） | オーナーが Claude Code との対話で伝える → LLM が `flywheel approve <id> --relayed --session <会話の識別> --quote <発言の要旨>` を実行 → core（M4 の S3） | 承認（本番に届くものを含む）・差し戻し・回答・予算の増額（`flywheel budget … --relayed`。M4 の M4H28） |
| 画面の対話の欄（`chat`・`relayed`） | オーナーが画面の欄へ文で伝える → サーバが、会話ごとに起動したままの実行エンジンへ送る → 実行エンジンが `flywheel approve <id>` などを、環境の印（会話の識別）つきで実行 → core（設計の見直しの区切り S4d） | 承認・差し戻し・回答・取り下げ・予算の増額・フォローアップの操作。不可逆操作の承認は、宣言 `chat_approvable_operations` にある種類だけ（既定は反映〔`release`〕だけ）。反映の承認を含む完了の承認も同じ絞りを受ける |

GitHub 上のチェックボックス承認と、「人間の git identity でのコミット」による真正性の担保は廃止する。

### 画面の対話の欄の経路 `chat`（UX の決定 27 を改める）

UX の決定 27 は「ターミナルの対話と同じ扱い」だったが、「経路 `chat`。不可逆操作は、宣言で選んだ種類だけ」に改める。

- **登録**: 本人確認の登録簿（`verification.go`）に (`chat`, `relayed`) の行を置く。この組はすべての操作を受ける。不可逆操作の種類の絞りと、反映の承認を含む完了の承認の絞りは、登録簿の外の core の検査で行う（経路が `chat` のとき、宣言 `chat_approvable_operations` の一覧を読んで判定する）。
- **記録**: 記録の「発言」には、その会話の最後のオーナーの発言の文面に、その返事の中で答えた問いの回答（問いの文と答え。答えた順）をつなげたものを core が入れる。「承認する」を選んだ答えのように、問いの回答も承認の根拠になりうるためである。欄の実行エンジンの環境の印は、会話の識別（`FLYWHEEL_CHAT_SESSION`）だけにする（プロセスを会話の間残すので、環境は起動のときに決まり、発言ごとに変えられない）。欄から起動された flywheel のコマンドは、この印をそのまま core へ渡す。`Verify` は印が空でないことだけを見る。操作を行う core の処理が、同じトランザクションの中で印の検査（印の会話が開いている・その会話の最後のオーナーの発言への返事が進行中である）を行い、発言と問いの回答をストアから引いて、記録の「発言」と「会話の識別」を埋める。CLI はストアを開かず、承認の記録も組み立てない。
- **欄から起こせること**: flywheel の側では、欄から起こせるコマンドを一覧で絞らない。印があるときは、印の検査・経路 `chat` での記録・不可逆操作の種類の絞りをかける。委譲の子の印（`FLYWHEEL_DELEGATED_RUN`）の検査を先に行い、子が欄の印を足しても断る。
- **印の検査だけをかけるコマンド**: 本人確認を通らない記録のコマンド（フォローアップを済みにする・課題を作る・取り込み元を指定した取り込み）は、印の検査だけをかけ、経路は渡さない（経路 `chat` で記録するのは、本人確認を通る操作だけ）。
- **許可の正本は Claude Code の設定のファイル**（2026-11-24 オーナー。flywheel#1266 の決定 5）: flywheel は、道具の許可の仕組みを自前で持たない。欄の実行エンジンは、利用者の設定（ホームの `~/.claude/settings.json`）とワークスペースの設定（`.claude/settings.json`）を、ターミナルの Claude Code と同じに読む形で起動する（設定の出どころを空にする指定・許す道具と禁じる道具の指定・すべて許す指定を付けない）。設定で許した操作は尋ねずに進み、それ以外は、次の許可の確認として画面へ届く。
- **許可の確認と問いは、画面で受ける**: 欄の実行エンジンは、許可の確認と選択肢の問い（AskUserQuestion）をサーバへ渡す指定で起動する。サーバは、届いた確認を、進行中の返事に結び付いた「確認」としてストアに記録し、画面のボタンの答えを待つ。許可の確認には、道具の名前と対象の全文（シェルのコマンドならコマンドの全文。切らない）を出し、「許可する」か「断る」（理由の文は任意）で答える。問いは、選択肢を選ぶか、文で答える。答えは、答えを待っている確認の識別へ 1 回だけ受ける（core が書き込みの中で確かめる）。「許可する」はその 1 回だけを許し、設定のファイルへ許可を書き足す答え（以後も許す）は返さない。答えは、先に実行エンジンへ送り、送れたらストアに記録する（送れなければ、確認は「答えられなかった」になる）。答えはストアに残り、後から見分けられる。口の守りは、画面のほかの口と同じである（`127.0.0.1` だけで待ち受ける・Host と Origin の検査・書き込みは CSRF の値）。サーバに遠隔の口（M4 の S5）を足すときも、対話の欄の口は同じマシンからの接続だけで受ける。

#### 受け入れた危険

サーバは要求の送り手を見分けない。同じマシンのプロセス（委譲の子を含む）は、画面の HTML から CSRF の値を取って、欄へ文を送り、許可の確認に「許可する」と答えられる。欄の文が「承認します」なら、オーケストレーターは承認を記録しうる。さらに、許可のボタンで任意のコマンドを許せるので、欄の実行エンジンは、印を外したシェルで、ターミナルの対話の記録の形（`--relayed`）で承認を記録できる。欄から承認できる不可逆操作の種類の絞り（宣言 `chat_approvable_operations`）も壁にならない。つまり、**欄を通して、オーナーの権限で何でも起こせる**。これは、ターミナルの Claude Code で許可を出して使うときと同じ危険で、すべてのワークスペースが負う。守りは、エージェントが手順を守ることに頼る。

歯止めは次の 4 つで、どれも壁ではない。

- (a) 許可の確認にコマンドの全文を出し（切らない）、オーナーが何を許すかを見て決められる。
- (b) 指示文で手順を守るように求める。
- (c) 承認が記録に残り、経路で後から見分けられる。ただし、印を外して記録した承認は、経路がターミナルの対話の記録と同じになる。
- (d) 委譲の子にだけ、起動の引数でマージと push を禁じる柵（flywheel#1282。対話の欄の作り替えの範囲外で、別に入れる）。

送り手を見分ける仕組み（パスキーなど。D18 で外した）は足さない。

残る危うさがほかに 2 つある。第 1 に、印は環境変数なので、同じマシンのプロセスは自分で付けられる（印の検査は、返事が進行中の間だけ通る）。返事が許可の確認や問いで長く待つ間も通る。サーバが落ちて進行中の返事の行が残っている間も通りうる（次の起動で「止めた」に直す）。第 2 に、プロセスが返事をまたいで残るので、前の返事で裏で始めたコマンドやサブエージェントが、後の返事の進行中に印の検査を通り、後の返事の発言を根拠に承認を記録しうる（検査は、コマンドがどの返事から始まったかを見分けない）。

### 画面のボタンの回答の限り（経路 `ui`。区切り S4d-2）

画面のボタンで保留に答える口（`POST …/challenges/{id}/holds/{hold}/answer`）は、経路 `ui` で次の範囲だけを受ける。判定は core が行い、サーバと画面は写すだけにする。

- **選択肢だけ**: 保留が持つ選択肢の識別で答える回答だけ。文で書く回答と、選択肢に添え書きをつけた回答は受けない。選択肢を持たない保留・ボタンで選べない選択肢は断る。
- **作り直しなし**: 計画を作り直す回答（`--replan`）と、予算の上限が上がる選択は受けない。範囲や完了条件が変わる回答は、対話（か端末）で伝える。
- **足す依頼の「足す」「計画を作り直す」を受けない**: 上限を超える足す依頼の問い（選択肢 `add`・`skip`・`replan`）のうち、ボタンで受けるのは「足さずに進める」（`skip`）だけ。「足す」は上限を超えるタスクを足すことで、「計画を作り直す」は作り直しなので、対話（か端末）で伝える。
- **読んだ内容の照合**: 要求は、読んだときの問いと選択肢の照合の値を添える。問いか選択肢が変わっていた・保留が閉じていたときは断り、画面に読み直させる。
- 差し戻し・取り下げ・予算の増額・フォローアップをタスクに上げることも、ボタンでは受けない（対話か端末）。

画面がボタンを出すために読む保留の値（照合の値・選択肢ごとの「ボタンで選べるか」）は、課題の詳細・`questions` の保留と、サーバの `status` の口の `needs_human.holds[]` に置く。`needs_human.holds[]` は、あなたの番の課題（`needs_human.challenges`）の、開いている保留だけを載せ、ターミナルの `status --json` には出さない（2026-11-23 のオーナーの決定）。

フォローアップを捨てる口（`POST …/followups/drop`）は、捨てる理由を添えて受ける。捨てるは本人確認を通す操作（§21 の冒頭の区切り S2b）だが、画面のボタンの範囲として経路 `ui` で受ける。

#### 受け入れた危険（画面のボタンを広げたこと）

サーバは要求の送り手を見分けない。同じマシンのプロセス（委譲の子を含む）は、画面の HTML から CSRF の値を取って、Host と Origin の検査を通る要求を送れる。広げた口で、そのプロセスは次のことができる: 選択肢を選んで保留に答える・フォローアップを捨てる・取り込みで課題を作ってサイクルを始める・走っているサイクルを止める（フォローアップを済みにするも同じ。済みにするは本人確認を要らない）。小さくする守りは 3 つ。(1) 受ける回答を選択肢だけにし、予算の増額・取り下げ・計画の作り直しと、選択肢の文から起こす承認は経路 `ui` で受けない（計画の承認と、反映を保留にした完了の承認は、いままでどおり受ける）。(2) 書き込む前に、読んだ問いと選択肢の照合の値が同じであることを core が確かめる。(3) 記録に経路 `ui` が残り、後から見分けられる。送り手を見分ける仕組みは足さない（D18）。残る危うさは 2 つ。委譲先やスーパーバイザーが作った選択肢は自由な文なので、選んだ先で範囲や費用に触れる中身でも core は見分けない。また、どの操作も予算の上限・範囲・反映先を直接は変えない（捨てたフォローアップは記録が残り、消えない）。

### 経路と本人確認の方式は後から足せる作りにする（D15 からの入力）

モバイルから UI を使う要件（D15）により、「承認するのは同じマシンのブラウザか端末」という前提はいずれ崩れる。将来、端末の外から届く経路（例: パスキー〔WebAuthn〕で本人確認するブラウザ経路）を足すときに core を作り直さないよう、**core の承認は「経路（channel）」と「本人確認の方式」を差し替えられる作りにする**。core は、許可した経路と本人確認の方式の組み合わせだけを受け付け、どの組み合わせで承認されたかを作業ログに残す。M1 で許可する組み合わせは「CLI ＋ 端末（TTY）での対話的な確認」の 1 つだけである。

どの経路を、どの段階で、どこまで（閲覧・通知・承認）開くかは、M4 の機能仕様で決めた（2026-10-09。2026-10-12 改訂。D18・[M4 の機能仕様](features/m4-ui-server.md) M4H4・M4H5・M4H20・M4H21）。登録簿には `(ui, none)` と `(cli, relayed)` を足し、組ごとに受けられる承認の範囲を持たせる。端末の外からは、私設ネットワークの逆プロキシから転送される別ポートの待ち受けで閲覧と通知を開く（サインインの方式と承認のボタンを開くかは M4 の S5 の着手時に決め直す）。本番に届く承認は本システムで最も守るべき操作であり、安易に広げない。

選択肢で答える操作（`flywheel answer --option`。2026-11-22 の設計の見直しの区切り S4b-1 で足した）は、保留への回答の一形態であり、**回答と同じ種類の操作として、回答と同じ本人確認を通る**（端末での本人確認、または対話で受けた記録 `relayed`。対話の欄の経路も回答と同じ扱い）。経路と本人確認の方式の組の登録簿は変えない。core が見るのは選ばれた識別から解決した見出し（回答の文）だけで、選択肢の文から承認・予算の増額・取り下げを起こさない。画面のボタンで選択肢に答える口は、区切り S4d-2 で足した（下の「画面のボタンの回答の限り」）。

### 対話での承認（AI への指示による承認）を一度外し、戻した理由

当初は「対話で『承認して』と指示すると Claude が承認コマンドを実行する」経路を残す想定だった。しかしこの経路を残すと、承認コマンドが Claude から呼べることになり、**自走中の Claude が自分の計画を自分で承認できる**経路が開く。塞ぐには「自走セッションへ deny の権限設定を渡す」「自走文脈を示す環境変数を検査する」といった仕組みが要るが、いずれも回避可能で、完全にはならない。さらに対話セッションでは、承認が本当に人間の指示によるものかを区別する根拠が会話の中にしか無い。そこで 2026-09-20 に、承認を人間の直接操作に限り、経路を持たないことで解決した。

2026-10-12 に、M4 の UX モックを触ったオーナーの判断でこの経路を戻した（D5 の改訂・[M4 の機能仕様](features/m4-ui-server.md) M4H21）。2 つの理由には次のように答える。

- 自走中の Claude の自己承認: 新しい構成では、1 周を進めるのは core であり、LLM のセッションではない。LLM は判断点の呼び出し（`--allowedTools Read Grep Glob` だけで Bash を持たない）と委譲の子（`--disallowedTools Bash(flywheel:*)` と、委譲の目印 `FLYWHEEL_DELEGATED_RUN` のある環境で `flywheel` の全コマンドを拒否する規則）にしか現れない。`flywheel` を実行できる LLM は、オーナーが対話しているセッションだけになる。2026-09-20 に退けた「回避可能な deny」は、自走の担い手が LLM のセッションだった旧構成で唯一の歯止めになる前提の話で、新しい構成では自走の担い手から `relayed` の口までの経路そのものが無い（UI のボタンの口には委譲の子からも `curl` で届きうるが、受けるのは計画の承認と本番反映を保留した完了の承認だけである）。
- 承認が人間の指示である根拠: 対話で受けた承認は、本人確認の方式を `relayed` として端末・UI の承認と区別し、会話の識別（サイクル名かセッションの ID）とオーナーの発言の要旨を必須で記録に残す。根拠が会話にあることは変わらないが、記録から会話へ辿れる。

予算の増額も同じ口で受ける（[M4 の機能仕様](features/m4-ui-server.md) M4H28）。対話中の LLM は委譲の予算を上げられるようになるが、自走中の LLM（判断点と委譲の子）は `flywheel` を実行できないので、自分の予算を上げる経路は無い。

既知の限界として、対話のセッションの LLM がオーナーの指示なしに承認や予算の増額を記録することは防げず、会話の手がかりも LLM が書く。これは旧 Tom の「対話で承認（サイクル名）」の運用と同じ水準であり、防ぐのではなく、記録から後で見つける。

### Claude から実行できないことの担保

- CLI の承認は、**端末（TTY）が接続されていなければ拒否**し、接続されていれば対象の要約を表示して確認の入力を求める。Claude Code の Bash 実行には端末が接続されないため、Claude は確認に答えられない。補助として、環境変数 `CLAUDECODE` が設定されていれば拒否する（2026-09-21 オーナー決定。回避できるため根拠にはしない。人間が Claude Code の `!` から承認することもできなくなる）。
- server の承認 API は、計画の承認と、本番反映を保留した完了の承認だけを受ける（範囲は core が強制する）【決定 2026-10-12 オーナー＝D18】。ボタンだけで成立し、Claude が通常の道具立て（ブラウザの操作・`curl`）で到達できることは受け入れる。到達しても本番には届かない。2026-10-09 の版は操作のたびのパスキーの署名を求めたが、普通の開発の承認で毎回生体確認を求めるのは過剰だとして改めた（その前の「server の起動時のトークン」案は、Claude がトークンを読めるため 2026-10-09 に退けている）。
- 対話で受けた承認（`relayed`）は、委譲の子と判断点の呼び出しからは実行できない（上の「戻した理由」）。対話のセッションの LLM が記録すること自体は防がず、方式と会話の手がかりを記録に残す。
- 補助として、invoker が起動する Claude セッションには承認コマンドの実行を deny する権限設定を渡す（委譲の子の `Bash(flywheel:*)`）。
- 承認の `actor`・`channel`・`verification` は作業ログに必ず残る。

同じマシン・同じユーザーで動くプロセスによる意図的な回避（疑似端末の作成など）までは防げない。ここで防ぐのは、**Claude が通常の道具立てで本番に届く承認に到達してしまうこと**である。本番に届く承認は、端末の `tty_confirm` か、オーナーが対話しているセッションの `relayed` でしか成立しない。

### 対話セッションでの体験

対話で Claude は、承認待ちの一覧と各課題の要約を示し、オーナーが対話で伝えた承認・差し戻し・回答・予算の増額を `--relayed` で記録する（M4 の S3 から。2026-10-12 改訂）。記録には会話の識別とオーナーの発言の要旨を必ず添える。オーナーの指示の無い承認を記録してはならない。UI のボタンと端末の `flywheel approve <id>` も引き続き使える。

UI サーバが落ちていても、端末の CLI で承認できる（P6 を保つ）。

## 10. 接続ツールとの契約（D7・D8）

> **フローの移植の区切り S1 で実装済み（2026-11-24 の決定。D7 の改訂・D35）**: 宣言に、4 つ目の形「組み込みのフロー」（`form: flow`）を足した。flywheel が、フローの定義と進める仕組み（claude-harness の runtime から写したもの。`internal/flow/`）を自分で持ち、core が自分の実行ファイルの `flywheel flow start|status|resume|cancel` を契約のコマンドとして組み立て、`cli` の形と同じ起動の口で呼ぶ。`flow` の形の `commands` は書けず、反映の依頼の口は宣言に書かなくても持つ。操作ごとに進めるフローの名前（S1 は `ticket`）を `flow` に書き、`permission_mode` を `--permission-mode` で進める側へ渡す（S1 は、`models`〔フロー名 → 変数 → 値〕も `--model <変数>=<値>` で渡したが、S2 で外した。下の注記）。契約（版 1 のまま）に、任意の欄 `flow`（フローの名前）と `steps`（ステップの一覧。形が合わなければ全体を「無い」として扱う）を足した。既存の 3 つの形（`plugin`・`cli`・`brief`）と、これらの欄を返さない外部の委譲先は、変えない。詳細: [features/flow-port.md](features/flow-port.md)・契約の欄は [M3 の機能仕様](features/m3-invoker-delegation.md)の契約の節。

> **フローの移植の区切り S2 で実装済み（2026-11-24 の決定）— 操作の `flow` に書ける値**: `flow` の形の委譲先の操作の `flow` に書ける値は、`ticket`（標準の実装フロー）と `ticket-light`（簡略なフロー）。計画を作る判断点（J2）がタスクごとに操作を選び、理由をタスクの `flow_reason` に書く。計画の承認で認めた操作のフロー（`planned_flow`）を記録し、委譲はそのフローで始める（承認の後に宣言の操作の `flow` を書き換えても変えない。フローを選ぶ前に承認したタスクは、そのときの宣言の操作の `flow` で始める）。承認したフローがあるのに、いまの委譲先が `flow` の形でなければ、起動せずオーナーへの保留にする。1 つの委譲先に、フローの違う操作を並べて書ける。

> **フローの移植の区切り S2 で実装済み（2026-11-24 の決定）— `models` を外した**: モデル・effort・Codex のレビューを使うかは、フローの定義（埋め込んだ YAML と指示文）に書いて固定し、委譲先の宣言では差し替えない。S1 で入れた宣言の `models` と `flywheel flow start` の `--model` は外した（どちらも誤りになる。宣言は設定の誤り、`--model` は使い方の誤り）。フローの定義の中の変数 `models`・`efforts` は残す（最上位の `efforts` の値は `low`・`medium`・`high`・`xhigh`・`max` の 5 つで、ステップは `$efforts.<名前>` で指し、指せるのは `llm` のステップだけ）。標準のフロー `ticket` の実装のステップは、Codex のレビューを `/self-review` と並べて走らせる（Codex の費用は flywheel の費用・予算に数えない。Codex が使えなくても止めない）。変えたいときは、値を差し替えずにフローを使い分ける。契約（版 1 のまま）の `steps` の要素には、任意の欄 `effort` を足した。

> **2026-11-17 の設計の見直しで改める（未実装）**: 委譲先に頼むことを「タスクの実行」と「課題を反映先へ上げる」の 2 種類にし、どちらも頼んだら終わりまで委譲先が進める（D24）。渡すのは背景と指定のタスク（D25）。宣言に、作業ツリーの持ち主を足す案は、S3a では足さなかった（§21.3）。

> **core の見直し（§17 の段 2）の区切り S1「外す」で実装済み（2026-11-17）**: 接続ツールの契約の「コンフリクトの予測」の口を外した（D29）。宣言の `conflict_prediction` は removed として止まる。参照: [features/core-redesign.md](features/core-redesign.md)。

> **core の見直しの区切り S3a で実装済み**: 契約（版 1 のまま）に、差し込み `{task_file}`・`{task_id}`・`{uses_integration}`（`start`）・`{approved_ref}`（`resume`）・`{artifact_ref}`（`reflect`）、反映の依頼を始める `commands.reflect`、レビュー待ちの選択肢 `land`、成果物の `role`、出力の `facts`（宣言の `required_facts` で必須にできる）を足した。flywheel は `ready` を返さなくなり、反映の実行は委譲先へ移った。詳細: [features/core-redesign.md](features/core-redesign.md)・[M3 の機能仕様](features/m3-invoker-delegation.md)。

core は接続ツールを知らない。エージェントごとの**宣言**が、何をどう呼ぶかを持つ。現行の `positions/<domain>.md` §5 がこの役割を担っているが、スラッシュコマンドで書く前提になっており、CLI 形態の接続ツールを表現できない（claude-flywheel#95）。

宣言に持たせるもの【仮定】:

| 項目 | 内容 |
|---|---|
| 形態 | `plugin`（Claude Code のスキルとして呼ぶ）／ `cli`（外部コマンドとして呼ぶ）／ `brief`（接続ツールなし。ブリーフを直接渡す）／ `flow`（組み込みのフロー。flywheel 自身のバイナリを契約のコマンドとして呼ぶ。**実装済み**） |
| 呼び出し方 | 形態ごとの起動形。`cli` なら開始・状態確認・承認・再開・中止のコマンド |
| 対話前提の操作 | 成果物の中身を意思決定者との対話で確定させる操作と、その対話相手（親 / 人間） |
| 子に決定を委ねてよい操作 | 「何を作るか」が確定済みで、「どう作るか」だけを担う操作 |
| 人間へ上げる問いの種類 | 親も代わりに決めない問い |
| 束ね | 1 回の委譲で複数課題を受け取れるか |
| コンフリクトの予測 | 同じリポジトリの複数課題のコンフリクトを予測する読み取り専用の口（あれば）。予測だけを返し、並列にするかは flywheel が決める（§11） |

形態が `cli` または `flow` のとき core が扱う情報は、実行 ID・汎用の状態・要約・人間に求める操作・成果物の参照・中止と再開に必要な情報、に限る。接続ツール内部の手順や判断値は core に持ち込まない（claude-harness#201 最終決定 §3 と整合）。

宣言は散文ではなく**構造化された設定**として持ち、core が読み込み時に検証する。ミッションや守備範囲のような、LLM が読む部分は Markdown に残す。

## 11. 実行環境（スロット）

> **2026-11-17 の設計の見直しで改める（未実装）**: スロットは「同時に走らせる数の席」として flywheel が数え続ける。作業ツリーは、委譲先のフローを通る委譲では委譲先が作って片付ける（D24）。形は §21.3・§21.7。

> **core の見直し（§17 の段 2）の区切り S1「外す」で実装済み（2026-11-17）**: コンフリクトの予測の口の呼び出し・直列化グループ・`challenge_conflict` を外した（D29）。課題どうしを直列にするかは、記録した前提・同時に走らせる数の上限・スロットの空きだけで決める。オーナーの回答待ちの契約の実行は、同時に走らせる数に数えない（D33 の一部）。参照: [features/core-redesign.md](features/core-redesign.md)。

旧 claude-flywheel は repo あたり作業用クローンが 1 本で、同一 repo の課題を並列に走らせられなかった（flywheel#73 の観測: 互いに独立な 3 件が直列に並び、仕様 → 実装の流れを律速した）。core が**実行スロット**を払い出す（claude-flywheel#154 の要件を取り込み、flywheel#73 で具体化した【決定 2026-10-01】）。詳細は [M3 の機能仕様](features/m3-invoker-delegation.md) §実行スロット・§クリティカル設計決定 7。

- **複数課題の並列実行は flywheel の責務**。接続ツール（claude-harness）は並列度・直列化・fan-out を持たない（claude-harness#201）。
- **1 スロット 1 セッション**（作業ツリー 1 本につき子 1 つ）は守る。やめるのは「リポジトリあたりスロット 1 本」の運用である。
- プロバイダは `clone`（既存の作業用クローン）／ `worktree` ／ `container` を宣言でリポジトリごとに選ぶ。**`clone` と `worktree` は M3 S2、`container` は S4**。
- **払い出しは直列、使用は並列。** `git worktree add` は共有 `.git` を触るため並列に実行しない。払い出したスロットは使い回す。
- worktree の `.git` は書き換え可能なポインタファイルである。外側から git を実行するときは `GIT_DIR` / `GIT_WORK_TREE` を明示し、割り当ての前にポインタを検査する（claude-harness#200 の実測）。
- worktree は同一ファイルシステムのため、ビルド成果物・`node_modules`・ポートが衝突しうる。S2 では flywheel が手当てせず、そのリポジトリを `clone` か 1 本にする宣言で避ける。隔離が要るものは container（S4）。
- **同じリポジトリで並列にしてよいかは、委譲の前に接続ツールのコンフリクトの予測の口（claude-harness `harness predict-conflicts`・claude-harness#288）を問い、その予測から flywheel が組ごとの直列化グループを作って決める**。接続ツールは予測だけを返し、決定は flywheel が持つ。予測が得られないものは直列にする。
- 接続ツールは flywheel が払い出した作業ツリーを受け取って使う（claude-harness の `harness run ticket` は渡された作業ツリーを `provided` として受け、消さない）。§10 の宣言で「スロットを接続ツールに任せる」選択肢（`slot_owner: connector`）は M3 S2 では持たず、持つかは M3 S3 の分解時に決める（M3 仕様 M3P37）。

### クラウドのセッション（#382 の結論。2026-11-01）

委譲の子を Claude のクラウドのセッションで動かせるかを、Claude Code `2.1.316` で実物と資料で確かめた。手順・観測・確証のレベルは [調査メモ](cloud-session-delegation-investigation.md) にある。確かめた事実の要点: 新しいセッションは `claude --cloud` の対話の起動でしか作れず（`-p` と併用できない）、セッション ID はサーバが振る。続きの文は `claude -p "<文>" --cloud <ID>` で送れて文脈が残るが、応答は `{ok, session_id, url}` だけで、結果は claude.ai の events を読む。`--max-budget-usd` は受け付けられるが効かず、費用の値はどこにも返らない。既定の権限モードでは権限の確認で止まり、無人では `--permission-mode auto` が要る。リポジトリの `CLAUDE.md`・`.claude/settings.json`（`env`・拒否の規則）・`.mcp.json` は効く。push・PR は、このリポジトリへの GitHub の接続が無効なため確かめられていない（未確証）。GitHub の接続（Claude GitHub App の承認か `/web-setup`）をして push と PR を確かめるのは、クラウドの実装の予定が立つまで行わず、前提条件として残す【決定 2026-11-02 オーナー】。

- **① 持ち方: クラウドのセッションはスロットのプロバイダにしない。持つときは §10 の `cli` 形態と同じ契約（実行 ID・汎用の状態・要約・成果物の参照・中止と再開に必要な情報）の「実行先」として持つ。** スロットは「flywheel が検査できる手元の作業ツリー」を前提にしている（割り当て前の未コミットの変更とリモートの検査・照合での現在のブランチの読み取り・`GIT_DIR` の明示）。クラウドの作業ツリーは VM の中にあって flywheel から見えず、1 スロット 1 セッションの規律も手元の本数では数えられないため、スロットの規則に当てはまらない。**いまは実装しない**: 無人の起動の口が無い（対話の起動だけ）・1 起動の予算の打ち切りが効かない・push と PR が未確証で、委譲の前提の 3 つが揃っていないため。
- **② 照合・再開・予算の規律のうちクラウドで変わるもの**（持つと決めたときの前提）:
  - セッション ID: 事前に決められない。起動の後に返った ID を run に記録し、`session_id_mismatch` の検査は意味を持たない。
  - 結果: `--output-format json`・`--json-schema` の返り値が無い。報告は events の最後の応答を指示文で決めた JSON として読み、読めなければ `malformed` と同じ扱いにする。
  - 再開: `--resume` の代わりに `-p --cloud <ID>` で文を送る。送った時点では終わりを待てないため、状態は events を読み直して判定する（pid・host・heartbeat による中断の回収は使えない）。
  - 予算: 1 起動の打ち切り（`--max-budget-usd`）が効かず、費用も返らない。M3 仕様 §費用の記録の「渡した上限額を費用とし出所を `unknown`」は額の根拠を失うため、USD の枠では守れない（下の ④）。
  - 照合: 子の報告に依らずリモートのブランチと PR を `gh` で読む規律はそのまま使える。スロットの作業ツリーの検査は無くなる。
  - 権限: 無人では `--permission-mode auto` を必須にする。既定の権限モードでは確認待ちのまま止まり、続きの文を送っても解けない。
- **③ どの委譲をクラウドへ出すかの宣言は、リポジトリごととする。** GitHub への接続・`.mcp.json`・環境の変数と network secrets（資格情報の単位）・ネットワークの許可リストが、どれもリポジトリと環境の単位で決まるため。ポジションごとは #381 の範囲の決め方とあわせて決めるもので、ここでは持たない。課題のサイズごとは、サイズを機械的に測る根拠が無く、費用の上限も効かないため持たない。
- **④ 費用は周の USD の予算に入れない。** クラウドのセッションはプランの利用上限に数えられ（資料だけ）、1 起動ごとの額は取れない（実物で確証）。持つときは USD の枠の代わりに起動の回数の上限で数え、レート制限は手元の `claude` と共有するため M3 仕様 §枠超過の扱いをそのまま当てる。USD の枠で天井を守る委譲（費用の上限が要る課題）は、手元の `claude -p` に残す。
- コンテナ（M3 S4）との関係（片方だけにするか、両方を持つか）は、#381 と一緒に別の課題で決める。

### 12.3 解禁される操作と、5 つの迷いへの対応

書き込み経路が core に一本化されるため、board で「段階を分けてスコープ外」とされていた操作を解禁できる: 承認、差し戻し、優先度の並べ替え、課題の新規起票、人間記入欄の編集、保留中の問いへの回答。M4 の UI がこのうち受けるのは、計画と完了の承認（本番反映は保留）と 1 周の手動の起動だけにした。起票と優先度は AI が行い、差し戻しと回答は対話で伝えて LLM が記録する（2026-10-12。[M4 の機能仕様](features/m4-ui-server.md) M4H19〜M4H22）。

| 運用者の迷い（§1.2） | 設計上の対応 |
|---|---|
| 1. サイクルを回すのか、対話で指示するのか | UI が「いま人間の操作を待っているもの」と「システムが次に進められるもの」を分けて示す。サイクルの仕事を細かい操作へ分解する（§7） |
| 2. 承認はいつ・どこで行うのか | 承認待ちを UI のボードの上の人間待ちの帯に集約する。承認した瞬間に core が状態を進める（次のサイクルを待たない） |
| 3. サイクルの終わりと仕事の終わりがずれる | 課題単位で「外部で待っているもの（PR のレビュー、CI、昇格マージの承認）」を状態として持ち、表示する（CI は flywheel が待つ状態ではなく、取ってきた事実として読む。M3P48・M45H38。コードの変更は #547 の後） |
| 4. 1 セッションで何周回してよいか | 構造的に消える（§7） |
| 5. 定期実行と都度実行のどちらが標準か | どちらでも同じコマンドが走る。heartbeat の意味が変わらないよう、core が実行の契機を作業ログに残す。定期実行は要件にせず、都度実行（CLI・UI の手動の起動）を標準とする（D17） |

### 12.4 UI の形とモバイル（D15・D16）

- **UI はブラウザ UI で始める**（D16）。「API を呼ぶ React」として作り、後からデスクトップ・モバイルアプリで包む場合にもコードをほぼそのまま使えるようにする。画面幅の狭い端末でも使える作りにする。
- 2026-09-21 時点で、ブラウザでは対応できない中核機能は見つかっていない。状態の閲覧・承認・起票・並べ替えは通常の Web 画面で足り、モバイルへの通知は Web の通知機能で届く（iOS はホーム画面へ追加した場合に限る）。本人確認にはパスキー（WebAuthn）がブラウザ・モバイルの両方で使える（UI の承認には 2026-10-12 に使わないと決めた＝D18。遠隔のサインインに使うかは M4 の S5 で決め直す）。ブラウザでできないのはメニューバー常駐・OS 全体のショートカット・手元のエディタやターミナルの直接起動で、いずれも中核ではない。

モバイルから使うなら、形に関係なく次を設計で決める。いずれも M4 の機能仕様で決めた（2026-10-09。[M4 の機能仕様](features/m4-ui-server.md) M4H1・M4H4〜M4H6。本人確認は D18）。

1. **HTTPS が必須になる。** 通知もパスキーも暗号化された接続（secure context）でしか動かない。同じマシンからの接続は例外だが、スマートフォンからは必要になる。
2. **端末の外から届く経路と本人確認。** 起草時の候補は、私設ネットワーク（VPN 型）経由にして server をインターネットへ直接さらさない案と、まず閲覧と通知だけを開き、承認は本人確認を入れてから開く段階の案だった。M4 の機能仕様で次のとおり決めた（2026-10-09 オーナー）: 私設ネットワークの逆プロキシが HTTPS で受け、別ポートで `127.0.0.1` に待ち受ける遠隔の口へ転送する。本人確認は操作のたびのパスキー（2026-10-09 の D18）で、手元でも同じなので、閲覧・通知・承認を S5 で同時に開く。S5 は M5 の後へ送った（D19）。2026-10-12 に D18 を改めて UI の承認からパスキーを外したため、遠隔のサインインの方式と、遠隔で承認のボタンを開くかは S5 の着手時に決め直す。
3. **埋め込みターミナルを端末の外へ開くか。** ネットワーク越しのターミナルは実質的に遠隔シェルであり、承認より危険な口になる。**既定は「同じマシンからの接続に限る」**とする。
   - **埋め込みターミナルは作らない（2026-11-24 オーナー。flywheel#1266 の決定 2）。** モバイルからの経路と埋め込みターミナルを M5 の後へ送った決定（D19）のうち、**埋め込みターミナルの部分を、この決定で置き換える**。モバイルからの経路を M5 の後へ送る部分は変えない。長い対話は、画面の対話の欄（チャットの見た目）で行う（[対話の欄の作り替え](features/chat-session.md)）。「同じマシンからの接続に限る」は、ターミナルの代わりになる対話の欄に当てる（§9）。
4. **モバイルのブラウザは裏へ回ると止まる。** 画面を閉じている間の変化はライブ更新では届かないため、通知で補う。

## 13. 外部連携（adapters）

> **2026-11-17 の設計の見直しで改める（未実装）**: 取り込み元に親子の関係（sub-issue）があれば、親を課題にし、子はそのタスクとして取り込む（D22。§21.1）。親の無い取り込み元は、いまと同じく独立した課題にする。外部へ書き戻さない点は変えない。

- 最初の対象は、現行 `ingest-challenges` の置き換えである **GitHub Issue の取り込み**。assignee によるフィルタ、fingerprint による冪等な更新、取り込み解除を引き継ぐ。**LLM を介さない最初の実例**になる。
- **上流の close を取り込む**（claude-flywheel#140）。`source_binding.upstream_state` に保持し、core が課題の状態との食い違いを検出する。
- 書き戻し（flywheel 側の状態を外部へ反映する）は、現行は「外部へは書き戻さない」方針である。UI からの状態変更と外部連携を射程に入れるなら見直しの対象になる（§16）。
- adapter は差し替え可能な単位とし、core の語彙（課題・状態・対応）だけに依存させる。
- M2 の機能仕様: [docs/features/m2-github-issue-ingest.md](features/m2-github-issue-ingest.md)（取り込み元の宣言・`source_binding`・fingerprint・上流の close の表し方・書き戻しの可否。2026-09-24 決定）。

## 14. Claude Code との接点

> **2026-11-17 の設計の見直しで改める（未実装）**: オーケストレーターがオーナーの指示でフォローアップをタスクに上げる・済みにする・捨てる操作が増える（D22）。上げる操作は、対話で受けた承認と同じ形（会話の識別と、オーナーの発言の要旨）で記録する。オーケストレーターのエージェントを「オーケストレーター」と呼び、core の「いま進められること」の一覧を読んで提案する役目を足す（D34。§21.4）。

対話で指示する体験は残す。承認・差し戻し・回答・予算の増額は、オーナーが対話で伝えたものを LLM が `--relayed` で記録する（2026-10-12 改訂。§9）。オーナーの指示の無い承認は記録しない。プラグインは薄い入口として残し、各スキルは「いつ CLI を呼ぶか」「結果をどう人間に伝えるか」だけを持つ。状態を直接読み書きする手順は持たせない。

プラグインの同梱スクリプトが権限の allowlist で覆えない問題（claude-flywheel#139）は、CLI が PATH 上のコマンドになることで解消する。`flywheel` という先頭トークンは allowlist のパターンとして書ける。

## 15. 技術スタックとリポジトリ構成

言語の分け方は【決定 2026-09-21】（D14）。表のうち言語以外の個別の道具と、ディレクトリ構成は【仮定】である。

| 層 | 選択 | 理由 |
|---|---|---|
| 言語（バックエンド） | **Go**【決定】（core・CLI・server・invoker・adapters） | 配布がバイナリ 1 つになり、UI のビルド結果もバイナリへ埋め込める（Node.js と依存パッケージの導入が要らない）。invoker（`claude` の起動と監視）は Go の得意分野。claude-harness の runtime と言語がそろい、知見と道具立てを 1 系統にできる（コードは共有しない） |
| 言語（UI） | **React / TypeScript**【決定】 | board の UI 資産を引き継ぐ |
| ストア | SQLite（C コンパイラ不要の Go 実装） | ファイル 1 個・常駐不要（P6）。CLI と server が同じファイルを開ける。cgo を使わずにバイナリ 1 つを保つ |
| server | Go の標準 HTTP サーバ | core を同じプロセス内のライブラリとして呼ぶ |
| UI のビルド | Vite | board で採用済み |
| API の型 | API の定義から TypeScript の型を生成する | UI と server の言語が分かれるため（D14 で受け入れた 1 手間） |
| テスト | Go 標準の `testing`（UI は Vitest） | core は実ストア（一時ディレクトリの SQLite）で検証し、ストアをモックしない |
| 整形・lint | `gofmt`・`go vet`・golangci-lint（UI は Biome） | Go の標準的な道具立て。UI は board で採用済み |

```text
go.mod                Go モジュール 1 つ（リポジトリ直下）
cmd/flywheel/         バイナリの入口（CLI・server を 1 バイナリで）
internal/
  core/               状態機械・承認・ロック・予算・スケジューリング・作業ログ
    internal/store/   ストア（SQLite）・スキーマ・マイグレーション。Go の internal 規則により core からしか import できない（P2）
  cli/                flywheel コマンド
  invoker/            Claude の呼び出し・指示文・出力スキーマ
  adapters/           外部連携（github-issue ほか）
  server/             UI 用 API（埋め込みターミナルは作らない。D19 のこの部分を置き換えた。§12.4 の 3）
web/                  ブラウザ UI（React / TypeScript）。ビルド結果をバイナリへ埋め込む
plugin/               Claude Code 用の薄いスキル
docs/
```

- **「状態を書けるのは core だけ」（P2）をディレクトリ構成で強制する。** ストアのパッケージを core の `internal/` の下に置くと、Go のコンパイラが core 以外からの import を拒否する。
- 現行の bash / ruby スクリプト（13 本・6,265 行。テストは 20 本・9,676 行。claude-flywheel 0.29.0＝`75bf13f` で計測。起草時の「テスト込みで 6,227 行・テスト 19 本」は計測条件が不明のため置き換えた）は移植の対象であり、そのまま持ち込まない。ただしテストが固定している振る舞い（冪等性、fail-closed、語彙の一致）は要件として引き継ぐ（M1 の分は [M1 の機能仕様](features/m1-core.md)）。
- **動作環境は macOS と Linux**（2026-09-21 オーナー決定。[M1 の機能仕様](features/m1-core.md) A2）。Windows は対象外。
- **この環境での Go の委譲開発は実績が無い。** claude-harness#201 の最初の実装で先に確かめる（D14 の判断材料として記録されたリスク）。

## 18. 移行方針（D6）

旧台帳からの移行を、機能（変換スクリプト）としては作らない（2026-10-25 オーナー＝claude-flywheel#99。D6 の「方向は一括移行」と、ここに書いていた「変換は専用のスクリプト 1 本で行う」を改めた）。open の課題（完了していないもの。分類済・承認待ち・保留中を含む）とその状態が引き継げれば十分で、履歴は持ち込まない。全ワークスペースを一括では移さず、Tom を先に移し、問題が出たら直しながら進め（2026-10-18 オーナー）、Tom で評価した後に他のワークスペースを同じ手順で移す（2026-10-29 オーナー）。移行は機能として開発せず、照らし合わせ・旧 ID の対応・ファイルの移動も手順と使い捨ての簡易スクリプトで行う。機能にするのは、切り替えの後も常設で要る書き出し（`flywheel export`／`import`）と、周の最後に書き出しと記憶をコミットする段だけである（2026-10-29 オーナー）。手順と受入基準は [M5 の機能仕様](features/m5-tom-migration-and-switchover.md)。

| 対象 | 規模（Tom・2026-10-29 の実測） | 移し方 |
|---|---|---|
| 課題台帳（open の課題） | 3 件（分類済 1・着手中 2。3 件とも取り込み元マーカーを持つ） | GitHub Issue 由来の課題は M2 の取り込みで入れ直し、分類・依存・保留中の問いはエージェントが手で移す。計画は J2 に作り直させ、旧側の承認は移さず、オーナーが新しい側で承認し直す |
| 課題アーカイブ | 360 件（15,799 行） | 持ち込まない。ワークスペースの `legacy/` へ移して残す。M4.5 S3 の指標は新しいストアの 0 から数える |

| journal | 182 ファイル | 持ち込まない。`legacy/` へ移して残す。新しい構成は journal を持たず（M4.5 の M45H6）、所感も新しいストアへ移さない |
| ドメイン記憶 | 226 ファイル | 変換しない。`agent.json` の `memory_dir` で置き場を指す |
| ポジション・取り込み元・関連リポジトリ・予算の設定 | 数ファイル | エージェントが宣言（`agent.json`・`connectors.json`・`sources.json`）へ書き移す。優先度の方針はモードの仕組みを持ち込まず、稼働中の判定規則をポジションへ、着手順を依存へ写す |

移す作業はエージェントが行い、照らし合わせを使い捨てのスクリプトで機械的に行う: 旧台帳の open の課題の ID・状態・優先度・依存の一覧（旧 claude-flywheel の `ledger-index.rb` の出力）と、新しい flywheel の `list --json`・`show --json` を突き合わせ、一致してから新しい側の周を回す。旧形式との並走や互換層は作らない。完了済みの履歴も移す必要が出たら（例: 指標を旧側から続けて数えたい）、そのときに改めて考える（数千行をエージェントに移させると漏れを防げないので、その場合はスクリプトのほうが向く）。

## 19. リスクと撤退条件

**最大のリスクは二重管理の長期化**である。旧システムを保守モードに置いている期間が延びるほど、旧側への修正と新側の設計がずれていく。

次のいずれかに該当したら、作り直しを中止して旧 repo の漸進的な改善へ戻ることを検討する。

- M1〜M2 を終えても、LLM コストの削減が測定できない
- 判断点への分割によって、判断の質が現行より明確に落ちる（分類の誤り、計画の劣化）
- 旧システムの保守が、保守モードの範囲（日々の運用に必要な修正）に収まらなくなる
- UI を統合しても、§1.2 の 5 つの迷いが解消しない

### 設計の見直し（2026-11-17）のリスクと撤退条件

§21 の形に改めることのリスクは次の 4 つ。数値は、Tom で安定を見る段（§17 の段 4）で測る。

| リスク | 見る数字 | 超えたときの戻し方 |
|---|---|---|
| 直列をやめてコンフリクトが増える（D29） | 反映のうち、コンフリクトで検証や承認をやり直した割合（2026-11-01〜11-16 は 128 件中 9 件） | 記録した前提を計画の判断点に積極的に書かせる。それでも減らなければ、同じ場所を触る課題の直列を戻す |
| SV が同じ手を繰り返す（D27） | 同じ止まり方に対する SV の手の回数 | 2 回までの上限は core が強制する。繰り返しが多い止まり方は、LLM なしの決まりとして core に取り込む |
| 長いサイクルの費用と中断（D26） | 1 サイクルの費用と、中断の後に回収できなかった実行の数 | サイクルごとの費用の上限で止める。中断した実行は、次のサイクルの最初に core が状態を読み直す |
| 委譲先の改修が遅れる（D24・D32） | claude-harness 側の口（Issue の無い入力・任意の成果物を反映先へ上げる口など）の出来具合 | 口ができるまで、いまの core の処理を残して動かす |

### 21.1 仕事の単位: 課題 ＞ タスク ＞ フォローアップ（D22）

- **課題**: 解きたいことの単位。いまの課題のまま（取り込み元の 1 件＝課題 1 件。取り込み元に親子があるときは、下の「取り込み元との関係」）。新しい層を上に足さず、課題の下に次の 2 つを足す。
- **タスク**: 委譲して成果物が出る作業の単位。課題の中で、前提と派生の線でつながるツリーになる。

  ```text
  課題 A
    仕様 ── 設計 A ──┬─ 実装 A1 ─┬─ 結合テスト
                     ├─ 実装 A2 ─┤
                     └─ 実装 A3 ─┘
  ```

  - 単発の課題は、タスク 1 個のツリーになる。
  - あるタスクの作業から後で生まれたタスク（派生）は、元のタスクにぶら下がる。次のタスクを止めないなら、前提の線は引かない。
  - 後から必要と分かったタスクは、それを決めたタスク（例: 設計 A）から新しく伸ばす。
- **フォローアップ**: 課題やタスクにぶら下がる 1 行の項目（確認ごと・軽い指摘・片付け・気づき）。状態は「未・済み・捨てた」だけで、分類・計画・承認を通さない。
  - 学びの出口（SV の振り返り。§21.5）は、課題を起票せず、フォローアップを書く。
  - タスクに上げるのは、オーナーか、オーナーの指示を受けたオーケストレーターだけ。自動では上げない。上げたものは、その課題の中の派生のタスクになる。上げる操作は、対話で受けた承認と同じ形（会話の識別と、オーナーの発言の要旨）で記録する。
  - フォローアップは、課題に属さなくてもよい。サイクル全体の振り返りが出す改善の候補（指示文の直しなど）は、課題に属さないフォローアップとして未の一覧に並び、オーナーが上げたときに課題になる（取り込み元の無い課題。いまの手で足した課題と同じ入口で扱う）。
  - 済みにするのに、1 件ずつの承認は要らない。確かめた結果を書いて済みにし、課題の完了の承認のときにまとめて見せる（承認の後に済みにしたものは、フォローアップの一覧で見える）。
- **課題の完了とフォローアップは切り離す**: 未のフォローアップが残っていても、課題は完了の承認で通常の「完了」になる。「閉じた」という別の状態と、自動で閉じる仕組みは作らない（「フォローアップが全部片付いたら課題は自動で閉じる」は、同じ日に取り下げた）。取り込み元の Issue は、フォローアップを待たずに、課題の完了（成果が反映先へ入ること）で閉じる（閉じるのは委譲先の反映の側〔開発では PR のマージ〕で、flywheel は外部へ書き戻さない。§16 の Q4 のまま）。
  - 未のフォローアップは開いたまま残し、後日まとめて整理する。そのために、未のフォローアップを課題をまたいで一覧する口（完了した課題を開くのと同じように開ける）を用意する。
  - 済みにする: タスクに上げたものは、そのタスクの完了で core が自動で済みにする。それ以外は、オーナーとオーケストレーターが、確かめた結果を書いて済みにする。
  - 捨てる: オーナーと、指示を受けたオーケストレーター。まとめて捨てる操作を用意し、オーケストレーターからも使えるようにする。
  - SV は、済みにも捨てたにもせず、印も付けない（整理が負担になったら、そのとき足す）。
- **取り込み元との関係**: Issue は入力としてだけ扱い、タスクのツリーとフォローアップは flywheel の中で完結させる（外部へ書き戻さない＝§16 の Q4 のまま）。取り込み元の側に親子の関係があれば、親の Issue を課題にし、子の Issue はそのタスクとして取り込む（claude-harness の流れ〔親の要件チケットを実装チケットに分け、統合ブランチに集め、親の受入基準で確かめる〕と同じ形）。読むのはツリーの初期値としてで、正本は flywheel。親の無い Issue は、いまと同じく独立した課題にする。計画の判断点が作る、Issue の無いタスクとも共存する。いまある課題の親子の記録（2 件）は、課題の選別（§17 の段 3）で扱う。

### 21.2 承認の単位（D23）

> **区切り S3b の注記**: 課題の単位の確かめ（J5）が「満たしていない」と判定したときは、課題を着手中へ戻して保留にする。オーナーは、計画を作り直す回答（`--replan`）で、直すタスクを足せる（済みのタスクは残る。足したタスクは計画の承認をやり直す。承認なしでタスクを足す形は S4）。

- **論点と計画を同時に出す**: 計画の判断点（J2）は、課題ごとに「方針・論点ごとの問いと推奨・完了したら見えるもの・やらないこと・タスクのツリー」を 1 回で作る（「こういう論点で、こういう計画にしました」）。オーナーは 1 回承認する。推奨と違う答えを選んだ問いがあると、計画を作り直す（オーナーに確かめる 1 件ずつは「問い」と呼ぶ。語は用語集）。計画の前に論点を問う段（D20）の目的（計画と完了で見る面をそろえる）は、論点を計画の画面に残すことで保つ。
- **計画の承認は課題ごとに 1 回**: ツリーの中のタスクは、個別の承認なしで走る。後からタスクが増えるのは、フォローアップを上げたとき（オーナーの指示）か、計画の判断点が「方針の外」と判断して問うたとき、または次の「計画の後にタスクを足す」のとき。
- **計画の後にタスクを足す**: 計画の承認で、方針・範囲・予算の上限を承認する。その内なら、計画の判断点（J2）が承認なしでタスクを足す（設計が済んでから実装のタスクを確定する課題など）。足したことは記録して知らせる。（S4c-1 で実装したのは、足したことの記録と API の値まで。区切り S4d-2 で、記録から作る知らせ〔足した件数と出どころ。決まった文〕を、画面の「いま進められること」の「最近起きたこと」と、対話の欄に出す。知らせは記録から導き、既読は持たない）（S4c-2 で実装済みなのは、フォローアップを上げたときに足す依頼を作り、上げる指示を上限の引き上げの承認として扱うことまで。上げた先のタスクが済んだときのフォローアップの済みも含む）
  - 足した後の予算の合計が承認した上限を超えるなら、必ずオーナーへ問う（core が数字で判定する）。
  - 計画に書いた「やらないこと」に触れるタスクは足せない。判断点が迷ったら、問う側に倒す。
  - 判断や人の作業が要る点（API トークンの用意など）が出たら、オーナーへ上げる。
  - 計画を 2 段にする（設計の後にもう一度承認する）形は、既定にしない。
- **完了の承認も、既定は課題ごと**: 統合先を使う課題（§21.3）では、タスクの成果を統合先に集め、最後にまとめて確かめてから、完了と反映を 1 回で承認する（D12 のまま）。統合先へ入れる関所は、人の承認ではなく完了の検証（J5）。
- **課題の単位の確かめ**: 統合先を使う課題では、全タスクが統合先に入ったら、完了の検証の判断点（J5）が、課題の完了条件で統合先の全体を確かめる。その結果と「完了したら見えるもの（実物）」を、オーナーの完了の承認に出す。委譲先の昇格前の検証の結果は、材料として読む。統合先を使わない課題（タスクが 1 個の課題など）は、タスクの検証がそのまま課題の検証になる。
- **単位は設定で変えられる**: ワークスペースの設定で、計画の承認の単位・完了の承認の単位を、課題ごとかタスクごとに選ぶ。課題ごとの設定は持たない。値は計画の承認の時点で課題に記録し、サイクルは課題に記録された値で動く（進行中の課題の進め方は、設定を変えても途中で変わらない）。
- **「タスクごと」の承認の意味**: 承認の粒度を細かくしたいという要望に応えるための設定で、必須ではない。オーケストレーターではなく、オーナーへの問いが増える形になる。意味は「統合先を使わず、タスクの成果ごとにオーナーが承認して反映先（開発では既定ブランチ）へ入れる」。core の改修（§17 の段 2）では「課題ごと」だけを作り、「タスクごと」は要るときに足す。
- 危険の小さい課題の承認を省くか（§16 の Q11）は、今回は決めない。決める時期は Q11 のとおりで、段 4 で測る承認の件数を材料に足す。

### 21.3 委譲先との境界（D24・D25・D31〜D33）

flywheel が委譲先に頼むことを 2 種類にし、どちらも「頼んだら終わりまで委譲先が進める」形にする。

> **区切り S3b の注記**: 統合先を使う課題は、タスクのリポジトリを 1 つに限る。2 つ以上にまたがる課題は、計画の検査で不正にし、すり抜けた課題は保留の理由 `tasks_blocked` で保留にする。委譲の形が `form: cli` でないタスクは起動しない（理由 `integration_unavailable`）。上げる依頼は完了の承認の前に始め、承認した中身は `land` で渡す。

| 頼むこと | flywheel が渡すもの | 委譲先がやること |
|---|---|---|
| タスクの実行 | 背景・指定のタスク・この課題が統合先を使うかどうかと、課題の識別（統合先の名前と作り方は委譲先が決め、無ければ委譲先が作る） | 作業 → 成果物 → 完了の検証（J5）の「よい」を受けて統合先へ入れる → 片付け |
| 課題を反映先へ上げる | 承認した中身（委譲先が返した識別子。開発では head のコミット） | 上げる前の検証 → 承認した中身と一致するときに反映先へ入れる（反映先が動いていたときは、下の「完了を承認した後に反映先が動いたとき」） → 統合先の片付け |

- **flywheel に残すもの**: 同時に走らせる数（スロットの数）・承認とその時点の中身の記録・結果の記録。
- **flywheel が持たなくなるもの**: マージ・ブランチ・片付け。
- **反映は、委譲先の宣言にある 1 つの操作にする**（D32）: 誰が作った成果物でも（スキルを直接呼ぶ形・指示文を直接渡す形の委譲を含む）、core は「この成果物を、この中身で反映先へ」と委譲先へ頼み、core からマージの処理を無くす。
  - 委譲先（claude-harness）に、任意の成果物（開発では PR）を受けて反映先へ上げる口が要る。口ができるまでは、いまの core の処理を残す。
  - オーケストレーターが直接作った成果物は、いまと同じく flywheel の外で、オーナーの指示を受けてオーケストレーターが反映先へ入れる。
- **完了を承認した後に反映先が動いたとき**（D31）: 反映先の最新の取り込みと反映先へ入れる操作は委譲先が行い、変わった中身の判定は core が持つ（委譲先の申告は使わない）。委譲先は、完了の検証へ出す前にも反映先の最新を取り込む。
  - 判定の材料: core は、委譲先を介さず、上流のアダプタの比較の口（開発では GitHub のコミットの比較。いまの作りと同じ）から自分で読む。開発に固有の形（マージのコミットの親など）はアダプタの側に閉じ、core が受け取るのは「取り込みだけ・コンフリクトの解消あり・関係のない変更あり・判定できない」の区別と、直した差分。D32 の「core はブランチの構成を知らない」は、統合先の作り方と成果の宛先の話で、この比較とは別。比較の口を持たない委譲先では、判定できないものとして検証と承認へ戻す。
  - やりとり: ①core が承認した中身を付けて「入れてよい」を返す。②反映先が動いていて入れられないとき、委譲先は反映先の最新を取り込み、反映先へは入れずに、新しい中身を返して待つ。③core が下の区別で判定し、通すときは新しい中身を付けてもう一度「入れてよい」を返す。④委譲先は、その中身と一致するときだけ反映先へ入れる。
  - 記録: 承認し直さずに通したときは、承認の記録に、元の承認した中身と、通した後の中身の両方を残す（いまの「取り込みだけで承認したときの検証の中身」の記録と同じ考え方）。
  - 変わった分が反映先の最新の取り込みだけで、チェックがすべて通っている → 承認し直さずに反映先へ入れる（見直し前と同じ）。
  - コンフリクトを手で直した → core が「コンフリクトを直した」と機械的に判定し、完了の検証の判断点（J5）に「承認した中身からの差分」を渡して起動する。完了条件を満たしたままで、チェックがすべて通っていれば、承認し直さずに反映先へ入れる。通したことと直した差分を記録し、オーナーへ知らせる。「問題あり」「判定できない」のときは、検証と承認へ戻す。
  - 取り込みと関係のない変更が足された → 検証と承認をやり直す（見直し前と同じ）。
  - コンフリクトの解消を、SV とオーケストレーターは確かめない（SV は承認と反映ができない決まり。対話のセッションは常には開いていない）。判断点が判定できずに止まったときだけ、SV がオーナーへ上げる。
  - 保証の文言は「反映先に入るのは、承認した中身か、それに反映先の最新の取り込みと、検証を通ったコンフリクトの解消だけを足したもの」に改める。
- **統合先**（開発では統合ブランチ）: 委譲先が作る。まとめて反映先へ入れる機能の単位で用意するのが目安（どういうときに使うかは、下のとおりリポジトリごとに違ってよい）。
- **ブランチの運びは委譲先（リポジトリごとの決まり）に任せる**（D32）: 統合先の作り方・成果の宛先は委譲先の側で決め、core はブランチの構成を知らない。core が持つのは「この課題は統合先を使うか」の記録だけで、計画の承認のときに決めて課題に記録し（計画の判断点が案を出し、オーナーが決める）、委譲先へ渡す。どういうときに使うかの目安は、リポジトリごとに違ってよい。オーナーが管理するリポジトリでの運びは次のとおりで、flywheel の決まりにはしない（会社のリポジトリなどには個別の決まりがある）。
  - タスクが複数の課題は、統合先に集める。タスクが 1 個の課題は、成果を既定ブランチ宛てにする。
  - タスクが 1 個でも、リリースの順序などで既定ブランチへ一定の期間入れられないときは、例外の処理を足さずに、統合先を使う。
  - どちらでも、完了の承認は課題ごとに 1 回。
- **タスクの実行は、成果が宛先（統合先か、反映先〔開発では既定ブランチ〕）へ入るまで待つ**（D33。見直し前と同じ形）: タスクの数で流れを分けず、例外の処理を作らない。成果の宛先が反映先のタスクでは、完了の承認を待つ間、委譲先の実行が残ることを許す。完了の承認の後、core が承認した中身を付けて「入れてよい」を返し、委譲先が反映先へ入れる。
- **反映の依頼の届け方**（D32・D33）: 反映は委譲先の宣言にある 1 つの操作で、core の扱い（承認した中身を渡す・結果を記録する）はどれも同じ。届け方だけが 2 つある。待っている実行があるとき（成果の宛先が反映先のタスク）は、その実行へ「入れてよい」を返す。待っている実行が無いとき（統合先から反映先へ上げる・委譲先のフローを通らない成果物）は、新しい依頼として出す。
- **同時に走らせる数の数え方**（D33）: オーナーの承認や回答を待っているだけの実行は、同時に走らせる数（スロットの数）に数えない。待っている実行は席の中身（作業ツリーなど）を持ったまま残るので、作業ツリーの数は、同時に走らせる数の上限を超えることがある（上限は、作業している実行だけに掛ける）。「サイクルは、どのタスクもオーナー待ちか完了になったら終わる」（§21.4）と同じ区別を使う（flywheel#695）。
- **作業ツリーの持ち主**: 委譲先のフローを通る委譲では、委譲先が作って片付ける。それ以外（スキルを直接呼ぶ形・指示文を直接渡す形）は、いまと同じく flywheel が払い出す。持ち主は委譲先の宣言ごとに選ぶ（§11 で保留にしていた `slot_owner` を足す）。
  - **S3a では足さなかった**: 持ち主を選ぶキー（`slot_owner`）は、区切り S3a で足していない。いまの 3 つの形は形と持ち主が 1 対 1 に決まっていて選ぶ余地が無いので、持ち主は委譲の形で決まるまま（`form: cli` は委譲先、`form: plugin`・`brief` は flywheel）。形と持ち主が食い違う委譲先が出てきたときに足す。
- **委譲先へ渡すもの**（D25）: 計画をまるごとは渡さない。計画の判断点は、計画を「課題に共通の部分（背景: 方針・論点の決定・完了したら見えるもの・やらないこと）」と「タスクごとの部分（何をするか・完了条件・やらないこと）」に分けて書く。core が、背景・指定のタスクの部分・ツリーのほかのタスクの題名の一覧（中身は渡さない）を LLM なしで組み立て、「ほかのタスクは範囲外」と明記して渡す。
- **委譲先が値で返すもの**: 自己レビューを実行したかなど、機械的に確かめられることは、委譲先が契約の結果に値で返し、core が LLM なしで確かめる。
- **汎用の道具としての線**: core が知るのは「タスクの成果は、課題の完了の承認の後に反映先に入る（まとめて入れる課題では、統合先に集まってから入る）」まで。ブランチ・PR・マージという開発に固有の語と操作は、委譲先の側に置く（D7・P5）。**2026-11-24 に改めた（D7 の改訂・D35）**: 「汎用の道具」であることはやめ、flywheel は開発に特化する。core が知る範囲（この線）は変えない。ブランチ・PR・マージの操作は、core の外の、組み込みのフロー（flywheel が自分で進めるフロー。flywheel のバイナリの一部）か、外の委譲先が持つ（[features/flow-port.md](features/flow-port.md)）。

**claude-harness の側で足りないもの**（2026-11-17 に `runtime/workflows/ticket.yaml` で確かめた）: 統合ブランチ宛ての PR を自分でマージして片付ける流れ・宛先の入力（`base`）・自分で作業ツリーを作って片付ける流れは、すでにある。足りないのは、Issue の無い入力（文面かファイル）・統合ブランチを作る口・既定ブランチ宛てを承認した中身つきでマージする口・統合ブランチから反映先へ上げるフロー・任意の PR を受けて反映先へ上げる口（D32）・反映先が動いていたら取り込んで、反映先へは入れずに新しい中身を返して待つ口（D31）。

**外側のフロー（検討）**: 課題の進め方（計画 → タスクのツリーを回す → 統合先でまとめて確かめる → 反映先へ上げる）を flywheel の汎用の YAML に書き、その 1 段として委譲先の子のフロー（`ticket.yaml` など）を呼ぶ形にする案がある（flywheel#266・#265）。承認の単位の設定も、ここに書く候補になる。段 2 に含めるかは、段 2 の範囲を決めるときに決める。

### 21.4 サイクルの進め方（D26・D34）

- サイクルは、走っているタスクが残っている間は終わらない。成果物がレビュー待ちになったらすぐ完了の検証をして答えを返し、統合先へ入ったらツリーの次のタスクを起動する。
- 終わるのは、どのタスクも「オーナー待ち」か「完了」になったとき、または費用の上限に達したとき。計画を承認した課題は、1 回のサイクルで「課題の完了の承認待ち」まで届く。
- 見直し前は「起動したらすぐ戻り、続きは次のサイクルで読む」形（`form: cli`）で、差し戻しを返す・「入れてよい」を返す・終わりを読むのそれぞれに 1 サイクルかかっていた。
- オーナーの承認や回答は、走っているサイクルがすぐ拾って委譲先へ届ける。走っているサイクルが無ければ、その操作がサイクルを 1 回始める。定期実行は持たない（D17 のまま）。常駐プロセスを必須にしない（P6）も変えない。サイクルは長くなるが、有限のプロセスのままである。
- **承認がサイクルを始める形**: 承認のコマンドは、サイクルを切り離して始め、すぐ戻る。UI の計画の承認でも始める（計画の承認は予算の上限の承認を含む）。UI の完了の承認は、見直し前と同じく反映を保留にする（D18 は変えない）。走っているサイクルは、回りの頭でストアを読み直して承認・回答を拾う（段の切れ目で読むのは止める指示）。
- **何もしないサイクルを回さない**: 始める前に、core が「進められるものがあるか」を LLM なしで数え、0 件なら始めない。
- **オーケストレーターが提案を持ってくる**（D34）: 対話のセッションのエージェントを「オーケストレーター」と呼ぶ。core に「いま進められること」を一覧する口を足す（承認待ち・回答待ち・未のフォローアップ・取り込める Issue・回した場合の費用の見込み）。オーケストレーターはそれを読み、横断的な知識と合わせて提案する。
  - 提案のきっかけは、対話を開いたときと、オーナーが尋ねたとき。定期的に起きて通知する形は、Tom で安定した後（§17 の段 4 の後）に検討する。
  - オーケストレーターは提案まで。サイクルを始めるのは、オーナーの承認か指示。
  - 先の要望（オーナー）: 取り込み元を走査して提案するだけでなく、ミッション（ゴール）を与えると、オーケストレーターが自分で課題の案を考えて提案する形にしたい。時期と形は決めていない。
- **個別操作は残す**: サイクルが進行役になった後も、1 件だけ委譲する・1 件だけ検証するなどの個別操作は残す（D11）。オーナーの指示でオーケストレーターが 1 件だけ進める場面と、不具合のときの手の補いに使う。新しい個別操作は足さない。

### 21.5 スーパーバイザー（SV）（D27）

想定外のことの上げ先を 3 段にする: core（通常の進行・LLM なし）→ SV → オーナー。見直し前は、想定外のことが起きると「同じことをやり直す」か「オーナーへ上げる」しか無かった。

**出番 1: その場の対処**

- **呼ぶきっかけ（core が機械的に検知）**: 段の失敗・不正な出力・完了の検証の「判断できない」・同じタスクが同じ場所で 2 回止まる・費用や時間の超過・委譲先の想定外の状態・子の問い。
- **やること**: 読み取りで調べる（成果物の差分と説明・検査の結果・実行の記録・過去の事例の記憶）。そのうえで、次の手の一覧から 1 つ選ぶ。選んだ手を実行するのは core（P2 のまま）。SV も、ほかの判断点と同じく読み取りの道具だけを持つ（コマンドを実行する道具を持たない。D5 の前提のまま）。

| 手 | 使う場面 |
|---|---|
| 1. 調べた結果を添えて、完了の検証をやり直す | 判断点が成果物の中身を読めない・成果物が見つからない・基準の食い違いの一部 |
| 2. 添え書きを付けて委譲先へ差し戻す | 品質ゲートの失敗など |
| 3. 同じ入力でやり直す（1 回まで） | 一時的な失敗 |
| 4. 委譲先に片付けを頼んで、起動し直す | 作業ツリーのぶつかり |
| 5. 残った条件をフォローアップへ回して、ほかの条件で判定する | 反映の後でしか満たせない条件（オーナーに聞かずに使ってよい。条件は消えずにフォローアップとして残り、課題の完了の承認のときにオーナーに見えるので、範囲の変更には当たらない） |
| 6. 計画を作り直す | 計画と完了条件が食い違っている |
| 7. このサイクルでは見送る | 外の出来事を待つしかない |
| 8. 調べた内容と推奨を付けて、オーナーへ上げる | 上のどれでも決められない |
| 9. 根拠を示して、子の問いに答える | 計画・Issue・記憶・コードに根拠がある問い |

- **子の問いに答えるときの歯止め**: 答えには根拠の場所（どの文書のどこか）を必ず付け、示せないときはオーナーへ上げる。範囲・完了条件・予算を変える問い、好みを問う問い、取り消せない操作に関わる問いは、必ずオーナーへ上げる。SV が答えた問いと答えは記録し、完了の承認のときにまとめて見せる。

- **J4 を外した旨（区切り S4b-3）**: 子の問いに答える判断点（J4）の新しい呼び出しと指示文 `j4.md` は外した。子の問いはスーパーバイザーが受ける。J4 の定数と、過去の J4 の実行の記録の読み取りは残し、過去の J4 の実行の記録がある課題は `flywheel show` で読める。
- **できないこと**: 承認・反映・取り下げ・予算の増額・範囲の変更。一覧に無い操作。成果物の手直し（直すのはタスクの進み方だけで、中身は委譲先へ差し戻す。検証する側と作る側を同じにしない）。
- **回数の上限**: 同じタスクの同じ止まり方に 2 回まで。進まなければオーナーへ上げる。

**区切り S4b-2 で実装した範囲（上の手の表との違い）**

### 21.7 並列と直列（D29）

- **課題の中のタスク**: ツリーの前提の線だけで並べる。線の無いタスクどうしは並列。
- **課題どうし**: 同じ場所を触る見込みを理由には直列にしない（記録した前提がある課題どうしは、いまと同じく前提が終わるまで始めない）。それぞれ別に（統合先を使う課題は別の統合先で）進み、反映先とのずれは委譲先が反映先の最新を取り込んで解く。機械的に解けないコンフリクトは、SV が委譲先へ差し戻す。委譲先は、完了の検証へ出す前にも反映先の最新を取り込む。完了の承認の後に中身が変わったときの扱いは §21.3（D31）。
- **タスク 1 個の課題どうし**: これも直列にしない。反映先へ入れられなくなった成果は、委譲先へ差し戻して追従させる（追従で中身が変わった後の承認の扱いは §21.3。D31）。
- **外すもの**: コンフリクトの予測の呼び出し・同時に進めてよいかの判断点（J9）・直列化グループ・コンフリクトの記録。
- **残すもの**: 記録した前提（依存。課題どうし・タスクどうし）と、同時に走らせる数の上限（スロットの数。オーナーの承認や回答を待っているだけの実行は数えない。D33）。
- **見直す条件**: 段 4 で、反映先へ上げるときの手直しの回数を SV の振り返りで見る。多ければ、課題を始める前に課題どうしを判断し「強い」組だけ直列にする形を足す（撤退条件は §19）。
- **根拠**: J9 は 105 回のうち 74 回（70%）が「並列でよい」。見直し前は、同じファイルを触る見込みの線でつながった課題の全体が 1 つの直列化グループになり、ほぼ 1 件ずつしか流れなかった（flywheel#725）。
