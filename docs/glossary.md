# flywheel 用語集

人が読む文章（画面・報告・Issue・仕様・指示文）で使う語をそろえるための一覧です。コードの識別子は「コードでの名前」の列に添えるだけにし、文章では左の列の語を使います。

- 「いつから」が **予定** の語は、設計の見直し（2026-11-17。flywheel#724・#725・#726）で決めた語で、実装はこれからです。それまでの仕様には、古い意味や古い言い方が残っています。
- 語を足す・変えるときは、この表を先に直します。

## 仕事の単位

| 語 | 意味 | 使わない言い方 | コードでの名前 | いつから |
|---|---|---|---|---|
| 課題 | 解きたいことの単位。取り込み元の 1 件（例: Issue 1 件）が課題 1 件になる（取り込み元に親子があれば、選んだ Issue が課題になり、その子孫は「取り込み元の子」として（取り込めるものの中で親をたどれる範囲を）記録する。子は、その課題のタスクの初期値として記録し、タスクにするかは計画を作る判断点〔J2〕が決める）。計画の承認と完了の承認は、既定ではこの単位で行う | 枠・案件・チケット | `challenge` | いまある（取り込み元の子の記録は S2b で入った） |
| タスク | 課題の中の、委譲して成果物が出る作業の単位。課題の中で、前提と派生の線でつながるツリーになる。単発の課題はタスク 1 個のツリーになる | （委譲する作業の意味での）課題 | `task`（表 `task`・タスクの前提の表 `task_dependency`） | ストアと計画は S2a で入った（委譲と完了の検証の対象をタスクにするのは S2a の範囲）。同時に走らせるのは S3b で入った |
| 成果物の種類 | タスクの実行にぶら下がる成果物の種類。画面では「プルリクエスト」「ブランチ」「コミット」と出す（知らない値は「成果物（値そのまま）」）。中身が開発のものは開発の語で出す（決定 2026-11-21 #963。画面に開発に固有の語を出さない決まりは外した。汎用にするかは設計の見直し #981 で決める） | 変更の提案・作業の枝・記録点（遠回しな言い換え） | `run_artifact.kind`（`pr`・`branch`・`commit`） | いまある（語は #963 で入った） |
| 見込み | 課題が使いうる額の見積もり。取りやめでないタスク（済みを含む）の枠（実装の枠とレビュー対応の枠）を足した合計。枠を決められないタスクがある課題の見込みは不明（`null`）。承認した上限とは別のもの（旧称: 課題の上限〔枠の合計〕） | 課題の上限（枠の合計の意味で） | `estimate`（API の `budget.estimate_usd`・core の `ChallengeBudget` の `*EstimateUSD`・見込みを数える関数 `sumTaskBudgets`） | S4c-1 |
| 上限 | オーナーが承認した、課題の費用の額。実装の枠とレビュー対応の枠を足した 1 つの額で、計画の承認で課題に記録する（理由つき）。上限の記録が無い課題は、見込みと同じ額として読む。見込みが上限を超えるタスクを足すには、オーナーの承認が要る | 枠の合計（見込みのこと） | `challenge.budget_limit_micros`・`budget_limit_reason`（API の `budget.limit_usd`・`limit_reason`） | S4c-1 |
| 足す依頼 | 計画の承認の後に、タスクを足すことの 1 件の記録。足したことの記録と、足されたタスクの印（`task.addition_id`）を兼ねる。出どころは、続きを決めるタスクが済んだ（`expand`。S4c-1）か、フォローアップを上げた（`followup`。S4c-2 から）。状態は、仕様待ち・オーナー待ち・足した・足さない・見送り・取り替え | 提案（タスクの状態に「提案」は無い） | 表 `task_addition`・core の `TaskAddition`（ID は `TA-<n>`） | S4c-1 |
| フォローアップ | 課題やタスクにぶら下がる 1 行の項目（確認ごと・軽い指摘・片付け・気づき）。状態は「未・済み・捨てた」だけで、分類・計画・承認を通さない。タスクに上げられるのはオーナー（とオーナーの指示を受けたオーケストレーター）だけ。課題に属さなくてもよい（サイクルの振り返りが出す改善の候補など）。未のフォローアップが残っていても、課題は完了にできる。済みにするのは core（タスクに上げたものが完了したとき）とオーナー・オーケストレーター、捨てるのはオーナーと指示を受けたオーケストレーター | 残り・残件 | `followup`（表 `followup`。表示は `F-<番号>`、状態は `open`・`done`・`dropped`） | S2b で入った範囲: 学びの判断点（J6）がフォローアップの行を書く（課題は起票しない。出どころは `learn` だけ）、一覧・済みにする・捨てる・課題に上げる（`followup list`・`done`・`drop`・`promote`）、課題の表示と状況への表示。上げるといつも新しい課題になる（開いている課題のタスクにするのは S3 から）。タスクにぶら下がるフォローアップ・スーパーバイザーの手・改修提案の判断点（J8）の出力の置き換えは S5 以降。core が済みにするきっかけは、S2b では上げた先の課題の完了で、上げた先のタスクの完了になるのは S3 から。過去の `origin = followup` の課題は移さない |
| 取り込み元の子 | オーナーが選んだ取り込み元の 1 件（Issue）の子孫を、親子の深さを問わず平らに記録したもの（たどるのは取り込めるものの中だけで、16 段まで）。課題にはせず、その課題のタスクの初期値として使う（タスクにするかは計画を作る判断点〔J2〕が決める）。取り込みの後に上流で足された子は自動では記録しない。課題を取り下げても記録は残り、`flywheel unbind` で消える | 子課題・子チケット | `source_child`（表 `source_child`。タスクとの対応は `task.source_key`） | S2b で入った（子ごとに別のタスクを走らせて子を渡すのは S3b で入った） |
| 取り込めるもの | 取り込み元の上流にある開いている Issue のうち、取り込みの方針に合い、まだ課題になっておらず、どの課題の取り込み元の子としても記録されていないもの。オーナーが選んで取り込む（`flywheel ingest <指定>...`）。新しいコマンドは足さず、`flywheel status` に出す（状況の API は `ingestable=true` が付いたときだけ上流を読む） | 取り込み候補・未取り込み | `ingestable`（`flywheel status` のキー） | S2b で入った |
| 前提 | あるタスクが終わらないと次のタスクを始められない、というつながり | 依存（文章では） | `challenge_dependency`（課題どうし）・`task_dependency`（タスクどうし） | いまある（課題どうし）・S2a で入った（タスクどうしの表。タスクの前提の線で並べて走らせるのは S3b で入った） |
| 派生 | あるタスクの作業から後で生まれたタスク。元のタスクにぶら下がる。次のタスクを止めないなら前提の線は引かない | — | — | 予定 |
| 統合先 | タスクの成果を集めておき、課題の完了でまとめて反映先へ入れる場所。開発では統合ブランチ。作るのも片付けるのも委譲先。まとめて反映先へ入れる機能の単位で用意するのが目安。統合先の作り方・成果の宛先は、委譲先の側（リポジトリごとの決まり）で決める。flywheel が持つのは「この課題は統合先を使うか」（計画の承認のときに決める）と、委譲先が返した統合先の識別の記録だけ | 置き場（データの保存場所の意味の「置き場」は別の語で、そのまま使う） | `challenge.uses_integration`・`challenge.integration_ref` | S3b で入った |

## 進め方

| 語 | 意味 | 使わない言い方 | コードでの名前 | いつから |
|---|---|---|---|---|
| サイクル | 進められるものを、回りを繰り返して全部進める 1 回の一括の操作。どのタスクも「オーナー待ち」か「完了」になるまで、走っているタスクを見ながら進める（回りの間隔は宣言の `cycle_poll_interval_sec`）。進められるものが 0 件なら始めない。終わった理由（`end_reason`）を記録する | 周・1 周 | `cycle` | いまある（進められるものが 0 件ならサイクルを始めない形は S2b、回りを繰り返して見張って進める形は S4a で入った） |
| 回り | サイクルの中で、進める段（反映・取り込み・分類・計画・委譲・完了の検証）を 1 回ずつ通すこと。サイクルは回りを、進められるものが無くなるまで繰り返す。段の中身は変えない。通した数は `rounds` | ラウンド・周（サイクルと混ぜない） | `rounds`（サイクルの記録の列） | いまある（S4a） |
| 判断点 | サイクルの中で、意味の判断のために LLM を呼ぶ箇所。文章では役割の言葉で呼び、番号は括弧で添える（例: 計画を作る判断点（J2）） | J2 が〜（番号だけ） | `judgment` | いまある |
| スーパーバイザー（SV） | サイクルを見て手を打つ判断点。出番は 2 つ。①想定外のこと（段の失敗・判断できない・同じ場所で 2 回止まる・費用の超過など）が起きたときに呼ばれ、読み取りで調べて、core が用意した手の一覧から次の手を選ぶ。子の問いには、計画・Issue・記憶・コードに根拠があれば根拠を示して答え、無ければオーナーへ上げる。②サイクルの終わりに振り返り、事例の記憶を書き、改善の候補をフォローアップとして出す（いまの学びの判断点〔J6〕と改修提案の判断点〔J8〕をまとめる）。承認・反映・取り下げ・予算の増額・範囲の変更と、成果物の手直しはしない。2 回目からは SV と略してよい | 見張り役 | — | 一部いまある（出番 1 のその場の対処は区切り S4b-2 で入った。子の問いは区切り S4b-3 で入った、振り返りは後続）。それ以外は予定 |
| 止まり方 | 保留を作る呼び出し元が、保留と一緒に渡す、スーパーバイザーを呼ぶきっかけの種類。保留の理由から導かない。9 つ（検証が判断できない・成果物が見つからない・委譲先の実行の失敗や中止・求める値を満たさないレビュー待ちの継続・差し戻しの上限・中身の確かめの失敗・判断点の連続失敗・統合先への受け取りの不成立・上流を読めない）で、止まり方ごとに選べる手が決まっている。止まり方を渡さない保留は、スーパーバイザーを呼ばず、はじめからオーナーへ上がる | きっかけ（止まり方の意味で） | `StopKind`・`hold.stop_kind` | いまある |
| 対処 | スーパーバイザーの判断 1 回と、core がその手を実行した結果の記録。結果は、実行した・失敗した・断った（実行の直前に状態が変わっていた、または判断の間にオーナーが回答した）の 3 つ。同じタスクの同じ止まり方には、手が見送り・上げる以外で実行した対処を 2 回まで。保留の閉じ方は、オーナーの回答と区別して `supervisor` と記録する | 処置 | `supervisor_action`・`SupervisorActionResult` | いまある |
| スーパーバイザー待ち | 保留のうち、スーパーバイザーが先に見る状態（`supervisor_state` が `pending`）。オーナーの回答待ちとしては出さない。スーパーバイザーが手を打って閉じれば処理済み、上げればオーナーの回答待ちになる。見送りは同じ保留に 3 サイクルまでで、超えるとオーナーへ上がる | — | `supervisor_state`・`SupervisorStatePending` | いまある |
| フロー | タスクの作業を進める手順の定義（YAML）。ステップの並びと、結果ごとの行き先を書く。どのフローで進めるかで、品質の水準が決まる。標準の実装のフロー（`ticket`）・簡略なフロー（`ticket-light`）・統合先を反映先へ上げるフロー（`reflect`）がある | ワークフロー（文章では）・パイプライン | `flow`（宣言の `operations[].flow`・`contract_run.flow`） | 予定（[フローの移植](features/flow-port.md) の S1） |
| ステップ | フローの中の 1 つの処理（YAML の `steps` の 1 件）。種類は、claude を呼ぶ・コマンドを実行する・待つ・振り分ける・作業ツリー・PR の 6 つ。サイクルの回りの中の「段」（反映・取り込み・分類・計画・委譲・完了の検証）とは別のもの | 段（フローの中の処理の意味で）・フェーズ（タスクの表示の区分 `phase` と混ざる） | `step`（表 `contract_run_step`） | 予定（同上） |
| 組み込みのフロー | flywheel が自分で進めるフロー。委譲先の宣言の 4 つ目の形（`flow`）。外の委譲先（スキルを呼ぶ形・外部コマンドの形・指示文だけの形）と違い、flywheel のバイナリがフローを進め、ステップの進み・費用・使ったモデルを flywheel の記録に持つ。ステップの中の指示文（スキル・エージェント）は、claude-harness のプラグインを使う | 内蔵ハーネス | `form: flow`・`internal/flow` | 予定（同上） |
| 簡略なフロー | 組み込みのフローの 1 つ（識別子 `ticket-light`）。標準の `ticket` から `analyze`・`e2e-route`・`e2e` のステップを外し、作業ブランチ名を決める `branch` のステップ（`feature/<鍵>-light`）を足し、`implement` と `fix` の指示文を簡略なフローの指示文に替えたもの。実装エージェント（`feature-implementer`）と Codex のレビューを使わず、モデルと effort も軽い値にしてある。文書だけの直しや小さな直しを速く安く進めるために、計画を作る判断点（J2）がタスクごとに選ぶ | 軽量フロー・ライトフロー | `ticket-light` | [フローの移植](features/flow-port.md) の S2 で入った |
| 軽いセルフレビュー | 簡略なフローの実装と直しのステップが行うセルフレビュー。プラグインのレビュアー 2 体（`code-reviewer`・`design-reviewer`）を並べて 1 回呼び、重さが中以上の指摘を直し、直した箇所だけを 1 回確かめ直す。懐疑者（`finding-verifier`・`design-deviation-verifier`）は呼ばない | — | — | [フローの移植](features/flow-port.md) の S2 で入った |
| effort | フローのステップ（`llm`）に渡す `claude --effort` の値。`low`・`medium`・`high`・`xhigh`・`max` の 5 つ。フローの定義の `efforts`（変数）に書いて固定し、委譲先の宣言では差し替えない。契約の `steps` の要素の欄 `effort` に記録する（無ければ `null`） | 努力量・思考量 | `efforts`・`steps[].effort` | [フローの移植](features/flow-port.md) の S2 で入った |
| 委譲 | タスクの作業を、委譲先に任せること | — | `delegate`・`contract` | いまある |
| 委譲先 | 委譲を受けて作業する道具（例: claude-harness）。flywheel から見て取り替えられる部品で、flywheel の本体は委譲先に固有の手順を持たない | 接続ツール・ハーネス（一般名として） | `connector` | いまある（設計書では「接続ツール」） |
| 対話のセッション | オーナーが Claude と直接話しているセッションそのもの。そこで動くエージェントは「オーケストレーター」と呼ぶ | 親（説明なしで） | — | いまある |
| オーケストレーター | 対話のセッションのエージェント。ワークスペースの横断的な知識を使い、状況を見て提案し、オーナーの承認・回答を記録し、オーナーの指示で課題を直接進める。予定の形では、core の「いま進められること」の一覧を読んで提案する。提案までが役目で、サイクルを始めるのはオーナーの承認か指示 | 親（説明なしで） | — | いまある（「いま進められること」を読む口〔`flywheel status`〕は S2b で入った） |
| エージェント（画面での呼び方） | 画面で、ワークスペース 1 つを指す呼び方。1 つのワークスペースにオーケストレーターは 1 つなので、オーナーは「どのエージェントと話すか」で切り替える。画面には「ワークスペース」の語を出さない。文書・設定・CLI では、置き場所を指すときに「ワークスペース」を使ってよい | ワークスペース（画面で） | `workspace` | いまある（画面は S2c で入った） |
| 実行（run） | 判断点の呼び出し 1 回、または委譲 1 回の記録。契約の形の委譲では、委譲 1 回の記録（`contract_run`）のほかに、委譲先へのコマンド 1 回ごとの記録（`run`）も持つ | — | `run`・`contract_run` | いまある |

## 人の操作と待ち

| 語 | 意味 | 使わない言い方 | コードでの名前 | いつから |
|---|---|---|---|---|
| オーナー | 承認と決定をする人 | 人間（画面と報告では） | — | いまある |
| 計画の承認 | 課題の計画（方針・問いと推奨・完了したら見えるもの・やらないこと・タスクのツリー）をオーナーが認めること。承認の後、ツリーの中のタスクは個別の承認なしで走る | — | `approval.kind = plan` | いまある（課題ごとに 1 回・問いと同時の形は S2a で入った） |
| 論点 | 計画を決めるために検討する観点（例: 「どこまでを 1 回で入れるか」）。計画を作る判断点（J2）が立て、計画の本文に書く。1 つの論点に、オーナーへの問いが 0 件以上ぶら下がる。オーナーに確かめる 1 件ずつは「問い」と呼ぶ | 問い（検討する観点の意味で） | 計画の出力の `topics` | S2a で入った（計画と同時に出す形）。見直し前の記録（課題の `issues`）の「論点」は、問い 1 件を指す |
| 問い | オーナーに確かめる 1 件。選択肢・推奨・例を付ける。出どころは 2 つ。①計画の論点から出る問い（計画と同時に出す。計画の承認の画面で論点ごとにまとめて見せる形は、S2c で入った。推奨のままでよければ、答えずに承認できる）。②作業の途中で委譲先やスーパーバイザーが上げる問い（保留になる）。画面と報告では「問い」と書く | 論点（オーナーに確かめる 1 件の意味で）・質問 | `topics` の `questions`（計画の論点から出る問い）・答えの記録 `plan_answer`・`hold` の問い（作業の途中の問い）。見直し前の記録は `issues` の 1 要素 | いまある（計画と同時に出す形は S2a で入った） |
| 対話の欄 | 画面の中の、選んだエージェントのオーケストレーターと文で話す欄。送った文のたびに実行エンジンが 1 回起動して返事を作る。承認・差し戻し・回答・取り下げ・予算の増額・フォローアップを文で伝えられ、記録には経路 `chat` と、欄に書いた文面そのものが残る。不可逆操作の承認は、宣言で選んだ種類だけ（既定は反映だけ） | チャット・ボット | 経路 `chat`（表 `chat_session`・`chat_message`。宣言 `chat_tools` ほか） | S4d で入った |
| 完了の承認 | 成果が課題の完了条件を満たしたとオーナーが認めること。反映の承認と 1 回の操作で行い、記録は分ける | 完了確認 | `approval.kind = completion` | いまある |
| 反映 | 成果を反映先へ入れること（開発では既定ブランチへのマージ）。実際のリリース（デプロイ）は含まない。実行するのは委譲先で、flywheel は承認した中身を伝えて結果を記録する。反映先に入るのは、承認した中身か、それに反映先の最新の取り込みと、検証を通ったコンフリクトの解消だけを足したもの | 本番反映（見直し前の文書と画面に残る語）・リリース・マージ（一般の語として） | `release` | いまある。委譲先が実行する形は、S3a で入った。コンフリクトの解消を承認し直さずに通す形は、S3c で入った |
| コンフリクト | 宛先（統合先か反映先）が動いたあとの取り込みで、同じ場所を別々に変えたために自動では混ぜられないこと。Git のマージのコンフリクトの意味でだけ使う語で、名前・鍵・ID の重なりや、ポートやファイルの取り合い、同時の書き込みの競合には使わない（それらは「重なる」「取り合う」「競合する」など、起きたことをそのまま書く）。決定 2026-11-21（#979）で、語を「衝突」からカタカナに替えた。試作（`docs/features/core-redesign/prototype/`）は固めた時点の写しで、適用済みのマイグレーションのコメントとともに、古い語「衝突」のまま残してある（書き換えない） | 衝突 | `conflict`（`conflict_fix_passed`〔作業ログの `action`〕・`conflict_fixes[]`〔API の値〕など。ストアの値と識別子は替えない） | いまある（語は #979 で替えた） |
| コンフリクトの解消の確かめ | 宛先（統合先か反映先）が動き、コンフリクトを直して中身が変わったとき、完了の検証の判断点（J5）が、直した差分だけを確かめること。通した中身の意図を保ったまま、宛先の変更と両立させているかを見る（全体を検証し直さない）。範囲を超えて振る舞いを足している・消しているときは「満たしていない」（統合先宛てはタスクを着手中へ戻して差し戻し、反映先宛ては検証と承認をやり直す）、入力の差分が上限を超えて切られたとき・差分を上流が返さなかった（読めない）ファイルがあるとき（どちらも、判断点が「満たした」と答えても core が読み替える）は「判断できない」（検証を最初からやり直す）になる。通したときは記録して、反映先宛ては承認し直さずに、統合先宛ては検証し直さずに、宛先へ入れる。その見分けと差分は core が上流のアダプタの比較の口から自分で読む | 衝突の解消の確かめ・再検証（一般の語として）・マージ後の確認 | `conflict_fix_passed`（作業ログの `action`） | いまある。S3c で入った。記録して課題の詳細で読めるところまでが実装で、対話の欄での知らせは S4 |
| 反映先 | 成果を最終的に入れる正式な場所。開発では既定ブランチ（例: main）。「本番」は、実際のリリース先を指す語として空けておく | 本番（反映先の意味で） | — | S3a で入った |
| 完了の検証 | 成果が完了条件を満たすかを判断点（J5）が確かめること | — | `verify` | いまある |
| 保留 | 課題か、課題の 1 つのタスクが、オーナーの回答か、オーケストレーターの作業を待って止まっていること。問いと回答と、止める範囲を記録に持つ。課題には保留を重ねて持てる（課題の状態は、開いている保留が 1 つでもあれば人間対応待ちで、最後の保留が閉じたら、その保留の戻り先へ戻る。重ねた保留の戻り先は着手中）。表示用の ID は `H-<番号>` | 人間対応待ち（説明なしで）・hold | `hold`・`hold.scope` | いまある（課題かタスクかを分けて重ねる形は S4c-3） |
| タスクを止める保留 | 止める範囲が 1 つのタスクの保留。開いている間は、そのタスクだけが進まず、同じ課題のほかのタスクは進む（止めたタスクを前提に持つタスクと、上げる依頼・課題の単位の確かめなど課題の単位の段は進まない）。開いている保留が、どれもタスクを止める保留のあいだ、課題は人間対応待ちのまま、ほかのタスクを進める。重ねられるのは、開いている保留の無い別のタスクを止める保留だけ | タスクの保留（説明なしで） | `hold.scope` = `task` | いまある（S4c-3） |
| 課題を止める保留 | 止める範囲が課題の全体の保留（`hold.scope` が NULL）。開いている間は、課題のどのタスクも進めない。課題の単位の確かめ・計画・足す依頼の問いなどで立つ。開いている間は、ほかの保留を重ねない（タスクを止める保留も重ねない）。過去の保留と、統合先を使わない課題（タスクが 1 個）の保留は、これとして読む | 課題の保留（説明なしで） | `hold.scope` が NULL | いまある（S4c-3） |
| 選択肢つきの問い | 問いの文に加えて、選択肢の並び（識別・見出し・説明）を持つ保留。選択肢の識別（`flywheel answer --option`）を選んで答えられ、選んだ見出しが回答の文になる。回答と同じ本人確認を通る。委譲先が選択肢を付けて返した問いに使う。画面のボタンでの回答は後の区切り | 選択式の質問・選ぶ問い | `hold` の `options`・`answer_option`・`option_required` | いまある（S4b-1） |
| 差し戻し | 計画か完了を認めず、理由を付けて戻すこと | reject | `approval.decision = rejected` | いまある |
| 取り下げ | 課題をやらないと決めて閉じること | — | `withdrawn` | いまある |
